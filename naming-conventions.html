نام‌ها فقط برچسب نیستند؛ اولین سندِ هر کد هستند. در این مقاله، snake_case، camelCase، PascalCase و kebab-case را با همه‌ی قواعد و استثناهایشان واکاوی می‌کنیم، برای هر زبان از پایتون و جاوا تا کاتلین و Rust راهنمای رسمی‌اش را مرور می‌کنیم و با یک چک‌لیست عملی، نام‌گذاری را از یک سلیقه‌ی شخصی به یک قرارداد تیمی تبدیل می‌کنیم.

بخش ۱چرا نام‌گذاری مهم است؟ قواعد عمومی مشترک همه‌ی زبان‌ها

در دنیای برنامه‌نویسی، نوشتن کد تنها به تولید خطوط دستور محدود نمی‌شود. یکی از جنبه‌های کلیدی موفقیت در این حوزه، انتخاب نام‌های مناسب برای متغیرها، توابع، کلاس‌ها و سایر عناصر کد است. تصور کنید کدی را بنویسید که نام‌های آن بی‌معنی و پراکنده باشند؛ این کد شبیه داستانی ناتمام است که شخصیت‌هایش هرگز معرفی نشده‌اند. خواننده — چه خودتان پس از چند ماه، و چه همکارانتان — با دشواری می‌تواند محتوای آن را درک کند.

نکته‌ای مهم: قواعد نام‌گذاری را نباید میان زبان‌های مختلف مخلوط کرد. مثلاً جاوا و جاوااسکریپت هر کدام سبک‌های خاص خودشان را دارند و ترکیب نادرست آن‌ها به کدی آشفته و غیرقابل نگهداری می‌انجامد. به‌طور کلی این قواعد به دو دسته تقسیم می‌شوند:

  • قواعد عمومی: در همه‌ی زبان‌ها مشترک‌اند — خوانایی نام‌ها، اجتناب از اعداد بی‌ربط، رعایت یکنواختی حروف بزرگ و کوچک و دوری از علائم خاص.
  • قواعد خاص: مختص هر زبان‌اند — مانند شیوه‌ی نام‌گذاری در پایتون (PEP 8) یا جاوا (Google Java Style Guide).

پیش از ورود به جزئیات، کل نقشه را ببینید. هر سبک فقط یک ترکیب از دو تصمیم است: چه حروفی؟ و چه جداکننده‌ای؟

بخش ۳snake_case: نام‌گذاری شبیه خزیدن مار

چرا به این سبک snake_case می‌گوییم؟ چون وقتی کلمات را با زیرخط (_) از هم جدا می‌کنید، شکلش شبیه ماری می‌شود که روی زمین می‌خزد! در این سبک همه‌ی حروف کوچک‌اند و کلمات فقط با زیرخط جدا می‌شوند — نه خط تیره، نه فاصله، نه هیچ نماد دیگری. 

# پایتون — خانه‌ی اصلی snake_case (PEP 8)
def get_user_profile(user_id: int) -> UserProfile:
    full_name = fetch_full_name(user_id)
    return UserProfile(user_id, full_name)

total_user_count             # ✓ حوزه‌ی معنایی روشن

۳.۱ قوانین snake_case

  1. حروف کوچک: همه‌ی حروف باید کوچک باشند؛ user_age درست و User_Age نادرست است.
  2. جداکننده‌ی منحصربه‌فرد: فقط زیرخط (_)؛ نه خط تیره، نه نماد دیگر. نمونه: calculate_total_price().
  3. اجتناب از کاراکترهای خاص: فقط حروف، اعداد (در صورت ضرورت) و زیرخط مجاز‌اند.
  4. شروع و پایان مناسب: از زیرخط اضافه در آغاز یا پایان خودداری کنید؛ user_id صحیح است، user_id_ نه.
  5. خوانایی و اختصار: نام‌ها معنادار و کوتاه باشند؛ total_user_count عالی است، tuc مبهم.

نکته: جایگاه snake_case در خانواده‌ی C در جاوا، جاوااسکریپت و TypeScript، snake_case نادر است و عمدتاً به ثابت‌ها محدود می‌شود — آن هم با حالت ویژه‌ای به نام SCREAMING_SNAKE_CASE که در بخش ۷ همین مقاله بررسی می‌شود. در عوض، زبان‌های پایتون، روبی و پایگاه‌های داده (نام ستون‌ها) به‌طور گسترده این سبک را رعایت می‌کنند.

بخش ۴camelCase: نام‌گذاری شبیه کوهان شتر

چرا camelCase؟ چون وقتی کلمات را پشت سر هم می‌نویسید و حرف اول هر کلمه (به‌جز کلمه‌ی اول) را بزرگ می‌کنید، شکل آن شبیه کوهان شتر می‌شود! مثلاً userName یا userId. این سبک شاید رایج‌ترین شیوه میان زبان‌های خانواده‌ی C باشد. 

// جاوا / کاتلین — متغیرها، Properties، متدها و توابع
String userName;
int itemCount;

void calculateTotalPrice() { ... }
boolean isOrderReady;

// جاوااسکریپت
const eventDispatcher = new Dispatcher();
function getParentComment(id) { return comments.get(id); }

۴.۱ قوانین camelCase

  • نام نباید با حرف بزرگ پایان یابد (مانند someVariablE).
  • حروف بزرگ فقط می‌توانند ابتدای کلمه‌ی دوم یا بعدی بیایند (مانند someVariable).
  • نقطه، زیرخط، خط تیره یا هیچ کاراکتر خاص دیگری در داخل کلمه مجاز نیست (مانند som.eVar-1able).

۴.۲ lowerCamelCase در برابر UpperCamelCase

برخی برنامه‌نویسان میان lowerCamelCase (حرف اول کوچک) و UpperCamelCase (حرف اول بزرگ) تمایز قائل می‌شوند، اما در عمل اغلب اولی را صرفاً camelCase و دومی را PascalCase می‌نامند. قانون سرانگشتی: مقادیر و توابع → lowerCamel؛ ساختارهای نوع → Pascal.

هشدار: camelCase در پایتون جرم است! در پایتون، userName از نظر سینتکسی مجاز است اما کاملاً غیراستاندارد است؛ PEP 8 صریحاً snake_case را برای توابع و متغیرها الزامی می‌داند. ترکیب دو سبک در یک پروژه‌ی پایتون، اولین نشانه‌ی بی‌نظمی و مشکل‌سازترین مورد در بازبینی کد است.

بخش ۵PascalCase: نام‌گذاری الهام‌گرفته از زبان پاسکال

این نام از زبان پاسکال (Pascal) گرفته شده که در دهه‌ی ۱۹۷۰ توسط Niklaus Wirth ساخته شد؛ یکی از نخستین زبان‌هایی که از این سبک برای شناساگرها استفاده کرد — هرچند خودِ زبان به حروف بزرگ و کوچک حساس نبود! PascalCase تقریباً قوانین camelCase را دنبال می‌کند، با این تفاوت که حرف اول کلمه هم بزرگ است (SomeVariable).

class OrderRepository { ... }
interface UserProfile { ... }
namespace MyApp.Services { ... }      // C#

// در پایتون فقط برای کلاس‌ها
class UserProfile:                    // ✓
    pass

user_profile = ...                    # متغیر/تابع: snake_case

۵.۱ چالش سرواژه‌ها (Acronyms)

یکی از مسائل کلیدی PascalCase، نحوه‌ی برخورد با مخفف‌هاست. فرض کنید با APIهای بانک مرکزی اروپا (ECB) کار می‌کنید؛ هر دو شکل زیر از نظر قواعد PascalCase صحیح‌اند: 

ECBRates        // با نام رسمی European Central Bank همخوان است — ترجیح برای برندها
EcbRates        // برای برخی افراد خواناتر است

نمونه‌ی دیگر، نگارش HTML در کلاس‌ها و متدهاست: بعضی کتابخانه‌ها آن را کامل بزرگ می‌نویسند (HTMLParser، HTMLRenderer) و بعضی دیگر شکل تعدیل‌شده (HtmlHelper، HtmlView).

بخش ۶kebab-case و نسخه‌ی فریادزن: scream-kebab

kebab-case سبکی است که در آن کلمات با خط تیره (-) جدا می‌شوند و همه‌ی حروف کوچک‌اند؛ به آن hyphen-case یا hyphenated هم می‌گویند. مثلاً برای تعداد آیتم‌های فروخته‌شده، item-qty. نام این سبک از شباهت خط تیره‌ها به سیخ کباب گرفته شده: درست مثل تکه‌های غذا که روی سیخ می‌نشینند، کلمات روی خط تیره «سیخ» می‌شوند. مبدعش مشخص نیست و احتمالاً به‌صورت ارگانیک در جوامع برنامه‌نویسی وب رشد کرده است.

۶.۱ scream-kebab-case: نسخه‌ی فریادزن

scream-kebab (یا uppercase kebab) نسخه‌ای است که همه‌ی حروف بزرگ‌اند؛ نامش از شباهت حروف بزرگ به «فریاد زدن» در شبکه‌های اجتماعی آمده است: 

THIS-IS-A-SCREAM-KEBAB        # فریاد!
this-is-not-a-scream-kebab    # فقط kebab-case معمولی

۶.۲ قوانین kebab-case

  1. حروف کوچک: همه‌ی حروف کوچک باشند؛ user-id مناسب است، User-Id و USER-ID نادرست (این قانون برای kebab استاندارد است؛ scream-kebab برعکس عمل می‌کند).
  2. جداکننده‌ی منحصربه‌فرد: فقط خط تیره؛ نه زیرخط. نمونه: calculate-total-price.
  3. بدون کاراکتر خاص و فاصله: user-full-name-2023 قابل قبول است، user@name نه.
  4. بدون خط تیره‌ی اضافه: user-id صحیح؛ -user-id و user--id نادرست.
  5. خوانایی و اختصار: total-user-count عالی است؛ tuc مبهم.

۶.۳ محدودیت‌های زبانی kebab-case

در بیشتر زبان‌ها (جاوا، پایتون، جاوااسکریپت) خط تیره به‌عنوان عملگر تفریق تفسیر می‌شود، پس برای شناساگرهای داخلی مجاز نیست. کاربرد اصلی‌اش در این زمینه‌هاست: CSS و HTML (کلاس‌ها و IDها)، URLها و مسیرها، نام فایل‌ها، و کلیدهای JSON سمت وب.

نکته: ابزارهای نگهبان یک سبک ثابت در کل پروژه داشته باشید و با ابزارهایی مثل Prettier یا Stylelint آن را به‌صورت خودکار بررسی و تضمین کنید — به‌خصوص در CSS که BEM یا هر متدولوژی دیگری را انتخاب کرده‌اید.

    def fetch_total_price(self, order_id) -> float:
        order = self._fetch_order(order_id)
        return sum(item.price for item in order.items)

    def GetTotal(self):                   # متد باید snake باشد
        pass
عمیق‌تر: ابزارهای خودکار پایتون black (قالب‌بندی)، isort (ترتیب import) و ruff/flake8 (lint) تضمین می‌کنند که قواعد نام‌گذاری و قالب‌بندی بدون بحث در تیم اجرا شوند. فعال‌کردن این سه در هر پروژه‌ی پایتون، هزینه‌ی بازبینی درباره‌ی «شکل کد» را تقریباً صفر می‌کند.

۱۰.۱ نکته‌ی حیاتی فرانت‌اند: زبان و پلتفرم، هر کدام قاعده‌ی خودشان

مهم‌ترین اشتباه در وب، تحمیل قاعده‌ی یک پلتفرم به پلتفرم دیگر است:

  • snake_case در نام متغیرهای جاوااسکریپت ← غیراستاندارد (مگر داده‌ی دریافتی از API).
  • camelCase در کلاس‌های CSS ← غیراستاندارد؛ CSS همیشه kebab یا BEM.
  • kebab-case در نام متغیرهای JS ← غیرممکن (خط تیره = عملگر تفریق).
  • نام فایل‌های کامپوننت React: هر دو شکل رایج است (UserProfile.tsx یا user-profile.tsx) — اما در یک پروژه فقط یکی.
آفت شماره ۲: سه سبک در یک پروژه‌ی وب فایل با kebab، کامپوننت با Pascal، متغیر داخلی با snake، و prop با camel — این چهارگانه خوانایی را نابود می‌کند. قاعده‌ی طلایی: فایل و CSS ← kebab؛ داخل کد ← camel/pascal؛ داده‌ی سرور ← قرارداد API.

۱۲.۳ مخفف‌ها و اعداد

  • مخفف ناشناخته ممنوع: ctx، mgr، cfg فقط در صورتی خوب‌اند که در پروژه همه‌جا یکسان و جاافتاده باشند؛ context و manager همیشه امن‌ترند.
  • جداکردن کلمات در مخفف: برای خوانایی، مخفف‌ها را مثل یک کلمه ببینید: xmlHttpRequest (نه XMLHTTPRequest).
  • اعداد بی‌ربط ممنوع: line2 فقط وقتی خوب است که واقعاً «خط دوم» باشد؛ شماره‌گذاری برای رفع مشکل دوباره‌نامیدن، تکنیک نیست بلکه پنهان‌کاری است.
  • حوزه (Scope) را در نام بیاورید: cartTotal بهتر از total است وقتی هم‌زمان invoiceTotal هم دارید.
نکته: نام‌ها را با جستجوی سریع بسنجید یک تمرین عملی: نام موردنظر را در پروژه جستجو کنید. اگر معنای مشابه با نام‌های متفاوت پیدا کردید (getUser، fetchUser، loadUser برای یک کار)، زنگ خطر است: یک مفهوم باید یک نام داشته باشد و هر نام فقط یک معنا.

بخش ۱۴جمع‌بندی، چک‌لیست و منابع

نام‌گذاری خوب نه سلیقه‌ی فردی است و نه تجمل؛ یک قرارداد تیمی است که با ابزار اجرا می‌شود. انتخاب سبک به زبان برنامه‌نویسی، نوع پروژه و توافق تیم بستگی دارد؛ همیشه با مطالعه‌ی راهنمای رسمی (مثل PEP 8 برای پایتون یا Google Java Style Guide) شروع کنید و در تیم خود یک سند راهنما تدوین کنید. این کار باعث کاهش خطا، افزایش سرعت توسعه و تبدیل کد به میراثی قابل استفاده و قابل فهم می‌شود.

۱۴.۱ چک‌لیست بازبینی نام‌گذاری

  1. در کل پروژه فقط یک سبک برای هر نقش استفاده شده (متغیر، کلاس، ثابت، فایل).
  2. هیچ نام مبهم تک‌حرفی یا شماره‌دارِ بی‌ربط (x1، data2) وجود ندارد.
  3. نام‌ها فعل/اسم درست دارند: توابع با فعل، متغیرها با اسم، بولین‌ها با is/has/can.
  4. مخفف‌های سرواژه‌ای در کل پروژه یکسان نوشته شده‌اند (ApiResponse یا APIResponse — فقط یکی).
  5. نام‌های منفی و دوگانه حذف شده‌اند؛ هر مفهوم دقیقاً یک نام دارد.
  6. راهنمای تیم مستند شده و lint/format در CI آن را اجرا می‌کند.
  7. نام فایل‌ها و کلاس‌های CSS با قرارداد پلتفرم (kebab) هماهنگ است.
  8. حوزه‌ی نام‌ها روشن است: cartTotal نه total وقتی رقیب دارد.
