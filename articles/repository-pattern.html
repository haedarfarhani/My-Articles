Repository یعنی یک مجموعه‌ی موجودیت‌های دامنه، به‌علاوه‌ی یک Interface که لایه‌ی بالاتر را از جزئیات ذخیره‌سازی دور نگه می‌دارد. در این راهنما تعریف، تفاوت دقیق با DAO و Data Mapper، پیاده‌سازی کامل با Java 21 روی JPA و JDBC، Unit of Work، تست واحد با JUnit 5، معایب صادقانه و ۲۰ سؤال مصاحبه را بررسی می‌کنیم.

بخش ۱مقدمه: وقتی SQL به همه‌جا سرایت می‌کند

در یک اپلیکیشن فروشگاهی، منطق ثبت سفارش باید سه چیز را بداند: موجودی کم است؟ تخفیف چقدر است؟ کاربر مسدود شده است؟ هیچ‌کدام از این‌ها ربطی به SQL ندارد.

اما اگر کد را بنویسیم بدون الگویی که مرز مشخص کند، Service شما Connection می‌سازد، PreparedStatement می‌نویسد، ردیف را به Entity نگاشت می‌کند و بعد منطق تخفیف را اعمال می‌کند. یعنی سیستم باید در حافظه بماند، اما کد مجبور است جزئیات ذخیره‌سازی را هم بداند. 

public void placeOrder(Order order) {
    Connection conn = DriverManager.getConnection(URL, USER, PASSWORD);   // ۱
    try {
        conn.setAutoCommit(false);

        // ۲) موجودی بررسی می‌شود — با یک Query ساده
        PreparedStatement stock = conn.prepareStatement(
                "SELECT quantity FROM inventory WHERE sku = ?");
        stock.setString(1, order.sku());
        ResultSet rs = stock.executeQuery();
        if (!rs.next() || rs.getInt(1) < order.quantity()) {
            throw new OutOfStockException(order.sku());
        }

        // ۳) تخفیف محاسبه می‌شود — منطق کسب‌وکار قاطی SQL
        BigDecimal discount = order.isVip()
                ? BigDecimal.valueOf(0.15)
                : BigDecimal.ZERO;
        order.applyDiscount(discount);

        // ۴) ذخیره‌سازی با نگاشت دستی ردیف به Entity
        PreparedStatement ps = conn.prepareStatement(
                "INSERT INTO orders (id, sku, qty, total) VALUES (?,?,?,?)");
        ps.setString(1, order.id().toString());
        ps.setString(2, order.sku());
        ps.setInt(3, order.quantity());
        ps.setBigDecimal(4, order.total());
        ps.executeUpdate();

        conn.commit();
    } catch (SQLException e) {
        conn.rollback();
        throw new StorageException(e);   // ۵) خطای دیتابیس به بیرون نشت می‌کند
    } finally {
        conn.close();
    }
}
ریشه‌ی مشکل پنج مسئولیت در یک متد. مهم‌تر از آن، تست این کد نیاز به دیتابیس‌ی واقعی دارد و قانون «تخفیف مشتریان VIP» به‌جای اینکه یک واحد مستقل باشد، بین SQL و محاسبه گیر کرده است. Repository Pattern با یک جمله حل می‌کند: دسترسی به مجموعه‌ی موجودیت‌ها را پشت یک Interface پنهان کن.

ایده‌ی Repository به دهه‌ی ۱۹۹۰s برمی‌گردد و از دنیای پایگاه‌داده‌ی شیءگرا (OODB) می‌آید. محققانی مثل Jim Fowler و David Martin در کتاب Patterns of Enterprise Application Architecture (۲۰۰۲) آن را به‌صورت رسمی در کنار Data Mapper و Unit of Work معرفی کردند.

بخش ۳Repository Pattern چیست؟ (تعریف دقیق)

تعریف رسمی Repository یک مجموعه‌ی موجودیت‌های دامنه است که دسترسی به آن‌ها را مانند یک کتابخانه در حافظه فراهم می‌کند. لایه‌ی بالاتر می‌تواند موجودیت را بخواند، اضافه کند یا حذف کند، بدون آنکه از وجود SQL، JPA یا حتی دیتابیس باخبر باشد. 
تعریف کلاسیک (Eric Evans، DDD):

  «یک مخزن، دسترسی به مجموعه‌ای از Aggregateهای هم‌نوع را فراهم می‌کند،
    با این تصور که این مجموعه یک مجموعه‌ی کامل است.»

سؤالاتی که Repository به آن‌ها پاسخ می‌دهد:
  ✗ «چطور کاربر را پیدا کنم؟»        → users.findById(id)
  ✗ «آیا این کاربر وجود دارد؟»       → users.existsByEmail(email)
  ✗ «چطور همه را ذخیره کنم؟»        → users.save(user)

سؤالاتی که Repository از آن‌ها فرار می‌کند:
  ✗ «چه جدولی؟»                     → نام جدول یک جزئیات پیاده‌سازی است
  ✗ «چه ستون‌هایی؟»                 → مدل دیتابیس یک جزئیات است
  ✗ «چه Indexی؟»                    → نگرانی زیرساخت است
  ✗ «تراکنش کجاست؟»                 → در Unit of Work یا Service

نکته‌ی مهم درباره‌ی جریان Repository:

  ۱) لایه‌ی Service هرگز نمی‌داند پیاده‌سازی مخزن JPA است یا JDBC یا In-Memory
  ۲) پیاده‌سازی مخزن هم هیچ قاعده‌ی کسب‌وکاری اعمال نمی‌کند
     → «کاربر مسدود نباید ذخیره شود» در Service/Domain است، نه در Repository
  ۳) مخزن فقط «انتقال داده» است، نه «انجام عملیات کسب‌وکار»

مثال عملی:
  users.save(user)         → ذخیره‌ی یک کاربر            (بدون قاعده)
  users.findActive()       → خواندن کاربران فعال        (بدون قاعده)
  userService.activate(u)  → فعال‌سازی کاربر             (قاعده‌ی کسب‌وکار)
مرز مخزن و سرویس متدی مثل saveOnlyVipUsers() یا updateAndNotify() از پس responsibilities مخزن خارج شده است. اگر مخزن شما شروع به «تصمیم‌گیری» کرد، دیگر مخزن نیست — یک سرویس است با نام اشتباه.

بخش ۹مثال عملی کامل: مدیریت کاربران

  • کاربر ثبت‌نام می‌کند؛ دامنه قاعده‌ی «ایمیل تکراری مجاز نیست» را در خود دارد.
  • سرویس ابتدا با existsByEmail بررسی می‌کند.
  • سپس مخزن را صدا می‌زند و مدل دامنه را ذخیره می‌کند.
  • پیاده‌سازی مخزن، مدل دامنه را به مدل دیتابیس نگاشت و ذخیره می‌کند.
  • در تست، به‌جای دیتابیس یک مخزن In-Memory استفاده می‌شود.
توزیع مسئولیت در یک سناریو:

  «ایمیل @test.com مجاز نیست»
      → User.create() در دامنه    (نه مخزن، نه سرویس)

  «ایمیل نباید تکراری باشد»
      → UserService.register()     (نیازمند جست‌وجو)

  «کاربر با این ایمیل در دیتابیس هست؟»
      → UserRepository.existsByEmail()

  «INSERT INTO users ...»
      → JpaUserRepositoryImpl      (جزئیات فنی)

نکته: هیچ‌کدام از قوانین دامنه در Repository نیست.
مسئله‌ی نیمه‌کاره اگر قاعده‌ی «ایمیل تکراری مجاز نیست» فقط در سرویس باشد و دو نقطه‌ی مختلف سرویس آن را صدا بزنند، ممکن است یکی فراموش شود. راه‌حل حرفه‌ای: قید یکتایی در دیتابیس + پیام خطای قابل‌فهم + رعایت در دامنه. دیتابیس آخرین خط دفاع است، نه اولین خط.

مدل دامنه

package com.app.user.domain.model;

import java.util.Objects;

/** Aggregate Root — ریشه‌ی تجمیع کاربر. هیچ وابستگی بیرونی ندارد. */
public final class User {

    private final Long id;
    private final Email email;
    private String fullName;
    private UserStatus status;
    private final java.time.Instant createdAt;

    private User(Long id, Email email, String fullName,
                 UserStatus status, java.time.Instant createdAt) {
        this.id = id;
        this.email = email;
        this.fullName = fullName;
        this.status = status;
        this.createdAt = createdAt;
    }

    /** قاعده‌ی کسب‌وکار در دامنه، نه در مخزن. */
    public static User register(Email email, String fullName) {
        if (fullName == null || fullName.trim().length() < 3) {
            throw new IllegalArgumentException("نام باید حداقل ۳ کاراکتر باشد");
        }
        if (email.domain().endsWith("@test.com")) {
            throw new IllegalArgumentException("دامنه‌ی آزمایشی مجاز نیست");
        }
        return new User(null, email, fullName.trim(),
                UserStatus.ACTIVE, java.time.Instant.now());
    }

    public void changeName(String newName) {
        if (status == UserStatus.DELETED) {
            throw new IllegalStateException("کاربر حذف‌شده قابل تغییر نیست");
        }
        if (newName == null || newName.trim().length() < 3) {
            throw new IllegalArgumentException("نام باید حداقل ۳ کاراکتر باشد");
        }
        this.fullName = newName.trim();
    }

    public void deactivate() {
        this.status = UserStatus.INACTIVE;
    }

    public Long id() { return id; }
    public Email email() { return email; }
    public String fullName() { return fullName; }
    public UserStatus status() { return status; }
    public java.time.Instant createdAt() { return createdAt; }

    @Override
    public boolean equals(Object o) {
        if (this == o) {
            return true;
        }
        if (!(o instanceof User other)) {
            return false;
        }
        return Objects.equals(id, other.id);
    }

    @Override
    public int hashCode() {
        return Objects.hash(id);
    }
}

/** Value Object — ایمیل با اعتبار و متد equals درست. */
public record Email(String value) {

            throw new IllegalArgumentException("ایمیل نامعتبر: " + value);

        value = value.toLowerCase();
    }

    /** بخشی که بعد از @ است — برای قاعده‌ی دامنه استفاده می‌شود. */
    public String domain() {
        return value.substring(value.indexOf('@'));

import com.app.user.domain.model.Email;
import com.app.user.domain.model.User;
import com.app.user.domain.repository.UserRepository;
import java.util.ArrayList;
import java.util.List;
import java.util.Optional;
import java.util.concurrent.atomic.AtomicLong;

/** مخزن حافظه‌ای برای تست — کمتر از ۳۰ خط */
public final class InMemoryUserRepository implements UserRepository {

    private final java.util.Map<Long, User> store = new java.util.HashMap<>();
    private final AtomicLong sequence = new AtomicLong();

    @Override
    public Optional<User> findById(Long id) {
        return Optional.ofNullable(store.get(id));
    }

    @Override
    public Optional<User> findByEmail(Email email) {
        return store.values().stream()
                .filter(u -> u.email().equals(email))
                .findFirst();
    }

    @Override
    public boolean existsByEmail(Email email) {
        return findByEmail(email).isPresent();
    }

    @Override
    public List<User> findActive() {
        return store.values().stream()
                .filter(u -> u.status() == UserStatus.ACTIVE)
                .toList();
    }

    @Override
    public User save(User user) {
        long id = user.id() != null ? user.id() : sequence.incrementAndGet();
        User saved = User.restore(id, user.email(), user.fullName(),
                user.status(), user.createdAt());
        store.put(id, saved);
        return saved;
    }

    @Override
    public void deleteById(Long id) {
        store.remove(id);
    }
}

مزیت عملی کل تست‌های بالا در کمتر از ۱۰۰ میلی‌ثانیه و بدون Testcontainer اجرا می‌شوند. برای تست‌های CI، این یعنی اجرای ده‌ها بار در روز بدون هزینه‌ی زیرساخت.

بخش ۲۱مثال در پروژه واقعی

۱) فروشگاه اینترنتی — مخزن سفارش

در فروشگاه‌های اینترنتی، مخزن OrderRepository فقط عملیات سفارش را انجام می‌دهد، نه عملیات کاربر و کالا. این تصمیم باعث می‌شود مرزهای تراکنش شفاف بماند: ثبت سفارش یک تراکنش است، اما خواندن کالا یک تراکنش دیگر. مخزن سفارش معمولاً متدهایی مثل findByCustomerIdAndStatus و findExpiredUnpaid دارد که هر دو به زبان کسب‌وکار نوشته شده‌اند.

۲) سامانه‌ی بانکی — مخزن حساب

در سامانه‌های بانکی، مخزن حساب بهینه‌سازی کوئری را خودش انجام می‌دهد. برای مثال وقتی می‌خواهید ۱۰۰۰ تراکنش آخر یک حساب را با یک کوئری بخوانید، متد مخزن findRecentTransactions(accountId, limit) یک کوئری LIMIT دارد. بدون مخزن، این منطق در سرویس تکرار می‌شد و کوئری‌های N+1 ایجاد می‌شد.

۳) اپ پیام‌رسان — مخزن گفت‌وگو

در اپ‌های چت، مخزن ConversationRepository مسئول بارگذاری گفت‌وگوهای کاربر با صفحه‌بندی است. به‌علاوه، یک پیاده‌سازی محلی (Room) و یک پیاده‌سازی راه دور (Firestore) برای همان پورت وجود دارد. با تعویض پورت، منطق سرویس بدون تغییر باقی می‌ماند.

۴) اپ سلامت — مخزن نسخه

در سیستم‌های پزشکی، هر رکورد نسخه تغییرناپذیر است؛ بنابراین مخزن به‌جای update متد append دارد که نسخه‌ی جدید را اضافه می‌کند. این مدل مخزن، تاریخچه‌ی کامل بیمار را تضمین می‌کند و Audit Trail به‌صورت خودکار ساخته می‌شود.

۵) پروژه‌های چندسکویی — یک پورت، چند پیاده‌سازی

در پروژه‌های Kotlin Multiplatform، یک پورت در ماژول shared تعریف می‌شود و هر پلتفرم پیاده‌سازی خودش را دارد: روی اندروید Room، روی iOS Core Data، و در تست In-Memory. منطق دامنه و تست‌ها یک بار نوشته و اجرا می‌شوند.

بخش ۲۳۲۰ سؤال مصاحبه

سطح Junior
سؤال ۱ — Repository Pattern چیست؟ الگوی دسترسی به داده که یک مجموعه‌ی موجودیت‌های دامنه را مانند یک کتابخانه در حافظه در اختیار لایه‌ی بالاتر قرار می‌دهد و جزئیات ذخیره‌سازی را پنهان می‌کند.
سؤال ۲ — تفاوت Repository و DAO چیست؟ DAO یک لایه‌ی فنی برای یک جدول است و به زبان دیتابیس صحبت می‌کند. Repository یک انتزاع دامنه‌محور است و به زبان کسب‌وکار صحبت می‌کند؛ DAO می‌داند جدول چیست، Repository نمی‌داند.
سؤال ۳ — چه کسی پیاده‌سازی مخزن را می‌نویسد؟ پیاده‌سازی در لایه‌ی زیرساخت (Infrastructure) نوشته می‌شود، ولی Interface در لایه‌ی دامنه قرار می‌گیرد. این ترتیب، قانون وابستگی معکوس را رعایت می‌کند.
سؤال ۴ — بهترین نام برای متدهای مخزن چیست؟ نام‌هایی که به زبان دامنه اشاره دارند. مثلاً findActiveCustomers() به‌جای selectByStatusEquals1().
سؤال ۵ — آیا مخزن می‌تواند منطق کسب‌وکار داشته باشد؟ نه. مخزن فقط داده را جابه‌جا می‌کند. اگر مخزن شما تصمیم بگیرد تخفیف بدهد یا کاربر را رد کند، دیگر مخزن نیست.
سؤال ۶ — تفاوت Repository و Active Record چیست؟ در Active Record، خود Entity متد save() دارد و هم داده را نگه می‌دارد و هم ذخیره می‌کند. در Repository، Entity فقط داده و قوانین دارد و ذخیره‌سازی جدا شده است.
سؤال ۷ — Data Mapper چه ربطی به Repository دارد؟ Data Mapper مسئله‌ی «تبدیل مدل دیتابیس و مدل دامنه» را حل می‌کند و Repository مسئله‌ی «دسترسی به مجموعه». مخزن تقریباً همیشه از یک mapper استفاده می‌کند. این دو مکمل‌اند.
سؤال ۸ — آیا باید برای هر جدول یک مخزن بسازیم؟ نه. برای هر Aggregate یک مخزن بسازید. اگر مخزن‌ها آینه‌ی جداول شوند، مزیت الگو از بین می‌رود.
سؤال ۹ — Unit of Work چیست؟ الگویی که تغییرات مدل در حافظه را ردیابی می‌کند و در پایان تراکنش، همه را یک‌جا ذخیره و commit می‌کند. در JPA همان EntityManager است.
سؤال ۱۰ — چرا متد save باید Entity برگرداند؟ چون شناسه‌ی تولیدشده (مثلاً کلید خودکار) فقط پس از ذخیره معلوم می‌شود. اگر void برگرداند، این شناسه را از دست می‌دهید.
سطح Mid
سؤال ۱۱ — چطور با N+1 در مخزن مقابله کنیم؟ با join در کوئری، یا متدهای مخزن که DTO برمی‌گردانند، یا fetch join در JPA. کلید ماجرا این است که رابطه‌ها در یک کوئری بارگذاری شوند.
سؤال ۱۲ — آیا Spring Data همان Repository Pattern است؟ نه دقیقاً. Spring Data یک پیاده‌سازی خودکار با نام Repository می‌سازد، ولی معمولاً یک لایه‌ی نازک روی ORM است. اگر می‌خواهید الگوی واقعی داشته باشید، باید یک Domain Repository جدا از CrudRepository تعریف کنید.
سؤال ۱۳ — مخزن چندمنبعی چیست؟ مخزنی که هم از دیتابیس و هم از کش یا سرویس بیرونی می‌خواند. مزیت: لایه‌ی سرویس متوجه نمی‌شود داده از کجا آمده. عیب: خطر ناسازگاری داده و پیچیدگی تراکنش.
سؤال ۱۴ — چطور خطای دیتابیس را به لایه‌ی بالاتر منتقل کنیم؟ در پیاده‌سازی مخزن، Exception فنی (SQLException) را بگیرید و به Exception دامنه (مثلاً UserNotFoundException) تبدیل کنید.
سؤال ۱۵ — مشکل Identity Map چیست؟ در برخی ORMها، اگر دو بار یک موجودیت را بخوانید، یک نمونه‌ی مشترک در حافظه برمی‌گردد. این باعث می‌شود تغییر یکی، روی دیگری هم اثر بگذارد. مخزن‌های مدرن معمولاً این رفتار را خاموش می‌کنند.
سؤال ۱۶ — Lazy Loading در مخزن چه خطری دارد؟ اگر رابطه‌ها تنبل بارگذاری شوند و نشست ORM بسته شود، با LazyInitializationException مواجه می‌شوید. راه‌حل: بارگذاری کامل در مرز مخزن، یا طراحی صریح مدیریت نشست.
سؤال ۱۷ — چطور مخزن را در تست جایگزین می‌کنید؟ با یک پیاده‌سازی In-Memory که همان Interface را پیاده می‌کند. تست‌ها به پورت وابسته‌اند نه به پیاده‌سازی، پس به‌طور خودکار با Fake کار می‌کنند.
سؤال ۱۸ — آیا مخزن باید Interface باشد؟ از نظر تست و انعطاف، بله. اما در پروژه‌های بسیار کوچک که فقط یک پیاده‌سازی می‌خواهند، می‌توان کلاس مشخص بدون Interface داشت.
سطح Senior
سؤال ۱۹ — مخزن در DDD چه نقشی دارد؟ مخزن مرز تراکنش Aggregate است. یک Aggregate فقط از طریق مخزنش به‌روزرسانی می‌شود و مخزن تضمین می‌کند که چند Aggregate با هم به‌صورت اتمیک ذخیره شوند. مخزن، API Aggregate در دامنه است — نه یک جزئیات فنی.
سؤال ۲۰ — بزرگ‌ترین خطر معماری در استفاده از مخزن چیست؟ اینکه مخزن‌ها به‌تدریج بیشترین منطق کسب‌وکار را جذب کنند و به سرویس تبدیل شوند. اگر متدی دارید که تصمیم می‌گیرد، در مخزن نیست. همچنین خطر دوم: ساختن یک مخزن برای هر جدول، که عملاً Repository را به یک لایه‌ی بی‌ارزش تبدیل می‌کند.

بخش ۲۴پرسش‌های متداول (FAQ)

پرسش‌های پرتکرار
۱) تفاوت Repository و DAO دقیقاً چیست؟ DAO یک ابزار فنی برای یک جدول است و به زبان دیتابیس حرف می‌زند. Repository یک انتزاع دامنه‌ای است و به زبان کسب‌وکار حرف می‌زند. مثال: DAO می‌گوید findByStatus(1)، Repository می‌گوید findActive().
۲) آیا Spring Data Repository با الگوی Repository فرق دارد؟ بله. Spring Data یک پیاده‌سازی خودکار است، نه الگو. اگر فقط از CrudRepository استفاده کنید، لایه‌ی دامنه به ساختار جدول‌ها وابسته می‌ماند. اگر یک Domain Repository بسازید که خودش به CrudRepository وابسته باشد، الگو را واقعاً پیاده کرده‌اید.
۳) آیا برای هر جدول یک مخزن لازم است؟ نه. برای هر Aggregate یک مخزن کافی است. گاهی حتی یک مخزن برای کل Aggregate کافی است، حتی اگر چند جدول داشته باشد.
۴) مخزن و Unit of Work چه تفاوتی دارند؟ مخزن درباره‌ی یک موجودیت و ذخیره‌سازی آن است. Unit of Work درباره‌ی تراکنش و همگام‌سازی تغییرات است. در JPA هر دو به‌شکل Repository و EntityManager ظاهر می‌شوند.
۵) آیا Repository Pattern باعث افت کارایی می‌شود؟ خودِ الگو خیر. اما اگر مدل دیتابیس و مدل دامنه را جدا کنید، نگاشت اضافه می‌شود. این هزینه معمولاً در برابر سود تست‌پذیری و تعویض‌پذیری کاملاً به‌صرفه است.
۶) چطور Exception دیتابیس را پنهان کنیم؟ در پیاده‌سازی مخزن، Exception فنی را بگیرید و به Exception دامنه تبدیل کنید. از این پس هیچ لایه‌ی بالاتری SQLException نمی‌بیند.
۷) آیا می‌توان مخزن را با حافظه‌ی نهان ترکیب کرد؟ بله. یک پیاده‌سازی CachingUserRepository بنویسید که مخزن اصلی را در اختیار دارد. لایه‌ی سرویس هیچ تغییری نمی‌بیند.
۸) آیا Repository Pattern برای اپ موبایل لازم است؟ اگر فقط Room دارید، Room خودش مخزن است و لایه‌ی اضافه لازم نیست. اما اگر می‌خواهید منطق دامنه از Room جدا باشد یا از حافظه‌ی نهان استفاده کنید، مخزن ارزشش را دارد.
۹) تفاوت Repository و Gateway چیست؟ مخزن برای داده‌ای است که مالکیتش با شماست و در دیتابیس خودتان ذخیره می‌شود. Gateway برای داده‌ی شخص ثالث که از سرویس بیرونی می‌آید. استفاده از نام درست، انتظارات تیم را روشن می‌کند.
۱۰) آیا مخزن باید تراکنش را مدیریت کند؟ خیر. تراکنش معمولاً در لایه‌ی Service یا Unit of Work مدیریت می‌شود. مخزن فقط در محدوده‌ی تراکنش فعال کار می‌کند.
۱۱) چطور متدهای پرس‌وجوی زیاد را مدیریت کنیم؟ به‌جای ده‌ها متد findBy...، از الگوی Specification استفاده کنید. این الگو معیارهای قابل ترکیب می‌سازد و پوشش پرس‌وجوها را بدون انفجار متدها بالا می‌برد.
۱۲) آیا Repository Pattern و DDD با هم سازگارند؟ بله، Repository یکی از الگوهای تاکتیکی اصلی DDD است. در DDD، مخزن فقط برای Aggregate Rootها تعریف می‌شود، نه برای هر موجودیت.
۱۳) چطور جلوی رشد بی‌رویه‌ی مخزن‌ها را بگیریم؟ فقط وقتی یک نیاز واقعی دامنه وجود دارد مخزن بسازید. اگر متدی در مخزن هیچ استفاده‌ای در لایه‌ی بالاتر ندارد، آن را حذف کنید.
۱۴) مخزن چه چیزی را نباید انجام دهد؟ نباید تصمیم بگیرد، اعلان بفرستد، یا کاربر را تأیید کند. این‌ها قواعد کسب‌وکار هستند و در دامنه یا سرویس زندگی می‌کنند.
۱۵) آیا مخزن در معماری میکروسرویس هم کاربرد دارد؟ بله، اما دقت کنید: در میکروسرویس، مرز سرویس خودش یک مخزن کلان است. مخزن درون سرویس، جزئیات محلی ذخیره‌سازی آن سرویس است و نباید از مرز سرویس عبور کند.

جمع‌بندی

Repository Pattern پلی است میان دنیای دامنه و دنیای ذخیره‌سازی. این پل را باید آگاهانه بسازید: اگر فقط یک لایه‌ی نازک روی ORM باشد، فایل اضافه ساخته‌اید بدون آنکه ارزشی بیفزایید.

معیار ساده‌ای برای ارزیابی وجود دارد: آیا می‌توانید کل لایه‌ی سرویس را بدون هیچ دیتابیسی تست کنید؟ اگر پاسخ بله است، الگو را درست پیاده کرده‌اید. اگر نه، هنوز یک لایه دارید اما آن لایه انتزاع نیست.

پیام پایانی سری ۱۴ مقاله‌ای این مقاله نهمین عضو سری «معماری‌های نرم‌افزاری» است. اکنون الگوهای رابط کاربری (MVC، MVP، MVVM، MVI) و الگوهای معماری (Clean، Onion، Hexagonal، Layered و Repository) را پوشش داده‌اید. در ادامه سری به حوزه‌ی مدل‌سازی دامنه (DDD) و معماری‌های سطح بالا (Feature-Based، Event-Driven، CQRS، Microservices) می‌رسیم.
