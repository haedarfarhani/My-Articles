بخش ۱روش عیب‌یابی سیستماتیک

فرق مهندس تازه‌کار و باتجربه در حادثه این است که باتجربه تصادفی لاگ نمی‌زند؛ یک مسیر دارد: اول دامنه‌ی مشکل را مشخص می‌کند (کی، کجا، چه خطایی)، بعد لایه‌به‌لایه از بیرون به داخل حرکت می‌کند و هر فرضیه را با داده تأیید یا رد می‌کند.

سه سؤال اول حادثه ۱) از کِی شروع شد؟ (Deploy، Cron، تغییر DNS) ۲) همه‌ی کاربران یا بعضی؟ (شبکه vs کد) ۳) دقیقاً چه خطایی؟ (پاسخ HTTP، Timeout، Connection Refused)
Prerequisites Logging و Monitoring و NGINX.

بخش ۲خطاهای HTTP: 502 و 504 و 413

خطامعنی واقعیرایج‌ترین علت
502 Bad GatewayProxy پاسخ نامعتبر یا رد اتصال از Backend گرفتBackend down، Port اشتباه، Crash حین درخواست
504 Gateway TimeoutBackend خیلی دیر جواب دادQuery کند، Deadlock، Pool تمام‌شده، timeout کم
413 Request Entity Too Largeبدنه‌ی درخواست بزرگ‌تر از حد مجازclient_max_body_size در NGINX و محدودیت فریم‌ورک
503 Service Unavailableهیچ Backend سالمی موجود نیستHealth Check شکست، all workers busy، Maintenance
# 502: آیا اصلاً Backend زنده است و روی پورت درست گوش می‌دهد؟
curl -v http://127.0.0.1:8080/healthz
ss -ltnp | grep 8080
systemctl status myapp

# 504: درخواست مستقیم به Backend را زمان‌بندی کنید تا مقصر پیدا شود
time curl -o /dev/null -s -w '%{http_code} %{time_total}\n' http://127.0.0.1:8080/api/slow

# 413: سقف حجم بدنه را در NGINX بالا ببرید (context: http/server/location)
# client_max_body_size 25m;
nginx -t && systemctl reload nginx
# تنظیمات متعارف Proxy در برابر این خطاها
server {
  listen 443 ssl;
  server_name example.com;

  client_max_body_size 25m;                 # درمان 413

  location / {
    proxy_pass http://app_upstream;
    proxy_connect_timeout 5s;               # اتصال به Backend
    proxy_send_timeout    60s;
    proxy_read_timeout    60s;              # درمان 504 ناشی از Backend کند
    proxy_next_upstream error timeout http_502 http_503 http_504;
    proxy_set_header Host              $host;
    proxy_set_header X-Real-IP         $remote_addr;
    proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
  }
}
نکته‌ی مهم خواندن error.log مهم‌تر از حدس زدن است: connect() failed یعنی Backend پاسخ نمی‌دهد (502)؛ upstream timed out یعنی زنده است ولی دیر (504). خودِ پیام، جهت حل را نشان می‌دهد.

بخش ۳منابع: CPU و RAM و Disk

علامتابزارچه نگاه کنید
CPU بالاhtop / topکاربر یا سیستم؟ load average نسبت به هسته‌ها
RAM بالاfree -hتفاوت available و free؛ swap در حال استفاده؟
Disk پرdf -h/var/log، Docker images، دیتابیس
کدام دایرکتوری؟du -sh /*مرتب‌سازی نزولی و Drill-down
I/O کندiostat -x 1%util و await بالای دیسک
# نگاه ۳۰ ثانیه‌ای به وضعیت سرور
uptime                       # load average در برابر تعداد هسته‌ها
free -h                      # available و swap
df -h                        # پر بودن فایل‌سیستم‌ها (خط Use% 100 یعنی خطر)
du -sh /var/log/* 2>/dev/null | sort -rh | head   # بزرگ‌ترین لاگ‌ها

# کدام فرآیند CPU/RAM را می‌خورد؟
htop    # یا: ps aux --sort=-%cpu | head ; ps aux --sort=-%mem | head

# پر شدن Disk به‌خاطر journald: سقف بگذارید
journalctl --disk-usage
sudo journalctl --vacuum-size=500M
Disk 100% = فاجعه وقتی دیسک پر می‌شود، دیتابیس Write نمی‌کند، لاگ‌ها می‌چسبند و سرویس‌ها یکی‌یکی می‌میرند. پاک‌سازی موقت: journalctl --vacuum-size، حذف imageهای بلااستفاده Docker (docker system prune) و چرخش لاگ با logrotate.
OOM Killer اگر فرآیند بی‌دلیل می‌میرد، شکار OOM شده: sudo dmesg -T | grep -i 'killed process'. درمان: افزایش RAM/سقف حافظه‌ی برنامه، محدودکردن فرآیندهای موازی، یا اضافه‌کردن swap اضطراری.

بخش ۴شبکه: ss و netstat و پورت‌ها

# چه سرویس‌هایی روی چه پورت‌هایی گوش می‌دهند؟
ss -ltnp                     # netstat مدرن؛ p یعنی PID/نام فرآیند
ss -ltnp | grep :443         # آیا NGINX روی HTTPS هست؟

# تعداد کانکشن‌ها به Backend و وضعیت‌ها
ss -tan | awk '{print $1}' | sort | uniq -c
ss -tan state established '( dport = :5432 )' | wc -l

# کانکشن‌های TIME_WAIT زیاد؟ (طبیعی ولی اگر خیلی زیاد شد keepalive فعال کنید)
ss -s                        # خلاصه‌ی آماری سوکت‌ها

# مسیر تا مقصد و دیوار کجاست؟
ping -c 3 db.internal
traceroute db.internal
curl -v telnet://127.0.0.1:8080   # یا nc -vz host port
علامتمحتمل‌ترین علتاقدام
Connection refusedسرویس down یا پورت اشتباهsystemctl status + ss -ltnp
Connection timed outFirewall یا مسیر شبکهufw status / Security Group
Too many open filesسقف فایل‌دسکریپتورulimit -n / LimitNOFILE در unit
Address already in useپورت درگیر سرویس دیگرss -ltnp | grep :PORT و حذف تضاد
Expected Behavior ss -ltnp باید NGINX را روی :443 و :80 و Backend را روی پورت داخلی (مثلاً 127.0.0.1:8080) نشان دهد. هر چیزی که گوش نمی‌دهد، همان است که 502 می‌سازد.

بخش ۵لاگ‌ها: journalctl و nginx

# لاگ یک سرویس systemd: زنده، از بوت قبلی، با زمان واقعی
journalctl -u myapp -f                       # دنبال‌کردن زنده
journalctl -u myapp --since "30 min ago"     # پنجره‌ی زمانی
journalctl -u myapp -b -1                    # از بوت قبلی (بعد از Crash)
journalctl -u myapp -p err --since today     # فقط خطاها
journalctl -u nginx -u myapp --since "10 min ago"  # چند سرویس با هم

# NGINX: خطاها را از access جدا ببینید
tail -f /var/log/nginx/error.log
tail -n 200 /var/log/nginx/error.log | grep -E 'upstream|timed out|failed'

# کدام IPها و کدام URLها بیشترین خطا را می‌گیرند؟
grep ' 502 ' /var/log/nginx/access.log | awk '{print $1}' | sort | uniq -c | sort -rn | head
grep ' 504 ' /var/log/nginx/access.log | awk '{print $7}' | sort | uniq -c | sort -rn | head
جریان کلاسیک 502 ۱) tail error.log → ۲) اگر connect() failed (111) → سرویس down است → ۳) journalctl -u myapp -n 100 → ۴) اگر برنامه Crash کرده، آخرین Exception قبل از خروج دلیل است → ۵) پس از اصلاح: systemctl restart myapp و تست با curl.

بخش ۶چک‌لیست نهایی

چک‌لیست حادثه (به ترتیب اجرا)
  • دامنه‌ی مشکل: چه کسی، از کِی، چه خطایی؟ یک curl -v واقعی بگیرید.
  • وضعیت سرویس: systemctl status همه‌ی سرویس‌های درگیر.
  • منابع: uptime، free -h، df -h، htop.
  • شبکه: ss -ltnp — پورت‌ها و فرآیندها، کانکشن‌های Backend.
  • لاگ‌ها: journalctl -u app --since + /var/log/nginx/error.log.
  • خطای HTTP: 502→Backend down، 504→Backend کند، 413→client_max_body_size.
  • پس از رفع: پاسخ 200 با curl، متریک‌ها و لاگ‌ها چند دقیقه تماشا؛ سپس Postmortem.
بعد از آتش‌نشانی مشکل را که حل کردید، علت ریشه‌ای را بنویسید و یک Monitoring/Alert برایش بسازید — Logging و Monitoring یعنی دفعه‌ی بعد قبل از کاربر بفهمید.

عیب‌یابی مهارت ابزارها نیست؛ مهارت پرسیدن سؤال درست است. این چک‌لیست را کنار داشته باشید و برای دیدن تصویر بزرگ، آکادمی معماری سرور و معماری Production بک‌اند را ببینید.
