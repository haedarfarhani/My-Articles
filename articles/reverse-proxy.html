Reverse Proxy؛ چرا هر معماری Production یک لایه‌ی میانی دارد؟

Reverse Proxy واسطه‌ای است که به‌جای کلاینت، از سمت سرور درخواست‌ها را می‌پذیرد و به Backend می‌رساند. همین یک تصمیم ساده، ده‌ها مسئولیت را از دوش برنامه برمی‌دارد: TLS Termination، Routing، Caching، Compression، Rate Limiting، Authentication، Centralized Logging و پنهان‌کردن زیرساخت.

بخش ۱مقدمه: مسئله‌ای که حل می‌کند

فرض کنید یک Backend دارید که روی پورت ۳۰۰۰ گوش می‌دهد و باید عمومی باشد. اگر آن را مستقیم در معرض اینترنت بگذارید، مجبورید درون برنامهٔ خود این‌ها را پیاده کنید:

نیازهزینه‌ی پیاده‌سازی درون برنامه
TLS و تمدید Certificateمدیریت کلید، Handshake و Restart برای تمدید
Rate Limitingشمارش در حافظه یا Redis و پیچیدگی توزیع‌شده
Static Filesکدگذاری سرو فایل و کش
Routing چند سرویسبازنویسی مجدد مسیرها در هر سرویس
Logging یکپارچههر سرویس لاگ خودش را دارد
راه‌حل یک لایه‌ی میانی این کارها را یک‌بار انجام می‌دهد و Backend فقط روی منطق کسب‌وکار تمرکز می‌کند. این لایه همان Reverse Proxy است.

بخش ۲Reverse Proxy چیست؟

تعریف رسمی Reverse Proxy سروری است که درخواست‌های ورودی از اینترنت را می‌پذیرد، بخشی از پردازش لبه را انجام می‌دهد و درخواست را به یک یا چند سرور داخلی می‌فرستد؛ پاسخ نیز از همان مسیر برمی‌گردد. از دید کلاینت، تنها Reverse Proxy وجود دارد و ساختار داخلی ناشناخته است.

بخش ۳Reverse Proxy در برابر Forward Proxy

ویژگیForward ProxyReverse Proxy
سمتکنار کلاینتکنار سرور
می‌داند چه کسیکلاینت‌ها راسرورها را
هدف اصلیکنترل خروجی و ناشناسی کلاینتورودی، امنیت، مقیاس و بهینه‌سازی
نمونهپروکسی سازمانی، VPN اخلاقیNGINX، Caddy، HAProxy، ALB
اشتباه رایج گاهی گفته می‌شود «Reverse Proxy برای پنهان‌شدن کلاینت است». نه — این کار Forward Proxy است. Reverse Proxy پشت سرور می‌نشیند و زیرساخت را پنهان می‌کند.

بخش ۵مسئولیت‌ها: TLS و امنیت

مسئولیتچرا در لبه؟
TLS TerminationCertificate و کلید در یک نقطه مدیریت می‌شود؛ Backendها ساده می‌مانند
Rate Limitingمحافظت یکپارچه از همه‌ی سرویس‌ها
Authentication / Authorizationتوکن در لبه بررسی و هدر داخلی ساخته می‌شود
IP Allowlist / Denylistمسدودسازی قبل از رسیدن به برنامه
Security HeadersHSTS، CSP و … یک‌بار اعمال می‌شوند
Hiding Infrastructureپورت، نسخه و ساختار داخلی لو نمی‌رود
مرز اعتماد هدرهای X-Forwarded-For و X-Real-IP فقط باید از Reverse Proxy مورد اعتماد پذیرفته شوند. در Backend با یک Middleware، منبع آن‌ها را محدود کنید.

بخش ۶مسئولیت‌ها: Routing و Caching

Path-based Routing

  /api/*        → http://backend-api:8080
  /auth/*       → http://auth-service:9000
  /static/*     → /var/www/static  (فایل ثابت)
  /ws           → WebSocket upgrade

Caching

  GET /products (public)  → Cache 10m
  GET /me     (private)   → بدون Cache
قابلیتاثرملاحظه
Routingیک ورودی، چند سرویسمسیرها را ثابت و مستند نگه دارید
Cachingکاهش Latency و بار Backendمحتوای خصوصی را کش نکنید
Compressionکاهش حجم متنروی محتوای نامتناسب اثر منفی دارد
Bufferingآزادکردن سریع Backendبرای Streaming باید خاموش شود

بخش ۷پیکربندی NGINX

upstream api {
    server 127.0.0.1:8080;
    server 127.0.0.1:8081;
    keepalive 32;
}

server {
    listen 443 ssl http2;
    server_name app.example.com;

    ssl_certificate     /etc/letsencrypt/live/app.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/app.example.com/privkey.pem;

    # فایل‌های ثابت مستقیم از دیسک
    location /static/ {
        root /var/www/app;
        expires 30d;
    }

    # API به Backend
    location /api/ {
        proxy_pass http://api;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
Expected Behavior یک درخواست به /api/orders باید با مسیر کامل به Backend برسد، در حالی که /static/app.js بدون دخالت Backend از دیسک سرو می‌شود.

بخش ۸پیکربندی Caddy

app.example.com {
    encode gzip zstd

    handle /static/* {
        root * /var/www/app
        file_server
    }

    handle /api/* {
        reverse_proxy 127.0.0.1:8080 127.0.0.1:8081 {
            lb_policy least_conn
            health_uri /health
            health_interval 10s
        }
    }

    # TLS خودکار و تمدید خودکار Certificate
}

بخش ۱۰مزایا، معایب و چه زمانی استفاده کنیم

AdvantagesDisadvantages
تمرکز TLS و امنیت در یک نقطهیک جزء جدید که باید مانیتور و به‌روز شود
پنهان‌کردن زیرساخت و کاهش سطح حملهپیکربندی اشتباه آن کل سرویس را قطع می‌کند
بهینه‌سازی متمرکز: Cache، Compression، Keep-Aliveنقطه‌ی شکست تک در نبود Redundancy
امکان Scaling و Routing بدون تغییر برنامهافزایش Latency کوچک به‌ازای یک Hop اضافه
When to Use هر سرویس وب عمومی که TLS، چند سرویس، فایل ثابت یا نیاز به Rate Limiting دارد.
When NOT to Use برای یک سرویس داخلی با یک Backend و بدون TLS، افزودن لایه فقط پیچیدگی است. همچنین اگر Latency داخلی بسیار حساس است، Hop اضافه را با معیار واقعی بسنجید.

بخش ۱۱جمع‌بندی و مقالات مرتبط

Reverse Proxy یک انتخاب معماری است، نه فقط یک ابزار. با آن، ده‌ها مسئولیت مشترک از برنامه‌ها بیرون می‌آید و در یک لایه‌ی قابل کنترل متمرکز می‌شود.
