بخش ۱مقدمه

Apache HTTP Server همچنان روی بخش بزرگی از سرورهای جهان اجرا می‌شود و مزیت اصلی‌اش ماژولار بودن است: هر قابلیت (Proxy، TLS، Rewrite، Auth، Compression) یک ماژول مستقل است. همین انعطاف آن را به یک انتخاب قدرتمند برای سناریوهای پیچیده تبدیل می‌کند.

در این مقاله یاد می‌گیرید معماری Apache، بلوک VirtualHost، ماژول‌های کلیدی و پیکربندی Production برای Reverse Proxy و TLS — به‌همراه مقایسه‌ی صادقانه با NGINX.

بخش ۴Virtual Host و دایرکتیوها

Listen 80

<VirtualHost *:80>
    ServerName example.com
    ServerAlias www.example.com
    DocumentRoot /var/www/app

    <Directory /var/www/app>
        Options -Indexes +FollowSymLinks
        AllowOverride All
        Require all granted
    </Directory>

    ErrorLog  ${APACHE_LOG_DIR}/example-error.log
    CustomLog ${APACHE_LOG_DIR}/example-access.log combined
</VirtualHost>
دایرکتیوکار
ServerNameدامنه‌ی اصلی این VirtualHost
DocumentRootریشه‌ی فایل‌ها
Directoryقواعد دسترسی سطح پوشه
AllowOverrideاجازه‌ی .htaccess (برای Performance روی None بگذارید)
ModPagespeedماژول بهینه‌سازی (اختیاری، در نسخه‌های جدید توسعه فعال نیست)
Production Note AllowOverride All در همه‌ی پوشه‌ها باعث جست‌وجوی مکرر فایل .htaccess و افت کارایی می‌شود. ترجیحاً پیکربندی را در VirtualHost نگه دارید.

بخش ۵Reverse Proxy و Load Balancing

Reverse Proxy در Apache با mod_proxy و ماژول‌های زیرمجموعه انجام می‌شود:

a2enmod proxy proxy_http proxy_balancer headers

<VirtualHost *:80>
    ServerName app.example.com
    ProxyPreserveHost On

    ProxyPass        / http://127.0.0.1:8080/
    ProxyPassReverse / http://127.0.0.1:8080/

    RequestHeader set X-Forwarded-Proto "http"
</VirtualHost>

# Load Balancing
<Proxy balancer://appcluster>
    BalancerMember http://127.0.0.1:8080 route=app1
    BalancerMember http://127.0.0.1:8081 route=app2
    ProxySet lbmethod=byrequests
</Proxy>
ProxyPass / balancer://appcluster/
دایرکتیوکار
ProxyPassنگاشت مسیر محلی به Backend
ProxyPassReverseبازنویسی هدرهای Location در پاسخ
ProxyPreserveHostحفظ دامنه‌ی اصلی برای Backend
lbmethodbyrequests، bytraffic، bybusyness
Common Mistake فراموش‌کردن ProxyPassReverse؛ نتیجه‌اش شکستن Redirectها در مرورگر است چون Backend آدرس داخلی خودش را در Location می‌گذارد.

بخش ۶TLS، Rewrite و Authentication

a2enmod ssl rewrite headers

<VirtualHost *:443>
    ServerName app.example.com
    SSLEngine on
    SSLCertificateFile      /etc/letsencrypt/live/app.example.com/fullchain.pem
    SSLCertificateKeyFile   /etc/letsencrypt/live/app.example.com/privkey.pem
    SSLProtocol -all +TLSv1.2 +TLSv1.3

    Header always set X-Content-Type-Options "nosniff"
    Header always set X-Frame-Options "SAMEORIGIN"
    Header always set Strict-Transport-Security "max-age=63072000"
</VirtualHost>

# ریدایرکت اجباری به HTTPS
RewriteEngine On
RewriteCond %{HTTPS} off
RewriteRule ^ https://%{HTTP_HOST}%{REQUEST_URI} [R=301,L]

# Basic Auth روی یک مسیر
<Location /admin>
    AuthType Basic
    AuthName "Restricted"
    AuthUserFile /etc/apache2/.htpasswd
    Require valid-user
</Location>
.htaccess و Performance اگر از .htaccess استفاده می‌کنید، دستورات بالا در هر درخواست خوانده می‌شوند. در Production آن‌ها را به VirtualHost منتقل کنید.

<Location "/downloads">

    SetEnv rate-limit 800
</Location>

بخش ۸مقایسه، مزایا و جمع‌بندی

موضوعApache HTTP ServerNGINX
مدل پردازشProcess/Thread با MPMEvent-driven با Worker
پیکربندی سطح پوشه.htaccessندارد
ماژول‌هابسیار غنی و بالغکمتر اما به‌اندازه‌ی کافی
مصرف حافظه در Concurrency بالابیشترکمتر
وضعیت بازاررو به کاهش در لبهغالب در لبه
AdvantagesDisadvantages
انعطاف ماژولی و بالغ‌بودنمصرف منابع بالاتر در بار زیاد
پیکربندی سطح پوشه و اکوسیستم بزرگ.htaccess می‌تواند کارایی را کم کند
مستندات فراوان و پایداری بالامدل Process/Thread برای C10K بهینه‌ نیست
When to Use وقتی به ماژول‌های خاص، .htaccess، میزبانی اشتراکی یا سازگاری با اپلیکیشن‌های قدیمی نیاز دارید.

Apache HTTP Server یک Web Server بالغ و ماژولار است. اگر پیکربندی Virtual Host، Proxy و TLS آن را درست ببندید، سرویسی پایدار خواهید داشت؛ فقط برای بار بسیار زیاد و Keep-Alive سنگین، NGINX معمولاً منابع کمتری مصرف می‌کند.
