بخش ۱مقدمه و اهداف یادگیری

در REST، قرارداد این است که سرور endpoint ها را طراحی می‌کند و کلاینت باید با همان مسیرها کنار بیاید. اگر صفحه‌ی محصول هم نام، هم قیمت، هم موجودی و هم نظرات می‌خواهد، کلاینت سه یا چهار درخواست جدا می‌فرستد و بخشی از پاسخ‌ها را دور می‌ریزد. GraphQL این معادله را برعکس می‌کند: سرور یک Schema منتشر می‌کند که همه‌ی فیلدها و ارتباطشان را اعلام می‌کند و کلاینت در هر درخواست دقیقاً می‌نویسد چه می‌خواهد.

اهداف یادگیری
  1. فهمیدن اینکه GraphQL دقیقاً کدام مشکل REST را حل می‌کند و کدام مشکلات را حل نمی‌کند.
  2. نوشتن Schema با Scalar، Object، Input، Enum، Interface و Union.
  3. تسلط بر سه عملیات اصلی: Query، Mutation و Subscription.
  4. نوشتن Resolver و فهمیدن ترتیب اجرای فیلدها در یک درخواست.
  5. تشخیص و رفع مشکل کلاسیک N+1 با DataLoader و batch کردن درخواست‌ها.
  6. صفحه‌بندی درست با Cursor به‌جای offset.
  7. طراحی دفاعی در برابر کوئری‌های مخرب: depth limit، cost analysis و غیرفعال کردن introspection در production.
  8. تصمیم‌گیری آگاهانه بین GraphQL و REST برای پروژه‌ی واقعی.
پیش‌نیاز

درک خوبی از HTTP (متدها، هدرها، status code)، JSON و مفاهیم پایه‌ی پایگاه‌داده لازم است. تجربه‌ی عملی با یک فریم‌ورک سمت سرور هم کمک بزرگی است، چون GraphQL جایگزین فریم‌ورک نیست؛ یک لایه روی آن است.

بخش ۲GraphQL چیست؟ و تاریخچه

تعریف

GraphQL یک زبان پرسش برای API و یک مشخصات باز است که به کلاینت اجازه می‌دهد شکل و محتوای پاسخ را خودش تعیین کند. سرور یک Schema تعریف می‌کند و یک نقطه‌ی ورودی (معمولاً /graphql) که Query، Mutation و Subscription را اجرا می‌کند و JSON برمی‌گرداند. ریشه‌ی نام آن از «گراف» می‌آید: داده یک گراف از موجودیت‌ها و رابطه‌های بین آن‌هاست، نه جدول‌های جدا و بی‌ارتباط.

یک تصحیح مهم: GraphQL یک زبان برنامه‌نویسی نیست

GraphQL زبان پرسش است، نه زبان برنامه‌نویسی و نه پایگاه‌داده. یعنی نمی‌توانید در آن حلقه بنویسید، یا کد دلخواه اجرا کنید. فقط می‌نویسید چه داده‌ای می‌خواهید؛ اجرای واقعی در Resolver های شما و در کد سمت سرور اتفاق می‌افتد. همین محدودیت امنیت را ساده‌تر می‌کند، چون کلاینت نمی‌تواند کد دلخواه روی سرور اجرا کند — اگر کوئری‌ها را محدود کنید.

نکته‌ی ظریف دیگر: GraphQL خودش مستقل از پروتکل انتقال است، ولی در عمل تقریباً همیشه روی HTTP اجرا می‌شود و برای داده‌ی بلادرنگ از WebSocket استفاده می‌کند.

بخش ۳معماری: از چند endpoint به یک نقطه

فرض کنید صفحه‌ی محصول به این داده نیاز دارد: نام و قیمت محصول، موجودی انبار، امتیاز، و سه نظر آخر. در REST این‌ها معمولاً سه endpoint جدا هستند و کلاینت سه درخواست می‌فرستد.

یک request در برابر سه request

# مسیر REST برای همان صفحه — سه رفت و برگشت، داده‌ی تکراری
GET /api/products/42
  ⇒ JSON با ۴۰ فیلد؛ صفحه فقط ۲ فیلد می‌خواهد
GET /api/inventory?productId=42
  ⇒ موجودی ۱ عدد
GET /api/reviews?productId=42&limit=3
  ⇒ سه نظر آخر
# مجموع: ۳ رفت‌وبرگشت، ۴۰+ فیلد ناخواسته، تکرار داده در هر پاسخ
# یک request، یک پاسخ، دقیقاً همان چیزی که خواسته شد
query ProductPage {
  product(id: "42") {
    name
    price
    inventory { available }
    reviews(first: 3) { nodes { rating body } }
  }
}
نکته‌ای که اغلب نادیده گرفته می‌شود Over-fetching (داده‌ی اضافه) مشکل REST است و Under-fetching (نبود داده‌ی لازم) هم مشکل REST است که به درخواست‌های اضافه و N+1 می‌انجامد. GraphQL هر دو را کم می‌کند چون پاسخ دقیقاً برابر انتخاب کلاینت است. اما این «دقیقاً» هزینه دارد: پیچیدگی به کلاینت منتقل می‌شود و سرور باید کوئری‌های پیچیده را ایمن و کند اجرا کند — بخش‌های ۱۲، ۱۳ و ۱۷ دقیقاً به همین می‌پردازند.

بخش ۴Schema و سیستم انواع

قلب GraphQL یک Schema است: یک سند machine-readable که می‌گوید چه نوع‌هایی وجود دارند، چه فیلدهایی دارند و چه ارتباطی بینشان است. Schema هم قرارداد است و هم مستند زنده؛ از روی آن هم کلاینت تایپ‌دار تولید می‌شود و هم مستندات. 

type Query {
  product(id: ID!): Product
  products(filter: ProductFilter, first: Int = 20): ProductConnection!
}

type Mutation {
  createProduct(input: CreateProductInput!): CreateProductPayload!
}

# تعریف یک نوع شیء‌ای
type Product {
  id: ID!                 # Non-null: همیشه مقدار دارد
  name: String!
  description: String     # Nullable: ممکن است null باشد
  price: Money!
  tags: [String!]!        # لیست غیرقابل null، اعضایش هم غیرقابل null
  reviews(first: Int, after: String): ReviewConnection!
}

# نوع ورودی برای آرگومان‌ها — همیشه input است، نه type
input CreateProductInput {
  name: String!
  price: Float!
  categoryId: ID
}

enum Category { ELECTRONICS, BOOK, CLOTHING }

بزرگ‌ترین تصمیم طراحی Schema این است که کدام فیلدها ! داشته باشند. قاعده‌ی عملی: فیلدی که همیشه وجود دارد را Non-null کنید. اگر Client روی یک فیلد Non-null خطا بگیرد، GraphQL کل پاسخ را null می‌کند و خطا را به بالا می‌فرستد. یعنی یک فیلد اشتباه می‌تواند کل صفحه را خالی کند. در مقابل، فیلد Nullable خطا را فقط در همان مسیر نشان می‌دهد و بقیه‌ی داده سالم می‌ماند.

قاعده‌ی طلایی طراحی Schema

Mutation را با یک نوع payload برمی‌گردانید، نه با Boolean. مثلاً createProduct(input): CreateProductPayload! که داخلش product، errors و clientMutationId است. این کار هم کلاینت را در توسعه‌ی آینده نجات می‌دهد، هم خطای اعتبارسنجی را به شکل ساخت‌یافته برمی‌گرداند.

بخش ۵Query و خواندن داده

هر عملیات خواندن در GraphQL با نام Query شروع می‌شود. Query می‌تواند هم‌زمان چند فیلد دلخواه از چند نوع داشته باشد؛ همین ویژگی است که نیاز به چند درخواست را حذف می‌کند. 

query GetProductPage {
  product(id: "42") {
    id
    name
    price { amount currency }
    inventory {
      available
      warehouse { city }
    }
    reviews(first: 3) {
      totalCount
      nodes { rating body author { name } }
    }
  }
}

آرگومان‌ها، alias و فیلدهای پویا

query {
  # آرگومان با مقدار ثابت
  cheap: products(filter: { maxPrice: 100 }, first: 5) { nodes { name } }

  # alias: اجازه می‌دهد یک فیلد را چند بار با آرگومان متفاوت صدا بزنید
  english: product(id: "42") { name }
  persian: product(id: "77") { name }

  # فیلد پویا: نام فیلد از کلاینت می‌آید (برای جدول‌های ادمین)
  settings(version: 3)
}
alias چه مشکلی را حل می‌کند؟

بدون alias نمی‌توانید product(id: "42") و product(id: "77") را در یک درخواست بیاورید، چون کلید JSON هر دو product می‌شود و یکی روی دیگری می‌نویسد. alias کلید پاسخ را عوض می‌کند و هر دو نتیجه جدا می‌مانند.

نکته‌ی RTL

در کد فارسی، نام فیلدها را انگلیسی نگه دارید و برای متن نمایشی از فیلد جدا استفاده کنید (مثلاً name و nameFa یا یک فیلد ترجمه‌شده با locale). همچنین در خروجی JSON مقادیر متنی را با dir="auto" رندر کنید تا نمایش عدد و متن درست باشد — جزئیات رندر در مقاله‌ی SOAP هم به همین شکل پوشش داده شده است.

بخش ۶Mutation و نوشتن داده

هر عملیات نوشتن یا تغییر وضعیت با نام Mutation تعریف می‌شود. تفاوت مهم با Query این است که فیلدهای یک Mutation در GraphQL به ترتیب سریالی اجرا می‌شوند — همین ویژگی برای عملیات نوشتن دقیقاً همان چیزی است که می‌خواهیم، ولی برای خواندن هدرد می‌رود. 

type Mutation {
  createProduct(input: CreateProductInput!): CreateProductPayload!
  updateProduct(id: ID!, input: UpdateProductInput!): Product!
  deleteProduct(id: ID!): DeleteResult!
}

type CreateProductPayload {
  product: Product        # اگر خطا نبود پر می‌شود
  errors: [UserError!]!   # خطاهای اعتبارسنجی و کسب‌وکار
}

type UserError {
  field: String
  message: String
  code: ErrorCode!
}

enum ErrorCode {
  DUPLICATE_SLUG
  INSUFFICIENT_PERMISSION
  INVALID_PRICE
  NOT_FOUND
}
mutation CreateProduct {
  createProduct(input: { name: "کیبورد مکانیکی", price: 2490000, categoryId: "7" }) {
    product { id name price { amount currency } }
    errors { field message code }
  }
}
{
  "data": {
    "createProduct": {
      "product": { "id": "904", "name": "کیبورد مکانیکی", "price": { "amount": 2490000, "currency": "IRR" } },
      "errors": []
    }
  }
}
قاعده‌ی طلایی: خطای اعتبارسنجی داخل payload

اگر ورودی نامعتبر باشد، Mutation یک payload با errors پر برمی‌گرداند و product می‌ماند null — ولی خود HTTP همچنان 200 است. این الگو به کلاینت اجازه می‌دهد خطای اعتبارسنجی را کنار فیلد مربوطه (مثلاً فرم «قیمت») نمایش دهد. خطاهای سطح سیستم (دیتابیس قطع است، توکن نامعتبر) باید exception باشند و در آرایه‌ی errors سطح بالا گزارش شوند.

دو آسیب‌پذیری که باید بشناسید
  • Mutation بدون احراز هویت: هر Mutation نوشتن را در resolver با requireUser(context) محافظت کنید. داشتن Schema به‌معنای داشتن دسترسی نیست.
  • Idempotency: در REST با هدر Idempotency-Key تکرار درخواست را کنترل می‌کردید. در GraphQL هیچ هدر استانداردی نیست؛ خودتان این کلید را به‌عنوان آرگومان Mutation بگیرید و در Redis نگه دارید تا ارسال دوباره‌ی یک فرم، رکورد تکراری نسازد.

بخش ۷Subscription و داده‌ی بلادرنگ

اگر REST با long-polling و WebSocket خام این کار را با کد زیاد انجام می‌دهد، GraphQL آن را به بخشی از قرارداد رسمی تبدیل کرده است: Subscription. کلاینت یک کوئری می‌فرستد و تا وقتی اتصال باز است، هر بار داده عوض شود پیام جدید دریافت می‌کند. 

type Subscription {
  # پیام‌های جدید یک گفت‌وگو
  messageAdded(conversationId: ID!): Message!

  # تغییر وضعیت سفارش
  orderStatusChanged(orderId: ID!): OrderStatus!
}
subscription OnMessageAdded {
  messageAdded(conversationId: "c-17") {
    id
    body
    createdAt
    author { name }
  }
}
نکته‌ی ظریف درباره‌ی WebSocket

در پروتکل GraphQL روی WebSocket (که آن را graphql-ws یا graphql-transport-ws می‌نامند)، کلاینت پیام connection_init می‌فرستد، سرور با connection_ack جواب می‌دهد، سپس کلاینت subscribe می‌فرستد و پیام‌های next جریان دارند. مزیت مهم این است که کلاینت می‌تواند چند subscription را روی یک اتصال باز نگه دارد؛ در WebSocket خام برای هر topic یک اتصال جدا لازم بود. 

// کلاینت → سرور
{ "type": "subscribe", "id": "1", "payload": { "query": "subscription { orderStatusChanged(orderId: \"905\") { status } }" } }

// سرور → کلاینت (هر بار وضعیت عوض شود)
{ "type": "next", "id": "1", "payload": { "data": { "orderStatusChanged": { "status": "SHIPPED" } } } }

// پایان جریان
{ "type": "complete", "id": "1" }
محدودیت‌هایی که باید بپذیرید
  • مقیاس‌پذیری: هر اتصال باز، یک منبع نگه‌داشته‌شده روی سرور است. برای میلیون‌ها کلاینت به معماری event-driven و ابزارهایی مثل Redis Pub/Sub یا Kafka نیاز دارید.
  • پیچیدگی پروکسی: بعضی پروکسی‌ها و load balancer ها WebSocket را قطع می‌کنند؛ heartbeat و reconnect با backoff را از اول پیاده کنید.
  • ترتیب و تکرار: دریافت دوباره‌ی یک event پس از reconnect طبیعی است؛ کلاینت باید state را دوباره بگیرد.

بخش ۸Resolver ها و جریان یک درخواست

Schema می‌گوید چه چیزی وجود دارد؛ Resolver می‌گوید از کجا بیاید. Resolver ها همان جایی هستند که منطق واقعی می‌نشیند و می‌توانند به دیتابیس، سرویس دیگر یا API بیرونی وصل شوند.

    products: (parent, { filter, first = 20 }, context) =>
      context.services.product.list({ filter, first })
  },

      if (existing) {
        return {
          product: null,
          errors: [{ field: "slug", message: "این نشانی قبلاً ثبت شده است", code: "DUPLICATE_SLUG" }]
        };
      }
      context.audit.log(user.id, "PRODUCT_CREATED", input.slug);
      const product = await context.services.product.create({ ...input, ownerId: user.id });
      context.pubsub.publish("PRODUCT_ADDED", { productAdded: product });
      return { product, errors: [] };
    }
  },

  // فیلدهای سطح پایه خودکار از داده‌ی والد خوانده می‌شوند؛ resolver لازم ندارند.
  // فقط برای فیلدهایی که محاسبه یا نیازمند داده‌ی بیرونی‌اند می‌نویسیم:
  Product: {
    reviews: (product, { first, after }, context) =>
      context.loaders.reviewByProduct(product.id, { first, after }),
    averageRating: (product, _args, context) =>
      context.loaders.ratingSummary(product.id).then(r => r.average)
  },

};

سه تکنیک که باید بدانید

این مهم‌ترین بخش عملی GraphQL است. چون فیلدهای یک Query موازی اجرا می‌شوند، یک مدل رابطه‌ای که با join کار می‌کند، در GraphQL به یک فاجعه‌ی کارایی تبدیل می‌شود.

چه اتفاقی می‌افتد؟

۱ درخواست از کلاینت می‌آید، ولی به سرور شما ۲۰۱ درخواست به دیتابیس می‌زند (1 + 20 + 20). با صفحه‌بندی و صفحه‌ی ۵۰۰ محصول، این عدد به ۱۰۰۱ می‌رسد. به این می‌گویند مشکل N+1 و نتیجه‌اش timeout یا فشار کامل روی دیتابیس است.

راه‌حل: batch کردن با DataLoader

import DataLoader from "dataloader";

// یک بار برای کل عمر درخواست ساخته می‌شود، نه برای هر فیلد
const loaders = {
  categoryById: new DataLoader(async (ids) => {
    // به‌جای ۱۰۰ کوئری، یک کوئری با IN(...)
    const rows = await db.category.findMany({ where: { id: { in: [...ids] } } });
    const byId = new Map(rows.map(r => [r.id, r]));
    return ids.map(id => byId.get(id) ?? null);
  }),

  reviewsByProduct: new DataLoader(async (productIds) => {
    const rows = await db.review.groupBy({
      by: ["productId"],
      where: { productId: { in: [...productIds] } },
      _count: { _all: true }
    });
    const map = new Map(rows.map(r => [r.productId, r._count._all]));
    return productIds.map(id => map.get(id) ?? 0);
  })
};

// در هر درخواست HTTP یک نمونه‌ی تازه می‌سازیم تا کش بین کاربران قاطی نشود
app.use((req, res, next) => {
  req.context.loaders = createLoaders();
  next();
});
سه قاعده‌ی حیاتی
  1. یک نمونه به‌ازای هر درخواست. اگر DataLoader را یک بار برای همیشه بسازید، داده‌ی کاربر الف در پاسخ کاربر ب دیده می‌شود — نشت داده، نه بهینه‌سازی.
  2. کلید فقط مقدار کلید باشد. نه کل آبجکت؛ کلید آبجکت همیشه تازه است و کش هیچ‌وقت hit نمی‌شود.
  3. Batch مجدد در Mutation. پس از تغییر، loaders.reviewsByProduct.clear(id) را صدا بزنید وگرنه پاسخ کش‌شده‌ی قدیمی برمی‌گردد.

بخش ۱۴صفحه‌بندی با Cursor

در GraphQL معمولاً offset را کنار می‌گذاریم. علت: با صفحه‌های شماره‌ی بالا و داده‌ی در حال تغییر، رکوردها جا می‌افتند یا تکرار می‌شوند و در دیتابیس OFFSET 100000 کوئری بسیار کندی می‌سازد. راه استاندارد، پیمایش مبتنی بر cursor است. 

type ProductConnection {
  edges: [ProductEdge!]!
  pageInfo: PageInfo!
  totalCount: Int!        # اختیاری: در صفحات بزرگ بهتر است حذف شود
}

type ProductEdge {
  cursor: String!          # توکن شفاف و base64 از کلید مرتب‌سازی
  node: Product!
}

type PageInfo {
  hasNextPage: Boolean!
  hasPreviousPage: Boolean!
  startCursor: String
  endCursor: String
}

type Query {
  products(first: Int, after: String, last: Int, before: String): ProductConnection!
}
// سمت سرور: cursor یعنی «آخرین مقداری که دیدم»، نه «شماره‌ی ردیف»
async function listProducts({ first = 20, after }, context) {
  const decoded = after ? decodeCursor(after) : null;
  const where = decoded ? { createdAt: { lt: decoded.createdAt } } : {};
  const rows = await db.product.findMany({
    where,
    orderBy: { createdAt: "desc" },
    take: first + 1                 // یکی بیشتر برای فهمیدن صفحه‌ی بعدی
  });

  const hasNextPage = rows.length > first;
  const nodes = hasNextPage ? rows.slice(0, first) : rows;

  return {
    nodes,
    edges: nodes.map(node => ({ node, cursor: encodeCursor(node) })),
    pageInfo: {
      hasNextPage,
      hasPreviousPage: Boolean(decoded),
      startCursor: nodes.length ? edges[0].cursor : null,
      endCursor: nodes.length ? edges[nodes.length - 1].cursor : null
    }
  };
}
چرا این الگو از Relay آمده و چرا همه تقلیدش می‌کنند؟

این شکل دقیقاً همان چیزی است که Relay در سال ۲۰۱۵ معرفی کرد (Connection/Edge/PageInfo). دلیل محبوبیت: کلاینت برای «صفحه‌ی بعد» به یک توکن نیاز دارد، نه به یک عدد؛ کلاینت می‌تواند هم‌زمان جلو و عقب برود و نتیجه با تغییر داده‌ها پایدار می‌ماند. اگر پروژه‌تان از این الگو استفاده کند، Apollo Client و Relay از قبل ابزارش را دارند.

مراقب totalCount باشید

totalCount روی جدول بزرگ باید COUNT(*) بزند که می‌تواند گران باشد. دو راه: نمایه‌ی مناسب یا تخمین (مثلاً از جدول شمارنده یا سرویس آمار). برای صفحاتی مثل «محصولات» معمولاً اصلاً لازم نیست — کلاینت فقط hasNextPage را می‌خواهد.

سرور GraphQL می‌تواند Schema خودش را به‌صورت داده برگرداند (به‌جای اینکه کسی فایل آن را بنویسد). به همین دلیل ابزارها می‌توانند Schema را بخوانند، کلاینت تولید کنند، مستندات بسازند و GraphiQL کار کند. در production معمولاً introspection را خاموش می‌کنند (بخش ۱۷)، ولی در محیط توسعه نگهش می‌دارند.

بخش ۱۶پیاده‌سازی با Apollo Server

سرور

import { ApolloServer } from "@apollo/server";
import { startStandaloneServer } from "@apollo/server/standalone";
import { ApolloServerPluginLandingPageLocalDefault } from "@apollo/server/plugin/landingPage/default";

const server = new ApolloServer({
  typeDefs,
  resolvers,
  plugins: [
    // در production: صفحه‌ی فرود به‌جای GraphiQL
    process.env.NODE_ENV === "production"
      ? ApolloServerPluginLandingPageLocalDefault({ embed: false })
      : undefined,
    { async requestDidStart() { return { async didResolveOperation() {
      console.log("GraphQL op:", request.operationName); } }; } }
  ],
  formatError: (formatted) => {
    // جزئیات داخلی هرگز به کلاینت نرود
    const code = formatted.extensions?.code ?? "INTERNAL_SERVER_ERROR";
    if (code === "INTERNAL_SERVER_ERROR") {
      log.error(formatted.message, formatted);
      return { message: "خطای داخلی سرور", extensions: { code } };
    }
    return formatted;
  }
});

const { url } = await startStandaloneServer(server, {
  listen: { port: 4000 },
  context: async ({ req }) => ({          // هر درخواست: context و loader تازه
    user: await authenticate(req.headers.authorization),
    loaders: createLoaders(),
    services: buildServices()
  })
});
console.log(`GraphQL ready at ${url}`);

آیا Schema-first یا code-first؟

Schema-first

  • اول SDL نوشته می‌شود، بعد resolver
  • خوانا، مستقل از زبان، مناسب تیم‌های بزرگ
  • هشدار: Schema و کد ممکن است از هم جدا بیفتند
VS

Code-first

  • اول کد و decoratorها، Schema از کد ساخته می‌شود
  • همیشه هماهنگ با کد، تایپ‌ها یکپارچه
  • هشدار: Schema دیگر سند مستقل و قابل استفاده‌ی چندزبانه نیست

برای پروژه‌های سازمانی و چندتیمی معمولاً schema-first انتخاب امن‌تری است، چون Schema به یک محصول تیمی تبدیل می‌شود که می‌توان روی آن کامنت، تست و review نوشت.

بخش ۱۷مزایا

✅ مزایا
  • پاسخ دقیقاً مطابق نیاز — نه over-fetching، نه under-fetching، و همه در یک رفت‌وبرگشت.
  • کاهش شدید تعداد درخواست‌ها — برای صفحات ترکیبی از ۵ فراخوانی به ۱ می‌رسید.
  • تیپ‌بودن در هر دو طرف — Schema منبع حقیقت است و کلاینت تایپ‌دار از آن ساخته می‌شود.
  • ساختار تیمی روشن — هر تیم Schema خودش را دارد و Federation آن‌ها را ترکیب می‌کند.
  • مستندسازی زنده — مستندات از خود Schema تولید می‌شود و هرگز کهنه نمی‌ماند.
  • یک نقطه‌ی ورود برای داده‌های چندمنبعی — کلاینت فقط یک میزبان را می‌شناسد.
  • قابلیت توسعه بدون تغییر سرور — فیلد جدید فقط با افزودن فیلد و resolver اضافه می‌شود.
  • کش نرمال‌شده سمت کلاینت — داده‌ی تکراری یک‌بار ذخیره و در صفحه‌های بعدی استفاده می‌شود.
  • سازگاری بین‌پلتفرمی — همه‌ی کلاینت‌ها (وب، موبایل، CLI) دقیقاً یک قرارداد می‌خوانند.
  • بهینه‌سازی تدریجی — می‌توانید یک endpoint موجود را پشت یک gateway اضافه کنید بدون آنکه کلاینت‌ها را بشکنید.

بخش ۱۸معایب

⚠️ معایب
  • مقیاس‌پذیری سخت‌تر — یک کوئری می‌تواند کل دیتابیس را درگیر کند؛ نیاز به limit و تحلیل هزینه دارید.
  • کش HTTP بی‌اثر — چون مسیر و متد ثابت است، باید کش اختصاصی بسازید.
  • هزینه‌ی سرور بیشتر — همان کوئری می‌تواند از ۱ مسیر به ۵۰ مسیر داده تبدیل شود.
  • نیاز به مهارت جدید — طراحی Schema، تفکر گرافی و ابزارهای اختصاصی یادگیری لازم دارد.
  • مشاهده‌پذیری کمتر — یک درخواست HTTP به ده‌ها query داخلی نگاشت می‌شود؛ APM باید per-field را نشان دهد.
  • منحنی یادگیری برای کلاینت — ذهنیت «فیلد را انتخاب کن» جایگزین «endpoint را صدا بزن» می‌شود.
  • ریسک امنیتی — کوئری عمیق، alias زیاد و introspection عمومی می‌توانند به کار زیاد روی سرور تبدیل شوند.
  • خطاهای موازی و پیچیده — داده‌ی جزئی درست کار می‌کند ولی مدیریت آن در کلاینت سخت‌تر است.
  • مناسب همه‌ی مصرف‌کننده‌ها نیست — وب‌سایت عمومی ساده با HTML ایستا بهتر از GraphQL است.
  • versioning سخت‌تر — تغییر Schema می‌تواند کلاینت‌های قدیمی را بشکند؛ deprecation لازم می‌شود.
قاعده‌ی صادقانه

GraphQL یک معامله است: کارایی کلاینت را به بهای بار سرور می‌خرد. در تیم‌هایی که می‌دانند دقیقاً چه داده‌ای لازم دارند و ابزار پایش دارند، این معامله می‌ارزد. در غیر این صورت REST با یک CDN ساده هم جواب می‌دهد — بخش‌های ۱۹ و ۲۰ مرز دقیق را می‌گویند.

الگوی ورود کم‌ریسک: GraphQL به‌عنوان لایه‌ی رویی

لازم نیست همه‌ی سرویس‌ها را بازنویسی کنید. یک GraphQL BFF جلوی سرویس‌های REST موجود بگذارید: کلاینت‌های جدید یک Schema می‌بینند و این لایه با REST داخلی حرف می‌زند. مهاجرت تدریجی، بازگشت‌پذیر و قابل اندازه‌گیری است.

🚫 چراغ‌های قرمز
  • هیچ DataLoader ای ندارید — بدون batch کردن، GraphQL فقط N+1 را مقیاس‌پذیر می‌کند.

  • آپلود فایل و استریم باینری — ابزارهای اختصاصی لازم دارد.
  • انتظار Status Code تمیز دارید — در GraphQL خطا داخل بدنه است، نه در هدر.
  • پایش per-field ندارید — نمی‌دانید کدام فیلد کند است یا کدام resolver خطا می‌دهد.

GraphQL و REST رقیب کامل نیستند

در عمل بهترین سیستم‌ها هر دو را دارند: gRPC برای ارتباط داخلی، GraphQL برای BFF کلاینت‌های محصول، و REST برای وب‌هوک‌ها و API عمومی. GraphQL بیشتر وقتی ارزش دارد که لایه‌ی تجمیع باشد، نه جایگزین کامل همه‌ی API ها.

پاسخ مصاحبه‌ای

«اگر از من بپرسند REST یا GraphQL: اول می‌پرسم مصرف‌کننده کیست و چند تیم دارد. برای API عمومی و پایتخت‌های ثابت، REST با کش CDN برنده است. برای محصولی با چند کلاینت که فیلدهای متفاوت می‌خواهند و داده از چند سرویس می‌آید، GraphQL ارزش دارد — به شرطی که DataLoader، depth limit و پایش per-field داشته باشیم. بدون آن سه‌تا، GraphQL فقط یک راه گران برای ساختن N+1 است.»

بخش ۲۲اشتباهات رایج و تست

هشت اشتباه رایج
  1. استفاده از Boolean برای نتیجه‌ی Mutation — به‌جای آن payload با فیلدهای واقعی برگردانید.
  2. نبود DataLoader — رایج‌ترین دلیل کندی GraphQL در پروژه‌های واقعی.
  3. اجازه دادن به کوئری عمیق — یک مسیر ۱۲ تودرتو می‌تواند صدها resolver را صدا بزند.
  4. فاش کردن خطای داخلی — پیام استثنا و مسیر فایل نباید به کلاینت برسد.
  5. پیام خطای فارسی بدون کد — کلاینت باید روی extensions.code تکیه کند، نه متن.
  6. مجوز دادن فقط در وب‌سایمکان — فیلد حساس باید خودش سطح دسترسی را بررسی کند.
  7. ساخت Schema بدون مکث برای داده‌ی ناقص — Non-null کردن فیلدی که همیشه پر نیست، کل پاسخ را null می‌کند.
  8. نادیده گرفتن هزینه‌ی کوئری — تحلیل هزینه روی هر فیلد، نه روی هر درخواست.

بخش ۲۳سؤالات مصاحبه

سطح پایه (Junior)

سؤال ۱ — GraphQL چیست و چه مشکلی را حل می‌کند؟

یک زبان پرسش برای API است که به کلاینت اجازه می‌دهد شکل و محتوای پاسخ را خودش تعیین کند. مشکل اصلی‌ای که حل می‌کند، over-fetching (دریافت فیلدهای اضافه) و under-fetching (نبود داده‌ی لازم و در نتیجه درخواست‌های اضافه) در الگوی endpoint محور REST است.

سؤال ۲ — تفاوت اصلی GraphQL با REST چیست؟

در REST سرور مسیرها را طراحی می‌کند و کلاینت باید با آن‌ها کنار بیاید؛ در GraphQL سرور یک Schema از همه‌ی فیلدها منتشر می‌کند و کلاینت کوئری خودش را می‌نویسد. نتیجه: در REST مسیر و متدها متنوع و کش‌پذیرند؛ در GraphQL یک مسیر ثابت است و کش HTTP ضعیف، ولی پاسخ دقیق و کارایی کلاینت بالا.

سؤال ۳ — Schema چیست؟

سند machine-readable که همه‌ی نوع‌ها، فیلدها، آرگومان‌ها و ارتباطشان را تعریف می‌کند. Schema هم‌زمان قرارداد، مستند و منبع تولید کد تایپ‌دار است. مهم‌تر اینکه یک type Query در آن اجباری است، وگرنه سرور هیچ عملیات خواندنی ندارد.

سؤال ۴ — Query، Mutation و Subscription چه تفاوتی دارند؟

Query فقط می‌خواند و فیلدهایش موازی اجرا می‌شوند. Mutation می‌نویسد و فیلدهایش سریال اجرا می‌شوند تا ترتیب عملیات حفظ شود. Subscription یک جریان بلادرنگ از طریق WebSocket باز می‌کند که تا وقتی اتصال باز است ادامه دارد.

سؤال ۵ — تفاوت Object و Input در چیست؟

هر دو مجموعه‌ی فیلد هستند، ولی Object برای خروجی است (فیلد output دارد و resolver می‌گیرد) و Input برای ورودی (فیلد input دارد، resolver ندارد و می‌تواند مقدار پیش‌فرض داشته باشد). جدا کردنشان مانع آن می‌شود که کلاینت بتواند فیلدی را که سرور باید محاسبه کند، مستقیم در ورودی بنویسد.

سؤال ۶ — alias چه کاری انجام می‌دهد؟

نام کلید پاسخ را عوض می‌کند. بدون آن نمی‌توانید یک فیلد را با آرگومان‌های متفاوت چند بار در یک کوئری صدا بزنید، چون همه با یک کلید در JSON برمی‌گردند و روی هم می‌نویسند. نمونه: cheap: products(maxPrice: 100) و expensive: products(minPrice: 1000).

سؤال ۷ — GraphQL روی چه متدهایی اجرا می‌شود؟

POST برای تقریباً همه‌ی کوئری‌ها و mutation ها، و GET فقط برای کوئری‌های خواندن کوتاه و بدون داده‌ی حساس. نکته‌ی مهم: متد HTTP دیگر نوع عملیات را مشخص نمی‌کند؛ خود کوئری با کلمه‌ی query، mutation یا subscription شروع می‌شود.

سؤال ۸ — خطای کوئری چه Status Code دارد؟

تقریباً همیشه 200 OK. خطا داخل آرایه‌ی errors با message، path، locations و extensions.code برمی‌گردد. اگر رسیدگی به خطا نکنید، کلاینت خطا را نمی‌بیند چون Status Code موفق است.

سؤال ۹ — اگر کوئری فیلدی را بخواهد که در Schema نیست چه می‌شود؟

در مرحله‌ی اعتبارسنجی رد می‌شود، پیش از آنکه resolver صدا زده شود. کلاینت یک پیام روشن با مسیر دقیق فیلد مشکل‌دار می‌گیرد. این نکته‌ی خوبی است: اعتبارسنجی نوع‌ها از کار کلاینت و سرور در زمان اجرا محافظت می‌کند.

سؤال ۱۰ — introspection چیست؟

قابلیتی که به کلاینت اجازه می‌دهد Schema زنده را به‌صورت داده بپرسد. به همین دلیل GraphiQL، تولید کد و مستندسازی خودکار ممکن است. در production معمولاً آن را غیرفعال می‌کنند تا مهاجم نقشه‌ی کامل داده را نبیند، و برای ابزارهای داخلی از حساب جدا با آن باز می‌کنند.

سطح متوسط (Mid)

سؤال ۱۱ — fragment چه سودی دارد؟

بخش‌های تکراری کوئری را یک‌بار تعریف و چند جا استفاده می‌کنید، و مخصوصاً روی Interface و Union فیلدهای مخصوص هر نوع را می‌نویسید. fragment روی interface Node در واقع الگویی است که باعث می‌شود کلاینت بتواند هر نوعی را که در پاسخ آمده با فیلدهای درست بخواند.

سؤال ۱۲ — چرا variables مهم‌اند؟

سه دلیل: نوع مقادیر در Schema اعتبارسنجی می‌شود؛ کوئری یک رشته‌ی ثابت و قابل cache و قابل ثبت در لاگ می‌ماند؛ و از تزریق کد جلوگیری می‌شود، چون داده هرگز داخل رشته‌ی کوئری چسبانده نمی‌شود. تقریباً قانون است: کوئری با متغیر، نه با چسباندن مقدار.

سؤال ۱۳ — مشکل N+1 چیست و چرا در GraphQL رایج است؟

کوئری‌ای که فیلدهای سطح اول خوب کار می‌کنند، ولی هر رکورد در نتیجه یک درخواست جدا به منبع داده می‌زند. در GraphQL رایج است چون فیلدهای یک Query موازی اجرا می‌شوند و درخت به‌راحتی عمیق می‌شود: ۲۰ محصول × ۲ رابطه = ۴۱ کوئری. نتیجه timeout یا فشار کامل روی دیتابیس.

سؤال ۱۴ — DataLoader چگونه کار می‌کند و چرا باید per-request باشد؟

کلیدها را در یک tick جمع می‌کند و به‌جای صدها کوئری، یک کوئری با IN(...) می‌زند و نتیجه را به‌ترتیب کلیدها برمی‌گرداند. باید در هر درخواست HTTP ساخته شود، چون کش آن برای مدت عمر درخواست است؛ اگر یک نمونه‌ی دائمی بسازید، داده‌ی یک کاربر در پاسخ کاربر دیگر leak می‌کند. کلید هم باید فقط مقدار کلید باشد، نه آبجکت.

سؤال ۱۵ — چرا صفحه‌بندی offset در GraphQL بد است؟

سه دلیل: با درج رکورد جدید، offset جابه‌جا می‌شود و رکورد تکراری یا جاافتاده می‌دهید؛ OFFSET 100000 در دیتابیس معمولاً کل جدول را می‌خواند؛ و نمی‌توان هم‌زمان به جلو و عقب رفت. به همین دلیل الگوی Connection با first/after و یک cursor شفاف استاندارد شد.

سؤال ۱۶ — Mutation باید خطا را چطور برگرداند؟

با یک نوع payload که هم نتیجه و هم فیلد errors دارد. خطاهای اعتبارسنجی و کسب‌وکار داخل payload، خطاهای زیرساختی به‌صورت exception. در پاسخ هم extensions.code بگذارید تا کلاینت روی متن پیام تکیه نکند، چون متن ممکن است تغییر یا محلی‌سازی شود.

سؤال ۱۷ — چطور جلوی کوئری مخرب را می‌گیرید؟

سه لایه: depth limit روی عمق درخت، cost analysis روی تعداد فیلدها (چون تعداد alias و fragment می‌تواند یک فیلد ساده را هزار بار اجرا کند)، و timeout و محدودیت نرخ. اگر این سه را نداشته باشید، یک کوئری عمیق می‌تواند کل سرویس را برای بقیه از کار بیندازد.

سؤال ۱۸ — چطور یک GraphQL را پایش می‌کنید؟

در سطح درخواست: نرخ خطا، زمان پاسخ و نرخ cache hit در Apollo Client. در سطح فیلد: یک plugin که زمان هر resolver را ثبت کند و فیلدهای کند را در داشبورد نشان دهد. بدون این سطح دوم، دیدن یک کوئری ۳ ثانیه‌ای که از هزار alias ساخته شده ممکن نیست.

سطح پیشرفته (Senior)

سؤال ۱۹ — در سازمانی با ۳۰ تیم و API های REST موجود، چگونه GraphQL را معرفی می‌کنید؟

هرگز با مهاجرت همه‌جا شروع نمی‌کنم. ۱) یک GraphQL BFF جلوی چند سرویس پرترافیک می‌گذارم که فقط خواندن را انجام می‌دهد؛ ریسک کم است. ۲) Schema را به‌عنوان محصول تیمی معرفی می‌کنم: مالکیت مشخص، بازبینی، و تست اسنپ‌شات در CI. ۳) استانداردها را از روز اول می‌گذارم: نام‌گذاری، صفحه‌بندی Connection، کد خطا، و depth limit در همه‌ی سرویس‌ها. ۴) ابزار مشاهده‌پذیری per-field را قبل از اولین ترافیک واقعی راه می‌اندازم. ۵) به‌جای مهاجرت اجباری، مسیر تدریجی باز می‌گذارم و با معیار عددی (تعداد رفت‌وبرگشت، زمان بارگذاری، نرخ خطا) تصمیم را ادامه می‌دهم. مهم‌ترین تصمیم این است که GraphQL را در جایی بگذاریم که واقعاً ارزش دارد: جایی که چند کلاینت، داده‌ی چندمنبعی و نیازهای متنوع دارند.

سؤال ۲۰ — GraphQL Federation چیست و چه زمانی واقعاً لازم می‌شود؟

وقتی چند تیم هر کدام Schema خودش را دارند، Federation آن‌ها را در یک Graph واحد ترکیب می‌کند: هر تیم یک subgraph دارد و یک router کوئری را می‌گیرد، به هر subgraph جداگانه می‌فرستد و نتیجه را نرمال می‌کند. مزیت اصلی، مالکیت مستقل تیم‌ها با یک قرارداد مشترک است. هشدار: Federation سربار معماری واقعی دارد — نسخه‌بندی subgraph، تشخیص نسخه ناسازگار، و پیچیدگی عیب‌یابی. اگر فقط یک تیم دارید، این پیچیدگی را نپردازید.

بخش ۲۴پرسش‌های متداول (FAQ)

آیا GraphQL منسوخ شده است؟

خیر. در ۲۰۱۵ به‌عنوان مشخصات باز منتشر شد و امروز GitHub، Shopify، Yelp و ده‌ها شرکت بزرگ از آن استفاده می‌کنند. GraphQL در کنار REST و gRPC جای ثابتی دارد؛ فقط دیگر «راه‌حل همه‌ی مسائل» نیست و انتخاب آن آگاهانه و بر اساس نیاز است.

آیا GraphQL بهتر از REST است؟

به‌طور مطلق هیچ‌کدام بهتر نیست. GraphQL وقتی بهتر است که کلاینت‌ها نیازهای متنوع دارند و داده از چند منبع می‌آید؛ REST وقتی بهتر است که ساده‌گی، کش CDN و پذیرش عمومی مهم است. پرسش درست «کدام بهتر است؟» نیست؛ «کدام هزینه‌ی کمتری برای این کاربرد دارد؟» است.

آیا GraphQL جایگزین REST می‌شود؟

معمولاً نه. در معماری‌های بالغ هر سه با هم هستند: gRPC برای ارتباط داخلی بین سرویس‌ها، GraphQL به‌عنوان لایه‌ی تجمیع برای کلاینت‌های محصول، و REST برای وب‌هوک‌ها و API های عمومی. GraphQL جای خود را در لایه‌ی BFF پیدا کرده است.

برای یک پروژه‌ی کوچک مناسب است؟

اغلب نه. اگر یک اپ کوچک با دو یا سه صفحه دارید، REST با JSON کامل پاسخ‌گو و سریع‌تر است. هزینه‌ی اولیه‌ی GraphQL (Schema، resolver، DataLoader، ابزار پایش) در مقیاس کوچک توجیه ندارد.

مستندات GraphQL را چطور نگه دارم؟

Schema خودش مستند زنده است: کامنت‌ها با triple-quote کنار هر نوع و فیلد، مستندات GraphiQL و مستندات تولیدشده را پر می‌کنند. این‌ها را در مخزن نسخه‌بندی کنید و تغییرات Schema را در CI با تست اسنپ‌شات بسنجید تا کامنت‌ها هرگز از کد عقب نیفتند.

GraphQL چطور کش می‌شود؟

کش HTTP معمولی تقریباً بی‌فایده است چون همه‌ی کوئری‌ها به یک مسیر با متد POST می‌روند. راه‌حل‌های عملی: کش نرمال‌شده‌ی سمت کلاینت (Apollo Client)، persisted queries با کلید هش، کش اختصاصی در Gateway بر اساس متن کوئری و variables، و CDN با هدرهای سفارشی برای کوئری‌های بدون mutation.

آیا introspection را در production خاموش کنم؟

بله، معمولاً. introspection نقشه‌ی کامل مدل داده را به هر کسی می‌دهد و برای حمله‌ی DoS با کوئری‌های تودرتو هم مفید است. اما ابزارهای داخلی و مستندات را نابود نکنید: introspection را محدود به حساب‌های داخلی کنید یا schema snapshot را در یک مستندات عمومی منتشر کنید.

Mutation را چطور idempotent کنم؟

REST با هدر Idempotency-Key این کار را می‌کند، ولی GraphQL چنین استانداردی ندارد. راه عملی: یک آرگومان clientMutationId در Mutation بگذارید، آن را در Redis نگه دارید و اگر تکرار شد نتیجه‌ی ذخیره‌شده را برگردانید. برای عملیات مالی، کلید یکتای خود کاربر هم معمولاً کافی است.

آیا برای آپلود فایل و استریم باینری مناسب است؟

به‌صورت پیش‌فرض نه. خودِ مشخصات GraphQL برای داده‌ی ساخت‌یافته طراحی شده، نه باینری. راه‌های رایج: استفاده از یک سرویس فایل جدا با URL امضاشده و سپس فرستادن فقط شناسه در Mutation، یا پروتکل‌هایی مثل graphql-upload-files. برای ویدیو و فایل حجیم، REST یا پروتکل اختصاصی ساده‌تر است.

GraphQL و gRPC چه تفاوتی دارند؟

مکمل‌اند. gRPC یک RPC با قرارداد سفت و باینری است که در آن کلاینت متدهای مشخص را صدا می‌زند — مناسب ارتباط داخلی و کارایی بالا. GraphQL یک زبان پرسش است که کلاینت شکل داده را تعیین می‌کند — مناسب لایه‌ی تجمیع و کلاینت‌های محصول. بسیاری از سازمان‌ها هر دو را دارند و حتی gRPC را پشت GraphQL قرار می‌دهند.

اگر Schema خیلی بزرگ شد چه کنم؟

سه مسیر دارید: تقسیم به چند سرویس با Federation، یا یک BFF کوچک که فقط فیلدهای مورد نیاز محصول را نگه می‌دارد، یا بازبینی مدل و حذف فیلدهای منسوخ با @deprecated. مهم‌تر اینکه Schema را قبل از بزرگ شدن مالکیت‌دار کنید: هر بخش یک مالک و یک بازبین داشته باشد.

Subscription در مقیاس بالا چطور کار می‌کند؟

هر کلاینت یک اتصال باز نگه می‌دارد، پس سرور باید از یک broker مثل Redis Pub/Sub، Kafka یا NATS استفاده کند تا رویداد از سرویسی که تولیدش کرده به همه‌ی سرورهای نگه‌دارنده‌ی اتصال برسد. در مقیاس خیلی بزرگ، ابزارهایی مثل GraphQL over Server-Sent Events یا polling کوتاه‌تر ساده‌تر و ارزان‌تر تمام می‌شوند.

آیا GraphQL فقط برای اپ موبایل است؟

نه. ریشه‌اش در اپ موبایل فیس‌بوک است چون آن‌جا مشکل over-fetching شدید بود، ولی امروز در داشبورد‌های وب، پنل‌های ادمین و محصولات SaaS هم استفاده می‌شود. هرجا چند کلاینت با نیازهای متفاوت به همان داده‌ها دسترسی دارند، GraphQL کاندیدای خوبی است.

یادگیری GraphQL چقدر طول می‌کشد؟

مفاهیم پایه (Schema، Query، Mutation، variables و fragment) در یک روز قابل یادگیری است. بخش‌های سخت‌تر—DataLoader، طراحی Nullability، صفحه‌بندی Connection و امنیت—چند هفته تمرین واقعی می‌خواهد. مهارت اصلی که باید از قبل داشته باشید، طراحی قرارداد داده و توانایی خواندن کد تولیدشده از Schema است.

اگر مجبور به استفاده از GraphQL شدم، از کجا شروع کنم؟

۱) کوچک‌ترین دامنه‌ی واقعی را انتخاب کنید، مثلاً صفحه‌ی جزئیات سفارش. ۲) Schema را بنویسید و آن را با تیم بازبینی کنید. ۳) resolver ها و DataLoader را کامل کنید. ۴) depth limit و cost analysis را از روز اول بگذارید. ۵) پایش per-field را فعال کنید. ۶) با یک کلاینت واقعی و اندازه‌گیری زمان بارگذاری، نتیجه را تأیید کنید.

بخش ۲۵جمع‌بندی و مقالات مرتبط

آنچه باید به یاد بماند
  1. GraphQL یک زبان پرسش است، نه یک زبان برنامه‌نویسی و نه جایگزین HTTP.
  2. Schema منبع حقیقت است — قرارداد، مستند و منبع تولید کد تایپ‌دار به‌طور هم‌زمان.
  3. پاسخ دقیق، کارایی کلاینت را بالا می‌برد ولی بار سرور را هم بالا می‌برد؛ این یک معامله است.
  4. Query موازی و Mutation سریال اجرا می‌شود — این قانون تعیین‌کننده‌ی طراحی resolver است.
  5. DataLoader غیرقابل مذاکره است — بدون آن، GraphQL فقط مشکل N+1 را مقیاس‌پذیر می‌کند.
  6. خطا داخل بدنه است؛ همیشه آرایه‌ی errors را بخوانید و روی extensions.code تکیه کنید.
  7. depth limit و cost analysis را از روز اول بگذارید، نه بعد از اولین حادثه.
  8. GraphQL را در لایه‌ی تجمیع به کار ببرید؛ برای API عمومی و صفحات ساده، REST انتخاب منطقی‌تری است.
