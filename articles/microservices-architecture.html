بخش ۱مقدمه: وقتی مونولیت به سقف می‌رسد

فرض کنید یک فروشگاه اینترنتی دارید که با یک اپلیکیشن ساده شروع کرده. ۱۵۰ هزار خط کد، یک تیم، یک مخزن، یک استقرار. سه سال بعد: 

وضعیت امروز:
  ├── ۲۲ توسعه‌دهنده در یک تیم
  ├── ۱۲۰ هزار کامنت لاگ در ماه
  ├── استقرار = ۴۵ دقیقه (build + تست + deploy)
  ├── «چه کسی می‌دهد؟» — همه، همه‌چیز را می‌توانند بشکنند
  └── سرعت تحویل = یک قابلیت در ۳ هفته

مشکلات واقعی که تیم را فرسوده کرده‌اند:

  1. استقرار یک‌طرفه — هر تغییر کوچک یعنی کل سیستم مستقر شود
  2. انتظار برای تست — ۴۵ دقیقه برای فهمیدن اینکه آیا یک خط درست است
  3. merge conflict دائمی — همه در یک مخزن، همه در یک شاخه‌ی اصلی
  4. مقیاس یکسان — بخش گزارش‌گیری همان منابع بخش سفارش را می‌گیرد
  5. مالکیت مبهم — هیچ‌کس نمی‌داند مسئول کدام بخش است
  6. باگ سراسری — یک تغییر کوچک می‌تواند کل سیستم را از کار بیندازد
راه‌حلی که صنعت پذیرفت سیستم را به چند سرویس کوچک بشکنید که هرکدام مستقلاً قابل استقرار باشند، داده‌ی خودش را داشته باشند و توسط تیم خودشان نگهداری شوند.

این کار باعث می‌شود تیم «فروش» فقط سرویس فروش را مستقر کند، تیم «گزارش» فقط سرویس گزارش. یک باگ در فروش، گزارش را از کار نمی‌اندازد.

ولی قیمت دارد

هشدار صادقانه همین کار، مشکلات جدید و بزرگی می‌سازد: داده‌ها دیگر یک‌جا نیستند، نمی‌توانید یک تراکنش روی همه بزنید، عیب‌یابی سخت‌تر شده، و ناگزیر سیستم‌هایی مثل API Gateway، Service Discovery، Circuit Breaker و پیام‌رسان لازم می‌شوند. اینها همه هزینه‌های واقعی‌اند، نه ترس‌های تئوری. 
سؤال درست این نیست: «میکروسرویس خوب است یا بد؟»
سؤال درست این است: «آیا هزینه‌ی توزیع‌شده کردن، از ارزشش بیشتر است؟»

برای یک تیم ۵ نفره: تقریباً همیشه نه
برای یک سازمان ۱۰۰ نفره با ۲۰ تیم: اغلب بله

بخش ۴مشکل قبل از استفاده

۱. بن‌بست استقرار

شنبه، ۱۶:۵۸
  علی یک خط در ماژول «تخفیف» را اشتباه کرد
  ← merge می‌کند در شاخه‌ی اصلی
  ← pipeline شروع می‌شود: build (8min) + تست (22min) + deploy (15min)
  ← علی باید ۴۵ دقیقه منتظر بماند
  ← اگر تست شکست بخورد، همه‌ی ۲۰ نفر تیم ۴۵ دقیقه معطل‌اند

  ← علی تغییر را انجام می‌دهد، ولی این پنج‌شنبه از دست رفته

۲. کوپل در زمان استقرار

سرویس A می‌گوید: «فیلد جدیدی به پاسخ اضافه کردم»
سرویس B می‌گوید: «من آن را لازم دارم»

  A: منتظر B می‌ماند تا مستقر کند     ← A مسدود
  B: منتظر A می‌ماند تا تست کند       ← B مسدود

← هیچ‌کدام نمی‌تواند جلو برود
← کمپل در زمان استقرار، ۱۰۰۰ برابر گران‌تر از کوپل در زمان کد

۳. مقیاس یکسان برای همه

سرویس گزارش روزی ۱۰۰۰ درخواست می‌گیرد، ۲ ثانیه هر کدام
سرویس سفارش روزی ۱ میلیون درخواست می‌گیرد، ۲۰۰ میلی‌ثانیه هر کدام

  اگر یک سرویس باشند: باید برای اوج گزارش، ۵۰ سرور سفارش هم بخری
  ← هزینه: ۵۰ × (هزینه‌ی یک سرور غیرضروری)

  اگر جدا باشند: گزارش ۱ سرور، سفارش ۵ سرور

۴. مالکیت مبهم در مقیاس

سؤال: «این باگ در محاسبه‌ی مالیات کجاست؟»
پاسخ در مونولیت: «یکی باید پیدا کند» ← ۳ روز
پاسخ در سرویس: «سرویس مالیات» ← ۳ دقیقه

۵. شکست سراسری

یک تغییر کوچک در ماژول «جست‌وجو» باعث NullPointerException
  ← کل اپلیکیشن بالا نمی‌آید
  ← فروشگاه کاملاً از کار افتاده

در سرویس:
  یک تغییر کوچک در سرویس «جست‌وجو» باعث خطا
  ← سرویس جست‌وجو down می‌شود
  ← بخش جست‌وجوی سایت کار نمی‌کند
  ← فروشگاه همچنان کار می‌کند

۶. صف انتظار برای بازبینی

تیم ۲۰ نفره، یک مخزن:
  ← PR queue: ۴۵ PR باز
  ← میانگین زمان تا merge: ۲ روز
  ← هر PR کوچک هم باید بازبینی شود

تیم‌های کوچک‌تر، مخازن جدا:
  ← PR queue: ۳ PR باز
  ← میانگین زمان تا merge: ۲ ساعت

بخش ۵ایده اصلی: تجزیه‌ی دامنه

مهم‌ترین نکته‌ی کل مقاله مرز میکروسرویس را فناوری یا سایز تعیین نمی‌کند؛ آن را مرز دامنه‌ی کسب‌وکار تعیین می‌کند. اگر مرز درست نباشد، هر چقدر هم زیرساخت خوبی داشته باشید، شکست خواهید خورد.

جریان یک سفارش — نمای کامل

چه چیزی هم‌زمان و چه چیزی ناهمگام است درگاه پرداخت هم‌زمان است چون کاربر منتظر نتیجه می‌ماند (می‌خواهد بداند پرداخت شد یا نه). انبار و اعلان ناهمگام هستند چون کاربر منتظر آن‌ها نیست. این ترکیب، حرفه‌ای‌ترین حالت است.

جریان خطا در سیستم توزیع‌شده

چهار نوع خطا در سیستم توزیع‌شده

نوع خطانمونهراه‌حل
سخت (Hard failure)سرویس ۵۰۰ می‌دهدCircuit Breaker، retry با backoff
نرم (Soft failure)پاسخ کند یا timeouttimeout کوتاه، fallback
جزئی (Partial)یکی از سرویس‌های موازی جواب ندادپاسخ ناقص با وضعیت مشخص

قواعد طلایی ارتباط

  • همیشه timeout داشته باشید — بدون timeout، درخواست بی‌نهایت منتظر می‌ماند
  • همیشه retry محدود با فاصله‌ی فزاینده — نه بی‌نهایت و نه بلافاصله
  • همیشه idempotency key برای عملیات نوشتن — تا retry تکرار ایجاد نکند
  • همیشه circuit breaker برای تماس بیرونی
  • همیشه correlationId بین سرویس‌ها
  • هرگز کلاس پیاده‌سازی سرویس دیگر را صدا نزنید، فقط قراردادش را

package com.shop.order.integration.client;

import java.math.BigDecimal;

/** Port: فقط قرارداد. هیچ چیزی درباره‌ی HTTP نمی‌داند. */
public interface PaymentClient {

    PaymentResult capture(String orderId, BigDecimal amount,
                          String currency, String callbackUrl);

    void refund(String orderId, BigDecimal amount);

    record PaymentResult(String transactionId, Status status, String referenceCode) {
        public enum Status { CAPTURED, FAILED }
    }
}

package com.shop.order.integration.client;

import com.shop.contracts.payment.v1.PaymentApi;
import io.github.resilience4j.circuitbreaker.annotation.CircuitBreaker;
import io.github.resilience4j.retry.annotation.Retry;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.stereotype.Component;

import java.math.BigDecimal;

@Component
class HttpPaymentClient implements PaymentClient {

    private static final Logger log = LoggerFactory.getLogger(HttpPaymentClient.class);

    private final PaymentApi api;

    HttpPaymentClient(PaymentApi api) {
        this.api = api;
    }

    @Override
    @CircuitBreaker(name = "payment", fallbackMethod = "captureFallback")
    @Retry(name = "payment")
    public PaymentResult capture(String orderId, BigDecimal amount,
                                 String currency, String callbackUrl) {
        var response = api.capture(new PaymentApi.CaptureRequest(
                orderId, amount.longValue(), currency, callbackUrl));

        return new PaymentResult(response.transactionId(),
                "CAPTURED".equals(response.status())
                        ? PaymentResult.Status.CAPTURED
                        : PaymentResult.Status.FAILED,
                response.referenceCode());
    }

    /**
     * وقتی سرویس پرداخت خراب است، این متد صدا زده می‌شود.
     * نکته: سفارش نباید خراب شود — فقط در وضعیت انتظار قرار می‌گیرد.
     */
    private PaymentResult captureFallback(String orderId, BigDecimal amount,
                                          String currency, String callbackUrl,
                                          Throwable cause) {
        log.warn("درگاه پرداخت در دسترس نیست، سفارش {} در انتظار ماند", orderId);
        throw new PaymentUnavailableException("سرویس پرداخت موقتاً در دسترس نیست");
    }

    @Override
    @CircuitBreaker(name = "payment")
    public void refund(String orderId, BigDecimal amount) {
        api.refund(new PaymentApi.RefundRequest(orderId, amount.longValue()));
    }
}

package com.shop.order.api;

import com.shop.order.domain.*;
import com.shop.order.integration.client.PaymentClient;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

import java.math.BigDecimal;
import java.time.Instant;

@Service
public class OrderService {

    private static final Logger log = LoggerFactory.getLogger(OrderService.class);

    private final OrderRepository orders;
    private final PaymentClient payments;
    private final DomainEventPublisher events;

    public OrderService(OrderRepository orders, PaymentClient payments,
                        DomainEventPublisher events) {
        this.orders = orders;
        this.payments = payments;
        this.events = events;
    }

    @Transactional
    public String place(PlaceOrderCommand command, String correlationId) {
        Order order = Order.create(command.customerId());

        command.lines().forEach(l ->
                order.addLine(l.productId(), l.quantity(), l.unitPrice()));

        order.place();
        orders.save(order);

        // رویداد در همان تراکنش ذخیره می‌شود
        events.record(new OrderPlaced(order.id(), order.customerId(),
                order.total(), order.lines().size(),
                Instant.now()), correlationId);

        return order.id();
    }

    /**
     * پرداخت در تراکنش جداگانه.
     * دلیل: تماس شبکه‌ای نباید تراکنش دیتابیس را باز نگه دارد.
     */
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public PaymentOutcome processPayment(String orderId) {
        Order order = orders.findById(new OrderId(orderId))
                .orElseThrow(() -> new OrderError("سفارش یافت نشد"));

        try {
            var result = payments.capture(orderId, order.total(),
                    "IRR", "https://shop.example/callback");

            order.markPaid(result.transactionId());
            orders.save(order);
            return PaymentOutcome.PAID;

        } catch (PaymentUnavailableException e) {
            // درگاه خراب است: سفارش سالم می‌ماند، بعداً دوباره تلاش می‌شود
            log.warn("پرداخت سفارش {} به تعویق افتاد", orderId);
            order.markPaymentPending();
            orders.save(order);
            return PaymentOutcome.PENDING;

        } catch (PaymentFailedException e) {
            order.markPaymentFailed(e.getMessage());
            orders.save(order);
            events.record(new PaymentFailed(orderId, e.getMessage(),
                    Instant.now()), null);
            return PaymentOutcome.FAILED;
        }
    }

    public enum PaymentOutcome { PAID, PENDING, FAILED }
}

package com.shop.order.integration.event;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.data.domain.PageRequest;
import org.springframework.kafka.core.KafkaTemplate;
import org.springframework.scheduling.annotation.Scheduled;
import org.springframework.stereotype.Component;
import org.springframework.transaction.annotation.Transactional;

@Component
public class OutboxRelay {

    private static final Logger log = LoggerFactory.getLogger(OutboxRelay.class);
    private static final int MAX_ATTEMPTS = 8;

    private final OutboxEventRepository repository;
    private final KafkaTemplate<String, String> kafka;
    private final String topic;

    public OutboxRelay(OutboxEventRepository repository,
                       KafkaTemplate<String, String> kafka,
                       @Value("${app.outbox.topic}") String topic) {
        this.repository = repository;
        this.kafka = kafka;
        this.topic = topic;
    }

    @Scheduled(fixedDelayString = "${app.outbox.interval:1000}")
    @Transactional
    public void publishPending() {
        var batch = repository.findUnpublished(PageRequest.of(0, 200));

        for (OutboxEvent event : batch) {
            try {
                // کلید = شناسه‌ی سفارش → ترتیب به‌ازای سفارش حفظ می‌شود
                kafka.send(topic, event.eventKey(), event.payload())
                        .get(5, java.util.concurrent.TimeUnit.SECONDS);
                event.markPublished();

            } catch (Exception e) {
                event.markFailed(e.getMessage());
                log.warn("انتشار ناموفق ({}): {}",
                        event.eventType(), e.getMessage());
            }
        }
    }
}

package com.shop.inventory.integration;

import com.shop.contracts.order.v1.OrderPlacedV1;
import com.shop.inventory.domain.StockService;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.kafka.annotation.KafkaListener;
import org.springframework.stereotype.Component;
import org.springframework.transaction.annotation.Transactional;

@Component
public class OrderPlacedConsumer {

    private static final Logger log = LoggerFactory.getLogger(OrderPlacedConsumer.class);

    private final StockService stock;
    private final ProcessedEventStore processed;

    public OrderPlacedConsumer(StockService stock, ProcessedEventStore processed) {
        this.stock = stock;
        this.processed = processed;
    }

    @KafkaListener(topics = "orders", groupId = "inventory-service",
                   concurrency = "4")
    @Transactional
    public void on(OrderPlacedV1 event) {
        // ۱. حذف تکرار
        if (processed.wasProcessed(event.eventId())) {
            return;
        }

        // ۲. منطق کسب‌وکار
        for (OrderPlacedV1.Line line : event.lines()) {
            try {
                stock.reserve(line.productId(), line.quantity(), event.orderId());
            } catch (InsufficientStockException e) {
                // ۳. اعلام شکست به سرویس سفارش (جبران)
                log.warn("موجودی ناکافی برای سفارش {}", event.orderId());
                stock.release(event.orderId());
                rejectionPublisher.publish(new OrderRejectedV1(
                        event.orderId(), "موجودی ناکافی",
                        java.time.Instant.now()));
            }
        }

        // ۴. ثبت در همان تراکنش
        processed.markProcessed(event.eventId());
    }
}

فیلتر correlationId در Gateway

package com.shop.gateway.filter;

import org.springframework.core.Ordered;
import org.springframework.cloud.gateway.filter.GatewayFilterChain;
import org.springframework.cloud.gateway.filter.GlobalFilter;
import org.springframework.core.annotation.Order;
import org.springframework.stereotype.Component;
import org.springframework.web.server.ServerWebExchange;
import reactor.core.publisher.Mono;

import java.util.UUID;

@Component
@Order(Ordered.HIGHEST_PRECEDENCE)
public class CorrelationIdFilter implements GlobalFilter {

    private static final String HEADER = "X-Correlation-Id";

    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        String correlationId = exchange.getRequest().getHeaders()
                .getFirst(HEADER);

        if (correlationId == null || correlationId.isBlank()) {
            correlationId = UUID.randomUUID().toString();
        }

        exchange.getRequest().mutate()
                .headers(h -> h.set(HEADER, correlationId))
                .build();

        return chain.filter(exchange)
                .doOnSuccess(v -> exchange.getResponse().getHeaders()
                        .set(HEADER, correlationId));
    }
}

@Component

    private final Counter paymentsFailed;
    private final Timer paymentCall;

        this.ordersPlaced = Counter.builder("orders.placed")
                .description("تعداد سفارش‌های ثبت‌شده")
                .register(registry);

                .description("تعداد پرداخت‌های ناموفق")
                .register(registry);

        this.paymentCall = Timer.builder("payments.call.duration")
                .description("مدت تماس با سرویس پرداخت")
                .publishPercentileHistogram()
                .register(registry);
    }

    public void recordPlaced() {
        ordersPlaced.increment();
    }

    public void recordPaymentFailed() {
        paymentsFailed.increment();
    }

    public void recordPaymentCall(long millis) {
        paymentCall.record(millis, TimeUnit.MILLISECONDS);
    }

    public void recordPaymentCall(Runnable call) {
        long start = System.nanoTime();
        try {
            call.run();
        } finally {
            paymentCall.record(System.nanoTime() - start, TimeUnit.NANOSECONDS);
        }
    }
}

 * Readiness: آیا سرویس آماده‌ی دریافت ترافیک است؟
 * این دو نباید یکی باشند — یکی از اشتباهات رایج.

@Component("paymentReadiness")
class PaymentReadinessIndicator implements HealthIndicator {

    private final PaymentClient payments;

    @Override
    public Health health() {
        try {
            payments.healthCheck();
            return Health.up()
                    .withDetail("payment", "reachable")
                    .build();
        } catch (Exception e) {
            // سرویس پرداخت خراب است، ولی سرویس سفارش زنده است
            return Health.down()
                    .withDetail("payment", "unreachable")
                    .withDetail("error", e.getMessage())
                    .build();
        }
    }
}

کپی داده بین سرویس‌ها — قواعد

  • فقط داده‌ی لازم را کپی کنید، نه کل مدل
  • کپی محلی باشد، نه دسترسی مستقیم به دیتابیس دیگری
  • کپی همیشه قابل بازسازی باشد (از رویدادها)
  • مالکیت با سرویس مبدأ است؛ کپی فقط مصرف‌کننده دارد
  • تغییر ساختار کپی باید نسخه‌بندی شود

class FakePaymentClient implements PaymentClient {

    private boolean shouldFail = false;

    void failNextCalls(boolean fail) {
        this.shouldFail = fail;
    }

    @Override
    public PaymentResult capture(String orderId, BigDecimal amount,

    }

Saga Orchestration — پیاده‌سازی

package com.shop.checkout.saga;

import com.shop.checkout.integration.client.*;
import com.shop.checkout.domain.*;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.stereotype.Component;

/**
 * Saga مرحله‌ای: هر گام یک تراکنش محلی + یک عملیات جبرانی.
 */
@Component
public class CheckoutSaga {

    private static final Logger log = LoggerFactory.getLogger(CheckoutSaga.class);

    private final InventoryClient inventory;
    private final PaymentClient payment;
    private final OrderClient orders;
    private final NotificationClient notifications;

    public CheckoutSaga(InventoryClient inventory, PaymentClient payment,
                        OrderClient orders, NotificationClient notifications) {
        this.inventory = inventory;
        this.payment = payment;
        this.orders = orders;
        this.notifications = notifications;
    }

    public CheckoutResult run(String orderId, long amount) {
        // ── گام ۱: رزرو موجودی ──
        if (!inventory.reserve(orderId)) {
            log.warn("موجودی ناکافی برای سفارش {}", orderId);
            return CheckoutResult.OUT_OF_STOCK;
        }

        try {
            // ── گام ۲: پرداخت ──
            payment.capture(orderId, amount);

        } catch (PaymentUnavailableException e) {
            // ── جبران گام ۱ ──
            inventory.release(orderId);
            return CheckoutResult.PENDING;

        } catch (PaymentDeclinedException e) {
            // ── جبران گام ۱ ──
            inventory.release(orderId);
            orders.reject(orderId, "پرداخت رد شد");
            return CheckoutResult.PAYMENT_DECLINED;

        } catch (Exception e) {
            // خطای غیرمنتظره: همه‌ی گام‌ها را جبران می‌کنیم
            log.error("خطای غیرمنتظره در تسویه: {}", orderId, e);
            inventory.release(orderId);
            orders.reject(orderId, "خطای داخلی");
            return CheckoutResult.FAILED;
        }

        // ── گام ۳: تأیید نهایی (جبران‌ناپذیر) ──
        orders.confirm(orderId);
        notifications.sendConfirmation(orderId);

        return CheckoutResult.COMPLETED;
    }

    public enum CheckoutResult {
        COMPLETED, PENDING, OUT_OF_STOCK, PAYMENT_DECLINED, FAILED
    }
}

package com.shop.gateway;

/**
 * مسیریابی تدریجی: برای هر مسیر، سرویس جدید یا قدیم؟

@Component
public class StranglerRouter {

    private final FeatureToggles toggles;

    public StranglerRouter(FeatureToggles toggles) {
        this.toggles = toggles;
    }

    public String routeFor(String path) {
        if (path.startsWith("/api/orders")) {
            // پرچم را می‌توانید بدون استقرار تغییر دهید
            return toggles.isEnabled("orders.new-service")
                    ? "http://order-service-v2"
                    : "http://monolith";
        }
        return "http://monolith";
    }
}

قواعد بهینه‌سازی

  • مکالمه‌ی شبکه کم، پیام بزرگ: به‌جای ۱۰ تماس با ۱۰ کاربر، یک تماس با یک DTO کامل
  • bulkhead واقعی: هر وابستگی thread pool جدا؛ بدون آن یک وابستگی کند، همه را می‌بلعاند
  • timeout کوتاه: بیشتر تماس‌ها باید زیر ۵۰۰ میلی‌ثانیه بسته شوند؛ تماس باز، بیشترین ضرر را می‌زند
  • circuit breaker: روی همه‌ی تماس‌های بیرونی اجباری است
  • cache محلی: داده‌ی کم‌تغییر (مثل کاتالوگ) را در سرویس مصرف‌کننده نگه دارید
  • جریان ناهمگام: هر کاری که کاربر منتظرش نیست، باید از مسیر پاسخ خارج شود
  • پایش: بدون متریک، هر بهینه‌سازی حدس و گمان است
package com.shop.order.integration;

import io.github.resilience4j.bulkhead.annotation.Bulkhead;
import io.github.resilience4j.circuitbreaker.annotation.CircuitBreaker;
import io.github.resilience4j.retry.annotation.Retry;
import io.github.resilience4j.timelimiter.annotation.TimeLimiter;
import org.springframework.stereotype.Component;

import java.util.concurrent.CompletableFuture;
import java.util.concurrent.TimeUnit;

/**
 * ترکیب چهار الگوی تاب‌آوری برای یک وابستگی بیرونی.
 */
@Component
public class ResilientInventoryClient {

    private final InventoryHttpClient http;

    public ResilientInventoryClient(InventoryHttpClient http) {
        this.http = http;
    }

    @CircuitBreaker(name = "inventory", fallbackMethod = "cachedAvailability")
    @Retry(name = "inventory")                 // فقط خطای گذرا
    @TimeLimiter(name = "inventory")           // سقف زمانی
    @Bulkhead(name = "inventory", type = Bulkhead.Type.THREADPOOL)
    public CompletableFuture<Availability> check(long productId) {
        return http.getAvailability(productId);
    }

    /** اگر سرویس خراب بود، آخرین داده‌ی معتبر را برمی‌گردانیم. */
    private CompletableFuture<Availability> cachedAvailability(
            long productId, Throwable cause) {
        return http.getLastKnownAvailability(productId);
    }
}
تله‌ی رایج Retry روی خطای ۴۰۴ یا اعتبارسنجی نادرست، بار را ۳ برابر می‌کند بی‌آنکه فایده‌ای داشته باشد. فقط خطاهای گذرا (timeout، ۵۰۳، قطعی شبکه) را با backoff تصادفی تکرار کنید.

بخش ۲۳سوالات مصاحبه

سطح Junior

سؤال 1 — Microservices چیست و چه فرقی با مونولیت دارد؟

Microservices یعنی تقسیم سیستم به مجموعه‌ای از سرویس‌های کوچک که هرکدام مستقل اجرا، مستقل مستقر و مستقل در داده هستند. تفاوت اصلی با مونولیت فقط اندازه نیست؛ در استقلال است. در مونولیت، تغییر یک بخش نیازمند کل سیستم است؛ در Microservices، سرویس مربوطه مستقل تغییر، تست و منتشر می‌شود.

سؤال 2 — تفاوت microservice با یک ماژول معمولی در مونولیت چیست؟

ماژول در مونولیت معمولاً در همان فرایند اجرا می‌شود، دیتابیس مشترک دارد و انتشار آن نیازمند کل سرویس است. Microservice مستقل اجرا می‌شود، پروتکل ارتباطی مشخص دارد و مستقل منتشر می‌شود. مرز کد یکسان است؛ مرز اجرا و داده متفاوت.

سؤال 3 — چه زمانی نباید Microservices بسازید؟

وقتی تیم کوچک است، محصول تازه و مدل کسب‌وکار هنوز تغییر می‌کند، زیرساخت DevOps ندارید، یا ترافیک و تیم شما آن‌قدر کوچک است که یک برنامه به‌راحتی از پس آن برمی‌آید. در این شرایط Modular Monolith انتخاب بسیار بهتری است.

سؤال 4 — Bounded Context در DDD چه ربطی به Microservices دارد؟

Bounded Context مرز مدل دامنه است؛ جایی که یک واژه می‌تواند دو معنای متفاوت داشته باشد. Microservice معمولاً نگاشت یک‌به‌یک یا یک‌به‌چند با Bounded Context است. اگر یک سرویس شامل دو Bounded Context باشد، احتمالاً باید به دو سرویس تقسیم شود.

سؤال 5 — تفاوت سرویس stateless و stateful چیست؟

سرویس stateless هیچ نشستی را در حافظه نگه نمی‌دارد؛ هر درخواست کامل است. این نوع را به‌راحتی می‌توان مقیاس داد و پشت Load Balancer قرار داد. سرویس stateful نشست را در حافظه نگه می‌دارد؛ مقیاس‌پذیری آن سخت است و به Sticky Session یا ذخیره‌سازی بیرونی نشست نیاز دارد. سرویس‌های مایکروسرویس ترجیحاً stateless هستند.

سؤال 6 — timeout چرا حیاتی است؟

بدون timeout، تماس بین دو سرویس می‌تواند تا ابد منتظر بماند و thread ها را اشغال کند. در بار زیاد این اشغال زنجیره‌ای می‌شود و کل سیستم از کار می‌افتد. timeout یک مرز زمانی مشخص می‌گذارد تا منابع آزاد شوند و فراخوان مقطعی دریافت خطا کند.

سؤال 7 — چرا دیتابیس به‌ازای هر سرویس؟

چون مالکیت داده را روشن می‌کند. هیچ سرویسی نباید مستقیم جدول سرویس دیگر را بخواند یا بنویسد؛ اگر بتواند، استقلال آن سرویس شکننده می‌شود. داده‌های موردنیاز سرویس دیگر باید از طریق API یا رویداد در اختیارش قرار گیرد، ترجیحاً به‌شکل نسخه‌ی محلی و فقط‌خواندنی برای پرهیز از تماس در هر درخواست.

سؤال 8 — تفاوت REST، gRPC و پیام‌سازی چیست؟

REST ساده و همه‌جا در دسترس است اما کارایی پایین‌تری دارد. gRPC بر پایه‌ی protobuf است، باینری و سریع، و برای ارتباط داخلی مناسب است ولی در مرورگر و دیوارهای سازمانی گاهی مشکل‌ساز می‌شود. پیام‌سازی برای کارهای ناهمگام و غیرهم‌زمان مناسب است و مزیت اصلی آن تحمل خطا و مقاومت است.

سؤال 9 — چه زمانی از پیام‌سازی به‌جای فراخوانی مستقیم استفاده کنیم؟

وقتی مصرف‌کننده به نتیجه‌ی فوری نیاز ندارد، وقتی می‌خواهیم سرویس‌ها را مستقل از هم مقیاس دهیم، وقتی می‌خواهیم کاری را به چند مصرف‌کننده برسانیم، و وقتی نیاز به تحمل خطا و تحویل دوباره داریم. در مقابل، وقتی کاربر منتظر نتیجه است، فراخوانی هم‌زمان ساده‌تر است.

سؤال 10 — چطور یک سرویس را مستقل مستقر می‌کنید؟

هر سرویس مخزن و خط لوله‌ی CI خودش را دارد. استقرار باید backward-compatible باشد: نسخه‌ی جدید را کنار نسخه‌ی قبلی بالا می‌آورید، ترافیک را جابه‌جا می‌کنید و اگر مشکلی بود برمی‌گردید. اسکیمای پیام هم باید سازگار بماند تا مصرف‌کننده‌های قدیمی نشکنند.

سؤال 11 — چه ابزارهایی در اکوسیستم لازم است؟

حداقل: یک ابزار Orchestration مثل Kubernetes، یک سیستم پیام مثل Kafka یا RabbitMQ، ابزار پیکربندی مرکزی، ابزار observability مثل Prometheus و Grafana، و یک ابزار مدیریت اسکریم. در سطح پیشرفته‌تر Service Mesh و CI/CD خودکار هم لازم می‌شود.

سطح Mid

سؤال 12 — Saga چیست و چرا ACID کافی نیست؟

ACID روی یک دیتابیس کار می‌کند. در چند سرویس با دیتابیس جدا، تراکنش توزیع‌شده یعنی ۲PC که کارایی و دسترس‌پذیری را به‌شدت کاهش می‌دهد. Saga به‌جای یک تراکنش بزرگ، زنجیره‌ای از تراکنش‌های محلی است که هرکدام رویدادی منتشر می‌کند و در صورت شکست، تراکنش‌های قبلی با عملیات جبرانی خنثی می‌شوند.

سؤال 13 — Saga در دو نوع Choreography و Orchestration

در Choreography، سرویس‌ها به رویدادها گوش می‌دهند و خودشان تصمیم می‌گیرند؛ هیچ مرکز فرمانی وجود ندارد. مزیت: کم‌جفتگی و افزودن سرویس جدید آسان. عیب: جریان کار در کل سیستم پخش است و دیباگ سخت می‌شود. در Orchestration، یک سرویس هماهنگ‌کننده مراحل را مدیریت می‌کند؛ جریان شفاف‌تر و خطایابی آسان‌تر است، اما آن سرویس به همان اندازه‌ی دیگران نقطه‌ی قوت و ضعف دارد.

سؤال 14 — مشکل Dual Write چیست و راه‌حل آن؟

اگر در یک درخواست هم دیتابیس را بنویسید هم پیام را منتشر کنید، یکی از این دو ممکن است موفق و دیگری شکست بخورد. حالت ناسازگار پایدار ایجاد می‌شود. راه‌حل: الگوی Outbox. رویداد را در همان تراکنش دیتابیس ذخیره می‌کنید، سپس یک پروسه‌ی جداگانه آن را منتشر می‌کند. تضمین می‌شود رویداد هرگز گم نمی‌شود.

سؤال 15 — Idempotency چیست و چگونه پیاده می‌شود؟

یعنی اجرای دوباره‌ی یک عملیات، همان اثر یک بار اجرا را داشته باشد. در مصرف‌کننده‌ی پیام، کلید یکتای شناسه‌ی پیام را در جدولی ثبت می‌کنید و اگر قبلاً دیده شده، بی‌صدا رد می‌شود. این تنها راه مقابله با تحویل دوباره است، چون تضمین exactly-once در شبکه وجود ندارد.

سؤال 16 — Circuit Breaker چگونه کار می‌کند؟

سه حالت دارد: بسته یعنی تماس عادی؛ باز یعنی خطا زیاد بوده و تماس‌ها رد می‌شوند تا سرویس پایین بیاید؛ نیمه‌باز یعنی چند تماس آزمایشی برای سنجش وضعیت فرستاده می‌شود. اگر موفق باشند به حالت بسته برمی‌گردد. فایده‌اش این است که سرویس سالم، منابعش را صرف سرویس مرده نمی‌کند و پاسخ سریع می‌دهد.

سؤال 17 — Bulkhead چه تفاوتی با Circuit Breaker دارد؟

Circuit Breaker تصمیم می‌گیرد اصلاً تماس بگیریم یا نه. Bulkhead تصمیم می‌گیرد با چه منابعی تماس بگیریم؛ یعنی هر وابستگی منابع خودش را دارد. اگر سرویس پرداخت کند شود و thread pool آن پر شود، سرویس کاتالوگ که pool جدا دارد همچنان سالم می‌ماند. ترکیب این دو الگو پایداری سیستم را چند برابر می‌کند.

سؤال 18 — چطور در سیستم توزیع‌شده ردیابی می‌کنید؟

با تولید یک شناسه‌ی یکتا در بدو ورود در Gateway و انتقال آن در هدر به همه‌ی تماس‌های بعدی. با این کار تمام گزارش‌های مربوط به یک درخواست قابل اتصال می‌شوند. ابزارهایی مثل OpenTelemetry و Jaeger این رد را به‌شکل یک نمای درختی از اجرای سرویس‌ها نشان می‌دهند.

سؤال 19 — چه چیزی درباره‌ی نسخه‌بندی API باید بدانید؟

در API داخلی، نسخه‌بندی کمتر لازم است چون همه‌ی مصرف‌کننده‌ها را خودتان کنترل می‌کنید؛ کافی است تغییر را backward-compatible نگه دارید. در API عمومی نسخه‌بندی اجباری است و باید سیاست روشن دوره‌گردانی و تاریخ حذف داشته باشید. افزودن فیلد معمولاً سازگار است، اما حذف فیلد یا تغییر نوع آن نیست.

سطح Senior

سؤال 20 — چگونه از تخریب یک سرویس جلوگیری می‌کنید؟

اول با مقاومت‌سازی شروع می‌کنیم: timeout کوتاه روی همه‌ی تماس‌ها، circuit breaker، bulkhead، retry با backoff تصادفی فقط برای خطاهای گذرا، و در نهایت fallback که به‌جای خطا یک پاسخ کاهش‌یافته برمی‌گرداند. دوم کاری می‌کنیم که دامنه‌ی خرابی محدود بماند: صف پیام به‌جای تماس هم‌زمان، صفچینگ در ورودی، و مستقل بودن داده‌ی هر سرویس. سوم با مشاهده‌پذیری و هشدار دقیق، خرابی را پیش از گسترش می‌بینیم.

سؤال 21 — چطور از مهاجرت یک سرویس بزرگ مطمئن شویم؟

هرگز Big Bang نداریم. با Strangler Fig از یک مسیر کم‌خطر شروع می‌کنیم، مثلاً مسیر خواندن کم‌حجم. پرچم ویژگی پشت یک مسیر می‌گذاریم، سرویس جدید را در سایه اجرا می‌کنیم و خروجی آن را با خروجی قدیمی مقایسه می‌کنیم. درصد ترافیک را مرحله‌به‌مرحله بالا می‌بریم و در هر مرحله معیار عددی مثل نرخ خطا و زمان پاسخ را می‌سنجیم. معماری را برای بازگشت سریع آماده نگه می‌داریم، چون بازگشت باید یک تغییر کوچک باشد نه یک پروژه.

سؤال 22 — درباره‌ی تراکنش توزیع‌شده چه رویکردی دارید؟

به‌جای دو فاز که سردستی و کارایی دارد، Saga ترجیح می‌دهم: تراکنش‌های محلی با جبران. دو فاز را فقط وقتی استفاده می‌کنم که شرکت‌کننده‌ها کم و پایدار باشند و منابع قفل‌شدن کوتاه باشد. مهم‌تر از همه، طراحی می‌کنم که عملیات جبرانی همیشه اجرا شود، حتی وقتی خود سرویس پرداخت خراب است؛ برای همین جبران را در صف جداگانه می‌گذارم و برای آن هم retry و هشدار دارم.

سؤال 23 — چگونه تضمین می‌کنید که مهاجرت پیام، مصرف‌کننده‌های قدیمی را نشکند؟

قرارداد را تست می‌کنم: تولیدکننده قرارداد را ذخیره می‌کند و مصرف‌کننده در خط لوله‌ی خودش آن را با کلاینت واقعی مقایسه می‌کند. قوانین سخت‌گیرانه دارم: فیلد جدید اختیاری، فیلد قدیمی هرگز حذف نمی‌شود مگر پس از حذف کامل مصرف‌کننده‌ی قدیمی، و نسخه‌ی قرارداد در نام رویداد قرار می‌گیرد. تغییر ناسازگار بدون مهاجرت دوسطه‌ای قابل‌قبول نیست.

سؤال 24 — چطور هزینه‌ی عملیاتی Microservices را کاهش می‌دهید؟

اول از همه تعداد سرویس را کم می‌کنم؛ سرویس ریز فقط دردسر است. سرویس‌ها را بر اساس مالکیت داده مرز می‌کنم نه بر اساس اندازه‌ی کد. استقرار را یکنواخت می‌کنم تا ابزارها عمومی باشند: یک الگوی مشترک برای لاگ، متریک، trace و پیکربندی. قالب‌های آماده‌ی سرویس و یک اسکلت مشترک، کار تیم‌های جدید را چند برابر کوتاه‌تر می‌کند. خودکارسازی کامل استقرار و پایش، هزینه‌ی انسانی را کاهش می‌دهد. در نهایت معیارم سادگی است: هر چیزی که نتوان توضیحش داد یا کسی مالکش نیست، باید حذف شود.

سؤال 25 — در طراحی Microservice، ترتیب اولویت شما چیست؟

اول مرزها: تا دامنه روشن و قابل‌دفاع نباشد، هیچ تصمیم دیگری معتبر نیست. دوم قراردادها و سازگاری رو به عقب، چون شکست آن‌ها در محیط مستقل و نامنسجم بسیار گران است. سوم مشاهده‌پذیری از روز اول، چون بدون آن عیب‌یابی در سیستم توزیع‌شده غیرممکن است. چهارم تاب‌آوری: timeout، circuit breaker و bulkhead. پنجم مدل داده و مالکیت داده. و ششم قرارداد تیمی؛ چون بدون تیم‌های مستقل، Microservices تنها هزینه است بدون فایده.

بخش ۲۴سوالات متداول

آیا Microservices همیشه بهتر است؟

نه. Microservices یک تصمیم اقتصادی و سازمانی است، نه یک برتری فنی مطلق. هزینه‌های آن شامل زیرساخت، پیچیدگی عملیات، دشواری عیب‌یابی و کندی توسعه در مقایسه با مونولیت است. این هزینه‌ها فقط وقتی توجیه می‌شوند که تعداد تیم‌ها و سرعت تغییر از حد مشخصی عبور کرده باشد.

تفاوت Microservices با Service-Oriented Architecture چیست؟

SOA عبارت گسترده‌ای است که دهه‌ها قبل برای یکپارچه‌سازی سازمانی با سرویس‌های درشت و قراردادهای سفت (WSDL) مطرح شد. Microservices نسخه‌ی سبک و مدرن آن است: سرویس‌های کوچک، قرارداد سبک، مالکیت مستقل داده و مستقل از فناوری. هر Microservice یک SOA است، اما هر SOA لزوماً Microservice نیست.

آیا هر سرویس باید دیتابیس جدا داشته باشد؟

این یک قاعده‌ی سخت نیست، اما استثنای آن مهم است. اگر دو سرویس به‌طور دائم به جدول‌های یکدیگر نیاز دارند، عملاً یک سرویس هستند و بهتر است ادغام شوند. راه عملی میانه: هر سرویس دیتابیس منطقی خودش را دارد که کسی بیرون از آن مستقیم نمی‌نویسد، و یک نسخه‌ی فقط‌خواندنی از داده‌ی موردنیاز در اختیار مصرف‌کننده قرار می‌گیرد.

Monolith First یعنی چه؟

یعنی عمداً از ابتدا با یک Modular Monolith شروع کنید و ماژول‌ها را با مرزهای روشن بسازید. وقتی واقعاً به مرز مستقل نیاز پیدا کردید، همان ماژول را بدون بازنویسی به سرویس تبدیل کنید. مزیت این رویکرد آن است که از هزینه‌ی توزیع از روز اول پرداخت نمی‌کنید، ولی در عین حال مسیر مهاجرت باز می‌ماند.

چه زمانی باید از Microservices به سمت سرویس‌های درشت‌تر برگردیم؟

وقتی تعداد سرویس‌ها زیاد و بی‌مورد شده، وقتی مرزها مبهم شده و سرویس‌ها دائماً هم را صدا می‌زنند، وقتی استقرار و پایش از خود محصول مهم‌تر شده، یا وقتی تیم‌ها نمی‌توانند سرویس مستقل خود را بدون هماهنگی تغییر دهند. ادغام سرویس‌های به‌شدت وابسته یک تصمیم سالم است، نه عقب‌گرد.

API Gateway چه تفاوتی با BFF دارد؟

API Gateway یک لایه‌ی مشترک برای همه‌ی مسیریابی، احراز هویت و سیاست‌گذاری است. BFF یا Backend for Frontend یک نمونه‌ی اختصاصی برای هر نوع کلاینت است؛ مثلاً یکی برای اپ موبایل و یکی برای وب. اگر کلاینت‌های شما نیازهای متفاوت و پرحجم دارند، BFF بهتر است چون پاسخ‌ها را بهینه برای همان کلاینت می‌سازد. البته BFF را به‌عنوان Anti-Pattern BFF باید از آن پرهیز کرد، مخصوصاً وقتی منطق دامنه در آن جا می‌افتد.

چگونه از قطع سرویس در زمان استقرار جلوگیری کنیم؟

با استقرار تدریجی: نسخه‌ی جدید را کنار قبلی بالا می‌آورید، سلامت آن را می‌سنجید، ترافیک را جابه‌جا می‌کنید و در صورت مشکل برمی‌گردید. الگوهای شناخته‌شده شامل Rolling Update، Blue-Green و Canary هستند. مهم این است که نسخه‌ی جدید با نسخه‌ی قبلی و با مصرف‌کننده‌های قدیمی سازگار باشد.

Event Sourcing و Microservices چه ارتباطی دارند؟

Event Sourcing رویکردی است که وضعیت را به‌صورت توالی رویداد نگه می‌دارد. این با معماری رویدادمحور Microservices هم‌راستا است و تاریخچه‌ی کامل و بازسازی‌پذیر می‌دهد. اما Event Sourcing پیچیدگی زیادی دارد: نیاز به مدیریت نسخه‌بندی رویداد، مدیریت همزمانی و ابزار دیدن وضعیت فعلی. برای بیشتر سیستم‌ها، دیتابیس فعلی به‌همراه رویدادهای دامنه کافی و بسیار کم‌هزینه‌تر است.

رابطه‌ی CQRS با Microservices چیست؟

هر دو مفهوم مستقل هستند اما اغلب با هم به‌کار می‌روند. CQRS جداسازی مدل نوشتن از مدل خواندن است و Microservices جداسازی مرزهای اجرایی. CQRS در یک سرویس هم قابل پیاده‌سازی است؛ لازم نیست حتماً مدل خواندن و نوشتن در دو سرویس باشند. ترکیب بی‌دلیل این دو، پیچیدگی زیادی بدون فایده‌ی روشن می‌سازد.

چطور داده را بین سرویس‌ها منتقل کنیم؟

سه راه اصلی: فراخوانی هم‌زمان API هنگام نیاز به داده‌ی تازه و فوری؛ پیام‌رسانی وقتی داده فقط باید برسد و زمان‌بندی مهم نیست؛ و تکرار ناهمگام وقتی می‌خواهیم مصرف‌کننده بدون تماس در هر درخواست کار کند. روش سوم سریع‌تر است اما داده را کهنه می‌کند، پس باید تاریخ انقضای داده و رفتار هنگام کهنگی را صریح تعریف کنید.

آیا هر سرویس باید فناوری جداگانه داشته باشد؟

این یکی از جذاب‌ترین و در عین حال خطرناک‌ترین ادعاها در دنیای Microservices است. هر سرویس جداگانه فناوری خودش دارد در تئوری آزادی می‌دهد، اما در عمل سطح مهارت موردنیاز، هزینه‌ی نگهداری و سربار هماهنگی را چند برابر می‌کند. در عمل بهتر است فناوری اصلی سازمان یکسان بماند و تفاوت‌ها فقط جایی مجاز باشند که واقعاً ارزش عملی دارد.

Service Mesh چیست و چه زمانی لازم است؟

Service Mesh یک لایه‌ی زیرساختی است که ارتباط بین سرویس‌ها را مدیریت می‌کند: رمزنگاری، retry، مشاهده‌پذیری و مسیریابی بدون تغییر کد برنامه. معمولاً با Sidecar پیاده می‌شود، مثلاً Envoy. وقتی لازم است که سیاست‌ها به‌صورت یکنواخت و بدون دست‌زدن به کد اعمال شوند و تعداد سرویس‌ها زیاد باشد ارزشمند است. برای یک سرویس یا دو، پیچیدگی اضافه است.

چطور مصرف رویداد را در برابر پیام تکراری مقاوم کنیم؟

هر پیام یک شناسه‌ی یکتا دارد. مصرف‌کننده پیش از انجام اثر، این شناسه را در یک جدول اختصاصی ثبت می‌کند. اگر شناسه از قبل وجود داشت، پیام را بدون انجام دوباره‌ی اثر رد می‌کند. این الگو Idempotent Consumer است و در عمل جایگزین قابل‌اعتماد برای تحویل دقیقاً یک‌بار محسوب می‌شود.

مهم‌ترین مهارتی که برای Microservices لازم داریم چیست؟

نه فریم‌ورک و نه زبان. مهم‌ترین مهارت، طراحی مرزها و درک هزینه‌ی هر تصمیم است. توانایی اینکه بدانید چه چیزی باید یکی بماند و چه چیزی باید جدا شود، صدها برابر از دانستن جزئیات یک ابزار خاص اهمیت دارد. در کنار آن، مهارت‌های عملیاتی مثل مشاهده‌پذیری و عیب‌یابی شبکه هم عملاً ضروری هستند.

آیا می‌توان از دیتابیس یک سرویس مستقیم پرسید؟

از نظر فنی بله، از نظر معماری نه. این کار مرزها را نامرئی می‌کند و باعث می‌شود تغییر اسکیمای یک سرویس، سرویس دیگری را بشکند. اگر مجبورید (مثلاً برای گزارش‌گیری سنگین) از دسترسی فقط‌خواندنی به یک انبار داده استفاده کنید، حداقل مطمئن شوید که این یک استثنای مستند و محدود است و در طراحی کلی نقشی جزیفی ندارد.

چه زمانی داده‌ی تکرارشده به مشکل می‌خورد؟

وقتی دو نمایش از یک واقعیت هم‌زمان تغییر کنند و هر دو در سرویس‌های جدا ذخیره شوند. آن‌وقت باید منبع حقیقت را تعیین کنید و قانون حل تعارض را صریح بنویسید. اگر کسب‌وکار شما به سازگاری فوری نیاز دارد، تکرار ناهمگام انتخاب درستی نیست؛ باید به فراخوانی هم‌زمان یا یک سرویس مرجع واحد تکیه کنید.

مونولیت ماژولار چه زمانی به Microservices تبدیل می‌شود؟

سه نشانه‌ی روشن وجود دارد: تیم‌های متعدد که برای تغییر یک بخش ناچار به هماهنگی مداوم می‌شوند، مستقل‌سازی بخش‌هایی که رشد متفاوت دارند، و نیاز به مقیاس‌پذیری مستقل یا استقرار مستقل در یک ناحیه‌ی مشخص. اگر هیچ‌کدام را ندارید، تبدیل زودهنگام فقط هزینه می‌سازد.

خطایابی در Microservices چگونه انجام می‌شود؟

با سه ابزار که با هم کار می‌کنند: لاگ ساختاریافته با شناسه‌ی همبستگی، متریک برای دیدن روند نرخ خطا و زمان پاسخ، و Trace توزیع‌شده برای دیدن مسیر درخواست بین سرویس‌ها. بدون این سه، عیب‌یابی یعنی حدس زدن از روی چندین سرور. ساخت این زیرساخت را به تعویق نیندازید؛ از اولین سرویس باید وجود داشته باشد.

بخش ۲۶نقشه‌ی راه

مرحله ۱ — بنیاد (هفته ۱ تا ۲)

  • شناخت دامنه و استخراج Bounded Context‌ها
  • نوشتن یک سند کوتاه که در آن برای هر زمینه مالک، داده و قرارداد مشخص باشد
  • آماده‌سازی زیرساخت پایه: مخزن Git، خط لوله‌ی CI، لاگ ساختاریافته، متریک و trace
  • ساخت اسکلت مشترک سرویس برای کاهش زمان راه‌اندازی تیم‌های بعدی

مرحله ۲ — یک سرویس واقعی (هفته ۳ تا ۵)

  • استخراج یک قابلیت کم‌ریسک از مونولیت با Strangler Fig
  • پیاده‌سازی کامل زنجیره‌ی تاب‌آوری: timeout، circuit breaker، bulkhead
  • راه‌اندازی داشبورد مشاهده‌پذیری و هشدار برای همان یک سرویس
  • افزودن تست قرارداد برای مرز سرویس

مرحله ۳ — پیام‌رسانی و دوام (هفته ۶ تا ۸)

  • راه‌اندازی صف پیام و تعریف قرارداد رویداد
  • پیاده‌سازی Outbox و مصرف‌کننده‌ی idempotent
  • اجرای یک جریان کامل با Saga و عملیات جبرانی
  • افزودن داشبورد مصرف پیام و هشدار برای پیام‌های دفن‌شده

مرحله ۴ — مقیاس‌پذیری و انتشار (هفته ۹ تا ۱۲)

  • استقرار خودکار با Canary و معیار توقف خودکار
  • تنظیم rate limit و page chunk در مرز سرویس
  • آزمون بار و شناسایی گلوگاه‌های شبکه
  • تمرین بازیابی از خرابی و مستندسازی نتیجه

مرحله ۵ — سازمان و استاندارد (هفته ۱۳ به بعد)

  • تعریف قرارداد تیمی: مالکیت سرویس، ساعت پاسخ‌گویی، مسیر ارتقا
  • کاتالوگ سرویس‌ها به‌همراه مستندات و مالک هر سرویس
  • بازبینی دوره‌ای معماری و حذف سرویس‌های بی‌مصرف
  • آموزش تیم‌ها در عیب‌یابی توزیع‌شده
جمع‌بندی

Microservices یعنی تبدیل مسئله‌ی کد به مسئله‌ی سازمان. ارزش آن از مرزهای روشن، تیم‌های مستقل و سرعت تغییر می‌آید، نه از تعداد سرویس‌ها. هزینه‌اش را هم باید پذیرفت: پیچیدگی عملیات، تأخیر شبکه، سختی عیب‌یابی و هزینه‌ی زیرساخت.

اگر این هزینه‌ها را نپذیرفته‌اید، Modular Monolith انتخاب درست‌تری است و هیچ اشکالی ندارد. اما اگر پذیرفته‌اید، باید آن را کامل انجام دهید: نیمی از راه میکروسرویس، بدترین حالت ممکن است، چون هزینه را پرداخت کرده‌اید اما هیچ سودی نبرده‌اید.

اگر قرار است امروز تصمیم بگیرید، با یک Modular Monolith شروع کنید، مرزها را از روز اول جدی بگیرید، مشاهده‌پذیری را کامل بسازید و اولین سرویس را فقط وقتی استخراج کنید که دلیل روشنی برای جدایی دارید. بقیه‌اش در پیش است.
