TLS و HTTPS؛ گواهی، Handshake و امنیت ترافیک

امروز HTTPS اختیاری نیست؛ پیش‌نیاز اعتماد و امنیت است. این مقاله از Handshake و گواهی دیجیتال تا TLS 1.3، HSTS و mTLS را مرور می‌کند و پیکربندی امن NGINX را نشان می‌دهد.

بخش ۱مقدمه

HTTPS همان HTTP است روی بستری رمزنگاری‌شده به‌نام TLS. TLS سه چیز می‌دهد: محرمانگی، یکپارچگی و احراز هویت سرور. بدون آن، هر گره‌ای در مسیر شبکه می‌تواند ترافیک را بخواند یا تغییر دهد.

در این مقاله Handshake، گواهی و CA، دریافت خودکار گواهی، پیکربندی امن NGINX و مباحث HSTS و mTLS.
Prerequisites Web Server و NGINX.

بخش ۲TLS چیست؟

تعریف TLS (Transport Layer Security) پروتکلی است که بین Client و Server یک کانال امن می‌سازد: تبادل کلید با رمزنگاری نامتقارن، سپس رمزنگاری متقارن داده‌ها، همراه با تأیید هویت سرور با گواهی.
نسخهویژگی کلیدی
TLS 1.2پایه‌ی رایج، دو Round-trip برای Handshake
TLS 1.3Handshake سریع‌تر (1-RTT، حتی 0-RTT) و Cipher Suiteهای امن‌تر
هرگز نسخه‌های SSLv3، TLS 1.0 و TLS 1.1 را غیرفعال کنید؛ امروز ناامن شناخته می‌شوند.

بخش ۳Handshake و گواهی

زنجیره‌ی اعتماد گواهی شما توسط یک CA امضا شده و مرورگر آن را با ریشه‌های اعتماد خود بررسی می‌کند؛ اگر زنجیره کامل یا دامنه مطابق نباشد، هشدار امنیتی ظاهر می‌شود.

بخش ۴گرفتن گواهی با ACME

# Let's Encrypt با certbot برای NGINX
sudo certbot --nginx -d example.com -d www.example.com

# تمدید خودکار (certbot یک تایمر systemd می‌سازد)
sudo systemctl list-timers | grep certbot
sudo certbot renew --dry-run

# گواهی Wildcard نیازمند Challenge نوع DNS است
sudo certbot certonly --manual --preferred-challenges dns \
  -d '*.example.com'
Expected Behavior گواهی در مسیر /etc/letsencrypt/live/... قرار می‌گیرد و هر ۶۰ تا ۹۰ روز خودکار تمدید می‌شود؛ دیگر نگران انقضای ناگهانی نخواهید بود.

بخش ۵پیکربندی امن NGINX

server {
    listen 80;
    server_name example.com;
    return 301 https://$host$request_uri;   # اجبار HTTPS
}

server {
    listen 443 ssl http2;
    server_name example.com;

    ssl_certificate     /etc/letsencrypt/live/example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/example.com/privkey.pem;

    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_ciphers ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256;
    ssl_prefer_server_ciphers off;
    ssl_session_cache shared:SSL:10m;
    ssl_session_timeout 1d;

    add_header Strict-Transport-Security "max-age=63072000; includeSubDomains; preload" always;
    add_header X-Content-Type-Options "nosniff" always;
    add_header X-Frame-Options "SAMEORIGIN" always;
    add_header Referrer-Policy "strict-origin-when-cross-origin" always;
}
Session Resumption با ssl_session_cache، Handshakeهای تکراری سریع‌تر می‌شوند و CPU کمتری مصرف می‌شود.

بخش ۶HSTS، OCSP و mTLS

مفهومکارکرد
HSTSمرورگر را مجبور می‌کند همیشه via HTTPS وصل شود
OCSP Staplingسرور وضعیت گواهی را ضمیمه می‌کند؛ تأخیر و privacy بهتر
mTLSاحراز هویت دوطرفه؛ مناسب ارتباط سرویس‌به‌سرویس
TLS Terminationشکستن TLS در NGINX و پروکسی HTTP به Backend داخلی
Passthroughانتقال ترافیک رمزنگاری‌شده تا Backend؛ مناسب L4
# OCSP Stapling
ssl_stapling on;
ssl_stapling_verify on;
ssl_trusted_certificate /etc/letsencrypt/live/example.com/chain.pem;
resolver 1.1.1.1 8.8.8.8 valid=300s;

# mTLS: اجبار گواهی کلاینت
ssl_client_certificate /etc/nginx/ca.crt;
ssl_verify_client on;
HSTS را با احتیاط اگر preload را اشتباه فعال کنید، بازگردانی آن دشوار است. ابتدا با مدت کوتاه تست کنید و مطمئن شوید همه‌ی زیر‌دامنه‌ها HTTPS دارند.

بخش ۷جمع‌بندی

AdvantagesDisadvantages
محرمانگی و یکپارچگی ترافیکهزینه‌ی CPU برای Handshake (با TLS 1.3 کم شده)
اعتماد کاربر و SEO بهترنیاز به مدیریت و تمدید گواهی
امکان HTTP/2 و HTTP/3پیکربندی اشتباه، امنیت را توهمی می‌کند
When to Useهمیشه. هر سرویس عمومی امروز باید HTTPS داشته باشد.
When NOT to Useفقط ترافیک داخلی کاملاً ایزوله که لایه‌ی دیگری از امنیت دارد — و حتی آنجا هم mTLS توصیه می‌شود.

TLS پایه‌ی امنیت وب است. با گواهی خودکار، TLS 1.3، HSTS و پیکربندی درست، می‌توانید با اطمینان سرویس‌هایتان را روی اینترنت منتشر کنید.
