NGINX؛ پرکاربردترین Reverse Proxy و Web Server

NGINX امروز لبه‌ی ورودی بیشتر سرویس‌های وب است: TLS Termination، سرو فایل ثابت، Reverse Proxy، Load Balancing، Caching و Rate Limiting. در این راهنما معماری آن، بلوک‌های nginx.conf، server، location و upstream، و پیکربندی Production را قدم‌به‌قدم می‌سازیم.

بخش ۱مقدمه و قابلیت‌ها

NGINX ابتدا به‌عنوان یک Web Server برای حل مشکل C10K (ده‌هزار اتصال همزمان) ساخته شد و امروز به یک لبه‌ی کامل تبدیل شده است. یک NGINX می‌تواند هم‌زمان چند نقش داشته باشد:

قابلیتDirective کلیدیکاربرد در Production
TLS Terminationssl_certificateرمزگشایی در لبه و ترافیک ساده‌تر داخلی
Reverse Proxyproxy_passرساندن درخواست به Backend
Load Balancingupstreamپخش بار بین نمونه‌ها
Static Filesroot / aliasسرو بهینه‌ی فایل
Cachingproxy_cacheکاهش بار Backend
Compressiongzipکاهش حجم پاسخ متنی
Rate Limitinglimit_reqمحافظت در برابر سوءاستفاده
Prerequisites Web Server چیست؟ و Reverse Proxy را پیش از این مقاله بخوانید.

بخش ۲معماری NGINX

Directiveمعنامقدار عملی
worker_processesتعداد Workerauto (برابر تعداد CPU Core)
worker_connectionsحداکثر اتصال هر Worker۱۰۲۴ تا ۱۰۲۴۰ بسته به حافظه

بخش ۳ساختار nginx.conf

worker_processes auto;

events {
    worker_connections 1024;
    use epoll;
    multi_accept on;
}

http {
    include       /etc/nginx/mime.types;
    default_type  application/octet-stream;

    sendfile        on;
    tcp_nopush      on;
    keepalive_timeout 65;

    gzip on;
    gzip_types text/plain text/css application/json application/javascript;

    include /etc/nginx/conf.d/*.conf;
}
Contextمعنا
mainتنظیمات سراسری مثل worker_processes
eventsمدیریت اتصال‌ها
httpتنظیمات مشترک HTTP و میزبان بلوک‌های server
serverیک Virtual Host (دامنه یا IP + Port)
locationمسیر خاص درون یک server
Production Note پیکربندی را همیشه به بخش‌های کوچک در conf.d/ بشکنید و پس از هر تغییر nginx -t بزنید. Reload نرم با nginx -s reload بدون قطعی سرویس انجام می‌شود.

بخش ۴server block و Virtual Host

server {
    listen 80;
    server_name example.com www.example.com;

    return 301 https://$host$request_uri;   # ریدایرکت به HTTPS
}

server {
    listen 443 ssl http2;
    server_name example.com;

    root  /var/www/app;
    index index.html;

    # اولین server به‌عنوان default_server پاسخ نام ناشناس را می‌دهد
}
Directiveکار
listenپورت و آدرس گوش‌دادن
server_nameدامنه‌هایی که این بلوک میزبان آن‌هاست
rootپوشه‌ی ریشه برای مسیرها
return 301ریدایرکت دائمی (بهتر برای SEO)

بخش ۵location block و اولویت‌ها

انتخاب location قلب پیکربندی NGINX است. ترتیب اولویت دقیقاً این‌طور است: 

server {
    # ۱) تطبیق دقیق = بالاترین اولویت
    location = /health { return 200 "ok"; }

    # ۲) تطبیق پیشوندی ترجیحی ^~
    location ^~ /static/ {
        root /var/www/app;
        expires 30d;
    }

    # ۳) Regex با ~ (حساس) یا ~* (غیرحساس)
    location ~* \.(?:css|js|webp|woff2)$ {
        expires 30d;
        add_header Cache-Control "public, immutable";
    }

    # ۴) پیشوند عادی / — پایین‌ترین اولویت
    location / {
        proxy_pass http://backend;
    }
}
ترتیبنوعمثال
۱دقیق= /health
۲پیشوندی ترجیحی^~ /static/
۳Regex~* \.js$
۴پیشوندی/
Common Mistake فرض این‌که location / که اول نوشته شده اول اجرا می‌شود. NGINX بر اساس اولویت نوع تطبیق تصمیم می‌گیرد، نه ترتیب نگارش.

بخش ۶upstream و Load Balancing

upstream backend {
    least_conn;                 # الگوریتم توزیع
    keepalive 32;               # اتصال‌های Keep-Alive به Backend

    server 127.0.0.1:8080 weight=3 max_fails=3 fail_timeout=15s;
    server 127.0.0.1:8081 weight=2;
    server 127.0.0.1:8082 backup;
}
الگوریتمDirectiveمناسب برای
Round Robinپیش‌فرضنمونه‌های هم‌توان
Least Connectionsleast_connدرخواست‌های با زمان متغیر
IP Haship_hashSticky Session ساده
Weightedweight=Nسخت‌افزار ناهمگون
Randomrandomتوزیع تصادفی با بار کم
پارامترمعنا
max_failsتعداد خطا پیش از علامت‌زدن گره به‌عنوان خراب
fail_timeoutمدت خارج بودن گره از گردش
backupگره‌ی پشتیبان که فقط در نبود گره‌های اصلی استفاده می‌شود
Health Check نسخه‌ی Open Source NGINX Active Health Check ندارد و به‌جای آن از max_fails و fail_timeout (Passive) استفاده می‌کند. برای Active Health Check به NGINX Plus یا یک Load Balancer مجزا نیاز دارید.

بخش ۷proxy_pass و هدرها

location /api/ {
    proxy_pass http://backend;

    proxy_http_version 1.1;
    proxy_set_header Connection "";                 # حفظ Keep-Alive

    proxy_set_header Host              $host;
    proxy_set_header X-Real-IP         $remote_addr;
    proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Forwarded-Host  $host;

    proxy_connect_timeout 5s;
    proxy_send_timeout    30s;
    proxy_read_timeout    30s;
}
Directiveکارخطای رایج
proxy_passآدرس Backendاسلش انتهایی که مسیر را عوض می‌کند
Hostنگه‌داشتن دامنه‌ی اصلینبود آن باعث خطای Virtual Host در Backend
X-Forwarded-ForIP واقعی کاربراعتماد کورکورانه به آن
proxy_read_timeoutحد انتظار برای پاسخمقدار پیش‌فرض ۶۰ ثانیه برای API کند
تفاوت proxy_pass با و بدون اسلش proxy_pass http://backend/; پیشوند /api/ را حذف می‌کند، اما proxy_pass http://backend; مسیر کامل را نگه می‌دارد. این تفاوت منبع بسیاری از خطاهای ۴۰۴ است.

بخش ۸TLS و HTTPS

server {
    listen 443 ssl http2;
    server_name api.example.com;

    ssl_certificate     /etc/letsencrypt/live/api.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/api.example.com/privkey.pem;

    ssl_protocols       TLSv1.2 TLSv1.3;
    ssl_ciphers         HIGH:!aNULL:!MD5;
    ssl_prefer_server_ciphers on;

    ssl_session_cache   shared:SSL:10m;
    ssl_session_timeout 1d;

    add_header Strict-Transport-Security "max-age=63072000" always;

    location / { proxy_pass http://backend; }
}
Expected Behavior curl -I https://api.example.com باید HTTP/2 و strict-transport-security را نشان دهد. تست TLS: openssl s_client -connect api.example.com:443 -tls1_2.

بخش ۹Caching، Compression و Rate Limiting

# --- Caching پاسخ Backend ---
proxy_cache_path /var/cache/nginx levels=1:2 keys_zone=api_cache:10m
                 max_size=1g inactive=60m use_temp_path=off;

location /api/public/ {
    proxy_cache api_cache;
    proxy_cache_valid 200 302 10m;
    proxy_cache_valid 404 1m;
    proxy_cache_use_stale error timeout updating;
    add_header X-Cache-Status $upstream_cache_status;
    proxy_pass http://backend;
}

# --- Rate Limiting ---
limit_req_zone $binary_remote_addr zone=api_limit:10m rate=10r/s;

location /api/ {
    limit_req zone=api_limit burst=20 nodelay;
    limit_req_status 429;
    proxy_pass http://backend;
}
قابلیتDirectiveاثر
Cachingproxy_cacheکاهش بار Backend و Latency
Compressiongzip / gzip_typesکاهش حجم پاسخ متنی
Rate Limitinglimit_reqمحدودکردن نرخ درخواست هر IP
Connection Limitlimit_connمحدودکردن اتصال همزمان
Production Note پاسخ‌های شخصی‌سازی‌شده (مثل /api/me) را هرگز Cache نکنید. برای آن‌ها proxy_cache_bypass بر اساس Cookie یا Authorization بگذارید.

بخش ۱۰Logging و Monitoring

log_format main_ext '$remote_addr - $remote_user [$time_local] '
                    '"$request" $status $body_bytes_sent '
                    '"$http_referer" "$http_user_agent" '
                    'rt=$request_time uct=$upstream_connect_time '
                    'uht=$upstream_header_time urt=$upstream_response_time';

access_log /var/log/nginx/access.log main_ext;
error_log  /var/log/nginx/error.log warn;

# نقطه‌ی سلامت برای Load Balancer
location = /health {
    access_log off;
    return 200 "ok\n";
    add_header Content-Type text/plain;
}
فیلدمعنا
$request_timeکل زمان پاسخ از دید کلاینت
$upstream_response_timeزمان پاسخ Backend
$upstream_connect_timeزمان اتصال به Backend

بخش ۱۱Performance و Production

# تست پیکربندی پیش از reload
sudo nginx -t

# reload بدون قطعی
sudo nginx -s reload

# مشاهده‌ی وضعیت Workerها و اتصال‌ها
sudo systemctl status nginx
ss -lntp | grep nginx

# بنچمارک (روی سرویس تست، نه Production)
wrk -t4 -c200 -d30s https://staging.example.com/api/products
تنظیماثرملاحظه
worker_processes autoاستفاده‌ی کامل از CPUدر Container برای CPU Limit بررسی کنید
sendfile onسرو سریع‌تر فایلبرای فایل‌های بزرگ عالی است
keepalive در upstreamحذف هزینه‌ی اتصال مکرر به Backendهمراه با proxy_http_version 1.1
Cache روی دیسک/Tmpfsکاهش I/Oبرای محتوای پرتکرار مفید است
هیچ ادعای بدون اندازه‌گیری «NGINX همیشه سریع‌تر است» درست نیست. کارایی به Workload، پیکربندی، سخت‌افزار، شبکه، برنامه و دیتابیس بستگی دارد. همیشه روی سناریوی خودتان بنچمارک بگیرید.

بخش ۱۳مزایا، معایب و جمع‌بندی

AdvantagesDisadvantages
مصرف کم حافظه و پشتیبانی از اتصال‌های بسیارپیکربندی مبتنی بر فایل؛ برای کارهای داینامیک پیچیده محدود است
ابزار کامل لبه: TLS، Cache، Rate LimitActive Health Check در نسخه‌ی Open Source نیست
Logging و Monitoring غنی و قابل اندازه‌گیریمنطق پیچیده‌ی مسیریابی نیاز به ماژول یا ابزار مکمل دارد
Reload بدون قطعی سرویسنگه‌داری و پیکربندی درست نیازمند دانش واقعی است
When to Use تقریباً همیشه به‌عنوان لایه‌ی ورودی و Reverse Proxy.
When NOT to Use وقتی منطق مسیریابی بسیار پویا و وابسته به داده دارید، API Gateway اختصاصی مناسب‌تر است. برای ترافیک بسیار بالا در Layer 4 محض، HAProxy ابزار دقیق‌تری است.

NGINX ستون فقرات لبه‌ی Production است. اگر معماری آن را بفهمید و چند directive کلیدی را درست به‌کار ببرید، بخش بزرگی از مشکلات امنیت، کارایی و پاسخ‌گویی حل می‌شود.
