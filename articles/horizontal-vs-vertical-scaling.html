Horizontal در برابر Vertical Scaling

وقتی سرویس کند می‌شود، دو راه دارید: بزرگ‌ترکردن ماشین (Scale Up) یا افزودن ماشین‌های بیشتر (Scale Out). این دو فلسفه‌ی متفاوت‌اند و انتخاب درست، به معماری و محدودیت‌های شما بستگی دارد.

بخش ۱مقدمه

مقیاس‌پذیری یعنی توان افزودن ظرفیت همراه با رشد بار. دو راه‌برد اصلی وجود دارد و هرکدام محدودیت‌های خودش را دارد. انتخاب درست، پیش از بحران باید انجام شود، نه در لحظه‌ی افزایش ترافیک.

در این مقاله تفاوت Scale Up و Scale Out، طراحی Stateless، مدیریت Session، مقیاس‌پذیری دیتابیس و Autoscaling.
Prerequisites Load Balancing و High Availability.

بخش ۲دو محور مقیاس‌پذیری

معیارVertical (Scale Up)Horizontal (Scale Out)
روشافزودن CPU/RAM به یک ماشینافزودن ماشین‌های بیشتر
سقفسخت‌افزار محدود استتقریباً نامحدود
نگهدارینیازمند Restart و Downtimeبدون Downtime
هزینه‌ی اولیهساده و ارزان در شروعپیچیدگی معماری
ترکیب هوشمندانه در عمل بهترین راهبرد ترکیبی است: ابتدا عمودی تا سقف منطقی، سپس افقی برای ادامه‌ی رشد و تاب‌آوری.

بخش ۴Stateless و مدیریت Session

مقیاس‌پذیری افقی بدون Stateless بودن برنامه تقریباً ناممکن است. اگر وضعیت کاربر روی خود Process ذخیره شود، افزودن نسخه‌ی جدید بی‌فایده یا حتی خطرناک می‌شود.

وضعیتمحل درست
Session کاربرRedis یا دیتابیس مشترک
فایل‌های آپلودیObject Storage مشترک
Rate LimitRedis مشترک
Cache محلیمشترک یا Sticky با آگاهی
Lock و Queueسرویس مشترک
Sticky Session راه‌حل موقت است. اگر چند نسخه دارید و State محلی دارید، حتماً Session را به منبع مشترک منتقل کنید؛ وگرنه Deploy یا خرابی یک نسخه، کاربر را بیرون می‌اندازد.

بخش ۵مقیاس‌پذیری دیتابیس

روشتوضیح
Index و Query Tuningاولین و کم‌هزینه‌ترین گام
Read Replicaتوزیع خواندن بین چند نسخه
Cachingکاهش بار با Redis
Shardingتقسیم داده بین چند دیتابیس
Connection Poolingکاهش هزینه‌ی اتصال (PgBouncer)
دیتابیس گلوگاه است اغلب برنامه‌ها را می‌توان افقی مقیاس داد، اما دیتابیس تک‌نقطه‌ای باقی می‌ماند. ابتدا با Index، Cache و Replica سراغش بروید و Sharding را آخرین گزینه بگذارید.

بخش ۶Autoscaling و جمع‌بندی

# نمونه‌ی Horizontal Pod Autoscaler در Kubernetes
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: api }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: api }
  minReplicas: 2
  maxReplicas: 20
  metrics:
    - type: Resource
      resource: { name: cpu, target: { type: Utilization, averageUtilization: 65 } }
Expected Behavior با افزایش بار، تعداد نسخه‌ها خودکار بیشتر می‌شود و با افت بار کم می‌شود؛ هزینه با نیاز هم‌راستا می‌شود.
AdvantagesDisadvantages
رشد بدون سقف و با افزونگینیاز به طراحی Stateless
Autoscaling و هزینه‌ی پویامدیریت پیچیده‌ی State و دیتابیس
Deploy بدون قطعینیاز به Observability قوی
When to Use Verticalپروژه‌های کوچک یا دیتابیس‌هایی که افقی‌کردنشان پرهزینه است.
When to Use Horizontalسرویس‌های Stateless با بار متغیر و نیاز به تاب‌آوری.

انتخاب بین Scale Up و Scale Out، یک تصمیم معماری است نه فقط عملیاتی. با طراحی Stateless و لایه‌بندی درست، مقیاس‌پذیری افقی می‌تواند رشد و پایداری را همزمان بدهد.
