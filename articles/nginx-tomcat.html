NGINX + Tomcat؛ چیدمان Production برای اپلیکیشن Java

الگوی استاندارد برای اپلیکیشن Java: NGINX در لبه برای TLS، فایل ثابت و Rate Limiting، و Tomcat در شبکه‌ی خصوصی برای اجرای منطق برنامه. در این مقاله پیکربندی کامل، هدرهای Forwarded، Timeout، Buffering و Connection Pool را می‌سازیم.

بخش ۱معماری کلی

بخش ۲پیکربندی NGINX

upstream tomcat {
    server 127.0.0.1:8080;
    keepalive 32;
}

server {
    listen 443 ssl http2;
    server_name app.example.com;

    ssl_certificate     /etc/letsencrypt/live/app.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/app.example.com/privkey.pem;
    ssl_protocols       TLSv1.2 TLSv1.3;

    location /static/ {
        root /var/www/app;
        expires 30d;
    }

    location / {
        proxy_pass http://tomcat;
        proxy_http_version 1.1;
        proxy_set_header Connection "";

        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Forwarded-Host  $host;
    }
}
Expected Behavior /static/* بدون Tomcat پاسخ می‌گیرد و /* با هدرهای Forwarded به Tomcat می‌رسد. بدون این هدرها، اپلیکیشن IP واقعی و Scheme را اشتباه می‌بیند و ممکن است Redirect اشتباه بزند.

بخش ۳پیکربندی Tomcat

<!-- server.xml : فقط روی شبکه‌ی داخلی گوش بده -->
<Connector port="8080" protocol="HTTP/1.1"
           address="127.0.0.1"
           connectionTimeout="20000"
           maxThreads="200" acceptCount="100" />

<!-- RemoteIpValve : خواندن X-Forwarded-* -->
<Valve className="org.apache.catalina.valves.RemoteIpValve"
       remoteIpHeader="X-Forwarded-For"
       protocolHeader="X-Forwarded-Proto"
       internalProxies="127\.0\.0\.1" />
تنظیمچرا
address="127.0.0.1"Tomcat از بیرون دیده نشود
RemoteIpValveIP و Scheme واقعی کاربر
maxThreadsهماهنگ با ظرفیت Connection Pool
Production Note internalProxies را به IP همان NGINX محدود کنید؛ در غیر این صورت هر کلاینتی می‌تواند هدر X-Forwarded-For جعل کند.

بخش ۴Timeout، Buffering و Compression

location / {
    proxy_pass http://tomcat;

    proxy_connect_timeout 5s;
    proxy_send_timeout    30s;
    proxy_read_timeout    30s;

    proxy_buffering on;
    proxy_buffers 8 16k;
    proxy_buffer_size 16k;

    gzip on;
    gzip_types text/plain text/css application/json application/javascript;
    gzip_min_length 1024;
}
Directiveاثرملاحظه
proxy_read_timeoutحد انتظار پاسخبه‌درستی با کندی Backend تنظیم شود
proxy_bufferingآزادکردن سریع Threadبرای SSE/Streaming خاموش شود
gzipکاهش حجمروی محتوای از قبل فشرده بی‌اثر است

بخش ۵Connection Pool و Health Check

<!-- context.xml : Connection Pool -->
<Resource name="jdbc/appdb" auth="Container" type="javax.sql.DataSource"
          maxTotal="50" maxIdle="10" maxWaitMillis="10000"
          url="jdbc:postgresql://db.internal:5432/app"
          username="${DB_USER}" password="${DB_PASSWORD}" />
location = /health {
    access_log off;
    proxy_pass http://tomcat/health;   # یا return 200 "ok"
}
هماهنگی اعداد اگر maxThreads=200 و maxTotal=50 باشد، در بار زیاد درخواست‌ها در انتظار Connection می‌مانند. نسبت متعادل معمولاً ۵ تا ۱۰ Thread به ازای هر Connection است.
