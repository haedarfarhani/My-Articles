بخش ۱مقدمه: چرا پروژه‌ها بدون معماری فرو می‌پاشند؟

یک پروژه‌ی فروشگاهی را تصور کنید که با یک Controller ساده شروع شده است: 

Version 1 — شروع کار

Controller
   │
   └──→ Database

کد کار می‌کند، تیم خوشحال است و نسخه‌های اولیه سریع تحویل داده می‌شوند. اما بعد از چند ماه، سیستم رشد می‌کند: 

Version 2 — بعد از رشد

Controller
   │
   ├──→ Business Logic
   │
   ├──→ Database
   │
   ├──→ Payment Gateway
   │
   └──→ Email / SMS Services

حالا همان Controller هم قیمت محاسبه می‌کند، هم موجودی را چک می‌کند، هم پرداخت را ثبت می‌کند، هم ایمیل می‌فرستد و هم پاسخ HTTP می‌سازد. نتیجه‌ی این رشدِ بدون مرز، پنج مشکل کلاسیک است:

  • وابستگی زیاد (High Coupling): یک تغییر کوچک در قیمت‌گذاری، کل Controller را می‌شکند.
  • تغییر سخت: افزودن درگاه پرداخت دوم یعنی بازنویسی مسیری که ماه‌ها بدون تغییر مانده بود.
  • تست دشوار: برای تست یک قانون تخفیف مجبورید Database و درگاه پرداخت را بالا بیاورید.
  • نگهداری سخت: هیچ‌کس جرأت نمی‌کند فایل ۲۰۰۰ خطی را دست بزند؛ تغییرات با ترس انجام می‌شوند.
  • توسعه‌ی کند: ورود یک توسعه‌دهنده‌ی جدید هفته‌ها طول می‌کشد چون همه‌چیز به همه‌چیز وصل است.
ریشه‌ی مشکل ریشه‌ی این دردها «کد بد» نیست؛ نبود مرز (Boundary) است. وقتی مشخص نیست کجا تصمیم تجاری گرفته می‌شود و کجا جزئیات فنی، همه‌چیز با هم قاطی می‌شود. Clean Architecture برای همین به وجود آمد: برای کشیدن مرزهای شفاف بین تصمیم‌های پایدار و جزئیات فرار.

بخش ۲تاریخچه و دلیل ایجاد

Clean Architecture را Robert C. Martin (ملقب به Uncle Bob) در سال‌های ۲۰۱۲ تا ۲۰۱۴ معرفی کرد؛ مقاله‌ی کلیدی او با عنوان «Clean Architecture» در The Clean Coder (2011) و سپس در blog.cleancoder.com منتشر شد و کتاب Clean Architecture (2017) آن را به‌طور کامل بسط داد.

او با مشاهده‌ی چندین معماری قدیمی به این نتیجه رسید که نقطه‌ی مشترک همه‌ی آن‌ها یک چیز است:

ایده‌ی مشترک همه‌ی معماری‌های خوب جداسازی سطوح لایه‌بندی (Separation of Concerns) و کنترل وابستگی‌ها. Clean Architecture فقط نسخه‌ی تکمیل‌شده و نام‌گذاری‌شده‌ی همین ایده است؛ نه اختراع از صفر.
معماریزمانچه چیزی مشکل داشت؟
Monolithic Layeredدهه‌ی ۱۹۹۰لایه‌ها با هم درگیر بودند؛ افزودن یک UI جدید کل سیستم را می‌لرزاند
MVCدهه‌ی ۲۰۰۰Controller چاق می‌شد؛ Business Logic به View یا Controller نشت می‌کرد
Layered N-Tier۲۰۰۵–۲۰۱۰لایه‌ی Domain وابستگی به Infrastructure پیدا می‌کرد (وابستگی معکوس)
Onion / Hexagonal۲۰۰۵–۲۰۱۲خوب بودند اما توصیف استاندارد یکپارچه‌ای نداشتند

جامعه‌ی Agile و TDD (به‌ویژه پروژه‌های Test-First) بزرگ‌ترین محرک محبوبیت Clean Architecture بودند: وقتی می‌خواهید هر تغییر را با تست پوشش دهید، بدون مرزِ وابستگی، تست‌ها کند و شکننده می‌شوند.

نکته‌ی تاریخی Martin ایده‌هایش را از Hexagonal Architecture (Alistair Cockburn، ۲۰۰۵)، Onion Architecture (Jeffrey Palermo، ۲۰۰۸) و DCI وام گرفت؛ و تأکید کرد: «من چیز جدیدی اختراع نکردم، فقط یک شکل از ایده‌های قدیمی کشیدم.»

بخش ۳Clean Architecture چیست؟ (تعریف دقیق)

تعریف رسمی Clean Architecture یک روش سازمان‌دهی کد است که در آن سیستم به لایه‌های متحدالمرکز تقسیم می‌شود، قوانین کسب‌وکار (Business Rules) در مرکز قرار می‌گیرند و تمام جزئیات فنی (UI، Database، Framework) در لایه‌های بیرونی می‌نشینند؛ به‌طوری‌که وابستگی‌ها همیشه به سمت داخل جریان دارند (Dependency Rule).

برای روشن شدن مرز تعریف، ببینیم چه چیزی هست و چه چیزی نیست:

✅ Clean Architecture هست…❌ Clean Architecture نیست…
یک روش سازمان‌دهی ساختار سیستم و کشیدن مرز بین لایه‌هایک Framework (مثل Spring یا Django) نیست
یک چارچوب فکری برای جهت‌دهی به وابستگی‌هایک Library یا پکیج قابل نصب نیست
مجموعه‌ای از اصول و قواعد طراحی (چیدمان لایه، جهت وابستگی، مرزها)یک Design Pattern (مثل Strategy یا Factory) نیست
به پوشه‌ها و ماژول‌ها شکل می‌دهد اما به فریم‌ورک وابسته نیستقانون مقدسِ بدون استثنا نیست؛ انعطاف دارد
رایج‌ترین سوءتفاهم خیلی‌ها فکر می‌کنند Clean Architecture یعنی «ساختن ۶ پوشه‌ی Entity/UseCase/Repository/…». این نتیجه‌ی ظاهری آن است، نه خودِ معماری. اگر مرز و جهت وابستگی درست رعایت شود، حتی با ۳ پوشه هم معماری تمیز دارید؛ و اگر رعایت نشود، با ۲۰ پوشه هم فقط آشوب مرتب‌شده دارید.

بخش ۴مشکل قبل از استفاده: سیستم فروشگاه بدون معماری

یک سیستم فروشگاهی با موجودیت‌های User، Product، Order، Payment و Notification را در نظر بگیرید. نسخه‌ی بدون معماری معمولاً این شکلی است: 

public class OrderController {

    private final JdbcTemplate db = new JdbcTemplate("jdbc:mysql://...");

    public ResponseEntity<?> createOrder(@RequestBody OrderDto dto) {
        // ۱) قیمت‌گذاری (Business Rule)
        BigDecimal total = dto.items().stream()
                .map(i -> i.price().multiply(BigDecimal.valueOf(i.qty())))
                .reduce(BigDecimal.ZERO, BigDecimal::add);

        // ۲) ذخیره‌سازی (Database)
        db.update("INSERT INTO orders(total) VALUES(?)", total);

        // ۳) ارسال ایمیل (External Service)
        new SmtpClient("smtp.shop.com").send(dto.email(), "Order OK");

        // ۴) ساخت پاسخ HTTP (Web)
        return ResponseEntity.ok(Map.of("total", total));
    }
}

تحلیل این کد، چهار مشکل جدی را آشکار می‌کند:

  • مسئولیت‌های زیاد: یک متد هم‌زمان تاجر (قیمت)، DBA (ذخیره)، شبکه (ایمیل) و وب است.
  • Coupling بالا: به JdbcTemplate و SmtpClient مستقیماً وابسته است؛ تست بدون سرور ایمیل غیرممکن است.
  • تست سخت: برای اطمینان از صحت قیمت، باید کل Controller + DB + SMTP بالا بیاید.
  • تغییر سخت: جایگزینی SMTP با SendGrid یعنی تغییر همین فایل و بازبینی همه‌ی تست‌های مرتبط.
وابستگی‌های این کد (همه به سمت بیرون):

OrderController ──→ JdbcTemplate ──→ MySQL
       │
       ├──→ SmtpClient ──→ SMTP Server
       │
       └──→ ResponseEntity ──→ HTTP / Spring MVC

قوانین کسب‌وکار (قیمت و تخفیف) داخل Controller گیر افتاده‌اند.
نتیجه قوانین کسب‌وکار به جزئیات فنی وابسته شده‌اند. در Clean Architecture باید دقیقاً معکوس شود: جزئیات فنی به قوانین کسب‌وکار وابسته باشند، نه برعکس.

بخش ۵ایده اصلی: Dependency Rule

قلب Clean Architecture یک جمله بیشتر نیست:

Dependency Rule (قانون وابستگی) کدِ لایه‌ی بیرونی فقط می‌تواند به لایه‌ی داخلی وابسته باشد؛ هرگز برعکس. یعنی موجودیت‌های دامنه (Entity) هیچ وابستگی‌ای به Use Case، Database یا UI ندارند؛ هر Use Case هم فقط Entity را می‌شناسد؛ و فریم‌ورک/Database در بیرونی‌ترین لایه می‌نشیند و به همه‌ی لایه‌های داخلی وابسته است.

برای اجرای این قانون، سه ابزار عملی وجود دارد:

  • Abstraction: لایه‌ی داخلی یک interface تعریف می‌کند (مثل OrderRepository) و بیرون، پیاده‌سازی آن را می‌دهد.
  • Dependency Inversion (DIP): جهت وابستگی در زمان کامپایل و اجرا، همیشه به سمت داخل است.
  • Dependency Injection: شیء‌ی وابسته از بیرون تزریق می‌شود؛ لایه‌ی داخلی هرگز new نمی‌کند.
// لایه‌ی داخلی: فقط interface را می‌شناسد (نه JPA، نه JDBC)
public interface OrderRepository {
    void save(Order order);
    Optional<Order> findById(OrderId id);
}

// لایه‌ی بیرونی: پیاده‌سازی جزئیات فنی و وابستگی به داخل
public final class JpaOrderRepository implements OrderRepository {
    private final SpringDataOrderJpa jpa;

    public JpaOrderRepository(SpringDataOrderJpa jpa) {
        this.jpa = jpa;
    }

    @Override
    public void save(Order order) {
        jpa.save(OrderJpaEntity.from(order)); // ترجمه به مدل پایگاه‌داده
    }

    @Override
    public Optional<Order> findById(OrderId id) {
        return jpa.findById(id.value()).map(OrderJpaEntity::toDomain);
    }
}
آزمون ساده هر وقت خواستید بفهمید مرز درست است یا نه، این سؤال را بپرسید: «آیا می‌توانم لایه‌ی Database را با یک فایل متنی جایگزین کنم بدون اینکه یک خط از Entity و Use Case تغییر کند؟» اگر پاسخ نه است، وابستگی معکوس رخ داده است.

بخش ۶ساختار معماری: لایه‌ها

Clean Architecture معمولاً به چهار لایه‌ی متحدالمرکز تقسیم می‌شود (از داخل به بیرون):

لایه‌ی ۱ — Entities

  • مسئولیت: حمل قوانین کسب‌وکار پایدار و پیچیده‌ترین داده‌ها.
  • داخل آن: کلاس‌های Domain مثل Order، Product، Money و قواعدی مثل «سفارش منفی معتبر نیست».
  • نباید داخل آن باشد: هیچ وابستگی به Database، HTTP، UI یا Framework.

لایه‌ی ۲ — Use Cases (Application Layer)

  • مسئولیت: سناریوهای کاربردی خاص سیستم؛ «سیستم چه کاری باید انجام دهد».
  • داخل آن: CreateOrderUseCase، ApplyDiscountUseCase، RefundPaymentUseCase.
  • نباید داخل آن باشد: منطق UI، جزئیات SQL، دانش HTTP.

لایه‌ی ۳ — Interface Adapters

  • مسئولیت: ترجمه‌ی داده بین فرمت لایه‌های داخلی و فرمت بیرونی.
  • داخل آن: کنترلرها، Presenter، ViewModel و پیاده‌سازی Repository.
  • نباید داخل آن باشد: قواعد کسب‌وکار (باید به Use Case بسپارند).

لایه‌ی ۴ — Frameworks & Drivers (بیرونی‌ترین)

  • مسئولیت: جزئیات فریم‌ورکی و ابزارها: Web Framework، ORM، ابزارهای تست، اتصال DB.
  • داخل آن: Spring MVC، Room، Retrofit، ابزارهای DI، فایل‌های پیکربندی.
  • نباید داخل آن باشد: هیچ منطق کسب‌وکاری — فقط سیم‌کشی (Wiring).
مرز لایه‌ها در عمل مرز لایه‌ها می‌تواند یک ماژول Gradle/Maven، یک پکیج یا صرفاً یک قرارداد تیمی باشد. هرچه مرز فیزیکی‌تر باشد، نقض آن زودتر در کامپایل لو می‌رود — به همین دلیل معماری چندماژوله پیشنهاد می‌شود.

بخش ۷جریان داده (Data Flow)

مسیر یک درخواست «ثبت سفارش» در Clean Architecture این شکلی است:

مرحلهچه اتفاقی می‌افتد؟چه چیزی ممنوع است؟
۱. Controllerدرخواست خام را اعتبارسنجی و به مدل داخلی ترجمه می‌کندمنطق کسب‌وکار
۲. Use Caseسناریو را اجرا می‌کند: Entity را صدا می‌زند، خروجی را هماهنگ می‌کنددانستن نوع Database یا فریم‌ورک
۳. Entityقوانین واقعی (قیمت، موجودی، اعتبار) را اعمال می‌کنددانستن اینکه کجا فراخوانی می‌شود
۴. Gateway/Repositoryinterface فراخوانی می‌شود و پیاده‌سازی بیرونی کار را انجام می‌دهدبرگرداندن نوع خام ORM به لایه‌ی داخلی
۵. Presenterنتیجه را برای UI یا API پاسخ آماده می‌کندمنطق کسب‌وکار مخفی
نکته‌ی کلیدی در جریان داده جریان فراخوانی (Call) از بیرون به داخل است، اما جهت وابستگی کامپایلی هم به داخل است؛ چون لایه‌ی بیرونی interface‌های داخلی را پیاده‌سازی می‌کند. همین تقارن، رمز تست‌پذیری بالاست.

بخش ۹مثال عملی کامل: سیستم سفارش فروشگاه

دامنه (Domain) را مشخص می‌کنیم: موجودیت‌های Product، Order، Payment و یک سناریوی اصلی: ثبت سفارش با تخفیف و پرداخت.

Domain
├── Product     (موجودیت محصول: قیمت، موجودی)
├── Order       (سفارش: اقلام، وضعیت، جمع کل)
├── Payment     (پرداخت: مبلغ، وضعیت تأیید)
└── Rules
    ├── تخفیف بالای ۵۰۰ هزار تومان: ۱۰٪
    ├── سفارش نمی‌تواند خالی باشد
    └── پرداخت ناموفق = سفارش در وضعیت PENDING می‌ماند

گردش کار (Workflow) سناریو را با هم دنبال می‌کنیم:

1. کاربر سبد خرید را ثبت می‌کند (POST /orders)
2. CreateOrderUseCase اجرا می‌شود
3. Order ساخته می‌شود و قانون تخفیف روی آن اعمال می‌شود
4. موجودی Productها کم می‌شود (اگر کافی نباشد → خطا)
5. Order از طریق OrderRepository ذخیره می‌شود
6. PaymentGateway پرداخت را انجام می‌دهد
7. نتیجه به OrderResult ترجمه و به Controller برمی‌گردد
نکته‌ی طراحی توجه کنید مرز بین Policy (قواعد ثابت: تخفیف، اعتبار سفارش) و Mechanism (جزئیات: SQL، HTTP، Stripe) کجاست. Policy فقط در domain و application می‌نشیند؛ Mechanism فقط در infrastructure. این مرز، همان چیزی است که Clean Architecture را «تمیز» می‌کند.

بخش ۱۰پیاده‌سازی کد با Java 21

لایه‌ی Entity: موجودیت Order و قانون تخفیف

import java.math.BigDecimal;
import java.math.RoundingMode;
import java.util.List;
import java.util.Objects;

public final class Order {

    public static final BigDecimal DISCOUNT_THRESHOLD = new BigDecimal("500000");
    public static final BigDecimal DISCOUNT_RATE = new BigDecimal("0.10");

    private final String id;
    private final List<OrderItem> items;
    private final OrderStatus status;

    public Order(String id, List<OrderItem> items, OrderStatus status) {
        if (items == null || items.isEmpty()) {
            throw new IllegalArgumentException("Order must contain at least one item");
        }
        this.id = Objects.requireNonNull(id);
        this.items = List.copyOf(items);
        this.status = Objects.requireNonNull(status);
    }

    // قانون کسب‌وکار: جمع کل + تخفیف شرطی
    public BigDecimal total() {
        BigDecimal gross = items.stream()
                .map(OrderItem::lineTotal)
                .reduce(BigDecimal.ZERO, BigDecimal::add);

        if (gross.compareTo(DISCOUNT_THRESHOLD) >= 0) {
            BigDecimal discount = gross.multiply(DISCOUNT_RATE)
                    .setScale(2, RoundingMode.HALF_UP);
            return gross.subtract(discount);
        }
        return gross.setScale(2, RoundingMode.HALF_UP);
    }

    public String id() { return id; }
    public List<OrderItem> items() { return items; }
    public OrderStatus status() { return status; }
}

تحلیل خط به خط:

  • final class و فیلدهای final: Entity تغییرناپذیر (Immutable) است؛ وضعیت با withStatus جدید ساخته می‌شود.
  • List.copyOf: کپی تغییرناپذیر — Entity از بیرون قابل دستکاری نیست.
  • total(): قانون تخفیف دقیقاً همان چیزی است که ارزش تجاری دارد و بدون هیچ وابستگی به DB/UI اجرا می‌شود.
  • هیچ import از Spring/JDBC/HTTP وجود ندارد — همین یعنی تست‌پذیری کامل.

لایه‌ی Use Case: CreateOrderUseCase

import java.util.List;

public final class CreateOrderUseCase {

    private final OrderRepository orders;
    private final ProductRepository products;
    private final PaymentGateway paymentGateway;
    private final IdGenerator ids;

    public CreateOrderUseCase(OrderRepository orders,
                              ProductRepository products,
                              PaymentGateway paymentGateway,
                              IdGenerator ids) {
        this.orders = orders;
        this.products = products;
        this.paymentGateway = paymentGateway;
        this.ids = ids;
    }

    public OrderResult execute(CreateOrderCommand command) {
        // Arrange — اعتبارسنجی موجودی همه‌ی اقلام
        List<OrderItem> items = command.items().stream()
                .map(cmd -> {
                    Product product = products.findById(cmd.productId())
                            .orElseThrow(() -> new ProductNotFound(cmd.productId()));
                    product.assertStock(cmd.quantity());
                    return new OrderItem(product, cmd.quantity());
                })
                .toList();

        // Act — ساخت Entity و اعمال قوانین
        Order order = new Order(ids.nextId(), items, OrderStatus.PENDING);
        Payment payment = paymentGateway.charge(order.id(), order.total());

        Order confirmed = payment.isCompleted()
                ? new Order(order.id(), order.items(), OrderStatus.CONFIRMED)
                : order;

        orders.save(confirmed);

        // Assert — نتیجه‌ی قابل نمایش به لایه‌ی بیرونی
        return new OrderResult(confirmed.id(), confirmed.total(), confirmed.status());
    }
}

نکات مهم این Use Case:

  • Dependency به صورت interface تزریق می‌شود؛ کلاس هیچ‌کدام را new نمی‌کند.
  • ترکیب‌پذیری: دو interface داریم (OrderRepository و ProductRepository) که هر دو در لایه‌ی داخلی تعریف شده‌اند.
  • بدون Catch واقعی: خطاهای دامنه مثل ProductNotFound نوع‌دار هستند، نه رشته‌ی استثنای مبهم.

بخش ۱۷ارتباط با SOLID

Clean Architecture عملاً پیاده‌سازی عملی اصول SOLID است؛ مهم‌ترین آن‌ها برای این معماری:

SRP — Single Responsibility Principle

هر لایه و هر کلاس فقط یک دلیل برای تغییر دارد: Entity به تغییر قانون، Use Case به تغییر سناریو، Adapter به تغییر پروتکل.

OCP — Open/Closed Principle

Use Case برای افزودن درگاه پرداخت جدید بسته است؛ کافی است کلاس جدیدی interface موجود را پیاده‌سازی کند:

// Use Case تغییر نمی‌کند — فقط یک پیاده‌سازی جدید اضافه می‌شود
public interface PaymentGateway {
    Payment charge(OrderId orderId, Money amount);
}

public final class StripePaymentGateway implements PaymentGateway { /* ... */ }
public final class ZarinPalPaymentGateway implements PaymentGateway { /* ... */ }

DIP — Dependency Inversion Principle

این اصل، همان ستون فقرات Dependency Rule است: لایه‌ی داخلی interface می‌سازد، بیرون پیاده‌سازی می‌دهد.

// قبل از DIP — وابستگی مستقیم به بیرون (بد)
public class OrderService {
    private final MysqlOrderDao dao = new MysqlOrderDao();
}

// بعد از DIP — وابستگی به abstraction (درست)
public class OrderService {
    private final OrderRepository repository; // تزریق می‌شود

    public OrderService(OrderRepository repository) {
        this.repository = repository;
    }
}
رابطه‌ی سه‌گانه SRP محل هر تصمیم را مشخص می‌کند · OCP امکان افزودن را بدون تغییر می‌دهد · DIP جهت وابستگی را به داخل می‌چرخاند. هر سه باهم = Clean Architecture.

چرا تست‌ها سریع‌ترند؟ چون لایه‌ی دامنه به هیچ زیرساختی وابسته نیست، تست‌های آن بدون Thread، بدون Network و بدون Database اجرا می‌شوند؛ تست‌های ادغامی فقط مرز بیرونی را پوشش می‌دهند و تعدادشان کم است.

بخش ۲۲Performance

پاسخ کوتاه: نه — Clean Architecture خودِ Runtime را سریع‌تر نمی‌کند.

بعدتأثیر Clean Architecture
نگهداشت‌پذیری✅ بهبود چشمگیر
تست‌پذیری✅ بهبود چشمگیر
مقیاس‌پذیری سازمانی (تیم/کد)✅ بهبود چشمگیر
Throughput / Latency⬜ بی‌تأثیر (یا اندکی منفی به خاطر لایه‌ی ترجمه)
مصرف حافظه‌ی اجرا⬜ تقریباً بی‌تأثیر

تنها هزینه‌ی Performance واقعی، Translation Overhead است: تبدیل DTO به Command و فراخوانی چند لایه. در مقیاس اکثر اپلیکیشن‌ها این هزینه در حد میکروثانیه است و در برابر سودِ تغییر سریع و تست‌پذیری، ناچیز است.

کی باید نگران بود؟ در مسیرهای بسیار داغ (مثلاً پردازش ده‌ها هزار پیام در ثانیه) هر لایه‌ی اضافه حساب می‌شود. آن‌جا می‌توانید در مسیر Hot Path از Adapter سبک‌تر استفاده کنید — بدون شکستن مرزهای اصلی.

بخش ۲۳۲۴ سؤال مصاحبه شغلی

سطح Junior

سؤال ۱ — Clean Architecture چیست؟ یک روش سازمان‌دهی کد است که سیستم را به لایه‌های متحدالمرکز تقسیم می‌کند، قوانین کسب‌وکار را در مرکز می‌گذارد و جزئیات فنی مثل UI و Database را در بیرون قرار می‌دهد؛ با قانون اصلیِ «وابستگی همیشه به داخل».
سؤال ۲ — لایه‌های Clean Architecture را نام ببرید. از داخل به بیرون: Entities (موجودیت‌ها و قوانین پایدار)، Use Cases (سناریوها)، Interface Adapters (Controller/Presenter/Repository Impl) و Frameworks & Drivers (Web/DB/CLI).
سؤال ۳ — تفاوت Entity و DTO چیست؟ Entity موجودیت دامنه با رفتار و قوانین کسب‌وکار است و بین لایه‌ها سیر می‌کند؛ DTO یک حامل داده‌ی بدون رفتار برای انتقال بین لایه‌ها یا مرز HTTP است و نباید منطق داشته باشد.
سؤال ۴ — Use Case دقیقاً چه کار می‌کند؟ یک سناریوی کاربردی خاص را هماهنگ می‌کند: ورودی را می‌گیرد، موجودیت‌های دامنه را فراخوانی می‌کند، وابستگی‌ها (Repository/Gateway) را به کار می‌اندازد و خروجی سازگار با لایه‌ی بیرونی برمی‌گرداند.
سؤال ۵ — تفاوت Clean Architecture با MVC چیست؟ در MVC تفکیک بین Model/View/Controller است و منطق اغلب در Controller یا View نشت می‌کند؛ Clean Architecture مرز وابستگی تعریف می‌کند و قوانین کسب‌وکار در لایه‌ی داخلی و خالص می‌مانند — تأکید روی جهت وابستگی، نه فقط تفکیک وظیفه.
سؤال ۶ — Dependency Rule چیست؟ قانونی که می‌گوید هر لایه‌ی بیرونی فقط می‌تواند به لایه‌ی داخلی وابسته باشد؛ هیچ لایه‌ی داخلی نباید از لایه‌ی بیرونی چیزی بداند.
سؤال ۷ — Repository Pattern چه نقشی در این معماری دارد؟ Interface مربوط به دسترسی به داده را در لایه‌ی داخلی نگه می‌دارد و جزئیات ذخیره‌سازی (SQL، NoSQL، فایل) را در بیرون پیاده‌سازی می‌کند؛ بنابراین Use Case از نوع Database بی‌خبر می‌ماند.
سؤال ۸ — اگر Database عوض شود چه فایل‌هایی تغییر می‌کنند؟ فقط پیاده‌سازی‌های لایه‌ی Infrastructure (مثل JpaOrderRepository و پیکربندی اتصال). Use Case و Entity دست‌نخورده می‌مانند؛ این مهم‌ترین آزمون درستی معماری است.

سطح Mid

سؤال ۹ — تفاوت Clean با Onion Architecture؟ هر دو متحدالمرکزند. Onion صریحاً می‌گوید Domain Model در مرکز است و هیچ لایه‌ی بیرونی نباید از آن بیشتر بداند؛ Clean بر Use Case و قانون وابستگی تأکید دارد و نام‌گذاری چهارلایه‌ای مشخص‌تری دارد. پیاده‌سازی عملی اغلب همپوشانی زیادی دارند.
سؤال ۱۰ — تفاوت Clean با Hexagonal؟ Hexagonal هر ورودی/خروجی را Port و پیاده‌سازی را Adapter می‌نامد (Ports & Adapters) و مرکز، هسته‌ی دامنه است؛ Clean جهت وابستگی را با چهار لایه‌ی مشخص توصیف می‌کند. هر دو یک هدف دارند: حفاظت هسته از جزئیات.
سؤال ۱۱ — در چه پروژه‌ای اصلاً استفاده نمی‌کنید؟ پروژه‌های کوتاه‌عمر، Prototype، CRUD بدون قانون کسب‌وکار، اسکریپت‌ها و پنل‌های داخلی کوچک؛ چون هزینه‌ی مرزبندی از فایده‌اش بیشتر است.
سؤال ۱۲ — DIP و DI یکی هستند؟ خیر. DIP اصل طراحی است (لایه‌ی داخلی به abstraction وابسته شود)؛ DI تکنیک اجرایی آن است (شیء از بیرون تزریق شود). DIP بدون DI هم مثلاً با Factory قابل اجراست، اما DI رایج‌ترین راه است.
سؤال ۱۳ — چطور جهت وابستگی را در تیم تضمین می‌کنید؟ با ابزار: ArchUnit در جاوا، lint قواعد پکیج در Kotlin/TS، بررسی Import در Code Review و جداسازی فیزیکی با ماژول‌های جدا (Gradle/npm workspace) که نقض مرز را در کامپایل لو می‌دهد.
سؤال ۱۴ — اگر Use Case شروع به منطق خام کند چه می‌کنید؟ نشانه‌ی «上帝 Use Case» است. آن را به چند سناریوی کوچکتر می‌شکنیم، قوانین خالص را به Entity/Value Object منتقل می‌کنیم و هماهنگی‌های بین سناریوها را در لایه‌ی Application نگه می‌داریم.
سؤال ۱۵ — Entity و Value Object تفاوت دارند؟ بله. Entity هویت دارد (شماره‌ی سفارش) و با آن شناسایی می‌شود؛ Value Object فقط با مقدارش سنجیده می‌شود (مثل Money یا Address) و تغییرناپذیر است. هر دو در لایه‌ی Domain می‌نشینند.
سؤال ۱۶ — تست‌های این معماری چند لایه‌اند؟ سه سرعت: تست خالص دامنه (میلی‌ثانیه‌ای، بدون I/O)، تست Use Case با Fake درایورها، و تست ادغام برای Adapterها. معمولاً نسبت ۷۰/۲۰/۱۰ بین آن‌ها منطقی است.

سطح Senior

سؤال ۱۷ — Trade-offهای واقعی این معماری چیست؟ هزینه‌ی اولیه‌ی بیشتر (کلاس و لایه‌ی اضافی)، سربار Mapping، زمان آموزش تیم و ریسک مرزِ اشتباه در برابر فایدهی نگهداری بلندمدت، تست سریع و تعویض آسان زیرساخت. تصمیم درست به عمر پروژه و نرخ تغییر بستگی دارد، نه مد روز.
سؤال ۱۸ — چه زمانی Clean را به Hexagonal ترجیح می‌دهید و بالعکس؟ اگر مدل دامنه پیچیده و سناریوها محورند، Clean (Use Case محور) طبیعی‌تر است؛ اگر سیستم چند درایور هم‌زمان دارد (چند پروتکل ورودی/خروجی، سخت‌افزار جانبی)، Ports & Adapters شفاف‌تر است. خیلی از تیم‌ها ترکیبی از هر دو را عملاً استفاده می‌کنند.
سؤال ۱۹ — مهاجرت یک Legacy به Clean را چگونه انجام می‌دهید؟ به روش Strangler: ابتدا مرزِ جدید دور یک قابلیت پرتکرار می‌کشم، Use Case را از کد قدیمی بیرون می‌کشم، پشت interface می‌گذارم و بقیه را تدریجی جذب می‌کنم. Big Bang ممنوع — چون تست پوشش کافی ندارد.
سؤال ۲۰ — چطور به مدیر توضیح می‌دهید چرا زمان بیشتری لازم است؟ با عدد هزینه‌ی تغییر: «الان افزودن یک درگاه پرداخت ۳ روز کار دارد و ۲ باگ می‌دهد؛ با مرزبندی، یک روز و بدون دست‌زدن به بقیه.» معماری را به زبان ریسک کسب‌وکار ترجمه می‌کنم، نه به زبان تئوری.
سؤال ۲۱ — مدل‌سازی Eventها و Notification در این معماری؟ رویدادهای دامنه (OrderConfirmed) در لایه‌ی داخلی تعریف و توسط Use Case منتشر می‌شوند؛ Listenerهای بیرونی (ایمیل، تحلیل، انبار) به آن وصل‌اند. این‌جا وابستگی معکوس رعایت شده: بیرون به داخل وابسته است.
سؤال ۲۲ — اگر تیم لایه‌ها را درست نگه ندارد چه می‌کنید؟ سه ابزار: ۱) تست معماری خودکار (ArchUnit) در CI که نقض را رد می‌کند، ۲) جداسازی فیزیکی ماژول‌ها، ۳) ADR و جلسه‌ی کوتاه مرزبندی برای هر قابلیت جدید. فرهنگ بدون ابزار دوام نمی‌آورد.
سؤال ۲۳ — آیا Microservices لزوماً Clean Architecture است؟ خیر. هر سرویس می‌تواند لایه‌ای یا حتی مونولیتیک داخلی باشد. Clean داخل هر سرویس کاربرد دارد؛ مرز سرویس‌ها مسئله‌ی جدا (bounded context در DDD) است. ترکیب رایج: سرویس‌ها با مرز DDD و هر کدام با Clean داخلی.
سؤال ۲۴ — سنجه‌ی (Metric) موفقیت معماری چیست؟ زمان تغییر (Lead Time for Changes)، نرخ باگ پس از تغییر، زمان اجرای تست‌ها، درصد پوشش تست دامنه و هزینه‌ی onboarding توسعه‌دهنده‌ی جدید. اگر این اعداد بعد از مهاجرت بهتر نشوند، معماری فقط شکل گرفته، نه اصلاح شده است.

بخش ۲۴پرسش‌های متداول (FAQ)

۱. آیا Clean Architecture فقط برای پروژه‌های بزرگ است؟ نه، اما فایده‌ی اصلی‌اش در پروژه‌های بلندمدت و پر-تغییر است. پروژه‌ی کوچک هم می‌تواند از مرزهای ساده (دو پوشه‌ی domain/infrastructure) بهره ببرد.
۲. آیا حتماً باید چهار لایه داشته باشیم؟ خیر. چهار لایه، رسمی‌ترین شکل آن است. پروژه‌های کوچک با ۲–۳ لایه هم می‌توانند Dependency Rule را رعایت کنند.
۳. Clean Architecture همان MVC نیست؟ خیر. MVC یک الگوی UI است و تمرکزش تفکیک View از Controller است؛ Clean یک چیدمان کل سیستم است با قاعده‌ی جهت وابستگی. یک اپ می‌تواند هم MVC (در UI) و هم Clean (کلی) داشته باشد.
۴. با Kotlin یا C# هم می‌شود پیاده‌سازی کرد؟ بله. هر زبانی با Interface و DI. در Kotlin اندروید، در C# با ASP.NET Core و در TS با NestJS/Angular نمونه‌های رایج دارد.
۵. Use Case و Service فرقی دارند؟ اسم‌گذاری فرق دارد، مفهوم نه. «Use Case» تأکید می‌کند که کلاس، یک سناریوی مشخص کاربر را اجرا می‌کند؛ «Service» مبهم‌تر است و اغلب به چندعمله‌های بی‌مرز تبدیل می‌شود.
۶. کجا DTO بسازم؟ در لایه‌ی Interface Adapter (یا پکیج presentation/web). DTO برای عبور از مرز HTTP/UI است، نه برای حمل قواعد دامنه.
۷. Repository در کجای ساختار می‌نشیند؟ interface آن در لایه‌ی داخلی (domain/application) و پیاده‌سازی‌اش در infrastructure. این تفکیک، همان DIP است.
۸. Clean Architecture سرعت اجرا را کم می‌کند؟ در عمل تفاوت ناچیز است (چند لایه‌ی فراخوانی). آنچه واقعاً سرعت را بالا می‌برد، تست‌های سریع و استقرار مطمئن‌تر است.
۹. از Dependency Injection چه فریم‌ورکی استفاده کنم؟ Java: Spring یا Dagger · Kotlin/Android: Hilt یا Koin · C#: built-in DI · TS: Inversify یا سیستم native NestJS. خودِ معماری به فریم‌ورک خاصی وابسته نیست.
۱۰. اگر فقط یک نفر توسعه‌دهنده باشم چطور؟ حتی تک‌نفره، مرز domain/infrastructure کمک می‌کند تست‌ها را سریع نگه دارید و شش ماه بعد کد را سریع‌تر پیدا کنید؛ با این حال حجم لایه‌ها را متناسب نگه دارید.
۱۱. مستندسازی هم لازم است؟ بله — یک ADR کوتاه برای مرزها و یک نمودار لایه‌ها در README کافی است. کدِ خوب هم نیاز به توضیح تصمیم دارد.
۱۲. آیا Entity می‌تواند به دیتابیس وصل شود؟ خیر — به‌جز لایه‌ی Adapter که Entity را به ردیف DB ترجمه می‌کند. اگر Entity شما @Table بگیرد، مرز شکسته و با ORM کوپل شده‌اید.
۱۳. CQRS با Clean Architecture جور درمی‌آید؟ بله — CQRS جداسازی مسیر خواندن/نوشتن را در لایه‌ی Application اعمال می‌کند و با Use Case‌های جداگانه خوب کار می‌کند.
۱۴. تفاوت مرز (Boundary) با Layer چیست؟ Layer چیدمان فایل‌هاست؛ Boundary قراردادی است که مشخص می‌کند چه کسی چه چیزی را می‌داند. می‌توانید یک لایه‌ی واحد با چند مرز مختلف (چند Use Case) داشته باشید.
۱۵. برای شروع، اول چه چیزی را یاد بگیرم؟ اول SOLID و الگوی Repository، بعد Dependency Injection، سپس یک پروژه‌ی کوچک را دستی لایه‌بندی کنید؛ خواندن کتاب Clean Architecture اثر Uncle Bob مرحله‌ی تثبیت است.

جمع‌بندی نهایی

Clean Architecture یک فریم‌ورک نیست که نصب کنید؛ یک شیوه‌ی فکر کردن درباره‌ی مرزها است. مسیر طلایی این مقاله را مرور کنید: Problem → Why Created → Concept → Structure → Data Flow → Implementation → Real Project → Advantages → Disadvantages → When To/NOT To → Comparison → Interview.

پیام نهایی هدف، حفظ کردن چهار نام لایه نیست؛ هدف این است که برای مسئله‌ی واقعی، معماری مناسب انتخاب کنید. گاهی Clean درست است، گاهی یک MVC ساده. معمار خوب کسی است که Trade-off را می‌فهمد، نه کسی که مُدها را کپی می‌کند.
