بخش ۱چه فرقی بین RxJava و RxAndroid دارد؟

RxJava و RxAndroid دو کتابخانه‌ی متوالی برای برنامه‌نویسی واکنش‌گرا (Reactive Programming) در اندروید و جاوا هستند. RxJava استاندارد و سازنده‌ی این الگوی کار است؛ RxAndroid هم‌چیزی جز سرویسی که سفارشی شده تا فعالیت‌های UI، Palette و بک‌اند را در سوییچ‌لاگ‌های صحیح اجرا کند.

۱.۱ چه‌هایی را می‌آموزیم

در این مقاله، اول از هم‌رسانی، سپس چارچوب‌ها، سپس Operatorها، Schedulers، Subjectها و در نهایت یکپارچه‌سازی اندرویدی می‌آورم. تمام نمونه‌کدها به کاتلین و هم‌چنین به جاوا نوشته شده‌اند تا هر دو مخاطب را در بر کند.

۱.۲ چرایی استفاده از Observable؟

وقتی قراره چندین مرحله از داده‌ها اعمال شود، چنین که یک «آسه» امری از بالا به پایین رد می‌شود، باید از observable استفاده کرد تا:

  • کد را از فراخانی متعقل (callback hell) دور سازد.
  • سربار متقابل، ترتیب، تاخیر و خرابی را کنترل کند.
  • ورودی‌ها و خروجی‌ها را به صورت یک جریان (stream) در نظر بگیرد.

بخش ۲Observable، Observer، Subscriber و Flowable

در RxJava، اصلی‌ترین مدل‌ها عبارت‌اند از Observable، Observer، Subscriber و Flowable. هر کدام در چه موقعیت مورد استفاده قرار می‌گیرند، ما اینجا بررسی می‌کنیم.

۲.۱ Observable و Observer

مختصرتر: Observable دورamide‌ می‌دهد و Observer آن را می‌گیرد. زمانی که داده‌ی جدیدی آمد، تابع onNext تماس می‌گیرد؛ در پایان از onComplete پیدا می‌شود و در صورت خرابی onError صدا زده می‌شود. 

// Kotlin — Observable با Observer
val observable = Observable.create<String> { emitter ->
    emitter.onNext("Kotlin")
    emitter.onNext("Java")
    emitter.onComplete()
}

observable.subscribe(
    { item -> println("گرفته: $item") },      // onNext
    { err -> println("خطا: $err") },          // onError
    { println("پایان") }                        // onComplete
)
// Java — همان را با Consumer و Consumer از rx.functions
Observable<String> observable = Observable.create(
    new Observable.OnSubscribe<String>() {
        @Override
        public void call(Subscriber<? super String> subscriber) {
            subscriber.onNext("Java");
            subscriber.onNext("Kotlin");
            subscriber.onCompleted();
        }
    }
);

observable.subscribe(
    new Action1<String>() {
        @Override
        public void call(String s) { System.out.println("گرفته: " + s); }
    },
    new Action1<Throwable>() {
        @Override
        public void call(Throwable t) { System.err.println("خطا: " + t); }
    },
    new Action0() { public void call() { System.out.println("پایان"); }
);

۲.۲ Subscriber (نسخه‌ی دو‌طرفه و وقف‌شده)

Subscriber از Observer می‌ترشد و کنترل‌های isUnsubscribed، onStart و setSubscription را به آن می‌دهد. این، سند حریمی برای Cancellation و Backpressure است. 

Observable<String> source = Observable.just("A", "B", "C");

Subscription sub = source.subscribe(
    { item -> println("گرفته: $item") },
    { err -> println("خطا: $err") }
);

// در هر لحظه میتوانیم اشتراک را لغو کنیم
// sub.unsubscribe()
نکته: استفاده از Subscription و فراخونی آن با CompositeDisposable.add در کد‌های اندرویدی، روش استاندارد برای cancellation به صورت گروه‌بندی شده است.

۲.۳ Flowable برای Backpressure

وقتی تعداد داده‌های تولید شده از آنچه که گیرنده می‌تواند پرسودی کند، بیشتر شود، Flowable به جای Observable انتخاب می‌شود. به Flowable Backpressure Support دارد: می‌تواند کمترین میزانِ داده‌ها را که گیرنده می‌خواهد را تنظیم کند و جلوگیری از ذبده شدن حافظه کند. 

Flowable<Long> flowable = Flowable.create(
    new FlowableOnSubscribe<Long>() {
        @Override
        public void subscribe(FlowableEmitter<Long> emitter) throws Exception {
            long i = 0;
            while (!emitter.isCancelled()) {
                emitter.onNext(i++);
                Thread.sleep(100); // تولید مکرر
            }
        }
    },
    BackpressureStrategy.BUFFER
);

Subscription sub = flowable
    .observeOn(Schedulers.io())
    .subscribe(
        { v -> println("مقرا: $v") },
        { err -> err.printStackTrace() }
    );
عمیق‌تر: Backpressure وقتی می‌خواهیم تولید داده‌ها تاخیر پیدا کند و گیرنده برای حفظ هم‌تناسب عمل کند، ممکن است از Flowable به همراه استراتژی‌هایی مانند BUFFER، DROP، LATEST و ERROR استفاده شود.

بخش ۳چارچوب هم‌رسانی: Single، Maybe، Completable و Observable

RxJava چهار نوع سینگلتور برای حالت‌های مختلف داده ارائه می‌دهد. یک رشته‌بان برای خروجی یک آیتم، یا واحد، یا نادری، أو Thu حسابی، می‌توانند به صورت جداگانه تکیه کنند.

نوعنمونه‌ی خروجیوقتی onComplete می‌آیدفرقی با Observable دارد؟
Observable۰ تا n آیتمسازه خاتمه می‌گیردغیراردضمیمی، می‌تواند خالی باشد
Singleدقیقاً یک آیتمشروع می‌شود نامه‌ی اتمامخروجی همیشه یک آیتم، خطا دریافت می‌شود
Maybeصفر تا یک آیتمیک بار خاتمه می‌یابدپوشش می‌دهد اگر داده وجود نداشته باشد
Completableهیچ آیتمیسازه‌ی کامل شدن می‌دهدفقط عوارض؛ ن�다وته‌ای خروجی

۳.۱ Single — یک پاسخ واحد

Single<User> userSingle = Single.create(emitter -> {
    emitter.onSuccess(fetchUserById(42));
    // یا emitter.onError(exception);
});

userSingle.subscribe(
    { user -> showDetail(user) },
    { err -> showError(err) }
)

۳.۲ Maybe — صفر یا یک آیتم

Maybe<User> maybeUser = Maybe.create(emitter -> {
    User u = findUser(42);
    if (u != null) emitter.onSuccess(u); else emitter.onComplete();
});

maybeUser.subscribe(
    { user -> showDetail(user) },
    { println("هیچ کار برای انجام نداریم") }
)

۳.۳ Completable — بدون خروجی

Completable completable = Completable.create(emitter -> {
    saveSettings(userId, prefs);
    emitter.onComplete();
});

completable.subscribe(
    { println("ذخیره‌ی فایل با موفقیت انجام شد") },
    { err -> println("خطا: $err") }
)
نکته انتخابی: اگر می‌شود از Single یا Maybe به جای Completable در حالتی استفاده کرد که خروجی فاقد‌دلیل‌اند؛ این جور تجزیه‌ی خطا مستقیم‌تر و اطمینان‌ورزی از جانب لینک‌ریزی‌گری‌پذیر می‌دهد.

بخش ۴Operatorهای اصلی: map، filter، take، drop، distinct

Operatorها تابعی هستند که با دریافت هر عنصر، آن را به شکل جدیدی_study نشان می‌دهند؛ یا شکل جمله‌ای از عناصر. در این بخش از Operatorهای بسیار پرکاربرد صحبت می‌شود.

۴.۱ map — تبدیل کردن

Observable<String> names = Observable.just("Ali", "Sara", "Reza");

names.map { name -> name.length }          // [3, 4, 4]
     .subscribe { println("طول: $it") }

۴.۲ filter — فیلتر کردن

Observable<Integer> numbers = Observable.range(1, 10);

numbers.filter { it % 2 == 0 }             // 2، 4، 6، 8، 10
      .subscribe { println("پرداختی: $it") }

۴.۳ take / drop / skip

Observable.range(1, 20)
    .take(5)                                 // ۱ تا ۵
    .subscribe { println("take: $it") }

Observable.range(1, 20)
    .skip(10)                                // ۱۱ تا ۲۰
    .subscribe { println("skip: $it") }

Observable.range(1, 20)
    .dropWhile { it <= 10 }                  // ۱۱ تا ۲۰
    .subscribe { println("dropWhile: $it") }

۴.۴ distinct / elementAt

Observable.just(1, 2, 1, 3, 2, 4)
    .distinct()                              // 1، 2، 3، 4
    .subscribe { println("distinct: $it") }

Observable.range(1, 10)
    .elementAt(3)                            // ۴ (یونکد‌های ۰-አbased)
    .subscribe { println("elementAt: $it") }

۴.۵ first / last

Observable.just(4, 7, 2, 9)
    .first()                                 // ۴
    .last()                                  // ۹
    .subscribe { println("آخرین: $it") }

بخش ۵زنجیره‌سازی و تبدیل کردن آیتم‌ها: flatMap، concatMap، switchMap

وقتی هر انتخاب یک Observable دیگر را تولید می‌کند (یعنی ما یک ساخت‌زنجیره‌ای داخل رشته‌بان داریم)، از Operatorهای flatMap، concatMap و switchMap استفاده می‌شود. در اینجا تفاوت کلیدی بین این‌ها است.

Operatorترتیب پردازشرفرانس خارجیدرباره‌یWaveform
flatMapاغلب سازگار (non-deterministic)همه‌چیز برابر استپس از اتمام، تمام خود را داخلی را صدا می‌زند
concatMapترتیب ردیکاً ثابتسرویس‌های با گارانتیترتیب خروجی با ترتیب ورودی مطابق است
switchMapمهم‌ترین (latest) تغییرنزدیک‌تر به بروزترین Sourseساخته‌ی vibration، روی‌ی آن حذف می‌شوند

۵.۱ flatMap — همزمان کردن چند خروجی

// هر کامنت یک درخواست جداگانه را برگردانده
Observable<Comment> comments = fetchPostComments(postId);

comments.flatMap { comment ->
    fetchLikeCount(comment.id)
         .map { likeCount -> comment.copy(likeCount = likeCount) }
}

۵.۲ concatMap — حفظ ترتیب

// استراتژی‌های شبیه abstraction
Observable.just("A", "B", "C")
    .concatMap { item ->
        heavyWork(item)          // اجرا به ترتیب، خروجی هم ترتیب
    }

۵.۳ switchMap — استفاده از آخرین ورودی

// جستجوی لحظه‌ای: هنگامی که کاربر تایپ می‌کرد، رشته‌ای که در حال آن‌حال تایپ می‌شد حذف می‌شد
searchTextField
    .debounce(300, TimeUnit.MILLISECONDS)
    .observeOn(Schedulers.computation())
    .switchMap { query ->
        searchService.search(query)       // هر تایپی جدید، جریان پیشین را رها می‌کند
    }
نکته: در جستجوهای موبایل، switchMap که برای اسکن‌سازها طراحی شده است، چون از لزوم بی‌نیاز بودن و غیر‌فعال‌کردن درخواست‌های قبلی جلوگیری می‌کند.

بخش ۶جمع‌بندی و کاهش داده‌ها: reduce، fold، collect

وقتی می‌خواهیم چندین عنصر را به یک آیتم واحد کاهش دهیم، از این Operatorها استفاده می‌شود.

۶.۱ reduce — خروجی یک آیتم واحد

Observable.just(1, 2, 3, 4, 5)
    .reduce { acc, item -> acc + item }      // ۱۵
    .subscribe { println("مجموع: $it") }

۶.۲ scan — خروجی هر مرحله‌ای

Observable.range(1, 5)
    .scan { acc, item -> acc + item }        // ۱، ۳، ۶، ۱۰، ۱۵
    .subscribe { println("مجموع تا کنار: $it") }

۶.۳ collect / collectInto — به‌راحتی جمع‌آوری

Observable.just(1, 2, 3, 4, 5)
    .collect(
        { ArrayList<Int>() },                 // مقدار شروع
        { list, item -> list.add(item) }      // عملکرد کاهش
    )
    .subscribe { list -> println("لیست نهایی: $list") }

۶.۴ grouping کرد (toList / groupBy)

Observable.just(1, 2, 3, 4, 5)
    .toList()                                // [1, 2, 3, 4, 5]
    .subscribe { println("همه‌ی اعداد: $it") }

Observable.just("apple", "banana", "apricot", "cherry")
    .groupBy { it[0] }                       // گروه‌بندی بر پایه‌ی حرف اول
    .subscribe { group ->
        group.toList().subscribe { items ->
            println("گروه ${group.key}: $items")
        }
    }

بخش ۷تحكم در زمان و سرعت: throttleFirst، debounce، delay

وقتیکه یک ورودی سریع‌تر از خروجی‌گذاری می‌رود (یعنی کاربر در یک کادر جستجوی سریع تایپ می‌کند، یا سوییچ‌لاگ‌ها سریع‌تر از یکدیگر فراخوانی می‌شوند)، از Operatorهای کنترل‌دار برای برطرف کردن این مشکل استفاده می‌شود.

Operatorرفرانس خارجیوقتی فعال می‌شودکاربرد
throttleFirstوضوح تمام زمانپیوند هر بازرسیمحدود کردن واردات هر N واحد زمان
debounceتایپ اولین ورودی لغو امکانتوقف یا وفاداریدر جستجوی موبایل، پس از تایپ، یک دوره پایا
delayتأخیر در فراخوانیتاخیر قابل تنظیمتأخیر دادن به یک جریان
sampleنمونه‌برداری از جریانهر زمان ثابتگرفتن آخرین پیش‌آمد در یک بازه زمانی

۷.۱ debounce برای جستجو

searchTextField
    .debounce(300, TimeUnit.MILLISECONDS)
    .observeOn(Schedulers.computation())
    .map { query -> query.trim().uppercase() }
    .filter { it.isNotEmpty() }
    .switchMap { query ->
        searchService.search(query)
    }

۷.۲ throttleFirst برای دکمه‌یouble-safe

// دکمه‌ی بلاگ پست: هیچ‌کدام از این‌ها نمی‌تواند به‌راحتی لغو شود
sendButton.clicks()
    .throttleFirst(500, TimeUnit.MILLISECONDS)   // تایپ‌های سریع را نادیده می‌گیرد
    .subscribe { submitForm() }

۷.۳ delay — تأخیر کامل از اول

Observable.timer(2, TimeUnit.SECONDS)
    .flatMap { fetchDashboardData() }
    .subscribe { showDashboard(it) }

بخش ۸Schedulers: newThread، computation، io، mainThread

Scheduler در RxJava جایی است که جریان از دسته‌ای به دسته‌ی دیگر منتقل می‌شود؛ به عنوان مثال، بک‌اند روی Schedulers.io() و UI روی AndroidSchedulers.mainThread().

Schedulerاستفاده می‌شود در کجاتقسیم‌بندی به.poolنوع کار
Schedulers.newThreadدرخواست‌های آرام‌تر ماژول‌های جداگانهیک ترد برای هر اشتراکعملیات سنگین، غیرهمزمان
Schedulers.computationحساب‌های سنگین، پردازش‌های پیچیدهتقریباً برابر تعداد هسته‌هاکارهای غیرمبهم
Schedulers.ioآپلود، دریافت، پایگاه‌داده‌ها، فایل‌هاpool بزرگخوانش و نوشتن
Schedulers.trampolineترتیب دوره‌ای (اختیاری)در همین threadاجرای در زمان فعلی
AndroidSchedulers.mainThreadUI، تازه‌سازی، انیمیشن‌های آرام‌تر، UIروی سوییچ‌لاگ اصلی اندرویدعمل‌های UI

۸.۱ استفاده از Schedulers در کد اندرویدی

apiService
    .getUser(id)
    .subscribeOn(Schedulers.io())              // از io، بک‌اند
    .observeOn(AndroidSchedulers.mainThread()) // به UI، UI
    .subscribe(
        { user -> updateUI(user) },
        { err -> showError(err) }
    )

۸.۲ ترکیب Scheduler‌ها

dataService
    .loadList()
    .subscribeOn(Schedulers.io())
    .observeOn(Schedulers.computation())
    .map { processData(it) }                  // پردازش سنگین درcomputation
    .observeOn(AndroidSchedulers.mainThread())
    .subscribe(
        { displayList(it) },
        { showError(it) }
    )
عمیق‌تر: subscribeOn در چند نقطه‌ی متوالی اگر در یک به‌هم‌ریختگی از subscribeOn‌ها قرار دید، فقط اولینsubscription حیاتی است؛ بقیه اطمینان‌ها از تنظیمات انباشته‌ی Scheduler‌اساس (exception) استفاده می‌کنند. بهتر است در یک دستور واحد، در سمت چپ، از Scheduler‌های مورد نیاز استفاده کنید.

بخش ۹سامانه‌ی خطا و بازیابی: onErrorReturn، retry، onErrorResumeNext

اشکال‌زدایی (Error Handling) یکی از اهمیت‌ترین بخش‌های برنامه‌نویسی واکنش‌گراست؛ چون در میکروسرویس‌ها و شبکه‌ها، خطاها غیرقابل‌پیش‌بینی هستند و باید به درستی بازیابی شوند.

۹.۱ onErrorReturn — برگرداندن یک آیتم جایگزین

apiService
    .getUser(id)
    .onErrorReturn { User.getDefault() }     // در صورت خطا، یک کاربر پیش‌فرض برگردان
    .observeOn(AndroidSchedulers.mainThread())
    .subscribe(
        { showUser(it) },
        { /* این تابع اجرا نمی‌شود */ }
    )

۹.۲ retry — دوباره‌ی تلاش در صورت خطا

apiService
    .getData()
    .retry(۳)                                // تا ۳ بار دوباره سعی شود
    .subscribe(
        { showData(it) },
        { err -> println("پس از ۳ تکرار، خطا: $err") }
    )

۹.۳ onErrorResumeNext — جریان جایگزین

apiService
    .getFeed()
    .onErrorResumeNext(Observable.empty())   // در صورت خطا، خروجی خالی برمی‌گردد
    .subscribe(
        { displayFeed(it) },
        { println("خطا پردازش شد") }
    )

۹.۴ onExceptionResumeNext — خطا‌های استثنایی

apiService
    .getReport()
    .onExceptionResumeNext(Observable.just(defaultReport()))
    .subscribe(
        { render(it) },
        { println("خالی شد") }
    )

بخش ۱۰Subjects: Publish، Behavior، Replay، Serialized و Variable

Subjectها به‌جاهای Observable و Observer به‌هم‌ریختگی هستند؛ بخاطر این می‌توانند به‌عنوان منبع توسط یکی از اوایل‌ها، و به‌عنوان گیرنده توسط دیگری استفاده شوند.

Subjectافزودن تاخیری (backpressure)؟چه زمانی وقتی آیتم آخر و جدی‌تر است؟کاربرد اصلی
PublishSubjectخیر (یادداشت‌ها)زنده‌ترین آیتم‌ها را نگهداری می‌کند و هر آیتم را تابع می‌زندیافتن انفجار داده‌ها
BehaviorSubjectخیرمقادیر پیشین را در صورتی باعث می‌شود که زمانی از دهم باقی بماندوضعیت فعلی، نشانه‌ی فعلی
ReplaySubjectخیرآیتم‌های قبلی را مجدد می‌فرستدثبت کارهای طولانی کاری یا جستجوهای تکراری
SerializedSubjectخیر (پوشش)تأمین‌کننده‌ی پایه را به‌عنوان رگه‌ی فعلی که از دهم باقی می‌ماند می‌گذاردرفع همزمانی و مشکلات خطا قبل از کار
Variable (RxJava 2)خیر (پوشش داخلی)ذخیره‌سازی ساختاری را به‌عنوان به‌کارش می‌گیریمترجیحاً از BehaviorSubject

۱۰.۱ PublishSubject

// PublishSubject: هر آیتم به تمام گیرندگان تابع می‌زند
val subject = PublishSubject.create<String>()

subject.subscribe { println("غیرمشاهده‌ی ۱: $it") }
subject.onNext("A")          // شما را مشاهده نمی‌کنید
subject.subscribe { println("غیرمشاهده‌ی ۲: $it") }
subject.onNext("B")          // هر دو گیرنده را تابع می‌زند

۱۰.۲ BehaviorSubject

// BehaviorSubject: در صورتی که گیرنده خاموش بود، به‌ترین مقادیر را به‌دست می‌آورد
val subject = BehaviorSubject.create<Int>()

subject.onNext(1)
subject.onNext(2)
subject.subscribe { println("مشاهده حالت ۱: $it") }   // 2 را تابع می‌زند
subject.onNext(3)                                    // 3 را تابع می‌زند

۱۰.۳ ReplaySubject

// ReplaySubject: تمام آیتم‌های گذشته را مجدد به گیرنده می‌فرستد
val subject = ReplaySubject.create<String>()

subject.onNext("A")
subject.onNext("B")
subject.onNext("C")

subject.subscribe { println("مشاهده ۱: $it") }
subject.subscribe { println("مشاهده ۲: $it") }

۱۰.۴ SerializedSubject و Variable

//SerializedSubject: بین چند گیرنده، همزمانی را رفع می‌کند
val subject = PublishSubject.create<String>()
val serialized = subject.serialize()

serialized.subscribe { println("غالبی ۱: $it") }
serialized.subscribe { println("غالبی ۲: $it") }

serialized.onNext("S")
نکته: در RxJava 2، Variable به‌طور پیش‌فرض به‌عنوان BehaviorSubject پوشش‌یافته بودند؛ اما در نسخه‌ی‌های سال ۲۰۲۰ با خطاها‌ای دربرگرفته بودند. برای فعالی‌تر، ترجیحاً از BehaviorSubject استفاده کنید.

بخش ۱۱Cancellation، Disposable و Subscription

در اندروید، وقتی یک Activity یا Fragment دسکتب می‌شود، تمام جریانی که برای او در حال اجرا هستند باید لغو شوند؛ در غیر این صورت، حافظه‌ی نشت و آپدیت‌های UI پیش‌فرض در زمان‌های ناگهانی رخ می‌دهد.

۱۱.۱ استفاده از CompositeDisposable

private lateinit var composite: CompositeDisposable

override fun onCreate(savedInstanceState: Bundle?) {
    super.onCreate(savedInstanceState)

    composite = CompositeDisposable()

    composite.add(
        apiService
            .getUser(id)
            .subscribeOn(Schedulers.io())
            .observeOn(AndroidSchedulers.mainThread())
            .subscribe(
                { showUser(it) },
                { showError(it) }
            )
    )

    // وقتی زندگی این کامپوننتی به اتمام می‌رسد، همه‌ی زیرمجموعه‌ها را لغو می‌کنیم
    LifecycleEventObserver { _, event ->
        if (event == Lifecycle.Event.ON_DESTROY) composite.dispose()
    }
}

۱۱.۲ لغو نselective (بی‌عزیزانه)

Subscription sub = apiService.load()
    .subscribe(
        { show(it) },
        { err -> err.printStackTrace() }
    );

// در کد واقعی، ممکن است استفاده از یک لغو‌گر prop‌ساز شود
sub.unsubscribe()
عمیق‌تر: Subscription vs Disposable در نسخه‌های جدید RxJava (۳) کلاس Disposable مانند Subscription در نمودار استفاده شده است و CompositeDisposable به‌صورت یکدیگر استفاده می‌شود. در نسخه‌ی ۲، Subscription و CompositeSubscription استفاده می‌شوند.

بخش ۱۲حیطه بستگی (Backpressure) و Flowable

وقتی یک Observable خیلی سریع داده می‌سازد و گیرنده (Subscriber) نمی‌تواند با سرعت آن‌ها را دریافت کند، حافظه اشغال می‌شود و ممکن است برنامه cease کار کند. در اینجا استفاده از Flowable و استراتژی‌های backpressure به کمک می‌آید:

  • BUFFER: همه‌ی داده‌ها را در حافظه ذخیره می‌کند تا تمام داده‌ها را نجات دهد.
  • DROP: وقتی buffer پر شد، داده‌های جدید را نادیده می‌گیرد.
  • LATEST: آخرین داده را نگه می‌دارد.
  • ERROR: در صورت پرشدن buffer، خطا می‌دهد.

۱۲.۱ استراتژی‌های Backpressure

Flowable<Long> source = Flowable.create(
    { emitter ->
        var i = 0L
        while (!emitter.isCancelled()) {
            emitter.onNext(i++)
            Thread.sleep(10)
        }
    },
    BackpressureStrategy.BUFFER   // داده‌ها در حافظه ذخیره می‌شوند
)

source.observeOn(Schedulers.io())
    .subscribe(
        { println("مقرا: $it") },
        { err -> err.printStackTrace() }
    )

۱۲.۲ consume এবং doOnNext

Flowable.range(1, 1_000_000)
    .doOnNext { value -> println("مقدار فعلی: $value") }
    .subscribe(
        { value -> process(value) },
        { err -> err.printStackTrace() }
    )

بخش ۱۳یکپارچه‌سازی با Android و Compose

این بخش نشان می‌دهد که RxJava و RxAndroid در اندروید چگونه استفاده می‌شوند و چگونه با Compose و ViewModel تعامل دارند.

۱۳.۱ ViewModel و RxJava

class UserViewModel(private val repository: UserRepository) : ViewModel() {

    private val composite = CompositeDisposable()

    fun getUser(userId: String) {
        composite.add(
            repository.getUser(userId)
                .subscribeOn(Schedulers.io())
                .observeOn(AndroidSchedulers.mainThread())
                .subscribe(
                    { user -> _user.value = user },
                    { err -> _error.value = err.message }
                )
        )
    }

    override fun onCleared() {
        super.onCleared()
        composite.dispose()
    }
}

۱۳.۲ Compose + LiveData / StateFlow

@Composable
fun UserScreen(viewModel: UserViewModel) {
    val user by viewModel.user.collectAsStateWithLifecycle()

    Column(modifier = Modifier.fillMaxSize().padding(16.dp)) {
        Text(text = " نام کاربری: $user")
    }
}

// کد جاوا: استفاده از RxAndroid برای رویدادهای UI
RxTextView.textChanges(searchEditText)
    .debounce(300, TimeUnit.MILLISECONDS)
    .observeOn(AndroidSchedulers.mainThread())

نکته: در کامپوز، جریان‌های مشابه با StateFlow یا Flow به‌کار می‌روند؛ اما RxJava در تجزیه‌ی موقت‌ها، نسخه‌های فعلی و برخی کتابخانه‌ها خالی‌تر است. برای کد جدید، معمولاً StateFlow/Flow ترجیح داده می‌شود.

بخش ۱۴بهترین شیوه‌ها، چک‌لیست و منابع

۱۴.۱ بهترین شیوه‌ها

  1. همیشه Disposable را به CompositeDisposable اضافه کنید. این جلوگیری از حافظه‌ی نشت در Activity/Fragment دسکتب‌شده و اپدیت‌های UI در زمان‌های ناگهانی را می‌آموزد.
  2. از subscribeOn به یک نقطه استفاده کنید و در پشت با observeOn.
  3. در جستجوها، از debounce + distinctUntilChanged + switchMap استفاده کنید.
  4. زمانی که COUNT بسیار بزرگ است، از Flowable و BackpressureStrategy استفاده کنید.
  5. خطاهای رایج را به‌صورت دستی از خطرات پنهان‌ها دور بگیرید. زمانی که خروجی دوی پارچه‌ای وجود دارد، از retry با شمارش‌پذیر استفاده کنید.
  6. در کد‌های اندرویدی، از try-with-resources یا try-catch (finally) برای حذف اشتراک‌های آزاد در صورت پروداکشن حیاتی انتها را بگذارید.

۱۴.۲ چک‌لیست نهایی
