RxJava و RxAndroid: راهنمای کامل از Observable تا Flowable و Subject

RxJava و RxAndroid کتابخانه‌های قدرتمندی برای برنامه‌نویسی ناهم‌زمان و واکنش‌گرا در جاوا و کاتلین هستند. در این مقاله کلاس‌های اصلی، مهم‌ترین Operatorها، Schedulers، Subjectها و بهترین شیوه‌ها را از صفر تا صد می‌آورم؛ همراه با نمودارهای SVG، جدول‌های مقایسه‌ای، نکات مهم و نمونه‌کدهای واقعی اندروید و Compose.

بخش ۱چه فرقی بین RxJava و RxAndroid دارد؟

۱.۱ برنامه‌نویسی واکنش‌گرا: مسئله‌ی x = y + z

در برنامه‌نویسی دستوری (Imperative) نتایج را خودمان محاسبه و به‌روز می‌کنیم. فرض کنید x = y + z است؛ اگر z تغییر کند، باید دستی یادمان باشد که x را هم دوباره حساب کنیم — در پروژه‌های بزرگ، همین یک فراموشی منبع اصلی باگ‌های وضعیت (State Bug) می‌شود. 

// رویکرد دستوری: با تغییر z باید x را خودمان دوباره بسازیم
var y = 2
var z = 3
var x = y + z          // x = 5
z = 10
x = y + z              // اگر این خط را فراموش کنیم، x کهنه می‌ماند!

// رویکرد واکنش‌گرا: جریان‌ها خودشان زنجیره را به‌روز می‌کنند
val y = BehaviorSubject.createDefault(2)
val z = BehaviorSubject.createDefault(3)

val x = Observable.combineLatest(y, z) { a, b -> a + b }
x.subscribe { println("x = $it") }   // x = 5

z.onNext(10)                         // بدون هیچ فراخوانی دستی: x به‌صورت خودکار 15 می‌شود
نکته: در واکنش‌گرایی، «داده» و «تغییر» را جریان (Stream) در نظر می‌گیریم و ما فقط زنجیره‌ی تبدیل‌ها را تعریف می‌کنیم؛ این‌که کِی، روی کدام ترد و با چه ترتیبی اجرا شود را RxJava برعهده می‌گیرد.

۱.۲ ReactiveX چیست؟

ReactiveX (یا به‌اختصار Rx) یک زبان مشترک و مجموعه‌ای از کتابخانه‌ها برای برنامه‌نویسی واکنش‌گراست که همه‌جا روی یک مدل واحد استوار است: Observable (جریان داده) + Operator (تبدیل‌ها) + Subscriber (گیرنده). پیاده‌سازی‌های معروف آن:

  • RxJava — پیاده‌سازی استاندارد Rx برای جاوا و کاتلین (پایه‌ی اصلی همه‌ی نمونه‌کدهای این مقاله).
  • RxAndroid — تنها یک تکه کوچک ولی حیاتی: Schedulers‌های سفارشیِ اندروید، مهم‌تر از همه AndroidSchedulers.mainThread() که خروجی جریان را روی ترد اصلی UI تحویل می‌دهد.
  • RxKotlin / RxBinding — پسوندهای راحت‌تر برای کاتلین و رویدادهای ویو (دکمه، متن و…).
عمیق‌تر: تفاوت دقیق RxJava و RxAndroid RxJava کتابخانه‌ای مستقل و بدون هیچ وابستگی به اندروید است و روی سرور، اندروید، تست یونیت و هرجای جاوا اجرا می‌شود؛ RxAndroid فقط یک ماژول کوچک است که ترد اصلی اندروید را به شکل یک Scheduler درمی‌آورد. بدون RxAndroid می‌توانید RxJava را استفاده کنید، اما برای نمایش نتایج در UI باید خودتان ترد اصلی را مدیریت کنید.

۱.۳ در این مقاله چه چیزهایی می‌آموزیم؟

در این مقاله ابتدا مفاهیم پایه، سپس کلاس‌ها، بعد Operatorها، Schedulers، Subjectها و در نهایت یکپارچه‌سازی با اندروید را بررسی می‌کنیم؛ هر مفهوم همراه با دیاگرام ماربل متحرک، نمونه‌کد جاوا/کاتلین و خروجی LogCat واقعی آورده شده است.

۱.۴ چرا از Observable استفاده کنیم؟

وقتی قرار است چند مرحله روی داده‌ها انجام شود — مثلاً وقتی یک زنجیره از عملیات به‌صورت پشت‌سرهم از بالا به پایین اجرا می‌شود — استفاده از Observable کمک می‌کند تا:

  • کد را از تودرتویی فراخوانی (callback hell) دور کنیم.
  • هم‌زمانی، ترتیب، تأخیر و خطا را کنترل کنیم.
  • ورودی‌ها و خروجی‌ها را به‌صورت یک جریان (stream) ببینیم.

بخش ۲Observable، Observer، Subscriber و Flowable

در RxJava، مهم‌ترین مدل‌ها Observable، Observer، Subscriber و Flowable هستند. در ادامه می‌بینیم هرکدام در چه موقعیتی به کار می‌روند.

۲.۱ Observable و Observer

به‌طور خلاصه: Observable داده تولید می‌کند و Observer آن را دریافت می‌کند. هر بار که دادهٔ جدیدی برسد، تابع onNext صدا زده می‌شود؛ در پایان onComplete فراخوانی می‌شود و اگر خطایی رخ دهد، onError اجرا می‌شود.

متد Observerچه زمانی صدا زده می‌شودتوضیح
onSubscribe(Disposable)یک‌بار، در شروعتنها جایی است که دسته‌ی لغو (Disposable) را می‌گیرید؛ قبل از هر رویداد دیگر
onNext(T)به‌ازای هر مقدارتعدادش نامحدود است (تا وقتی جریان باز است)
onError(Throwable)در صورت خطاجریان برای همیشه بسته می‌شود؛ بعد از آن نه onNext می‌آید نه onComplete
onComplete()پایان موفق جریانیک‌بار؛ بعد از آن جریان بسته است و مصرف‌کننده دیگر رویدادی نمی‌گیرد
// Kotlin — Observable با Observer
val observable = Observable.create<String> { emitter ->
    emitter.onNext("Kotlin")
    emitter.onNext("Java")
    emitter.onComplete()
}

observable.subscribe(
    { item -> println("گرفته: $item") },      // onNext
    { err -> println("خطا: $err") },          // onError
    { println("پایان") }                        // onComplete
)
// Java — همان مثال با ObservableOnSubscribe (RxJava 3)
Observable<String> observable = Observable.create(
    new ObservableOnSubscribe<String>() {
        @Override
        public void subscribe(ObservableEmitter<String> emitter) {
            emitter.onNext("Java");
            emitter.onNext("Kotlin");
            emitter.onComplete();
        }
    }
);

Disposable disposable = observable.subscribe(
    s -> System.out.println("گرفته: " + s),   // onNext
    t -> System.err.println("خطا: " + t),     // onError
    () -> System.out.println("پایان")          // onComplete
);

// Disposable را نگه دارید و در onDestroy فراخوانی کنید:
// disposable.dispose();
// خروجی LogCat پس از اجرای مثال (فقط بخش مهم)
01-12 10:24:31.482  8621  8621 I/System.out: گرفته: Java
01-12 10:24:31.483  8621  8621 I/System.out: گرفته: Kotlin
01-12 10:24:31.483  8621  8621 I/System.out: پایان

۲.۲ دسته‌ی لغو: Disposable به‌جای Subscription

در RxJava 2 و 3، متد subscribe(...) یک Disposable برمی‌گرداند؛ با dispose() می‌توانید در هر لحظه اشتراک را لغو کنید و جریان را متوقف سازید. کلاس Subscriber نسخه‌ی پیشرفته‌تری از Observer است که علاوه بر دریافت داده، درخواست (request) و لغو را هم کنترل می‌کند و پایه‌ی Backpressure در Flowable است. 

val source = Observable.just("A", "B", "C")

val disposable: Disposable = source.subscribe(
    { item -> println("گرفته: $item") },
    { err -> println("خطا: $err") }
)

// در هر لحظه می‌توانیم اشتراک را لغو کنیم
disposable.dispose()
هشدار: اگر Disposable را جایی نگه ندارید و dispose() را صدا نزنید، جریان تا انتهای عمر Activity به کارش ادامه می‌دهد و به همراه Listenerهایش نگه داشته می‌شود؛ این رایج‌ترین علت نشت حافظه (Memory Leak) در اپ‌های اندرویدی مبتنی بر Rx است. راه‌حل استاندارد: CompositeDisposable (بخش ۱۱).
نکته: نگه‌داشتن اشتراک‌ها در یک CompositeDisposable و افزودن آن‌ها با CompositeDisposable.add، روش استاندارد برای لغو گروهی آن‌ها در کد اندرویدی است.

۲.۳ Flowable برای Backpressure

وقتی نرخ تولید داده از توان دریافت گیرنده بیشتر می‌شود، به‌جای Observable از Flowable استفاده می‌شود. Flowable از Backpressure پشتیبانی می‌کند: مشخص می‌شود گیرنده در هر لحظه آمادهٔ دریافت چند آیتم است و از پرشدن بی‌رویهٔ حافظه جلوگیری می‌شود. 

val flowable = Flowable.create<Long>({ emitter ->
    var i = 0L
    while (!emitter.isCancelled) {
        emitter.onNext(i++)       // تولید مکرر و سریع داده
        Thread.sleep(100)
    }
}, BackpressureStrategy.BUFFER)

val disposable = flowable
    .observeOn(Schedulers.io())
    .subscribe(
        { v -> println("مقدار: $v") },
        { err -> err.printStackTrace() }
    )
عمیق‌تر: Backpressure وقتی تولید داده‌ها سریع‌تر از پردازش گیرنده پیش می‌رود، می‌توان با Flowable و استراتژی‌هایی مانند BUFFER، DROP، LATEST و ERROR سرعت جریان را کنترل کرد.

بخش ۳انواع جریان داده: Single، Maybe، Completable و Observable

RxJava چهار نوع جریان برای حالت‌های مختلف داده ارائه می‌دهد: جریانی برای یک آیتم، جریانی برای صفر یا یک آیتم، جریانی برای فقط اعلام تکمیل، و جریانی برای تعداد نامشخص آیتم. هرکدام برای موقعیت خاصی مناسب‌اند.

نوعنمونهٔ خروجیپایان جریانتفاوت با Observable
Observable۰ تا n آیتمبا onCompleteحالت پیش‌فرض؛ می‌تواند خالی هم باشد
Singleدقیقاً یک آیتمبا onSuccessهمیشه یک آیتم می‌دهد؛ خطا فقط از راه onError
Maybeصفر تا یک آیتمبا onSuccess یا onCompleteاگر داده‌ای وجود نداشته باشد هم درست کار می‌کند
Completableهیچ آیتمیبا onCompleteفقط اعلام رویداد انجام‌شدن کار؛ بدون خروجی

۳.۱ Single — یک پاسخ واحد

Single<User> userSingle = Single.create(emitter -> {
    emitter.onSuccess(fetchUserById(42));
    // یا emitter.onError(exception);
});

userSingle.subscribe(
    { user -> showDetail(user) },
    { err -> showError(err) }
)

۳.۲ Maybe — صفر یا یک آیتم

Maybe<User> maybeUser = Maybe.create(emitter -> {
    User u = findUser(42);
    if (u != null) emitter.onSuccess(u); else emitter.onComplete();
});

maybeUser.subscribe(
    { user -> showDetail(user) },
    { println("هیچ کار برای انجام نداریم") }
)

۳.۳ Completable — بدون خروجی

Completable completable = Completable.create(emitter -> {
    saveSettings(userId, prefs);
    emitter.onComplete();
});

completable.subscribe(
    { println("ذخیره‌سازی با موفقیت انجام شد") },
    { err -> println("خطا: $err") }
);
کدام را انتخاب کنیم؟ اگر عملیات شما خروجی دارد، به‌جای Completable از Single (دقیقاً یک آیتم) یا Maybe (صفر تا یک آیتم) استفاده کنید؛ این انتخاب هم خواناتر است و هم مدیریت خطا را دقیق‌تر می‌کند.

بخش ۴Operatorهای اصلی: map، filter، take، drop، distinct

Operatorها توابعی هستند که جریان ورودی را می‌گیرند و تغییرش می‌دهند: ممکن است هر آیتم را به شکل تازه‌ای بسازند یا تعداد آیتم‌ها را کم و اضافه کنند. در این بخش پرکاربردترین‌هایشان را می‌بینیم.

۴.۱ map — تبدیل کردن

Observable<String> names = Observable.just("Ali", "Sara", "Reza")

names.map { name -> name.length }          // [3, 4, 4]
     .subscribe { println("طول: $it") }

۴.۲ filter — فیلتر کردن

Observable<Integer> numbers = Observable.range(1, 10)

numbers.filter { it % 2 == 0 }             // 2، 4، 6، 8، 10
      .subscribe { println("مقدار: $it") }

۴.۳ take / skip / takeWhile

Observable.range(1, 20)
    .take(5)                                 // ۱ تا ۵، سپس onComplete
    .subscribe { println("take: $it") }

Observable.range(1, 20)
    .skip(10)                                // ۱۱ تا ۲۰
    .subscribe { println("skip: $it") }

Observable.range(1, 20)
    .takeWhile { it <= 10 }                  // تا وقتی شرط برقرار است
    .subscribe { println("takeWhile: $it") }

۴.۴ distinct / elementAt

Observable.just(1, 2, 1, 3, 2, 4)
    .distinct()                              // 1، 2، 3، 4
    .subscribe { println("distinct: $it") }

Observable.range(1, 10)
    .elementAt(3)                            // Maybe: ۴ (اندیس‌ها از ۰ شروع می‌شوند)
    .subscribe { println("elementAt: $it") }

۴.۵ first / last

// در RxJava 3 این متدها Single برمی‌گردانند نه Observable
Observable.just(4, 7, 2, 9)
    .firstItem()                             // Single<Int> → 4
    .subscribe { println("اولین: $it") }

Observable.just(4, 7, 2, 9)
    .last(0)                                 // Single<Int> → 9 (آرگومان = مقدار پیش‌فرض)
    .subscribe { println("آخرین: $it") }

بخش ۵زنجیره‌سازی و تبدیل کردن آیتم‌ها: flatMap، concatMap، switchMap

وقتی هر آیتم ورودی یک Observable دیگر تولید می‌کند (یعنی هر آیتم به یک درخواست جداگانه تبدیل می‌شود)، از Operatorهای flatMap، concatMap و switchMap استفاده می‌شود. تفاوت کلیدی این سه در نحوهٔ ترکیب نتایج است.

Operatorترتیب خروجیمعادل سادهرفتار
flatMapغیرقابل پیش‌بینی (non-deterministic)همه‌چیز برابر استهمهٔ درخواست‌ها هم‌زمان اجرا می‌شوند
concatMapکاملاً به‌ترتیب ورودیصف کارهای سریالیخروجی‌ها دقیقاً به همان ترتیب ورودی می‌آیند
switchMapفقط آخرین آیتم باقی می‌ماندنزدیک‌ترین حالت به «تازه‌ترین حالت»با هر ورودی جدید، درخواست‌های قبلی لغو می‌شوند

۵.۱ flatMap — همزمان کردن چند خروجی

// هر کامنت یک درخواست جداگانه برای شمارش لایک می‌سازد
val comments: Observable<Comment> = fetchPostComments(postId)

comments.flatMap { comment ->
    fetchLikeCount(comment.id)
         .map { likeCount -> comment.copy(likeCount = likeCount) }
}

۵.۲ concatMap — حفظ ترتیب

// اجرای پشت‌سرهم و یکی‌یکی
Observable.just("A", "B", "C")
    .concatMap { item ->
        heavyWork(item)          // اجرا به ترتیب، خروجی هم به همان ترتیب
    }

۵.۳ switchMap — استفاده از آخرین ورودی

// جستجوی لحظه‌ای: با هر کلید جدید، درخواست قبلی لغو می‌شود
searchEditText.textChanges()                // از RxBinding
    .debounce(300, TimeUnit.MILLISECONDS)
    .observeOn(Schedulers.computation())
    .switchMap { query ->
        searchService.search(query)       // جریان پیشین رها می‌شود
    }
    .observeOn(AndroidSchedulers.mainThread())
    .subscribe { results -> showResults(results) }
نکته: در جستجوهای موبایل، switchMap بهترین گزینه است؛ چون با هر ورودی جدید درخواست‌های قبلی را لغو می‌کند و جلوی نمایش نتایج منسوخ را می‌گیرد.

بخش ۶جمع‌بندی و کاهش داده‌ها: reduce، fold، collect

وقتی می‌خواهیم چندین عنصر را به یک آیتم واحد کاهش دهیم، از این Operatorها استفاده می‌شود.

۶.۱ reduce — خروجی یک آیتم واحد

Observable.just(1, 2, 3, 4, 5)
    .reduce { acc, item -> acc + item }      // ۱۵
    .subscribe { println("مجموع: $it") }

۶.۲ scan — خروجی هر مرحله‌ای

Observable.range(1, 5)
    .scan { acc, item -> acc + item }        // ۱، ۳، ۶، ۱۰، ۱۵
    .subscribe { println("مجموع تا کنار: $it") }

۶.۳ collect / collectInto — به‌راحتی جمع‌آوری

Observable.just(1, 2, 3, 4, 5)
    .collect(
        { ArrayList<Int>() },                 // مقدار شروع
        { list, item -> list.add(item) }      // عملکرد کاهش
    )
    .subscribe { list -> println("لیست نهایی: $list") }

۶.۴ گروه‌بندی (toList / groupBy)

Observable.just(1, 2, 3, 4, 5)
    .toList()                                // [1, 2, 3, 4, 5]
    .subscribe { println("همه‌ی اعداد: $it") }

Observable.just("apple", "banana", "apricot", "cherry")
    .groupBy { it[0] }                       // گروه‌بندی بر پایه‌ی حرف اول
    .subscribe { group ->
        group.toList().subscribe { items ->
            println("گروه ${group.key}: $items")
        }
    }

بخش ۷کنترل در زمان و نرخ: throttleFirst، debounce، delay

وقتی ورودی‌ها سریع‌تر از پردازش خروجی می‌رسند (مثلاً کاربر در یک کادر جستجو سریع تایپ می‌کند، یا رویدادها پشت‌سرهم فراخوانی می‌شوند)، از Operatorهای کنترل نرخ استفاده می‌کنیم تا این مشکل برطرف شود.

Operatorمعادل سادهزمان فعال‌شدنکاربرد
throttleFirstفقط اولین رویداد هر بازهبلافاصله در شروع هر بازهمحدود کردن نرخ رویدادها؛ مثلاً یک‌بار در هر N میلی‌ثانیه
debounceصبر تا آرام‌شدن ورودی‌هاپس از توقف ورودی‌هاجستجوی موبایل؛ ارسال درخواست بعد از چند میلی‌ثانیه سکوت
delayتأخیر در انتشاربا تأخیر قابل تنظیمعقب‌انداختن یک جریان
sample / throttleLastنمونه‌برداری از جریاندر بازه‌های زمانی ثابتگرفتن آخرین آیتم در هر بازهٔ زمانی
bufferجمع‌کردن در لیستپایان هر بازهپردازش گروهی رویدادهای پشت‌سرهم

۷.۱ debounce برای جستجو

searchEditText.textChanges()                // از RxBinding
    .debounce(300, TimeUnit.MILLISECONDS)
    .observeOn(Schedulers.computation())
    .map { query -> query.toString().trim().uppercase() }
    .filter { it.isNotEmpty() }
    .distinctUntilChanged()
    .switchMap { query ->
        searchService.search(query)
    }

۷.۲ throttleFirst برای دکمه‌های ضدتکرار

// دکمهٔ ارسال پست: جلوی ارسال‌های تکراری و سریع را می‌گیرد
sendButton.clicks()                          // از RxBinding
    .throttleFirst(500, TimeUnit.MILLISECONDS)   // کلیک‌های سریع بعدی را نادیده می‌گیرد
    .subscribe { submitForm() }

۷.۳ delay — تأخیر کامل از اول

Observable.timer(2, TimeUnit.SECONDS)
    .flatMap { fetchDashboardData() }
    .subscribe { showDashboard(it) }

۷.۴ throttleLast (sample) — آخرین مقدار هر بازه

// گزارش موقعیت کاربر: هر ثانیه فقط آخرین مقدار ارسال شود
locationUpdates
    .sample(1, TimeUnit.SECONDS)
    .subscribe { sendLocation(it) }

۷.۵ buffer — جمع‌کردن رویدادها در بازه‌های زمانی

// کلیک‌های چندثانیه‌ای یک‌جا پردازش شوند
view.clicks()
    .buffer(1, TimeUnit.SECONDS)
    .subscribe { clicks -> println("تعداد کلیک در این بازه: ${clicks.size}") }

بخش ۸Schedulers: newThread، computation، io، mainThread

Scheduler در RxJava جایی است که جریان از دسته‌ای به دسته‌ی دیگر منتقل می‌شود؛ به عنوان مثال، بک‌اند روی Schedulers.io() و UI روی AndroidSchedulers.mainThread(). به‌زبان ساده: subscribeOn مشخص می‌کند «کار از کجا شروع شود» و observeOn مشخص می‌کند «نتایج از کجا دیده شوند».

Schedulerکجا استفاده شودنوع تردنوع کار
Schedulers.io()شبکه، پایگاه‌داده، فایل، I/Opool بزرگ و انعطاف‌پذیر (بدون سقف سخت)خواندن/نوشتن مسدودکننده (blocking)
Schedulers.computation()محاسبات سنگین، رمزنگاری، پردازش تصویربه تعداد هسته‌های پردازندهکارهای CPU-محورِ بدون مسدودکردن
Schedulers.newThread()ماژول‌هایی که ترد جدا می‌خواهندیک ترد تازه برای هر اشتراککارهای طولانی و مستقل
Schedulers.single()کارهای ترتیبی سراسریِ یکتایک ترد مشترک برای کل برنامهثبت لاگ، شمارنده‌ها، کارهای نباید هم‌زمان شوند
Schedulers.trampoline()زمان‌بندی فوریِ ترتیبی در همین ترددر همین thread، صف داخلیتست، اجرای فوری بدون تعویض ترد
Schedulers.from(executor)اتصال به یک ExecutorService خودمانیهمان Executor شمایکپارچه‌سازی با کد قدیمی یا محدودکردن ترد
Schedulers.io() + AndroidSchedulers.mainThread()الگوی استاندارد اندرویدبک‌اند + ترد اصلی UIدریافت داده در io و نمایش در UI

کلاس AndroidSchedulers.mainThread() را خودِ پکیج RxAndroid می‌سازد؛ بدون آن باید با Handler(Looper.getMainLooper()) دستی خروجی را به ترد UI ببرید.

۸.۱ استفاده از Schedulers در کد اندرویدی

apiService
    .getUser(id)
    .subscribeOn(Schedulers.io())              // درخواست شبکه در بک‌اند
    .observeOn(AndroidSchedulers.mainThread()) // نمایش نتیجه در ترد اصلی UI
    .subscribe(
        { user -> updateUI(user) },
        { err -> showError(err) }
    )
// ترد اجرای هر بخش (با فیلتر Tracer یا Log.i در subscribeOn/observeOn)
01-12 10:26:02.114  8621  8740 I/RxSample: fetch from network (Schedulers.io #3)
01-12 10:26:02.389  8621  8621 I/RxSample: render user on main thread

۸.۲ ترکیب Scheduler‌ها

dataService
    .loadList()
    .subscribeOn(Schedulers.io())
    .observeOn(Schedulers.computation())
    .map { processData(it) }                  // پردازش سنگین روی ترد محاسبات
    .observeOn(AndroidSchedulers.mainThread())
    .subscribe(
        { displayList(it) },
        { showError(it) }
    )
عمیق‌تر: subscribeOn فقط یک‌بار معنا دارد اگر چند subscribeOn پشت‌سرهم بگذارید، فقط اولین‌شان (نزدیک‌ترین به subscribe) مسیر شروع را تعیین می‌کند؛ اما چند observeOn کاملاً معتبر است و هرکدام جریان را به ترد بعدی می‌برد. توصیه: یک subscribeOn در ابتدای زنجیره و هرچند observeOn که لازم دارید.

بخش ۹مدیریت خطا و بازیابی: onErrorReturn، retry، onErrorResumeNext

مدیریت خطا (Error Handling) یکی از مهم‌ترین بخش‌های برنامه‌نویسی واکنش‌گراست؛ چون در شبکه‌ها و سرویس‌های راه دور، خطاها غیرقابل‌پیش‌بینی‌اند و باید درست بازیابی شوند. به‌یاد داشته باشید: onError جریان را برای همیشه می‌بندد — اگر آن را مدیریت نکنید، جریان بی‌صدا می‌میرد و کاربر فقط «هیچ‌چیز اتفاق نیفتاد» می‌بیند.

۹.۱ onErrorReturn — برگرداندن یک آیتم جایگزین

apiService
    .getUser(id)
    .onErrorReturn { User.getDefault() }     // در صورت خطا، یک کاربر پیش‌فرض برمی‌گرداند
    .observeOn(AndroidSchedulers.mainThread())
    .subscribe(
        { showUser(it) },
        { /* این تابع اجرا نمی‌شود */ }
    )

۹.۲ retry — تلاش دوباره در صورت خطا

apiService
    .getData()
    .retry(3)                                 // حداکثر ۳ بار تلاش مجدد
    .subscribe(
        { showData(it) },
        { err -> println("پس از ۳ تکرار، خطا: $err") }
    )

۹.۳ onErrorResumeNext — جریان جایگزین

apiService
    .getFeed()
    .onErrorResumeNext { Observable.empty() }   // در صورت خطا، جریان خالی ادامه می‌دهد
    .subscribe(
        { displayFeed(it) },
        { println("خطا مدیریت شد") }
    )

۹.۴ retryWhen — تلاش مجدد با تأخیر افزایشی

apiService
    .getReport()
    .retryWhen { errors ->
        errors.zipWith(Observable.range(1, 5)) { err, attempt -> attempt }
            .flatMap { attempt ->
                Observable.timer(attempt.toLong(), TimeUnit.SECONDS) // ۱، ۲، ۳... ثانیه صبر
            }
    }
    .subscribe(
        { render(it) },
        { println("پس از ۵ تلاش هنوز خطا داریم: $it") }
    )

بخش ۱۰Subjects: Publish، Behavior، Replay، Serialized و Variable

Subjectها ترکیبی از Observable و Observer هستند؛ یعنی هم می‌توانند منبع داده باشند و هم گیرنده. به همین دلیل می‌توان یک Subject را به‌عنوان منبع به زنجیره‌ها وصل کرد و هم‌زمان چند گیرنده به آن داشت.

Subjectپشتیبانی از Backpressureرفتار با گیرندهٔ دیرهنگامکاربرد اصلی
PublishSubjectخیرفقط آیتم‌های بعد از زمان اشتراک را می‌فرستدرویدادهای لحظه‌ای و جریان پرسرعت
BehaviorSubjectخیرآخرین آیتم را نگه می‌دارد و برای گیرندهٔ تازه دوباره می‌فرستدنگهداری وضعیت فعلی (state)
ReplaySubjectخیرآیتم‌های قبلی را دوباره برای گیرندهٔ تازه می‌فرستدبازپخش رویدادها، لاگ و تاریخچه
AsyncSubjectخیرفقط آخرین مقدار را در لحظهٔ onComplete می‌فرستدنتیجهٔ نهاییِ یک فراخوانی (مثل پاسخ شبکه)
SerializedSubjectخیرمثل PublishSubject، اما با محافظت در برابر فراخوانی هم‌زمانرفع خطاهای هم‌زمانی در چند ترد
Variable (RxJava 2)خیرمثل BehaviorSubject، با مقدار اولیهحذف‌شده؛ به‌جای آن از BehaviorSubject استفاده کنید

۱۰.۱ PublishSubject

// PublishSubject: هر آیتم فقط به گیرنده‌های فعلی ارسال می‌شود
val subject = PublishSubject.create<String>()

subject.subscribe { println("گیرندهٔ ۱: $it") }
subject.onNext("A")          // هنوز گیرنده‌ای وجود ندارد
subject.subscribe { println("گیرندهٔ ۲: $it") }
subject.onNext("B")          // هر دو گیرنده این آیتم را دریافت می‌کنند

۱۰.۲ BehaviorSubject

// BehaviorSubject: گیرندهٔ دیرهنگام هم آخرین مقدار را دریافت می‌کند
val subject = BehaviorSubject.create<Int>()

subject.onNext(1)
subject.onNext(2)
subject.subscribe { println("مشاهدهٔ حالت ۱: $it") }   // مقدار ۲ را دریافت می‌کند
subject.onNext(3)                                    // مقدار ۳ را دریافت می‌کند

۱۰.۳ ReplaySubject

// ReplaySubject: تمام آیتم‌های گذشته را دوباره به گیرندهٔ تازه می‌فرستد
val subject = ReplaySubject.create<String>()

subject.onNext("A")
subject.onNext("B")
subject.onNext("C")

subject.subscribe { println("مشاهدهٔ ۱: $it") }
subject.subscribe { println("مشاهدهٔ ۲: $it") }

۱۰.۴ SerializedSubject و Variable

// SerializedSubject: از تداخل در فراخوانی هم‌زمان جلوگیری می‌کند
val subject = PublishSubject.create<String>()
val serialized = subject.serialize()

serialized.subscribe { println("گیرندهٔ ۱: $it") }
serialized.subscribe { println("گیرندهٔ ۲: $it") }

serialized.onNext("S")
نکته: در RxJava 2 کلاس Variable در عمل همان نقش BehaviorSubject را داشت و در نسخه‌های بعدی حذف شد. برای کد امروزی، ترجیحاً از BehaviorSubject استفاده کنید.

۱۰.۵ AsyncSubject — فقط نتیجهٔ نهایی

// AsyncSubject: تا onComplete چیزی نمی‌فرستد؛ فقط آخرین مقدار را تحویل می‌دهد
val subject = AsyncSubject.create<String>()

subject.onNext("a")
subject.onNext("b")
subject.subscribe { println("دریافت: $it") }   // چیزی نمی‌گیرد!

subject.onNext("final")
subject.onComplete()                           // حالا فقط "final" ارسال می‌شود
Subject داغ یا سرد؟ Subjectها «داغ» (Hot) هستند: جریان بدون توجه به تعداد مشترک‌ها جلو می‌رود و اگر کسی دیر برسد، بخشی از داده را از دست می‌دهد. بر خلاف آن، Observable‌های معمولی «سرد» (Cold) هستند و هر مشترک از ابتدا کل جریان را می‌بیند.

بخش ۱۱Cancellation، Disposable و Subscription

در اندروید، وقتی یک Activity یا Fragment نابود می‌شود، همهٔ جریان‌هایی که برای آن در حال اجرا هستند باید لغو شوند؛ در غیر این صورت خطر نشت حافظه (Memory Leak) و به‌روزرسانی UI پس از نابودی شدن Activity وجود دارد.

۱۱.۱ استفاده از CompositeDisposable

private lateinit var composite: CompositeDisposable

override fun onCreate(savedInstanceState: Bundle?) {
    super.onCreate(savedInstanceState)

    composite = CompositeDisposable()

    composite.add(
        apiService
            .getUser(id)
            .subscribeOn(Schedulers.io())
            .observeOn(AndroidSchedulers.mainThread())
            .subscribe(
                { showUser(it) },
                { showError(it) }
            )
    )

    // وقتی چرخهٔ عمر این کامپوننت تمام می‌شود، همهٔ اشتراک‌ها را لغو می‌کنیم
    LifecycleEventObserver { _, event ->
        if (event == Lifecycle.Event.ON_DESTROY) composite.dispose()
    }
}

بخش ۱۲فشار بازگشتی (Backpressure) و Flowable

وقتی یک Observable خیلی سریع داده تولید می‌کند و گیرنده (Subscriber) نمی‌تواند به همان سرعت دریافت کند، حافظه اشغال می‌شود و برنامه ممکن است کرش کند. اینجاست که Flowable و استراتژی‌های Backpressure به کمک می‌آیند:

  • BUFFER: همهٔ داده‌ها را در بافر داخلی نگه می‌دارد تا گیرنده عقب نیفتد (خطر پر شدن حافظه).
  • DROP: وقتی بافر پر شد، داده‌های جدید را نادیده می‌گیرد.
  • LATEST: فقط آخرین داده را نگه می‌دارد و بقیه را دور می‌ریزد.
  • ERROR: به‌محض پر شدن بافر، خطا می‌دهد.
  • MISSING: هیچ استراتژی‌ای اعمال نمی‌کند؛ خطای MissingBackpressureException را به شما واگذار می‌کند.

۱۲.۱ استراتژی‌های Backpressure

val source = Flowable.create<Long>({ emitter ->
    var i = 0L
    while (!emitter.isCancelled) {
        emitter.onNext(i++)
        Thread.sleep(10)
    }
}, BackpressureStrategy.BUFFER)   // داده‌ها در بافر داخلی ذخیره می‌شوند

source.observeOn(Schedulers.io())
    .subscribe(
        { println("مقدار: $it") },
        { err -> err.printStackTrace() }
    )

۱۲.۲ مصرف داده و doOnNext

Flowable.range(1, 1_000_000)
    .doOnNext { value -> println("مقدار فعلی: $value") }
    .subscribe(
        { value -> process(value) },
        { err -> err.printStackTrace() }
    )

بخش ۱۳یکپارچه‌سازی با Android و Compose

این بخش نشان می‌دهد RxJava و RxAndroid در اندروید چگونه استفاده می‌شوند و چگونه با Compose و ViewModel تعامل دارند.

۱۳.۱ ViewModel و RxJava

class UserViewModel(private val repository: UserRepository) : ViewModel() {

    private val composite = CompositeDisposable()

    fun getUser(userId: String) {
        composite.add(
            repository.getUser(userId)
                .subscribeOn(Schedulers.io())
                .observeOn(AndroidSchedulers.mainThread())
                .subscribe(
                    { user -> _user.value = user },
                    { err -> _error.value = err.message }
                )
        )
    }

    override fun onCleared() {
        super.onCleared()
        composite.dispose()
    }
}

۱۳.۲ Compose + LiveData / StateFlow

@Composable
fun UserScreen(viewModel: UserViewModel) {
    val user by viewModel.user.collectAsStateWithLifecycle()

    Column(modifier = Modifier.fillMaxSize().padding(16.dp)) {
        Text(text = "نام کاربر: $user")
    }
}

۱۳.۳ RxBinding / RxAndroid و رویدادهای UI

// کد جاوا: استفاده از RxAndroid برای رویدادهای UI
RxTextView.textChanges(searchEditText)
    .debounce(300, TimeUnit.MILLISECONDS)
    .observeOn(AndroidSchedulers.mainThread())

نکته: در Compose معمولاً از StateFlow یا Flow استفاده می‌شود؛ اما در کتابخانه‌های قدیمی‌تر که هنوز RxJava دارند، تعامل با لایهٔ Compose از طریق collectAsStateWithLifecycle انجام می‌شود. برای کد جدید، StateFlow/Flow ترجیح داده می‌شود.

بخش ۱۴بهترین شیوه‌ها، چک‌لیست و منابع

۱۴.۱ بهترین شیوه‌ها

  1. همیشه Disposable را به یک CompositeDisposable اضافه کنید. این کار از نشت حافظه در Activity/Fragment نابودشده و به‌روزرسانی UI پس از نابودی جلوگیری می‌کند.
  2. از subscribeOn فقط یک‌بار، در ابتدای زنجیره استفاده کنید و در ادامه با observeOn جابه‌جا شوید.
  3. در جستجوها، از debounce + distinctUntilChanged + switchMap استفاده کنید.
  4. وقتی تعداد آیتم‌ها بسیار زیاد است، از Flowable و BackpressureStrategy استفاده کنید.
  5. خطاهای رایج را صریح مدیریت کنید. برای خطاهای گذرا، retry را با تعداد مشخص به کار ببرید.
  6. در کدهای اندرویدی، منابع را با try-with-resources یا try-catch/finally ببندید و در صورت نیاز اشتراک‌ها را آزاد کنید.

۱۴.۲ چک‌لیست نهایی

✅ چک‌لیستنحوهٔ انجام
داده‌ها به‌درستی برمی‌گردند؟همهٔ onNext، onComplete و onError

Scheduler صحیح برای UI؟observeOn(AndroidSchedulers.mainThread())
Backpressure برطرف می‌شود؟از Flowable و استراتژی مناسب
خطاها مدیریت می‌شوند؟onErrorReturn / retry / onErrorResumeNext
داده‌های تکراری حذف می‌شوند؟distinct / distinctUntilChanged

بخش ۱۵ساخت جریان: just، from، range، repeat، interval، timer

پیش از این‌که داده را transform کنید، باید یک Observable بسازید. در کنار create، متدهای ایستای زیر ۹۰٪ نیازهای روزمره را پوشش می‌دهند.

۱۵.۱ just و from — از مقادیر آماده

val numbers = Observable.just(1, 2, 3)          // از آرگومان‌ها
val names = Observable.fromIterable(listOf("A", "B", "C"))  // از کالکشن
val one = Observable.fromCallable { fetchFromDb() }         // lazy: هنگام subscribe اجرا می‌شود

numbers.subscribe { println(it) }

۱۵.۲ range و repeat — تولید الگویی

Observable.range(1, 5)          // ۱، ۲، ۳، ۴، ۵ سپس onComplete
Observable.just("tick").repeat(3)
Observable.range(0, 10).repeatWhen { it.zipWith(Observable.just(2)) { _, n -> n } }

۱۵.۳ interval و timer — زمان‌بندی

// هر ۵۰۰ میلی‌ثانیه یک نمونهٔ جدید (تیک ثانیه)
val ticker = Observable.interval(500, TimeUnit.MILLISECONDS)

ticker
    .observeOn(AndroidSchedulers.mainThread())
    .subscribe { second -> clock.text = "گذشته: $second ثانیه" }

// فقط یک تأخیر ۲ ثانیه‌ای، سپس onComplete
Observable.timer(2, TimeUnit.SECONDS)
    .subscribe { println("۲ ثانیه گذشت") }

کی از create استفاده کنیم؟ وقتی منبع داده‌تان callback محور است (websocket، listener سخت‌افزاری، addCallback)، با create { emitter -> … } آن را در یک Observable بپیچید و در onDispose listener را حذف کنید. برای بقیه‌ی موارد just/from/range کافی‌اند.

بخش ۱۶ترکیب جریان‌ها: merge، zip، combineLatest

گاهی چند جریان مستقل باید را با هم ترکیب کنید — مثلاً پروفایل کاربر و اعلان‌های هم‌زمان، یا متن جستجو و نتایج سرور. سه Operator پرکاربرد:

Operatorرفتارچه‌وقت استفاده کنیم؟
mergeهر دو جریان هم‌زمان می‌شوند؛ ترتیب تضمین نمی‌شودجریان‌های هم‌ارز مثل چند سنسور
zipآیتمِ n از جریان اول با آیتمِ n از دوم جفت می‌شود؛ تا رسیدن هر دو صبر می‌کندنتیجه + متادیتا، قیمت + نرخ ارز
combineLatestبه‌محض تغییر هر ورودی، با آخرین مقدارِ بقیه ترکیب می‌شودفرم‌ها (ایمیل + رمز)، ترکیب چند فیلد

۱۶.۱ merge — ادغام موازی

val location = locationUpdates()      // هر ۵ ثانیه
val heartbeat = heartBeat()           // هر ۲ ثانیه

Observable.merge(location, heartbeat)
    .observeOn(AndroidSchedulers.mainThread())
    .subscribe { event -> analytics.track(event) }

۱۶.۲ zip — جفت‌سازی هم‌شماره

Observable.zip(
    userSingle.toObservable(),
    postsSingle.toObservable(),
    BiFunction { user, posts -> ProfileScreen(user, posts) }
)
    .observeOn(AndroidSchedulers.mainThread())
    .subscribe { screen -> render(screen) }

۱۶.۳ combineLatest — آخرین وضعیت همه

Observable.combineLatest(
    emailInput.textChanges(),      // هر بار تغییر کند
    passwordInput.textChanges(),   // هر بار تغییر کند
    BiFunction { e, p -> e.isNotBlank() && p.length >= 8 }
).subscribe { enabled -> loginButton.isEnabled = enabled }
merge/join در برابر flatMap flatMap برای هر آیتمِ ورودی یک جریان داخلی می‌سازد؛ merge چند جریان آماده را کنار هم می‌گذارد. اگر جریان‌های داخلی را از روی داده می‌سازید، flatMap؛ اگر از قبل داریدشان، merge.

بخش ۱۷ابزارهای پیشرفته: DisposableObserver، RxBinding و تست

۱۷.۱ DisposableObserver — Observerای که لغوِ خودش را دارد

وقتی به یک Observer کامل نیاز دارید اما می‌خواهید خودش Disposable باشد، DisposableObserver را subclass کنید؛ خطر فراموش‌کردن dispose کم می‌شود: 

class SearchObserver : DisposableObserver<List<Item>>() {
    override fun onNext(items: List<Item>) = showResults(items)
    override fun onError(e: Throwable) = showError(e)
    override fun onComplete() = hideLoading()
}

// مثلاً در ViewModel:
private var searchObserver: SearchObserver? = null

fun search(query: String) {
    searchObserver?.dispose()
    SearchObserver().also { observer ->
        searchObserver = observer
        api.search(query)
            .debounce(300, TimeUnit.MILLISECONDS)
            .observeOn(AndroidSchedulers.mainThread())
            .subscribe(observer)          // خودش Disposable است
    }
}

۱۷.۲ RxBinding — رویدادهای UI به‌صورت جریان

RxTextView.textChanges(queryInput)          // از اولین مقدار هم شروع می‌کند
    .skip(1)                                // مقدار اولیهٔ EditText را رد کن
    .map { it.toString().trim() }
    .debounce(300, TimeUnit.MILLISECONDS)
    .distinctUntilChanged()
    .switchMap { q -> if (q.isEmpty()) Observable.empty() else api.search(q) }
    .observeOn(AndroidSchedulers.mainThread())
    .subscribe(::renderResults, ::renderError)
    .addTo(composite)                       // نصب RxBinding: io.reactivex.rxjava3.android.schedulers
عمیق‌تر: قابلیت تست زنجیره را جوری ببندید که TestObserver/TestSubscriber بتواند انتها وصل شود و با TestScheduler زمان را جلو ببرد: 
val scheduler = TestScheduler()
val observer = api.search("rx")
    .debounce(300, TimeUnit.MILLISECONDS, scheduler)
    .test()

observer.assertNoValues()
scheduler.advanceTimeBy(301, TimeUnit.MILLISECONDS)
observer.assertValueCount(1)          // بدون خوابِ واقعی در تست

۱۷.۳ RxJava یا Flow؟

  • کتابخانه/کد اشتراکی بدون اندروید: Kotlin Flow سبک‌تر است.
  • کد اندرویدی موجود با Rx: مهاجرت تدریجی با flowable.asFlow() و asObservable().
  • Operatorهای زمان‌سنج پیچیده (debounce/switchMap/zip ترکیبی): هنوز RxJava روان‌تر است.
جمع‌بندی: از Observable برای UI و رویدادها، از Flowable برای دادهٔ پرتکرار با backpressure، از Single/Maybe/Completable برای یک نتیجه استفاده کنید؛ همیشه Disposable را جمع کنید، خطاها را صریح مدیریت کنید و جستجو را با debounce + distinctUntilChanged + switchMap ببندید.
