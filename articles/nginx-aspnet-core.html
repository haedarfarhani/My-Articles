NGINX + ASP.NET Core؛ استقرار روی Linux

ASP.NET Core به‌لطف Kestrel روی Linux هم اجرا می‌شود، اما برای Production آن را پشت NGINX می‌گذاریم. این مقاله نحوه‌ی اجرای سرویس با systemd، انتقال هدرهای Forwarded و پشتیبانی از WebSocket را نشان می‌دهد.

بخش ۱مقدمه

ASP.NET Core دیگر فقط برای ویندوز نیست؛ روی Linux بسیار رایج شده است. الگوی استاندارد Microsoft این است: Kestrel به‌عنوان سرور HTTP داخلی روی یک پورت محلی، و NGINX در لبه برای TLS و پروکسی. این ترکیب هم سبک است و هم امن.

در این مقاله اجرای برنامه با systemd، پیکربندی upstream، خواندن هدرهای Forwarded و پیکربندی WebSocket پشت NGINX.
Prerequisites Reverse Proxy و Microsoft IIS.

بخش ۲چرا NGINX جلوی ASP.NET Core؟

دلیلتوضیح
TLS Terminationمدیریت گواهی و Cipherها در لبه، نه در برنامه
فایل استاتیکسرو سریع‌تر و کش بهتر توسط NGINX
محافظتRate Limit، محدودیت اندازه درخواست و فیلتر
Reverse Proxy استانداردالگوی رسمی Microsoft برای حفاظت Kestrel
الگوی رسمی مستندات ASP.NET Core برای Linux، اجرای برنامه پشت یک Reverse Proxy را «توصیه‌شده» می‌داند، نه اختیاری؛ چون Kestrel برای مواجهه‌ی مستقیم با اینترنت طراحی نشده است.

بخش ۳معماری Kestrel + NGINX

بخش ۴پیکربندی NGINX و systemd

server {
    listen 80;
    server_name app.example.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl http2;
    server_name app.example.com;
    ssl_certificate     /etc/letsencrypt/live/app.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/app.example.com/privkey.pem;

    location / {
        proxy_pass         http://127.0.0.1:5000;
        proxy_http_version 1.1;
        proxy_set_header   Host              $host;
        proxy_set_header   X-Real-IP         $remote_addr;
        proxy_set_header   X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header   X-Forwarded-Proto $scheme;
        proxy_set_header   Upgrade           $http_upgrade;   # WebSocket
        proxy_set_header   Connection        "upgrade";
        proxy_cache_bypass $http_upgrade;
    }
}
; /etc/systemd/system/myapp.service
[Unit]
Description=My ASP.NET Core App
After=network.target

[Service]
WorkingDirectory=/var/www/myapp
ExecStart=/usr/bin/dotnet /var/www/myapp/MyApp.dll
Restart=always
RestartSec=5
User=www-data
Environment=ASPNETCORE_ENVIRONMENT=Production
Environment=ASPNETCORE_URLS=http://127.0.0.1:5000

[Install]
WantedBy=multi-user.target
// Program.cs
builder.Services.Configure<ForwardedHeadersOptions>(o => {
    o.ForwardedHeaders = ForwardedHeaders.XForwardedFor |
                         ForwardedHeaders.XForwardedProto;
    o.KnownNetworks.Clear();     // در شبکه‌ی خصوصی قابل اعتماد
    o.KnownProxies.Clear();
});
app.UseForwardedHeaders();
Expected Behavior NGINX تنها روی 443 گوش می‌دهد، به 127.0.0.1:5000 پروکسی می‌کند و X-Forwarded-Proto می‌فرستد؛ برنامه در Redirectها و ساخت URL از https استفاده می‌کند.
نکته‌ی امنیتی KnownNetworks و KnownProxies خالی‌کردن فقط وقتی درست است که سرور فقط از طرف یک پروکسی قابل اعتماد در دسترس باشد؛ وگرنه مهاجم می‌تواند هدر جعل کند.

بخش ۵WebSocket و Production

برای SignalR یا WebSocket، باید NGINX هدرهای Upgrade و Connection را منتقل کند و Timeout طولانی داشته باشد؛ وگرنه اتصال‌های طولانی زودتر بسته می‌شوند.

موضوعتصمیم Production
WebSocket Timeoutproxy_read_timeout 3600s;
Keep-Aliveروشن با proxy_http_version 1.1
Health Check/health و نگه‌داشتن فرآیند با systemd
Loggingلاگ NGINX و stdout برنامه در مرکز لاگ
Envمتغیرها در Environment=، نه داخل فایل‌های برنامه
Kestrel مستقیم حالت inprocess فقط در IIS معنا دارد. روی Linux، Kestrel با NGINX جلوی آن، مدل استاندارد و سبک است.

بخش ۶جمع‌بندی

مزایامعایب
اجرای .NET روی Linux با هزینه‌ی پایینمدیریت دو سیستم (NGINX + systemd)
کارایی بالا و سبکیحساسیت هدرهای Forwarded
پشتیبانی خوب WebSocketنیاز به تنظیم دقیق Timeout
When to Useهر تیم .NET که می‌خواهد روی Linux با هزینه‌ی کمتر و انعطاف‌پذیری بیشتر اجرا کند.
When NOT to Useسازمانی که کاملاً روی ویندوز استاندارد شده؛ آنجا IIS ساده‌تر است.

ترکیب NGINX و ASP.NET Core روی Linux یک انتخاب بالغ و پرکاربرد است. با systemd، هدرهای Forwarded درست و Health Check، سرویسی پایدار خواهید داشت.
