بخش ۱چرا همزمانی؟ و چرا Thread به‌تنهایی کافی نیست

همزمانی (Concurrency) یعنی انجام چند کار در یک بازه‌ی زمانی، و موازی‌سازی (Parallelism) یعنی انجام هم‌زمان آن‌ها روی واحدهای پردازشی مجزا. این دو مفهوم یکی نیستند: برنامه‌ای می‌تواند همزمان باشد بدون این‌که موازی اجرا شود (مثلاً روی تک‌هسته، با سوییچ بین کارها) و برعکس.

در اپلیکیشن‌های امروزی، همزمانی دیگر «انتخاب» نیست؛ یک ضرورت است: درخواست شبکه، کوئری دیتابیس، رندر UI، پردازش تصویر، WebSockets و... همه باید هم‌زمان پیش بروند بدون این‌که رابط کاربری قفل (ANR) شود.

۱.۱ مشکل اصلی: وضعیت مشترک مبتنی بر Thread

اجزای اصلی مدل همزمانی سنتی (thread-per-task) سه مشکل ذاتی دارند:

  • Race Condition: وقتی دو thread روی یک متغیر مشترک بنویسند، ترتیب اجرا مشخص نیست و نتیجه غیرقطعی می‌شود.
  • Deadlock: دو thread که هر کدام منتظر قفل دیگری مانده‌اند؛ برنامه برای همیشه می‌ایستد.
  • هزینه‌ی بالا: هر thread حدود ۱ مگابایت پشته (stack) حافظه دارد، تعویض context گران است و تعداد آن‌ها محدود است.

۱.۲ Thread در برابر Coroutine

Kotlin راه‌حل مدرن ارائه می‌دهد: Coroutine — واحد اجرایی سبکی که روی thread‌ها سوار می‌شود، هنگام انتظار آزاد می‌شود و هزینه‌اش چندین مرتبه کمتر از thread است.

هزینه‌ی تعویضگران (switch to kernel)بسیار ارزان (در همان فضای کاربر)

عمیق‌تر: همزمانی ≠ موازی‌سازی Coroutine فقط زمانی موازی اجرا می‌شود که روی dispatcher موازی (مثل Dispatchers.Default) باشد. یک coroutine روی Dispatchers.Main همیشه تک‌رشته است. سبک‌بودن coroutine به معنای «سریع‌تر شدن محاسبات» نیست؛ به معنای «مدیریت ارزان‌تر انتظارها»ست.
هشدار: قفل کردن همیشه بد نیست synchronized یا Lock برای بلوک‌های کوتاه و کاملاً کنترل‌شده قابل قبول است. آن چه خطرناک است، نگه‌داشتن قفل در طول یک فراخوانی شبکه یا دیتابیس است — با coroutine این یعنی گرفتن یک thread کامل در تمام مدت انتظار.

بخش ۲Coroutine چیست و زیر کلاه چه می‌گذرد؟

Coroutine یک تابع قابل تعلیق (suspendable) است: می‌تواند وسط کار متوقف شود، thread را تحویل دهد، و بعداً — شاید روی thread دیگری — از همان‌جا ادامه یابد. کلید واژه‌ی suspend به کامپایلر می‌گوید این تابع می‌تواند «تعلیق» شود. 

suspend fun loadUser(id: Long): User {
    val raw = api.fetchUser(id)     // اینجا تعلیق: Thread آزاد می‌شود
    val avatar = imageLoader.load(raw.avatarUrl)
    cache.save(raw)
    return raw.copy(avatar = avatar)
}

// فراخوانی از یک CoroutineScope
viewModelScope.launch {
    _uiState.value = UiState.Loading
    _uiState.value = runCatching { loadUser(userId) }
        .fold({ UiState.Content(it) }, { UiState.Error(it.message) })
}

۲.۱ زیر کلاه: کامپایلر چه می‌کند؟

توابع suspend در زمان اجرا شبیه کد خطی به‌نظر می‌رسند، اما کامپایلر آن‌ها را به ماشین وضعیت (State Machine) تبدیل می‌کند: وضعیت اجرا در شیء Continuation ذخیره می‌شود، thread رها می‌شود، و هنگام ادامه، اجرا از همان وضعیت — روی هر thread‌ای — دوباره شروع می‌شود. به همین دلیل است که Coroutine به پشته‌ی عمیقی نیاز ندارد و انتقال بین thread‌ها کاملاً امن است.

عمیق‌تر: context از کجا می‌آید؟ هر Coroutine یک CoroutineContext دارد: مجموعه‌ای از Job، CoroutineDispatcher، CoroutineName، CoroutineExceptionHandler و مقادیر سفارشی شما. این context هنگام شروع snapshot می‌شود؛ بنابراین عوض‌کردن dispatcher فقط با withContext یا flowOn انجام می‌شود، نه با تغییر متغیر در حین اجرا.

بخش ۳Structured Concurrency: قانون طلایی

مهم‌ترین تفاوت Kotlin با راه‌حل‌های قدیمی همزمانی همین‌جاست. در Structured Concurrency هیچ coroutine‌ای «شناور» نیست؛ هر coroutine یک فرزند از یک scope محسوب می‌شود و سه تضمین دارد:

  1. سلسله‌مراتب: هر coroutine دارای یک Job پدر است که به‌عنوان والدِ همه‌ی فرزندان شناخته می‌شود.
  2. لغوی: لغو والد ⇒ لغو همه‌ی فرزندان (و فرزندانِ فرزندان، به‌صورت بازگشتی).
  3. انتظاری: والد فقط زمانی خاتمه می‌یابد که همه‌ی فرزندانش خاتمه یافته باشند — حتی اگر launch کرده باشید!

۳.۱ ترکیب چند عملیات موازی به‌صورت امن

suspend fun fetchDashboard(): Dashboard = coroutineScope {
    val profile = async { api.profile() }      // موازی
    val stats   = async { api.stats() }        // موازی
    val posts   = async { api.posts() }        // موازی

    // اگر هر کدام استثنا بدهد، coroutineScope بقیه را لغو می‌کند
    // و خطا را به فراخواننده می‌رساند
    Dashboard(profile.await(), stats.await(), posts.await())
}

coroutineScope یک scope موقت می‌سازد که منتظر همه‌ی فرزندانش می‌ماند و فقط بعد از اتمام همه، مقدار نهایی را برمی‌گرداند. این یعنی «موازی‌سازی بدون leak شدن coroutine».

۳.۲ Scopeهایی که خودتان می‌سازید

هر شیءای که lifecycle دارد، باید scope خودش را داشته باشد و هنگام مرگ، آن را لغو کند: 

class SearchRepository(
    private val api: SearchApi,
    private val dispatchers: AppDispatchers,
) : AutoCloseable {

    private val scope = CoroutineScope(
        SupervisorJob() + dispatchers.io + CoroutineName("search")
    )

    fun query(term: String): Flow<List<Result>> = flow {
        emit(api.search(term))
    }.flowOn(dispatchers.io)

    override fun close() {
        scope.cancel()          // همه‌ی فرزندان لغو می‌شوند
    }
}
آفت شماره ۱: Scope بدون مالک اگر scope را در init یک کلاس معمولی بسازید و جایی آن را cancel نکنید، coroutineهای آن بعد از مرگ شیء همچنان زنده می‌مانند و به شیء‌ای نیمه‌مرده دست می‌زنند (Leak). همیشه باید یک نقطه‌ی close()/cancel() صریح داشته باشید.

بخش ۴Job، چرخه حیات و لغو (Cancellation)

هر Coroutine یک Job دارد — دسته‌ای از عملیات با یک چرخه‌ی حیات. Deferred<T> همان Job است با یک مقدار خروجی. مراحل را ببینید:

۴.۱ لغو مشارکتی (Cooperative Cancellation)

لغو در Kotlin «مشارکتی» است: فراخوانی cancel() فقط یک درخواست است. coroutine تنها در نقطه‌های تعلیق (delay، suspendCall،...) متوقف می‌شود. اگر وسط یک حلقه‌ی سنگین CPU باشید، تا پایان حلقه متوقف نمی‌شود — باید خودتان همکاری کنید: 

launch {
    try {
        while (isActive) {                 // بررسی وضعیت
            heavyComputeChunk()
            ensureActive()                 // اگر لغو شده، CancellationException پرتاب کن
            yield()                        // فرصت اجرا به coroutineهای دیگر بده
            delay(50)                      // تعلیق واقعی: هم لغو، هم صرفه‌جویی CPU
        }
    } finally {
        // بلوک finally هنگام لغو هم اجرا می‌شود
        withContext(NonCancellable) {      // اما تعلیق در آن مجاز نیست!
            releaseResources()
            db.flush()
        }
    }
}
نکته‌ی حیاتی: CancellationException را نبلعید catch (e: Throwable) در یک coroutine، خطای لغو را هم می‌گیرد و برنامه‌ی شما به‌جای لغوِ واقعی، «ادامه» می‌دهد — یعنی coroutine خراب لغو نمی‌شود و scope فکر می‌کند همه‌ی فرزندان سالم‌اند. اگر لازم است استثناهای دیگر را بگیرید، حتماً CancellationException را دوباره پرتاب کنید: 
try {
    doWork()
} catch (e: CancellationException) {
    throw e                              // ← هرگز حذف نکنید
} catch (e: Exception) {
    report(e)
}

۴.۲ محدوده‌ی زمانی (Timeout)

val user = withTimeout(3_000) { api.fetchUser(id) }   // استثنا در صورت تأخیر

val userOrNull = withTimeoutOrNull(3_000) { api.fetchUser(id) }  // null در صورت تأخیر

نکته‌ی پیشرفته: withTimeout هم مثل cancel() عمل می‌کند؛ اگر درون آن منابعی دارید که باید حتماً آزاد شوند، از try/finally با NonCancellable استفاده کنید.

بخش ۵Dispatcherها: کدام Coroutine روی کدام Thread؟

Coroutine خودش تصمیم نمی‌گیرد کجا اجرا شود؛ این Dispatcher است که مشخص می‌کند کد روی کدام thread (یا استخر thread) برود. انتخاب اشتباه dispatcher یعنی قفل شدن UI یا هدر رفتن هسته‌های CPU.

Dispatcherمناسب براینوع کارمنابع
Main / Main.immediateUI اندروید، Swing/JavaFXکار سبک و به‌روزرسانی رابط کاربریتک‌رشته
Defaultمحاسبات سنگین CPUرمزنگاری، تجزیه، مرتب‌سازی، پردازش تصویرتعداد هسته‌ها (حداقل ۲)
IOشبکه، دیسک، دیتابیس، فایلعملیات blocking یا I/O محورتا ۶۴ thread (مشترک با Default)
Unconfinedتست و موارد خاصبدون تغییرِ dispatcher؛ تا اولین تعلیق در همان thread—
TestDispatcherتست با زمان مجازیStandardTestDispatcher / UnconfinedTestDispatcher—

۵.۱ جابه‌جایی با withContext و flowOn

suspend fun readConfig(path: String): Config = withContext(Dispatchers.IO) {
    // کل این بلوک روی IO اجرا می‌شود
    val raw = File(path).readText()
    parse(raw)
}
// اینجا به dispatcher قبلی (مثلاً Default) برمی‌گردیم — ترتیبی، نه موازی

val uiFlow = repo.watch()          // اجرای upstream روی IO
    .flowOn(Dispatchers.IO)        // فقط بخش بالای flow را جابه‌جا می‌کند
    .map { it.toUiModel() }

۵.۲ کنترل موازی‌سازی با limitedParallelism

// سهمیه‌ی جداگانه تا یک نوع کار، کل استخر را نبلعد
private val diskLimiter = Dispatchers.IO.limitedParallelism(4)
private val heavyCpu = Dispatchers.Default.limitedParallelism(8)

suspend fun loadAllImages(urls: List<String>) = coroutineScope {
    urls.map { url ->
        async(diskLimiter) { downloadAndCache(url) }
    }.awaitAll()
}
DI کردن Dispatcherها = تست‌پذیری Dispatcherها را hard-code نکنید؛ از یک کلاس تنظیمات وارد کنید تا در تست‌ها قابل تعویض باشند: 
data class AppDispatchers(
    val main: CoroutineDispatcher = Dispatchers.Main.immediate,
    val io: CoroutineDispatcher = Dispatchers.IO,
    val default: CoroutineDispatcher = Dispatchers.Default,
)
هشدارهای dispatcher • هرگز روی Dispatchers.Default فراخوانی blocking (مثل Thread.sleep، Socket، I/O فایل) نزنید؛ هسته‌ها را قفل می‌کنید.
• Dispatchers.Main.immediate اگر همین حالا روی thread اصلی باشید، dispatch مجدد ندارد و از پرش‌های بی‌جهت جلوگیری می‌کند.
• Unconfined در production رفتار غیرقابل پیش‌بینی (re-entrancy و پشته‌ی عمیق) دارد؛ فقط برای تست مناسب است.

بخش ۶launch، async، runBlocking و withContext

۶.۱ موازی‌سازی واقعی با async

suspend fun prefetch(ids: List<Long>): List<Item> = coroutineScope {
    ids.map { id ->
        async(dispatchers.io) { repository.load(id) }   // اجرای موازی
    }.awaitAll()                                        // انتظار همه + جمع‌آوری خطاها
}

نکته‌ی پیشرفته: async استثنا را «ذخیره» می‌کند تا await() آن را پرتاب کند؛ اما این بدان معنا نیست که scope آرام می‌ماند — طبق قواعد structured concurrency، استثناهای async هم والد را لغو می‌کنند. تنها استثنا: scope مبتنی بر SupervisorJob (بخش ۷).

۶.۲ با withContext یا با async؟

  • withContext = «همین کار را روی dispatcher دیگری ادامه بده» — ترتیبی است و موازی‌سازی نمی‌کند.
  • async = «این کار را هم‌زمان شروع کن و بعداً نتیجه را بگیر» — برای موازی‌سازی چند فراخوانی مستقل.
// ترتیبی (با withContext): اول شبکه، بعد دیتابیس — متوالی
suspend fun loadSequential(): Data = withContext(Dispatchers.IO) {
    val remote = api.fetch()
    db.save(remote)
    remote
}

// موازی (با async): هر دو هم‌زمان
suspend fun loadParallel(): Data = coroutineScope {
    val remote = async(Dispatchers.IO) { api.fetch() }
    val cached = async(Dispatchers.IO) { db.read() }
    merge(remote.await(), cached.await())
}

۶.۳ runBlocking فقط در نقطه‌ی ورود

// درست: تبدیل دنیای suspend به دنیای blocking در نقطه‌ی ورود
fun main() = runBlocking {
    launch { doWork() }.join()
}

// اشتباه در اندروید: رشته‌ی UI را قفل می‌کند ← ANR
// fun onCreate() { runBlocking { ... } }   ✗
Anti-pattern: runBlocking در کتابخانه یا ViewModel runBlocking یک coroutine را به thread فراخواننده گره می‌زند. در اندروید یعنی قفل شدن UI، در سرور یعنی از دست رفتن یک worker thread و افت شدید throughput. تنها جای مجاز: main()، نقاط ورود CLI، و تست‌هایی که به runTest دسترسی ندارند.

بخش ۷مدیریت خطا: SupervisorJob و CoroutineExceptionHandler

در structured concurrency، خطا هم «ساخت‌یافته» منتشر می‌شود. چهار قانون را حفظ کنید:

  1. استثنای یک فرزند ← والد لغو می‌شود ← همه‌ی فرزندان دیگر لغو می‌شوند ← خطا تا ریشه بالا می‌رود.
  2. استثناهای CancellationException «طبیعی» هستند و به والد گزارش نمی‌شوند.
  3. در ریشه، اگر CoroutineExceptionHandler باشد صدا زده می‌شود؛ وگرنه به thread منتقل و موجب کرش می‌شود.
  4. try/catch دورِ launch کمکی نمی‌کند، چون استثنا به‌صورت ناهمزمان پرتاب می‌شود — استثنا را درون بدنه بگیرید.

۷.۱ الگوی کامل مدیریت خطا

val appScope = CoroutineScope(
    SupervisorJob() +
    Dispatchers.IO +
    CoroutineName("app") +
    CoroutineExceptionHandler { context, throwable ->
        CrashReporter.record(throwable, context[CoroutineName]?.name)
    }
)

// فرزندان مستقل: خرابی یکی، بقیه را نمی‌کشد
suspend fun syncAll() = supervisorScope {
    launch { syncContacts() }
    launch { syncCalendar() }
    launch { syncPhotos() }
    // همه‌شان join می‌شوند؛ خطاها جداگانه به handler می‌رسند
}
// خطای کنترل‌شده داخل launch — نه دورِ آن!
viewModelScope.launch {
    val state = try {
        val data = repository.refresh()
        UiState.Content(data)
    } catch (e: CancellationException) {
        throw e                       // لغو را حفظ کن
    } catch (e: Exception) {
        UiState.Error(e.message ?: "خطای ناشناخته")
    }
    _uiState.value = state
}
تله‌ی runCatching runCatching همه‌ی Throwableها را می‌گیرد؛ یعنی CancellationException را هم می‌بلعد و جریان لغو را می‌شکند. اگر در coroutine از آن استفاده می‌کنید، لغو را دوباره پرتاب کنید یا از try/catch صریح استفاده نمایید.

بخش ۸Flow: ریخت‌درمانی داده به‌صورت غیرمسدودکننده

Flow<T> جریانی از مقادیر غیرمسدودکننده است: انتظار بین دو مقدار، thread را آزاد می‌کند. Flow سرد (Cold) است: منبع فقط زمانی اجرا می‌شود که کسی collect کند و هر collector یک اجرای مستقل دارد.

۸.۱ ساخت و مصرف یک Flow

fun search(query: Flow<String>): Flow<List<Result>> =
    query
        .debounce(300)                 // صبر تا وقفه‌ی تایپ
        .distinctUntilChanged()
        .flatMapLatest { term ->       // جستجوی قبلی را لغو کن
            flow {
                emit(api.search(term))
            }.flowOn(Dispatchers.IO)
        }
        .catch { e -> emit(emptyList()) }   // فقط خطاهای بالادست را می‌گیرد

// مصرف:
lifecycleScope.launch {
    repeatOnLifecycle(Lifecycle.State.STARTED) {
        search(_query).collect { results ->
            adapter.submit(results)
        }
    }
}

۸.۲ قواعد طلایی Flow

  • Context Preservation: نمی‌توانید در flow builder روی dispatcher دیگری emit کنید؛ فقط با flowOn بالادست را جابه‌جا کنید.
  • شفافیت خطا: operator سردشده‌ی catch فقط خطاهای بالادست را می‌بیند؛ خطای داخل collect مال شماست.
  • انفصال (Cancellation): لغوِ collector جریان را می‌بُرد؛ هر منبع باید try/finally یا awaitClose داشته باشد.
  • Backpressure: buffer()، flowOn(n) و conflate() رفتار بین تولیدکننده و مصرف‌کننده را تنظیم می‌کنند.
// تبدیل callback به Flow — با بستن منبع هنگام لغو
fun locationUpdates(): Flow<Location> = callbackFlow {
    val callback = object : LocationCallback() {
        override fun onLocationResult(loc: Location) {
            trySend(loc)               // اگر بافر پر باشد، بسته به strategy
        }
    }
    client.requestUpdates(callback)
    awaitClose { client.removeUpdates(callback) }   // لغو ← تمیزکاری
}.buffer(Channel.CONFLATE)
عمیق‌تر: buffer کجای ماجراست؟ Flow بر پایه‌ی Channel ساخته شده است. flowOn(n) یعنی یک بافر nتایی میان تولید و مصرف؛ conflate() یعنی فقط آخرین مقدار مهم است؛ buffer(Channel.UNLIMITED) یعنی هرگز منتظر نمان — که اگر مصرف‌کننده کند باشد، حافظه را منفجر می‌کند. بافر را متناسب با «اهمیت هر مقدار» انتخاب کنید.

۹.۱ Conflation: چرا میانی‌ها گم می‌شوند؟

۹.۲ الگوی استاندارد UiState

data class UiState(
    val loading: Boolean = false,
    val items: List<Item> = emptyList(),
    val error: String? = null,
)

class ArticleViewModel(
    private val repo: ArticleRepository,
) : ViewModel() {

    private val _state = MutableStateFlow(UiState())
    val state: StateFlow<UiState> = _state.asStateFlow()   // فقط خواندنی بیرون

    fun refresh() = viewModelScope.launch {
        _state.update { it.copy(loading = true, error = null) }   // atomic
        val next = runCatching { repo.fetch() }
        _state.update {
            next.fold(
                onSuccess = { items -> it.copy(loading = false, items = items) },
                onFailure = { e -> it.copy(loading = false, error = e.message) },
            )
        }
    }
}
چرا update به‌جای value = ...؟ _state.value = ... یک read-modify-write غیراتمیک است؛ اگر دو coroutine هم‌زمان بنویسند، یک تغییر گم می‌شود. update { } با حلقه‌ی Compare-And-Swap کار می‌کند و همیشه از آخرین مقدار شروع می‌کند.

بخش ۱۰Channel: پیام بین Coroutineها

اگر Flow «ریخت‌درمانی داده» است، Channel «لوله‌ی پیام میان تولیدکننده و مصرف‌کننده» است: دو طرف دارد، send و receive دارد، و مهم‌تر از همه Backpressure واقعی دارد — یعنی وقتی مصرف‌کننده کند است، تولیدکننده منتظر می‌ماند (یا طبق سیاست، پیام‌ها را دور می‌ریزد).

۱۰.۱ الگوی چند Worker موازی

suspend fun processAll(files: List<File>) = coroutineScope {
    val channel = Channel<File>(capacity = 16)

    // ۴ worker که از کانال می‌خورند
    repeat(4) { id ->
        launch(dispatchers.default) {
            channel.consumeEach { file ->
                println("worker $id → ${file.name}")
                process(file)
            }
        }
    }

    // تولیدکننده
    try {
        files.forEach { channel.send(it) }
    } finally {
        channel.close()          // پایان جریان را اعلام کن
    }
}

۱۰.۲ تولید مقدار با produce

fun squares(): ReceiveChannel<Int> = produce {
    for (x in 1..10) send(x * x)   // به محض لغوِ مصرف‌کننده، بسته می‌شود
}

suspend fun use() = coroutineScope {
    val ch = squares()
    for (v in ch) println(v)

actor دیگر قدیمی است Builder مربوط به actor { } با @ObsoleteCoroutinesApi علامت خورده است. برای پیاده‌سازی الگوی Actor (پیام‌محور بدون state مشترک) از یک Channel درونی با while (isActive)، یا از SharedFlow پخش پیام استفاده کنید.

۱۱.۱ Mutex: قفلِ تعلیقی

class SessionCache {
    private val mutex = Mutex()
    private val sessions = mutableMapOf<String, Session>()

    suspend fun getOrCreate(token: String): Session = mutex.withLock {
        sessions.getOrPut(token) { createSession(token) }
    }
}

// قفل را هرگز دورِ یک انتظار بلند نگیرید:
mutex.withLock {
    // ✗ delay()، شبکه یا دیتابیس اینجا یعنی بقیه منتظر می‌مانند
}
عمیق‌تر: چرا synchronized با coroutine مشکل دارد؟ synchronized یک thread را تا پایان بلوک نگه می‌دارد. اگر درون آن delay() یا فراخوانی شبکه بزنید، آن thread عملاً «قرض» گرفته می‌شود — با صدها coroutine، استخر IO از کار می‌افتد. Mutex به‌جای نگه‌داشتن thread، coroutine را suspend می‌کند و thread را به کار دیگری می‌سپارد.

۱۱.۲ Atomic و Compare-And-Swap

// شمارنده‌ی اتمیک
private val counter = atomic(0)                 // kotlinx-atomicfu
fun inc(): Int = counter.incrementAndGet()

// StateFlow خودش اتمیک است — همیشه update استفاده کنید
_state.update { it.copy(count = it.count + 1) }

// CAS دستی وقتی منطق پیچیده است
fun incrementCount() {
    while (true) {
        val cur = state.get()
        val next = cur.copy(count = cur.count + 1)
        if (state.compareAndSet(cur, next)) return
    }
}
@Volatile کافی نیست @Volatile فقط دیده‌شدن مقدار جدید را در همه‌ی thread‌ها تضمین می‌کند، نه اتمیک بودنِ عملیاتِ خواندن-نوشتن. شمارنده با @Volatile++ همچنان Race Condition دارد؛ برای آن Atomic یا Mutex بخواهید.

۱۱.۳ محدود کردن همزمانی با Semaphore

private val limiter = Semaphore(8)   // حداکثر ۸ درخواست هم‌زمان

suspend fun downloadAll(urls: List<String>) = coroutineScope {
    urls.map { url ->
        async {
            limiter.withPermit {      // اجازه‌ی ورود = دسترسی به منبع
                download(url)
            }
        }
    }.awaitAll()
}

Semaphore بهتر از limitedParallelism است وقتی محدودیت مربوط به یک منبع خارجی است (مثلاً سقف نرخ یک API) و می‌خواهید روی چند dispatcher پخش شود.

عمیق‌تر: بهترین قفل، نبودِ قفل است بهترین «قفل»، نبودِ state مشترک است. یک coroutine واحد که از Channel پیام می‌گیرد و state را مالکیت می‌کند (الگوی Actor)، نه برنامه‌نویس را با قفل درگیر می‌کند نه با CAS. اگر منطق همزمانی‌تان پیچیده شد، به‌جای لایه‌ی قفلِ سوم، ساختار را بازنویسی کنید: مالکیت داده در یک محل، پیام‌دهی با Channel.

۱۲.۴ خطا‌محور: تلاش مجدد با Backoff

suspend fun <T> retryWithBackoff(
    times: Int = 3,
    factor: Double = 2.0,
    block: suspend () -> T,
): T {
    var current = block()
    var attempt = 0
    while (true) {
        try {
            return current
        } catch (e: CancellationException) {
            throw e
        } catch (e: Exception) {
            if (++attempt >= times) throw e
            delay((100L * factor.pow(attempt)).toLong())
            current = block()
        }
    }
}

۱۳.۱ یک Lifecycle کامل و امن

class SyncManager(
    private val api: SyncApi,
    dispatchers: AppDispatchers,
) : Closeable {

    private val scope = CoroutineScope(
        SupervisorJob() + dispatchers.io + CoroutineExceptionHandler { _, t ->
            log.error("sync failed", t)
        }
    )

    private var loop: Job? = null

    fun startPeriodic() {
        loop?.cancel()
        loop = scope.launch {
            while (isActive) {
                runCatching { api.syncAll() }
                    .onFailure { if (it is CancellationException) throw it }
                delay(60_000)
            }
        }
    }

    override fun close() {
        scope.cancel()          // همه‌ی فرزندان، از جمله حلقه، لغو می‌شوند
    }
}
پرفورمنس: قبل از بهینه‌سازی، اندازه بگیرید • ایجاد Coroutine ارزان است، ولی در حلقه‌های میلیونی هم مهم می‌شود؛ کارهای ریز را دسته‌بندی کنید.
• Dispatchers.IO بین همه‌ی کارهای I/O مشترک است؛ یک انتظارِ طولانیِ غیرلازم می‌تواند سهمیه‌ی ۶۴تایی را پر کند.
• انتشار یک مقدارِ پُرحجم در StateFlow، هر بار کپی/محاسبه‌ی equal دارد؛ مدل‌های UI را سبک نگه دارید.
• برای ادعای سرعت، از androidx.benchmark یا JMH استفاده کنید — «احساس» معیار خوبی نیست.

            val loading = awaitItem()
            assertTrue(loading.loading)

            advanceUntilIdle()      // همه‌ی coroutineها تمام شدند

            val loaded = awaitItem()
            assertEquals(2, loaded.books.size)
            cancelAndIgnoreRemainingEvents()
        }
    }

    @Test
    fun `error is mapped to ui state`() = runTest {
        val viewModel = SearchViewModel(FailingRepository(), StandardTestDispatcher(testScheduler))
        viewModel.onQueryChange("x")
        advanceUntilIdle()
        assertNotNull(viewModel.uiState.value.error)
    }
}
API تستچه می‌کند؟
runTest { }جایگزین runBlocking؛ زمان مجازی + تایم‌اوت ایمن
StandardTestDispatcherزمان‌بندی سخت‌گیرانه؛ کارها فقط با runCurrent/advanceUntilIdle اجرا می‌شوند (برای ترتیب دقیق)
UnconfinedTestDispatcherبدون انتظار؛ برای تست‌های ساده بدون ترتیب حساس
advanceTimeBy(ms)پیشروی زمان مجازی (delayها را آزاد می‌کند)
advanceUntilIdle()تا خالی شدن صفِ همه‌ی coroutineها جلو برو
backgroundScopeبرای حلقه‌های بی‌پایانِ تست (لغو خودکار در پایان)
دو قانون طلایی تست ۱) هرگز در تست واقعی منتظر delay نمانید — با زمان مجازی، کل تست در میلی‌ثانیه تمام می‌شود.
۲) Dispatcherها را inject کنید؛ تستِ کدی که Dispatchers.IO را hard-code کرده، کند و شکننده است.

۱۵.۱ ViewModel با UiState و رویدادهای یک‌بارمصرف

sealed interface UiEvent {
    data class ShowMessage(val text: String) : UiEvent
    data object NavigateBack : UiEvent
}

class ArticlesViewModel(
    private val repo: ArticlesRepository,
    savedState: SavedStateHandle,
) : ViewModel() {

    private val query = savedState.getStateFlow(KEY_QUERY, "")

    private val _events = MutableSharedFlow<UiEvent>(
        extraBufferCapacity = 1,                 // برای رویدادهای یک‌بارمصرف
        onBufferOverflow = BufferOverflow.DROP_OLDEST,
    )
    val events: SharedFlow<UiEvent> = _events.asSharedFlow()

    val uiState: StateFlow<ArticlesUiState> = query
        .debounce(300)
        .distinctUntilChanged()
        .flatMapLatest { q ->
            if (q.isBlank()) flowOf(ArticlesUiState.Content(emptyList()))
            else flow { emit(ArticlesUiState.Loading) }
                .onCompletion { emitAll(repo.search(q).map { ArticlesUiState.Content(it) }) }
        }
        .catch { emit(ArticlesUiState.Error(it.message ?: "خطا")) }
        .stateIn(viewModelScope, SharingStarted.WhileSubscribed(5_000), ArticlesUiState.Initial)

    fun onQueryChange(value: String) { savedState[KEY_QUERY] = value }

    fun onFavorite(article: Article) = viewModelScope.launch {
        val ok = runCatching { repo.toggleFavorite(article) }.isSuccess
        _events.emit(UiEvent.ShowMessage(if (ok) "ذخیره شد" else "خطا در ذخیره"))
    }

    private companion object { const val KEY_QUERY = "query" }
}

۱۵.۴ کار تضمین‌شده با WorkManager

class SyncWorker(
    appContext: Context,
    params: WorkerParameters,
) : CoroutineWorker(appContext, params) {

    override suspend fun doWork(): Result = try {
        syncRepo.pull()
        Result.success()
    } catch (e: CancellationException) {
        throw e
    } catch (e: Exception) {
        Result.retry()                // با backoff کارگزار سیستم دوباره تلاش می‌کند
    }
}

قاعده: کاری که باید حتی بعد از بسته شدن اپ انجام شود → WorkManager؛ کاری که به عمر UI یا Session گره خورده → viewModelScope / scope اختصاصی.

بخش ۱۶جمع‌بندی، چک‌لیست و منابع

همزمانی در Kotlin سه ستون دارد: Coroutine سبک که انتظار را ارزان می‌کند، Structured Concurrency که عمر و خطا را ساخت‌یافته نگه می‌دارد، و Flow که داده را به‌صورت غیرمسدودکننده بین لایه‌ها جابه‌جا می‌کند. هر جا این سه را رعایت کنید، کد هم‌زمانی‌تان هم خوانا می‌شود هم قابل تست.

۱۶.۱ چک‌لیست کدِ همزمانیِ سالم

  1. هر scope یک مالک دارد و در نقطه‌ی مرگِ شیء، cancel() می‌شود — نه GlobalScope.
  2. Dispatcherها درست انتخاب شده‌اند: UI روی Main، محاسبه روی Default، blocking روی IO — و inject‌پذیرند.
  3. حلقه‌ها while (isActive) دارند و به‌جای Thread.sleep از delay استفاده می‌کنند.
  4. CancellationException هیچ‌جا بلعیده نمی‌شود؛ runCatching در coroutine با احتیاط.
  5. خطای بدون handler نداریم: یا در UiState، یا CoroutineExceptionHandler.
  6. state مشترک یا با update{}/Mutex اتمیک است، یا اصلاً وجود ندارد (پیام با Channel).
  7. ابزار جریان درست انتخاب شده: Flow / StateFlow / SharedFlow / Channel.
  8. در UI با repeatOnLifecycle یا collectAsStateWithLifecycle جمع‌آوری می‌شود.
  9. تست‌ها با runTest و زمان مجازی‌اند و نتیجه‌ی قطعی دارند.
  10. کارِ تضمینِ اجرا (پس‌زمینه/بعد از بسته شدن اپ) با WorkManager، نه coroutine خام.
