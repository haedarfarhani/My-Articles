بخش ۱مقدمه: وقتی چرخش صفحه همه‌چیز را پاک می‌کند

یک فرم پروفایل کاربر را تصور کنید. کاربر نام و ایمیل را تایپ می‌کند و در حالی که دارد شهر را انتخاب می‌کند، گوشی را می‌چرخاند. اگر وضعیت در Activity نگه‌داری شده باشد، همه‌ی آن‌ها پاک می‌شود و کاربر باید از اول شروع کند.

این یعنی کاربر هر بار که گوشی را بچرخاند یا از اپ خارج و وارد شود، باید دوباره همه‌چیز را وارد کند. برای دیتابیسی که با هر بار خواندن، یک درخواست شبکه می‌فرستد، این هم کند است هم هزینه‌بر. 

مشکل دوگانه:

  ۱) وضعیت UI (تایپ کاربر، اسکرول، انتخاب تب)
     → با چرخش صفحه یا خروج از اپ از بین می‌رود

  ۲) منطق UI (کی دکمه فعال است، چه پیامی نشان دهم)
     → داخل کلاس Activity است و تست‌ناپذیر

راه‌حل: یک کلاس که زنده می‌ماند و وضعیت را نگه می‌دارد
        → ViewModel
ریشه‌ی مشکل ViewModel در اندروید یک کلاس است که سیستم نگهش می‌دارد تا وقتی کاربر اپ را ببندد باقی می‌ماند، اما وقتی Activity واقعاً تمام شود (مثلاً فشار دکمه‌ی Back در حالتی که صفحه در پشته باقی نمی‌ماند) پاک می‌شود. یعنی دقیقاً عمر مورد نیاز شما را دارد.

بخش ۳MVVM چیست؟ (تعریف دقیق)

تعریف رسمی MVVM یک الگوی معماری است که برنامه را به سه نقش تقسیم می‌کند: Model (داده و قواعد کسب‌وکار)، View (رابط کاربری کاملاً منفعل) و ViewModel (که وضعیت صفحه و منطق نمایش را نگه می‌دارد). ViewModel به View ارجاع مستقیم ندارد؛ یعنی می‌توان آن را کاملاً بدون اندروید تست کرد.
نقشمسئولیتنمونه
Modelداده و قوانین کسب‌وکار؛ منبع حقیقتUser، UserRepository
ViewModelوضعیت صفحه، تبدیل داده به فرمت نمایشی، مدیریت چرخه‌ی حیاتProfileViewModel
Viewنمایش داده‌ی ViewModel و ارسال رویداد به آنProfileFragment + layout
سه اصل بنیادین MVVM ۱) ViewModel هرگز View را نمی‌بیند — نه Context، نه View، نه Fragment.
۲) ViewModel زنده می‌ماند — با چرخش صفحه و تغییر پیکربندی از دست نمی‌رود.
۳) ViewModel وضعیت را نگه می‌دارد — نه View، نه Activity.
سوءتفاهم رایج MVVM با MVP تقریباً یکسان به نظر می‌رسد، اما یک تفاوت حیاتی دارد: در MVP، View باید صریحاً از Presenter داده بگیرد (Presenter مستقیماً متدهای View را صدا می‌زند)؛ در MVVM، ViewModel وضعیت را منتشر می‌کند و View خودش آن را مشاهده (observe) می‌کند و به‌روز می‌شود. همین تفاوت، تمام قدرت MVVM است.

    protected void onCreate(Bundle savedInstanceState) {
        super.onCreate(savedInstanceState);
        setContentView(R.layout.activity_profile);

        nameInput  = findViewById(R.id.name);
        emailInput = findViewById(R.id.email);
        citySpinner = findViewById(R.id.city);
        saveButton = findViewById(R.id.save);

        // ۱) هر بار ساخت صفحه، دوباره درخواست شبکه
        api.fetchUser(getIntent().getStringExtra("user_id"))
           .enqueue(new Callback<User>() {
               @Override
               public void onResponse(Call<User> call, Response<User> r) {
                   // ۲) منطق نمایش در Callback
                   loadedUser = r.body();
                   nameInput.setText(loadedUser.getName());
                   saveButton.setEnabled(isValid(loadedUser));
               }
               @Override
               public void onFailure(Call<User> call, Throwable t) {
                   // ۳) خطا فقط با Toast
                   Toast.makeText(ProfileActivity.this,

               }
           });

        nameInput.addTextChangedListener(new TextWatcher() {
            @Override public void afterTextChanged(Editable s) {
                saveButton.setEnabled(s.length() > 2);
            }
        });
    }

    private boolean isValid(User user) {
        return user.getName().length() > 2 && user.getCity() != null;
    }
}

بخش ۵ایده اصلی: ViewModel و وضعیت

ViewModel چیست؟ کلاسی که سیستم برای مدت حیات یک صفحه (یا Activity) در حافظه نگه می‌دارد و با چرخش صفحه و تغییر پیکربندی از بین نمی‌رود. اگر کاربر اپ را کامل ببندد، پاک می‌شود — که درست همان چیزی است که می‌خواهیم. 
سه سطح مسئولیت در MVVM:

  Model      : "قیمت محصول چقدر است؟"      → داده خام و قانون کسب‌وکار
  ViewModel  : "با ۹٪ تخفیف نمایش بده"    → تبدیل داده به فرمت نمایشی
  View       : "این متن را روی صفحه بنویس"  → فقط اجرای دستور

سؤال راهنما برای هر خط کد:
  این خط به دیتابیس وصل می‌شود؟      → Model
  این خط رشته‌ی نمایشی می‌سازد؟      → ViewModel
  این خط فقط صفحه را تغییر می‌دهد؟    → View
تفاوت کلیدی با MVP در MVP، Presenter متدهایی مثل view.setName(...) را روی View صدا می‌زند؛ یعنی View باید در زمان اجرا وجود داشته باشد. در MVVM، ViewModel فقط LiveData منتشر می‌کند. اگر View نبود (مثلاً در تست)، ViewModel همچنان کار می‌کند — و همین تست را ممکن می‌سازد.

بخش ۷جریان داده (Data Flow)

دو جریان در MVVM:

  ۱) جریان یک‌طرفه (View → ViewModel)
     View رویداد کاربر را به متد ViewModel می‌دهد.
     ViewModel وضعیت را به‌روز و LiveData را منتشر می‌کند.

  ۲) جریان مشاهده (ViewModel → View)
     View با observe() به LiveData گوش می‌دهد و هر تغییر را رندر می‌کند.

نکته: هر دو جریان از وسط (ViewModel) می‌گذرند.
ViewModel تنها منبع حقیقت برای وضعیت صفحه است.
چرخه‌ی حیات‌آگاه بودن اگر Activity در حالت STOPPED باشد، LiveData فعال نمی‌شود و View به‌روزرسانی نمی‌شود. وقتی Activity دوباره STARTED می‌شود، LiveData آخرین مقدار را بلافاصله به View می‌دهد. این یعنی UI همیشه آخرین وضعیت را نشان می‌دهد، حتی اگر مدتی در پس‌زمینه بوده باشد.

بخش ۹مثال عملی کامل: صفحه‌ی پروفایل کاربر

  • کاربر صفحه‌ی پروفایل را باز می‌کند؛ ViewModel در onInit داده را می‌خواند.
  • ViewModel داده خام را به UiState تبدیل می‌کند (مثلاً قالب‌بندی تاریخ تولد).
  • View به LiveData مشاهده می‌کند و مقادیر را در UI می‌گذارد.
  • کاربر نام را تغییر می‌دهد؛ ViewModel وضعیت را به‌روز می‌کند و دکمه‌ی ذخیره فعال می‌شود.
  • با چرخش صفحه، ViewModel باقی می‌ماند و همه‌ی این وضعیت حفظ می‌شود.
توزیع مسئولیت در سناریو:

  «کاربر در این آدرس زندگی می‌کند»
      → Model (User entity، روش getAddress())

  «آدرس را به این شکل نمایش بده»
      → ViewModel (تبدیل آدرس به رشته‌ی نمایشی)

  «آدرس را در TextView نشان بده»
      → View (setText)

اگر فردا UI را عوض کنیم (مثلاً آدرس روی نقشه نشان داده شود)،
فقط View تغییر می‌کند. منطق در ViewModel و مدل ثابت می‌ماند.
نمونه‌ی اشتباه رایج اگر ViewModel شامل new TextView(context) باشد، دیگر ViewModel نیست. اگر ViewModel به getApplication() نیاز داشته باشد، تست آن سخت می‌شود. ViewModel باید یک کلاس Java/Kotlin خالص باشد — فقط با ورودی و خروجی.

UiState

package com.example.ui.common;

/**
 * وضعیت کامل صفحه‌ی پروفایل. هر حالت ممکن صفحه دقیقاً یک حالت از این رکورد است.
 */
public record ProfileUiState(
        boolean loading,
        String displayName,
        String formattedAddress,
        String avatarUrl,
        boolean saveEnabled,
        String errorMessage) {

    public static ProfileUiState loading() {
        return new ProfileUiState(true, "", "", "", false, null);
    }

    public static ProfileUiState empty() {
        return new ProfileUiState(false, "", "", "", false, null);
    }

    public static ProfileUiState of(User user, boolean hasChanges) {
        return new ProfileUiState(
                false,
                user.fullName(),
                formatAddress(user.address()),
                user.avatarUrl(),
                hasChanges,
                null);
    }

    public static ProfileUiState error(String message) {
        return new ProfileUiState(false, "", "", "", false, message);
    }

    /** تبدیل آدرس به رشته‌ی نمایشی — این کار متعلق به ViewModel است، نه View. */
    private static String formatAddress(Address address) {
        if (address == null) {
            return "ثبت نشده";
        }
        StringBuilder sb = new StringBuilder(address.city());
        if (address.street() != null && !address.street().isBlank()) {
            sb.append("، ").append(address.street());
        }
        return sb.toString();
    }
}

package com.example.presentation.profile;

import androidx.lifecycle.LiveData;
import androidx.lifecycle.MutableLiveData;
import androidx.lifecycle.Transformations;
import androidx.lifecycle.ViewModel;
import com.example.domain.model.User;
import com.example.domain.repository.UserRepository;
import com.example.ui.common.ProfileUiState;

/**
 * نگه‌دارنده‌ی وضعیت صفحه‌ی پروفایل.
 * این کلاس هیچ وابستگی‌ای به Android UI ندارد و کاملاً قابل تست است.
 */
public class ProfileViewModel extends ViewModel {

    /** قانون: نام باید حداقل ۳ کاراکتر باشد. */
    private static final int MIN_NAME_LENGTH = 3;

    private final UserRepository userRepository;
    private final MutableLiveData<ProfileUiState> state = new MutableLiveData<>(ProfileUiState.empty());
    private final MutableLiveData<Event<Void>> events = new MutableLiveData<>();

    private User original;
    private String draftName = "";
    private boolean hasChanges;

    public ProfileViewModel(UserRepository userRepository) {
        this.userRepository = userRepository;
    }

    public LiveData<ProfileUiState> state() {
        return state;
    }

    public LiveData<Event<Void>> events() {
        return events;
    }

    /** فقط یک‌بار در طول عمر ViewModel صدا زده می‌شود. */
    public void load(String userId) {
        if (original != null) {
            return;
        }
        state.setValue(ProfileUiState.loading());
        userRepository.getUser(userId, new UserCallback() {
            @Override
            public void onLoaded(User user) {
                original = user;
                draftName = user.fullName();
                hasChanges = false;
                state.postValue(ProfileUiState.of(user, false));
            }

            @Override
            public void onError(Throwable error) {
                state.postValue(ProfileUiState.error("بارگذاری پروفایل ناموفق بود"));
            }
        });
    }

    /** رویداد دوحالته: کاربر نام را تغییر داده است. */
    public void onNameChanged(String name) {
        this.draftName = name == null ? "" : name.trim();
        boolean valid = this.draftName.length() >= MIN_NAME_LENGTH;
        if (valid && original != null) {
            hasChanges = !this.draftName.equals(original.fullName());
        } else {
            hasChanges = false;
        }
        ProfileUiState current = state.getValue();
        if (current != null && !current.loading()) {
            state.setValue(new ProfileUiState(
                    false,
                    this.draftName,
                    current.formattedAddress(),
                    current.avatarUrl(),
                    valid && hasChanges,
                    null));
        }
    }

    public void onSaveClicked() {
        ProfileUiState current = state.getValue();
        if (current == null || !current.saveEnabled() || original == null) {
            return;
        }
        original = original.withName(draftName);

/** رویداد یک‌بارمصرف: با مصرف، محتوا خالی می‌شود تا دوباره اجرا نشود. */
public final class Event<T> {

    private final T content;
    private boolean handled;

    public Event(T content) {
        this.content = content;
    }

    public synchronized T consume() {
        if (handled) {
            return null;
        }
        handled = true;
        return content;
    }
}

بخش ۲۱مثال در پروژه واقعی

۱) اپ فروشگاهی اندروید با MVVM

در اپ‌های فروشگاهی، صفحه‌ی لیست محصولات یک ProductListViewModel دارد که سبد خرید، فیلتر دسته‌بندی و وضعیت بارگذاری را نگه می‌دارد. با چرخش صفحه، سبد خرید حفظ می‌شود و کاربر مجبور نیست دوباره همه‌چیز را انتخاب کند. این دقیقاً همان چیزی است که MVP به‌سختی می‌توانست انجام دهد.

۲) اپ بانکی با MVVM

در اپ بانکی، صفحه‌ی تراکنش داده‌ی حساس دارد. ViewModel وضعیت فرم (مبلغ، مقصد، توضیح) را نگه می‌دارد و فقط وقتی همه‌ی قواعد اعتبارسنجی پاس شوند، دکمه‌ی پرداخت را فعال می‌کند. تست‌های واحد این ViewModel تمام حالت‌های ممکن تراکنش را پوشش می‌دهند — چیزی که برای یک سیستم مالی الزامی است.

۳) اپ پیام‌رسان با MVVM و LiveData

در اپ چت، هر ChatViewModel وضعیت پیام‌ها، وضعیت تایپ و اتصال را نگه می‌دارد. وقتی کاربر به هر صفحه می‌رود، LiveData آخرین وضعیت را تحویل می‌دهد و نیازی به بارگذاری مجدد نیست. این باعث می‌شود اسکرول در جای خودش باقی بماند.

۴) اپ سلامت و پایش بیمار

در اپ‌های پایش سلامت، ViewModel داده‌ی حساس را در حافظه نگه می‌دارد و با SavedStateHandle از مرگ فرایند محافظت می‌کند. اگر کاربر اپ را از فهرست اخیر ببندد و دوباره بازش کند، وضعیت فرم از دست نمی‌رود. این برای داده‌های سلامتی حیاتی است.

۵) اپ فروشگاهی با Compose و MVVM

در پروژه‌های مدرن Compose، همان ViewModel استفاده می‌شود اما LiveData با StateFlow جایگزین شده. مزیت این تغییر: سرعت بیشتر، پشتیبانی از مقدار اولیه و ترکیب‌پذیری با combine و اپراتورهای Flow.

بخش ۲۳۲۰ سؤال مصاحبه

سطح Junior
سؤال ۱ — MVVM چیست؟ الگوی معماری با سه نقش: Model (داده و منطق)، ViewModel (وضعیت صفحه و منطق نمایش) و View (رابط کاربری کاملاً منفعل). تفاوت اصلی با MVC در این است که ViewModel وضعیت را نگه می‌دارد و داده را از طریق LiveData منتشر می‌کند.
سؤال ۲ — تفاوت اصلی MVVM و MVP چیست؟ در MVP، Presenter داده را به View می‌فرستد. در MVVM، ViewModel داده را منتشر می‌کند و View خودش آن را مشاهده می‌کند. نتیجه: در MVVM، ViewModel حتی بدون View هم کار می‌کند و چرخه‌ی حیات خودش مدیریت می‌شود.
سؤال ۳ — ViewModel دقیقاً چه کاری انجام می‌دهد؟ وضعیت صفحه را نگه می‌دارد، با Model ارتباط برقرار می‌کند، داده را به فرمت نمایشی تبدیل می‌کند و با LiveData در اختیار View می‌گذارد.
سؤال ۴ — چطور یک ViewModel بسازیم؟ از ViewModelProvider سیستم استفاده می‌کنیم (نه با new) تا سیستم آن را در چرخش صفحه نگه دارد. برای وابستگی‌های خاص از ViewModelProvider.Factory یا Hilt استفاده می‌کنیم.
سؤال ۵ — LiveData چیست؟ یک ظرف داده‌ی قابل مشاهده و آگاه به چرخه‌ی حیات. وقتی مقدارش تغییر کند، فقط به اجزایی که در حالت فعال هستند اطلاع می‌دهد و در نتیجه هم بهینه و هم امن است.
سؤال ۶ — تفاوت LiveData و StateFlow چیست؟ LiveData مخصوص اندروید است و چرخه‌ی حیات‌آگاه است. StateFlow مخصوص Kotlin است، سریع‌تر است، مقدار اولیه دارد و با اپراتورهای Flow ترکیب می‌شود. در پروژه‌های جدید Compose معمولاً StateFlow ترجیح داده می‌شود.
سؤال ۷ — آیا ViewModel می‌تواند به Context دسترسی داشته باشد؟ نه به Context خودش؛ ViewModel اصلاً دنبال آن نمی‌گردد. اگر واقعاً لازم است (مثلاً برای یک سرویس سیستمی)، باید آن را به‌عنوان وابستگی از بیرون تزریق کنید، نه اینکه خودتان getApplication() صدا بزنید.
سؤال ۸ — داده‌ی دوحالته در MVVM یعنی چه؟ یعنی داده هم از Model به View جریان دارد (پایین‌رو) و هم تغییرات کاربر در View به ViewModel منتقل می‌شود (بالا‌رو). LiveData این را با twoWayBinding در Data Binding ممکن می‌کند.
سؤال ۹ — چه زمانی از Event استفاده می‌کنیم؟ وقتی رویدادی باید فقط یک بار اجرا شود (مثل ناوبری به صفحه‌ی دیگر یا نمایش Snackbar). اگر LiveData معمولی استفاده کنیم، با چرخش صفحه دوباره اجرا می‌شود.
سطح Mid
سؤال ۱۰ — ViewModel در چرخش صفحه چه می‌شود؟ نابود نمی‌شود. سیستم آن را نگه می‌دارد و در Activity جدید دوباره به ViewModelProvider تحویل می‌دهد. این اصلی‌ترین دلیل وجود MVVM است.
سؤال ۱۱ — تفاوت setValue و postValue چیست؟ setValue فقط روی Main Thread کار می‌کند و در غیر این صورت کرش می‌دهد. postValue از هر thread قابل استفاده است و مقدار را در صف Main Thread می‌گذارد.
سؤال ۱۲ — چطور تست ViewModel بنویسیم؟ با Fake Repository و InstantTaskExecutorRule. LiveData را با observeForever مشاهده می‌کنیم و تغییرات وضعیت را با getOrAwaitValue می‌خوانیم. هیچ شبیه‌ساز اندرویدی لازم نیست.
سؤال ۱۳ — چطور از ساخت چندباره‌ی ViewModel جلوگیری کنیم؟ در متد onInit (که فقط یک بار صدا زده می‌شود) داده را بارگذاری کنید، یا یک فلگ hasLoaded نگه دارید. صدا زدن load() در onViewCreated در هر بار ساخت View، درخواست شبکه‌ی تکراری می‌سازد.
سؤال ۱۴ — مشکل God ViewModel چیست؟ وقتی یک ViewModel همه‌ی کارهای صفحه (شبکه، ذخیره‌سازی، ناوبری، اعلان، اعتبارسنجی) را انجام می‌دهد، تست آن سخت و تغییرش پرهزینه می‌شود. راه‌حل: تقسیم به Use Caseهای کوچک و استفاده از Coordinator برای ناوبری.
سؤال ۱۵ — MVVM در Compose چه تفاوتی دارد؟ مفهوم عوض نمی‌شود. فقط ابزارها عوض می‌شوند: LiveData با StateFlow، observe با collectAsStateWithLifecycle، و Data Binding با ترکیب‌پذیری (Composition).
سؤال ۱۶ — چرا یک ViewModel برای هر صفحه بهتر است؟ چون هر صفحه چرخه‌ی حیات و وضعیت مستقل خودش را دارد. یک ViewModel بزرگ برای کل اپ باعث می‌شود با هر صفحه‌ی جدید، وضعیت صفحات دیگر هم در حافظه بماند و مسئولیت‌ها قاطی شوند.
سطح Senior
سؤال ۱۷ — در چه شرایطی MVVM کافی نیست؟ وقتی جریان داده بسیار پیچیده و رویدادمحور باشد (مثلاً یک ویرایشگر چندمرحله‌ای با undo/redo). در این حالت MVI با State واحد و Reducer قابل پیش‌بینی‌تر است. همچنین برای منطق کسب‌وکار پیچیده، MVVM به‌تنهایی کافی نیست و باید با لایه‌بندی یا Clean Architecture ترکیب شود.
سؤال ۱۸ — چطور MVVM را در پروژه‌ی بزرگ‌تر مقیاس‌پذیر می‌کنیم؟ با تقسیم‌بندی Feature-Based: هر فیچر پوشه‌ی خودش را دارد که شامل View، ViewModel و Contract است. در این حالت ViewModelها مستقل و قابل تست هستند و تیم‌ها کمتر با هم تداخل دارند.
سؤال ۱۹ — تفاوت ViewModel و Presenter در مدیریت چرخه‌ی حیات؟ ViewModel توسط فریم‌ورک Android به‌طور خودکار با چرخه‌ی حیات هماهنگ می‌شود و تا وقتی Activity وجود دارد باقی می‌ماند. Presenter باید دستی مدیریت شود (attach/detach) و معمولاً باید خودش منطق حفظ وضعیت را پیاده کند.
سؤال ۲۰ — چه زمانی MVVM را با لایه‌بندی ترکیب کنیم؟ وقتی منطق کسب‌وکار پیچیده باشد. در این حالت MVVM فقط در لایه‌ی Presentation به‌عنوان الگوی ارتباط با UI استفاده می‌شود، و منطق در لایه‌ی Domain قرار می‌گیرد. این ترکیب در پروژه‌های بزرگ اندروید بسیار رایج است.

بخش ۲۴پرسش‌های متداول (FAQ)

پرسش‌های پرتکرار
۱) تفاوت MVVM و MVP دقیقاً چیست؟ تفاوت در مکانیزم انتقال داده است. در MVP، Presenter متدهای View را صدا می‌زند. در MVVM، ViewModel داده را منتشر می‌کند و View فقط مشاهده می‌کند. نتیجه: در MVVM، ViewModel حتی بدون View هم قابل تست و قابل استفاده است.
۲) آیا ViewModel در چرخش صفحه باقی می‌ماند؟ بله، این اصلی‌ترین ویژگی آن است. سیستم اندروید نمونه‌ی ViewModel را نگه می‌دارد و در Activity جدید تحویل می‌دهد، بنابراین وضعیت صفحه از دست نمی‌رود.
۳) آیا MVVM برای پروژه‌های غیراندرویدی هم کاربرد دارد؟ مفهوم آن بله، اما کلاس ViewModel خاص اندروید است. در سایر پلتفرم‌ها می‌توانید یک کلاس مشابه با خودتان بسازید که توسط فریم‌ورک مدیریت شود.
۴) LiveData یا StateFlow؟ اگر پروژه Kotlin و Compose است، StateFlow بهتر است (سریع‌تر، مقدار اولیه دارد، با Flow ترکیب می‌شود). اگر XML استفاده می‌کنید یا تیم Java است، LiveData انتخاب طبیعی‌تری است.
۵) آیا ViewModel باید Context داشته باشد؟ نه به‌صورت مستقیم. اگر به Context نیاز دارید (مثلاً برای یک سرویس سیستمی)، آن را به‌عنوان وابستگی از بیرون تزریق کنید. به این ترتیب تست واحد باقی می‌ماند.
۶) آیا MVVM برای پروژه‌های کوچک مناسب است؟ اگر صفحه‌ی ساده‌ای دارید که فقط داده نمایش می‌دهد، ممکن است MVVM بیش از حد مهندسی باشد. اما برای صفحات با فرم و وضعیت پیچیده، ارزشش را دارد.
۷) تفاوت onInit و onViewCreated برای بارگذاری داده؟ اگر می‌خواهید داده فقط یک بار بارگذاری شود (معمولاً برای درخواست شبکه)، از onInit استفاده کنید. اگر می‌خواهید با هر بار نمایش صفحه (مثلاً بازگشت از صفحه‌ی دیگر) به‌روزرسانی شود، از onViewCreated.
۸) آیا باید از Data Binding استفاده کنیم؟ نه. MVVM بدون Data Binding هم کار می‌کند — کافی است ViewModel را با observe بخوانید. Data Binding فقط کد تکراری را کم می‌کند و زمان build را بالا می‌برد.
۹) چطور رویداد یک‌بارمصرف پیاده کنیم؟ از کلاس Event استفاده کنید که با مصرف شدن محتوا پاک می‌شود. در Kotlin می‌توانید از Channel (بافر ۱) یا SharedFlow هم استفاده کنید.
۱۰) آیا MVVM برای صفحات با وضعیت پیچیده کافی است؟ نه همیشه. اگر وضعیت شما آن‌قدر پیچیده است که باید همه‌ی حالت‌های ممکن را ردیابی کنید، الگوی MVI با State واحد و Reducer کنترل بهتری به شما می‌دهد.
۱۱) تفاوت MVVM و لایه‌بندی چیست؟ MVVM یک الگو است که فقط لایه‌ی UI را توضیح می‌دهد. لایه‌بندی یک معماری است که کل سیستم را به لایه‌ها تقسیم می‌کند. این دو مکمل یکدیگرند و اغلب با هم استفاده می‌شوند.
۱۲) چطور MVVM را با لایه‌بندی ترکیب کنیم؟ MVVM را در لایه‌ی Presentation (جایی که View و ViewModel هستند) استفاده کنید و منطق کسب‌وکار را به لایه‌ی Domain منتقل کنید. ViewModel فقط Use Caseها را صدا می‌زند و داده را برای نمایش آماده می‌کند.
۱۳) آیا ViewModel می‌تواند داده را کش کند؟ بله، اما بهتر است منطق کش در Repository باشد و ViewModel فقط از آن استفاده کند. اگر کش در ViewModel باشد، با تغییر ViewModel داده از دست می‌رود.
۱۴) چطور مشکل God ViewModel را حل کنیم؟ ViewModel را به Use Caseهای کوچک تقسیم کنید، برای ناوبری از یک Coordinator جدا استفاده کنید، و اگر لازم بود از چند ViewModel کوچک برای بخش‌های مختلف صفحه به‌کار ببرید.
۱۵) آیا MVVM برای سیستم‌های غیر UI هم کاربرد دارد؟ خیر. MVVM یک الگوی رابط کاربری است. برای سرویس‌های بک‌اند و منطق کسب‌وکار، لایه‌بندی یا Clean Architecture مناسب‌تر است.

جمع‌بندی

MVVM الگویی است که مشکل واقعی چرخه‌ی حیات را حل می‌کند: اینکه چگونه وضعیت صفحه را نگه دارید در حالی که سیستم‌عامل به‌طور دائم آن را نابود می‌کند. راه‌حل ساده و عمیقی است: وضعیت را در یک کلاس بگذارید که سیستم مدیریتش می‌کند.

اگر در حال یادگیری هستید، پیشنهاد می‌کنم مسیر MVP → MVVM → MVI را دنبال کنید. MVP به شما یاد می‌دهد منطق را از View جدا کنید، MVVM به شما یاد می‌دهد وضعیت را مدیریت کنید، و MVI به شما یاد می‌دهد جریان را کاملاً قابل پیش‌بینی کنید.

پیام پایانی سری ۱۴ مقاله‌ای این مقاله هفتمین عضو سری «معماری‌های نرم‌افزاری» است. اکنون شما سه الگوی کلاسیک UI (MVC، MVP، MVVM) را می‌شناسید و ساختارهای کلان معماری را هم پوشش داده‌اید. مقاله‌ی بعدی به MVI می‌پردازد — الگویی که همه‌ی این‌ها را به اوج می‌رساند.
