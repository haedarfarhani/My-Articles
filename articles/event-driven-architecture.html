بخش ۱مقدمه: زنجیره‌ای که شکستن می‌خورد

یک سیستم فروش را در نظر بگیرید که وقتی سفارش ثبت می‌شود، این اتفاق‌ها باید بیفتد:

  1. ثبت سفارش در دیتابیس
  2. کم‌شدن موجودی انبار
  3. رزرو وقت ارسال
  4. ارسال ایمیل تأیید
  5. ساخت فاکتور
  6. به‌روزرسانی امتیاز وفاداری مشتری
  7. ثبت در گزارش فروش روزانه

روش ساده این است: از هر سرویسی که لازم داری صدا بزن. 

OrderService.placeOrder():
    save(order)                    ← دیتابیس
    inventory.reserve(...)         ← HTTP به سرویس انبار    ⏱ ۸۰ms
    shipping.book(...)             ← HTTP به سرویس ارسال    ⏱ ۱۲۰ms
    email.send(...)                ← HTTP به سرویس ایمیل    ⏱ ۴۰ms
    billing.createInvoice(...)     ← HTTP به سرویس مالی     ⏱ ۹۰ms
    loyalty.addPoints(...)         ← HTTP به سرویس مشتری    ⏱ ۵۰ms
    analytics.track(...)           ← HTTP به سرویس گزارش    ⏱ ۶۰ms

زمان کل: ۴۴۰ms + ۶ نقطه‌ی شکست

حالا سرویس ایمیل ۳ ثانیه کند می‌شود. چه اتفاقی می‌افتد؟

زنجیره‌ی شکننده سفارش ثبت می‌شود ✅ ← ایمیل timeout می‌شود ❌ ← استثنا پرتاب می‌شود ← تراکنش rollback می‌شود ← سفارش از بین می‌رود، اما ایمیل نیمه‌ارسال شده ← موجودی انبار کم شده ولی سفارشی وجود ندارد ← مشتری پول کم کرده و سفارشی ندارد

این یک نمونه‌ی کوچک است. در واقعیت، هر فراخوانی timeout یا 500 یک حالت ناسازگار می‌سازد که بازگرداندن آن سخت است.

راه‌حل: بگذارید اتفاق بیفتد و بعداً واکنش نشان دهید

OrderService.placeOrder():
    save(order)                    ← فقط همین، در یک تراکنش
    outbox.save(OrderPlaced event)  ← رویداد در همان تراکنش
    return 201                      ← ۱۲ms

--- بعداً، ناهمگام، مستقل از هم ---
سرویس انبار   OrderPlaced → کم کردن موجودی
سرویس ارسال   OrderPlaced → رزرو وقت
سرویس ایمیل   OrderPlaced → ارسال ایمیل
سرویس مالی    OrderPlaced → ساخت فاکتور
سرویس گزارش   OrderPlaced → ثبت در گزارش

اگر ایمیل خراب شود:
  ← فقط ایمیل اثر می‌گیرد
  ← سفارش سالم است
  ← پیام دوباره تلاش می‌شود (retry)
تغییر ذهنیت از «وقتی سفارش ثبت شد، ایمیل بفرست» به «وقتی سفارش ثبت شد، بگو که ثبت شد؛ هرکس به این خبر نیاز دارد، خودش می‌آید و می‌گیرد.» این جمله کل تفاوت است.

سه موج فکری

موج اول — Pub/Sub عمومی

پیام را در یک صف عمومی می‌اندازید و هرکس خواست می‌خواند. مشکل: اگر دو مصرف‌کننده بخواهند مستقل مقیاس بگیرند، باید دو نسخه از پیام داشته باشید. راه‌حل: موضوعات (Topics).

موج دوم — Event Notification

هر مصرف‌کننده فقط اعلان می‌گیرد و اگر داده لازم داشت، خودش می‌پرسد. مزیت آن، کوچک بودن پیام و استقلال مصرف‌کنندگان است. عیب: یک round-trip اضافه و دو منبع حقیقت.

موج سوم — Event Carrying State Transfer

داده در خود پیام می‌آید و مصرف‌کننده لازم نیست چیزی بپرسد. مزیت: مصرف سریع. عیب: کوپل بیشتر و ریسک داده‌ی کهنه. 

کدام موج را انتخاب کنیم؟

  پیام کوچک (فقط شناسه + مقدار)          → ECST  ✅ پیشنهاد ما
  پیام بزرگ (کل مدل)                     → ECST
  فقط «اتفاق افتاد» بدون داده            → Notification
  داده حجیم، حتماً به‌روز                 → Notification (با cache)

قاعده: تا می‌توانید داده را در پیام ببرید، از رفت‌وبرگشت شبکه پرهیز کنید.

چرا دقیقاً حالا؟

  • زیرساخت ارزان: یک مجموعه‌ی topic مدیریت‌شده حالا هزینه‌ای معادل یک VPS است
  • تله‌تراشی: سرویس‌ها به هر تیم اجازه می‌دهند مستقل مستقر شوند
  • الگوی CQRS + Event Sourcing که بدون پیام‌رسان ممکن نبود
  • داده‌های حجم بالا و جریانی: لاگ، کلیک، IoT، معاملات
  • واکنش‌پذیری و مقیاس مستقل: یک مصرف‌کننده‌ی سنگین، بقیه را کند نمی‌کند

بخش ۳EDA چیست؟ (تعریف دقیق)

تعریف معماری رویدادمحور یعنی اجزای سیستم به‌جای اینکه یکدیگر را مستقیم صدا بزنند، رویدادهایی را منتشر می‌کنند که در دامنه اتفاق افتاده و اجزای دیگر هرکس به آن‌ها نیاز داشت، به‌صورت مستقل گوش می‌دهند.

هفت اصطلاح کلیدی که نباید اشتباه شوند:

اصطلاحمعنامثال
Eventیک اتفاق قطعی که در گذشته افتادهOrderPlaced
Producerتولیدکننده‌ی رویدادسرویس سفارش
Consumerمصرف‌کننده‌ای که به رویداد گوش می‌دهدسرویس انبار
Brokerواسط ذخیره و تحویل پیامKafka، RabbitMQ
Topicکانال دسته‌بندی رویدادهاorders
Subscriptionاشتراک یک گروه در یک topicinventory-service
Partitionبخش مرتب و پایدار یک topic۱۲ پارتیشن

سه ویژگی که EDA را متمایز می‌کند

  1. غیرهمگام بودن — تولیدکننده منتظر جواب نمی‌ماند
  2. عدم آگاهی از مصرف‌کننده — تولیدکننده اصلاً نمی‌داند چه کسی گوش می‌دهد
  3. استقلال زمانی — رویداد ممکن است دقیقه‌ها بعد پردازش شود

EDA یعنی همه‌چیز رویداد است؟

❌ برداشت اشتباه: هیچ سرویسی هرگز دیگری را صدا نمی‌زند
✅ واقعیت: EDA یعنی «کوپل» کم می‌شود، نه «صفر»

همیشه باید دو سؤال بپرسید:
  ۱. آیا مصرف‌کننده نتیجه را همین الان لازم دارد؟
        بله → فراخوانی همگام (RPC)
        نه  → رویداد

  ۲. آیا اگر مصرف‌کننده خراب شود، سرویس من باید هم بماند؟
        بله → رویداد + تحمل خطا
        نه  → تراکنش مشترک
قاعده‌ی طلایی رویداد برای «اتفاقی که افتاد» است، فراخوانی برای «کاری که باید انجام شود». اگر کاربر منتظر جواب بمیرد، RPC. اگر کار در پس‌زمینه انجام می‌شود، رویداد.

قواعد طلایی نام‌گذاری و طراحی رویداد

  • نام با گذشته: OrderPlaced، نه PlaceOrder
  • یک رویداد = یک واقعیت، نه یک درخواست
  • بدون فعل: OrderCreated بهتر از CreateOrder
  • نام گذشته در نام: PaymentFailed نه FailPayment
  • محدود (Small): هرچه کوچک‌تر، نسخه‌بندی آسان‌تر
  • غیرقابل تغییر (Immutable): نسخه‌ی قدیمی باید سال‌ها قابل پردازش باشد
  • بدون داده حساس: رمز، توکن و اطلاعات شخصی در رویداد نرود

حذف تکرار (Idempotency)

/**
 * مصرف‌کننده باید idem potent باشد:
 * پردازش دو بار همان پیام، همان نتیجه را بدهد.
 */
@Component
class InventoryEventHandler {

    private final ProcessedEventStore store;
    private final StockService stock;

    InventoryEventHandler(ProcessedEventStore store, StockService stock) {
        this.store = store;
        this.stock = stock;
    }

    @EventListener
    @Transactional
    void on(OrderPlaced event) {
        if (store.wasProcessed(event.eventId())) {
            return;                        // ← قبلاً پردازش شده
        }

        stock.reserve(event.productId(), event.quantity());
        store.markProcessed(event.eventId());   // ← در همان تراکنش
    }
}
چرا idempotency اجتناب‌ناپذیر است هیچ پیام‌رسانی تحویل «دقیقاً یک‌بار» نمی‌دهد. کمینه‌ی واقعی «حداقل یک‌بار» است، پس مصرف‌کننده ممکن است هر پیام را دو بار ببیند. اگر مصرف‌کننده idempotent نباشد، موجودی انبار را دو بار کم می‌کند.

بخش ۷ساختار معماری

اجزای سیستم رویدادمحور

۱. Producer (تولیدکننده)
   هسته‌ی سرویس. رویداد را تولید می‌کند و در همان تراکنش ذخیره می‌کند.
   هیچ‌چیز درباره‌ی Broker نمی‌داند.

۲. Outbox (صندوق خروج)
   جدولی در همان دیتابیس که رویداد را در همان تراکنش کسب‌وکار نگه می‌دارد.
   ← تضمین «یا هر دو، یا هیچ‌کدام»

۳. Relay (رله)
   پروسه‌ای که outbox را می‌خواند و به Broker منتشر می‌کند،
   سپس علامت «منتشر شد» می‌زند.

۴. Broker (واسط پیام)
   ذخیره‌سازی پایدار پیام + تحویل به مصرف‌کننده‌ها.
   Kafka، RabbitMQ، NATS، SQS.

۵. Consumer (مصرف‌کننده)
   گوش می‌دهد، اعتبارسنجی می‌کند، idem potent است، و تأیید (ack) می‌کند.

۶. DLQ (صف مرده)
   پیام‌هایی که چند بار شکست خورده‌اند، برای بررسی انسانی.

قواعد جریان داده

  • تولید رویداد در همان تراکنش کسب‌وکار، نه قبل یا بعد از آن
  • هر مصرف‌کننده idempotent است، چون تحویل حداقل یک‌بار است
  • پیام‌های شکست‌خورده به DLQ می‌روند، نه اینکه بی‌نهایت retry شوند
  • ترتیب فقط به‌ازای کلید تضمین می‌شود (مثلاً orderId)
  • هیچ مصرف‌کننده‌ای نباید پیام را بین دو سرویس پاس بدهد مگر با دلیل روشن
  • Schema را قبل از انتشار تعریف کنید و آن را در مخزن کد نگه دارید
  • نسخه‌ی مصرف‌کننده همیشه <= نسخه‌ی تولیدکننده است

ترتیب کارها در یک مصرف‌کننده

۱. دریافت پیام
۲. بررسی schema (نسخه پشتیبانی می‌شود؟)
۳. بررسی تکراری بودن (eventId قبلاً پردازش شده؟)  ← اگر آری، ack و تمام
۴. اعتبارسنجی محتوای پیام
۵. اجرای منطق کسب‌وکار در یک تراکنش محلی
۶. ثبت eventId به‌عنوان پردازش‌شده (در همان تراکنش!)
۷. ack به Broker
۸. در صورت خطا: rollback + نمایش به Broker برای retry

package com.shop.order.application;

import com.fasterxml.jackson.databind.ObjectMapper;
import com.shop.order.integration.outbox.OutboxEvent;
import com.shop.order.integration.outbox.OutboxEventRepository;
import org.springframework.stereotype.Component;

import java.time.Instant;

@Component
public class EventRecorder {

    private final OutboxEventRepository repository;
    private final ObjectMapper mapper;

    public EventRecorder(OutboxEventRepository repository, ObjectMapper mapper) {
        this.repository = repository;
        this.mapper = mapper;
    }

    /**
     * این متد باید در همان تراکنشی صدا زده شود
     * که تغییرات کسب‌وکار را ذخیره می‌کند.
     */
    public void record(Object event, String aggregateType,
                       String aggregateId, String eventKey,
                       String correlationId) {
        try {
            repository.save(OutboxEvent.pending(
                    UUID.randomUUID().toString(),
                    aggregateType,
                    aggregateId,
                    eventTypeOf(event),
                    eventKey,
                    mapper.writeValueAsString(event),
                    correlationId,
                    Instant.now()));
        } catch (Exception e) {
            throw new IllegalStateException("ثبت رویداد در outbox ناموفق بود", e);
        }
    }

    private String eventTypeOf(Object event) {
        return switch (event) {
            case com.shop.contracts.order.v1.OrderPlacedV1 e -> e.eventType();
            default -> event.getClass().getSimpleName();
        };
    }
}

    private String aggregateType;

    @Column(name = "aggregate_id", nullable = false, length = 100)
    private String aggregateId;

    @Column(name = "event_type", nullable = false, length = 200)
    private String eventType;

    @Column(name = "event_key", nullable = false, length = 100)

    private String payload;

    @Column(name = "correlation_id", length = 100)
    private String correlationId;

    @Column(name = "created_at", nullable = false)
    private Instant createdAt;

    @Column(name = "published_at")
    private Instant publishedAt;

    @Column(nullable = false)
    private int attempts;

    @Column(name = "last_error", columnDefinition = "text")
    private String lastError;

                                      String eventType, String eventKey,

        e.aggregateType = aggregateType;

        e.eventType = eventType;
        e.eventKey = eventKey;
        e.payload = payload;
        e.correlationId = correlationId;
        e.createdAt = createdAt;
        e.attempts = 0;
        return e;

        this.lastError = null;

package com.shop.inventory.integration.event;

import com.fasterxml.jackson.databind.ObjectMapper;
import com.shop.contracts.order.v1.OrderPlacedV1;
import com.shop.inventory.domain.StockService;
import org.apache.kafka.clients.consumer.ConsumerRecord;
import org.springframework.kafka.annotation.KafkaListener;
import org.springframework.stereotype.Component;
import org.springframework.transaction.annotation.Transactional;

@Component
public class OrderPlacedHandler {

    private static final int MAX_ATTEMPTS = 5;

    private final StockService stock;
    private final ProcessedEventStore processed;
    private final ObjectMapper mapper;

    public OrderPlacedHandler(StockService stock,
                              ProcessedEventStore processed,
                              ObjectMapper mapper) {
        this.stock = stock;
        this.processed = processed;
        this.mapper = mapper;
    }

    @KafkaListener(
            topics = "orders",
            groupId = "inventory-service",
            concurrency = "3")
    @Transactional
    public void on(ConsumerRecord<String, String> record) {

        OrderPlacedV1 event = deserialize(record.value());

        // ۱. حذف تکرار
        if (processed.wasProcessed(event.eventId(), "inventory-service")) {
            return;
        }

        // ۲. اعتبارسنجی
        validate(event);

        // ۳. منطق کسب‌وکار
        for (OrderPlacedV1.Line line : event.lines()) {
            stock.reserve(line.productId(), line.quantity(), event.orderId());
        }

        // ۴. ثبت در همان تراکنش ← اتمیک با منطق بالا
        processed.markProcessed(event.eventId(), "inventory-service");
    }

    private OrderPlacedV1 deserialize(String json) {
        try {
            return mapper.readValue(json, OrderPlacedV1.class);
        } catch (Exception e) {
            throw new NonRetryableException("پیام نامعتبر است: " + e.getMessage());
        }
    }

    private void validate(OrderPlacedV1 event) {
        if (event.eventId() == null || event.orderId() == null) {
            throw new NonRetryableException("فیلدهای اجباری وجود ندارد");
        }
        if (event.lines() == null || event.lines().isEmpty()) {
            throw new NonRetryableException("سفارش بدون خطا معتبر نیست");
        }
    }
}

package com.shop.inventory.integration.event;

import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.stereotype.Repository;

@Repository
public class ProcessedEventStore {

    private final JdbcTemplate jdbc;

    public ProcessedEventStore(JdbcTemplate jdbc) {
        this.jdbc = jdbc;
    }

    public boolean wasProcessed(String eventId, String consumer) {
        Integer count = jdbc.queryForObject(
                "SELECT count(*) FROM processed_events "
                        + "WHERE event_id = ? AND consumer = ?",
                Integer.class, eventId, consumer);
        return count != null && count > 0;
    }

    public void markProcessed(String eventId, String consumer) {
        // ON CONFLICT DO NOTHING → در برابر تلاش هم‌زمان مقاوم است
        jdbc.update("INSERT INTO processed_events (event_id, consumer) "
                + "VALUES (?, ?) ON CONFLICT (event_id) DO NOTHING",
                eventId, consumer);
    }
}

    private static final int MAX_ATTEMPTS = 10;

    private final OutboxEventRepository repository;
    private final KafkaTemplate<String, String> kafka;
    private final String topic;

    public OutboxRelay(OutboxEventRepository repository,
                       KafkaTemplate<String, String> kafka,
                       @Value("${app.outbox.topic}") String topic) {
        this.repository = repository;
        this.kafka = kafka;
        this.topic = topic;
    }

    @Scheduled(fixedDelayString = "${app.outbox.interval:1000}")
    @Transactional
    public void publishPending() {
        var batch = repository.findUnpublished(PageRequest.of(0, 100));

        for (OutboxEvent event : batch) {
            try {
                // key = eventKey → تضمین ترتیب به‌ازای موجودی
                kafka.send(topic, event.eventKey(), event.payload())
                        .get(5, java.util.concurrent.TimeUnit.SECONDS);

                event.markPublished();
                log.info("منتشر شد: {} [{}]", event.eventType(), event.id());

            } catch (Exception e) {
                event.markFailed(e.getMessage());
                log.warn("انتشار ناموفق: {} تلاش {}",
                        event.eventType(), event.attempts());

                if (event.attempts() >= MAX_ATTEMPTS) {
                    // دیگر تلاش نکن؛ به تیم عملیات اطلاع بده
                    log.error("رویداد به سقف تلاش رسید: {}", event.id());
                }
            }
        }
    }
}

import org.springframework.kafka.listener.DefaultErrorHandler;

import org.springframework.context.annotation.Configuration;

@Configuration
public class KafkaErrorHandlingConfig {

    private static final Logger log = LoggerFactory.getLogger(KafkaErrorHandlingConfig.class);

    @Bean
    public DefaultErrorHandler kafkaErrorHandler(
            DeadLetterPublishingRecoverer recoverer) {

        // ۳ تلاش با فاصله‌ی ۲ ثانیه
        var backOff = new FixedBackOff(2000L, 3L);

        var handler = new DefaultErrorHandler(recoverer, backOff);

    }
}

چهار سطح تضمین تحویل

سطحمعناامکان‌پذیر؟
حداقل یک‌بار (At-least-once)پیام حتماً می‌رسد، ممکن است تکرار شود✅ استاندارد صنعت
حداکثر یک‌بار (At-most-once)پیام حداکثر یک‌بار می‌رسد، ممکن است گم شود✅ ولی داده را گم می‌کند
دقیقاً یک‌بار (Exactly-once)دقیقاً یک‌بار می‌رسد⚠️ فقط در محدوده‌ی یک سیستم
تقریباً یک‌بار (Effectively-once)تکرار ممکن است ولی اثرش نمایی نیست✅ هدف عملی ما
توضیح دقیق Exactly-once در سطح شبکه در واقع ناممکن است چون نتیجه‌ی ack هنوز به تولیدکننده نرسیده است. چیزی که به‌دست می‌آید Effectively-once است: پیام ممکن است دو بار برسد، اما مصرف‌کننده‌ی idempotent باعث می‌شود اثر نهایی یکی باشد.

    private static final Logger log = LoggerFactory.getLogger(OutboxCleaner.class);

    private final JdbcTemplate jdbc;

    @Scheduled(cron = "0 0 3 * * *")            // هر روز ساعت ۳ صبح

                        + "WHERE published_at IS NOT NULL "
                        + "AND published_at < now() - ?",
                retention);

    }
}

package com.shop.order.integration.outbox;

@Component
public class OutboxEventRecorder implements EventRecorder {

    private final OutboxEventRepository repository;
    private final ObjectMapper mapper;

    @Override
    @Transactional
    public void record(Object event, String type, String id,
                       String key, String correlationId) {
        try {
            repository.save(OutboxEvent.pending(
                    UUID.randomUUID().toString(), type, type, type,
                    key, mapper.writeValueAsString(event),
                    correlationId, Instant.now()));
        } catch (Exception e) {
            throw new IllegalStateException("ثبت رویداد ناموفق", e);
        }
    }

Orchestration — نمونه

@Component
public class CheckoutSaga {

    private final InventoryApi inventory;
    private final PaymentApi payment;
    private final OrderRepository orders;

    @EventListener
    @Transactional
    public void on(OrderPlaced event) {
        try {
            inventory.reserve(event.orderId(), event.lines());
            payment.capture(event.orderId(), event.total());

            orders.confirm(event.orderId());
            events.publish(new OrderConfirmed(event.orderId()));

        } catch (InsufficientStockException e) {
            // جبران مرحله‌ی قبل
            payment.refund(event.orderId());
            orders.reject(event.orderId(), "موجودی ناکافی");
            events.publish(new OrderRejected(event.orderId(), e.getMessage()));

        } catch (PaymentException e) {
            inventory.release(event.orderId());
            orders.reject(event.orderId(), "پرداخت ناموفق");
            events.publish(new OrderRejected(event.orderId(), e.getMessage()));
        }
    }
}

/** ثبت‌کننده‌ی حافظه‌ای: هیچ Broker و دیتابیسی لازم نیست. */
public class InMemoryEventRecorder implements EventRecorder {

    private final List<RecordedEvent> recorded = new ArrayList<>();

    @Override
    public void record(Object event, String type, String id,
                       String key, String correlationId) {
        recorded.add(new RecordedEvent(event, type, id, key, correlationId));
    }

    public List<RecordedEvent> recorded() {
        return List.copyOf(recorded);
    }

    public List<RecordedEvent> ofType(String type) {
        return recorded.stream()
                .filter(e -> e.type().equals(type))
                .toList();
    }

    public void clear() {
        recorded.clear();
    }

    public record RecordedEvent(Object event, String type, String id,
                                String key, String correlationId) {}
}

بخش ۲۳۲۰ سؤال مصاحبه

سطح Junior (۱ تا ۱۰)

سؤال ۱ — Event Driven Architecture چیست؟ معماری‌ای که اجزا به‌جای صدا زدن یکدیگر، رویدادهایی را که در دامنه اتفاق افتاده منتشر می‌کنند و هر جزء‌ای که لازم دارد، مستقل به آن‌ها گوش می‌دهد. ویژگی اصلی: ناهمگامی و نبود آگاهی تولیدکننده از مصرف‌کننده.
سؤال ۲ — تفاوت رویداد و فراخوانی چیست؟ فراخوانی یعنی «این کار را انجام بده» و منتظر جواب می‌مانیم؛ کوپل مستقیم دارد. رویداد یعنی «این اتفاق افتاد» و هرکس خواست واکنش نشان می‌دهد؛ کوپل ندارد. اگر کاربر منتظر نتیجه بماند، فراخوانی؛ اگر کار در پس‌زمینه باشد، رویداد.
سؤال ۳ — چهار مؤلفه‌ی اصلی EDA چیست؟ Producer (تولیدکننده‌ی رویداد)، Broker (واسط ذخیره و تحویل)، Topic (کانال دسته‌بندی) و Consumer (مصرف‌کننده). بین Producer و Broker معمولاً یک Outbox هم هست برای تضمین اتمیک بودن.
سؤال ۴ — رویداد دامنه چیست؟ رویدادی که در مدل کسب‌وکار اتفاق افتاده و گذشته است؛ مثل OrderPlaced. تفاوتش با پیام سیستمی این است که پیام سیستمی درباره‌ی اطلاع‌رسانی است و وابستگی ایجاد می‌کند، ولی Domain Event درباره‌ی تغییر وضعیت است.
سؤال ۵ — چرا نام رویداد باید با گذشته باشد؟ چون رویداد یعنی اتفاقی که افتاده. نام با گذشته (مثل PaymentCaptured) جلوی اشتباه رایج را می‌گیرد: کسی که فکر می‌کند رویداد یک دستور است و کاری انجام نمی‌دهد چون «هنوز نیفتاده».
سؤال ۶ — Broker چه کاری انجام می‌دهد؟ پیام را ذخیره می‌کند، بین چند مصرف‌کننده توزیع می‌کند، تحویل را مدیریت می‌کند و تلاش مجدد و صف مرده را فراهم می‌کند. Kafka و RabbitMQ نمونه‌های رایج هستند.
سؤال ۷ — سازگاری نهایی (Eventual Consistency) یعنی چه؟ یعنی سیستم در یک لحظه ممکن است داده‌ی کهنه نشان دهد، ولی اگر مدتی صبر کنید و نوشتن جدیدی انجام نشود، همه‌جا به یک وضعیت می‌رسند. برای شمارنده و اعلان مناسب است، برای موجودی حساب بانکی نه.
سؤال ۸ — چه زمانی باید از فراخوانی استفاده کرد؟ وقتی کاربر منتظر نتیجه می‌ماند (مثل ثبت‌نام با ایمیل تأیید که باید بدانیم موفق بوده یا نه)، و وقتی نیاز به سازگاری فوری دارید (موجودی حساب). رویداد برای کارهای پس‌زمینه و واکنش‌های جانبی است.
سؤال ۹ — Topic چیست؟ کانال دسته‌بندی رویدادهای هم‌نوع. مثلاً topic به نام orders که همه‌ی رویدادهای سفارش به آن می‌روند. مصرف‌کنندگان به topic مربوطه subscribe می‌شوند.
سؤال ۱۰ — مصرف‌کننده چه کارهایی باید انجام دهد؟ دریافت، بررسی نسخه‌ی schema، بررسی تکراری نبودن، اعتبارسنجی، اجرای منطق در یک تراکنش محلی، ثبت eventId و در پایان تأیید به Broker.

سطح Mid (۱۱ تا ۱۷)

سؤال ۱۱ — چرا انتشار مستقیم رویداد قبل از تراکنش کار نمی‌کند؟ چون اگر رویداد ارسال شود و تراکنش بعداً شکست بخورد، رویدادی برای چیزی که ذخیره نشده منتشر شده. اگر بعد از تراکنش بفرستید و ارسال شکست بخورد، داده ذخیره شده ولی کسی خبردار نشده. Outbox هر دو را حل می‌کند.
سؤال ۱۲ — الگوی Outbox چطور کار می‌کند؟ رویداد در یک جدول کنار داده‌ی کسب‌وکار و در همان تراکنش ذخیره می‌شود. یک پروسه‌ی جدا (relay) رویدادهای منتشرنشده را می‌خواند و به Broker می‌فرستد و سپس علامت می‌زند. نتیجه: یا هر دو ذخیره می‌شوند یا هیچ‌کدام.
سؤال ۱۳ — idempotency چیست و چرا ضروری است؟ یعنی پردازش دو بار همان پیام، همان اثر را داشته باشد. ضروری است چون هیچ پیام‌رسانی تحویل «دقیقاً یک‌بار» نمی‌دهد؛ کمینه‌ی واقعی «حداقل یک‌بار» است و مصرف‌کننده هر پیام را ممکن است دوباره ببیند.
سؤال ۱۴ — چگونه مصرف‌کننده را idempotent می‌کنید؟ با جدول processed_events: قبل از پردازش بررسی می‌کنید eventId دیده شده یا نه، و پس از پردازش آن را ثبت می‌کنید — در همان تراکنش منطق، تا اتمیک باشد. روش‌های دیگر: کلید یکتای طبیعی روی داده، یا قابلیت idempotent در Broker.
سؤال ۱۵ — DLQ چیست و چه زمانی لازم است؟ Dead Letter Queue، صفی برای پیام‌هایی که پس از چند تلاش ناموفق به DLQ می‌روند. بدون آن، پیام یا بی‌نهایت retry می‌شود (و منابع را می‌بلعد) یا بی‌صدا گم می‌شود. مهم‌تر از خود DLQ، پایش و هشدار روی آن است.
سؤال ۱۶ — چطور ترتیب رویدادها را حفظ می‌کنید؟ با استفاده از یک کلید مشخص (مثلاً orderId) هنگام انتشار. در Kafka، رویدادهای با کلید یکسان همیشه در یک پارتیشن می‌روند و ترتیبشان حفظ می‌شود. بدون کلید، ترتیب تضمین نمی‌شود.
سؤال ۱۷ — رویداد را چطور نسخه‌بندی می‌کنید؟ در مسیر package: com.shop.order.v1.OrderPlaced. قواعد سازگاری: افزودن فیلد مجاز است، حذف یا تغییر نوع فیلد مجاز نیست. برای تغییرات ناسازگار، نسخه‌ی جدید می‌سازید و نسخه‌ی قدیمی را مدتی نگه می‌دارید.

سطح Senior (۱۸ تا ۲۰)

سؤال ۱۸ — Saga چیست و چه جایگزینی برای تراکنش توزیع‌شده؟ الگویی برای هماهنگی عملیات در چند سرویس که به‌جای Rollback، از عملیات جبرانی استفاده می‌کند. دو نوع دارد: Choreography (هر سرویس به رویداد بعدی گوش می‌دهد) و Orchestration (یک سرویس مرکزی ترتیب می‌دهد). جایگزین عملی برای 2PC است.
سؤال ۱۹ — چگونه یک جریان EDA را عیب‌یابی می‌کنید؟ با سه ابزار: (۱) correlationId که از درخواست کاربر تا هر سرویس منتشر می‌شود؛ (۲) ثبت eventId در لاگ هر مصرف‌کننده؛ (۳) ابزارهای ردیابی توزیع‌شده مثل Jaeger. پیام‌های مانده در DLQ را با replay در محیط تست بررسی می‌کنید.
سؤال ۲۰ — چگونه در یک سازمان بزرگ EDA را معرفی می‌کنید؟ تدریجی و با یک جریان مشخص شروع می‌کنید (مثلاً اعلان سفارش). اول Outbox را بدون Broker به کار می‌برید تا سازگاری به دست آید، سپس یک مصرف‌کننده را جدا می‌کنید، و وقتی تیم مسلط شد زیرساخت را جدی می‌کنید. نکته‌ی مهم: ابزار پایش (lag و DLQ) را از روز اول بسازید، وگرنه دیر می‌فهمید که پیام‌ها گم شده‌اند.

بخش ۲۴پرسش‌های متداول (FAQ)

آیا EDA یعنی همه‌چیز ناهمگام باشد؟ نه. بهترین سیستم‌ها ترکیبی هستند: کاری که کاربر منتظرش است همگام، و کار پس‌زمینه‌ای رویدادمحور. درگاه پرداخت را همگام صدا بزنید ولی فاکتور و اعلان را با رویداد.
تفاوت Event Driven و Event Sourcing چیست؟ EDA درباره‌ی الگوی ارتباط است: چطور اجزا با هم حرف می‌زنند. Event Sourcing درباره‌ی ذخیره‌سازی است: به‌جای نگه‌داشتن وضعیت فعلی، رویدادها را نگه می‌دارید و وضعیت را از آن‌ها می‌سازید. می‌توانید یکی بدون دیگری داشته باشید.
آیا Kafka همان Broker است؟ Kafka یک پیاده‌سازی است، نه خود مفهوم. Brokerهای دیگر RabbitMQ، NATS، AWS SQS و Azure Service Bus هم هستند. انتخاب بین آن‌ها بیشتر به نیاز شما به ترتیب، حجم و مدل مصرف بستگی دارد.
آیا Outbox خودش یک anti-pattern نیست؟ نه، یک راه‌حل شناخته‌شده و پذیرفته‌شده برای مسئله‌ی «دو نوشتن». نقطه‌ی ضعفش این است که رویداد یک‌بار دیرتر منتشر می‌شود (به اندازه‌ی فاصله‌ی polling) و یک جدول اضافه می‌کند. برای اکثر سیستم‌ها این هزینه ناچیز است.
چطور رویداد تکراری را تشخیص دهم؟ هر رویداد باید یک eventId یکتا داشته باشد. مصرف‌کننده آن را در یک جدول با قید یکتا ثبت می‌کند و قبل از پردازش بررسی می‌کند. ثبت باید در همان تراکنش منطق باشد تا در صورت rollback دوباره پردازش شود.
آیا پیام‌ها باید کوچک باشند؟ بله، تا حد ممکن. پیام بزرگ یعنی مصرف‌کننده به داده‌ای وابسته می‌شود که شاید به آن نیاز نداشته باشد، سریال‌سازی کند می‌شود و نسخه‌بندی‌اش سخت است. اگر داده زیاد است، فقط شناسه بفرستید و اجازه دهید مصرف‌کننده بپرسد.
مصرف‌کننده‌ی کند چه مشکلی ایجاد می‌کند؟ اگر پارتیشن اشغال شود، مصرف‌کنندگان پشت آن صف می‌کنند و lag بالا می‌رود. راه‌حل: افزایش concurrency مصرف‌کننده، یا کاهش بار آن با تقسیم کار.
آیا می‌توان چند سرویس یک topic را مصرف کنند؟ بله، ولی هرکدام باید گروه مصرف‌کننده‌ی (consumer group) متفاوت داشته باشند تا هر پیام را یکی از آن‌ها بگیرد. اگر گروه یکسان باشد، کار بین اعضای همان گروه تقسیم می‌شود.
چطور رویدادهای قدیمی را دوباره پردازش کنم؟ در Kafka با تغییر offset گروه به نقطه‌ی قبلی. اما حواستان باشد که این کار همه‌ی مصرف‌کنندگان آن گروه را تحت تأثیر قرار می‌دهد؛ معمولاً یک گروه موقت با شناسه‌ی دیگر می‌سازید و پیام‌ها را به یک topic دیگر هدایت می‌کنید.
آیا EDA برای اپ موبایل مناسب است؟ برای همگام‌سازی آفلاین، بله. یک لایه‌ی sync می‌تواند تغییرات محلی را به‌صورت رویداد بفرستد و سرور تغییرات را برگرداند. ولی هسته‌ی منطق برنامه معمولاً بهتر است ساده بماند.
Event Notification یا Event Carrying State Transfer؟ اگر مصرف‌کننده داده‌ی تازه لازم دارد، Notification بهتر است. اگر داده در پیام آمده و تازگی آن مهم نیست، ECST سریع‌تر است و یک رفت‌وبرگشت شبکه را حذف می‌کند.
چقدر طول می‌کشد تا راه بیفتد؟ برای یک تیم مسلط: ۲ تا ۴ هفته. برای تیم تازه‌کار: ۲ تا ۳ ماه. بیشترین وقت صرف درک مفاهیم تحویل، idempotency و عیب‌یابی می‌شود، نه در کد زدن.
آیا به DevOps نیاز دارد؟ بله. EDA بدون پایش، یعنی سیستمی که خراب می‌شود و شما نمی‌دانید. داشبورد lag، هشدار DLQ و ردیابی توزیع‌شده بخشی از معماری است، نه ابزار جانبی.
چطور بین سرویس‌ها قرارداد را مدیریت کنم؟ یک ماژول یا مخزن جدا برای قراردادها بسازید و نسخه‌بندی را در مسیر package بگذارید. فقط Integration Event را مشترک کنید، نه مدل دامنه را.
مهم‌ترین توصیه برای شروع چیست؟ با یک جریان کاملاً مشخص شروع کنید، همه‌چیز را ناگهانی رویدادمحور نکنید. و از روز اول پایش lag و DLQ را بسازید، حتی اگر سیستم کوچک است.
اگر کاربر از «هنوز در حال پردازش است» شکایت کرد چه؟ این یک مسئله‌ی تجربه‌ی کاربری است، نه یک اشکال. راه‌حل‌ها: نمایش وضعیت پیشرفت، ارسال اعلان push پس از پایان، یا بهینه‌سازی زمان پردازش. معمولاً ترکیب اول و دوم کافی است.
چه زمانی باید از EDA دست بکشیم؟ وقتی پیچیدگی‌ای که اضافه کرده‌اید از مشکلی که حل کرده بیشتر شده است و تیم نتواند جریان را در ذهن نگه دارد. یا وقتی کاربر نتیجه را «همین الان» لازم دارد و سازگاری نهایی قابل قبول نیست.

جمع‌بندی

Event Driven Architecture قدرتمندترین و در عین حال خطرناک‌ترین معماری این سری است. قدرتمند است چون کوپل را کم می‌کند و کاربر را منتظر نمی‌گذارد؛ خطرناک است چون سیستم را از حالت قابل ردیابی خارج می‌کند.

تفاوت یک پیاده‌سازی خوب از یک پیاده‌سازی بد، در چهار چیز خلاصه می‌شود: Outbox برای اتمیک بودن، idempotency برای تحمل تکرار، DLQ برای نداشتن پیام گم‌شده، و پایش lag برای دیدن آنچه در جریان است. اگر این چهار را دارید، EDA شما قابل اعتماد است.

پیام پایانی سری ۱۴ مقاله‌ای این مقاله دوازدهمین عضو سری «معماری‌های نرم‌افزاری» است. اکنون الگوهای رابط کاربری (MVC، MVP، MVVM، MVI)، الگوهای معماری (Clean، Onion، Hexagonal، Layered، Repository، DDD)، ساختار کد (Feature Based) و ارتباط بین سرویس‌ها (Event Driven) را پوشش داده‌ایم. دو مقاله‌ی پایانی سری: CQRS و Microservices.
