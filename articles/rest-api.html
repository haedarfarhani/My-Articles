بخش ۱مقدمه و اهداف یادگیری

اگر در مصاحبه بپرسند «REST چیست؟»، اکثر مصاحبه‌شوندگان جواب می‌دهند: «API ای که با HTTP و JSON کار می‌کند». این جواب اشتباه است — و دقیقاً همان سوءتفاهمی است که این مقاله می‌خواهد از بین ببرد. بسیاری از «API های RESTful» ادعایی، در واقع REST نیستند.

اهداف یادگیری
  1. شش محدودیت معماری REST را بشناسید و بتوانید تشخیص دهید API شما REST هست یا نه
  2. منابع را به‌درستی نام‌گذاری و URI طراحی کنید
  3. متد و Status Code درست را برای هر عملیات انتخاب کنید
  4. صفحه‌بندی، فیلتر و جستجو را استاندارد پیاده کنید
  5. نسخه‌بندی و سازگاری رو به عقب را مدیریت کنید
  6. یک API کامل با Spring Boot و ASP.NET Core بسازید
یک حقیقت مهم REST مخفف Representational State Transfer است — یک سبک معماری، نه یک پروتکل و نه یک کتابخانه. نمی‌توانید «کتابخانه‌ی REST» نصب کنید. REST مجموعه‌ای از قواعد طراحی است که رعایتشان یا نکردنشان را خودتان تشخیص می‌دهید.

بخش ۲REST چیست؟ و تاریخچه‌ی Fielding

تعریف رسمی

REST یک سبک معماری سیستم‌های توزیع‌شده است که Roy Fielding در پایان‌نامه‌ی دکترای ۲۰۰۰ خود با عنوان «Architectural Styles and the Design of Network-based Software Architectures» مطرح کرد. REST نتیجه‌ی تحلیل معماری‌های موفق اینترنت (HTTP، URIs، HTML) بود و شش محدودیت را به‌عنوان تعریف ارائه داد.

نکته‌ی ظریف: REST برای وب جهانی طراحی شد، نه برای API های داخلی سازمان. به همین دلیل رعایت کامل آن در ارتباط سرویس‌به‌سرویس، همیشه معنادار نیست — و این را در بخش مقایسه می‌بینید.

تکامل از RPC تا REST

دهه‌ی ۱۹۹۰ — RPC (Remote Procedure Call)
  ایده: از راه دور، مثل تابع محلی فراخوانی کن
  نمونه: XML-RPC
  مشکل: عملیات را با endpoint یکی می‌گرفت
         POST /getUser  ← متد در مسیر!

دهه‌ی ۲۰۰۰ — SOAP
  ایده: قرارداد سفت + پاکت XML + WS-*
  مشکل: وزن زیاد، پیچیدگی، کاربرد سازمانی

۲۰۰۰ — REST (Fielding)
  ایده: منبع + HTTP + متد + نمایش (Representation)
  نمونه: GET /api/users/42

۲۰۱۵ — GraphQL
  ایده: بگذار Client شکل پاسخ را تعیین کند
  مشکل: پیچیدگی امنیت و کش

امروز — ترکیب
  REST برای API عمومی، gRPC برای داخلی،
  GraphQL برای مصرف‌کننده‌ی متنوع، SSE/WS برای بلادرنگ

بخش ۳شش محدودیت معماری

این شش مورد تعریف واقعی REST هستند. اگر یکی را عمداً و آگاهانه رعایت نکنید، دیگر کاملاً RESTful نیستید — که اشکالی ندارد، مهم این است که بدانید و بتوانید توضیح دهید.

#محدودیتچه می‌گویدهزینه‌ی نقض
۱Client-Serverمرز مشخص بین Client و Server؛ هرکدام مستقل تکامل می‌یابندترکیب منطق، امکان مستقل‌سازی از بین می‌رود
۲Statelessnessسرور هیچ وضعیت نشستی بین درخواست‌ها نگه نمی‌دارد؛ هر درخواست کامل استمقیاس‌پذیری و بازیابی خرابی سخت می‌شود
۳Cacheabilityهر پاسخ باید قابل کش باشد یا صریحاً غیرقابل کش بودنش را اعلام کندبار بی‌مورد روی سرور و تأخیر غیرضروری
۴Uniform Interfaceچهار جزء: شناسایی منابع، نمایش خودتوصیفی، خودتوضیحی درخواست، تعامل مبتنی بر HATEOASقرارداد پنهان، Client به جزئیات داخلی وابسته می‌شود
۵Layered SystemClient نمی‌داند آیا مستقیم به سرور وصل است یا از لایه‌هایی (proxy, gateway) رد شدهامکان قرار دادن CDN و Gateway از بین می‌رود
۶Code on Demand اختیاریسرور می‌تواند کد قابل اجرا (مثل اسکریپت) برای Client بفرستدمحدود — فقط افزودنی است
نکته‌ی مصاحبه‌ای

در مصاحبه اگر پرسیدند «چند محدودیت دارد؟» بگویید شش تا، که ششمی اختیاری است. و اگر پرسیدند «کدام مهم‌تر است؟» — پاسخ درست این است که هیچ‌کدام تنها نیست؛ ولی Uniform Interface هسته‌ی تمایز REST است، چون چهار جزءش دقیقاً همان چیزی است که «منبع + متد + نمایش» را می‌سازد.

جزء چهارم: Uniform Interface از نزدیک

۱) شناسایی منابع در URI
   هر منبع شناسه‌ی یکتای خودش را دارد
   GET /api/orders/ORD-1042

۲) نمایشِ خودتوصیفی (Self-descriptive)
   هر پاسخ نوع خودش را می‌گوید
   Content-Type: application/json
   و هر درخواست قواعدش را مشخص می‌کند
   Accept: application/json

۳) خودتوضیحی بودن درخواست
   متد + هدر + بدنه = تمام معنا
   GET /api/orders?status=SHIPPED
   (سرور نیازی به دانستن تاریخچه‌ی Client ندارد)

۴) HATEOAS
   پاسخ لینک‌های مرتبط را برمی‌گرداند
   { \"id\": 1042, \"_links\": { \"cancel\": \"/api/orders/1042/cancel\" } }

بخش ۴طراحی منابع و URI

طراحی REST با شناسایی منابع شروع می‌شود، نه با نوشتن متد. اول بپرسید «چه چیزی را می‌خواهید نشان دهید؟» و بعد «با آن چه می‌خواهید بکنید؟».

قاعدهدرستغلط
اسم فعل نگذارید/api/orders/api/getOrders
جمع باشید/api/users/42/orders/api/getUserOrder?id=42
مرتب‌سازی سلسله‌مراتبی/api/orders/1042/items/3/api/orderItem?o=1042&i=3
حرف کوچک + جداکننده‌ی -/api/order-items/api/OrderItems
حالت را از URI حذف کنیدDELETE /api/users/42/api/users/42/delete
منابع دارایی (Collection)/api/users/api/userList

دو اشتباه مرگبار
  • URI حساس به حروف بزرگ: /API/Users و /api/users دو چیز متفاوت‌اند. یکی را انتخاب و رعایت کنید.
  • حالت نهفته در URI: /users/42/activate مجاز نیست مگر اینکه activate یک sub-resource واقعی باشد؛ وگرنه متد PATCH با {"active":true} درست‌تر است.

PUT در برابر PATCH

PUT — جایگزینی کامل

  • بدنه باید تمام فیلدهای لازم را داشته باشد
  • فیلدهای غایب، پیش‌فرض یا حذف می‌شوند
  • تکرار بی‌خطر است: همیشه به همان وضعیت می‌رسید
  • مثال: PUT /users/42
VS

PATCH — تغییر جزئی

  • فقط فیلدهای ارسالی عوض می‌شوند
  • بقیه‌ی فیلدها دست‌نخورده می‌مانند
  • تکرار بی‌خطر فقط اگر عملیات جایگزینی باشد
  • مثال: PATCH /users/42
PUT یا PATCH؟

اگر می‌توانید کل منبع را بدون اطلاع قبلی بازنویسی کنید، PUT. اگر کلاینت فقط بخشی را دارد (مثلاً فقط فیلد «نام خوانوادگی» عوض شده)، PATCH. اغلب سرویس‌ها هر دو را پشتیبانی می‌کنند و PATCH برای اپ‌های موبایل که فهرست فیلدها محدود است، راحت‌تر است.

بخش ۶جریان داده و نمونه‌ی Request/Response

یک چرخه‌ی کامل

① Client          GET /api/users/42
                  Accept: application/json
                  Authorization: Bearer ...

② Gateway         احراز هویت + Rate Limit + مسیریابی

③ Controller      پارس مسیر و هدر → ساخت DTO

④ Service         منطق دامنه + قواعد تجاری

⑤ Repository      SELECT ... WHERE id = 42

⑥ Database        رکورد یا عدم وجود

⑦ نگاشت          Entity → DTO (بدون لو رفتن جدول‌ها)

⑧ Serialization   تبدیل DTO به JSON

⑨ Response        200 OK + ETag + Cache-Control
🧪 دموی تعاملی: متد و Request زنده

متد را عوض کنید: بدنه، هدرها، ایدمپوتنت بودن و Status Code پاسخ تغییر می‌کنند.

بخش ۷Representations و Content Negotiation

نکته‌ی ظریف REST این است: منبع و نمایش آن، دو چیز جدا هستند. شما URL را /api/users/42 می‌گیرید، ولی می‌توانید JSON، XML یا حتی CSV بگیرید. همان منبع، نمایش‌های متعدد دارد.

نمایشهدرکاربرد
JSONapplication/jsonپیش‌فرض اکثر API ها
XMLapplication/xmlیکپارچگی سازمانی، SOAP
CSVtext/csvگزارش‌گیری و اکسل
HTMLtext/htmlHATEOAS و نمایش انسانی
HTML+JSONapplication/vnd.myapp.v2+jsonنسخه‌بندی با هدر
 
── درخواست: چه قالبی را می‌پذیرم؟
GET /api/users/42 HTTP/1.1
Accept: application/json;q=0.9, application/xml;q=0.8
Accept-Language: fa-IR, fa;q=0.9

── پاسخ: چه قالبی را انتخاب کردم

هدر Vary را فراموش نکنید بدون Vary: Accept، یک کش می‌تواند پاسخ JSON را به درخواست XML برگرداند. این یکی از رایج‌ترین خطاهای کش در سیستم‌های چندزبانه و چندقالبی است.
واقعیت عملی اکثر تیم‌ها فقط JSON تولید می‌کنند و این کاملاً قابل قبول است — به شرط آنکه صریحاً مستند کنند: «فقط JSON». سکوت درباره‌ی قالب‌ها، Client را وادار به حدس می‌کند.

بخش ۸صفحه‌بندی، فیلتر، مرتب‌سازی و جستجو

هر فهرستی در مرحله‌ای از رشد، بدون صفحه‌بندی از کار می‌افتد. قاعده: هیچ‌وقت یک endpoint فهرست بدون سقف تعداد نسازید — یک ?size=999999 می‌تواند کل دیتابیس را بیرون بکشد و سرور را زمین بزند.

نیازپارامترمثال
صفحه‌بندیpage + size?page=0&size=20
فیلترنام‌فیلد=مقدار?status=SHIPPED
مرتب‌سازیsort?sort=createdAt,desc
جستجوq یا search?q=ali
بازه‌ی زمانیfrom + to?from=2026-01-01&to=2026-03-31
انتخاب فیلدfields?fields=id,name

Offset یا Cursor؟

Offset-based

  • ?page=3&size=20
  • ساده و قابل فهم
  • در صفحات عمیق کند می‌شود (database باید ۶۰ رکورد را دور بریزد)
  • ناسازگار با داده‌ی در حال تغییر: رکورد جدید، آیتم را جابه‌جا می‌کند
VS

Cursor-based

  • ?after=eyJpZCI6MTA0Mn0
  • در عمق زیاد هم سریع (ایندکس مستقیم)
  • پایدار در برابر درج/حذف هم‌زمان
  • پیچیده‌تر؛ پیمایش تصادفی ندارد
Offset:  SELECT * FROM orders ORDER BY id LIMIT 20 OFFSET 40
         ► ایندکس را از ۰ تا ۴۰ طی می‌کند (در عمق زیاد گران)Cursor:  SELECT * FROM orders WHERE id > 1042 ORDER BY id LIMIT 20
         ► مستقیم از ۱۰۴۲ شروع می‌کند (همیشه ارزان)

قاعده‌ی انتخاب:
  لیست‌های کوتاه و صفحه‌بندی شماره‌دار  ►  offset
  فیدهای بی‌انتها و لیست‌های بلند      ►  cursor

بخش ۹HATEOAS

تعریف HATEOAS مخفف Hypermedia As The Engine Of Application State است: پاسخ علاوه بر داده، لینک‌های اقدام بعدی ممکن را هم برمی‌گرداند تا Client رفتارش را از خودِ پاسخ بیاموزد، نه از دانش ازپیش‌کدشده. 
{
  "id": 1042,
  "status": "PENDING",
  "total": 1450000,
  "_links": {
    "self":    { "href": "/api/orders/1042" },
    "cancel":  { "href": "/api/orders/1042/cancel", "method": "POST" },
    "payment": { "href": "/api/orders/1042/payment", "method": "POST" },
    "items":   { "href": "/api/orders/1042/items" }
  }
}

وقتی سفارش لغو می‌شود، لینک cancel دیگر برنمی‌گردد. Client مجبور نیست بداند «سفارشِ لغوشده قابل لغو نیست» — خودِ داده به او می‌گوید چه می‌تواند بکند.

چرا در عمل کم رعایت می‌شود؟

سه هزینه دارد: پیچیدگی سمت سرور، پیچیدگی تست (پاسخ‌ها به وابستگی حساس‌اند)، و نیاز به قرارداد لینک‌ها. به همین دلیل اکثر تیم‌ها به قرارداد ثابت + OpenAPI بسنده می‌کنند و HATEOAS را رها می‌کنند. این انتخاب آگاهانه‌ای است و اشکالی ندارد — فقط به یاد داشته باشید که در آن صورت، API شما کامل RESTful نیست.

بخش ۱۰نسخه‌بندی (Versioning)

نسخه‌بندی فقط برای تغییر شکننده لازم است. اگر فیلدی اضافه می‌کنید یا endpoint تازه می‌سازید، نسخه‌ی جدید لازم نیست.

روشمثالموافقمخالف
URI/api/v1/usersساده، قابل تشخیص، کش‌پذیرمسیر را شلوغ می‌کند؛ از نظر REST خالص اشکال دارد (منبع باید پایدار بماند)
هدرAccept: application/vnd.myapp.v1+jsonURI تمیز می‌ماندتست و کش سخت‌تر؛ در مرورگر مستقیم قابل تست نیست
Query?version=1خیلی سادهدر همه‌ی درخواست‌ها باید تکرار شود؛ فراموش‌شدنی است
Media Typeapplication/vnd.myapp.v1+jsonاز Content Negotiation واقعی استفاده می‌کندپیچیده‌ترین پیاده‌سازی
 
سازگاری رو به عقب (Backward Compatible) — مجاز بدون نسخه‌ی جدید:
  + افزودن فیلد جدید (اختیاری)
  + افزودن endpoint جدید
  + افزودن مقدار مجاز جدید به enum (با احتیاط)
  + افزودن پارامتر query اختیاری

تغییر شکننده (Breaking) — نیازمند نسخه‌ی جدید:
  − حذف فیلد
  − تغییر نوع فیلد (string → number)
  − تغییر معنای فیلد (amount به ریال، نه تومان!)
  − تغییر Status Code پاسخ
  − تغییر الزامی بودن فیلد
  − تغییر نام یا مسیر منبع

استراتژی خروج (Sunset)

  1. اعلام — هدر Sunset: Sat, 01 Nov 2027 00:00:00 GMT و مستندات
  2. هشدار — هدر Deprecation: true روی نسخه‌ی قدیمی
  3. دوره‌ی همپوشانی — هر دو نسخه هم‌زمان فعال باشند (معمولاً ۶ تا ۱۲ ماه)
  4. نظارت — ترافیک نسخه‌ی قدیمی را اندازه بگیرید تا بدانید کی واقعاً قطع کنید
  5. قطع — 410 Gone + پیام راهنمای مهاجرت
HTTP/1.1 200 OK
Deprecation: true
Sunset: Sat, 01 Nov 2027 00:00:00 GMT
Link: <https://api.example.com/v2/users>; rel="successor-version"
روش پیشنهادی URI versioning برای اکثر تیم‌ها عملی‌ترین انتخاب است: واضح، در لاگ‌ها قابل ردیابی، و در Gateway به‌سادگی مسیریابی می‌شود. پیچیدگی هدر را فقط وقتی بپذیرید که واقعاً نیاز دارید URI را تمیز نگه دارید.

ایدمپوتنت بودن در عمل

وقتی شبکه قطع می‌شود، Client نمی‌داند درخواست به سرور رسیده یا نه. تنها راه امن، تلاش مجدد است — و تنها راه امنِ تلاش مجدد، ایدمپوتنت بودن است.

package com.example.api.security;

import jakarta.servlet.FilterChain;
import jakarta.servlet.ServletException;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import org.springframework.lang.NonNull;
import org.springframework.security.core.Authentication;
import org.springframework.security.core.context.SecurityContextHolder;
import org.springframework.stereotype.Component;
import org.springframework.web.filter.OncePerRequestFilter;

import java.io.IOException;
import java.util.Set;

/**
 * کنترل مالکیت: کاربر فقط به منابع خودش دسترسی دارد.
 * قاعده‌ی طلایی: بررسی مالکیت، همیشه سمت سرور.
 */
@Component
public class OwnershipFilter extends OncePerRequestFilter {

    private static final Set<String> PROTECTED = Set.of("/api/users/");

    @Override
    protected void doFilterInternal(@NonNull HttpServletRequest req,
                                    @NonNull HttpServletResponse res,
                                    @NonNull FilterChain chain) throws ServletException, IOException {

        String path = req.getRequestURI();
        boolean isProtected = PROTECTED.stream().anyMatch(path::startsWith);

        if (isProtected) {
            Authentication auth = SecurityContextHolder.getContext().getAuthentication();
            if (auth == null || auth.isAuthenticated() == false) {
                res.sendError(HttpServletResponse.SC_UNAUTHORIZED, "Unauthorized");
                return;
            }
            String currentUserId = auth.getName();
            String pathUserId = extractUserId(path);   // /api/users/{id}/...

            // مدیر می‌تواند همه را ببیند؛ بقیه فقط خودشان را
            boolean isAdmin = auth.getAuthorities().stream()
                    .anyMatch(a -> "ROLE_ADMIN".equals(a.getAuthority()));

            if (pathUserId != null && !isAdmin && !pathUserId.equals(currentUserId)) {
                res.sendError(HttpServletResponse.SC_FORBIDDEN, "Forbidden");
                return;
            }
        }
        chain.doFilter(req, res);
    }

    private String extractUserId(String path) {
        String[] parts = path.split("/");
        // /api/users/42/orders → 42
        return parts.length > 3 && "users".equals(parts[2]) ? parts[3] : null;
    }
}

چهار عامل واقعی زمان پاسخ

زمان کل = تأخیر شبکه + سریال‌سازی + پردازش سرور + تأخیر دیتابیس

مثال واقعی (اندازه‌گیری، نه حدس):
  تأخیر شبکه (۱ hop)         ۸ ms
  سریال‌سازی JSON (۵ KB)     ۱ ms
  پردازش سرور (Business)    ۱۲ ms
  دیتابیس (ایندکس خوب)      ۱۴ ms
  ──────────────────────────────────
  جمع                      ۳۵ ms  ◄ این را گزارش کنید

با N+1 query:
  ۱ + ۲۰ فراخوانی = ۸ + ۱ + ۱۲ + ۲۰×۱۴ = ۳۰۱ ms  ◄ همان API، ۸ برابر کندتر
نکته‌ی مهم درباره‌ی کارایی هرگز ننویسید «X سریع‌تر از Y است». آنچه مهم است، تعداد round-trip، حجم payload، زمان دیتابیس و تعداد پرس‌وجو است. این‌ها را اندازه بگیرید و همان را گزارش کنید — نه عددی که از وبلاگی خوانده‌اید.

package com.example.shop.order;

import jakarta.validation.Valid;
import org.springframework.data.domain.Page;
import org.springframework.data.domain.PageRequest;
import org.springframework.data.domain.Pageable;
import org.springframework.data.domain.Sort;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;

import java.net.URI;
import java.util.List;

@RestController
@RequestMapping("/api/orders")
public class OrderController {

    private final OrderService service;
    private final OrderResourceAssembler assembler;

    public OrderController(OrderService service, OrderResourceAssembler assembler) {
        this.service = service;
        this.assembler = assembler;
    }

    /* ---------- GET /api/orders?status=&page=&size=&sort= ---------- */
    @GetMapping
    public Page<OrderResource> list(
            @RequestParam(required = false) String status,
            @RequestParam(required = false) String q,
            @RequestParam(defaultValue = "0") int page,
            @RequestParam(defaultValue = "20") int size,
            @RequestParam(defaultValue = "createdAt,desc" ) String sort) {

        int safeSize = Math.min(Math.max(size, 1), 100);      // سقف اجباری
        Sort sortOrder = parseSort(sort);                      // فقط فیلدهای مجاز!
        Pageable pageable = PageRequest.of(Math.max(page, 0), safeSize, sortOrder);

        return service.find(status, q, pageable).map(assembler::toResource);
    }

    /* ---------- GET /api/orders/1042 ---------- */
    @GetMapping("/{id}")
    public ResponseEntity<OrderResource> get(@PathVariable long id) {
        return service.findById(id)
                .map(assembler::toResource)
                .map(ResponseEntity::ok)
                .orElseGet(() -> ResponseEntity.notFound().build());
    }

    /* ---------- POST /api/orders → 201 + Location + ETag ---------- */
    @PostMapping
    public ResponseEntity<OrderResource> create(
            @Valid @RequestBody CreateOrderRequest req,
            @RequestHeader(value = "Idempotency-Key", required = false) String key) {

        Order created = service.create(req, key);              // کلید در همان تراکنش
        OrderResource body = assembler.toResource(created);

        return ResponseEntity
                .created(URI.create("/api/orders/" + created.id()))
                .eTag('"' + created.version() + '"')
                .body(body);
    }

    /* ---------- PUT /api/orders/1042 (idempotent) ---------- */
    @PutMapping("/{id}")
    public ResponseEntity<OrderResource> replace(
            @PathVariable long id,
            @Valid @RequestBody CreateOrderRequest req,
            @RequestHeader(value = "If-Match", required = false) String ifMatch) {

        Order updated = service.replace(id, req, ifMatch);     // شکست هم‌زمانی → 412
        return ResponseEntity.ok(assembler.toResource(updated));
    }

    /* ---------- DELETE /api/orders/1042 → 204 ---------- */
    @DeleteMapping("/{id}")
    public ResponseEntity<Void> delete(@PathVariable long id) {
        service.delete(id);
        return ResponseEntity.noContent().build();
    }

    /** فقط فیلدهای مجاز — جلوگیری از Sort Injection */
    private Sort parseSort(String raw) {
        String[] parts = raw.split(",");
        String field = parts[0];
        boolean asc = parts.length < 2 || "asc".equalsIgnoreCase(parts[1]);
        if (!Order.SORTABLE.contains(field)) field = "createdAt";
        return asc ? Sort.by(field).ascending() : Sort.by(field).descending();
    }
}

Domain نباید Spring یا EF بشناسد (تک‌منبعی و تست بدون زیرساخت). و DTO نباید Entity باشد (امنیت + قرارداد ثابت). هر سه این ها اگر رعایت نشوند، تغییر قرارداد API با تغییر جدول دیتابیس یکی می‌شود — و آن‌وقت دیگر نمی‌توانید مستقل تکامل دهید.

بخش ۱۸مزایا

✅ مزایا
  • سادگی مدل فکری — منبع + متد + پاسخ؛ هر کسی در چند دقیقه می‌فهمد.
  • بی‌طرفی کامل — زبان، فریم‌ورک و سیستم‌عامل مهم نیست؛ HTTP زبان مشترک است.
  • کش ذاتی — به‌لطف Cacheability، کش مرورگر/CDN/سرور بدون طراحی خاصی ممکن است.
  • مستندسازی ساده — OpenAPI از annotation تولید و خودکار نگه داشته می‌شود.
  • تست‌پذیری — با هر HTTP client ابزاری قابل آزمون است.
  • مقیاس‌پذیری — Statelessness امکان افزودن نمونه بدون پیکربندی خاص می‌دهد.
  • محدودیت نرخ و امنیت — در Gateway یکجا پیاده می‌شود.
  • زبان صنعت — تقریباً هر توسعه‌دهنده‌ای آن را می‌شناسد؛ هزینه‌ی استخدام کم.
  • مرحله‌به‌مرحله — می‌توانید endpoint را کم‌کم عرضه و نسخه‌بندی کنید.
  • پایش‌پذیری — هر درخواست قابل لاگ، متریک و ردیابی است.
  • سازگار با وب — مرورگر، CDN و ابزارهای شبکه بی‌واسطه کار می‌کنند.

بخش ۱۹معایب

⚠️ معایب
  • Over-fetching — ممکن است فیلدهایی را بگیرید که لازم ندارید (چون مسیر از پیش تعریف شده).
  • Under-fetching — برای نمایش یک صفحه‌ی پیچیده، چند round-trip لازم است.
  • تعداد round-trip بالا — در لایه‌ی UI پرحجم واقعاً به چشم می‌آید.
  • HTTP/1.1 محدودیت اتصال دارد — در ترافیک بالا، بهینه‌سازی لازم است.
  • هیچ قرارداد زمان‌دار ندارد — Webhook و جریان بلادرنگ خارج از مدل طبیعی REST هستند.
  • نیاز به صریح‌سازی مداوم — بدون نسخه‌بندی و مستند، به‌سرعت فرسوده می‌شود.
  • REST خالص به‌ندرت رعایت می‌شود — HATEOAS معمولاً حذف می‌شود و این باعث سوءتفاهم می‌شود.
  • امنیت وظیفه‌ی همیشگی است — CORS، rate limit، اعتبارسنجی، مالکیت — همیشه.
  • سرریز (Serialization) — تبدیل اشیاء به JSON در حجم بالا هزینه دارد.
  • پنهان‌سازی خطای دیتابیس — بدون قاعده، جزئیات خطا نشت می‌کند.
  • هیچ تضمین تحویلی ندارد — برای عملیات حساس به ایدمپوتنتی نیاز است.
بزرگ‌ترین سوءتفاهم «هر API ای که JSON برمی‌گرداند REST است» — غلط. اگر از POST برای خواندن استفاده می‌کنید، یا وضعیت را در سرور نگه می‌دارید، یا کش را کاملاً غیرفعال کرده‌اید، RESTful نیستید. این اشکالی ندارد — ولی باید بدانید و بتوانید دلیلش را توضیح دهید.

بخش ۲۳سؤالات مصاحبه

سطح پایه (Junior)

سؤال ۱ — REST چیست؟

یک سبک معماری سیستم‌های توزیع‌شده است که Roy Fielding در پایان‌نامه‌ی ۲۰۰۰ معرفی کرد. بر پایه‌ی شش محدودیت استوار است: Client-Server، Statelessness، Cacheability، Uniform Interface، Layered System و Code on Demand (اختیاری). تمرکزش روی منابع و نمایش‌ها است.

سؤال ۲ — آیا هر API ای که JSON برمی‌گرداند RESTful است؟

خیر. JSON فقط قالب داده است و هیچ ارتباطی با تعریف REST ندارد. REST یعنی رعایت شش محدودیت: منبع‌محور بودن، متد HTTP درست، Statelessness، قابلیت کش و … . یک API که با POST /getUser کار می‌کند و JSON برمی‌گرداند، RESTful نیست.

سؤال ۳ — تفاوت PUT و PATCH؟

PUT کل منبع را با بدنه‌ی داده‌شده جایگزین می‌کند؛ فیلدهای نیامده به پیش‌فرض می‌روند. PATCH فقط فیلدهای ارسالی را عوض می‌کند. هر دو می‌توانند ایدمپوتنت باشند، به شرطی که عملیات جایگزینی باشد.

سؤال ۴ — برای ساخت یک منبع کدام متد و کدام Status Code؟

POST روی collection (مثلاً /api/users) با پاسخ 201 Created و هدر Location که آدرس منبع تازه را مشخص می‌کند. هرگز 200 یا GET برای ساخت.

سؤال ۵ — 404 و 204 چه معنایی دارند؟

404 یعنی منبع وجود ندارد. 204 یعنی موفقیت بدون بدنه — معمولاً برای DELETE یا عملیاتی که چیزی برای برگرداندن ندارد. فرستادن 200 با بدنه‌ی خالی هم ممکن است ولی 204 صریح‌تر است.

سؤال ۶ — Idempotency یعنی چه؟ مثال بزنید.

یعنی تکرار درخواست، همان اثرِ یک بار را دارد. PUT و DELETE ذاتاً ایدمپوتنت‌اند (دو بار حذف = منبع از قبل حذف شده). POST نیست؛ برای آن از Idempotency-Key استفاده می‌کنیم.

سؤال ۷ — Statelessness یعنی چه و فایده‌اش چیست؟

سرور وضعیت نشست را بین درخواست‌ها نگه نمی‌دارد؛ هر درخواست خوداتکاست و اطلاعات لازم را حمل می‌کند (معمولاً توکن). فایده: می‌توانید بدون Sticky Session و پیکربندی خاص، نمونه‌های بیشتری اضافه و بار را تقسیم کنید.

سؤال ۸ — Content-Type و Accept چه فرقی دارند؟

Content-Type نوع بدنه‌ی فعلی را می‌گوید (در Request: نوع بدنه‌ی ارسالی؛ در Response: نوع بدنه‌ی برگشتی). Accept فقط در درخواست است و می‌گوید Client چه قالب‌هایی را می‌پذیرد.

سؤال ۹ — ETag چیست؟

اثر انگشت محتوای یک پاسخ است. Client آن را نگه می‌دارد و در درخواست بعدی با If-None-Match برمی‌گرداند. اگر سرور محتوا را تغییر نداده باشد، با 304 Not Modified پاسخ می‌دهد — بدون انتقال بدنه. نتیجه: پهنای باند و زمان پاسخ کمتر.

سؤال ۱۰ — چرا URI ها باید جمع باشند؟

چون منبع، خودِ موجودیت است نه عملیات. /api/users/42/orders یعنی «سفارش‌های این کاربر» — یک منبع. عملیات را متد HTTP بیان می‌کند، نه URI. نگاشت یک‌به‌یک «نام جدول ↔ نام endpoint» هم اشتباه است.

سطح متوسط (Mid)

سؤال ۱۱ — Offset یا Cursor، کدام را انتخاب می‌کنید و چرا؟

برای فیدهای بلادرنگ و لیست‌های بسیار طولانی، cursor چون با WHERE id > X ایندکس را مستقیم می‌زند و در عمق زیاد کند نمی‌شود. برای صفحه‌بندی شماره‌دار با صفحات کم، offset چون ساده و قابل پیمایش تصادفی است. نکته‌ی مهم: offset با درج هم‌زمان، آیتم‌ها را جابه‌جا می‌کند (رد شدن یا تکرار آیتم).

سؤال ۱۲ — اگر ?size=999999 بیاید چه می‌کنید؟

سقف را در سرور اعمال می‌کنم: size = Math.min(Math.max(size,1), 100). و به Client اعلام می‌کنم سقف چقدر است (در مستندات یا در بدنه‌ی پاسخ). تکیه بر اعتبارسنجی Client کافی نیست — هرکسی می‌تواند curl بزند.

سؤال ۱۳ — HATEOAS چیست و چرا کمتر پیاده می‌شود؟

یعنی پاسخ، لینک اقدام بعدی را هم برمی‌گرداند تا Client رفتارش را از داده بیاموزد. عملاً کم رعایت می‌شود چون پیچیدگی سرور و تست را بالا می‌برد و اکثر تیم‌ها قرارداد ثابت + OpenAPI را کافی می‌دانند. صادقانه بگویید که رعایت نکرده‌اید — بدتر از آن، ادعای REST بدون HATEOAS است.

سؤال ۱۴ — تفاوت private و public در Cache-Control؟

public یعنی هر کشی (شامل CDN) می‌تواند ذخیره کند — مناسب داده‌ی عمومی. private یعنی فقط کش مرورگر خود کاربر مجاز است — مناسب داده‌ی شخصی. اگر public را روی داده‌ی شخصی بگذارید، ممکن است پاسخ یک کاربر در CDN برای کاربر دیگر سرو شود — یک نشت واقعی.

سؤال ۱۵ — چرا POST کش نمی‌شود؟

چون GET تعریف‌شده‌اش ایمن و تکرارپذیر است؛ POST اثر جانبی ایجاد می‌کند و کش کردن آن یعنی اجرای نشدن عملیات واقعی. مرورگرها هم عملاً POST را کش نمی‌کنند. برای پاسخ‌های پس از POST باید Client صراحتاً یک GET بزند.

سؤال ۱۶ — محدودیت نرخ را کجا و با کدام الگوریتم؟

معمولاً در Gateway یا میدل‌ور وب، پیش از منطق دامنه و مبتنی بر شناسه‌ی Client (کلید یا IP). Token Bucket رایج‌ترین است چون موج کوتاه را می‌پذیرد؛ Sliding Window دقیق‌تر است ولی گران‌تر. پاسخ باید 429 + Retry-After باشد.

سؤال ۱۷ — چطور از خواندن هم‌زمان روی یک رکورد جلوگیری می‌کنید؟

با optimistic locking: نسخه را در ETag برگردانید و Client آن را در If-Match بفرستد. اگر نسخه عوض شده باشد، 412 Precondition Failed. جایگزین: pessimistic locking که قفل ردیف را می‌گیرد — ساده‌تر ولی در ترافیک بالا مقیاس نمی‌یابد.

سؤال ۱۸ — Mass Assignment چیست؟

وقتی کل بدنه‌ی درخواست مستقیماً به Entity دیتابیس bind می‌شود، Client می‌تواند فیلدی مثل role=admin یا balance بفرستد و اعمال شود. راه‌حل: DTO مجزا برای ورودی، با فیلدهای صریح و محدود — هرگز Entity را مستقیم bind نکنید.

سطح پیشرفته (Senior)

سؤال ۱۹ — اگر تیمی بخواهد REST خالص رعایت شود ولی سقف ددلاین داشته باشید، چه می‌کنید؟

اول اهمیت هر محدودیت را برای این مسئله می‌سنجم. Statelessness و Cacheability معمولاً بیشترین ارزش عملی را دارند و باید بمانند. HATEOAS (جزء Uniform Interface) معمولاً کمترین بازده را در قیاس با هزینه‌اش دارد و می‌توان با قرارداد ثابت جایگزین کرد — ولی باید صریحاً اعلام شود که «عمداً کامل RESTful نیستیم» و دلیلش در مستندات باشد. تصمیم باید آگاهانه و مستند باشد، نه پیش‌فرض.

سؤال ۲۰ — یک API با ۱۰ round-trip برای رندر یک صفحه دارید. چه می‌کنید؟

سه گزینه را با هزینه‌ی هرکدام می‌سنجم: ۱) تجمیع در سرور (endpoint فهرستی مثل /dashboard) — ساده، اما ممکن است مصرف‌کننده‌های دیگر را محدود کند؛ ۲) پارامترهای fields و expand تا پاسخ دقیقاً همان چیزی را بدهد که لازم است — انعطاف‌پذیر ولی قرارداد را پیچیده می‌کند؛ ۳) تغییر معماری به BFF برای آن کلاینت خاص یا GraphQL. انتخاب به تعداد مصرف‌کننده‌ها، میزان تفاوت نیازشان و توان نگهداری تیم بستگی دارد — معمولاً برای یک صفحه، گزینه‌ی ۱ پایین‌ترین هزینه را دارد.

بخش ۲۴پرسش‌های متداول (FAQ)

آیا REST همان HTTP است؟

نه. HTTP یک پروتکل انتقال است و REST یک سبک معماری. REST می‌تواند روی هر پروتکلی پیاده شود، ولی در عمل تقریباً همیشه روی HTTP است. بالعکس هم درست است: هر API مبتنی بر HTTP لزوماً REST نیست.

آیا REST باید حتماً JSON باشد؟

نه. REST با قالب داده کاری ندارد — XML، CSV، YAML و HTML هم می‌توانند نمایش (Representation) باشند. JSON فقط پرکاربردترین است چون سبک، خوانا و بومی مرورگرهاست.

PUT و POST هر دو داده می‌فرستند؛ کدام را انتخاب کنم؟

اگر منبع را می‌سازید یا عملیاتی دارید که هر بار اثر جدیدی می‌سازد: POST. اگر منبعی با شناسه‌ی مشخص را جایگزین می‌کنید: PUT. قاعده‌ی سریع: POST برای ساخت، PUT برای بازنویسی.

چرا GET /users/42/delete اشتباه است؟

چون سه مشکل دارد: ۱) فعل در URI آمده؛ ۲) GET باید ایمن باشد و نباید وضعیت عوض کند (مرورگر، کش و prefetch ممکن است آن را اجرا کنند)؛ ۳) معنای درست، DELETE /users/42 است. روش درست: DELETE.

محدودیت نرخ با کدام Status Code پاسخ داده می‌شود؟

429 Too Many Requests به‌همراه هدر Retry-After که مشخص می‌کند چند ثانیه بعد تلاش کنید، و هدرهای X-RateLimit-* برای نمایش باقی‌مانده. استفاده از 503 یا 403 اشتباه است.

چه زمانی نسخه‌ی جدید بدهم؟

فقط برای تغییر شکننده: حذف یا تغییر نوع/معنای فیلد، تغییر Status Code، تغییر الزامی بودن. افزودن فیلد اختیاری، افزودن endpoint یا افزودن مقدار جدید به enum معمولاً نیاز ندارد. جزئیات در مقاله‌ی نسخه‌بندی.

آیا باید همه‌ی endpoints ها را مستند کنم؟

بله — و بهترین راه، مستندسازی خودکار با OpenAPI است که از annotation تولید می‌شود تا با کد به‌روز بماند. مستندِ کهنه بدتر از نبود مستند است چون Client را به مسیر غلط می‌برد. جزئیات در مقاله‌ی مستندسازی.

HATEOAS را باید پیاده کنم؟

اگر API عمومی با مصرف‌کننده‌های ناشناس دارید، ارزش بررسی دارد. اگر مصرف‌کننده‌ها داخلی و کنترل‌شده‌اند، قرارداد ثابت + OpenAPI معمولاً کافی است. مهم‌تر از آن: تصمیم را صریحاً بگیرید و مستند کنید.

چطور یک خطای دیتابیس را به Client نشان ندهم؟

در لایه‌ی وب یک ExceptionTranslator (Spring) یا ExceptionMiddleware (ASP.NET) داشته باشید که استثناها را به پاسخ استاندارد تبدیل کند، جزئیات داخلی را فقط لاگ کند (با traceId) و در پاسخ فقط پیام عمومی + شناسه‌ی پیگیری بدهد.

برای لیست‌های بزرگ، چرا totalElements خطرناک است؟

چون COUNT(*) روی جدول بزرگ می‌تواند صدها میلی‌ثانیه طول بکشد و در لیست‌های پرتکرار جمع می‌شود. جایگزین: شمارش تخمینی، شمارش فقط در صفحه‌ی اول، یا حذف آن در فیدهای بی‌انتها.

آیا REST برای بلادرنگ مناسب است؟

نه به شکل ذاتی. مدل Request/Response برای جریان مداوم طراحی نشده. برای یک‌طرفه: SSE؛ برای دوطرفه: WebSocket؛ برای انتشار رویداد: Webhook.

اگر عملیات چند ثانیه طول بکشد چه کنم؟

آن را از مسیر پاسخ خارج کنید: 202 Accepted + آدرس پیگیری (مثلاً /api/jobs/j_991) برگردانید و نتیجه را بعداً با GET، یا از طریق Webhook/SSE اعلام کنید. علت: مرورگرها و پروکسی‌ها معمولاً پس از ۳۰–۶۰ ثانیه اتصال را می‌بندند.

بخش ۲۵جمع‌بندی و مقالات مرتبط

آنچه باید به یاد بماند
  1. اول منبع، بعد متد — بپرسید «چه چیزی؟» و بعد «چه عملیاتی؟»، نه برعکس.
  2. شش محدودیت را بشناسید — و بدانید کدام را عمداً رعایت نمی‌کنید و چرا.
  3. Status Code صادق باشد — 200 برای خطا ندهید؛ 401 و 403 را قاطی نکنید.
  4. سقف و whitelist — هیچ پارامتری از Client بدون محدودیت به دیتابیس نرسد.
  5. Idempotency-Key برای عملیات حساس — پرداخت، ثبت سفارش، انتقال وجه.
  6. Cache-Control صریح — یا private, no-store برای داده‌ی حساس، یا ETag + max-age برای داده‌ی گران.
  7. DTO از Entity جداست — قرارداد عمومی هرگز نباید به اسکیمای داخلی وابسته باشد.
