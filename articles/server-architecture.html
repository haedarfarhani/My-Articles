آکادمی معماری سرور؛ از Web Server تا Production

یک درخواست واقعی چطور از مرورگر به دیتابیس می‌رسد و دوباره برمی‌گردد؟ این مسیر یادگیری، هر لایه را جداگانه توضیح می‌دهد: DNS، Firewall، Web Server، Reverse Proxy، Load Balancer، Application Server، Backend، Redis و PostgreSQL — و سپس نشان می‌دهد این لایه‌ها در Production چطور با TLS، Health Check، Monitoring و Zero-Downtime Deployment به هم می‌بندند.

بخش ۱یک درخواست چطور به Production می‌رسد؟

وقتی کاربری در مرورگر خود https://shop.example.com/orders را باز می‌کند، یک زنجیره‌ی دقیق و چندلایه اجرا می‌شود. هر لایه یک مسئولیت دارد و همین تفکیک مسئولیت است که یک سیستم را قابل نگهداری، امن، مقیاس‌پذیر و قابل اشکال‌زدایی می‌کند. اگر این لایه‌ها را قاطی کنیم — مثلاً بک‌اند را مستقیم روی پورت ۳۰۰۰ در معرض اینترنت بگذاریم — همه‌ی این ویژگی‌ها را از دست می‌دهیم.

هدف این مسیر یادگیری در پایان این مجموعه می‌توانید از صفر یک سرور Linux را آماده کنید، یک Reverse Proxy با TLS بالا بیاورید، چند Backend را با Load Balancing و Health Check پشت آن بچینید، دیتابیس و Redis را ایزوله نگه دارید، برای Logging و Monitoring برنامه داشته باشید و با Zero-Downtime Deployment نسخه‌ی جدید را بدون قطعی منتشر کنید.

منتشرشده — همین حالا بخوانید

۰۱ Web Server چیست؟ چرخه‌ی Request/Response، Static و Dynamic، MIME، Header، Compression و مرز Web Server با Reverse Proxy. ۰۲ Web Server vs Application Server مقایسه‌ی دقیق مسئولیت‌ها: از فایل ثابت و TLS تا Business Logic و Runtime. ۰۳ Reverse Proxy چرا لایه‌ی میانی؟ TLS Termination، Routing، Caching و پنهان‌کردن زیرساخت. ۰۵ NGINX Architecture، nginx.conf، server/location/upstream، Reverse Proxy، Load Balancing، Caching و Rate Limiting. ۰۶ Apache HTTP Server Virtual Host، mod_proxy، mod_ssl، mod_rewrite و مقایسه با NGINX. ۰۷ Apache Tomcat Catalina، Coyote، Jasper، Connector، Thread Pool، WAR و استقرار Production. ۰۸ Apache TomEE Tomcat + Jakarta EE: CDI، EJB، JPA، JAX-RS، JMS، JNDI و Transaction. ۱۳ NGINX + Tomcat TLS Termination، Forwarded Headers، Timeout، Buffering و Connection Pool. ۳۲ Production Backend Architecture معماری نهایی و کامل: از اینترنت تا Cache/Queue، با Zero-Downtime. ۱۹ Complete Production Architecture معماری نهایی و کامل: از اینترنت تا Cache/Queue، با توضیح هر لایه.

      بخش ۶شبیه‌سازی خرابی و Failover

      یک سیستم Production خوب، «بدون خرابی» نیست؛ «در برابر خرابی تاب‌آور» است. روی دکمه‌های زیر بزنید و ببینید معماری چطور با از دست دادن یک گره رفتار می‌کند.

      NGINX ↓ Backend 1 Backend 2 Backend 3 ↓ PostgreSQL

      وضعیت: همه‌ی گره‌ها سالم هستند. Load Balancer ترافیک را بین سه Backend پخش می‌کند.

      سناریوواکنش معماریمفهوم کلیدی
      Backend 1 از دست می‌رودHealth Check آن را از چرخه حذف می‌کند؛ ترافیک بین Backend 2 و 3 پخش می‌شود.Health Check · Failover · Horizontal Scaling
      PostgreSQL از دست می‌رودConnection Timeout، خطای ۵۰۳، Retry با Backoff و در نهایت Circuit Breaker.Fault Tolerance · Graceful Degradation
      NGINX از دست می‌رودDNS Failover یا Floating IP به نسخه‌ی دوم؛ نیازمند Redundancy در لایه‌ی ورودی.High Availability
      Redis از دست می‌رودCache Miss و فشار به دیتابیس؛ برنامه باید Cache را «اختیاری» ببیند.Graceful Degradation

      بخش ۷چک‌لیست استقرار Production

      این چک‌لیست را قبل از هر Go-live مرور کنید. هر مورد که تیک نمی‌خورد، یک ریسک واقعی در Production است.

      • Domain configured
      • DNS configured (A / AAAA / CNAME)
      • Firewall configured — فقط پورت‌های لازم
      • SSH hardened — کلید به‌جای رمز
      • TLS configured
      • Certificate معتبر و در حال تمدید خودکار
      • Reverse Proxy configured
      • Backend deployed
      • Health Check configured
      • Logging configured
      • Monitoring configured
      • Backup configured و تست بازیابی انجام شده
      • Secrets protected (خارج از کد)
      • Database protected — بدون دسترسی عمومی
      • Redis protected — بدون دسترسی عمومی
      • Rate Limiting configured
      • Error handling tested
      • Load testing performed
      • Rollback strategy available
      • Zero-downtime strategy available

      بخش ۸واژه‌نامه (Glossary)

      هر واژه‌ی کلیدی این مجموعه، با تعریف، دلیل اهمیت و یک مثال واقعی. این واژه‌نامه در طول همه‌ی مقالات مرجع مشترک است.

      Web Server
      سروری که درخواست‌های HTTP را می‌پذیرد و پاسخ می‌دهد؛ مسئول فایل‌های ثابت، TLS و پایه‌ی Routing است. مثال: NGINX.
      Application Server
      محیط اجرای منطق برنامه (Business Logic) با Runtime و چرخه‌ی حیات مشخص. مثال: Apache Tomcat.
      Reverse Proxy
      واسطه‌ای که به‌جای کلاینت، از سمت سرور درخواست‌ها را می‌پذیرد و به Backend می‌فرستد. چرا مهم است: TLS Termination و پنهان‌کردن زیرساخت.
      Forward Proxy
      واسطه‌ای که به‌جای کلاینت به اینترنت وصل می‌شود. مثال: پروکسی سازمانی.
      Load Balancer
      توزیع‌کننده‌ی ترافیک بین چند Instance. مثال: HAProxy، upstream در NGINX.
      API Gateway
      لایه‌ی ورودی برای APIها با Authentication، Rate Limiting و Routing پیشرفته. مثال: Kong، Spring Cloud Gateway.
      Health Check
      آزمون دوره‌ای سلامت یک گره تا ترافیک فقط به گره‌های سالم برود. مثال: GET /health.
      Failover
      جابه‌جایی خودکار ترافیک از گره‌ی خراب به گره‌ی سالم.
      High Availability
      طراحی‌ای که با حذف یک جزء، سرویس از دست نرود. مثال: دو NGINX با Floating IP.
      Fault Tolerance
      تحمل خطا و ادامه‌ی کار با کیفیت پایین‌تر به‌جای ازکارافتادن کامل.
      Horizontal Scaling
      افزودن Instance بیشتر (Scale Out) به‌جای بزرگ‌ترکردن یک سرور.
      Vertical Scaling
      افزودن CPU/RAM به همان سرور (Scale Up). سقف دارد و معمولاً گران‌تر است.
      Stateless
      Instance که وضعیت کاربر را در خود نگه نمی‌دارد؛ پیش‌نیاز Scaling افقی.
      Sticky Session
      چسبیدن یک کاربر به یک Backend مشخص. راه‌حل ساده اما مانع توزیع متوازن.
      Connection Pool
      مجموعه‌ای از Connectionهای آماده‌ی دیتابیس برای حذف هزینه‌ی ساخت مکرر اتصال.
      Thread Pool
      مجموعه‌ی Thread آماده در Application Server برای پردازش درخواست‌ها. مثال: maxThreads در Tomcat.
      Buffer / Buffering
      نگه‌داشتن موقت داده پیش از ارسال یا پردازش. مثال: proxy_buffering.
      TLS Termination
      رمزگشایی HTTPS در لبه و ارسال ترافیک رمزگشایی‌شده به Backend داخلی.
      Caching
      نگه‌داشتن نتیجه‌ی پرهزینه برای پاسخ سریع‌تر. مثال: پاسخ در Redis.
      Latency
      زمان لازم برای یک رفت‌وبرگشت. چرا مهم است: تجربه‌ی کاربر را مستقیم تغییر می‌دهد.
      Throughput
      تعداد درخواست در واحد زمان که سیستم پردازش می‌کند.
      Observability
      توانایی فهم وضعیت داخلی سیستم از بیرون با Logs، Metrics و Traces.
