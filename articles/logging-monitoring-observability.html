Logging، Monitoring و Observability؛ دیدن آنچه در سیستم می‌گذرد

سیستمی که نمی‌بینید، نمی‌توانید درستش کنید. Observability سه ستون دارد: Logs برای «چه اتفاقی افتاد»، Metrics برای «چقدر و چقدر سریع»، و Traces برای «کجا کند شد». این مقاله این سه را به‌هم می‌بافد.

بخش ۱مقدمه

همه‌چیز تا وقتی سرویس سالم است خوب به‌نظر می‌رسد. مشکل از جایی شروع می‌شود که کاربر می‌گوید «کند شده» یا «خطا می‌دهد». Observability یعنی بتوانید از بیرون، وضعیت درونی سیستم را بفهمید و سریع به سراغ علت بروید.

در این مقاله تفاوت Logs، Metrics و Traces، لاگ ساختاریافته، Prometheus/Grafana، هشداردهی و SLO.
Prerequisites بهینه‌سازی کارایی سرور و عیب‌یابی سرور.

بخش ۲سه ستون Observability

ستونچه سؤالی را پاسخ می‌دهدابزار نمونه
Logsچه رخدادی اتفاق افتاد؟Loki، ELK، CloudWatch
Metricsچقدر/چند وقت/چند درصد؟Prometheus، Grafana
Tracesدرخواست کجا کند شد؟Jaeger، Tempo، OpenTelemetry
ارتباط سه‌گانه بهترین زمان عیب‌یابی وقتی است که هر لاگ یک trace_id داشته باشد و بتوانید از یک Spike روی نمودار به Trace و از آن به لاگ مربوطه پرش کنید.

بخش ۳معماری و جریان داده

بخش ۴Logging ساختاریافته

{
  "timestamp": "2026-10-05T10:15:23.442Z",
  "level": "ERROR",
  "service": "orders-api",
  "trace_id": "9f3c1a7b2e8d",

اصلدلیل
ساختاریافته (JSON)قابل جست‌وجو و فیلتر خودکار
trace_idاتصال لاگ به Trace
سطح‌بندی (Levels)کاهش نویز در محیط Production
بدون داده‌ی حساسرمز و توکن هرگز در لاگ ثبت نشود
حجم لاگ لاگ سطح DEBUG در Production می‌تواند هم هزینه‌ی ذخیره و هم Noise زیاد بسازد؛ فقط در موارد لازم فعالش کنید.

بخش ۵Metrics و Alerting

# prometheus.yml
scrape_configs:
  - job_name: "app"
    metrics_path: /actuator/prometheus
    static_configs:
      - targets: ["app1:8080", "app2:8080"]

  - job_name: "nginx"
    static_configs:
      - targets: ["nginx:9113"]     # nginx-prometheus-exporter
# هشدار نمونه روی نرخ خطای بالا
groups:
  - name: api
    rules:
      - alert: HighErrorRate
        expr: rate(http_requests_total{status=~"5.."}[5m]) > 0.05
        for: 5m
        labels: { severity: critical }
        annotations:
          summary: "نرخ خطای ۵xx بالای ۵٪ در ۵ دقیقه"
هشدار معنادار هشدار باید روی علائم کاربر (نرخ خطا، تأخیر بالا) باشد، نه روی هر نوسان منابع. هشدارهای بیش‌ازحد، سریع بی‌اثر می‌شوند.

بخش ۶Tracing و SLI/SLO

مفهومتعریف
SLIشاخصی که می‌سنجیم (مثلاً نرخ موفقیت)
SLOهدف مورد توافق (مثلاً ۹۹.۹٪ موفقیت)
Error Budgetسقف خطای مجاز در بازه‌ی زمانی
Traceمسیر یک درخواست از چند سرویس با زمان هر گام
// OpenTelemetry — ایجاد Span ساده
const { trace } = require("@opentelemetry/api");
const tracer = trace.getTracer("orders");

async function createOrder(req) {
  const span = tracer.startSpan("createOrder");
  try {
    await db.save(req.body);
    span.setAttribute("order.id", req.body.id);
  } finally {
    span.end();
  }
}
Expected Behavior هر درخواست یک Trace می‌سازد؛ با دیدن یک Spike در Grafana، می‌توانید دقیقاً بفهمید کدام گام کند بوده و کدام سرویس مسئول است.

بخش ۷جمع‌بندی

AdvantagesDisadvantages
عیب‌یابی سریع و دقیقهزینه‌ی ذخیره و زیرساخت پایش
هشدار پیش از بروز فاجعهنیاز به انضباط در لاگ‌نویسی
تصمیم‌گیری مبتنی بر دادهمدیریت حجم زیاد داده
When to Useهر سرویس Production؛ از روز اول لاگ ساختاریافته و متریک پایه را بگذارید.
When NOT to Useهیچ‌وقت لازم نیست همه‌چیز را کامل از روز اول بسازید؛ با Logs + Metrics پایه شروع کنید و Traces را در صورت نیاز Microservice اضافه کنید.

Observability یعنی توانایی پاسخ به سؤال‌های ناشناخته‌ی آینده. با سه ستون Logs، Metrics و Traces و با هشدارهای معنادار، تیم شما سریع‌تر و با اطمینان بیشتری عمل می‌کند.
