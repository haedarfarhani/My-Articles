امنیت سرور؛ سخت‌سازی، فایروال و دفاع لایه‌ای

امنیت یک محصول نیست؛ یک فرآیند لایه‌ای است. از سخت‌سازی SSH و فایروال تا Rate Limiting، Security Headers و مدیریت Secrets — هر لایه بخشی از بار دفاع را برمی‌دارد. این مقاله نقشه‌ی این دفاع را می‌سازد.

بخش ۱مقدمه

هر سرویس متصل به اینترنت هدف تلاش‌های خودکار و دستی است. امنیت یعنی کاهش سطح حمله (Attack Surface) و افزودن لایه‌های دفاعی، طوری که شکست یک لایه به نفوذ کامل منجر نشود. این مقاله یک راهنمای عملی و لایه‌ای است.

در این مقاله سخت‌سازی SSH، فایروال، fail2ban، Rate Limiting، Security Headers و مدیریت Secrets.
Prerequisites TLS و HTTPS و استقرار Production.

بخش ۳سخت‌سازی سرور و SSH

# /etc/ssh/sshd_config
PermitRootLogin no
PasswordAuthentication no
PubkeyAuthentication yes
MaxAuthTries 3
AllowUsers deploy

# غیرفعال‌سازی سرویس‌های غیرضروری
sudo systemctl disable --now telnet.socket
# به‌روزرسانی امنیتی منظم
sudo apt update && sudo apt upgrade -y
sudo unattended-upgrade --dry-run

# بررسی دسترسی‌های غیرعادی
find / -perm -4000 -type f 2>/dev/null     # فایل‌های SUID
sudo ss -tulpn                             # سرویس‌های در حال گوش‌دادن
کم‌ترین دسترسی هر سرویس باید با کاربر اختصاصی و کم‌دسترسی اجرا شود. هرگز برنامه‌ها را با کاربر root اجرا نکنید.

بخش ۴فایروال و Rate Limiting

# UFW — فقط پورت‌های لازم
sudo ufw default deny incoming
sudo ufw allow 22/tcp
sudo ufw allow 80,443/tcp
sudo ufw enable

# fail2ban برای SSH
sudo apt install fail2ban -y
# /etc/fail2ban/jail.local
# [sshd]
# enabled = true
# maxretry = 3
# bantime = 3600
# Rate Limiting در NGINX
limit_req_zone $binary_remote_addr zone=api:10m rate=10r/s;
limit_conn_zone $binary_remote_addr zone=conn:10m;

server {
    location /api/ {
        limit_req  zone=api burst=20 nodelay;
        limit_conn conn 20;
        limit_req_status 429;
        proxy_pass http://app;
    }
}
Expected Behavior درخواست‌های بیش از نرخ مجاز با کد 429 رد می‌شوند و اتصال‌های همزمان هر IP محدود می‌ماند؛ جلوی بسیاری از حملات ساده گرفته می‌شود.
پشت پروکسی اگر NGINX پشت CDN است، برای Rate Limit باید IP واقعی را از X-Forwarded-For با real_ip_module بخوانید؛ وگرنه همه‌ی ترافیک از یک IP دیده می‌شود.

بخش ۵Headers و مدیریت Secrets

add_header Strict-Transport-Security "max-age=63072000; includeSubDomains" always;
add_header X-Content-Type-Options    "nosniff" always;
add_header X-Frame-Options           "SAMEORIGIN" always;
add_header Referrer-Policy           "strict-origin-when-cross-origin" always;
add_header Content-Security-Policy   "default-src 'self'" always;
server_tokens off;    # پنهان‌کردن نسخه‌ی NGINX
اصلاقدام
Secretsدر Secret Manager یا Environment، نه در Git
Rotationچرخش منظم کلیدها و رمزها
Loggingهرگز رمز و توکن در لاگ ثبت نشود
Dependenciesاسکن آسیب‌پذیری و به‌روزرسانی منظم
Least Privilegeدسترسی دیتابیس و فایل محدود
CSP را با احتیاط Content-Security-Policy بسیار قدرتمند است اما پیکربندی نادرست آن صفحه را از کار می‌اندازد. با Content-Security-Policy-Report-Only شروع کنید.
