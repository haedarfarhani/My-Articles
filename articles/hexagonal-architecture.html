Hexagonal Architecture؛ Ports و Adapters در عمل

معماری شش‌ضلعی می‌گوید: هسته‌ی برنامه را پشت Portها پنهان کن و هر چیز بیرونی (DB، وب، صف پیام) را با Adapter وصل کن. در این راهنما درایور/درایو، پیاده‌سازی کامل Java 21، مقایسه با Clean و Onion، تست با JUnit 5 و ۲۰ سؤال مصاحبه را بررسی می‌کنیم.

بخش ۱مقدمه: وقتی درگاه‌ها زیاد می‌شوند

یک سرویس رزرو بلیت را تصور کنید که فقط یک ورودی REST دارد. شش ماه بعد باید به GraphQL، یک CLI برای ادمین، صف پیام برای پرداخت و وب‌هوک پاسخ دهد؛ و ذخیره‌سازی هم از PostgreSQL به MongoDB تغییر کرده. در معماری معمولی، این تغییرات یعنی دست‌زدن به هسته‌ی برنامه: 

بدون مرز — همه‌چیز به همه‌چیز وصل:

@RestController ──→ BookingService ──→ JpaRepository
      │                  │
      └── DTOهای وب       └── SQL و JPA در هسته‌ی منطق نشت کرده

افزودن CLI/ صف پیام = کپی دوباره‌ی منطق یا تغییر هسته
  • وابستگی به پروتکل: منطق رزرو می‌داند HTTP چیست.
  • تست دشوار: برای تست رزرو باید سرور وب بالا بیاید.
  • ورودی دوم گران: افزودن CLI یعنی بازنویسی یا کپی سناریو.
  • تعویض DB پرریسک: JPA در سراسر کد پراکنده است.
ریشه‌ی مشکل هسته‌ی برنامه با جزئیات محیط (وب، DB، صف) گره خورده است. Hexagonal Architecture با یک ایده آمد: هسته را پشت درگاه (Port) پنهان کن؛ هرچه بیرون است با مبدل (Adapter) وصل شود.

بخش ۲تاریخچه و دلیل ایجاد

Hexagonal Architecture (معماری شش‌ضلعی) را Alistair Cockburn در سال ۲۰۰۵ معرفی کرد؛ او خودش آن را ابتدا «Ports and Adapters» نامید. انگیزه، دیدن همان الگوی تکراری در پروژه‌های متعدد بود: هسته‌ی منطق با ابزارهای محیط قاطی شده و تست‌ها کند شده‌اند.

بسترچه شد؟
۲۰۰۵ — مقاله‌ی اصلی Cockburnالگوی Ports & Adapters با شکل شش‌ضلعی برای تفکیک درایور/درایو معرفی شد
۲۰۰۸ — Onion (Palermo)ایده‌ی مشابه را با حلقه‌های متحدالمرکز بازنویسی کرد
۲۰۱۲ — Clean (Martin)چهار لایه و Dependency Rule را تثبیت کرد
دهه‌ی ۲۰۱۰ — موج Microservicesسرویس‌های با چند ورودی/خروجی، Hexagonal را به انتخاب پیش‌فرض بسیاری تبدیل کرد
چرا شش‌ضلعی؟ Cockburn گفت شکل فقط «یک جای نقاشی» است — هر ضلع یک درگاه را نشان می‌دهد؛ مهم تعداد ضلع‌ها نیست، مهم مرز بین هسته و محیط است.

بخش ۳Hexagonal Architecture چیست؟ (تعریف دقیق)

تعریف رسمی Hexagonal Architecture روشی است که در آن برنامه به یک هسته‌ی کاربردی (Application Core) با درگاه‌ها (Ports) — یعنی interfaceهای مورد نیاز هسته — و مبدل‌ها (Adapters) — یعنی پیاده‌سازی‌های متصل به محیط — تقسیم می‌شود؛ به‌طوری که هسته هیچ وابستگی به محیط ندارد و با هر وب/CLI/DB قابل اجراست.
✅ هست…❌ نیست…
یک مرز بین هسته و محیط با interface صریحیک Framework یا پکیج
الگوی Ports & Adapters در مقیاس کل سیستمیک Design Pattern محلی مثل Adapter کلاسیک GoF
ترجمه‌ی عملیِ DIP + Adapter Patternقانونِ «حتماً ۶ ضلع داشته باشید»
همه‌پوشش برای چند ورودی/خروجی هم‌زمانمعادل دقیق Clean یا Onion (همپوشانی دارند اما یکی نیستند)

دو نوع Port:

  • Driving Port (درایور/ورودی): برنامه را راه‌اندازی می‌کند — مثل REST Controller، CLI، صف پیام ورودی.
  • Driven Port (درایو/خروجی): برنامه به بیرون نیاز دارد — مثل Repository، سرویس ایمیل، درگاه پرداخت.

بخش ۴مشکل قبل از استفاده

// همه‌چیز در یک کلاس — هسته و محیط قاطی
@RestController
public class BookingController {

    private final JdbcTemplate db = new JdbcTemplate("jdbc:...");

    @PostMapping("/bookings")
    public Map<String, Object> book(@RequestBody BookingDto dto) {
        // قانون تجاری: سقف رزرو روزانه ۵ بلیت
        int count = db.queryForObject(
                "SELECT COUNT(*) FROM bookings WHERE day = ?", Integer.class, dto.day());
        if (count >= 5) return Map.of("error", "limit reached");

        db.update("INSERT INTO bookings(...) VALUES(...)", dto.seat());
        return Map.of("ok", true);
    }
}
  • قانون تجاری داخل Controller: افزودن CLI یعنی کپی همان if.
  • SQL و HTTP در یک جا: تست بدون DB و سرور ممکن نیست.
  • تعویض پیام‌رسان: تغییر JdbcTemplate، کل کنترلر را می‌لرزاند.
در Hexagonal:

[REST Adapter] → [BookSeatPort] → هسته (قانون سقف روزانه) → [InventoryPort]
[CLI Adapter]  ↗                      ↑
                                      [JPA Adapter] → DB

قانون یک‌بار نوشته می‌شود؛ هر ورودی همان را صدا می‌زند.

بخش ۵ایده اصلی: Ports و Adapters

قاعده‌ی مرکزی هسته، درگاه‌ها را تعریف می‌کند (interface) و Adapterها آن‌ها را پیاده‌سازی می‌کنند. جهت وابستگی: Adapter ← Port ← هسته. هرگز برعکس.

سه پیامد این قاعده:

  • افزودن ورودی جدید فقط یک Adapter جدید است؛ هسته دست‌نخورده می‌ماند.
  • تعویض خروجی (DB، صف، ایمیل) فقط پیاده‌سازی جدید پشت همان Port.
  • تست هسته بدون هیچ Adapterی ممکن است — Port را با Fake پر می‌کنید.
نکته‌ی ظریف درایورها هسته را صدا می‌زنند (فراخوانی)، اما وابستگی کامپایلی همیشه به سمت داخل است؛ چون Adapter به interface موجود در هسته وابسته است. این تقارن، ستون فقرات Hexagonal است.

بخش ۹مثال عملی کامل: سرویس رزرو

دامنه و قواعد:

Domain
├── Booking    (رزرو: صندلی، روز، وضعیت)
├── Seat       (صندلی: شماره، ردیف)
└── Rules
    ├── هر صندلی فقط یک‌بار در هر روز رزرو می‌شود
    ├── سقف رزرو روزانه هر کاربر: ۵ بلیت
    └── رزرو فقط تا ۲۴ ساعت قبل از پرواز مجاز است
Workflow (BookSeat):
1. POST /bookings → BookingController (Driving Adapter)
2. ترجمه به BookSeatCommand → BookSeatPort
3. BookSeatUseCase قوانین را روی Booking اعمال می‌کند
4. BookingRepository (Driven Port) ذخیره می‌کند
5. NotificationPort ایمیل تأیید می‌فرستد
6. BookingResult به Controller و پاسخ برمی‌گردد
نکته‌ی طراحی همان سه قانون بالا در هسته‌اند → تستشان میلی‌ثانیه‌ای طول می‌کشد؛ ایمیل و DB پشت Port جداگانه‌اند → در تست با Fake جایگزین می‌شوند.

بخش ۱۰پیاده‌سازی کد با Java 21

هسته: Entity و قوانین

import java.time.LocalDateTime;

public final class Booking {
    private static final int DAILY_LIMIT = 5;

    private final String id;
    private final String seat;
    private final LocalDateTime flightAt;
    private final BookingStatus status;

    public Booking(String id, String seat, LocalDateTime flightAt, BookingStatus status) {
        this.id = id;
        this.seat = seat;
        this.flightAt = flightAt;
        this.status = status;
    }

    public static Booking create(String id, String seat, LocalDateTime flightAt) {
        if (flightAt.isBefore(LocalDateTime.now().plusHours(24)))
            throw new TooLateToBook(flightAt);
        return new Booking(id, seat, flightAt, BookingStatus.CONFIRMED);
    }

    public boolean isForSeat(String otherSeat) { return seat.equals(otherSeat); }
    public String seat() { return seat; }
    public static int dailyLimit() { return DAILY_LIMIT; }
    public String id() { return id; }
    public BookingStatus status() { return status; }
}

درگاه‌ها: Portهای ورودی و خروجی

// Driving Port — ورودی به هسته
public interface BookSeatPort {
    BookingResult book(BookSeatCommand command);
}

// Driven Portها — خروجی‌های مورد نیاز هسته
public interface BookingRepository {
    void save(Booking booking);
    long countByUserOnDay(String userId, LocalDate day);
    boolean existsSeatOnDay(String seat, LocalDate day);
}

public interface NotificationPort {
    void sendBookingConfirmed(String email, String bookingId);
}

Use Case (هسته)

public final class BookSeatUseCase implements BookSeatPort {

    private final BookingRepository bookings;
    private final NotificationPort notifications;
    private final IdGenerator ids;

    public BookSeatUseCase(BookingRepository bookings,
                           NotificationPort notifications,
                           IdGenerator ids) {
        this.bookings = bookings;
        this.notifications = notifications;
        this.ids = ids;
    }

    @Override
    public BookingResult book(BookSeatCommand cmd) {
        // Act — اعمال قوانین هسته
        if (bookings.existsSeatOnDay(cmd.seat(), cmd.day()))
            throw new SeatAlreadyBooked(cmd.seat());

        if (bookings.countByUserOnDay(cmd.userId(), cmd.day()) >= Booking.dailyLimit())
            throw new DailyLimitReached(cmd.userId());

        Booking booking = Booking.create(ids.nextId(), cmd.seat(), cmd.flightAt());
        bookings.save(booking);
        notifications.sendBookingConfirmed(cmd.email(), booking.id());

        return new BookingResult(booking.id(), booking.seat(), booking.status());
    }
}

Adapterها (محیط)

// Driving Adapter — REST
@RestController
@RequestMapping("/api/bookings")
public final class BookingController {
    private final BookSeatPort bookSeat;

    public BookingController(BookSeatPort bookSeat) { this.bookSeat = bookSeat; }

    @PostMapping
    public ResponseEntity<BookingResponse> create(@RequestBody BookingRequest req) {
        BookingResult result = bookSeat.book(BookingRequestMapper.toCommand(req));
        return ResponseEntity.ok(BookingResponse.from(result));
    }
}

// Driven Adapter — JPA
public final class JpaBookingAdapter implements BookingRepository {
    private final BookingJpaDao dao;

    public JpaBookingAdapter(BookingJpaDao dao) { this.dao = dao; }

    @Override
    public void save(Booking booking) { dao.save(BookingJpaEntity.from(booking)); }

    @Override
    public long countByUserOnDay(String userId, LocalDate day) {
        return dao.countByUserAndDay(userId, day);
    }

    @Override
    public boolean existsSeatOnDay(String seat, LocalDate day) {
        return dao.existsBySeatAndDay(seat, day);
    }
}

تحلیل: هسته فقط interface می‌شناسد؛ Controller و JPA Adapter هر دو به هسته وابسته‌اند؛ افزودن CLI فقط یک کلاس جدید می‌خواهد که BookSeatPort را صدا بزند — صفر تغییر در هسته.

واقع‌بین باشید این‌ها هزینه‌های معقول‌اند؛ سؤال درست این است: «آیا تعداد ورودی/خروجی‌ها و نرخ تغییر پروژه به اندازه‌ای هست که این هزینه برگردد؟» — در CRUD ساده، نه.

بخش ۱۴چه زمانی استفاده کنیم؟

  • چند ورودی/خروجی هم‌زمان — REST + CLI + صف + وب‌هوک با یک هسته
  • تعویض زیرساخت محتمل است — DB، صف پیام یا Provider ایمیل در برنامه‌ی تغییر است
  • تست خودکار اولویت دارد — هسته‌ی بدون I/O، تست سریع و پوشش بالا
  • پروژه بلندمدت و تیم بزرگ — مرزهای روشن، تداخل کاری را کم می‌کند
  • مهاجرت تدریجی سیستم قدیمی — الگوی Strangler پشت همان درگاه‌ها
  • سرویس‌های یکپارچه‌ی قدیمی — جداسازی هسته از ابزارهای قدیمی
نشانه‌ی طلایی اگر در جلسه‌ی طراحی گفتید «این سیستم باید هم API بدهد، هم صف بخواند، هم از چند DB پشتیبانی کند»، دقیقاً حالتی است که Hexagonal می‌درخشد.

تفاوت کلیدی:

  • Hex vs Clean: Hex بر interfaceهای محیط (Port) تأکید دارد؛ Clean بر ساختار لایه‌ها و قاعده‌ی وابستگی. هر دو جهت وابستگی را به داخل می‌کشانند.
  • Hex vs Onion: Onion حلقه‌ها را بر اساس نوع مسئولیت می‌چیند؛ Hex هسته را از محیط با یک مرز جدا می‌کند.
  • Hex vs Layered: Layered جهت وابستگی را آزاد می‌گذارد؛ Hex با interfaceها آن را وارونه می‌کند.
مرتبط در همین سایت مقایسه‌ی عمیق در مقاله‌ی Clean Architecture از همین سری آمده است.

بخش ۱۷ارتباط با SOLID

  • SRP: هر Adapter یک پروتکل را می‌داند؛ هر Use Case یک سناریو را.
  • OCP: افزودن ورودی/خروجی جدید = کلاس جدید، بدون تغییر هسته.
  • LSP: Adapterهای جایگزین باید قرارداد Port را حفظ کنند (مثلاً خطای ذخیره استثنا بدهد).
  • ISP: Portهای کوچک و متمرکز: BookSeatPort بهتر از BookingPort غول.
  • DIP: جان این معماری — هسته interface می‌سازد، Adapter پیاده‌سازی می‌کند.
// ✓ DIP در عمل — هسته به abstraction وابسته است
public final class BookSeatUseCase implements BookSeatPort {
    private final BookingRepository bookings;   // Driven Port — interface
    private final NotificationPort notifications;
    // ...
}

import static org.junit.jupiter.api.Assertions.*;
import java.time.LocalDateTime;
import org.junit.jupiter.api.DisplayName;
import org.junit.jupiter.api.Test;

class BookSeatUseCaseTest {

    @Test
    @DisplayName("رزرو تکراری همان صندلی باید خطا بدهد")
    void shouldRejectDuplicateSeat() {
        // Arrange
        FakeBookingRepository repo = new FakeBookingRepository();
        repo.reserveSeat("12A", LocalDateTime.now().plusDays(3));
        BookSeatUseCase useCase = new BookSeatUseCase(
                repo, new FakeNotificationPort(), new UuidIdGenerator());

        // Act & Assert
        assertThrows(SeatAlreadyBooked.class,
                () -> useCase.book(commandFor("12A")));
    }

    @Test
    @DisplayName("رزرو موفق، ایمیل تأیید می‌فرستد")
    void shouldNotifyOnSuccess() {
        // Arrange
        FakeNotificationPort mail = new FakeNotificationPort();
        BookSeatUseCase useCase = new BookSeatUseCase(
                new FakeBookingRepository(), mail, new UuidIdGenerator());

        // Act
        BookingResult result = useCase.book(commandFor("7C"));

        // Assert
        assertEquals(BookingStatus.CONFIRMED, result.status());
        assertTrue(mail.contains(result.id()));
    }
}

    @Override

}

بخش ۲۱مثال در پروژه واقعی

۱) بک‌اند (Java + Spring Boot)

یک هسته بین API و Worker زمان‌بندی‌شده مشترک است؛ قانون سقف روزانه دوباره نوشته نمی‌شود.

بخش ۲۲Performance

نه — Hexagonal Architecture به‌خودی‌خود Runtime را سریع‌تر نمی‌کند؛ آنچه بهتر می‌شود، کیفیت و سرعت تحویل است:

بعدتأثیر
سرعت تست و پوشش✅ بهبود چشمگیر (هسته بدون I/O)
نرخ تغییر و تحویل✅ بهبود (افزودن درگاه ارزان)
مقیاس‌پذیری سازمانی✅ بهبود
توان عبور / تأخیر⬜ بی‌تأثیر؛ هزینه‌ی یک فراخوانی interface ناچیز است
مصرف حافظه⬜ بی‌تأثیر عملی (تعداد شیءها کمی بیشتر)

تنها هزینه‌ی واقعی، ترجمه‌ی داده بین Adapter و هسته است؛ در مسیرهای بسیار داغ می‌توان Mapper را بهینه کرد یا از کپی غیرضروری جلوگیری نمود — بدون شکستن مرز.

کی نگران شویم؟ در پردازش هزاران پیام در ثانیه، اول پروفایل کنید؛ بهینه‌سازی باید محلی و داخل Adapter باشد، نه باز کردن هسته.

بخش ۲۳۲۰ سؤال مصاحبه شغلی

سطح Junior

سؤال ۱ — Hexagonal Architecture چیست؟ معماری‌ای است که برنامه را به هسته‌ی کاربردی، درگاه‌ها (interface) و مبدل‌ها (پیاده‌سازی متصل به محیط) تقسیم می‌کند؛ هسته به محیط وابسته نیست و هر وب/CLI/DB پشت همان درگاه قابل اتصال است.
سؤال ۲ — Port و Adapter یعنی چه؟ Port قراردادی است که هسته تعریف می‌کند (interface)؛ Adapter پیاده‌سازی آن قرارداد با جزئیات محیط است (JPA، REST، SMTP).
سؤال ۳ — Driving و Driven فرقشان؟ Driving (درایور) ورودی‌هایی‌ست که برنامه را راه می‌اندازد (Controller، CLI)؛ Driven (درایو) خروجی‌هایی‌ست که برنامه به آن نیاز دارد (Repository، ایمیل، پرداخت).
سؤال ۴ — چرا شکل شش‌ضلعی؟ صرفاً یک ترسیم بصری برای مرز هسته/محیط است؛ تعداد ضلع‌ها دلخواه و مهم نیست — قاعده، مرز است نه هندسه.
سؤال ۵ — اگر ورودی دوم (CLI) اضافه شود چه می‌شود؟ فقط یک Adapter جدید که همان Driving Port را صدا بزند؛ هیچ خطی از هسته تغییر نمی‌کند (OCP).
سؤال ۶ — اگر Database عوض شود؟ فقط پیاده‌سازی Driven Port (مثلاً JpaBookingAdapter) عوض می‌شود؛ Use Case و Entity دست‌نخورده می‌مانند.
سؤال ۷ — جهت وابستگی کجاست؟ Adapter ← Port ← هسته. یعنی Adapter به interface هسته وابسته است، نه برعکس؛ هرگز Adapter به Adapter وصل نمی‌شود.
سؤال ۸ — تست قوانین رزرو چطور است؟ مستقیماً روی Entity/Use Case با Fake Port — بدون DB و بدون سرور، در میلی‌ثانیه.

سطح Mid

سؤال ۹ — تفاوت با Clean Architecture؟ Clean چهار لایه با Dependency Rule را توصیف می‌کند و بر Use Case تأکید دارد؛ Hex بر interfaceهای محیط (Portها) و تفکیک درایور/درایو تأکید می‌کند. هر دو جهت وابستگی را به داخل می‌کشند.
سؤال ۱۰ — تفاوت با Onion؟ Onion حلقه‌های متحدالمرکز بر اساس نوع مسئولیت می‌چیند و مرکزش Domain است؛ Hex مرز هسته/محیط را با Port/Adapter مشخص می‌کند. در عمل اغلب ترکیبی‌اند.
سؤال ۱۱ — Adapter کلاسیک GoF با اینجا یکی است؟ نه. آنجا الگویی برای سازگاری دو شیء است؛ اینجا نام یک معماری کل است که کل محیط را پشت interface پنهان می‌کند — الهام گرفته اما متفاوت.
سؤال ۱۲ — کجا Composition Root است؟ تنها جایی که Adapterها به Portها وصل می‌شوند (config). در اپ Java معمولاً یک @Configuration یا main.
سؤال ۱۳ — اگر Use Case منطق تجاری پیدا نکرد و Adapter منطق گرفت؟ نشانه‌ی نشت مرز است: قانون باید به Entity/Use Case منتقل و Adapter به ترجمه محدود شود.
سؤال ۱۴ — چند Port لازم است؟ به نیاز واقعی؛ هر سناریوی ورودی یک Driving Port و هر خروجی ضروری یک Driven Port. Port زیاد یعنی پراکندگی، Port کم یعنی چسبندگی زیاد.
سؤال ۱۵ — DTO در کدام سمت است؟ در Adapter. DTO پروتکل وب/CLI را می‌شناسد و قبل از رسیدن به هسته به Command داخلی ترجمه می‌شود.

سطح Senior

سؤال ۱۶ — سازش‌های واقعی؟ فایل و Interface بیشتر، زمان اولیه‌ی بیشتر و ریسک مرز اشتباه — در برابر تست سریع، افزودن درگاه ارزان و تعویض زیرساخت امن. درستی تصمیم به تعداد درگاه‌ها و نرخ تغییر بستگی دارد.
سؤال ۱۷ — مهاجرت از سیستم قدیمی چطور انجام می‌شود؟ الگوی Strangler: قابلیتی را انتخاب کنید، پشت همان Port بیاورید، پیاده‌سازی قدیمی را به‌تدریج با Adapter جدید جایگزین کنید؛ بدون پوشش تست، مهاجرت آبشاری شکست می‌خورد.
سؤال ۱۸ — چطور مرز را تضمین می‌کنید؟ جداسازی پکیج/ماژول (وابستگی خلاف جهت = خطای کامپایل)، تست معماری (ArchUnit) در CI و بازبینی import در Review.
سؤال ۱۹ — به مدیر چطور توجیه می‌کنید؟ با عدد: «الان افزودن کانال فروش ۳ روز کار دارد؛ با درگاه‌ها، یک روز و بدون دست‌زدن به هسته.» — این را به ریسک کسب‌وکار ترجمه کنید.
سؤال ۲۰ — سنجه‌ی موفقیت؟ زمان تغییر، نرخ باگ پس از تغییر، زمان تست‌ها و هزینه‌ی آموزش نیروی تازه؛ اگر بعد از مهاجرت بهتر نشود، معماری فقط شکل گرفته است.

بخش ۲۴پرسش‌های متداول (FAQ)

۱. مترادف‌های این معماری؟ Ports and Adapters (نام اصلی Cockburn)، Hexagonal، معماری شش‌ضلعی و گاه «Core and Adapters».
۲. حتماً باید ۶ ضلع داشت؟ خیر — شکل نقاشی است؛ ۲ ورودی + ۲ خروجی یعنی ۴ ضلع عملی. قاعده، مرز هسته/محیط است.
۳. Driving Port همان interface معمولی است؟ بله، با یک قرارداد معنایی: این interface از بیرون فراخوانی می‌شود و نباید جزئیات پروتکل داشته باشد.
۴. برای چه زبانی مناسب است؟ هر زبان شیءگرا با Interface: Java، Kotlin، C#، TypeScript، Python. پیش‌نیاز DI و مرزبندی پکیج است.
۵. تفاوت Port و Repository؟ Repository یک نوع Driven Port است (دسترسی به داده)؛ Driven Portها انواع دیگر هم دارند: Notification، Payment، Clock.
۶. هسته از چه چیزی می‌تواند استفاده کند؟ فقط کتابخانه‌ی استاندارد زبان و کتابخانه‌های خالص دامنه (مثل Date/Time)؛ نه ORM، نه Web Framework.
۷. سیم‌کشی کجاست؟ در Composition Root (config): تنها جایی که Adapterها به Portها وصل می‌شوند — معمولاً با DI فریم‌ورک.
۸. با Microservices رابطه‌اش چیست؟ هر سرویس می‌تواند داخل خودش Hexagonal باشد؛ مرز بین سرویس‌ها مسئله‌ی جدا (DDD Bounded Context) است.
۹. CQRS هم می‌شود؟ بله — جداسازی مسیر خواندن/نوشتن معمولاً با دو مجموعه Port/Adapter مجزا اعمال می‌شود.
۱۰. اگر Port زیاد شود چه؟ نشانه‌ی پراکندگی است؛ Portها را بر اساس سناریوی کاربردی ادغام کنید نه بر اساس تکنیک.
۱۱. تست درایور چگونه است؟ Driving Adapter با ساخت درخواست خام (JSON/CommandLine) تست می‌شود و Port را با Fake جایگزین می‌کنید.
۱۲. معروف‌ترین ابزار تضمین مرز؟ ArchUnit (JVM)، لینتر import، جدا بودن پکیج/ماژول و بررسی CI.
۱۳. تفاوت با MVC چیست؟ MVC الگوی UI است (Model-View-Controller)؛ Hex معماری کل سیستم با مرز هسته/محیط. می‌توانند هم‌زمان باشند.
۱۴. از کجا شروع کنیم؟ SOLID و Adapter/Repository، بعد یک پروژه‌ی کوچک را با دو درگاه ورودی/خروجی پیاده کنید، سپس مقاله‌ی اصلی Cockburn.
۱۵. سریع‌ترین راه اشتباه؟ کپی کردن پوشه‌های core/adapter بدون فهم اینکه «کدام interface از بیرون فراخوانی می‌شود؟» — نتیجه‌اش یک پوشه‌ی بی‌مصرف است.
