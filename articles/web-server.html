بخش ۱مقدمه و آنچه یاد می‌گیرید

«Web Server» را همه‌جا می‌شنویم، اما تعریفش در ذهن بسیاری مبهم است. بعضی آن را با Application Server یکی می‌گیرند، بعضی با Reverse Proxy. این ابهام در Production گران تمام می‌شود: کسی که تفاوت را نمی‌داند، بک‌اند را مستقیم روی پورت عمومی می‌گذارد و بعد از دست‌دادن TLS، Rate Limiting و Caching متعجب می‌شود.

Prerequisites آشنایی مقدماتی با HTTP و مفاهیم Client/Server. اگر می‌خواهید همه‌چیز را در بافت بزرگ‌تر ببینید، ابتدا آکادمی معماری سرور را ببینید.

بخش ۲تعریف دقیق Web Server

تعریف رسمی Web Server نرم‌افزاری است که روی یک سرور اجرا می‌شود، روی یک یا چند Port به HTTP گوش می‌دهد، درخواست را می‌فهمد و پاسخی (فایل، محتوای تولیدشده یا ارجاع به سرور دیگر) برمی‌گرداند. مسئولیت اصلی آن تبدیل درخواست HTTP به پاسخ HTTP است — نه اجرای منطق کسب‌وکار.
✅ هست…❌ نیست…
نقطه‌ی ورود ترافیک HTTP/HTTPSمحل منطق کسب‌وکار و قوانین دامنه
سروکننده‌ی Static Files و تحویل پاسخاجباری برای اجرای JVM یا Runtime برنامه
پشتیبان TLS، Compression و Cachingبه‌معنای دیتابیس یا Cache داخلی
قابل استفاده به‌عنوان Reverse Proxyالزاماً یک محصول مشخص — NGINX، Apache، Caddy، IIS
سوءتفاهم رایج «اگر NGINX دارم، پس Application Server هم دارم.» خیر. NGINX فایل ثابت را عالی سرو می‌کند و می‌تواند ترافیک را Proxy کند، اما خودش برنامه‌ی Java یا Node.js را اجرا نمی‌کند. آن کار وظیفه‌ی Application Server است.

بخش ۳چرا Web Server وجود دارد؟

شاید بپرسید اگر یک برنامه‌ی Backend می‌تواند خودش مستقیم روی پورت گوش بدهد، چرا لایه‌ی جدا لازم است؟ پاسخ در سه دلیل عملی است:

دلیلتوضیح
کارایی در فایل ثابتسروکردن فایل با sendfile() و Cache کرنل بسیار ارزان‌تر از عبور از Runtime برنامه است.
امنیت و ایزولاسیونBackend در شبکه‌ی خصوصی می‌ماند و فقط لبه‌ی ورودی عمومی است؛ سطح حمله کوچک‌تر می‌شود.
قابلیت‌های مشترکTLS، Compression، Rate Limiting، Logging و Caching یک‌بار در لبه پیاده می‌شوند، نه در هر سرویس.
اصل تفکیک مسئولیت هر لایه باید یک کار را خوب انجام دهد. Web Server مسئول «حرف‌زدن HTTP» است؛ Application Server مسئول «اجرای منطق»؛ Reverse Proxy مسئول «ورودی و توزیع». همین جداسازی، ریشه‌ی نگهداری‌پذیری در مقیاس است.

بخش ۴معماری و اجزای داخلی

درون یک Web Server مدرن مثل NGINX سه جزء اصلی می‌بینیم: Master Process که مدیریت می‌کند، چند Worker Process که درخواست‌ها را پردازش می‌کنند، و یک Event Loop غیرمسدودکننده که هزاران Connection را با تعداد کم Thread مدیریت می‌کند.

مدل Process-per-Connection سنتی (که Apache در حالت prefork داشت) به‌ازای هر اتصال یک Process می‌سازد و حافظه‌بر است. مدل Event-driven مدرن با تعداد کم Thread، همان بار را با منابع بسیار کمتر جابه‌جا می‌کند. این تفاوت یکی از مهم‌ترین دلایل محبوبیت NGINX است — هرچند برای Workloadهای خاص، مدل‌های دیگر هم جای خود را دارند.

بخش ۵چرخه‌ی HTTP Request

یک درخواست HTTP یک پیام متنی ساختارمند است. حداقل چیزی که برای فهم آن لازم است، خط درخواست و هدرهاست: 

GET /products/42?ref=home HTTP/1.1
Host: shop.example.com
User-Agent: Mozilla/5.0
Accept: text/html,application/xhtml+xml
Accept-Encoding: gzip, br
Cookie: session=abc123; theme=dark
Connection: keep-alive

(body خالی — در GET معمولاً وجود ندارد)
بخشمعنانکته‌ی Production
MethodGET، POST، PUT، DELETE، …Idempotent بودن GET را در طراحی رعایت کنید
Path + Queryمنبع درخواستی و پارامترهاBase URL را در Reverse Proxy یکسان نگه دارید
Hostدامنه‌ی هدف (Virtual Host)پایه‌ی انتخاب server_name در NGINX
Accept-Encodingفرمت‌های فشرده‌سازی مورد پشتیبانی کلاینتپایه‌ی فعال‌کردن gzip/brotli
Cookieوضعیت نشستحساس؛ بدون Secure/HttpOnly آسیب‌پذیر است
Connectionباز یا بسته نگه‌داشتن اتصالKeep-Alive هزینه‌ی TLS Handshake را حذف می‌کند
مرز اعتماد به Header هدرهایی مثل X-Forwarded-For و X-Real-IP توسط کلاینت هم قابل جعل‌اند. تنها زمانی به آن‌ها اعتماد کنید که فقط Reverse Proxy شما بتواند آن‌ها را بگذارد.

ترتیب مراحل پاسخ مهم است: Web Server ابتدا Status و Header را می‌فرستد و بعد Body را. همین ویژگی باعث می‌شود Streaming ممکن باشد؛ برنامه می‌تواند Header را همین حالا بفرستد و Body را تکه‌تکه تولید کند.

بخش ۸Request Routing و MIME Type

MIME Type به کلاینت می‌گوید محتوا را چطور تفسیر کند. اشتباه در آن باعث می‌شود مرورگر فایل JS را به‌عنوان متن نشان دهد یا CSS را اجرا نکند. 

server {
    listen 80;
    server_name shop.example.com;
    root /var/www/shop;

    # سرو فایل ثابت با هدرهای درست
    location /static/ {
        expires 30d;
        add_header Cache-Control "public, immutable";
        # MIME از فایل mime.types گرفته می‌شود
        include /etc/nginx/mime.types;
    }

    # همه‌ی مسیرهای دیگر به Backend می‌روند
    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
Common Mistake استفاده از types { } خالی یا نبودن mime.types باعث می‌شود Content-Type برای .js بشود text/plain و ماژول‌های ES در مرورگر رد شوند.
پسوندContent-Type
.htmltext/html; charset=utf-8
.js / .mjstext/javascript
.csstext/css
.jsonapplication/json
.woff2font/woff2
.webpimage/webp

بخش ۹Headers، Cookies و Compression

هدرها زبان مشترک Web Server و کلاینت هستند. سه دسته‌ی مهم آن‌ها:

دستهمثالکاربرد
CacheCache-Control، ETag، Last-Modifiedکنترل کش مرورگر و Proxy
SecurityX-Frame-Options، Content-Security-Policyدفع Clickjacking و XSS
ContentContent-Type، Content-Encodingتفسیر و رمزگشایی محتوا
# Compression — مراقب جفت‌شدن با proxy باشید
gzip on;
gzip_types text/plain text/css application/json application/javascript image/svg+xml;
gzip_min_length 1024;

# Cookie امن
# Set-Cookie: session=abc123; Path=/; Secure; HttpOnly; SameSite=Lax
Production Note فشرده‌سازی روی محتوای از پیش فشرده (مانند .jpg یا .mp4) فقط CPU هدر می‌دهد. gzip_types را محدود به متن نگه دارید. برای بارهای سنگین، brotli بهتر است اما نیاز به ماژول و سطح CPU بالاتری دارد.
Cookie و نشست Secure فقط روی HTTPS ارسال می‌شود، HttpOnly دسترسی جاوااسکریپت را می‌بندد و SameSite جلوی CSRF را می‌گیرد. این سه ویژگی، حداقل امنیت یک Cookie نشست است.

بخش ۱۰TLS، Caching و Connection

TLS ترافیک را رمزنگاری می‌کند و سه ویژگی می‌دهد: محرمانگی، یکپارچگی و احراز هویت سرور. در عمل امروز، TLS Termination در لبه انجام می‌شود و ترافیک داخلی به Backend ساده‌تر است.

مفهوممعنااثر
TLS Handshakeتبادل کلید و توافق رمزنگاریهزینه‌ی اولیه؛ با session resumption کم می‌شود
Keep-Aliveباز نگه‌داشتن اتصال برای درخواست بعدیحذف هزینه‌ی Handshake مکرر
Cachingنگه‌داشتن پاسخ در لبهکاهش بار Backend و Latency
Connection Limitسقف اتصال هر کلاینتمحافظت از منابع در برابر سوءاستفاده
# لبه‌ی TLS
server {
    listen 443 ssl http2;
    server_name shop.example.com;

    ssl_certificate     /etc/letsencrypt/live/shop.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/shop.example.com/privkey.pem;
    ssl_protocols       TLSv1.2 TLSv1.3;

    keepalive_timeout 65;

    location / {
        proxy_pass http://127.0.0.1:8080;
    }
}
Common Mistake نوشتن ssl_protocols TLSv1 TLSv1.1. این نسخه‌ها منسوخ و ناامن‌اند؛ همیشه فقط TLSv1.2 و TLSv1.3 را فعال کنید.

بخش ۱۱Web Server در برابر بقیه‌ی لایه‌ها

نقشپرسشی که پاسخ می‌دهدنمونه
Web Serverاین درخواست HTTP چه پاسخی می‌گیرد؟NGINX، Apache، Caddy، IIS
Application Serverمنطق برنامه کجاست و چطور اجرا می‌شود؟Tomcat، TomEE، Kestrel، Node.js
Reverse Proxyترافیک را چطور به سرویس درست برسانم؟NGINX، Caddy، HAProxy

Load Balancerچطور بار را بین نمونه‌ها پخش کنم؟HAProxy، AWS ALB، upstream

بخش ۱۲پیکربندی نمونه

نمونه‌ی NGINX

server {
    listen 80;
    server_name example.com www.example.com;

    # ریدایرکت دائمی به HTTPS
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl http2;
    server_name example.com;

    ssl_certificate     /etc/nginx/ssl/fullchain.pem;
    ssl_certificate_key /etc/nginx/ssl/privkey.pem;

    root /var/www/app;
    index index.html;

    location /assets/ {
        expires 30d;
        add_header Cache-Control "public, immutable";
    }

    location /api/ {
        proxy_pass http://backend;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

نمونه‌ی Apache HTTP Server

<VirtualHost *:80>
    ServerName example.com

    # ریدایرکت به HTTPS
    RewriteEngine On
    RewriteCond %{HTTPS} off
    RewriteRule (.*) https://%{HTTP_HOST}%{REQUEST_URI} [R=301,L]
</VirtualHost>

<VirtualHost *:443>
    ServerName example.com
    SSLEngine on
    SSLCertificateFile      /etc/ssl/fullchain.pem
    SSLCertificateKeyFile   /etc/ssl/privkey.pem

    DocumentRoot /var/www/app
</VirtualHost>
Expected Behavior با این پیکربندی، ترافیک HTTP به HTTPS هدایت می‌شود، فایل‌های /assets/ یک ماه کش می‌شوند و درخواست‌های /api/ به Backend می‌رسند. تست: curl -I https://example.com/assets/app.js باید Cache-Control را نشان دهد.

بخش ۱۳مثال واقعی و Production

یک فروشگاه اینترنتی متوسط را در نظر بگیرید. معماری واقعی آن معمولاً این‌گونه است: 

Internet
   ↓
Firewall (443 فقط)
   ↓
NGINX (TLS + Static + Reverse Proxy)
   ├── /static/*      → دیسک (باتر)
   ├── /api/*         → Backend :8080
   └── /health        → پاسخ مستقیم 200
   ↓
Application (Spring Boot / Node.js)
   ↓
PostgreSQL + Redis
موضوعتصمیم Production
نسخه‌ی TLSفقط TLSv1.2 و TLSv1.3
Staticبا Cache-Control: immutable و نام‌گذاری hash در فایل
APIبدون Cache عمومی، با proxy_read_timeout تنظیم‌شده
LoggingAccess Log با X-Forwarded-For و زمان پاسخ
Backend bind127.0.0.1:8080 — بدون دسترسی عمومی
Production Note هرگز Backend را روی 0.0.0.0 و پورت عمومی نگذارید مگر NGINX روی همان میزبان باشد یا در شبکه‌ی خصوصی با Firewall محافظت شود.

بخش ۱۵مزایا، معایب و چه زمانی استفاده کنیم

AdvantagesDisadvantages
سرو سریع و کم‌هزینه‌ی فایل ثابتاجرای منطق کسب‌وکار را انجام نمی‌دهد
متمرکزکردن TLS، Compression و Securityیک لایه‌ی اضافه که باید پیکربندی و نگه‌داری شود
ایزوله‌کردن Backend در شبکه‌ی خصوصیپیکربندی اشتباه آن می‌تواند منبع خطاهای مبهم (502/504) شود
ابزار غنی Logging و Monitoringبرای مسیرهای ساده، ممکن است Over-engineering باشد
When to Use تقریباً همه‌ی سرویس‌های وب عمومی: هر زمان که فایل ثابت، TLS، Reverse Proxy یا چند Instance داری.
When NOT to Use (کورکورانه) برای یک ابزار داخلی کوچک با یک سرویس، افزودن NGINX بدون نیاز به TLS/Static/Proxy اضافات است. تصمیم را بر اساس محدودیت واقعی بگیرید، نه مد.

بخش ۱۶جمع‌بندی و مقالات مرتبط

Web Server نقطه‌ی ورود ترافیک HTTP است: درخواست را می‌فهمد، پاسخ مناسب را می‌سازد یا به لایه‌ی بعدی می‌رساند و کارهای مشترک (TLS، Compression، Caching، Logging) را یک‌بار و درست انجام می‌دهد. تفاوت آن با Application Server، Reverse Proxy و Load Balancer یک تفاوت مسئولیت است، نه برتری.

گام بعدی Web Server vs Application Server — دقیقاً همین مرز مسئولیت را با مثال و دیاگرام باز می‌کند.
