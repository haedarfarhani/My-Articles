بخش ۱تزریق وابستگی چیست و چه دردی را درمان می‌کند؟

تزریق وابستگی (Dependency Injection) یعنی: کلاس خودش وابستگی‌هایش را نسازد، بلکه کسی دیگر آن‌ها را «تزریق» کند. هدف، شکستن یک زنجیره‌ی ساختِ دستی و پنهان است: 

// ✗ بدون DI: کلاس، دنیای بیرون را می‌سازد — تست‌ناپذیر و شکننده
class OrderRepository {
    private val api = Retrofit.Builder().baseUrl("https://api.x.com/").build()
        .create(OrderApi::class.java)                  // ساخت مستقیم
    private val db = AppDatabase.create(MyApp.context) // وابستگی به singleton پنهان
    private val logger = FileLogger("/sdcard/log.txt") // وابستگی به فایل‌سیستم
}

// ✓ با DI: ورودی‌ها شفاف‌اند؛ کلاس فقط «چه چیزی لازم دارد» را اعلام می‌کند
class OrderRepository(
    private val api: OrderApi,
    private val db: OrderDao,
    private val logger: Logger,
) {
    // حالا تست می‌تواند FakeApi و FakeLogger بدهد
}

۱.۱ سه فایده‌ی عملی

فایدهبدون DIبا DI
تست‌پذیریفراخوانی شبکه واقعی در تستسپردن Fake به همان constructor
چندماژوله‌بودنماژول‌ها همدیگر را می‌شناسندفقط قرارداد (interface) مشترک
تعویض پیاده‌سازیویرایش همه‌ی جاهاتعویض یک تعریف در یک جا
عمیق‌تر: DI ≠ Service Locator هر دو «کنترل معکوس» (IoC) هستند، اما مسیر متفاوتی دارند. Service Locator یک نقشه‌ی سراسری است که کلاس خودش می‌رود و وابستگی را «می‌گیرد» — یعنی وابستگی پنهان می‌ماند. DI واقعی وابستگی را از بیرون «می‌دهد» و امضا (constructor) کلاس همه‌چیز را لو می‌دهد. همین تفاوت، ریشه‌ی تفاوت Hilt و Koin است.

بخش ۲دو رویکرد بنیادین: زمان کامپایل در برابر زمان اجرا

هر دو کتابخانه‌ی Hilt و Koin در اندروید «تزریق وابستگی» ارائه می‌دهند، اما مبنای متفاوتی دارند و همین مبنا، همه‌ی تفاوت‌های بعدی (سرعت، خطا، حجم) را می‌سازد.

ویژگیHilt (مبتنی بر Dagger)Koin
محل ساخت نمودارزمان کامپایل (KSP/Annotation Processor)زمان اجرا (DSL کاتلین)
زبان تعریفAnntation (@Inject، @Module)DSL (single، factory)
خطای تعریف ناقصخطای بیلد — زود و شفافاستثنا در runtime — دیر و گران
هزینه‌ی اجراتقریباً صفر (کد تولیدشده)جستجو در HashMap در هر resolve
هزینه‌ی بیلدبالاتر (پردازش annotation)تقریباً صفر
وابستگی به زیرساخت اندرویدبله (@HiltAndroidApp)خیر (کتابخانه‌ی خالص JVM)
هشدار: Koin «بدون کامپایلر» نیست، فقط «بدون تحلیل نمودار» است Koin با خوانایی عالی و یادگیری آسان، اما هیچ تحلیل ایستایی از نمودار ندارد؛ یعنی «single { Repo(get()) }» ممکن است ماه‌ها سالم بماند و تازه وقتی کسی آن مسیر را باز کند، بترکد. اگر این ریسک را می‌پذیرید، Koin انتخابی عالی است؛ اگر نه، Hilt هزینه‌ی بیلد را جبران می‌کند.

بخش ۳پیاده‌سازی عملی با Hilt

Hilt، Dagger را با قراردادهای ازپیش‌تعیین‌شده برای اندروید می‌پوشاند: شما کمتر annotation می‌نویسید و بیشتر فقط «کجا باید چه چیزی بیاید» را اعلام می‌کنید. 

// ۱) نقطه‌ی شروع: Application
@HiltAndroidApp
class App : Application()

// ۲) تعریف وابستگی‌ها — یک ماژول برای هر لایه/ماژول
@Module
@InstallIn(SingletonComponent::class)          // عمر: کل پروسه
object NetworkModule {

    @Provides
    @Singleton
    fun provideOkHttp(): OkHttpClient =
        OkHttpClient.Builder().callTimeout(15, TimeUnit.SECONDS).build()

    @Provides
    @Singleton
    fun provideRetrofit(client: OkHttpClient): Retrofit =
        Retrofit.Builder().baseUrl("https://api.example.com/")
            .client(client)
            .addConverterFactory(Json.asConverterFactory("application/json".toMediaType()))
            .build()

    @Provides
    fun provideOrderApi(retrofit: Retrofit): OrderApi = retrofit.create(OrderApi::class)
}

// ۳) مصرف‌کننده — فقط @Inject بزنید؛ constructor همه‌چیز را لو می‌دهد
class OrderRepository @Inject constructor(
    private val api: OrderApi,
    private val dao: OrderDao,
)

// ۴) تزریق در اندروید
@HiltViewModel
class OrderViewModel @Inject constructor(
    private val repo: OrderRepository,
) : ViewModel() { /* ... */ }

@AndroidEntryPoint
class OrderActivity : AppCompatActivity() {
    private val vm: OrderViewModel by viewModels()
}

Scopeعمرنمونه‌ی کاربرد
@Singletonکل پروسهRetrofit، Room، Logger

@ActivityScopedعمر یک Activityتنظیمات صفحه‌ی خاص

@FragmentScopedعمر یک Fragmentآداپترهای وابسته به صفحه
// تعریف وابستگی وابسته به عمر: سفارشی‌سازی برای هر مصرف‌کننده
@Module
@InstallIn(ViewModelComponent::class)
object CheckoutModule {

    @Provides
    @ViewModelScoped
    fun provideCalculateDiscount(
        @ApplicationContext context: Context,      // از ماژول سراسری می‌آید
        config: RemoteConfig,                     // تعریف در Singleton
    ): CalculateDiscount = CalculateDiscountImpl(config)
}

بخش ۴پیاده‌سازی عملی با Koin

Koin با یک زبان کاتلین خوانا تعریف می‌شود؛ خبری از annotation و پردازشگر نیست. تعریف‌ها در یک یا چند module می‌نشینند و در startKoin بارگذاری می‌شوند. 

// ۱) تعریف وابستگی‌ها — DSL خالص کاتلین
val networkModule = module {
    single {
        OkHttpClient.Builder().callTimeout(15, TimeUnit.SECONDS).build()
    }
    single {
        Retrofit.Builder().baseUrl("https://api.example.com/")
            .client(get())                        // get() = resolve از همین نمودار
            .addConverterFactory(Json.asConverterFactory("application/json".toMediaType()))
            .build()
    }
    factory { get<Retrofit>().create(OrderApi::class) }
}

val repositoryModule = module {
    single<OrderRepository> { OrderRepository(get(), get()) }
    factory { GetOrdersUseCase(get()) }
}

// ۲) مصرف‌کننده — constructor ساده، بدون annotation
class OrderRepository(
    private val api: OrderApi,
    private val dao: OrderDao,
)

// ۳) راه‌اندازی
class App : Application() {
    override fun onCreate() {
        super.onCreate()
        startKoin {
            androidContext(this@App)
            androidLogger(if (BuildConfig.DEBUG) Level.DEBUG else Level.NONE)
            modules(networkModule, repositoryModule, viewModelModule)
        }
    }
}

// ۴) تزریق در ViewModel و صفحه
class OrderViewModel(
    private val repo: OrderRepository,
) : ViewModel() { /* ... */ }

class OrderActivity : AppCompatActivity() {
    private val vm: OrderViewModel by viewModel()      // کتابخانه‌ی koin-android
}

۴.۱ بسته‌های اکوسیستم Koin

بستهنقشمعادل Hilt

نکته: Koin هم می‌تواند «تقریباً ایستا» باشد با فعال‌سازی koin-annotations می‌توانید Koin را با annotation سمت‌کاربر کار کنید و حتی مدل ایستا را فعال کنید؛ ولی پیش‌فرض همچنان runtime است. اگر مدل ایستا می‌خواهید ولی سبک Koin را دوست دارید، همین گزینه را امتحان کنید — وگرنه Hilt پیش‌فرض مطمئن‌تری برای پروژه‌های بزرگ است.

بخش ۵پروژه‌های چندماژوله (Multi-Module): جایی که بازی جدی می‌شود

در پروژه‌ی تک‌ماژوله، انتخاب DI تقریباً بی‌اهمیت است. در پروژه‌ی چندماژوله، قرارداد بین ماژول‌ها مشخص می‌کند که کدام کتابخانه کمتر دردسر می‌سازد: ماژول feature نباید ماژول دیگر را بشناسد؛ فقط interface آن را. 

// ---- Hilt: ماژول هر feature خودش نصب می‌شود ----
@Module
@InstallIn(ViewModelComponent::class)
object CheckoutBindings {

    @Binds
    @ViewModelScoped
    fun bindOrderRepository(impl: OrderRepositoryImpl): OrderRepository = impl
}

// ---- Koin: هر ماژول یک module؛ ترکیب در :app ----
val checkoutModule = module {
    single<OrderRepository> { OrderRepositoryImpl(get(), get()) }
    viewModel { CheckoutViewModel(get(), get()) }
}

// :app — نقطه‌ی ترکیب
startKoin {
    modules(networkModule, dataModule, checkoutModule, profileModule)
}
عمیق‌تر: جایگزینی در تست چندماژوله در Hilt، با @TestInstallIn(components = [TestComponent::class], replaces = [RealModule::class]) کل ماژول واقعی را در تست عوض می‌کنید. در Koin، با unloadModules/loadModules یا ساخت نمودار مخصوص تست این کار را می‌کنید؛ الگوی Koin ساده‌تر ولی دستی‌تر است.

بخش ۶تزریق به ViewModel و Lifecycle در Compose

رایج‌ترین نقطه‌ی اشتباه، تزریق به ViewModel است: ViewModel باید «پابرجا» باشد، ولی وابستگی‌هایش ممکن است «کوتاه‌عمر» باشند. هر دو کتابخانه برای این یک قرارداد سالم دارند. 

// ---- Hilt: تزریق کامل و اتصال به Navigation-Compose ----
@HiltViewModel
class CheckoutViewModel @Inject constructor(
    private val getCart: GetCartUseCase,
    private val placeOrder: PlaceOrderUseCase,
) : ViewModel()

@Composable
fun CheckoutRoute(nav: NavHostController) {
    val vm: CheckoutViewModel = hiltViewModel()       // مخصوص destination جاری
    val state by vm.state.collectAsStateWithLifecycle()
    // ...
}

// ---- Koin: دو مسیر رایج ----
class CheckoutViewModel(
    private val getCart: GetCartUseCase,
    private val placeOrder: PlaceOrderUseCase,
) : ViewModel()

val checkoutModule = module {
    viewModel { CheckoutViewModel(get(), get()) }     // koin-android
}

@Composable
fun CheckoutRoute(nav: NavHostController) {
    val vm: CheckoutViewModel = koinViewModel()       // koin-compose: به lifecycle گره می‌خورد
    val state by vm.state.collectAsStateWithLifecycle()
    // ...
}

بخش ۷تست‌پذیری و Mocking وابستگی‌ها

کل هدف DI، تست‌پذیری است. بیایید همان سناریوی تستِ Repository را در هر دو کتابخانه ببینیم. 

// ---- تست مشترک: Fake به‌جای وابستگی واقعی ----
class FakeOrderApi : OrderApi {
    var nextResult: Result<List<OrderDto>> = Result.success(emptyList())
    override suspend fun orders(): List<OrderDto> =
        nextResult.getOrThrow()
}

@Test
fun `orders are mapped to domain`() = runTest {
    val fakeApi = FakeOrderApi().apply {
        nextResult = Result.success(listOf(OrderDto(id = 7, total = 100)))
    }
    val repo = OrderRepositoryImpl(fakeApi, InMemoryDao(), TestDispatcher())
    val orders = repo.orders().first()
    assertEquals(7L, orders.first().id)               // بدون شبکه، قطعی و سریع
}

    single<OrderApi> { FakeOrderApi() }

@Test
fun koinTest() = koinTest {           // koin-test
    startKoin { modules(testAppModule) }
    val repo = get<OrderRepository>()
    // ...
}

بخش ۹درخت تصمیم: کدام یک را کی انتخاب کنیم؟

پاسخ کوتاه: «بستگی دارد» — ولی این جمله وقتی مفید است که شرایط «بستگی» را روشن کنیم.

۹.۱ مهاجرت از Koin به Hilt (یا برعکس)

  1. ابتدا همه‌ی وابستگی‌ها را در یک نقطه‌ی واحد (ماژول/مودول) جمع کنید؛ بدون این قدم، مهاجرت دردناک است.
  2. لایه‌ی Domain را خالی از DI نگه دارید (constructor-only)؛ این لایه در هر دو حالت دست‌نخورده می‌ماند.
  3. مرحله‌به‌مرحله مهاجرت کنید: اول Repositoryها، بعد ViewModelها، آخر صفحه‌ها.
  4. هیچ‌وقت هر دو سیستم را هم‌زمان برای «یک کلاس» نگه ندارید — دو منبع حقیقت، دو نوع باگ.

بخش ۱۰جمع‌بندی، چک‌لیست و منابع

هیچ‌کس با «بهترین» انتخاب نمی‌شناخته؛ با «مناسب‌ترین» انتخاب برای شرایطش. Hilt وقتی برنده است که مقیاس، ایمنی نوع و یکپارچگی با اکوسیستم اندروید مهم‌تر از زمان بیلد باشد؛ Koin وقتی برنده است که سرعت تیم، خوانایی و تست سبک JVM در اولویت باشد.

با Koin شروع کرده‌اید و دارید مقیاس می‌گیریدماندن + سفت‌کردن قراردادها؛ مهاجرت فقط با دلیل عددی

۱۰.۱ چک‌لیست نهایی بازبینی

  1. هیچ‌جا new/ساخت مستقیمِ وابستگی سنگین (Retrofit، DB، Logger) درون کلاس‌های domain/data نیست.
  2. هر وابستگی دقیقاً یک تعریف دارد (یک @Provides یا یک single/factory).
  3. Scope وابستگی‌ها با عمر واقعی‌شان جور است (singleton برای بدون‌وضعیت، کوتاه برای باوضعیت).
  4. ViewModelها از مسیر رسمی کتابخانه تزریق می‌شوند (hiltViewModel / koinViewModel).
  5. در تست‌ها، وابستگی‌های شبکه/دیتابیس با Fake عوض شده‌اند و تست بدون اینترنت اجرا می‌شود.
  6. تست «سلامت نمودار» (checkModules یا Hilt test) در CI هست.
  7. در پروژه‌ی چندماژوله، فقط :app ماژول‌های همه‌جا را می‌بیند.
  8. هیچ singleton با وضعیت مشترکِ آشکار (کش لاگین، شمارنده‌ی سراسری) وجود ندارد.
