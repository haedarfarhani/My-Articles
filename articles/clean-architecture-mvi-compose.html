معماری تمیز و الگوی MVI در Jetpack Compose: از تئوری تا پروداکشن

چرا وضعیت UI در Compose باید تک‌منبع حقیقت باشد؟ تفاوت UiState با UiEvent و UiEffect دقیقاً چیست و هر کدام کجا باید مصرف شوند؟ در این مقاله، جریان تک‌جهته داده‌ها (UDF) و الگوی MVI را در لایه‌های Domain، Data و UI با کاتلین مدرن پیاده‌سازی می‌کنیم، دیاگرام جریان State را رسم می‌کنیم و خطاهای رایج Recomposition را یک‌به‌یک رفع می‌کنیم.

بخش ۱چرا MVI؟ محدودیت‌های وضعیت پراکنده در Compose

وقتی اپلیکیشن کوچک است، هر ViewModel با چند StateFlow جداگانه کار می‌کند و همه‌چیز خوب پیش می‌رود. اما با بزرگ‌شدن پروژه، همین سادگی تبدیل به بزرگ‌ترین منبع باگ می‌شود: وضعیت‌های متعدد، ناسازگار و بدون مالک مشخص.

فرض کنید صفحه‌ی سفارش چهار MutableStateFlow دارد: isLoading، error، items و discount. هیچ‌کس تضمین نمی‌دهد که این چهار با هم یک‌دست باشند. لودینگ تمام شده ولی آیا error پاک شده؟ آیا وقتی خطا داریم، آیتم‌ها هنوز داده‌ی کهنه نشان می‌دهند؟ این‌ها دقیقاً همان باگ‌هایی‌ست که کاربر می‌گوید: «صفحه گاهی گیر می‌کند» یا «بعد از چرخش صفحه، پیام خطا دوباره ظاهر شد».

۱.۱ نشانه‌های خرابی وضعیت پراکنده

  • States متعدد و مستقل: هر کدام می‌توانند در ترکیب‌های نامعتبر با هم جمع شوند.
  • رویدادها در همه‌جا: onClick مستقیم Repository را صدا می‌زند؛ باگ اصلاح داده در چند جا کپی می‌شود.
  • Side-effectهای پراکنده: LaunchedEffectهای زیاد، Snackbarهای تکراری و Navigation دوباره‌ای بعد از چرخش صفحه.
  • تست سخت: برای تست باید پنج flow را هم‌زمان جمع‌آوری کنید و ترتیب انتشارها را حدس بزنید.

الگوی MVI (Model–View–Intent) این مشکل را با یک اصل ساده حل می‌کند: کل وضعیت صفحه در یک شیء غیرتغییرپذیر (Immutable) واحد می‌ریزیم، تغییرات فقط از یک دروازه‌ی واحد (reduce) عبور می‌کنند، و خروجی‌های گذرا (Effect) از جریان وضعیت جدا می‌شوند.

عمیق‌تر: MVI یک چارچوب نیست، یک قرارداد است هیچ کتابخانه‌ی «MVI» لازم نیست. MVI فقط می‌گوید: یک UiState واحد، یک UiEvent واحد برای ورودی‌ها، و یک UiEffect واحد برای خروجی‌های گذرا داشته باشید. پیاده‌سازی می‌تواند با StateFlow خام، Orbital، MVIKotlin یا هر چیز دیگری باشد.

بخش ۲UDF: جریان تک‌جهته داده‌ها چیست؟

UDF (Unidirectional Data Flow) یعنی داده فقط در یک جهت حرکت می‌کند: از Model به View می‌رود (State)، و از View به Model برمی‌گردد (Intent/Event). هیچ‌جا داده دوطرفه نیست؛ View هرگز مستقیماً وضعیت را تغییر نمی‌کند، فقط قصد (Intent) خود را اعلام می‌کند.

۲.۱ قواعد سه‌گانه‌ی UDF

  1. تک‌منبع حقیقت: تمام وضعیت صفحه از یک UiState خوانده می‌شود؛ نه از propها، نه از متغیرهای سراسری.
  2. تغییر خالص (Pure): تابع reduce(state, event) → state هیچ اثر جانبی ندارد؛ شبیه‌سازی آن یک خط است.
  3. ایمن در برابر چرخش صفحه: چون UiState در ViewModel زندگی می‌کند، Configuration Change آن را از بین نمی‌برد.
// هسته‌ی MVI در کمتر از ده خط — بدون هیچ کتابخانه‌ی اضافه
data class CounterState(val count: Int = 0, val loading: Boolean = false)

sealed interface CounterIntent {
    data object Increment : CounterIntent
    data object Load : CounterIntent
}

class CounterViewModel : ViewModel() {
    private val _state = MutableStateFlow(CounterState())
    val state: StateFlow<CounterState> = _state.asStateFlow()

    fun onIntent(intent: CounterIntent) {
        _state.update { current -> reduce(current, intent) }   // دروازه‌ی واحد
    }

    private fun reduce(state: CounterState, intent: CounterIntent): CounterState =
        when (intent) {
            CounterIntent.Increment -> state.copy(count = state.count + 1)
            CounterIntent.Load      -> state.copy(loading = true)
        }
}
نکته: update {} در برابر value = استفاده از _state.update { } به‌جای _state.value = ... تضمین می‌کند که اگر دو رویداد هم‌زمان برسند، خواندن–نوشتن روی آخرین مقدار انجام شود (CAS اتمیک) و یک به‌روزرسانی گم نشود.

بخش ۳معماری لایه‌ای: Domain، Data و UI

در معماری تمیز، هر لایه فقط به لایه‌ی داخلی‌تر وابسته است. UI می‌داند که چه چیزی نشان دهد، Data می‌داند داده از کجا می‌آید، و Domain قواعد کسب‌وکار را بدون هیچ وابستگی به اندروید نگه می‌دارد.

بخش ۴تفکیک UiState، UiEvent و UiEffect

پایه‌ی MVI درست‌کردن سه نوع داده‌ی کاملاً متمایز است. اشتباه رایج این است که همه‌چیز را داخل UiState بریزیم — مثلاً showSnackbar: Boolean. نتیجه؟ بعد از چرخش صفحه، Snackbar دوباره نشان داده می‌شود.

۴.۱ تعریف سه نوع داده

// ۱) وضعیت: تنها منبع حقیقت صفحه
data class LoginUiState(
    val email: String = "",
    val password: String = "",
    val submitEnabled: Boolean = false,
    val loading: Boolean = false,
    val error: String? = null,          // خطای پایدار، نه پیام لحظه‌ای
)

// ۲) رویداد: هر کنشی که از View به ViewModel می‌رود
sealed interface LoginUiEvent {
    data class EmailChanged(val value: String) : LoginUiEvent
    data class PasswordChanged(val value: String) : LoginUiEvent
    data object SubmitClicked : LoginUiEvent
}

// ۳) اثر گذرا: چیزی که فقط یک بار باید رخ دهد
sealed interface LoginUiEffect {
    data object ShowWelcome : LoginUiEffect
    data class OpenHome(val userId: Long) : LoginUiEffect
}
آفت شماره ۱: بولین نجات‌بخش! showSuccessDialog = true را در UiState نگذارید. State در Configuration Change بازیابی می‌شود و دیالوگ دوباره ظاهر خواهد شد. علاوه بر این، جمع‌شدن چند بولین (loading، error، dialog) به ترکیب‌های نامعتبر می‌انجامد — دقیقاً همان مشکلی که می‌خواستیم با MVI حل کنیم.

بخش ۵پیاده‌سازی کامل ViewModel مبتنی بر MVI

یک ViewModel MVI سه خروجی دارد: state (جریان وضعیت)، effect (جریان رویدادهای گذرا) و یک نقطه‌ی ورودی واحد به نام onEvent. هیچ تابع عمومی دیگری لازم نیست. 

class CheckoutViewModel(
    private val getCart: GetCartUseCase,
    private val placeOrder: PlaceOrderUseCase,
) : ViewModel() {

    private val _state = MutableStateFlow(CheckoutUiState())
    val state: StateFlow<CheckoutUiState> = _state.asStateFlow()

    // بافر کوچک: اگر کسی Effect را دیر collect کند، آخرین مورد از دست نرود
    private val _effects = MutableSharedFlow<CheckoutUiEffect>(extraBufferCapacity = 4)
    val effects: SharedFlow<CheckoutUiEffect> = _effects.asSharedFlow()

    init {
        viewModelScope.launch {
            getCart().collect { cart ->
                _state.update { it.copy(items = cart.items, total = cart.total) }
            }
        }
    }

    fun onEvent(event: CheckoutUiEvent) {
        when (event) {
            is CheckoutUiEvent.QuantityChanged -> {
                _state.update { it.copy(items = it.items.updateQty(event.id, event.qty)) }
            }
            CheckoutUiEvent.SubmitClicked -> submit()
        }
    }

    private fun submit() {
        val current = _state.value
        if (current.loading) return                       // محافظ در برابر دابل‌کلیک
        viewModelScope.launch {
            _state.update { it.copy(loading = true, error = null) }
            placeOrder(current.toOrderRequest())
                .onSuccess { order ->
                    _effects.emit(CheckoutUiEffect.OrderPlaced(order.id))
                }
                .onFailure { e ->
                    _state.update { it.copy(error = e.message ?: "خطای ناشناخته") }
                }
            _state.update { it.copy(loading = false) }
        }
    }
}

۵.۱ چرا Effect را از State جدا کردیم؟

چون StateFlow همیشه آخرین مقدار را نگه می‌دارد: مشترک تازه‌وارد همان مقدار را می‌بیند. این برای «وضعیت» عالی است، اما برای «ناوبری» فاجعه: کاربر بعد از چرخش صفحه دوباره به صفحه‌ی پرداخت فرستاده می‌شود. SharedFlow با بافر، هر Effect را دقیقاً یک بار به مشترکِ فعال تحویل می‌دهد.

عمیق‌تر: چرا بافر ۴ تایی؟ extraBufferCapacity = 4 به‌همراه BufferOverflow.DROP_OLDEST (پیش‌فرض) تضمین می‌کند که اگر Effect در فاصله‌ی کوتاهِ تعویض Composition پخش شود، emit پرتاب نکند و مهم‌ترین پیام‌ها زنده بمانند. برای سیستم‌های حساس‌تر (پرداخت مالی) می‌توانید از Channel با trySendBlocking استفاده کنید.

بخش ۶مصرف State و Effect در Compose

سمت Compose، قاعده این است: State را با collectAsStateWithLifecycle بخوان، Event را با یک lambda واحد بفرست، و Effect را فقط یک بار جمع‌آوری کن. 

@Composable
fun CheckoutRoute(
    viewModel: CheckoutViewModel = hiltViewModel(),
    onNavigateHome: () -> Unit,
) {
    val state by viewModel.state.collectAsStateWithLifecycle()

    // فقط یک LaunchedEffect برای کل صفحه — نه برای هر دکمه
    LaunchedEffect(viewModel) {
        viewModel.effects.collect { effect ->
            when (effect) {
                is CheckoutUiEffect.OrderPlaced -> onNavigateHome()
            }
        }
    }

    CheckoutScreen(
        state = state,
        onEvent = viewModel::onEvent,      // مرجع تابع: بدون آلفای اضافه
    )
}

@Composable
private fun CheckoutScreen(
    state: CheckoutUiState,
    onEvent: (CheckoutUiEvent) -> Unit,
) {
    Scaffold(
        snackbarHost = { SnackbarHost(hostState = remember { SnackbarHostState() }) },
    ) { padding ->
        Column(Modifier.padding(padding)) {
            CartList(
                items = state.items,
                onQtyChange = { id, qty ->
                    onEvent(CheckoutUiEvent.QuantityChanged(id, qty))
                },
            )
            PrimaryButton(
                enabled = state.submitEnabled && !state.loading,
                onClick = { onEvent(CheckoutUiEvent.SubmitClicked) },
            )
        }
    }
}

بخش ۷Recomposition: خطاهای رایج و مهار آن‌ها

در MVI، چون کل صفحه یک UiState دارد، هر تغییرِ state پتانسیل رندر مجدد کل صفحه را دارد. اگر state شما یک data class بزرگ باشد و Composableها نتوانند تغییر را محدود کنند، بازه‌ی رندر ۱۶ میلی‌ثانیه‌ای می‌شکند و کاربر «لرزش» می‌بیند.

۷.۱ چهار خطای رایج

  1. ساختن آبجکت در هر recomposition: Modifier.padding(...) سفارشی یا لیست فیلترشده داخل بدنه‌ی کامپوننت بدون remember.
  2. انتشار داده‌ی کل‌صفحه: وقتی فقط متن یک آیتم عوض می‌شود، کل LazyColumn از state بزرگ رد می‌شود.
  3. وابستگی نامرئی: خواندن state.loading داخل یک کامپوننت کوچک، آن را به کل state متصل می‌کند.
  4. lambdaهای تازه: عبور از { onEvent(...) } به‌جای مرجع تابع، استقرار یک‌نواخت را می‌شکند.
// ✗ غلط: لیست در هر بار رندر فیلتر می‌شود و کل صفحه می‌لرزد
@Composable
fun CartList(state: CheckoutUiState) {
    val visible = state.items.filter { it.visible }      // آبجکت جدید در هر recomposition
    LazyColumn { items(visible) { ItemRow(it) } }
}

// ✓ درست: محاسبه فقط وقتی تغییر می‌کند، خروجی پایدار، وابستگی محدود
@Composable
fun CartList(state: CheckoutUiState, modifier: Modifier = Modifier) {
    val visible by remember(state.items) {
        derivedStateOf { state.items.filter { it.visible } }
    }
    LazyColumn(modifier) { items(visible, key = { it.id }) { ItemRow(it) } }
}

// ✓ استقرار یک‌نواخت: کامپوننت فقط وقتی مقادیرش عوض شوند رندر می‌شود
@Composable

بخش ۸لایه‌های Domain و Data در عمل

ViewModel بدون UseCase و Repository فقط یک ظرف است. در این بخش، جریان کاملِ یک سفارش را از داده‌ی خام تا UiState دنبال می‌کنیم. 

// ---- Domain: منطق خالص، بدون اندروید ----
data class Cart(val items: List<CartItem>) {
    val total: Long get() = items.sumOf { it.price * it.qty }
}

class GetCartUseCase(private val repo: CartRepository) {
    operator fun invoke(): Flow<Cart> = repo.observeCart()
}

interface CartRepository {
    fun observeCart(): Flow<Cart>
    suspend fun placeOrder(request: OrderRequest): Result<Order>
}

// ---- Data: انتخاب منبع و مپ داده ----
class CartRepositoryImpl(
    private val api: CartApi,
    private val dao: CartDao,
    private val dispatcher: AppDispatcher,
) : CartRepository {

    override fun observeCart(): Flow<Cart> =
        dao.observeItems().map { rows -> Cart(rows.map { it.toDomain() }) }
            .flowOn(dispatcher.io)                 // مپ در IO، collect در Main

    override suspend fun placeOrder(request: OrderRequest): Result<Order> =
        runCatching { api.place(request).toDomain() }
}

بخش ۹تست‌پذیری: تست ViewModel و Effectها با Turbine

بزرگ‌ترین پاداش MVI این است که تست یک صفحه به یک الگوی خطی تبدیل می‌شود: «رویداد بفرست ← وضعیت نهایی را ببین ← Effect را قطعی چک کن». 

class CheckoutViewModelTest {

    @Test
    fun `submit success emits OrderPlaced effect`() = runTest {
        val repo = FakeCartRepository(orderResult = Result.success(Order(42)))
        val vm = CheckoutViewModel(GetCartUseCase(repo), PlaceOrderUseCase(repo))

        val states = mutableListOf<CheckoutUiState>()
        val job = backgroundScope.launch { vm.state.toList(states) }   // جمع‌آوری کل جریان

        vm.onEvent(CheckoutUiEvent.SubmitClicked)

        // Turbine: اثر گذرا را قطعی تست می‌کند
        vm.effects.test {
            assertEquals(CheckoutUiEffect.OrderPlaced(42), awaitItem())
            cancelAndIgnoreRemainingEvents()
        }

        assertTrue(states.none { it.loading && it.error != null })     // ترکیب نامعتبر هرگز
        job.cancel()
    }
}

بخش ۱۱جمع‌بندی، چک‌لیست و منابع

MVI در Compose سه وعده می‌دهد: قابل پیش‌بینی بودن (یک State، یک منبع)، قابل تست بودن (reduce خالص و Effect قطعی) و قابل نگهداری بودن (رویدادهای متمرکز که با افزودن قابلیت، الگو عوض نمی‌شود).

۱۱.۱ چک‌لیست بازبینی صفحه‌ی MVI

  1. دقیقاً یک UiState غیرتغییرپذیر برای صفحه وجود دارد (data class با valها).
  2. همه‌ی ورودی‌ها از طریق یک sealed interface واحد به نام onEvent می‌آیند.
  3. هیچ Boolean نجات‌بخشی برای Snackbar/Dialog/Navigation در State نیست؛ همه در UiEffect‌اند.
  4. تنها نقطه‌ی تغییر State، reduce یا _state.update است.
  5. UI با collectAsStateWithLifecycle و یک LaunchedEffect واحد جمع‌آوری می‌کند.
  6. Lambdaهای ثابت و مرجع تابع (viewModel::onEvent) برای استقرار یک‌نواخت استفاده شده.
  7. لیست‌ها key دارند و محاسبات تکرارشونده با remember/derivedStateOf محافظت شده‌اند.
  8. تست ViewModel با runTest و Turbine، هم State نهایی و هم Effect را قطعی چک می‌کند.
  9. گزارش stability از compose-compiler-metrics بررسی شده و فیلدهای ناپایدار رفع شده‌اند.
