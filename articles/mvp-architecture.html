بخش ۱مقدمه: مشکل تست‌ناپذیری Activity

یک صفحه‌ی ورود در اندروید را در نظر بگیرید. کلاس LoginActivity هم‌زمان: فرم را نمایش می‌دهد، اعتبارسنجی فرم را انجام می‌دهد، درخواست شبکه را می‌فرستد، پاسخ را پردازش می‌کند و به صفحه‌ی بعدی می‌رود. یک کلاس، ۵ مسئولیت.

حالا سؤال: چطور قانون «رمز عبور باید حداقل ۸ کاراکتر باشد» را تست می‌کنید؟ برای اجرای این تست باید یک دستگاه یا شبیه‌ساز بالا بیاید، Activity بسازید، شبکه را قطع کنید و دکمه را بزنید. یک تست ساده، ۹۰ ثانیه زمان می‌برد و بیش از یک بار شکست می‌خورد بدون آنکه مشکلی در کد باشد. 

تست قانون ساده در معماری Activity-centric:

  Android Studio → انتخاب Emulator → صبر تا بوت (۶۰ ثانیه)
      → اجرای اپ → تایپ در EditText
      → کلیک دکمه → بررسی Toast

  ⏱ زمان هر تست: ۹۰ ثانیه
  🐛 نرخ شکست جعلی: بالا (به‌خاطر شبکه و تایمر)
  🧪 پوشش قوانین کسب‌وکار: معمولاً زیر ۴۰٪
ریشه‌ی مشکل منطق کسب‌وکار به سیستم‌عامل گره خورده است. هر جا منطق به Android وابسته شود، تست آن گران می‌شود. MVP منطق را به کلاسی به نام Presenter منتقل می‌کند که هیچ وابستگی‌ای به اندروید ندارد و مثل یک کلاس Java ساده تست می‌شود.

بخش ۲تاریخچه و دلیل ایجاد

MVP مدت‌ها پیش از آنکه پایتخت محبوب باشد، در دنیای GUI و دسکتاپ وجود داشت. نام «Model-View-Presenter» از ترکیب MVC با یک نقش چهارم به‌دست آمد: کنترلر با Presenter جایگزین شد تا جریان داده کاملاً یک‌طرفه شود.

بسترچه اتفاقی افتاد؟
دهه‌ی ۱۹۸۰–۱۹۹۰MVC کلاسیک در Smalltalk؛ مشکل دسترسی مستقیم View به Model
دهه‌ی ۱۹۹۰تولد Visual Basic و Delphi؛ نیاز به جداسازی منطق از فرم
دهه‌ی ۲۰۰۰ — پلتفرم‌های مایکروسافتMVP به‌عنوان الگوی رسمی معرفی شد؛ جریان یک‌طرفه برای تست
۲۰۰۸–۲۰۱۳ — موج اندرویدActivity به‌مرور چاق شد و تیم‌ها به دنبال راه‌حل تست‌پذیری رفتند
۲۰۱۳ — Squareمقاله‌ی کلاسیک Presenter آمد و MVP در جامعه‌ی اندروید فراگیر شد
۲۰۱۷ به بعدMVVM و سپس MVI محبوب شدند، ولی MVP همچنان در پروژه‌های موجود زنده است
دلیل اصلی ایجاد MVP برای حل سه مشکل هم‌زمان ساخته شد: ۱) تست‌پذیری (Presenter یک کلاس ساده است)، ۲) جریان یک‌طرفه (View فقط فرمان می‌دهد و دستور نمایش می‌گیرد)، و ۳) جداسازی واقعی (View هرگز Model را نمی‌بیند).

بخش ۳MVP چیست؟ (تعریف دقیق)

تعریف رسمی MVP یک الگوی معماری است که برنامه را به سه نقش تقسیم می‌کند: Model (داده و منطق کسب‌وکار)، View (نمایش، کاملاً منفعل) و Presenter (واسط بین این دو). در این الگو، View هیچ ارجاعی به Model ندارد و همه‌ی تعامل از مسیر View → Presenter → Model → Presenter → View جریان می‌کند.
نقشمسئولیتنمونه
Modelداده، قوانین کسب‌وکار و ارتباط با دیتابیسUser، AuthRepository
Viewنمایش داده و ارسال رویداد؛ بدون هیچ منطقیLoginContract.View، LoginFragment
Presenterدریافت رویداد، فراخوانی Model، تولید دستور نمایشLoginPresenter
سه اصل کلیدی MVP ۱) View کاملاً منفعل است — فقط متدهای showX() را صدا می‌زند.
۲) Presenter همه‌ی منطق را دارد — جز منطق خالص نمایش.
۳) جریان یک‌طرفه است — View به Model دسترسی ندارد و Presenter تنها منبع حقیقت است.
سوءتفاهم رایج MVP با MVC یک تفاوت کلیدی دارد: در MVC، Model و View می‌توانند مستقیم با هم صحبت کنند. در MVP، این ارتباط قطع می‌شود و همه‌چیز از مسیر Presenter عبور می‌کند. اگر View شما مستقیم Repository را صدا بزند، در عمل MVC دارید، نه MVP.

بخش ۴مشکل قبل از استفاده

public class LoginActivity extends AppCompatActivity {

    private EditText emailInput;
    private Button loginButton;
    private ApiService api;
    private ProgressBar progress;

    @Override
    protected void onCreate(Bundle savedInstanceState) {
        super.onCreate(savedInstanceState);
        setContentView(R.layout.activity_login);

        emailInput = findViewById(R.id.email);
        loginButton = findViewById(R.id.login);
        api = RetrofitFactory.create();
        progress = findViewById(R.id.progress);

        loginButton.setOnClickListener(v -> {
            // ۱) اعتبارسنجی
            String email = emailInput.getText().toString();
            if (!Patterns.EMAIL_ADDRESS.matcher(email).matches()) {
                emailInput.setError("ایمیل نامعتبر");
                return;
            }

            // ۲) منطق کسب‌وکار
            if (email.endsWith("@blocked.com")) {
                Toast.makeText(this, "این ایمیل مسدود است", Toast.LENGTH_SHORT).show();
                return;
            }

            // ۳) ارتباط با شبکه
            progress.setVisibility(View.VISIBLE);
            api.login(email, "123456")
              .enqueue(new Callback<Token>() {
                  @Override
                  public void onResponse(Call<Token> call, Response<Token> r) {
                      // ۴) پردازش پاسخ
                      progress.setVisibility(View.GONE);
                      if (r.isSuccessful()) {
                          startActivity(new Intent(LoginActivity.this, HomeActivity.class));
                      } else {
                          showError(r.body().getMessage());
                      }
                  }
                  @Override
                  public void onFailure(Call<Token> call, Throwable t) {
                      // ۵) مدیریت خطا
                      progress.setVisibility(View.GONE);
                      showError("خطای شبکه");
                  }
              });
        });
    }
}

بخش ۵ایده اصلی: جریان یک‌طرفه

ایده‌ی مرکزی MVP در یک جمله: View فقط می‌پرسد و فقط دستور می‌گیرد؛ هرگز تصمیم نمی‌گیرد. همین یک قاعده، هم تست‌پذیری می‌آورد و هم قابلیت پیش‌بینی. 

قانون طلایی MVP (Unidirectional Data Flow):

  View  → Presenter : «این اتفاق افتاد»      (رویداد، فقط داده خام)
  Presenter → View  : «این کار را بکن»       (دستور، هرگز منطق)

View هرگز:
  ✗ از Presenter می‌پرسد «حالا چه کار کنم؟»  (چون خودش تصمیم می‌گیرد)
  ✗ مستقیم Model را صدا نمی‌زند
  ✗ شرط تصمیم‌گیر (if) ندارد، مگر if مربوط به نمایش
چرا یک‌طرفه بودن مهم است؟ با یک‌طرفه شدن جریان، هر تغییر وضعیت یک نقطه‌ی مشخص برای شروع دارد. یعنی هر باگ را می‌توانید دقیقاً بازتولید کنید: ورودی را بدهید، خروجی را ببینید. این همان چیزی است که در تست‌های واحد Presenter ممکن می‌شود.

بخش ۶ساختار معماری: اجزای MVP

نوع MVPتوضیحنمونه
Passive ViewView کاملاً منفعل؛ Presenter همه‌چیز را می‌داندرایج‌ترین حالت در اندروید
Supervising PresenterPresenter کارهای ساده‌ی نمایش را به View واگذار می‌کندپروژه‌های وب با فرم‌های پیچیده
Presenter + ViewModelترکیب MVP با MVVM؛ Presenter رویدادها می‌گیرد و State منتشر می‌کندالگوی نوسازی‌شده‌ی امروزی
الگوی Contract: کلید استفاده‌ی اصولی راه استاندارد تعریف MVP، ساختن یک Contract برای هر صفحه است: یک Interface برای View و یکی برای Presenter. با این کار، Presenter به هیچ کلاس اندرویدی وابسته نیست و View هم به پیاده‌سازی Presenter وابسته نیست.

بخش ۷جریان داده (Data Flow)

جریان خواندن داده در MVP:

  View.onStart()
      → Presenter.loadProfile()
          → Repository.getProfile()
              → Model → ViewModel (در صورت نیاز)
      → Presenter تبدیل Model به Contract.ViewState
      → View.render(state)

نکته: تبدیل داده به قالب نمایشی، وظیفه‌ی Presenter است نه View.
این باعث می‌شود ViewModel نهایی برای تست، کاملاً قابل پیش‌بینی باشد.
الگوی View State در MVP، Presenter معمولاً به‌جای ده‌ها متد showX()، یک state واحد به View می‌دهد. مثلاً LoginState(isLoading, error, token). این کار باعث می‌شود همه‌ی حالت‌های ممکن صفحه صریح تعریف شوند و باگِ حالت‌های ناقص کم شود.

بخش ۹مثال عملی کامل: صفحه‌ی ورود

  • کاربر ایمیل و رمز را وارد می‌کند.
  • اعتبارسنجی شکلی (ایمیل معتبر، رمز حداقل ۸ کاراکتر) باید سمت کلاینت هم باشد.
  • قانون کسب‌وکار («ایمیل مسدود شده») فقط در Presenter است.
  • درخواست شبکه از Repository انجام و نتیجه به Presenter برمی‌گردد.
  • Presenter به View فرمان می‌دهد: نمایش loader، نمایش خطا یا رفتن به صفحه‌ی خانه.
تفکیک مسئولیت در یک سناریو:

  Form     : "ایمیل خالی است"        → View (اعتبارسنجی اولیه)
  Password : "رمز اشتباه"            → Presenter (پاسخ سرور)
  Domain   : "ایمیل مسدود شده"        → Presenter (قانون کسب‌وکار)
  Network  : "اتصال برقرار نشد"       → Repository (تبدیل خطا)

Presenter تنها جایی است که قوانین سطح‌بالا را می‌داند.
اگر همین صفحه را دوباره در تب دیگری پیاده کنید، فقط View را کپی می‌کنید —
Presenter و Repository را دوباره استفاده می‌کنید.
مرز معیار MVP اگر LoginFragment خودش قبل از ارسال، ایمیل مسدود را بررسی کند، MVP شکسته است. هر تصمیمی که به «سیاست کسب‌وکار» مربوط است، باید در Presenter باشد، حتی اگر هزینه‌ی شبکه داشته باشد.

بخش ۱۰پیاده‌سازی کد با Java 21

قرارداد (Contract)

package com.example.login.ui.login;

/**
 * قرارداد صفحه‌ی ورود. تنها جایی که View و Presenter همدیگر را می‌شناسند.
 */
public interface LoginContract {

    interface View {
        /** نمایش وضعیت در حال بارگذاری */
        void showProgress(boolean visible);

        /** نمایش خطا؛ field می‌گوید خطا کنار کدام ورودی است */
        void showError(String message, ErrorField field);

        /** رفتن به صفحه‌ی خانه */
        void navigateToHome(String token);

        /** پر کردن ورودی‌ها از پاسخ سرور */
        void prefill(String email);
    }

    interface Presenter {
        void attach(View view);
        void detach();
        void onLoginClicked(String email, String password);
        void onEmailChanged(String email);
    }

    enum ErrorField { NONE, EMAIL, PASSWORD }
}

Presenter

package com.example.login.ui.login;

import com.example.login.domain.repository.AuthRepository;
import com.example.login.domain.usecase.ValidateCredentialsUseCase;

/**
 * تمام منطق صفحه‌ی ورود اینجاست. این کلاس هیچ وابستگی‌ای به Android ندارد،
 * بنابراین با یک تست واحد کامل قابل بررسی است.
 */
public final class LoginPresenterImpl implements LoginContract.Presenter {

    private static final int MIN_PASSWORD_LENGTH = 8;
    private static final java.util.Set<String> BLOCKED_DOMAINS =
            java.util.Set.of("blocked.com", "spam.local");

    private final AuthRepository authRepository;
    private final ValidateCredentialsUseCase validate;

    private LoginContract.View view;
    private String lastEmail = "";

    public LoginPresenterImpl(AuthRepository authRepository,
                              ValidateCredentialsUseCase validate) {
        this.authRepository = authRepository;
        this.validate = validate;
    }

    @Override
    public void attach(LoginContract.View view) {
        this.view = view;
    }

    @Override
    public void detach() {
        this.view = null;
    }

    @Override
    public void onEmailChanged(String email) {
        this.lastEmail = email;
    }

    @Override
    public void onLoginClicked(String email, String password) {
        this.lastEmail = email;

        // ۱) اعتبارسنجی شکلی
        if (!email.contains("@")) {
            showError("ایمیل نامعتبر است", ErrorField.EMAIL);
            return;
        }
        if (password.length() < MIN_PASSWORD_LENGTH) {
            showError("رمز عبور باید حداقل " + MIN_PASSWORD_LENGTH
                    + " کاراکتر باشد", ErrorField.PASSWORD);
            return;
        }

        // ۲) قانون کسب‌وکار (نه فرم، نه سرور لزوماً)
        if (isBlocked(email)) {
            showError("این ایمیل مسدود شده است", ErrorField.EMAIL);
            return;
        }

        // ۳) عملیات آسسته
        view.showProgress(true);
        authRepository.login(email, password, new AuthCallback() {
            @Override
            public void onSuccess(String token) {
                view.showProgress(false);
                view.navigateToHome(token);
            }

            @Override
            public void onFailure(AuthError error) {
                view.showProgress(false);
                switch (error.kind()) {
                    case INVALID_CREDENTIALS ->
                            showError("ایمیل یا رمز اشتباه است",
                                    ErrorField.PASSWORD);
                    case RATE_LIMITED ->
                            showError("تلاش بیش از حد؛ کمی بعد امتحان کنید",
                                    ErrorField.NONE);
                    case NETWORK ->
                            showError("اتصال برقرار نشد", ErrorField.NONE);
                }
            }
        });
    }

    /** قانون: دامنه‌ی ایمیل در لیست مسدودهاست؟ */
    private boolean isBlocked(String email) {
        String domain = email.substring(email.indexOf('@') + 1).toLowerCase();
        return BLOCKED_DOMAINS.contains(domain);
    }

    private void showError(String message, ErrorField field) {
        if (view != null) {
            view.showError(message, field);
        }
    }
}

View (بخش اندرویدی)

package com.example.login.ui.login;

/**
 * پیاده‌سازی اندرویدی. هیچ منطقی اینجا نیست:
 * فقط رویداد را به Presenter می‌دهد و دستور Presenter را اجرا می‌کند.
 */
public final class LoginFragment extends Fragment implements LoginContract.View {

    private LoginContract.Presenter presenter;
    private EditText emailInput;
    private EditText passwordInput;
    private ProgressBar progressBar;

    @Override
    public void onViewCreated(View view, Bundle savedInstanceState) {
        emailInput = view.findViewById(R.id.email);
        passwordInput = view.findViewById(R.id.password);
        progressBar = view.findViewById(R.id.progress);

        presenter = new LoginPresenterImpl(
                ((App) requireActivity().getApplication()).authRepository(),
                new ValidateCredentialsUseCase());

        presenter.attach(this);

        // رویداد به Presenter داده می‌شود؛ تصمیم‌گیری اینجا نیست
        view.findViewById(R.id.loginButton).setOnClickListener(v ->
                presenter.onLoginClicked(
                        emailInput.getText().toString().trim(),
                        passwordInput.getText().toString()));

        TextWatcher watcher = new SimpleTextWatcher() {
            @Override
            public void afterTextChanged(Editable s) {
                presenter.onEmailChanged(s.toString());
            }
        };
        emailInput.addTextChangedListener(watcher);
    }

    @Override
    public void onDestroyView() {
        // جدا کردن Presenter از View، نشتی حافظه را از بین می‌برد
        presenter.detach();
        presenter = null;
        super.onDestroyView();
    }

    @Override
    public void showProgress(boolean visible) {
        progressBar.setVisibility(visible ? View.VISIBLE : View.GONE);
        loginButton.setEnabled(!visible);
    }

    @Override
    public void showError(String message, ErrorField field) {
        switch (field) {
            case EMAIL -> emailInput.setError(message);
            case PASSWORD -> passwordInput.setError(message);
            case NONE -> Toast.makeText(requireContext(), message, Toast.LENGTH_LONG).show();
        }
    }

    @Override
    public void navigateToHome(String token) {
        NavHostFragment.findNavController(this)
                .navigate(R.id.action_login_to_home);
    }

    @Override
    public void prefill(String email) {
        emailInput.setText(email);
    }
}
نکته‌ی کلیدی کلاس LoginPresenterImpl حتی یک import از اندروید ندارد. یعنی می‌توان آن را در یک JVM معمولی و در کمتر از ۵۰ میلی‌ثانیه تست کرد — درست برخلاف نسخه‌ی قبلی که ۹۰ ثانیه تست می‌شد.

مفهوممعادل در اندروید

ContractInterfaceهای View و Presenter
چرخه‌ی عمرattach در onViewCreated و detach در onDestroyView
چرخه‌ی عمر MVP در اندروید — نکته‌ی امنیتی مهم:

  onCreate()       → Presenter را بساز (یا از DI بگیر)
  onViewCreated()  → presenter.attach(this)
                     ← متد امن برای تعامل با View
  onDestroyView()  → presenter.detach()
                     ← آزادسازی مرجع View از Presenter
  onDestroy()      → presenter = null

چرا این ترتیب مهم است؟ چون View (Fragment) می‌تواند در چرخه‌ی عمر نابود شود
در حالی که Presenter باید باقی بماند تا داده را نگه دارد.
چرا MVP کنار می‌رفت؟ دو دلیل: ۱) حجم کد زیاد — برای هر صفحه یک Contract و یک Presenter، و ۲) ناتوانی در مدیریت وضعیت پیچیده — چون ViewModel خودش وضعیت را نگه می‌دارد و با چرخه‌ی حیات بهتر هماهنگ می‌شود. MVVM دقیقاً برای حل همین دو مورد آمد.

بخش ۲۱مثال در پروژه واقعی

۱) اپلیکیشن فروشگاهی اندروید با MVP

در پروژه‌های فروشگاهی اندرویدی که با XML و Fragment نوشته می‌شوند، MVP هنوز الگوی رایجی است. هر صفحه یک Presenter دارد: LoginPresenter، ProductListPresenter و CartPresenter. قوانین مربوط به تخفیف و موجودی در Presenter صفحه‌ی سبد قرار می‌گیرد و با تست واحد پوشش داده می‌شود. تیم‌ها معمولاً از Dagger برای تزریق Presenter استفاده می‌کنند تا از داخلی شدن آن جلوگیری کنند.

۲) اپ پیام‌رسان با Presenter و RxJava

در اپ‌های چت، جریان پیام‌ها پیوسته و ناهمگام است. الگوی رایج این است که Presenter به‌جای Callback، یک Observable از وضعیت صفحه برگرداند و View با subscribe آن را مصرف کند. یعنی داده به‌صورت یک جریان پیوسته از Presenter به View می‌رود — همان ایده‌ی یک‌طرفه، اما با ابزار واکنشی.

۳) اپ مالی و بانکی

در اپ‌های بانکی، قوانین مالی (مبلغ انتقال، سقف روزانه، احراز هویت دومرحله‌ای) نباید در Fragment نوشته شوند. با MVP، هر قانون در Presenter مربوط به همان صفحه قرار می‌گیرد و با یک Fake می‌توان همه‌ی حالت‌های خطا را تست کرد. این برای حسابرسی و اثبات صحت قواعد، الزامی است.

۴) اپ سلامت و نوبت‌دهی

در اپ کلینیک، صفحه‌ی رزرو نوبت چند مرحله دارد: انتخاب پزشک، انتخاب بازه‌ی زمانی، تأیید و پرداخت. هر مرحله یک Presenter مستقل دارد که وضعیت مرحله‌ی قبلی را نگه می‌دارد. این ساختار از باگ‌های «مرحله‌ی بعدی با وضعیت ناقص» جلوگیری می‌کند.

۵) پروژه‌های شرکتی با UI دسکتاپ یا Vue

MVP در فرانت‌اند وب هم کاربرد دارد، هرچند کمتر از اندروید. در Vue و React، الگوی مشابهی به نام «Presentational Component» و «Container Component» وجود دارد که از نظر مفهومی نزدیک به MVP است: یک بخش فقط داده را می‌گیرد و نمایش می‌دهد، و بخش دیگری منطق را در اختیار دارد.

    view.setHint(formatHint(e))   // هر کاراکتر، یک به‌روزرسانی UI

بهتر — debounce با Rx:

  onEmailChanged()
    .debounce(300, MILLISECONDS)
    .distinctUntilChanged()
    .subscribe(email -> view.setHint(formatHint(email)))

همچنین: وضعیت سنگین (لیست ۱۰۰۰ ردیفی) را در Presenter نگه ندارید؛
فقط داده‌ی صفحه‌ی فعلی را در ViewState قرار دهید.
معیار تصمیم‌گیری اگر عملکرد رابط کاربری اولویت اصلی است، یا از صفحات بازی با حلقه‌ی رندر ۶۰ فریم استفاده می‌کنید، MVP با callback می‌تواند سربار ایجاد کند. در آن شرایط MVI با StateFlow یا Compose کارا‌تر است.

بخش ۲۳۲۰ سؤال مصاحبه

سطح Junior
سؤال ۱ — MVP چیست؟ الگوی معماری با سه نقش: Model (داده و منطق)، View (نمایش منفعل) و Presenter (واسط که منطق را از View جدا می‌کند و جریان داده را یک‌طرفه می‌سازد).
سؤال ۲ — تفاوت اصلی MVP و MVC چیست؟ در MVC، View می‌تواند مستقیم Model را صدا بزند؛ در MVP، این ارتباط قطع می‌شود و همه‌چیز از مسیر Presenter عبور می‌کند، بنابراین جریان داده یک‌طرفه است.
سؤال ۳ — تفاوت Presenter با Controller چیست؟ Presenter یک کلاس Java خالص است و از Android بی‌خبر است، اما Controller معمولاً به Activity یا Servlet وابسته است. به همین دلیل Presenter به‌راحتی قابل تست است.
سؤال ۴ — Presenter دقیقاً چه کاری انجام می‌دهد؟ رویداد کاربر را از View دریافت می‌کند، Model را صدا می‌زند، منطق را اعمال می‌کند و با فراخوانی متدهای Contract به View دستور نمایش می‌دهد.
سؤال ۵ — Contract در MVP چیست؟ یک Interface که متدهای View و Presenter را تعریف می‌کند تا این دو بدون وابستگی مستقیم به کلاس‌های همدیگر کار کنند.
سؤال ۶ — آیا View می‌تواند منطق داشته باشد؟ فقط منطق مربوط به نمایش، مثل این‌که آیا ProgressBar در حالت Loading باشد. قوانین کسب‌وکار باید در Presenter باشند.
سؤال ۷ — جریان یک‌طرفه یعنی چه؟ یعنی داده فقط از View به Presenter و از Presenter به View حرکت می‌کند و View هرگز از Model داده نمی‌گیرد. هیچ حلقه‌ی بازگشتی بین این دو وجود ندارد.
سؤال ۸ — MVP برای چه نوع اپ‌هایی ساخته شد؟ برای اندروید طراحی نشده بود؛ ریشه‌ی آن در GUI دسکتاپ است. اما در اندروید به‌دلیل مشکل تست‌ناپذیری Activity و نیاز به جداسازی منطق، فراگیر شد.
سؤال ۹ — Presenter را کجا بسازیم؟ بهتر است با DI (مانند Dagger یا Hilt) در یک کلاس جدا ساخته شود تا در چرخش صفحه از دست نرود. از ساخت دستی در Activity پرهیز کنید.
سؤال ۱۰ — چرا attach و detach مهم هستند؟ چون View (Fragment) می‌تواند در چرخه‌ی حیات نابود شود در حالی که Presenter باید باقی بماند. جدا کردن مرجع View از Presenter، هم نشتی حافظه را حذف می‌کند و هم از فراخوانی متد روی View نابود جلوگیری می‌کند.
سطح Mid
سؤال ۱۱ — Passive View و Supervising Presenter چه تفاوتی دارند؟ در Passive View، تمام حتی جزئی‌ترین تصمیم نمایشی هم در Presenter است و View کاملاً منفعل است. در Supervising، Presenter کارهای تکراری نمایش را به View واگذار می‌کند.
سؤال ۱۲ — چطور از نوشتن تست Presenter در ساخت نهایی جلوگیری کنیم؟ Presenter باید در ماژول یا پکیج دامنه باشد (نه در پکیج UI اندروید). ساخت پروژه‌ی کلاس دامنه نباید به SDK اندروید نیاز داشته باشد تا در JVM معمولی تست شود.
سؤال ۱۳ — آیا MVP برای پروژه‌های کوچک مناسب است؟ اگر پروژه کوچک باشد و تیم تست ننویسد، خیر. هزینه‌ی ساخت Presenter و Contract تنها زمانی توجیه می‌شود که ارزش تست‌پذیری آن را دریافت کنید.
سؤال ۱۴ — MVP در Compose چه معنایی دارد؟ معنای اصلی آن (جداسازی منطق از نمایش و تست‌پذیری) باقی می‌ماند، اما در Compose معمولاً به جای Presenter از ViewModel استفاده می‌شود (MVVM) یا از الگوی MVI. این‌ها عملاً همان مفهوم MVP را با ابزارهای بهتر پیاده می‌کنند.
سؤال ۱۵ — چگونه state را در MVP مدیریت کنیم؟ Presenter می‌تواند یک مدل ViewState نگه دارد و در هر تغییر، آن را به View بدهد. این کار باعث می‌شود همه‌ی حالت‌های ممکن صفحه صریح و قابل تست باشند.
سؤال ۱۶ — تفاوت MVP با MVVM در نگه‌داری وضعیت چیست؟ در MVP، Presenter وضعیت را در حافظه نگه می‌دارد و با چرخه‌ی حیات View هماهنگ نیست (مگر با تکنیک‌های دستی). در MVVM، ViewModel به‌طور خودکار با چرخه‌ی حیات هماهنگ می‌شود و LiveData/Flow ارائه می‌دهد.
سؤال ۱۷ — آیا می‌توان از Presenter در پروژه‌ی غیراندرویدی استفاده کرد؟ بله، این یک الگوی مستقل از پلتفرم است. در Vue و React هم الگوهای مشابه آن وجود دارد (Container و Presentational Component).
سطح Senior
سؤال ۱۸ — مهم‌ترین محدودیت نظری MVP چیست؟ جریان یک‌طرفه در MVP، جریان «فقط رو به جلو» است و رویدادهای یک‌بارمصرف را به‌صورت دسته‌ای (در حد یک پیام کوتاه) به View تحویل می‌دهد. برای اپ‌هایی با رویدادهای هم‌زمان و جریان‌های پیوسته، مدل push بهتری (MVI یا MVVM) وجود دارد.
سؤال ۱۹ — چگونه MVP را در یک پروژه‌ی بزرگ‌تر مدیریت می‌کنید؟ با تقسیم‌بندی بر اساس فیچر به جای لایه. هر فیچر یک پوشه دارد که شامل View، Presenter و Contract خودش است. این کار از تداخل تیم‌ها در فایل‌های مشترک جلوگیری می‌کند.
سؤال ۲۰ — MVP در معماری لایه‌ای (Layered) کجا قرار می‌گیرد؟ Presenter در لایه‌ی Presentation قرار می‌گیرد (جایی که View هم هست)، و Model در لایه‌ی Domain و Data. MVP و لایه‌بندی مکمل یکدیگرند: لایه‌بندی ساختار کلی را می‌دهد و MVP الگوی داخل لایه‌ی Presentation را مشخص می‌کند.

بخش ۲۴پرسش‌های متداول (FAQ)

پرسش‌های پرتکرار
۱) تفاوت MVP و MVC دقیقاً چیست؟ مهم‌ترین تفاوت این است که در MVC، View می‌تواند مستقیم Model را بخواند، ولی در MVP این ارتباط قطع می‌شود. این باعث می‌شود جریان داده یک‌طرفه و رفتار برنامه قابل پیش‌بینی شود.
۲) آیا MVP برای اپ‌های اندرویدی هنوز کاربرد دارد؟ بله، در پروژه‌های موجود و مبتنی بر XML هنوز بسیار رایج است. اما برای پروژه‌های جدید مبتنی بر Compose، MVVM یا MVI محبوب‌تر هستند.
۳) آیا MVP با MVVM رقیب است یا مکمل؟ بیشتر مکمل. در یک سیستم بزرگ، لایه‌ی Presentation را می‌توان به لایه‌های مختلف تقسیم کرد: معمولاً صفحات ساده‌تر با MVP و صفحات با وضعیت پیچیده‌تر با MVVM.
۴) تفاوت Presenter و ViewModel در MVVM چیست؟ ViewModel به‌طور خودکار با چرخه‌ی حیات هماهنگ می‌شود و LiveData/Flow ارائه می‌دهد، در حالی که Presenter باید دستی به چرخه‌ی حیات متصل شود.
۵) آیا MVP تست‌پذیری را ۱۰۰٪ تضمین می‌کند؟ فقط اگر View و Presenter واقعاً از هم جدا باشند. اگر Presenter به Context اندروید نیاز داشته باشد، عملاً همان مشکل قبلی برمی‌گردد.
۶) آیا باید یک Presenter برای هر صفحه بسازم؟ بله، بهتر است یک Presenter مستقل به‌ازای هر صفحه باشد. Presenter بزرگ که همه‌ی صفحه‌ها را مدیریت کند، همان مشکل Controller بزرگ را تکرار می‌کند.
۷) تفاوت Passive View و Active View چیست؟ در Passive View، تمام تصمیمات در Presenter است. در Active View، View خودش هم کمی منطق دارد. MVP کلاسیک به Passive View اشاره دارد چون ایده‌ی جداسازی را بهتر حفظ می‌کند.
۸) آیا می‌توان MVP را با لایه‌بندی ترکیب کرد؟ بله و این ترکیب بسیار رایج است: MVP درون لایه‌ی Presentation (که خودش یک لایه از ساختار لایه‌بندی است) و لایه‌بندی در سطح کل سیستم.
۹) آیا MVP برای پروژه‌های تیمی بزرگ مناسب است؟ تا حدی. مشکل اصلی، حجم زیاد کد است. اگر تیم بزرگ باشد، Feature-Based بهتر عمل می‌کند تا پیاده‌سازی‌های Presenter یک پوشه‌ی بزرگ به هم نریزند.
۱۰) چطور وضعیت را در MVP نگه دارم؟ معمولاً به دو روش: نگه‌داری وضعیت در فیلدهای Presenter و بازیابی از Bundle، یا تعریف یک ViewState واحد و کشش آن به‌صورت LiveData یا Flow.
۱۱) آیا می‌توان از callback به‌جای Flow در MVP استفاده کرد؟ بله، و این روش در MVP کلاسیک رایج است. اما برای جریان‌های پیوسته (مثل چت) استفاده از Flow یا Rx انتخاب بهتری است.
۱۲) آیا MVP به داده‌ی دوحالته نیاز دارد؟ خیر، در واقع MVP برای داده‌ی تک‌طرفه طراحی شده است. این یکی از نقاط قوت آن است.
۱۳) چگونه از انتقال منطق به View جلوگیری کنم؟ قانون بگذارید که View فقط متدهای showX() داشته باشد و هیچ repository یا if مربوط به کسب‌وکار در آن نباشد.
۱۴) آیا Contract باید برای هر صفحه باشد؟ بله، یک Contract به‌ازای هر صفحه یا جریان کاربر. قرار دادن همه‌ی متدها در یک Contract بزرگ، کد را غیرقابل نگهداری می‌کند.
۱۵) بهترین راه تست یک Presenter چیست؟ استفاده از یک پیاده‌سازی جعلی (Fake) ساده از Repository و یک View ضبط‌کننده (Recording View) که دستورات را ثبت می‌کند. این ترکیب، تست را سریع و قطعی می‌کند.

جمع‌بندی

MVP یک گام مهم در تاریخچه‌ی معماری اندروید بود: اولین الگویی که به‌طور جدی نشان داد می‌توان منطق را از کد سیستم‌عامل جدا کرد و آن را در میلی‌ثانیه تست کرد. این ایده هنوز پابرجاست و در قالب MVVM و MVI ادامه پیدا کرده است.

اگر امروز در حال شروع یک پروژه‌ی جدید اندرویدی هستید، شاید MVP انتخاب اول شما نباشد — MVVM یا MVI جلوتر هستند. اما فهم عمیق MVP به شما کمک می‌کند MVVM را بهتر درک کنید، چون تفاوت این دو فقط در نام ViewModel است.

پیام پایانی سری ۱۴ مقاله‌ای این مقاله ششمین عضو سری «معماری‌های نرم‌افزاری» است. اکنون شما الگوهای تقسیم مسئولیت (MVC، MVP) را می‌شناسید و ساختارهای کلان معماری (Layered، Clean، Onion، Hexagonal) را هم پوشش داده‌اید. مقاله‌ی بعدی به MVVM می‌پردازد.
