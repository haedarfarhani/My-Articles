Event Loop و همزمانی؛ مدل اجرای غیرهمگام JavaScript

JavaScript یک زبان تک‌رشته‌ای (single-threaded) با مدل اجرای غیرهمگام (asynchronous) و مبتنی بر رخداد است. این مقاله از صفر تا پیشرفته توضیح می‌دهد Call Stack و Event Loop و Microtask چطور کار می‌کنند، همه‌ی متدها و کلاس‌های مهم (setTimeout، Promise، async/await، Web Worker، AbortController، Atomics) را با کد نشان می‌دهد و با نمودارهای متحرک و پرسش‌های مهم، ذهنیت درست برای debugging ترتیب اجرا می‌سازد.

بخش ۱مقدمه: همزمانی، موازی‌سازی و مدل اجرای JavaScript

خطر رایج این است که «غیرهمگام» و «موازی» را یکی بدانیم. JavaScript در یک Thread واحد اجرا می‌شود، اما می‌تواند هزاران عملیات را همزمان «در جریان» داشته باشد؛ چون کارهای کند (شبکه، فایل، تایمر) را به Host می‌سپارد و خودش آزاد می‌ماند. این تفکیک، کلید فهم کل این مقاله است.

دو تعریف دقیق Concurrency (همزمانی) یعنی چند کارِ در حال پیشرفت که بین آن‌ها جابه‌جا می‌شویم — نه لزوماً در یک لحظه اجرا می‌شوند. Parallelism (موازی‌سازی) یعنی چند کار که واقعاً در همان لحظه روی هسته‌های CPU مختلف اجرا می‌شوند.
ویژگیConcurrencyParallelism

سخت‌افزارروی یک هسته هم ممکن استچند هسته لازم است
نمونه در JSEvent Loop، Promise، async/awaitWeb Worker، Worker Threads، child_process
هدفبهره‌وری و پاسخ‌گویی (پرهیز از انتظار)سرعت و توان محاسباتی بیشتر
// ✗ بد: Blocking — کل Thread (و UI) قفل می‌شود
function block(ms) {
  const end = Date.now() + ms;
  while (Date.now() < end) { /* هیچ‌کاری نمی‌شود کرد */ }
}

console.log('start');
block(3000);              // سه ثانیه هیچ کدی اجرا نمی‌شود
console.log('end');

// ✓ خوب: Non-blocking — کار را می‌سپاریم و آزاد می‌مانیم
console.log('start');
setTimeout(() => console.log('timer'), 3000);
console.log('end');
// ترتیب چاپ: start → end → timer
Single-Threaded ولی Non-Blocking JavaScript فقط یک Call Stack دارد؛ پس هرگز دو تابع هم‌زمان اجرا نمی‌کند. اما عملیات I/O را به Host (مرورگر یا libuv در Node.js) واگذار می‌کند که آن‌ها را در پس‌زمینه انجام دهد و نتیجه را به‌صورت Callback به صف برگرداند.
Prerequisites آشنایی مقدماتی با JavaScript و توابع؛ برای مقایسه‌ی ذهنی با زبان دیگر، همزمانی در کاتلین را ببینید.

بخش ۲Call Stack و Run-to-Completion

وقتی کدی اجرا می‌شود، برای هر فراخوانی یک Execution Context روی Call Stack گذاشته می‌شود. Stack ساختار LIFO است: آخرین فریم، اولین فریمِ خارج‌شده. قانون طلایی این است که هیچ تابعی نیمه‌کاره قطع نمی‌شود (Run-to-Completion) — تا وقتی Stack خالی نشود، Event Loop نمی‌تواند چیزی اجرا کند. 

function third() { throw new Error('boom'); }
function second() { third(); }
function first()   { second(); }

first();
// Uncaught Error: boom
//     at third
//     at second
//     at first
// این «Stack Trace» دقیقاً همان Call Stack در لحظه‌ی خطاست

// سرریز Stack با بازگشت بی‌پایان:
function recurse() { return recurse(); }
recurse();   // RangeError: Maximum call stack size exceeded
نکته‌ی عملی Stack Trace به‌ترتیب از داخل به بیرون است: بالاترین خط، جایی است که خطا اتفاق افتاده و پایین‌ترین خط، جایی است که شروع شده. برای دیباگ، از پایین به بالا بخوانید.

بخش ۳Event Loop: قلب اجرای JavaScript

Event Loop یک حلقه‌ی بی‌پایان است که یک کار ساده می‌کند: «آیا Call Stack خالی است؟ اگر بله، اولین کارِ آماده را از صف بردار و روی Stack اجرا کن.» کل شگفتی غیرهمگامی JavaScript در همین حلقه است. 

console.log('۱ script start');

setTimeout(() => console.log('۵ setTimeout'), 0);

Promise.resolve().then(() => console.log('۳ promise.then'));
queueMicrotask(() => console.log('۴ queueMicrotask'));

console.log('۲ script end');

// ترتیب قطعی:
// ۱ script start
// ۲ script end
// ۳ promise.then      (Microtask)
// ۴ queueMicrotask    (Microtask)
// ۵ setTimeout        (Task)
قانون طلایی ترتیب Sync → Microtask (تا تخلیه‌ی کامل) → Task بعدی → دوباره Microtask. یعنی بعد از هر Task، همه‌ی Microtaskهای جدید هم دوباره اجرا می‌شوند.

بخش ۴فازهای Event Loop در Node.js

در مرورگر Event Loop ساده‌تر است؛ در Node.js حلقه از چند فاز تشکیل شده که هر دور یکی‌یکی طی می‌شوند. process.nextTick و Microtaskها در فاصله‌ی بین هر فاز و بعد از هر Callback اجرا می‌شوند.

pollدریافت رخدادهای I/O و اجرای Callbackهای آماده (قلب حلقه)

  console.log('poll → I/O callback');
  setTimeout(() => console.log('timers (دور بعد)'), 0);
  setImmediate(() => console.log('check (دور بعد)'));
});

// خروجی تضمین‌شده:
// nextTick → promise → (timers/check: ترتیب در سطح ماژول قابل تضمین نیست)
// داخل Callback، چون در فاز poll هستیم: poll → check → timers
تله‌ی معروف در سطح ماژول، ترتیب setTimeout(fn, 0) و setImmediate قابل پیش‌بینی نیست. اما داخل یک Callback مربوط به I/O، همیشه setImmediate (فاز check) قبل از setTimeout (فاز timers دور بعد) اجرا می‌شود.

بخش ۵Task Queue و Microtask Queue

دو صف داریم و تفاوتشان حیاتی است: Microtask Queue تا زمانی که چیزی در آن باشد کامل تخلیه می‌شود، ولی از Task Queue بعد از هر Task فقط یک مورد برداشته می‌شود.

Microtask Starvation اگر داخل یک Microtask، Microtask جدید بسازید (مثلاً Promise.resolve().then(...) در حلقه)، صف هرگز خالی نمی‌شود و مرورگر هیچ‌وقت رندر نمی‌کند — صفحه یخ می‌زند. برای کارهای تکراری از setTimeout استفاده کنید تا فرصت رندر بماند.

بخش ۷Timerها: setTimeout، setInterval و setImmediate

مهم‌ترین سوءتفاهم درباره‌ی setTimeout(fn, 0) این است که «فوراً» اجرا شود. هرگز این‌طور نیست: فقط یعنی «حداقل ۰ میلی‌ثانیه بعد، در اولین فرصتِ صف Task». تأخیر واقعی به‌اندازه‌ی زمانِ اشغال بودن Stack است.

تابعمکانمعنی
setTimeout(fn, ms)مرورگر + Nodeاجرای یک‌باره پس از حداقل ms؛ برمی‌گرداند Timeout
setInterval(fn, ms)مرورگر + Nodeاجرای تکرارشونده با فاصله‌ی ms
setImmediate(fn)فقط Node.jsاجرا در فاز check، بعد از I/O همین دور
clearTimeout(id)مرورگر + Nodeلغو تایمر
clearInterval(id)مرورگر + Nodeلغو بازه‌ی تکرار
clearImmediate(id)فقط Node.jsلغو setImmediate
timer.ref() / timer.unref()فقط Node.jsنگه‌داشتن/رهاکردن پروسه تا اتمام تایمر
// یک‌باره
const id = setTimeout(() => console.log('once'), 1000);
clearTimeout(id);

// تکرارشونده با توقف
const tick = setInterval(() => console.log('tick'), 1000);
setTimeout(() => clearInterval(tick), 5000);

// setImmediate (Node.js) — داخل کار I/O برنده‌ی timers است
setImmediate(() => console.log('immediate'));

// unref: اگر این تنها دلیل زنده‌ماندن پروسه باشد، بگذار بسته شود
const keepAlive = setTimeout(() => {}, 60_000);
keepAlive.unref();

// تایمر در تایمر: تودرتویی بالای ۵ سطح، حداقل ۴ms می‌شود
function nested(n) {
  if (n <= 0) return;
  setTimeout(() => nested(n - 1), 0);
}
nested(10);
دقت (Precision) تایمرها دقیق نیستند: حداقل تأخیر ۰ است، اما تخلیه‌ی Microtaskها، رندر و Load سیستم می‌تواند اجرا را ثانیه‌ها عقب بیندازد. برای اندازه‌گیری زمان واقعی، نه شمارش تکرار، از performance.now() استفاده کنید.
جایگزین مدرن برای setInterval setInterval اگر Callback کند باشد، اجراها روی هم می‌افتند. الگوی درست، setTimeout بازگشتی است که فقط بعد از پایان کار تایمر بعدی را می‌گذارد.

بخش ۸queueMicrotask و process.nextTick

برای فرستادن کار به صف Microtask سه راه داریم: Promise.resolve().then()، queueMicrotask() و در Node.js process.nextTick(). اما process.nextTick حتی از Microtask هم جلوتر است و قبل از تخلیه‌ی Microtaskها اجرا می‌شود.

متدمکاناولویت
process.nextTick(fn)فقط Node.js۱ — بالاترین (قبل از Microtask)
queueMicrotask(fn)مرورگر + Node۲ — Microtask
Promise.resolve().then(fn)مرورگر + Node۲ — Microtask
setImmediate(fn)فقط Node.js۳ — فاز check
setTimeout(fn, 0)مرورگر + Node۴ — Task

queueMicrotask(() => console.log('microtask ۱'));
process.nextTick(() => console.log('nextTick ۲'));
Promise.resolve().then(() => console.log('promise ۱'));

// sync → nextTick ۱ → nextTick ۲ → microtask ۱ → promise ۱ → timer ۱
process.nextTick هرگز نه process.nextTick صف Microtask را دور نمی‌زند: اگر داخلش دوباره nextTick بسازید، I/O و تایمرها هرگز اجرا نمی‌شوند. در کد جدید از queueMicrotask یا setImmediate استفاده کنید؛ nextTick را برای سازگاری قدیمی نگه دارید.
queueMicrotask چرا؟ وقتی فقط می‌خواهید «بعد از پایان این اسکریپت ولی قبل از Task بعدی» کاری کنید، queueMicrotask صریح‌تر و سبک‌تر از ساختن یک Promise دور است.

بخش ۹Callback و Callback Hell

Callback نخستین راهِ غیرهمگام‌سازی در JavaScript بود: تابعی که «بعداً» صدا زده می‌شود. مشکل وقتی پیدا می‌شود که چند مرحله پشت‌سرهم لازم باشد و تودرتویی، کد را به «هرمِ عذاب» تبدیل کند. 

// Error-first Callback (Convention استاندارد Node.js)
function readConfig(path, callback) {
  fs.readFile(path, 'utf8', (err, data) => {
    if (err) return callback(err);      // خطا همیشه آرگومان اول
    try {
      callback(null, JSON.parse(data));
    } catch (e) {
      callback(e);
    }
  });
}

// ✗ Callback Hell: تودرتویی و مدیریت خطای تکراری
getUser(1, (err, user) => {
  if (err) return done(err);
  getOrders(user.id, (err, orders) => {
    if (err) return done(err);
    getInvoice(orders[0].id, (err, invoice) => {
      if (err) return done(err);
      done(null, invoice);
    });
  });
});
مشکل Callbackراه‌حل مدرن
تودرتویی عمیقPromise و async/await
مدیریت خطای تکرارییک try/catch یا .catch()
ترتیب کنترل‌نشدهPromise.all / for await
عدم توانایی برگشت نتیجهreturn یک Promise
وقتی Callback درست است رخدادهای تکرارشونده (Event) و APIهای سطح پایین مثل EventEmitter, fs.readFile و addEventListener ذاتاً Callback هستند. Callback بد نیست؛ تودرتویی بد است.

بخش ۱۰Promise و متدهای ترکیبی

Promise یک شیء با سه حالت است: pending، fulfilled و rejected. وقتی به حالت settled برسد، دیگر تغییر نمی‌کند. هر then/catch/finally یک Microtask می‌سازد.

متدنوعرفتار
Promise.resolve(v)StaticPromise حل‌شده با v
Promise.reject(e)StaticPromise رد‌شده با e
Promise.all(iter)Staticهمه موفق → آرایه؛ اولین رد → رد فوری
Promise.allSettled(iter)Staticهمه تمام شوند؛ هرگز رد نمی‌شود
Promise.race(iter)Staticاولین نتیجه (موفق یا ناموفق)
Promise.any(iter)Staticاولین موفق؛ اگر همه رد شوند AggregateError
Promise.withResolvers()Staticدسترسی بیرونی به resolve/reject
.then(onF, onR)Instanceزنجیره‌سازی نتیجه یا خطا
.catch(onR)Instanceگرفتن خطای زنجیره
.finally(onF)Instanceپاک‌سازی؛ بدون تغییر نتیجه
// ساخت و مصرف
const p = new Promise((resolve, reject) => {
  setTimeout(() => resolve(42), 1000);
});

p.then((v) => v * 2)
 .then((v) => console.log(v))          // 84
 .catch((err) => console.error(err))
 .finally(() => console.log('done'));

// ترکیب‌کننده‌ها
await Promise.all([a, b, c]);          // همه موفق لازم است
await Promise.allSettled([a, b]);      // [{status,value|reason}, ...]
await Promise.race([a, b]);            // اولین نتیجه
await Promise.any([a, b]);             // اولین موفق

// Promise.withResolvers (ES2024) — الگوی Deferred بدون پیچیدگی
const { promise, resolve, reject } = Promise.withResolvers();
someApi((err, data) => (err ? reject(err) : resolve(data)));
await promise;

// جلوگیری از Unhandled Rejection در سطح جهانی (Node.js)
process.on('unhandledRejection', (reason) => console.error('Unhandled:', reason));
// در مرورگر:
window.addEventListener('unhandledrejection', (e) => console.error(e.reason));
هر .then یک Microtask p.then(f) بلافاصله اجرا نمی‌شود؛ f به‌عنوان Microtask در صف گذاشته می‌شود. همین دلیل می‌شود که thenها همیشه بعد از کدِ همگامِ ادامه‌ی اسکریپت اجرا شوند.

بخش ۱۱async/await، Generator و async Iterator

async/await «شکرِ نحویِ» Promise است: کدِ غیرهمگام را همگام‌خوان می‌کند. await اجرای همان تابع را متوقف (suspend) می‌کند، اما Thread را آزاد می‌گذارد تا Event Loop کارهای دیگر را انجام دهد. 

async function loadUser(id) {
  try {
    const res = await fetch(`/api/users/${id}`);
    if (!res.ok) throw new Error(`HTTP ${res.status}`);
    return await res.json();
  } catch (err) {
    console.error('خطا:', err.message);
    throw err;                          // پرتاب دوباره برای فراخوان
  } finally {
    console.log('پایان درخواست');
  }
}

// ✗ ترتیبی: کند
const a = await loadUser(1);
const b = await loadUser(2);

// ✓ موازی: سریع
const [user1, user2] = await Promise.all([loadUser(1), loadUser(2)]);

// async generator + for await...of (صفحه‌بندی)
async function* paginate(url) {
  let next = url;
  while (next) {
    const res = await fetch(next);
    const page = await res.json();
    yield page.items;
    next = page.next;
  }
}

for await (const items of paginate('/api/items')) {
  console.log(items.length);
}

// Generator معمولی: توقف/ادامه‌ی دستی
function* range(n) {
  for (let i = 0; i < n; i++) yield i;
}
[...range(3)];   // [0, 1, 2]

// Top-level await فقط در ES Module
const cfg = await fetch('/config.json').then((r) => r.json());

بخش ۱۲Threading: Web Worker و Worker Thread

برای Parallelism واقعی در JavaScript باید Thread جدید بسازیم. مرورگر Web Worker و Node.js Worker Threads را دارد. Worker حافظه‌ی مستقل دارد و ارتباط فقط با پیام انجام می‌شود؛ پس هرگز DOM را مستقیماً لمس نمی‌کند. 

// ── Web Worker (مرورگر) ──
// main.js
const worker = new Worker('worker.js', { type: 'module' });
worker.postMessage({ n: 45 });
worker.onmessage = (e) => console.log('نتیجه:', e.data);
worker.onerror = (e) => console.error(e.message);
// worker.terminate();

// worker.js
self.onmessage = (e) => {
  self.postMessage(fib(e.data.n));   // محاسبه‌ی سنگین، بدون قفل UI
};

// ── Worker Threads (Node.js) ──
import { Worker, isMainThread, parentPort } from 'node:worker_threads';

if (isMainThread) {
  const w = new Worker(new URL(import.meta.url));
  w.on('message', (r) => console.log(r));
  w.postMessage({ n: 45 });
} else {
  parentPort.on('message', (msg) => parentPort.postMessage(fib(msg.n)));
}

هزینه‌ی Worker ساخت Worker گران است (چند مگابایت حافظه و زمان راه‌اندازی). برای کارهای کوچک، Worker بسازید و بکشید؛ برای بار زیاد، از Worker Pool استفاده کنید. داده با Structured Clone کپی می‌شود، مگر Transferable بفرستید.

بخش ۱۳SharedArrayBuffer، Atomics و MessageChannel

وقتی چند Thread باید روی داده‌ی مشترک کار کنند، SharedArrayBuffer حافظه‌ی مشترک می‌سازد و Atomics دسترسی اتمیک و ایمن را تضمین می‌کند. بدون Atomics، شرایط رقابتی (Race Condition) اجتناب‌ناپذیر است. 

// حافظه‌ی مشترک بین Workerها
const sab = new SharedArrayBuffer(4);          // ۴ بایت
const view = new Int32Array(sab);

Atomics.store(view, 0, 0);                     // نوشتن اتمیک
Atomics.add(view, 0, 1);                       // ++ اتمیک
Atomics.load(view, 0);                         // خواندن اتمیک

// هماهنگی بدون Busy-Wait
Atomics.wait(view, 0, 0);                      // منتظر بمان تا مقدار از ۰ عوض شود
Atomics.notify(view, 0, 1);                    // یک Thread منتظر را بیدار کن

// MessageChannel / MessagePort — کانال مستقیم دوطرفه
const { port1, port2 } = new MessageChannel();
port1.onmessage = (e) => console.log('از port2:', e.data);
port2.postMessage('hello');

// BroadcastChannel — انتشار بین Contextهای هم‌مبدأ
const bc = new BroadcastChannel('notify');
bc.onmessage = (e) => console.log(e.data);
bc.postMessage({ type: 'refresh' });

// Transferable: انتقال مالکیت بدون کپی حافظه
const buffer = new ArrayBuffer(1024 * 1024);
worker.postMessage({ buffer }, [buffer]);      // buffer اکنون بی‌استفاده است
APIکاربرد
SharedArrayBufferحافظه‌ی مشترک بین Threadها (نیازمند COOP/COEP در مرورگر)
Atomicsعملیات اتمیک روی Int32Array برای پرهیز از Race
Atomics.wait/notifyهماهنگی بلاک‌کننده به‌جای چرخش CPU
MessageChannelکانال ارتباطی دوطرفه بین Contextها
BroadcastChannelانتشار پیام بین تب‌ها/Workerهای هم‌مبدأ
هشدار امنیتی SharedArrayBuffer در مرورگر فقط با هدرهای Cross-Origin-Opener-Policy: same-origin و Cross-Origin-Embedder-Policy: require-corp در دسترس است، چون خطر حمله‌ی Spectre دارد.

بخش ۱۴لغو و رخداد: AbortController و EventEmitter

کارهای غیرهمگام باید قابل لغو باشند؛ وگرنه نتیجه‌ی دیرهنگام، وضعیت را خراب می‌کند. AbortController و AbortSignal استاندارد لغو هستند و EventEmitter الگوی رخداد-محور در Node.js. 

// لغو fetch با AbortController
const ac = new AbortController();
const timer = setTimeout(() => ac.abort(), 5000);

try {
  const res = await fetch('/api/slow', { signal: ac.signal });
  console.log(await res.json());
} catch (err) {
  if (err.name === 'AbortError') console.log('درخواست لغو شد');
} finally {
  clearTimeout(timer);                 // همیشه پاک‌سازی کن
}

// AbortSignal.timeout (مدرن و کوتاه)
await fetch('/api/slow', { signal: AbortSignal.timeout(5000) });

// ترکیب چند سیگنال
const sig = AbortSignal.any([ac.signal, AbortSignal.timeout(3000)]);

// EventEmitter (Node.js)
import { EventEmitter } from 'node:events';

class Store extends EventEmitter {}
const store = new Store();

const onChange = (v) => console.log('changed →', v);
store.on('change', onChange);          // ثبت
store.once('load', () => console.log('loaded'));
store.emit('change', 1);               // انتشار
store.off('change', onChange);         // حذف
عضوکارکرد
AbortController.abort()لغو کارهای متصل به signal
AbortSignal.timeout(ms)سیگنال خودکار پس از مهلت
AbortSignal.any([...])ترکیب چند سیگنال
emitter.on/off/onceثبت و حذف شنونده
emitter.emit(event, ...args)انتشار رخداد به‌صورت همگام
emit همگام است emitter.emit شنونده‌ها را همگام صدا می‌زند — نه در صف. اگر شنونده سنگین باشد، همان جا Event Loop را می‌بندد. برای جداکردن، از setImmediate یا queueMicrotask استفاده کنید.

بخش ۱۵Starvation، Anti-patternها و Best Practices

بیشتر باگ‌های «کندی» و «فریز» در JavaScript از یک ریشه‌اند: کاری که نباید روی Main Thread باشد. اینجا خطاهای رایج و درمانشان را می‌بینیم. 

// ✗ Anti-pattern: کار سنگین روی Main Thread
app.get('/report', (req, res) => {
  const data = heavyCpuReport();      // Event Loop قفل؛ همه‌ی درخواست‌ها منتظر
  res.json(data);
});

// ✓ درمان ۱: آفلود به Worker Thread
app.get('/report', (req, res) => {
  const worker = new Worker('./report-worker.js');
  worker.once('message', (data) => res.json(data));
  worker.once('error', (err) => res.status(500).send(err.message));
  worker.postMessage(req.query);
});

// ✓ درمان ۲: I/O غیرمسدودکننده به‌جای نسخه‌ی Sync
import { readFile } from 'node:fs/promises';
const data = await readFile(path, 'utf8');     // نه readFileSync

// ✗ Anti-pattern: await در حلقه برای کارهای مستقل
for (const id of ids) await fetchItem(id);     // ترتیبی و کند

// ✓ موازی
await Promise.all(ids.map((id) => fetchItem(id)));

// ✗ Anti-pattern: Microtask بی‌پایان → Starvation
function spin() {
  Promise.resolve().then(spin);                // رندر هرگز نمی‌رسد
}

// ✗ Anti-pattern: نادیده‌گرفتن خطا
fetch('/api').then((r) => r.json());           // بدون catch → Unhandled Rejection
Best Practices — چک‌لیست
  • هرگز کار CPU-سنگین روی Main Thread انجام ندهید؛ به Worker بسپارید.
  • در Node.js همیشه نسخه‌ی Promise ماژول‌ها را ترجیح دهید (fs/promises).
  • کارهای مستقل را با Promise.all موازی کنید، نه await ترتیبی.
  • هر عملیات غیرهمگام باید catch یا try/catch داشته باشد.
  • برای لغو، AbortController و پاک‌سازی منابع را جدی بگیرید.
  • در حلقه‌های تکراری، از setTimeout برای نفس‌کشیدن Event Loop استفاده کنید.
  • مصرف حافظه‌ی Workerهای زیاد را مدیریت کنید؛ از Pool استفاده کنید.
Starvation چیست؟ وقتی صف Microtask هرگز خالی نمی‌شود یا یک Task بی‌پایان اجرا می‌شود، رندر و Taskهای بعدی هرگز فرصت اجرا پیدا نمی‌کنند. صفحه یخ می‌زند و تایمرها عقب می‌افتند.

بخش ۱۶سوالات مهم و جمع‌بندی

در ادامه چند پرسش پرتکرار که در مصاحبه و debug واقعی زیاد پیش می‌آید.

Q1: JavaScript تک‌رشته‌ای است؟ بله؛ یک Call Stack و یک Thread اجرا. اما می‌تواند چندین کار را همزمان «در جریان» نگه دارد (Concurrency) و با Worker موازی‌سازی واقعی (Parallelism) انجام دهد.
Q2: تفاوت Microtask و Macrotask؟ Microtaskها (Promise، queueMicrotask) تا ته تخلیه می‌شوند و اولویت بالاتری دارند؛ Macrotaskها (setTimeout، I/O) یکی‌یکی و بین‌شان فرصت رندر است.
Q3: چرا setTimeout(fn, 0) فوراً اجرا نمی‌شود؟ چون فقط در صف Task اینسرت می‌شود و فقط وقتی Stack و Microtaskها خالی شدند اجرا می‌شود؛ تأخیر واقعی به بار سیستم هم بستگی دارد.
Q4: callStack خالی چه می‌شود؟ Event Loop یک کار از Microtask و سپس از Task برداشته و اجرا می‌کند؛ همین چرخه بی‌پایان است.
Q5: process.nextTick بهتر از setImmediate است؟ نه؛ nextTick بالاترین اولویت را دارد و می‌تواند I/O را گرسنه کند. setImmediate ایمن‌تر است و در فاز check اجرا می‌شود.
Q6: برای کار CPU-سنگین چه کنم؟ به Web Worker (مرورگر) یا Worker Threads (Node.js) بسپارید تا Main Thread آزاد بماند؛ در غیر این صورت UI فریز و سرور کند می‌شود.
Q7: تفاوت Concurrency و Parallelism؟ Concurrency = مدیریت هم‌زمانِ چند کار (روی یک Thread هم ممکن است)؛ Parallelism = اجرای فیزیکی هم‌زمان روی چند هسته.
Q8: async/await جایگزین Promise است؟ نه؛ روی Promise ساخته شده. هر await یک Microtask می‌سازد و رفتار زنجیره همان است — فقط خوانایی بهتر می‌شود.

مدل اجرای JavaScript با یک ایده‌ی ساده بنا شده: یک Thread، یک Call Stack، و یک Event Loop که کارها را از صف برمی‌دارد. اگر مرز بین همگام و Microtask و Task را بفهمید، و برای کارهای سنگین از Worker و برای لغو از AbortController استفاده کنید، کدِ غیرهمگام دیگر جادو نیست؛ یک الگوی قابل پیش‌بینی است.
