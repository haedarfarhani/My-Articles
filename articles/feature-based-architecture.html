Feature Based Architecture؛ وقتی «لایه‌ها» به کابوس تبدیل می‌شوند

به‌جای اینکه کد را بر اساس نوع کلاس (Controller، Service، Repository) دسته‌بندی کنید، آن را بر اساس قابلیت کسب‌وکار دسته‌بندی کنید. در این راهنما می‌بینیم چرا ساختار لایه‌ای در پروژه‌های بزرگ فرو می‌ریزد، چگونه هر فیچر را با پوشه‌ی خودش مستقل کنیم، و با Java 21 و Spring Modulith این ساختار را واقعاً پیاده می‌کنیم.

بخش ۱مقدمه: وقتی پوشه‌ها بزرگ می‌شوند

فرض کنید پروژه‌ی شما دو سال است زنده است. ساختارش «استاندارد» است: 

src/main/java/com/company/shop/
├── controller/          ← ۴۲ فایل
│   ├── UserController.java
│   ├── OrderController.java
│   ├── ProductController.java
│   └── ... ۳۹ فایل دیگر
├── service/             ← ۶۸ فایل
│   ├── UserService.java        ← ۱٬۲۰۰ خط
│   ├── OrderService.java       ← ۸۷۰ خط
│   └── ... ۶۶ فایل دیگر
├── repository/          ← ۳۱ فایل
├── entity/              ← ۲۸ فایل
├── dto/                 ← ۵۵ فایل
├── util/                ← ۲۴ فایل
└── config/              ← ۱۹ فایل

حالا یک فیچر جدید به شما می‌دهند: «سفارش عمده‌فروشی». اولین سؤال یک توسعه‌دهنده‌ی تازه‌وارد چیست؟

مشکل واقعی «کدام فایل‌ها را باید تغییر بدهم؟» جواب: یک Controller جدید، یک Service جدید، یک Repository جدید، دو DTO، و یک تغییر در OrderService. هشت فایل در شش پوشه‌ی مختلف. هیچ‌کدام کنار هم نیستند.

همین یک فیچر، سه مشکل جدی می‌سازد:

  1. نبود محل مالکیت — کدام تیم مسئول سفارش است؟ «هرکسی که به Order دست می‌زند.» یعنی همه.
  2. افزودن ویژگی جدید به سیستم نیازمند دانستن همه‌ی لایه‌هاست — این همان تعداد دفعات تغییر (Change Amplification) است.
  3. تست‌ها غیرقابل جداسازی‌اند — تست OrderService برای اجرا به ۱۲ Repository دیگر نیاز دارد.

ریشه‌ی مشکل: دسته‌بندی افقی

ساختار لایه‌ای کد را بر اساس نوع کلاس دسته‌بندی می‌کند: Controller، Service، Repository. این یعنی یک قابلیت کسب‌وکار (سفارش) به شش پوشه پخش می‌شود. به این می‌گویند برش افقی (Horizontal Slice).

معماری مبتنی بر قابلیت، دقیقاً برعکس عمل می‌کند: یک قابلیت = یک پوشه‌ی کامل که همه‌ی لایه‌هایش داخل خودش است. 

src/main/java/com/company/shop/
├── order/                    ← همه‌چیز مربوط به سفارش، یک‌جا
│   ├── api/     OrderController.java، OrderRequest، OrderResponse
│   ├── domain/  Order.java، OrderStatus، OrderService
│   ├── data/    OrderRepository.java، OrderJpaEntity
│   └── config/  OrderModuleConfig.java
├── product/
├── customer/
└── shared/                   ← فقط ابزارهای واقعاً مشترک

حالا همان فیچر «سفارش عمده‌فروشی» فقط داخل پوشه‌ی order/ پیاده می‌شود.

ریشه‌ی نیاز: هزینه‌ی تغییر

معیار Change Amplification «تعداد فایل‌هایی که برای افزودن یک قابلیت جدید باید تغییر کنند.» در ساختار افقی این عدد بزرگ است (هشت فایل در شش پوشه). در ساختار عمودی این عدد کوچک است (همه در یک پوشه) و مهم‌تر از آن، همه در یک جا هستند.

این عدد مستقیماً با «هزینه‌ی تغییر» رابطه دارد. اگر افزودن یک فیچر ساده دو هفته وقت بگیرد، تیم شما عملاً نمی‌تواند تغییر کند — و تغییر، همان چیزی است که محصول زنده نیاز دارد.

رابطه با موج Microservices

معماری مبتنی بر قابلیت، پیش‌نیاز موفقیت میکروسرویس است. اگر نمی‌توانید کدتان را در ماژول‌های مستقل (در یک فرایند) تقسیم کنید، قطعاً نمی‌توانید آن را بین چند سرویس مستقل (در چند فرایند) تقسیم کنید. دلیل اینکه بیشتر مهاجرت‌های میکروسرویس شکست می‌خورند، همین است.

بخش ۳Feature Based چیست؟ (تعریف دقیق)

تعریف معماری مبتنی بر قابلیت یعنی سازماندهی کد به‌گونه‌ای که هر پوشه‌ی اصلی، یک قابلیت کسب‌وکار کامل و مستقل باشد و همه‌ی لایه‌های لازم برای آن — از رابط کاربری تا دیتابیس — داخل همان پوشه قرار بگیرد.

به زبان ساده: «به‌جای ساختن لایه‌های بزرگ، پوشه‌های کوچک عمودی بساز».

تست حذف کامل

معتبرترین معیار انتخاب یک فیچر این است: آیا می‌توانید کل پوشه‌اش را حذف کنید و مطمئن باشید چیزی از کار نمی‌افتاد؟ 

# پوشه‌ی order/ کاملاً حذف می‌شود، بدون شکستن چیزی:
rm -rf src/main/java/com/shop/order/

# اگر این کار امن است → مرزها درست‌اند
# اگر چیزی از کار افتاد → یک فیچر دیگر به این پوشه وابسته بوده
# یعنی این پوشه یک فیچر نبوده، یک لایه بوده است

قواعد طراحی فیچر

  • نام پوشه = نام قابلیت کسب‌وکار (نه common، نه base)
  • هر فیچر، API عمومی مشخص دارد؛ بقیه‌ی کلاس‌ها package-private
  • فیچرها فقط از طریق API عمومی همدیگر را می‌شناسند
  • پوشه‌ی shared فقط برای چیزی که واقعاً به هر دو نیاز دارد
  • هر فیچر می‌تواند تست خودش را داشته باشد، مستقل از بقیه
  • هر فیچر یک تیم مالک دارد
  • هیچ فیچری به پوشه‌ی فیچر دیگر import نمی‌کند مگر از طریق قرارداد عمومی

کدام را انتخاب کنیم؟

قاعده‌ی تصمیم اگر تعداد تیم‌ها کم است و محصول در حال کشف است → Vertical Slice. اگر محصول تثبیت شده و ساختار مهم است → Feature Based. اگر پروژه کوچک است (زیر ۱۰ هزار خط) → لایه‌ای کافی است.

رابطه‌ی Feature Based با Modular Monolith

این دو یک چیز هستند. Modular Monolith یعنی «یک استقرار، چند ماژول». Feature Based بیان ساختار کد است و Modular Monolith بیان استقرار. یک پروژه‌ی Feature Based معمولاً Modular Monolith هم هست.

مسیر مهاجرت کم‌ریسک لایه‌ای → Feature Based (پوشه‌بندی) → Modular Monolith (مرز API) → Microservices (مرز استقرار). هر مرحله ارزش مستقل دارد و می‌توانید در همان‌جا متوقف شوید.

بخش ۸جریان داده (Data Flow)

جریان بین دو ماژول

قواعد جریان داده

  • ورودی همیشه Command/DTO محلی فیچر است، نه Entity فیچر دیگر
  • خروجی همیشه Response محلی فیچر است، نه مدل داخلی

  • واکنش‌های جانبی از راه رویداد، نه فراخوانی مستقیم
  • ماژول هرگز از لایه‌ی data/ فیچر دیگر چیزی نمی‌بیند

❌ نادرست:

import java.util.ArrayList;

/** Aggregate Root. عمداً package-private است تا فقط از راه {@link Orders} ساخته شود. */
final class Order {

    private final String id;
    private final String customerId;
    private final List<OrderLine> lines = new ArrayList<>();
    private OrderStatus status;
    private BigDecimal total = BigDecimal.ZERO;

    private Order(String id, String customerId) {
        this.id = id;
        this.customerId = customerId;
        this.status = OrderStatus.DRAFT;
    }

    static Order create(String id, String customerId) {
        if (customerId == null || customerId.isBlank()) {
            throw new OrderError("شناسه‌ی مشتری الزامی است");
        }
        return new Order(id, customerId);
    }

    // ← بازسازی از دیتابیس: قوانین اولیه را دور می‌زند
    static Order restore(String id, String customerId, OrderStatus status,
                         BigDecimal total, List<OrderLine> lines) {
        Order order = new Order(id, customerId);
        order.status = status;
        order.total = total;
        order.lines.addAll(lines);
        return order;
    }

    void addLine(String productId, int quantity, BigDecimal unitPrice) {
        ensureDraft();
        if (quantity <= 0) {
            throw new OrderError("تعداد باید بزرگ‌تر از صفر باشد");
        }
        if (lines.stream().anyMatch(l -> l.productId().equals(productId))) {
            throw new OrderError("این محصول قبلاً در سفارش هست");
        }
        lines.add(new OrderLine(productId, quantity, unitPrice));
        recalculate();
    }

    void place() {
        ensureDraft();
        if (lines.isEmpty()) {
            throw new OrderError("سفارش بدون ردیف قابل ثبت نیست");
        }
        this.status = OrderStatus.PLACED;
    }

    void cancel(String reason) {
        if (status != OrderStatus.PLACED) {
            throw new OrderError("فقط سفارش ثبت‌شده قابل لغو است");
        }
        this.status = OrderStatus.CANCELLED;
    }

    boolean requiresApproval() {
        return total.compareTo(new BigDecimal("10000000")) > 0;
    }

    private void ensureDraft() {
        if (status != OrderStatus.DRAFT) {
            throw new OrderError("سفارش قابل ویرایش نیست");
        }
    }

    private void recalculate() {
        BigDecimal sum = BigDecimal.ZERO;
        for (OrderLine line : lines) {
            sum = sum.add(line.subtotal());
        }
        this.total = sum;
    }

    String id()             { return id; }
    String customerId()     { return customerId; }
    OrderStatus status()    { return status; }
    BigDecimal total()      { return total; }
    List<OrderLine> lines() { return List.copyOf(lines); }

    @Override
    public boolean equals(Object o) {
        return (this == o) || (o instanceof Order other && id.equals(other.id));
    }

    @Override
    public int hashCode() {
        return Objects.hash(id);
    }
}

import com.shop.order.domain.*;
import org.springframework.stereotype.Service;

import java.util.List;
import java.util.UUID;

@Service
class OrderService {

    private final OrderRepository repository;
    private final ModuleEventPublisher events;

    OrderService(OrderRepository repository, ModuleEventPublisher events) {
        this.repository = repository;
        this.events = events;
    }

    String placeOrder(PlaceOrderCommand command) {
        Order order = Order.create(command.id(), command.customerId());

        command.lines().forEach(l ->
                order.addLine(l.productId(), l.quantity(), l.unitPrice()));

        order.place();
        repository.save(order);

        events.publish(new OrderPlacedEvent(order.id(), order.customerId(),
                order.total()));
        return order.id();
    }

    OrderResponse findById(String id) {
        return repository.findById(id)
                .map(o -> new OrderResponse(o.id(), o.status().name(),
                        o.total(), o.requiresApproval()))
                .orElseThrow(() -> new OrderError("سفارش یافت نشد"));
    }

    void cancel(String id, String reason) {
        Order order = repository.findById(id)
                .orElseThrow(() -> new OrderError("سفارش یافت نشد"));
        order.cancel(reason);
        repository.save(order);
        events.publish(new OrderCancelledEvent(id, reason));
    }
}

package com.shop.inventory.api;

import com.shop.order.api.OrderPlacedEvent;
import org.springframework.context.event.EventListener;
import org.springframework.stereotype.Component;
import org.springframework.transaction.annotation.Transactional;

@Component
class InventoryOrderListener {

    private final StockService stock;

    InventoryOrderListener(StockService stock) {
        this.stock = stock;
    }

    @EventListener
    @Transactional
    void onOrderPlaced(OrderPlacedEvent event) {
        // ← فقط اطلاعات لازم؛ بدون کشیدن مدل کامل order
        stock.reserveFor(event.customerId(), event.total());
    }
}

Facade — API عمومی فیچر

package com.shop.order.api;

import org.springframework.stereotype.Service;

/**
 * Facade فیچر order: تنها سطحی که ماژول‌های دیگر می‌بینند.
 * پیچیدگی داخلی (چند entity، چند repository) پشت این نقطه پنهان است.
 */
@Service
public class OrderApi {

    private final OrderService service;
    private final OrderRepository orders;

    public OrderApi(OrderService service, OrderRepository orders) {
        this.service = service;
        this.orders = orders;
    }

    public OrderSummary place(String customerId, List<LineRequest> lines) {
        String id = service.placeOrder(PlaceOrderCommand.of(customerId, lines));
        return summarize(orders.findById(id).orElseThrow());
    }

    public OrderSummary find(String orderId) {
        return summarize(orders.findById(orderId)
                .orElseThrow(() -> new OrderError("سفارش یافت نشد")));
    }

    public void cancel(String orderId, String reason) {
        service.cancel(orderId, reason);
    }

    private OrderSummary summarize(Order order) {
        return new OrderSummary(order.id(), order.customerId(),
                order.status(), order.total(), order.requiresApproval());
    }

    public record LineRequest(String productId, int quantity, java.math.BigDecimal price) {}

    public record OrderSummary(String orderId, String customerId, OrderStatus status,
                                java.math.BigDecimal total, boolean needsApproval) {}
}

 * محافظت از مدل داخلی از مدل بیگانه‌ی درگاه پرداخت.
 * اگر فردا درگاه عوض شد، فقط این کلاس تغییر می‌کند.
 */
@Component
class ZarinpalGateway implements PaymentGateway {

    private final ZarinpalClient client;      // ← مدل بیرونی

    @Override
    public Receipt capture(CaptureCommand command) {
        // مدل بیگانه در همین‌جا ترجمه می‌شود
        var request = new ZarinpalRequest(command.referenceId(),
                command.amount().toPlainString());

        var response = client.requestPayment(request);

        if (response.status() != 100) {          // ← کد بیگانه
            throw new PaymentFailed("پرداخت ناموفق: " + response.message());
        }

        return new Receipt(response.authority(), response.amount());  // ← مدل داخلی
    }
}

بخش ۲۳۲۰ سؤال مصاحبه

سطح Junior (۱ تا ۱۰)

سؤال ۱ — Feature Based Architecture چیست؟ سازماندهی کد به‌گونه‌ای که هر پوشه‌ی اصلی یک قابلیت کسب‌وکار کامل باشد و همه‌ی لایه‌های لازم (API، دامنه، داده، تست) داخل همان پوشه قرار بگیرد. یعنی ساختار عمودی به‌جای افقی.
سؤال ۲ — تفاوت پوشه‌بندی لایه‌ای و فیچرمحور چیست؟ لایه‌ای: پوشه‌ها بر اساس نوع کلاس (controller، service، repository). فیچرمحور: پوشه‌ها بر اساس قابلیت (order، payment). در لایه‌ای یک فیچر در چند پوشه پخش است؛ در فیچرمحور همه در یک پوشه.
سؤال ۳ — یک فیچر خوب چه ویژگی‌هایی دارد؟ نامش یک قابلیت کسب‌وکار است، همه‌ی لایه‌های لازم را دارد، API عمومی مشخص دارد، و می‌توان آن را مستقل از بقیه تست کرد. مهم‌تر: اگر کل پوشه را حذف کنید، فقط همان قابلیت از کار بیفتد.
سؤال ۴ — «برش عمودی» یعنی چه؟ یعنی کد به‌جای برش افقی (لایه‌ها)، عمودی بریده شود: هر ستون عمودی یک قابلیت کامل از رابط کاربری تا دیتابیس است.
سؤال ۵ — پوشه‌ی shared چه زمانی مجاز است؟ فقط وقتی یک مفهوم واقعاً در حداقل سه فیچر مختلف استفاده می‌شود (مثل Money یا PageResponse). اگر فقط دو جا لازم است، هنوز جای درستی ندارد؛ در یکی از همان دو فیچر یا جای دوم بماند.
سؤال ۶ — چطور مرز یک فیچر را تعیین می‌کنید؟ از زبان کسب‌وکار شروع کنید: یک قابلیت قابل توضیح به کاربر. سپس تست کنید: آیا می‌توان پوشه را کامل حذف کرد بدون آسیب به چیز دیگری؟ اگر نه، مرز جابه‌جا است.
سؤال ۷ — چرا visibility جاوا در این معماری مهم است؟ چون کامپایلر وابستگی ناخواسته را می‌گیرد. اگر کلاس‌های داخل فیچر package-private باشند، هر کامپایل ناموفق وابستگی غیرمجاز را نشان می‌دهد. این یعنی مرز بدون قوانین کتبی هم اجبار می‌شود.
سؤال ۸ — چه چیزی در پوشه‌ی فیچر قرار نمی‌گیرد؟ کدی که به هیچ قابلیت مشخصی تعلق ندارد. هر چیزی که نتوانید به یک قابلیت کسب‌وکار نسبت دهید، یا به shared تعلق دارد یا در جای درستی نیست.
سؤال ۹ — تفاوت Feature Based و Vertical Slice چیست؟ دانه‌بندی فرق دارد: Feature Based در سطح حوزه‌ی کسب‌وکار است (فیچر «سفارش»)، Vertical Slice در سطح هر درخواست کاربر (اسلایس «ثبت سفارش»، «لغو سفارش»). Vertical Slice ریزدانه‌تر و کم‌ریسک‌تر است ولی ریسک تکرار بیشتری دارد.
سؤال ۱۰ — تست ماژول چه چیزی را تضمین می‌کند؟ اینکه فیچر بدون بقیه‌ی سیستم کار می‌کند. اگر تست ماژول بدون بالا آمدن فیچرهای دیگر پاس شود، مرزهای ماژولار سالم‌اند. اگر شکست بخورد، یک وابستگی غیرمجاز وجود دارد.

سطح Mid (۱۱ تا ۱۷)

سؤال ۱۱ — چگونه از بازگشت به ساختار افقی جلوگیری می‌کنید؟ سه ابزار: (۱) تست ماژول در هر commit؛ (۲) ArchUnit برای بررسی خودکار قواعد وابستگی؛ (۳) بازبینی کد با تمرکز بر اینکه کلاس جدید در پوشه‌ی درست قرار گرفته. ابزار بدون بازبینی انسانی کافی نیست.
سؤال ۱۲ — چگونه کد موجود را به این ساختار مهاجرت می‌دهید؟ مرحله‌ای و بدون تغییر رفتار: (۱) فقط package-by-feature با refactor ابزار IDE؛ (۲) استخراج فیچرهای مستقل‌تر؛ (۳) تعیین API عمومی؛ (۴) افزودن تست ماژول؛ (۵) حذف لایه‌های افقی باقی‌مانده. هر مرحله را می‌توان متوقف کرد.
سؤال ۱۳ — فیچرها چطور با هم ارتباط بگیرند؟ به ترتیب اولویت: (۱) فقط شناسه؛ (۲) API عمومی یکدیگر؛ (۳) کلاس قراردادی مشترک در shared؛ (۴) Integration Event برای واکنش ناهمگام. فراخوانی مستقیم مدل داخلی دیگر فیچر، گزینه‌ی نادرست است.
سؤال ۱۴ — چه زمانی تکرار کد بین فیچرها قابل قبول است؟ تا سه بار. تکرار از انتزاع ناقص بهتر است چون انتزاع بد، وابستگی مصنوعی می‌سازد. اگر تکرار سه‌بار شد، بررسی کنید که آیا واقعاً یک مفهوم مشترک است یا فقط کد شبیه.
سؤال ۱۵ — تفاوت Modular Monolith و Feature Based چیست؟ Feature Based درباره‌ی ساختار کد است و Modular Monolith درباره‌ی استقرار. یک پروژه‌ی Feature Based معمولاً Modular Monolith هم هست: یک فرایند، چند ماژول مستقل در کد.
سؤال ۱۶ — Feature Based چه رابطه‌ای با DDD دارد؟ مکمل‌اند. DDD می‌گوید مرزها کجا باشند (Bounded Context) و Feature Based می‌گوید کد داخل هر مرز چطور چیده شود. پروژه‌ای که هر دو را رعایت کند، هم مدل درست دارد و هم ساختار درست.
سؤال ۱۷ — چطور یک فیچر را «API عمومی» می‌کنید؟ فقط کلاس‌های api/ را public می‌کنید و بقیه را package-private. اگر فیچر دیگری به چیزی بیرون از api/ نیاز داشت، آن API باید گسترده شود — نه اینکه visibility کلاس داخلی عوض شود.

سطح Senior (۱۸ تا ۲۰)

سؤال ۱۸ — Feature Based چه تأثیری بر عملکرد دارد؟ در زمان اجرا هیچ اثری ندارد؛ نام پوشه در bytecode نیست. تأثیر واقعی روی چرخه‌ی توسعه است: زمان build، زمان اجرای تست محلی و کاهش conflict. کامپایل موازی هم بهتر کار می‌کند چون کلاس‌های هر فیچر یک واحد هستند.
سؤال ۱۹ — چه زمانی Feature Based اشتباه است؟ وقتی قابلیت‌ها به‌شدت به هم چسبیده‌اند و هیچ مرز منطقی وجود ندارد؛ وقتی تیم یک‌نفره است؛ وقتی پروژه اسکریپتی یا کمتر از ۵ هزار خط است؛ یا وقتی دامنه هنوز کشف نشده و نمی‌دانید فیچرهای واقعی چه هستند. در این حالت‌ها هزینه بیشتر از سود است.
سؤال ۲۰ — چگونه یک تیم بزرگ را به رعایت این ساختار متقاعد می‌کنید؟ با ابزار، نه با شعار: اول یک فیچر را کامل به‌عنوان نمونه مهاجرت دهید و نتیجه را نشان دهید (زمان تست، کاهش conflict)، سپس تست مرز را در CI اجباری کنید، و در نهایت قاعده‌ی «کلاس جدید فقط در فیچر» را در PR template و بازبینی کد نهادینه کنید. ساختار بدون اجبار خودکار، بعد از دو ماه فرو می‌ریزد.

بخش ۲۴پرسش‌های متداول (FAQ)

آیا این فقط یک تغییر نام پوشه است؟ نه. اگر فقط پوشه‌ها را جابه‌جا کنید و همه‌چیز public بماند، فقط مسیر عوض شده. ارزش واقعی در سه چیز است: قاعده‌ی visibility، تست ماژول، و API عمومی.
آیا با Feature Based نیاز به DDD دارم؟ نه. DDD مدل‌سازی دامنه است و به دانش کسب‌وکار نیاز دارد؛ Feature Based فقط ساختار کد. می‌توانید Feature Based را بدون DDD و حتی در یک پروژه‌ی ساده اجرا کنید.
آیا Feature Based همان Modular Monolith است؟ نه، یکی نیستند ولی معمولاً با هم می‌آیند. Feature Based ساختار کد است، Modular Monolith نحوه‌ی استقرار. یک Modular Monolith معمولاً Feature Based هم هست.
چند فیچر برای یک پروژه مناسب است؟ بین ۵ تا ۲۰. کمتر از ۵ یعنی تفاوت چندانی با لایه‌بندی ندارد. بیشتر از ۲۰ یعنی فیچرها ریز و بی‌معنا می‌شوند و مدیریت سخت می‌شود.
آیا هر فیچر باید دیتابیس خودش را داشته باشد؟ نه. این تصمیم جداست. جداسازی کد را بدون جداسازی دیتابیس هم می‌توان انجام داد. جداسازی دیتابیس معمولاً قدم بعدی و پرهزینه‌تر است.
اگر دو تیم مجبور به تغییر یک فیچر شدند چه؟ این نشانه‌ی مرز اشتباه است: آن فیچر باید به دو فیچر تقسیم شود. اگر نمی‌شود، حداقل بخش مشترک را به shared منتقل کنید و مالکیت آن را مشخص کنید.
آیا Feature Based سرعت توسعه را کم می‌کند؟ در ابتدا بله، چون مرزها را باید فکر کنید. اما زمان بازخورد (build و تست) به‌شدت کم می‌شود. در پروژه‌های بلندمدت، سرعت کل بیشتر است.
بهترین ابزار راستی‌آزمایی چیست؟ ArchUnit در تست، برای بررسی خودکار قواعد وابستگی و visibility. مکمل خوبی هم Spring Modulith است که تست ماژول و مستندسازی را خودکار می‌کند.
آیا در اندروید هم کاربرد دارد؟ بله، به‌شکل package-by-feature که در پروژه‌های بزرگ اندروید استاندارد عملی است: feature/order/ شامل UI، ViewModel، Repository و مدل خودش.
چطور فیچرها را با هم ترکیب کنم؟ اگر دو فیچر همیشه با هم تغییر می‌کنند، یک فیچر هستند. اگر فقط گاهی، جدا نگه دارید و با رویداد یا API عمومی وصل کنید.
آیا پوشه‌ی shared اجتناب‌ناپذیر نیست؟ کاملاً می‌توان بدون آن کار کرد، به قیمت تکرار بیشتر. خیلی از تیم‌ها ترجیح می‌دهند فیچرها کاملاً مستقل باشند و هرچه لازم دارند را خودشان داشته باشند.
چگونه تشخیص دهم فیچرهایم بیش از حد بزرگ‌اند؟ وقتی یک پوشه بیش از ۲۰ کلاس دارد، وقتی چند تیم داخل آن کار می‌کنند، یا وقتی تست ماژولش کند است چون همه‌چیز را بالا می‌آورد.
آیا کد نوشتن را سخت‌تر می‌کند؟ اول کمی سخت‌تر است چون باید مرز فیچر را رعایت کنید. اما تغییر دادن کد را به‌مراتب آسان‌تر می‌کند، چون همه‌چیز مربوط در یک جاست.
ارتباطش با Microservices چیست؟ Feature Based پیش‌نیاز آن است. اگر نمی‌توانید کدتان را در یک فرایند به ماژول‌های مستقل تقسیم کنید، به میکروسرویس مهاجرت نکنید — شکست می‌خورید.
آیا می‌توانم ترکیبی از لایه و فیچر داشته باشم؟ در حین مهاجرت، بله و این طبیعی است. حالت پایدار بهتر است یکی از دو باشد؛ ساختار نیمه‌کاره از هر دو بدتر است.
مهم‌ترین توصیه برای شروع چیست؟ فقط پوشه‌بندی را انجام دهید، بدون قوانین سخت. این کم‌ریسک‌ترین قدم با بیشترین فایده است. اگر جواب داد، قدم بعدی را بردارید.
اگر تیمم مقاومت می‌کند چه کنم؟ مسئله را با عدد نشان دهید، نه با نظر: زمان merge conflict، زمان تست، و زمان onboarding را قبل و بعد اندازه بگیرید. مقاومت معمولاً از ترس تغییر است، نه از بی‌اعتمادی به فناوری.

جمع‌بندی

Feature Based Architecture ساده‌ترین معماری این سری با بیشترین بازده عملی است. بدون نیاز به دانش دامنه، بدون ابزار پیچیده، و بدون هزینه‌ی زیرساخت.

بیشترین ارزش آن در یک جمله خلاصه می‌شود: کد یک قابلیت باید در یک جا باشد. این جمله ساده، زمان تحویل، تعداد conflict، سرعت تست و زمان onboarding را به‌شدت کم می‌کند.

پیام پایانی سری ۱۴ مقاله‌ای این مقاله یازدهمین عضو سری «معماری‌های نرم‌افزاری» است. اکنون الگوهای رابط کاربری (MVC، MVP، MVVM، MVI)، الگوهای معماری (Clean، Onion، Hexagonal، Layered، Repository، DDD) و ساختار کد (Feature Based) را پوشش داده‌اید. در ادامه سری به معماری‌های توزیع‌شده می‌رسد: Event-Driven، CQRS و Microservices.
