بهینه‌سازی کارایی سرور؛ از Kernel تا Cache و CDN

کارایی خوب، نتیجه‌ی حدس‌زدن نیست؛ نتیجه‌ی اندازه‌گیری است. در این مقاله از پیدا کردن گلوگاه تا تنظیم Kernel و NGINX، Caching، Compression و CDN را مرور می‌کنیم تا تأخیر کم و Throughput بالا داشته باشید.

بخش ۱مقدمه

کارایی سرور چند بُعد دارد: Throughput (چند درخواست در ثانیه)، Latency (چقدر طول می‌کشد) و Resource Usage (چقدر CPU، RAM، I/O مصرف می‌شود). بهینه‌سازی بدون اندازه‌گیری، معمولاً فقط پیچیدگی اضافه می‌کند.

در این مقاله روش پیدا کردن گلوگاه، تنظیمات Kernel و NGINX، لایه‌های Caching و روش تست بار.
Prerequisites NGINX و Logging, Monitoring و Observability.

بخش ۲اول اندازه‌گیری کن

منبعابزارنشانه‌ی مشکل
CPUtop, vmstatLoad بالا و CPU id کم
حافظهfree, vmstatSwap شدن مکرر
دیسک I/Oiostat, iotopWait بالا (%iowait)
شبکهss, nloadSocketهای TIME_WAIT زیاد
اپلیکیشنAPM / Tracesکوئری کند یا Event Loop قفل
قانون طلایی همیشه قبل و بعد از هر تغییر، عدد بگیرید. اگر بهبود قابل اندازه‌گیری نیست، آن تغییر ارزش هزینه‌ی نگهداری ندارد.

بخش ۴تنظیم Kernel و NGINX

# /etc/sysctl.d/99-tuning.conf
net.core.somaxconn = 65535          # صف اتصال‌های ورودی
net.ipv4.tcp_max_syn_backlog = 65535
net.ipv4.tcp_tw_reuse = 1           # استفاده‌ی مجدد از TIME_WAIT
net.ipv4.ip_local_port_range = 10240 65535
fs.file-max = 2097152               # سقف فایل‌های باز سیستمی
worker_processes auto;              # برابر هسته‌های CPU
worker_rlimit_nofile 65535;

events {
    worker_connections 16384;       # مجموع ≈ processes × connections
    multi_accept on;
    use epoll;
}

http {
    sendfile on;
    tcp_nopush on;
    keepalive_timeout 65;
    keepalive_requests 1000;
    client_body_buffer_size 16k;
    client_header_buffer_size 1k;
    server_tokens off;
}
Expected Behavior با تنظیم درست worker_connections و Kernel، سرور می‌تواند ده‌ها هزار اتصال همزمان را بدون افت مدیریت کند.
محدودیت فایل بدون افزایش nofile (هم در Kernel و هم در systemd)، NGINX به‌سرعت به سقف فایل باز می‌خورد و خطای too many open files می‌دهد.

بخش ۵Cache، Compression و CDN

لایهچه چیزی را کش می‌کند
Browser CacheStatic assets با Cache-Control
CDNمحتوای ثابت نزدیک کاربر
Reverse Proxy Cacheپاسخ‌های پرهزینه (NGINX proxy_cache)
Application Cacheنتیجه‌ی کوئری در Redis
Database CacheBuffer Pool و Query Cache
proxy_cache_path /var/cache/nginx levels=1:2 keys_zone=app_cache:100m
                 max_size=10g inactive=60m use_temp_path=off;

server {
    location /api/ {
        proxy_cache app_cache;
        proxy_cache_valid 200 10s;
        proxy_cache_use_stale error timeout updating;
        add_header X-Cache-Status $upstream_cache_status;
        proxy_pass http://app;
    }
}
Header X-Cache-Status با این هدر می‌بینید پاسخ از HIT آمده یا MISS؛ ابزار خوبی برای تنظیم TTL و درصد کش مفید است.
