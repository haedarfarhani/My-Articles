بخش ۱مقدمه: وقتی همه‌چیز در یک کلاس است

یک کلاس ProductPage را تصور کنید که هم‌زمان: درخواست کاربر را می‌خواند، قیمت را از دیتابیس می‌گیرد، تخفیف را حساب می‌کند و HTML نهایی را با StringBuilder می‌سازد. کار می‌کند؟ بله. خوانا است؟ اصلاً.

مشکل این نیست که کد «کار» نمی‌کند؛ مشکل این است که سه دلیل کاملاً متفاوت برای تغییر دارد. طراح می‌خواهد رنگ دکمه را عوض کند (View)، محصول اضافه کند (Model)، و قوانین تخفیف را به‌روز کند (Business Logic). این سه نگرانی هیچ ارتباطی با هم ندارند، اما در یک فایل زندگی می‌کنند. 

ProductPage.java — وضعیت قبل از MVC:

  public String render(HttpServletRequest req) {
      // ۱) کنترل ورودی
      String id = req.getParameter("id");

      // ۲) دسترسی به داده
      Product p = jdbc.queryForObject("SELECT * FROM products WHERE id=?", Product.class, id);

      // ۳) منطق کسب‌وکار
      if (p.isExpired()) { p.applyDiscount(0.1); }

      // ۴) ساخت نمایش
      return "
" + p.getName() + "
" + p.getPrice() + "";
  }

یک تغییر در View → کل منطق کسب‌وکار در معرض خطر.
یک تغییر در دیتابیس → کل نمایش از کار می‌افتد.
ریشه‌ی مشکل هر سه مسئولیت به هم چسبیده‌اند. MVC با یک ایده‌ی ساده این را حل می‌کند: هر بخش را در یک نقش جدا بگذار و ارتباطشان را از طریق قرارداد مشخص کن.

بخش ۲تاریخچه و دلیل ایجاد

ریشه‌ی MVC به سال ۱۹۷۹ برمی‌گردد؛ زمانی که Trygve Reenskaug در مؤسسه‌ی فناوری نروژ (NTNU) آن را برای یک سیستم تعاملی به نام Smalltalk-80 معرفی کرد. جمله‌ی مشهور او این بود: «MVC یک ابزار برای فکر کردن درباره‌ی طراحی است، نه یک فرمول جادویی.»

بسترچه اتفاقی افتاد؟

دهه‌ی ۱۹۸۰ — Smalltalk و Objective-CMVC به پایه‌ی گرافیک‌های工作站 تبدیل شد

۱۹۹۵ — NeXTSTEP نیز در iOSUIKit و سپس SwiftUI بر همین زبان بصری ساخته شدند
۱۹۹۴ — Strutsنخستین پیاده‌سازی گسترده‌ی MVC در وب

دهه‌ی ۲۰۱۰ — MVVM در WPF و اندرویدبرای پشتیبانی بهتر از داده‌های دوحالته و تست ViewModel
دلیل ایجاد در دهه‌ی ۱۹۷۰ سیستم‌های گرافیکی با چند پنجره و کنترل هم‌زمان ساخته می‌شدند و مدیریت وضعیت آن‌ها عملاً غیرممکن شده بود. MVC ایده‌ی «مدیریت از طریق رویداد» را معرفی کرد: کاربر رویدادی می‌زند، Controller تصمیم می‌گیرد، Model وضعیت را به‌روز می‌کند و View دوباره رسم می‌شود.

بخش ۳MVC چیست؟ (تعریف دقیق)

تعریف رسمی MVC یک الگوی معماری است که برنامه را به سه نقش مجزا تقسیم می‌کند: Model (داده و قواعد کسب‌وکار)، View (نمایش) و Controller (ورودی کاربر و انتخاب پاسخ). این سه بخش از طریق رویداد و اشاره‌گر به داده با هم ارتباط دارند و هر بخش را می‌توان مستقل تست و تعویض کرد.
نقشمسئولیتنمونه
Modelنگه‌داری داده، وضعیت و قواعد کسب‌وکارProduct، Cart، User
Viewنمایش داده به کاربر؛ بدون منطق کسب‌وکارفایل Thymeleaf، RecyclerView.Adapter، Razor
Controllerدریافت رویداد، انتخاب Model و View مناسب@Controller، ProductController
سوءتفاهم رایج MVC یک الگو است، نه یک معماری کامل. MVC درباره‌ی «چگونه یک صفحه کار می‌کند» صحبت می‌کند، نه درباره‌ی «چگونه کل سیستم میان سرویس‌ها تقسیم می‌شود». یک سیستم بزرگ می‌تواند معماری میکروسرویسی داشته باشد و درون هر سرویس از MVC استفاده کند.

بخش ۴مشکل قبل از استفاده

public class ProductServlet extends HttpServlet {

    // همه‌چیز در یک کلاس: Model + View + Controller
    protected void doGet(HttpServletRequest req, HttpServletResponse resp)
            throws IOException {
        String id = req.getParameter("id");
        Connection conn = DriverManager.getConnection(DB_URL);
        Product product = null;

        PreparedStatement ps = conn.prepareStatement(
                "SELECT id, name, price FROM products WHERE id = ?");
        ps.setString(1, id);
        ResultSet rs = ps.executeQuery();
        if (rs.next()) {
            product = new Product(rs.getString("id"),
                    rs.getString("name"),
                    rs.getBigDecimal("price"));
        }

        if (product.getPrice().compareTo(new BigDecimal("1000000")) > 0) {
            product.applyDiscount(new BigDecimal("0.15"));
        }

        resp.setContentType("text/html;charset=UTF-8");
        resp.getWriter().print("<html><h1>" + product.getName()
                + "</h1><p>" + product.getPrice() + "</p></html>");
    }
}

بخش ۵ایده اصلی: سه نقش مجزا

سه اصل بنیادین MVC ۱) جدایی مسئولیت — هر نقش یک دلیل برای تغییر دارد.
۲) جریان رویدادمحور — View رویداد را به Controller می‌دهد، Controller Model را تغییر می‌دهد.
۳) اشاره‌گر به داده — Model مستقیماً View را باخبر می‌کند و Controller در مسیر نیست.
مهم‌ترین نکته‌ی MVC پیکان Model → View یعنی Model، View را می‌شناسد و به آن اطلاع می‌دهد. در MVC کلاسیک (مانند Smalltalk و ASP.NET) این پیکان وجود دارد؛ در بسیاری از پیاده‌سازی‌های امروزی این پیکان حذف شده است و به آن‌ها MVP یا MVVM می‌گویند.

سه نقش و دقیقاً کاری که هرکدام انجام می‌دهند:

مرز درست را نگه دارید View فقط باید نمایش بدهد. اگر داخل قالب بنویسید if (user.isVip()) price = price * 0.9، منطق کسب‌وکار را به سمت نمایش برده‌اید و MVC شکسته است.

بخش ۷جریان داده (Data Flow)

چرخه‌ی کامل یک درخواست در MVC:

  ۱) User → View          : یک رویداد تولید می‌کند
  ۲) View → Controller    : رویداد را با اطلاعات لازم ارسال می‌کند
  ۳) Controller → Model   : دستور «این عمل را انجام بده» می‌دهد
  ۴) Model → Database     : در صورت نیاز داده را می‌خواند/می‌نویسد
  ۵) Model → Model        : قواعد کسب‌وکار را اعمال می‌کند
  ۶) Model → View         : وضعیت جدید را اعلام می‌کند
  ۷) View → User          : نتیجه را نمایش می‌دهد

نکته: Controller در گام ۶ دخالتی ندارد. این همان تفاوت اصلی MVC با MVP است.
قانون جریان یک‌طرفه داده هرگز نباید از View به Model به‌صورت مستقیم برود. همیشه مسیر View → Controller → Model را حفظ کنید تا اعتبارسنجی حذف نشود.

بخش ۹مثال عملی کامل: فروشگاه اینترنتی

  • کاربر فهرست محصولات را می‌بیند و یک محصول را به سبد اضافه می‌کند.
  • سیستم موجودی را بررسی و قیمت را از دیتابیس می‌خواند.
  • تخفیف اعمال و مجموع سبد محاسبه می‌شود.
  • سبد به‌روزرسانی شده نمایش داده می‌شود.
سناریو: کاربر محصول ۵ را به سبد اضافه می‌کند

  Controller: CartController.addToCart(productId = "5")
      ↓
  Model: Cart.add(Product)
      ├─ قاعده: اگر موجودی کافی نبود → StockException
      ├─ قاعده: بیش از ۱۰ قلم یک محصول → محدودیت
      └─ نتیجه: مجموع سبد به‌روز شد
      ↓
  View: CartView دوباره رسم می‌شود (سبد جدید + پیام خطا در صورت شکست)

نکته: Controller هیچ if مربوط به موجودی ندارد.
تمام قواعد در Model (Cart) زندگی می‌کنند.
نمونه‌ی اشتباه رایج اگر CartController خودش بررسی کند «آیا موجودی هست؟»، یک بار در Controller و یک بار در Model این قانون نوشته می‌شود. به این می‌گویند تکرار منطق و در بلندمدت دو نسخه‌ی ناسازگار از قانون خواهید داشت.

بخش ۱۰پیاده‌سازی کد با Java 21

بخش Model

package com.app.shop.model;

import java.math.BigDecimal;
import java.util.ArrayList;
import java.util.Collections;
import java.util.List;

/** نقش MODEL: داده + قواعد کسب‌وکار. هیچ وابستگی‌ای به UI یا دیتابیس ندارد. */
public final class Cart {

    private final List<CartLine> lines = new ArrayList<>();
    private final List<CartListener> listeners = new ArrayList<>();
    private BigDecimal total = BigDecimal.ZERO;

    public void add(CartListener listener) {
        listeners.add(listener);
    }

    private void notifyChanged() {
        listeners.forEach(CartListener::onCartChanged);
    }

    /** قانون: حداکثر ۱۰ قلم از هر محصول. */
    private static final int MAX_PER_PRODUCT = 10;

    public void addItem(Product product, int quantity) {
        if (quantity <= 0) {
            throw new IllegalArgumentException("تعداد باید مثبت باشد");
        }
        if (quantity > MAX_PER_PRODUCT) {
            throw new CartLimitException(
                    "حداکثر " + MAX_PER_PRODUCT + " قلم از هر محصول مجاز است");
        }
        if (product.stock() < quantity) {
            throw new StockException("موجودی " + product.name() + " کافی نیست");
        }

        lines.stream()
                .filter(l -> l.productId().equals(product.id()))
                .findFirst()
                .ifPresentOrElse(
                        existing -> lines.set(lines.indexOf(existing),
                                new CartLine(product, existing.quantity() + quantity)),
                        () -> lines.add(new CartLine(product, quantity)));

        recalculate();
        notifyChanged();
    }

    public void removeItem(String productId) {
        boolean removed = lines.removeIf(l -> l.productId().equals(productId));
        if (!removed) {
            throw new CartLineNotFoundException(productId);
        }
        recalculate();
        notifyChanged();
    }

    /** قانون: برای سفارش بالای ۵ میلیون، ۵٪ تخفیف کل. */
    private void recalculate() {
        total = lines.stream()
                .map(CartLine::subtotal)
                .reduce(BigDecimal.ZERO, BigDecimal::add);

        if (total.compareTo(new BigDecimal("5000000")) > 0) {
            total = total.multiply(new BigDecimal("0.95"));
        }
    }

    public BigDecimal total() {
        return total;
    }

    public List<CartLine> lines() {
        return Collections.unmodifiableList(lines);
    }

    public boolean isEmpty() {
        return lines.isEmpty();
    }
}

package com.app.shop.model;

import java.math.BigDecimal;

/** مقدار شیئی: قیمت و موجودی با خود محصول یکی است. */
public record Product(String id, String name, BigDecimal price, int stock) {

    public Product {
        if (price == null || price.signum() < 0) {
            throw new IllegalArgumentException("قیمت نامعتبر است: " + name);
        }
        if (stock < 0) {
            throw new IllegalArgumentException("موجودی نامعتبر است: " + name);
        }
    }
}

بخش Controller

package com.app.shop.controller;

import java.util.List;

/** نقش CONTROLLER: فقط ورودی را می‌گیرد، به Model دستور می‌دهد، خروجی را برمی‌گرداند. */
public class CartController {

    private final ProductRepository productRepository;
    private final Cart cart;

    public CartController(ProductRepository productRepository, Cart cart) {
        this.productRepository = productRepository;
        this.cart = cart;
    }

    public CartView addToCart(String productId, int quantity) {
        Product product = productRepository.findById(productId)
                .orElseThrow(() -> new ProductNotFoundException(productId));

        cart.addItem(product, quantity);

        return CartView.from(cart);
    }

    public CartView removeFromCart(String productId) {
        cart.removeItem(productId);
        return CartView.from(cart);
    }

    public List<ProductView> listProducts(String query) {
        return productRepository.search(query).stream()
                .map(ProductView::from)
                .toList();
    }
}

بخش View

package com.app.shop.controller;

import java.math.BigDecimal;
import java.util.List;
import com.app.shop.model.Cart;

/**
 * نقش VIEW: مدل نمایشی برای قالب. هیچ منطق کسب‌وکاری اینجا نیست،
 * فقط تبدیل داده‌ی Model به ساختار قابل نمایش.
 */
public record CartView(String productId, String title,
                       String formattedTotal, boolean empty) {

    public static CartView from(Cart cart) {
        return new CartView(
                null,
                "سبد خرید شما",
                format(cart.total()),
                cart.isEmpty());
    }

    /** فقط قالب‌بندی نمایشی — نه محاسبه‌ی قیمت. */
    private static String format(BigDecimal amount) {
        return String.format("%,d ریال", amount.longValue());
    }
}
نکته‌ی کلیدی پیاده‌سازی قانون تخفیف در Cart (Model) است، نه در CartView (View). View فقط عدد آماده را می‌گیرد و قالب‌بندی می‌کند. اگر فردا نرخ مالیات عوض شود، فقط Cart تغییر می‌کند و View دست‌نخورده می‌ماند.

بخش ۱۹Testing

خبر خوب: در MVC، Model را می‌توان کاملاً مستقل تست کرد، چون به چیزی جز Repository وابسته نیست. 

package com.app.shop.model;

import java.math.BigDecimal;
import java.util.List;
import org.junit.jupiter.api.DisplayName;
import org.junit.jupiter.api.Test;

import static org.assertj.core.api.Assertions.assertThat;
import static org.assertj.core.api.Assertions.assertThatThrownBy;

class CartTest {

    private final Product laptop = new Product("p-1", "لپ‌تاپ",
            new BigDecimal("25000000"), 5);

    @Test
    @DisplayName("محصول باید به سبد اضافه و مجموع محاسبه شود")
    void addsProductAndCalculatesTotal() {
        Cart cart = new Cart();

        cart.addItem(laptop, 2);

        assertThat(cart.lines()).hasSize(1);
        assertThat(cart.total()).isEqualByComparingTo("50000000");
    }

    @Test
    @DisplayName("خرید بالای ۵ میلیون باید ۵٪ تخفیف بگیرد")
    void appliesBulkDiscount() {
        Cart cart = new Cart();

        cart.addItem(laptop, 1);

        assertThat(cart.total()).isEqualByComparingTo("23750000");
    }

    @Test
    @DisplayName("افزودن بیش از موجودی باید رد شود")
    void rejectsQuantityAboveStock() {
        Cart cart = new Cart();

        assertThatThrownBy(() -> cart.addItem(laptop, 6))
                .isInstanceOf(StockException.class)
                .hasMessageContaining("موجودی");
    }

    @Test
    @DisplayName("حداکثر ۱۰ قلم از هر محصول")
    void rejectsMoreThanTenUnits() {
        Cart cart = new Cart();
        Product abundant = new Product("p-2", "خودکار",
                new BigDecimal("1000"), 100);

        assertThatThrownBy(() -> cart.addItem(abundant, 11))
                .isInstanceOf(CartLimitException.class);
    }

    @Test
    @DisplayName("افزودن همان محصول باید مقدار را جمع کند")
    void mergesSameProduct() {
        Cart cart = new Cart();

        cart.addItem(laptop, 1);
        cart.addItem(laptop, 1);

        assertThat(cart.lines()).hasSize(1);
        assertThat(cart.lines().getFirst().quantity()).isEqualTo(2);
    }
}
نقشروش تستچه چیزی تست می‌شود
ModelUnit خالص با Fake Repositoryتمام قوانین کسب‌وکار — سریع و قطعی
ControllerUnit با Mock Model یا @WebMvcTestنگاشت درخواست به پاسخ
ViewSnapshot / رندر HTMLقالب خروجی نهایی
مزیت عملی MVC تست CartTest بالا به هیچ Spring Context، هیچ دیتابیس و هیچ Mock نیاز ندارد. اجرای کل تست‌ها زیر یک ثانیه طول می‌کشد. این یکی از بزرگ‌ترین دستاوردهای جداسازی نقش‌هاست.

بخش ۲۱مثال در پروژه واقعی

۱) Spring Boot — سیستم مدیریت محتوا

رایج‌ترین کاربرد MVC در دنیای واقعی، وب‌اپلیکیشن‌های Spring MVC است. در این پروژه‌ها Model معمولاً ترکیبی از JPA Entity و Service است، View یک قالب Thymeleaf و Controller یک کلاس با @RequestMapping. نمونه‌های شناخته‌شده مثل پنل‌های مدیریتی داخلی، فروشگاه‌های اینترنتی و سیستم‌های رزرو آنلاین، همگی با همین الگو ساخته شده‌اند و سال‌ها بدون مشکل توسعه یافته‌اند.

۲) Django و Rails — توسعه‌ی سریع وب

در Django، مدل‌ها با ORM خود در فایل models.py تعریف می‌شوند، قالب‌ها در templates/ و توابع نمایش (کنترلرها) در views.py. همین ساختار به تیم‌های کوچک اجازه داده است در چند هفته محصولی کامل بسازند. Rails با قرارداد Model-View-Controller و ActiveRecord همین الگو را با کمترین کد ممکن پیاده کرده است.

۳) ASP.NET Core MVC — سیستم‌های سازمانی مایکروسافتی

در ASP.NET Core MVC، کنترلرها از IActionResult استفاده می‌کنند و قالب‌های Razor دارای View Tag Helper هستند. مدل داده با Entity Framework مدیریت می‌شود و قوانین کسب‌وکار در سرویس‌های جدا قرار می‌گیرند. این ترکیب در سامانه‌های بانکی و بیمه‌ای رایج است.

۴) اپلیکیشن اندروید با معماری MVC کلاسیک

در سال‌های اولیه‌ی اندروید، Activity نقش View و Controller را همزمان بر عهده می‌گرفت و منطق در آن کلاس‌ها بود. این سبک برای اپلیکیشن‌های ساده مشکلی نداشت، اما با رشد پروژه، به مخلوط‌شدن نقش‌ها رسید؛ همین مسئله دلیل اصلی ظهور MVP و سپس MVVM شد. درس مهم: MVC برای اپلیکیشن‌های کوچک اندروید کار می‌کند، اما به‌سرعت به مرز خود می‌رسد.

۵) پنل‌های مدیریت داخلی

داشبوردهای داخلی بهترین نمونه‌ی MVC هستند: چند فرم ساده، جدول‌های خواندنی و عملیات CRUD. در این پروژه‌ها معمولاً Domain پیچیده نیست و MVC با کمترین کد ممکن همه‌ی نیازها را پوشش می‌دهد. برای همین استفاده از معماری‌های سنگین‌تر، فقط هزینه‌ی بی‌دلیل است.

بخش ۲۳۲۰ سؤال مصاحبه

سطح Junior
سؤال ۱ — MVC چیست؟ الگوی معماری که برنامه را به سه نقش تقسیم می‌کند: Model (داده و منطق)، View (نمایش) و Controller (ورودی و تصمیم‌گیری).
سؤال ۲ — وظیفه‌ی هر نقش چیست؟ Model داده و قوانین را نگه می‌دارد، View خروجی را نمایش می‌دهد، Controller رویدادها را دریافت و به Model فرمان می‌دهد و View مناسب را انتخاب می‌کند.
سؤال ۳ — MVC را چه کسی معرفی کرد؟ Trygve Reenskaug در سال ۱۹۷۹ برای سیستم Smalltalk-80 در دانشگاه NTNU نروژ.
سؤال ۴ — تفاوت MVC و سه‌لایه‌ای چیست؟ سه‌لایه‌ای (3-Tier) درباره‌ی محیط‌های اجرایی صحبت می‌کند (کلاینت، سرور، دیتابیس)؛ MVC درباره‌ی مسئولیت‌های داخل یک برنامه صحبت می‌کند.
سؤال ۵ — تفاوت MVC و لایه‌بندی چیست؟ در لایه‌بندی، بیشتر منطق در یک لایه (Service) متمرکز است. در MVC، منطق درون Model و Controller توزیع می‌شود و View نقشی مستقل دارد.
سؤال ۶ — MVC با چه Frameworkهایی یکپارچه شده است؟ Spring MVC، ASP.NET Core MVC، Rails، Django، Struts، Sinatra و Phoenix.
سؤال ۷ — MVC یک Design Pattern است یا Architecture؟ MVC یک الگو در سطح معماری است؛ یعنی ساختار کلی نرم‌افزار را تعیین می‌کند، نه جزئیات یک کلاس را.
سؤال ۸ — چه چیزی نباید در View باشد؟ منطق کسب‌وکار، دسترسی مستقیم به دیتابیس و تصمیم‌گیری. View فقط باید داده را نمایش دهد و رویداد تولید کند.
سؤال ۹ — Controller باید چه کارهایی انجام ندهد؟ نباید منطق کسب‌وکار بنویسد، نباید مستقیم به دیتابیس وصل شود، و نباید خودش داده را قالب‌بندی کند.
سؤال ۱۰ — تفاوت MVC و MVP چیست؟ در MVC، Model مستقیماً View را صدا می‌زند؛ در MVP، Presenter وضعیت را به View منتقل می‌کند و Model اصلاً از وجود View بی‌خبر است.
سطح Mid
سؤال ۱۱ — MVC کلاسیک با MVC مدرن چه تفاوتی دارد؟ در MVC کلاسیک، Model با استفاده از Observer، View را مستقیم به‌روزرسانی می‌کند. در MVC مدرن (Push/Pull)، Controller یا خودش خروجی View را می‌سازد یا View داده را از Model می‌کشد.
سؤال ۱۲ — مشکل اصلی MVC در اندروید چیست؟ اینکه Activity هم‌زمان نقش View و Controller را بر عهده می‌گیرد و تست واحد آن تقریباً غیرممکن است. به همین دلیل MVP و MVVM جایگزین شدند.
سؤال ۱۳ — چرا برای یک صفحه‌ی ساده MVC استفاده نمی‌کنیم؟ چون برای هر صفحه باید سه کلاس، سه فایل و قرارداد بین آن‌ها بسازید، در حالی که یک تابع ساده همان کار را انجام می‌دهد.
سؤال ۱۴ — چگونه از تکرار منطق جلوگیری کنیم؟ قانون را فقط در Model بنویسید. اگر برای اعتبارسنجی سریع در Controller هم لازم دارید، فقط به متد Model تکیه کنید، نه به بازنویسی قانون.
سؤال ۱۵ — تفاوت MVC و MVVM چیست؟ MVVM برای پلتفرم‌هایی با دوحالته‌سازی داده طراحی شده: ViewModel وضعیت را نگه می‌دارد و تغییرات به‌صورت خودکار به View منعکس می‌شود. MVC این قابلیت را ندارد.
سؤال ۱۶ — چطور Controller را قابل تست کنیم؟ با تزریق وابستگی و Mock کردن Model؛ یا در Spring با تست @WebMvcTest که لایه‌ی داده را کاملاً کنار می‌گذارد.
سؤال ۱۷ — آیا مدل در MVC باید مستقل از دیتابیس باشد؟ در MVC کلاسیک الزامی نیست، اما بهترین حالت این است که مدل دامنه مستقل باشد و مدل ORM جداگانه تعریف شود؛ وگرنه تست و مهاجرت سخت می‌شود.
سؤال ۱۸ — چه زمانی به جای MVC از MVI استفاده کنیم؟ وقتی جریان داده پیچیده است و می‌خواهید همه‌ی تغییرات از یک نقطه (Intent → State) عبور کنند؛ این کار تست، دیباگ و پیش‌بینی رفتار را آسان‌تر می‌کند.
سطح Senior
سؤال ۱۹ — مهم‌ترین محدودیت نظری MVC چیست؟ چرخه‌ی Update در MVC همیشه دردسرساز است: وقتی چند منبع داده با هم تغییر می‌کنند، View نمی‌تواند بفهمد کدام تغییر باید رندر شود. این دلیل اصلی ظهور MVVM و MVI است.
سؤال ۲۰ — MVC در معماری میکروسرویس کجا قرار می‌گیرد؟ MVC در لایه‌ی داخلی هر سرویس قرار می‌گیرد، نه در سطح معماری کلان. معماری کلان را Microservices تعیین می‌کند و MVC فقط نحوه‌ی پیاده‌سازی لایه‌ی ارائه در هر سرویس است.

بخش ۲۴پرسش‌های متداول (FAQ)

پرسش‌های پرتکرار
۱) تفاوت MVC و سه‌لایه‌ای (3-Tier) چیست؟ سه‌لایه‌ای درباره‌ی محل استقرار صحبت می‌کند (کلاینت/سرور/DB)؛ MVC درباره‌ی مسئولیت کد در یک برنامه. یک سیستم می‌تواند هم‌زمان هر دو باشد.
۲) آیا MVC خودش یک لایه‌بندی است؟ می‌توان MVC را نوعی لایه‌بندی دانست، اما تفاوت مهمی دارد: در MVC هر لایه مسئولیت معنایی دارد، در حالی که در لایه‌بندی کلاسیک لایه‌ها صرفاً بر اساس نوع کار تقسیم می‌شوند.
۳) چرا MVC در اندروید منسوخ شد؟ به‌خاطر دو محدودیت: Activity به‌سختی قابل تست است و سیستم بدون چرخه‌ی حیات، MVC را ناکارآمد می‌کند. MVVM این دو مشکل را حل می‌کند.
۴) آیا می‌توان MVC و MVVM را ترکیب کرد؟ بله، و این کار در پروژه‌های واقعی رایج است: لایه‌ی داده با Repository ساختار MVC دارد و لایه‌ی UI با ViewModel به سبک MVVM. در عمل این دو الگو کنار هم کار می‌کنند.
۵) بهترین Framework برای MVC در Java چیست؟ Spring MVC محبوب‌ترین گزینه است، اما Struts و JSF هم وجود دارند. اگر تازه‌کار هستید، Spring به‌دلیل مستندات و اکوسیستم، گزینه‌ی منطقی است.
۶) تفاوت Model و Entity چیست؟ Entity فقط داده را نگه می‌دارد (Getter/Setter)، اما Model می‌تواند شامل قواعد کسب‌وکار، اعلان تغییر و تعامل با دیتابیس باشد.
۷) چرا MVC باعث ساده‌تر شدن کد می‌شود؟ چون هر بخش را جداگانه می‌خوانید و تغییر می‌دهید. به‌جای خواندن یک فایل ۱۰۰۰ خطی، سه فایل کوچک و مشخص دارید.
۸) چطور Controller را نازک نگه داریم؟ با انتقال منطق به یک لایه‌ی Service بین Controller و Model. Controller فقط سه کار می‌کند: دریافت ورودی، صدا زدن Service، برگرداندن خروجی.
۹) آیا MVC برای API هم مناسب است؟ بله، اما در API معمولاً Controller نقش View را هم بر عهده می‌گیرد (چون JSON خروجی است و قالب ثابتی وجود دارد). به همین دلیل بسیاری از REST APIها عملاً از MVC استفاده نمی‌کنند و فقط از لایه‌بندی ساده بهره می‌گیرند.
۱۰) تفاوت MVC و Facade چیست؟ MVC یک الگوی ساختاری برای تقسیم مسئولیت‌ها در کل سیستم است؛ Facade یک الگوی ساختاری برای ساده‌سازی API یک زیرسیستم. Facade ممکن است درون یک لایه‌ی MVC به کار رود.
۱۱) آیا باید برای هر صفحه یک Controller بسازم؟ نه. بهتر است کنترلر را به واحدهایی هم‌اندازه‌ی یک Resource یا Use Case بشکنید و متدهای آن را کوتاه نگه دارید.
۱۲) MVC چه تفاوتی با MVVM در عمل دارد؟ در MVVM، ViewModel یک کلاس کاملاً مستقل و قابل تست است و View فقط به آن گوش می‌دهد. در MVC، View مستقیماً با Model درگیر است و همین، تست را سخت می‌کند.
۱۳) آیا تست View در MVC ارزش دارد؟ معمولاً نه، مگر اینکه قالب پیچیده باشد یا مشکل امنیتی داشته باشد. تست Model و Controller مهم‌تر است؛ تست View معمولاً هزینه‌ی نگهداری بیشتری از ارزش واقعی دارد.
۱۴) چطور از انتقال منطق به View جلوگیری کنم؟ در Code Review، هر شرطی که در قالب نوشته می‌شود را رد کنید. قالب فقط باید حلقه و نمایش داشته باشد؛ تمام تصمیم‌ها باید قبلاً در Model گرفته شده باشند.
۱۵) آیا MVC برای پروژه‌ی دانشگاهی مناسب است؟ بله، دقیقاً برای همین سطح از پروژه‌ها ایده‌آل است: ساختار را آموزش می‌دهد و بدون پیچیدگی اضافه، جداسازی واقعی ایجاد می‌کند.

جمع‌بندی

MVC الگویی است که بیش از چهار دهه عمر دارد و هنوز هم پایه‌ی بیشتر فریم‌ورک‌های وب دنیاست. نکته‌ی مهم این است که MVC را نباید با هر اپلیکیشنی تطبیق داد. این الگو برای صفحات با جریان یک‌طرفه عالی است، اما وقتی وضعیت UI پیچیده می‌شود، MVVM یا MVI انتخاب بهتری هستند.

درس اصلی که از MVC باید بگیرید این است: جدا کردن منطق کسب‌وکار از نمایش، بزرگ‌ترین دستاورد است — حتی اگر خود الگو را کنار بگذارید، این اصل باقی می‌ماند.

پیام پایانی سری ۱۴ مقاله‌ای این مقاله پنجمین عضو سری «معماری‌های نرم‌افزاری» است. اکنون شما هم معماری‌های ساختاری (Clean، Onion، Hexagonal، Layered) را می‌شناسید و هم الگوهای تقسیم مسئولیت (MVC). مقاله‌ی بعدی به MVP می‌پردازد و نشان می‌دهد چرا این الگو برای اپلیکیشن‌های موبایل ساخته شد.
