استقرار سرور با Kubernetes؛ از Pod تا Ingress

Kubernetes پیچیده است، اما دلیلش ساده است: مدیریت خودکار استقرار، مقیاس و بازیابی در مقیاس بزرگ. در این مقاله از مفاهیم پایه — Pod، Deployment و Service — تا Ingress، HPA و Rollout را مرور می‌کنیم.

بخش ۱مقدمه

Kubernetes یک Orchestrator است: به‌جای دستی‌کردن سرورها، فقط «چه می‌خواهیم» را می‌گوییم و Kubernetes تلاش می‌کند واقعیت را با آن هم‌راستا کند (Desired State). این مقاله مفاهیم کلیدی و مسیر استقرار را روشن می‌کند.

در این مقاله معماری Cluster، Pod و Deployment، Service، ConfigMap و Secret، Probes، Ingress و HPA.
Prerequisites استقرار با Docker و High Availability.

بخش ۲معماری Kubernetes

جزءنقش
Control PlaneAPI Server، Scheduler، Controller Manager، etcd
Nodeماشینی که Podها را اجرا می‌کند (kubelet + kube-proxy)
etcdپایگاه کلید-مقدار وضعیت Cluster
CNIشبکه‌ی Podها
Desired State در Kubernetes شما وضعیت مطلوب را توصیف می‌کنید و Controllerها دائماً آن را با وضعیت واقعی مقایسه و اصلاح می‌کنند؛ این «خودترمیمی» قلب این سیستم است.

بخش ۳Pod، Deployment و Service

apiVersion: apps/v1
kind: Deployment
metadata: { name: api }
spec:
  replicas: 3
  selector: { matchLabels: { app: api } }
  template:
    metadata: { labels: { app: api } }
    spec:
      containers:
        - name: api
          image: registry.example.com/app:1.4.2
          ports: [{ containerPort: 8080 }]
---
apiVersion: v1
kind: Service
metadata: { name: api }
spec:
  selector: { app: api }
  ports: [{ port: 80, targetPort: 8080 }]
Expected Behavior Deployment همیشه سه Pod سالم نگه می‌دارد؛ اگر یکی بمیرد، Pod جدید ساخته می‌شود. Service یک آدرس پایدار (api) می‌دهد که پشت آن Podهای گذرا قرار دارند.

بخش ۴ConfigMap، Secret و Probes

apiVersion: v1
kind: ConfigMap
metadata: { name: api-config }
data:
  APP_MODE: "production"
  LOG_LEVEL: "info"
---
apiVersion: v1
kind: Secret
metadata: { name: api-secret }
type: Opaque
stringData:
  DB_PASSWORD: "change-me"
---
# بخشی از Pod spec — Probes
livenessProbe:
  httpGet: { path: /health/live, port: 8080 }
  initialDelaySeconds: 15
  periodSeconds: 10
readinessProbe:
  httpGet: { path: /health/ready, port: 8080 }
  initialDelaySeconds: 5
resources:
  requests: { cpu: "250m", memory: "256Mi" }
  limits:   { cpu: "1",    memory: "512Mi" }
Probeکارکرد
livenessاگر شکست بخورد، Pod دوباره راه‌اندازی می‌شود
readinessاگر شکست بخورد، ترافیک به Pod نمی‌رود
startupبرای اپ‌های کند در شروع
Resource Limits بدون requests/limits، یک Pod می‌تواند منابع بقیه را بخورد و کل Node را بی‌ثبات کند. این تنظیمات اجباری است، نه اختیاری.

بخش ۵Ingress و HPA

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: api-ingress
  annotations:
    cert-manager.io/cluster-issuer: letsencrypt
spec:
  tls:
    - hosts: [api.example.com]
      secretName: api-tls
  rules:
    - host: api.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service: { name: api, port: { number: 80 } }
مؤلفهنقش
Ingressمسیریابی HTTP و TLS در لبه‌ی Cluster
cert-managerگرفتن و تمدید خودکار گواهی
HPAافزایش/کاهش خودکار تعداد Pod بر پایه‌ی متریک

بخش ۶Rollout/Rollback و جمع‌بندی

# استقرار نسخه‌ی جدید (Rolling Update پیش‌فرض)
kubectl set image deployment/api api=registry.example.com/app:1.4.3
kubectl rollout status deployment/api

# بازگشت سریع
kubectl rollout undo deployment/api

# تاریخچه‌ی نسخه‌ها
kubectl rollout history deployment/api
Expected Behavior Kubernetes Podها را تدریجی جایگزین می‌کند و تا آماده‌شدن Pod جدید، ترافیک را به قدیمی‌ها می‌فرستد؛ در صورت خطا، یک دستور Rollback کافی است.
AdvantagesDisadvantages
مقیاس، بازیابی و استقرار خودکارمنحنی یادگیری بالا
Zero-Downtime و Rollback آسانهزینه و پیچیدگی عملیاتی
مستقل از محیط زیرساختبرای پروژه‌های کوچک، Overkill
When to Useسازمان‌هایی با Microservice، نیاز به مقیاس خودکار و تیم DevOps.
When NOT to Useپروژه‌های کوچک تک‌سرویسی؛ Docker Compose یا یک سرور ساده کافی است.

Kubernetes ابزار قدرتمندی برای مدیریت استقرار در مقیاس است. اگر مفاهیم Pod، Service و Deployment را بفهمید، بقیه‌ی اکوسیستم بر پایه‌ی همین‌ها ساخته می‌شود.
