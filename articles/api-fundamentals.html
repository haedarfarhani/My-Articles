بخش ۱مقدمه و اهداف یادگیری

تا حالا برایتان پیش آمده که در یک اپلیکیشن دکمه‌ی «ورود» را بزنید و در همان لحظه عکس پروفایل، نام و فهرست اعلان‌هایتان بارگذاری شود؟ این یعنی اپ شما با سرور حرف زده است. اما دقیقاً چطور؟ با چه زبانی؟ چه چیزی فرستاده و چه چیزی برگشته است؟

پاسخ همه‌ی این پرسش‌ها یک کلمه است: API. این مقاله نقطه‌ی شروع سری API و ارتباطات است و برخلاف بقیه‌ی مقاله‌های این سری، فرض نمی‌کند که چیزی را از قبل بلدید.

اهداف یادگیری

بعد از خواندن این مقاله قادر خواهید بود:

  1. API، کلاینت، سرور، نقطه‌ی پایانی و URI را از هم تفکیک کنید
  2. یک درخواست و پاسخ را خط‌به‌خط بخوانید
  3. متدهای HTTP و معنای «امن» (Safe) و «ایدمپوتنت» بودن هرکدام را توضیح دهید
  4. کد وضعیت مناسب برای هر وضعیت را انتخاب کنید
  5. تفاوت احراز هویت با مجوزدهی را با مثال بیان کنید
  6. تأثیر ایدمپوتنت بودن و کش را روی طراحی API بسنجید
یک تذکر مهم درباره‌ی اصطلاحات در این سری، «API»، «سبک معماری» و «پروتکل» را یکی نمی‌گیریم. REST یک سبک معماری است، SOAP یک پروتکل پیام‌رسانی، رویدادمحور (Event-Driven) یک سبک معماری، و WebSocket یک پروتکل ارتباطی. بهتر است از همین ابتدا این مرزبندی را در ذهن نگه دارید — در مقاله‌ی مقایسه‌ی API ها به‌تفصیل بررسی می‌کنیم.

بخش ۲API چیست؟ و اصطلاحات کلیدی

تعریف

رابط برنامه‌نویسی (API — Application Programming Interface) قراردادی است که مشخص می‌کند دو برنامه چطور با هم ارتباط برقرار کنند: چه درخواستی بپذیرند، چه پاسخی بدهند و با چه قالب داده‌ای.

یک مثال غیردیجیتال: منوی رستوران. شما (کلاینت) منو (قرارداد) را می‌بینید، سفارش می‌دهید (درخواست)، و آشپزخانه (سرور) غذا را آماده و پشت پیشخوان تحویل می‌دهد (پاسخ). شما هرگز داخل آشپزخانه نمی‌روید — و این دقیقاً مزیت API است: پنهان کردن پیچیدگی پشت یک مرز مشخص.

واژه‌نامه‌ی پایه

🖥️

کلاینت (Client)

طرفی که درخواست را آغاز می‌کند و منتظر پاسخ می‌ماند: مرورگر، اپ موبایل، اپ دسکتاپ یا حتی یک سرویس دیگر.

⚙️

سرور (Server)

طرفی که درخواست را پردازش می‌کند، به داده دسترسی دارد و پاسخ را برمی‌گرداند.

📮

نقطه‌ی پایانی (Endpoint)

نشانی مشخصی که درخواست‌ها را می‌پذیرد؛ معمولاً ترکیب متد و مسیر، مثلاً GET /api/users/42.

🔗

URI / URL

URI شناسه‌ی یکتاست؛ URL نشانی‌ای است که علاوه بر شناسه، محل دسترسی را هم مشخص می‌کند.

📨

درخواست (Request)

چهار جزء دارد: خط شروع (متد و مسیر)، هدرها، خط خالی و بدنه.

📥

پاسخ (Response)

شامل کد وضعیت، هدرها و بدنه (معمولاً با قالب JSON).

سه موج فکری

موج اول (RPC) فکر می‌کرد دو سیستم باید مانند فراخوانی تابع محلی با هم حرف بزنند — XML-RPC و بعد SOAP حاصل آن‌اند. موج دوم (منبع‌محور) گفت: بیایید منابع را با URI شناسایی کنیم و با HTTP روی آن‌ها عمل کنیم — REST اینجا متولد شد. موج سوم (پرس‌وجومحور) پرسید: اگر کلاینت دقیقاً همان چیزی را که می‌خواهد بگوید، چه؟ — GraphQL محصول همین پرسش است.

نکته‌ی مهم API خودِ «فراخوانی از راه دور» نیست؛ قرارداد است. یک تابع کتابخانه‌ای هم یک API است. پس اول بپرسید مشکل چیست — شاید پاسخ یک API توزیع‌شده نباشد.

بخش ۵جریان داده و پروتکل HTTP

HTTP در لایه‌ی کاربرد، یک پروتکل متنی و بدون حالت (Stateless) بر پایه‌ی الگوی درخواست/پاسخ است. هر ارتباط یک درخواست دارد و یک پاسخ؛ سرور هیچ حافظه‌ای از درخواست پیشین نگه نمی‌دارد، مگر آنکه خودش عمداً چیزی ذخیره کند.

ساختار یک پیام HTTP

Host: api.example.com

Authorization: Bearer eyJhbGciOi...
User-Agent: MyApp/2.1

──── Response ────
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
Cache-Control: private, max-age=60
ETag: "a1b2c3"

{
  "id": 42,
  "name": "Ali",
  "email": "ali@example.com"

Blank Lineخط خالی: جداکننده‌ی هدر از بدنههمیشه

نسخه‌های HTTP — و اینکه چرا مهم‌اند

نسخهویژگی کلیدیاثر روی API
HTTP/1.1یک اتصال = یک درخواستِ منتظر (keep-alive با صف)Head-of-line blocking؛ چند درخواست هم‌زمان نیاز به چند اتصال دارد
HTTP/2ارسال هم‌زمان چند جریان روی یک اتصال (multiplexing) + فشرده‌سازی هدرچند درخواست هم‌زمان روی یک اتصال TCP؛ مناسب منابع زیاد
HTTP/3بر پایه‌ی QUIC روی UDP؛ بدون وابستگی به TCPمقاوم‌تر در برابر از دست رفتن بسته و شبکه‌های موبایل
دقت در بیان مزیت HTTP/2 و HTTP/3 را با اندازه‌گیری روی سیستم خودتان بسنجید. تغییر نسخه‌ی پروتکل تنها یکی از عوامل است؛ اندازه‌ی پاسخ، تعداد round-trip ها و زمان پردازش سرور اغلب تأثیر بزرگ‌تری دارند.

بخش ۷کد وضعیت و مدیریت خطا

کد وضعیت (Status Code) مهم‌ترین سیگنال قرارداد میان کلاینت و سرور است. انتخاب غلط آن، حتی وقتی بدنه‌ی پاسخ درست باشد، کلاینت را به بیراهه می‌برد.

  • Broken Authentication — توکن بدون انقضا، رمز ضعیف، یا نبود محدودیت تلاش.
  • Mass Assignment — کلاینت فیلدی مثل role=admin را در بدنه می‌فرستد و سرور بی‌چون‌وچرا آن را اعمال می‌کند.
  • Excessive Data Exposure — برگرداندن کل رکورد دیتابیس به‌جای حداقل فیلدهای لازم.
  • Lack of Resources & Rate Limiting — یک نقطه‌ی پایانی گران‌قیمت بدون سقف، قابل سوءاستفاده است.

/**
 * پاسخ خطای یکنواخت — بدون نشت اطلاعات داخلی.
 * هرگز پیام استثنای واقعی را به Client نمی‌فرستیم.
 */
@RestControllerAdvice
public class ApiExceptionHandler {

    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<Map<String, Object>> handleValidation(
            MethodArgumentNotValidException ex, HttpServletRequest req) {

        List<Map<String, String>> errors = ex.getBindingResult().getFieldErrors().stream()
                .map(f -> Map.of(
                        "field",   f.getField(),
                        "message", f.getDefaultMessage() == null ? "invalid" : f.getDefaultMessage()))
                .toList();

        return ResponseEntity.status(HttpStatus.UNPROCESSABLE_ENTITY).body(Map.of(
                "status",    422,
                "error",     "Unprocessable Entity",
                "message",   "Validation failed",
                "errors",    errors,
                "path",      req.getRequestURI(),
                "timestamp", Instant.now().toString()));
    }

    @ExceptionHandler(IllegalArgumentException.class)
    public ResponseEntity<Map<String, Object>> handleBadRequest(
            IllegalArgumentException ex, HttpServletRequest req) {
        return ResponseEntity.badRequest().body(Map.of(
                "status",  400,
                "error",   "Bad Request",
                "message", "ورودی نامعتبر است",
                "path",    req.getRequestURI()));
    }
}

بدون حالت (Stateless)

هر درخواست باید خودبسنده باشد: هر اطلاعاتی که سرور برای پردازش لازم دارد، باید در همان درخواست (معمولاً در توکن یا هدر) حمل شود. مزیت: مقیاس‌پذیری و بازیابی آسان. هزینه: کمی متادیتای اضافه در هر درخواست.

package com.example.api.user;

import jakarta.validation.Valid;
import jakarta.validation.constraints.Email;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.Size;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;

import java.net.URI;
import java.time.Instant;
import java.util.List;
import java.util.Map;
import java.util.Optional;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.atomic.AtomicLong;

@RestController
@RequestMapping("/api/users")
@Validated
public class UserController {

    private final Map<Long, User> store = new ConcurrentHashMap<>();
    private final AtomicLong seq = new AtomicLong(41);

    public UserController() {
        store.put(42L, new User(42L, "Ali", "ali@example.com", true, Instant.now()));
    }

    /* ---------- GET /api/users?role=&page= ---------- */
    @GetMapping
    public List<User> list(@RequestParam(required = false) String q,
                           @RequestParam(defaultValue = "0") int page,
                           @RequestParam(defaultValue = "20") int size) {
        int limit = Math.min(Math.max(size, 1), 100);   // سقف، در برابر سوءاستفاده
        return store.values().stream()
                .filter(u -> q == null || u.name().toLowerCase().contains(q.toLowerCase()))
                .skip((long) page * limit)
                .limit(limit)
                .toList();
    }

    /* ---------- GET /api/users/42 ---------- */
    @GetMapping("/{id}")
    public ResponseEntity<User> get(@PathVariable long id) {
        Optional<User> found = Optional.ofNullable(store.get(id));
        return found.map(ResponseEntity::ok)
                    .orElseGet(() -> ResponseEntity.notFound().build());
    }

    /* ---------- POST /api/users → 201 + Location ---------- */
    @PostMapping
    public ResponseEntity<User> create(@Valid @RequestBody CreateUserRequest req) {
        long id = seq.incrementAndGet();
        User created = new User(id, req.name(), req.email(), true, Instant.now());
        store.put(id, created);
        return ResponseEntity
                .created(URI.create("/api/users/" + id))   // هدر Location
                .body(created);
    }

    /* ---------- PUT /api/users/42 (idempotent) ---------- */
    @PutMapping("/{id}")
    public ResponseEntity<User> replace(@PathVariable long id,
                                        @Valid @RequestBody CreateUserRequest req) {
        if (!store.containsKey(id)) return ResponseEntity.notFound().build();
        User updated = new User(id, req.name(), req.email(), true, Instant.now());
        store.put(id, updated);                            // تکرار = همان وضعیت
        return ResponseEntity.ok(updated);
    }

    /* ---------- PATCH /api/users/42 (partial) ---------- */
    @PatchMapping("/{id}")
    public ResponseEntity<User> patch(@PathVariable long id,
                                      @RequestBody Map<String, Boolean> body) {
        User current = store.get(id);
        if (current == null) return ResponseEntity.notFound().build();
        Boolean active = body.get("active");
        if (active == null) {
            throw new IllegalArgumentException("فقط فیلد active قابل تغییر است");
        }
        User updated = current.withActive(active);
        store.put(id, updated);
        return ResponseEntity.ok(updated);
    }

    /* ---------- DELETE /api/users/42 → 204 ---------- */
    @DeleteMapping("/{id}")
    public ResponseEntity<Void> delete(@PathVariable long id) {
        store.remove(id);                                  // تکرار = همان نتیجه
        return ResponseEntity.noContent().build();         // 204 بدون بدنه
    }

    public record CreateUserRequest(
            @NotBlank @Size(min = 2, max = 80) String name,
            @NotBlank @Email String email) { }

    public record User(long id, String name, String email,
                       boolean active, Instant createdAt) {
        User withActive(boolean v) { return new User(id, name, email, v, createdAt); }
    }
}

بخش ۲۱سؤالات مصاحبه

سطح پایه (Junior)

سؤال ۱ — API چیست؟

قراردادی است که مشخص می‌کند دو برنامه چطور با هم ارتباط برقرار کنند: چه درخواستی بپذیرند، چه پاسخی بدهند و با چه قالبی. مثال ساده‌اش منوی رستوران است: شما منو را می‌بینید، سفارش می‌دهید و آشپزخانه غذا را برمی‌گرداند — بدون اینکه وارد آشپزخانه شوید.

سؤال ۲ — تفاوت کلاینت و سرور چیست؟

کلاینت طرفی است که درخواست را آغاز می‌کند (مرورگر، اپ موبایل، سرویس دیگر)؛ سرور طرفی است که درخواست را پردازش می‌کند، به داده دسترسی دارد و پاسخ را برمی‌گرداند. در HTTP همیشه کلاینت اولین قدم را برمی‌دارد.

سؤال ۳ — نقطه‌ی پایانی و نشانی چه فرقی دارند؟

نشانی (URL) یک آدرس کامل است (پروتکل + دامنه + مسیر). نقطه‌ی پایانی (Endpoint) همان نقطه‌ای است که درخواست را می‌پذیرد — معمولاً ترکیب متد و مسیر، مثل GET /api/users/42. هر نقطه‌ی پایانی یک نشانی دارد، ولی هر نشانی لزوماً یک نقطه‌ی پایانی نیست.

سؤال ۴ — تفاوت URI و URL چیست؟

هر URL یک URI است، ولی هر URI لزوماً URL نیست. URI صرفاً شناسه‌ی یکتاست؛ URL علاوه بر شناسه، محل (scheme، host، path) را هم مشخص می‌کند. مثال URI غیر-URL: urn:isbn:978-0132350884.

سؤال ۵ — متدهای اصلی HTTP را نام ببرید و بگویید هرکدام چه می‌کند.

GET خواندن؛ POST ساختن منبع یا اجرای عملیات؛ PUT جایگزینی کامل؛ PATCH تغییر جزئی؛ DELETE حذف. به‌علاوه HEAD (بدون بدنه)، OPTIONS (کاوش) و TRACE (تشخیصی).

سؤال ۶ — PUT و PATCH چه فرقی دارند؟

PUT کل منبع را با بدنه‌ی داده‌شده جایگزین می‌کند؛ فیلدهایی که نفرستید مقدار پیش‌فرض می‌گیرند یا حذف می‌شوند، و به همین دلیل ذاتاً ایدمپوتنت است. PATCH فقط فیلدهای ارسالی را عوض می‌کند و بقیه دست‌نخورده می‌ماند؛ این متد تنها وقتی ایدمپوتنت است که عملیاتش در واقع جایگزینی کامل باشد.

سؤال ۷ — ایدمپوتنت بودن یعنی چه و چرا مهم است؟

یعنی اجرای چندباره‌ی یک درخواست، همان اثرِ یک بار اجرا را دارد. مهم است چون شبکه قطع می‌شود و کلاینت مجبور به تلاش مجدد است؛ بدون ایدمپوتنت بودن، دوباره زدن POST /payments می‌تواند دو بار از حساب کم کند. راه‌حل برای POST هم افزودن Idempotency-Key است.

سؤال ۸ — تفاوت 401 و 403 چیست؟

401 یعنی «نمی‌دانم کی هستی» — توکن نیست یا نامعتبر است. 403 یعنی «می‌دانم کی هستی، ولی اجازه نداری» — هویت درست است ولی مجوز کافی نیست. پاسخ 401 باید هدر WWW-Authenticate داشته باشد.

سؤال ۹ — تفاوت JSON و XML چیست؟

JSON سبک‌تر و خواناتر است و سیستم نوع خفیفی دارد؛ XML با XSD نوع‌دهی قوی، فضای‌نام (namespace) و فراداده دارد، اما پرسروصداتر است. امروزه REST و GraphQL عمدتاً از JSON استفاده می‌کنند و XML بیشتر در SOAP و اسناد سازمانی دیده می‌شود.

سؤال ۱۰ — بدون حالت بودن یعنی چه؟

یعنی سرور وضعیت نشست را میان درخواست‌ها نگه نمی‌دارد؛ هر درخواست باید خودبسنده باشد و هر اطلاعات لازم را حمل کند (معمولاً توکن). مزیتش این است که می‌توانید نمونه‌های بیشتری را بدون پیکربندی خاص اضافه کنید.

سطح متوسط (Mid)

سؤال ۱۱ — چرا GET نباید وضعیت را تغییر دهد؟

چون مرورگرها، کش‌ها و CDN‌ها روی GET حساب می‌کنند که امن و تکرارپذیر است. اگر GET وضعیت را عوض کند، کش می‌تواند نتیجه‌ی کهنه را برگرداند، پیش‌خوان (prefetch) مرورگر می‌تواند بدون اجازه‌ی کاربر عملیات را اجرا کند و پیش‌بینی رفتار غیرممکن می‌شود.

سؤال ۱۲ — مذاکره بر سر قالب (Content Negotiation) چیست؟

توافقی میان کلاینت و سرور درباره‌ی قالب پاسخ، با هدر Accept در درخواست و Content-Type در پاسخ. مثال: Accept: application/xml اگر سرور پشتیبانی کند، پاسخ XML می‌دهد وگرنه ۴۰۶ برمی‌گرداند. در عمل بیشتر API ها فقط JSON را پشتیبانی می‌کنند.

سؤال ۱۳ — HATEOAS چیست و چرا کمتر دیده می‌شود؟

یعنی پاسخ علاوه بر داده، لینک‌های مرتبط را هم برمی‌گرداند تا کلاینت از قبل مسیرها را نداند و از قرارداد پیروی کند. پیاده‌سازی آن هزینه‌ی زیادی دارد و بیشتر تیم‌ها قرارداد ثابت به‌همراه OpenAPI را ترجیح می‌دهند؛ به همین دلیل در عمل، API های REST کمتر اصول HATEOAS را رعایت می‌کنند.

سؤال ۱۴ — اگر کلید ایدمپوتنتی را فراموش کنیم چه می‌شود؟

پس از قطعی، تلاش مجدد کلاینت رکورد تکراری می‌سازد — مثلاً دو بار پرداخت یا دو سفارش. راه‌حل‌های جایگزین: کلید یکتای دامنه‌ای (مثلاً orderId منحصربه‌فرد)، قید یکتای دیتابیس، یا تشخیص تکرار در لایه‌ی دامنه. همه‌ی آن‌ها یک اصل دارند: درخواست باید قابل تشخیص از تکرار باشد.

سؤال ۱۵ — وقتی پاسخ 304 برمی‌گردد چه اتفاقی می‌افتد؟

سرور فهمیده بدنه تغییری نکرده (با If-None-Match و ETag مقایسه کرده) و فقط سربرگ را برمی‌گرداند. کلاینت از کش محلی خودش استفاده می‌کند. نتیجه: بدنه‌ای جابه‌جا نمی‌شود و زمان پاسخ کوتاه‌تر می‌شود، بدون آنکه داده‌ی کهنه‌ای نمایش داده شود.

سؤال ۱۶ — محدودیت نرخ (Rate Limiting) را کجا باید پیاده کرد؟

معمولاً در دروازه (Gateway) یا میدل‌ور لایه‌ی وب، پیش از رسیدن درخواست به منطق دامنه. الگوریتم‌های رایج: Fixed Window (ساده اما دچار سرریز)، Sliding Window (دقیق‌تر)، Token Bucket (موج را می‌پذیرد) و Leaky Bucket (نرخ ثابت). پاسخ باید کد ۴۲۹ به‌همراه هدر Retry-After و هدرهای X-RateLimit-* باشد.

سؤال ۱۷ — اگر نقطه‌ی پایانی چند ثانیه طول بکشد چه کنیم؟

کار را از مسیر پاسخ خارج کنید: 202 Accepted به‌همراه نشانی‌ای برای پیگیری وضعیت، و نتیجه را بعداً با GET، WebSocket، SSE یا Webhook تحویل دهید. علت: محدودیت زمانی مرورگرها و پروکسی‌ها باعث می‌شود اتصال‌های طولانی بسته شوند.

سؤال ۱۸ — CORS چیست و چه زمانی مشکل‌ساز می‌شود؟

سیاستی در مرورگر است که جلوی دسترسی یک دامنه به پاسخ دامنه‌ی دیگر را می‌گیرد. مشکل‌ساز می‌شود وقتی Access-Control-Allow-Origin: * را با Allow-Credentials: true ترکیب کنید (مرورگر رد می‌کند و اگر بی‌اثر بماند، خطر نشت کوکی است) یا وقتی فکر می‌کنید CORS یک مکانیزم امنیتی است — نیست؛ فقط یک قاعده‌ی مرورگری است. کنترل دسترسی باید سمت سرور باشد.

سطح پیشرفته (Senior)

سؤال ۱۹ — اگر دو نقطه‌ی پایانی پاسخ‌های هم‌پوشان بدهند، کدام درست است؟

این پرسش درباره‌ی مالکیت داده است، نه نشانی. قاعده: هر منبع باید یک مالک واحد و یک منبع حقیقت داشته باشد. اگر دو نقطه‌ی پایانی یک داده را از دو منبع مختلف می‌خوانند، دیر یا زود ناسازگار می‌شوند. پاسخ درست: منبع حقیقت را مشخص کنید و بقیه را یا حذف کنید یا صریحاً به‌عنوان نمای فقط‌خواندنی (projection) با تاریخ انقضای روشن نام‌گذاری کنید.

سؤال ۲۰ — طراحی API چند مصرف‌کننده‌ی با نیاز متضاد را چطور مدیریت می‌کنید؟

سه گزینه دارید و باید هزینه‌ی هرکدام را بسنجید: ۱) پارامترهای انتخابی مثل fields و expand — انعطاف‌پذیر، ولی قرارداد را پیچیده می‌کند؛ ۲) نسخه‌های مجزا یا BFF برای هر کلاینت — تمیز، ولی چندپاره؛ ۳) GraphQL که خود کلاینت شکل پاسخ را تعیین می‌کند — اما هزینه‌ی امنیت و کش را بالا می‌برد. انتخاب درست به تعداد مصرف‌کننده‌ها، میزان تفاوت نیاز آن‌ها و توان نگهداری تیم بستگی دارد.

بخش ۲۲پرسش‌های متداول (FAQ)

آیا هر API یک وب سرویس است؟

خیر. وب سرویس زیرمجموعه‌ای از API است که از راه شبکه (معمولاً HTTP) در دسترس است. یک کتابخانه‌ی جاوا هم API است، ولی وب سرویس نیست.

آیا REST همان HTTP است؟

نه. HTTP یک پروتکل انتقال است و REST یک سبک معماری مبتنی بر چند محدودیت (کلاینت–سرور، بدون حالت، رابط یکنواخت و کش‌پذیری) است. یک API می‌تواند روی HTTP کار کند ولی REST نباشد.

آیا یک API فقط JSON تولید می‌کند؟

نه. JSON پرکاربردترین است، ولی XML، YAML، قالب‌های باینری (Protobuf، MessagePack)، HTML و حتی فایل (PDF، تصویر) هم ممکن است. تعیین‌کننده، هدر Content-Type و مذاکره بر سر قالب با Accept است.

API Key و Token چه فرقی دارند؟

API Key یک رشته‌ی ثابت و معمولاً بلندعمر است که بیشتر برای شناسایی سرویس در ارتباط سروربه‌سرور (Server-to-Server) به کار می‌رود. توکن (مثل JWT) اغلب کوتاه‌عمر، دارای ادعا (claims) و قابل لغو است و برای نمایندگی از هویت کاربر مناسب‌تر است.

چرا پاسخ من همیشه از کش می‌آید و داده‌ی تازه نمی‌بینم؟

به احتمال زیاد Cache-Control را عمداً یا سهواً public, max-age=… گذاشته‌اید، یا CDN کش را خالی (purge) نمی‌کند. برای داده‌ی شخصی از private، برای داده‌ی حساس از no-store و برای داده‌ای که باید تازه باشد اما کش شود، از ETag همراه max-age کوتاه استفاده کنید.

بهترین کد وضعیت برای «حذف موفق» کدام است؟

204 No Content. منبع حذف شده و چیزی برای نمایش نمانده. اگر بدنه‌ای مثل تأیید یا آمار لازم دارید، 200 با بدنه بفرستید — مهم این است که کلاینت بتواند تفاوت را تشخیص دهد.

تعداد زیاد درخواست کوچک بدهم یا یک درخواست بزرگ؟

به تعداد رفت‌وبرگشت‌های شبکه نگاه کنید. در حالت کلی، تجمیع سریع‌تر است، چون هر رفت‌وبرگشت هزینه‌ی ثابتی دارد. اما اگر یکی از آیتم‌ها خطا داشته باشد، کل درخواست بزرگ یکجا رد می‌شود؛ پس برای عملیات‌های حساس، batch با پاسخ جزئی بهتر است.

مستندات API را کجا و چطور نگه داریم؟

نزدیک‌ترین راه به کد: OpenAPI که از کد یا annotation تولید شود تا با هر تغییر به‌روز شود. سپس Swagger UI یا ReDoc برای نمایش، و تست قرارداد برای اطمینان از سازگاری. جزئیات در مقاله‌ی مستندسازی.

آیا باید برای هر Entity یک نقطه‌ی پایانی بسازم؟

نه لزوماً. منطق طراحی بر اساس منابع و رفتار معنایی است، نه جدول دیتابیس. گاهی یک منبع چند جدول را در بر می‌گیرد و گاهی یک جدول چند منبع می‌دهد. اگر نام نقطه‌ی پایانی از نام جدول آمده باشد، سیگنال هشدار است.

چه زمانی نسخه‌ی جدید بدهم؟

فقط برای تغییر شکننده: حذف فیلد، تغییر نوع، تغییر معنای فیلد یا تغییر کد وضعیت. افزودن فیلد اختیاری یا افزودن نقطه‌ی پایانی جدید شکننده نیست. جزئیات کامل در مقاله‌ی نسخه‌بندی.

خطا را کجا لاگ کنم؟

در سمت سرور، با یک traceId که در همه‌ی سرویس‌ها منتقل شود و در پاسخ هم دیده شود تا کاربر بتواند آن را گزارش دهد. لاگ باید ساختاریافته (JSON) و بدون رمز عبور، توکن یا داده‌ی شخصی باشد.

آیا درخواست‌های تکراری از سمت کلاینت ایراد دارد؟

خیر — تکرار نشانه‌ی شبکه‌ی ناپایدار یا خطای کلاینت است. آنچه ایراد دارد، ناتوانی سرور در مدیریت آن است: باید Idempotency-Key، کش و محدودیت نرخ داشته باشید تا تکرار هم امن و هم ارزان بماند.

بخش ۲۳جمع‌بندی و مقالات مرتبط

آنچه باید از این مقاله با خود ببرید

API یک قرارداد است، نه یک کتابخانه. اگر فقط چهار چیز را به یاد بماند، همین‌هاست:

  • متد درست — «امن» (Safe) و ایدمپوتنت بودن را جدی بگیرید؛ کش‌ها و کلاینت‌ها روی آن حساب می‌کنند.
  • کد وضعیت درست — برای خطا ۲۰۰ ندهید؛ ۴۰۱ و ۴۰۳ را قاطی نکنید.
  • کلید یکتا — هر عملیاتی که پول یا داده‌ی حساس را لمس می‌کند باید Idempotency-Key داشته باشد.
  • حداقل داده — کمترین فیلدهای لازم، صفحه‌بندی با سقف، و Cache-Control آگاهانه.

بقیه‌ی چیزها — GraphQL، gRPC، WebSocket، Webhook — فقط همین چهار اصل را در شرایط مختلف به کار می‌گیرند. اگر این چهار مورد را بفهمید، یادگیری بقیه‌ی این سری خیلی سریع‌تر می‌شود.
