بخش ۱مقدمه و اهداف یادگیری

تا حالا برایتان پیش آمده که در یک اپلیکیشن دکمه‌ی «ورود» را بزنید و در همان لحظه عکس پروفایل، نام و فهرست اعلان‌هایتان بارگذاری شود؟ این یعنی اپ شما با سرور حرف زده. اما دقیقاً چطور؟ با چه زبانی؟ چه چیزی فرستاده و چه چیزی برگشته است؟

پاسخ همه‌ی این پرسش‌ها یک کلمه است: API. این مقاله نقطه‌ی شروع سری API و ارتباطات است و بر خلاف بقیه‌ی مقالات‌ها، فرض نمی‌کند که چیزی را از قبل بلدید.

اهداف یادگیری

بعد از خواندن این مقاله قادر خواهید بود:

  1. API، Client، Server، Endpoint و URI را از هم تفکیک کنید
  2. یک Request و Response را خط‌به‌خط بخوانید
  3. متدهای HTTP و معنای Safe/Idempotent هرکدام را توضیح دهید
  4. Status Code مناسب برای هر وضعیت را انتخاب کنید
  5. تفاوت Authentication با Authorization را با مثال بیان کنید
  6. تأثیر Idempotency و Caching را روی طراحی API بسنجید
یک تذکر مهم درباره‌ی اصطلاحات در این سری، «معماری» و «API» و «پروتکل» را با هم قاطی نمی‌کنیم. REST یک سبک API است، SOAP یک پروتکل پیام، Event-Driven یک سبک معماری، و WebSocket یک پروتکل ارتباطی. بهتر است از همین ابتدا این مرزبندی را در ذهن نگه دارید — در مقاله‌ی مقایسه‌ی API ها به‌تفصیل بررسی می‌کنیم.

بخش ۲API چیست؟ و اصطلاحات کلیدی

تعریف

API (Application Programming Interface) قراردادی است که مشخص می‌کند دو برنامه چطور با هم ارتباط برقرار کنند: چه درخواستی بپذیرند، چه پاسخی بدهند و با چه قالبی.

یک مثال غیردیجیتال: منوی رستوران. شما (Client) منو (قرارداد) را می‌بینید، سفارش می‌دهید (Request)، و آشپزخانه (Server) غذا را آماده و پشت پیشخوان تحویل می‌دهد (Response). شما هرگز داخل آشپزخانه نمی‌روید — و این دقیقاً مزیت API است: پنهان کردن پیچیدگی پشت یک مرز مشخص.

واژه‌نامه‌ی پایه

🖥️

Client

طرفی که درخواست می‌فرستد: مرورگر، اپ موبایل، اپ دسکتاپ یا حتی یک سرویس دیگر.

⚙️

Server

طرفی که درخواست را پردازش می‌کند، به داده دسترسی دارد و پاسخ برمی‌گرداند.

📮

Endpoint

یک آدرس مشخص که درخواست‌ها را می‌پذیرد؛ مثلاً GET /api/users/42.

🔗

URI / URL

URI شناسه‌ی یکتاست؛ URL زیرمجموعه‌ی URI است که محل را هم مشخص می‌کند.

📨

Request

چهار جزء دارد: متد، مسیر، هدرها و بدنه.

📥

Response

شامل Status Code، هدرها و بدنه (معمولاً JSON).

بخش ۳چرا API ایجاد شد؟

بدون API، هر برنامه‌ای مجبور بود زبان و ساختار داخلی همتای خودش را بداند. این یعنی کوپل سخت‌افزاری: تغییر در یک طرف، همه‌ی طرف‌های دیگر را می‌شکست.

سه موج فکری

موج اول (RPC) فکر می‌کرد دو سیستم باید مثل فراخوانی تابع محلی حرف بزنند — XML-RPC و بعد SOAP حاصل آن‌اند. موج دوم (Resource-Oriented) گفت: بیایید منابع را با URI شناسایی و با HTTP عمل کنیم — REST اینجا متولد شد. موج سوم (Query-Oriented) پرسید: اگر بگذاریم Client دقیقاً همان چیزی را که می‌خواهد بگوید چه؟ — GraphQL محصول همین پرسش است.

نکته‌ی مهم API خودِ «فراخوانی از راه دور» نیست؛ قرارداد است. یک تابع کتابخانه‌ای هم یک API است. پس اول بپرسید مشکل چیست — شاید پاسخ یک API توزیع‌شده نباشد.

بخش ۵جریان داده و پروتکل HTTP

HTTP یک پروتکل Request/Response، متنی و بدون وضعیت (Stateless) در لایه‌ی برنامه است. هر ارتباط یک درخواست دارد و یک پاسخ؛ سرور هیچ حافظه‌ای از درخواست قبلی نگه نمی‌دارد مگر خودش عمداً چیزی ذخیره کند.

Content-Type: application/json; charset=utf-8

نسخه‌های HTTP — و اینکه چرا مهم‌اند

دقت در بیان مزیت HTTP/2 و HTTP/3 را با اندازه‌گیری روی سیستم خودتان بسنجید. تغییر نسخه‌ی پروتکل تنها یکی از عوامل است؛ اندازه‌ی پاسخ، تعداد round-trip ها و زمان پردازش سرور اغلب تأثیر بزرگ‌تری دارند.

بخش ۷Status Code و مدیریت خطا

کد وضعیت، مهم‌ترین سیگنال قرارداد بین سرور و Client است. انتخاب غلط آن، حتی وقتی بدنه‌ی پاسخ درست باشد، Client را به بیراهه می‌برد.

خطای Client400 – 499درخواست خودتان مشکل دارد400, 401, 403, 404, 409, 422, 429

سه قاعده‌ی طلایی
  • هرگز 200 برای خطا نفرستید — Client ها، کش‌ها و ابزارهای پایش روی کد حساب می‌کنند.
  • 401 با 403 فرق دارد: اولی «کی هستی؟»، دومی «اجازه نداری».
  • جزئیات خطا را محدود کنید: پیام مفید بدهید، ولی stack trace و نام جدول دیتابیس را نه.

                "message",   "Validation failed",

بخش ۱۱Statelessness، Idempotency و Caching

بدون وضعیت (Statelessness)

هر درخواست باید خوداتکا باشد: هر اطلاعاتی که سرور برای پردازش لازم دارد، باید در همان درخواست (معمولاً در توکن یا هدر) حمل شود. مزیت: مقیاس‌پذیری و بازیابی آسان. هزینه: حجم کمی اضافه‌ی متادیتا در هر درخواست.

ایدمپوتنت بودن (Idempotency)

یک عملیات ایدمپوتنت است اگر اجرای آن چند بار، دقیقاً همان اثرِ یک بار اجرا را داشته باشد. این مفهوم به‌خصوص وقتی حیاتی می‌شود که شبکه قطع می‌شود و Client مجبور به تلاش مجدد است.

متدSafeIdempotentتوضیح
GET✅ بله✅ بلهنباید وضعیت را تغییر دهد
HEAD✅ بله✅ بلهمثل GET بدون بدنه
OPTIONS✅ بله✅ بلهکاوش قابلیت‌ها
POST❌ نه❌ نههر بار منبع/عمل جدیدی می‌سازد
PUT❌ نه✅ بلهجایگزینی کامل با همان بدنه = همان وضعیت
PATCH❌ نه⚠️ بستگی داردفقط اگر عملیات جایگزینی باشد
DELETE❌ نه✅ بلهحذف دوباره = منبع از قبل حذف شده
چرا POST ایدمپوتنت نیست؟

POST /orders را دو بار بزنید = دو سفارش ساخته می‌شود. راه‌حل صنعتی، افزودن یک Idempotency-Key است: سرور کلید را ذخیره می‌کند و اگر بار دوم همان کلید آمد، پاسخ قبلی را بدون اجرای دوباره برمی‌گرداند. این دقیقاً همان کاری است که درگاه‌های پرداخت مثل Stripe انجام می‌دهند.

مثال زیر یک endpoint کامل با Spring Boot 3 / Java 21 است: اعتبارسنجی، احراز هویت، پاسخ درست و مدیریت خطا. 

package com.example.api.user;

import jakarta.validation.Valid;
import jakarta.validation.constraints.Email;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.Size;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;

import java.net.URI;
import java.time.Instant;
import java.util.List;
import java.util.Map;
import java.util.Optional;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.atomic.AtomicLong;

@RestController
@RequestMapping("/api/users")
@Validated
public class UserController {

    private final Map<Long, User> store = new ConcurrentHashMap<>();
    private final AtomicLong seq = new AtomicLong(41);

    public UserController() {
        store.put(42L, new User(42L, "Ali", "ali@example.com", true, Instant.now()));
    }

    /* ---------- GET /api/users?role=&page= ---------- */
    @GetMapping
    public List<User> list(@RequestParam(required = false) String q,
                           @RequestParam(defaultValue = "0") int page,
                           @RequestParam(defaultValue = "20") int size) {
        int limit = Math.min(Math.max(size, 1), 100);   // سقف، در برابر سوءاستفاده
        return store.values().stream()
                .filter(u -> q == null || u.name().toLowerCase().contains(q.toLowerCase()))
                .skip((long) page * limit)
                .limit(limit)
                .toList();
    }

    /* ---------- GET /api/users/42 ---------- */
    @GetMapping("/{id}")
    public ResponseEntity<User> get(@PathVariable long id) {
        Optional<User> found = Optional.ofNullable(store.get(id));
        return found.map(ResponseEntity::ok)
                    .orElseGet(() -> ResponseEntity.notFound().build());
    }

    /* ---------- POST /api/users → 201 + Location ---------- */
    @PostMapping
    public ResponseEntity<User> create(@Valid @RequestBody CreateUserRequest req) {
        long id = seq.incrementAndGet();
        User created = new User(id, req.name(), req.email(), true, Instant.now());
        store.put(id, created);
        return ResponseEntity
                .created(URI.create("/api/users/" + id))   // هدر Location
                .body(created);
    }

    /* ---------- PUT /api/users/42 (idempotent) ---------- */
    @PutMapping("/{id}")
    public ResponseEntity<User> replace(@PathVariable long id,
                                        @Valid @RequestBody CreateUserRequest req) {
        if (!store.containsKey(id)) return ResponseEntity.notFound().build();
        User updated = new User(id, req.name(), req.email(), true, Instant.now());
        store.put(id, updated);                            // تکرار = همان وضعیت
        return ResponseEntity.ok(updated);
    }

    /* ---------- PATCH /api/users/42 (partial) ---------- */
    @PatchMapping("/{id}")
    public ResponseEntity<User> patch(@PathVariable long id,
                                      @RequestBody Map<String, Boolean> body) {
        User current = store.get(id);
        if (current == null) return ResponseEntity.notFound().build();
        Boolean active = body.get("active");
        if (active == null) {
            throw new IllegalArgumentException("فقط فیلد active قابل تغییر است");
        }
        User updated = current.withActive(active);
        store.put(id, updated);
        return ResponseEntity.ok(updated);
    }

    /* ---------- DELETE /api/users/42 → 204 ---------- */
    @DeleteMapping("/{id}")
    public ResponseEntity<Void> delete(@PathVariable long id) {
        store.remove(id);                                  // تکرار = همان نتیجه
        return ResponseEntity.noContent().build();         // 204 بدون بدنه
    }

    public record CreateUserRequest(
            @NotBlank @Size(min = 2, max = 80) String name,
            @NotBlank @Email String email) { }

    public record User(long id, String name, String email,
                       boolean active, Instant createdAt) {
        User withActive(boolean v) { return new User(id, name, email, v, createdAt); }
    }
}

بخش ۱۷چه زمانی استفاده کنیم؟

  • چند مصرف‌کننده‌ی متفاوت دارید — وب، موبایل، دسکتاپ یا سرویس داخلی از یک قرارداد مشترک استفاده کنند.

  • تیم‌ها باید مستقل کار کنند — قرارداد مشخص، هماهنگی را حذف می‌کند.
  • قابلیت استقرار مستقل لازم است — به‌روزرسانی Client بدون استقرار سرور و بالعکس.
  • داده را با شرکا یا سیستم‌های بیرونی به اشتراک می‌گذارید — تنها راه عملی.
  • می‌خواهید قابلیت را مرحله‌به‌مرحله عرضه کنید — نسخه‌بندی و feature flag پشت API.
  • نیاز به اندازه‌گیری دارید — متریک روی endpoint ها دقیق‌تر از متریک روی توابع داخلی است.
نشانه‌ی آمادگی اگر دو یا چند مورد بالا را دارید و قرارداد روشنی می‌توانید بنویسید — بروید جلو. اگر فقط یک مورد دارید، اول ساده‌ترین شکل ممکن را بسازید و API را زمانی اضافه کنید که واقعاً لازم شد.

بخش ۱۸چه زمانی استفاده نکنیم؟

موقعیت‌هایی که API گزینه‌ی درستی نیست
  • فراخوانی داخلی همان فرایند — اگر Caller و Callee در یک JVM/.NET هستند، یک فراخوانی تابع ارزان‌تر و ساده‌تر است.
  • داده‌ی ثابت و تغییرناپذیر — یک فایل JSON ایستا کافی است؛ نیازی به endpoint نیست.
  • تجربه‌ی داخلی یک تیم — تا وقتی فقط یک مصرف‌کننده و یک تیم دارید، پروتکل رسمی زودهنگام است.
  • داده‌ی بلادرنگ واقعاً دوطرفه — HTTP ساده برای جریان دوطرفه‌ی مداوم مناسب نیست؛ WebSocket یا SSE ببینید.
  • حجم بسیار بالای پیام ریز — هر پیام هزینه‌ی HTTP دارد؛ MQTT یا پیام‌رسانی مناسب‌تر است.
  • میان‌افزار داخلی یک سیستم منفرد — لایه‌بندی بیش از اندازه، فقط کد اضافه تولید می‌کند.
  • بدون مالک مشخص — اگر کسی قرارداد را نگه نمی‌دارد، API به‌سرعت فرسوده می‌شود.
تله‌ی معماری اینکه «همه‌چیز باید API داشته باشد» یک اصل معماری نیست؛ یک مد است. اول مسئله را مشخص کنید، بعد ابزار را انتخاب کنید — نه برعکس.

بخش ۲۱سؤالات مصاحبه

سطح پایه (Junior)

سؤال ۱ — API چیست؟

قراردادی است که مشخص می‌کند دو برنامه چطور با هم ارتباط برقرار کنند: چه درخواستی بپذیرند، چه پاسخی بدهند و با چه قالبی. مثال ساده‌اش منوی رستوران است: شما منو را می‌بینید، سفارش می‌دهید و آشپزخانه غذا را برمی‌گرداند — بدون اینکه وارد آشپزخانه شوید.

سؤال ۲ — تفاوت Client و Server چیست؟

Client طرفی است که درخواست را آغاز می‌کند (مرورگر، اپ موبایل، سرویس دیگر)؛ Server طرفی است که درخواست را پردازش می‌کند، به داده دسترسی دارد و پاسخ برمی‌گرداند. در HTTP همیشه Client اول قدم را برمی‌دارد.

سؤال ۳ — Endpoint و URL چه فرقی دارند؟

URL یک آدرس کامل است (پروتکل + دامنه + مسیر). Endpoint آن نقطه‌ای است که درخواست را می‌پذیرد — معمولاً ترکیب متد و مسیر، مثل GET /api/users/42. هر Endpoint یک URL دارد، ولی هر URL لزوماً یک Endpoint نیست.

سؤال ۴ — تفاوت URI و URL چیست؟

هر URL یک URI است، ولی هر URI لزوماً URL نیست. URI شناسه‌ی یکتاست؛ URL علاوه بر شناسه، محل (scheme, host, path) را هم مشخص می‌کند. مثال URI غیر-URL: urn:isbn:978-0132350884.

سؤال ۵ — متدهای اصلی HTTP را نام ببرید و بگویید هرکدام چه می‌کند.

GET خواندن؛ POST ساختن منبع یا اجرای عملیات؛ PUT جایگزینی کامل؛ PATCH تغییر جزئی؛ DELETE حذف. به‌علاوه HEAD (بدون بدنه)، OPTIONS (کاوش)، TRACE (تشخیصی).

سؤال ۶ — PUT و PATCH چه فرقی دارند؟

PUT کل منبع را با بدنه‌ی داده‌شده جایگزین می‌کند؛ فیلدهایی که نفرستید با مقدار پیش‌فرض پر می‌شوند یا حذف می‌شوند. PATCH فقط فیلدهای ارسالی را عوض می‌کند و بقیه دست‌نخورده می‌مانند. هر دو می‌توانند ایدمپوتنت باشند، به شرطی که عملیات جایگزینی باشد.

سؤال ۷ — Idempotency یعنی چه و چرا مهم است؟

یعنی اجرای چندباره‌ی یک درخواست، همان اثرِ یک بار را دارد. مهم است چون شبکه قطع می‌شود و Client مجبور به تلاش مجدد است؛ بدون ایدمپوتنت بودن، دوباره زدن POST /payments می‌تواند دو بار پول کم کند. راه‌حل برای POST هم افزودن Idempotency-Key است.

سؤال ۸ — تفاوت 401 و 403 چیست؟

401 یعنی «نمی‌دانم کی هستی» — توکن نیست یا نامعتبر است. 403 یعنی «می‌دانم کی هستی، ولی اجازه نداری» — هویت درست است ولی مجوز کافی نیست. پاسخ 401 باید هدر WWW-Authenticate داشته باشد.

سؤال ۹ — تفاوت JSON و XML؟

JSON سبک‌تر و خواناتر است و تایپ‌سیستم خفیف دارد؛ XML با XSD نوع‌دهی قوی، namespace و metadata دارد اما پرسروصداتر است. امروزه REST و GraphQL عمدتاً JSON استفاده می‌کنند و XML بیشتر در SOAP و اسناد سازمانی دیده می‌شود.

سؤال ۱۰ — Statelessness یعنی چه؟

یعنی سرور وضعیت نشست را بین درخواست‌ها نگه نمی‌دارد؛ هر درخواست باید خوداتکا باشد و هر اطلاعات لازم را حمل کند (معمولاً توکن). مزیتش: می‌توانید نمونه‌های بیشتری بدون پیکربندی خاص اضافه کنید.

سطح متوسط (Mid)

سؤال ۱۱ — چرا GET نباید وضعیت را تغییر دهد؟

چون مرورگرها، کش‌ها و CDN ها روی GET حساب می‌کنند که امن و تکرارپذیر است. اگر GET وضعیت را عوض کند، کش می‌تواند نتیجه‌ی کهنه را برگرداند، prefetch مرورگر می‌تواند بدون اجازه‌ی کاربر عملیات را اجرا کند و پیش‌بینی رفتار غیرممکن می‌شود.

سؤال ۱۲ — Content Negotiation چیست؟

توافق بین Client و Server درباره‌ی قالب پاسخ، با هدر Accept در درخواست و Content-Type در پاسخ. مثال: Accept: application/xml اگر سرور پشتیبانی کند، پاسخ XML می‌دهد وگرنه 406 برمی‌گرداند. در عمل اکثر API ها فقط JSON را پشتیبانی می‌کنند.

سؤال ۱۳ — HATEOAS چیست و چرا کمتر دیده می‌شود؟

یعنی پاسخ علاوه بر داده، لینک‌های مرتبط را هم برمی‌گرداند تا Client از قبل مسیرها را نداند و از قرارداد پیروی کند. عملاً پیاده‌سازی آن هزینه‌ی زیادی دارد و اکثر تیم‌ها قرارداد ثابت + OpenAPI را ترجیح می‌دهند؛ به همین دلیل REST واقعاً HATEOAS را کمتر رعایت می‌کند.

سؤال ۱۴ — اگر کلید ایدمپوتنتی را فراموش کنم چه می‌شود؟

پس از قطعی، تلاش مجدد Client رکورد تکراری می‌سازد — مثلاً دو بار پرداخت یا دو سفارش. راه‌حل‌های جایگزین: کلید یکتای دامنه‌ای (مثلاً orderId منحصربه‌فرد)، قید یکتای دیتابیس، یا تشخیص در لایه‌ی دامنه. همه‌ی آن‌ها یک اصل دارند: درخواست باید قابل تشخیص از تکرار باشد.

سؤال ۱۵ — وقتی پاسخ 304 برمی‌گردد چه اتفاقی می‌افتد؟

سرور فهمیده بدنه تغییری نکرده (با If-None-Match و ETag مقایسه کرده) و فقط سربرگ برمی‌گرداند. Client از کش محلی خودش استفاده می‌کند. نتیجه: پهنای باند و زمان پاسخ چند برابر کم می‌شود، بدون اینکه داده‌ی کهنه‌ای نمایش داده شود.

سؤال ۱۶ — محدودیت نرخ (Rate Limiting) را کجا پیاده کنید؟

معمولاً در Gateway یا میدل‌ور لایه‌ی وب، پیش از رسیدن به منطق دامنه. الگوریتم‌ها: Fixed Window (ساده اما سرریز)، Sliding Window (دقیق‌تر)، Token Bucket (موج را می‌پذیرد) و Leaky Bucket (نرخ ثابت). پاسخ باید 429 + هدر Retry-After و X-RateLimit-* باشد.

سؤال ۱۷ — اگر endpoint ای چند ثانیه طول بکشد چه کنیم؟

کار را از مسیر پاسخ خارج کنید: 202 Accepted + آدرسی برای پیگیری وضعیت، و نتیجه را بعداً با GET، WebSocket، SSE یا Webhook تحویل دهید. علت: مرورگرها و پروکسی‌ها معمولاً timeout بین ۳۰ تا ۶۰ ثانیه دارند و اتصال را می‌بندند.

سؤال ۱۸ — CORS چیست و چه زمانی مشکل‌ساز می‌شود؟

سیاستی در مرورگر است که جلوی دسترسی دامنه‌ی دیگر به پاسخ یک دامنه را می‌گیرد. مشکل‌ساز می‌شود وقتی Access-Control-Allow-Origin: * را با Allow-Credentials: true ترکیب کنید (مرورگر رد می‌کند، و اگر کار نکند خطر نشت کوکی است) یا وقتی فکر می‌کنید CORS یک مکانیزم امنیتی است — نیست؛ فقط یک قاعده‌ی مرورگری است. کنترل دسترسی باید سمت سرور باشد.

سطح پیشرفته (Senior)

سؤال ۱۹ — اگر دو endpoint پاسخ‌های هم‌پوشان بدهند، کدام درست است؟

این پرسش درباره‌ی مالکیت داده است، نه URL. قاعده: هر منبع باید یک مالک واحد و یک منبع حقیقت داشته باشد. اگر دو endpoint یک داده را از دو منبع مختلف می‌خوانند، دیر یا زود ناسازگار می‌شوند. پاسخ درست: منبع حقیقت را مشخص کنید، بقیه را یا حذف کنید یا صریحاً به‌عنوان projection فقط‌خواندنی با تاریخ انقضای روشن نام‌گذاری کنید.

سؤال ۲۰ — طراحی API چند مصرف‌کننده‌ی با نیاز متضاد را چطور مدیریت می‌کنید؟

سه گزینه دارید و باید هزینه‌ی هرکدام را بسنجید: ۱) پارامترهای انتخابی مثل fields و expand — انعطاف‌پذیر ولی قرارداد را پیچیده می‌کند؛ ۲) نسخه‌های مجزا یا BFF برای هر کلاینت — تمیز ولی چندپاره؛ ۳) GraphQL که خود Client شکل پاسخ را تعیین می‌کند — اما هزینه‌ی امنیت و کش را بالا می‌برد. انتخاب درست به تعداد مصرف‌کننده‌ها، میزان تفاوت نیاز آن‌ها و توان نگهداری تیم بستگی دارد.

بخش ۲۲پرسش‌های متداول (FAQ)

آیا هر API یک وب سرویس است؟

خیر. وب سرویس زیرمجموعه‌ای از API است که از راه شبکه (معمولاً HTTP) در دسترس است. یک کتابخانه‌ی جاوا هم API است، ولی وب سرویس نیست.

آیا REST همان HTTP است؟

نه. HTTP پروتکل انتقال است و REST یک سبک معماری مبتنی بر محدودیت‌های خاص (Client-Server، Statelessness، Uniform Interface، Cacheability و …) است. یک API می‌تواند HTTP باشد ولی REST نباشد.

آیا یک API فقط JSON تولید می‌کند؟

نه. JSON پرکاربردترین است ولی XML، YAML، باینری (Protobuf، MessagePack)، HTML و حتی فایل (PDF، تصویر) هم ممکن است. تعیین‌کننده هدر Content-Type و مذاکره با Accept است.

API Key و Token چه فرقی دارند؟

API Key یک رشته‌ی ثابت و معمولاً بلندعمر است که بیشتر برای شناسایی سرویس (server-to-server) به کار می‌رود. Token (مثل JWT) اغلب کوتاه‌عمر، دارای ادعا (claims) و قابل لغو است و برای هویت کاربر مناسب‌تر است.

چرا پاسخ من همیشه از کش می‌آید و داده‌ی تازه نمی‌بینم؟

به احتمال زیاد Cache-Control را عمداً یا سهواً public, max-age=… گذاشته‌اید یا CDN کش را purge نمی‌کنید. برای داده‌ی شخصی از private، برای داده‌ی حساس از no-store، و برای داده‌ی تازه با کش، از ETag + max-age کوتاه استفاده کنید.

بهترین Status Code برای «حذف موفق» کدام است؟

204 No Content. منبع حذف شده و چیزی برای نمایش نمانده. اگر بدنه‌ای مثل تأیید یا آمار نیاز دارید، 200 با بدنه بفرستید — مهم این است که Client بتواند تفاوت را تشخیص دهد.

تعداد زیاد درخواست کوچک بدهم یا یک درخواست بزرگ؟

به تعداد round-trip های شبکه نگاه کنید. در حالت کلی، تجمیع سریع‌تر است چون هر تماس هزینه‌ی ثابت دارد. اما اگر یکی از آیتم‌ها خطا دارد، کل درخواست بزرگ یکجا رد می‌شود؛ پس برای عملیات‌های حساس، batch با پاسخ جزئی بهتر است.

مستندات API را کجا و چطور نگه داریم؟

نزدیک‌ترین راه به کد: OpenAPI که از کد یا annotation تولید شود، تا با هر تغییر به‌روز شود. سپس Swagger UI یا ReDoc برای نمایش و تست قرارداد برای اطمینان از سازگاری. جزئیات در مقاله‌ی مستندسازی.

آیا باید برای هر Entity یک endpoint بسازم؟

نه لزوماً. منطق طراحی بر اساس منابع و رفتار معنایی است، نه جدول دیتابیس. گاهی یک منبع چند جدول را در بر می‌گیرد و گاهی یک جدول چند منبع می‌دهد. اگر نام endpoint از نام جدول آمده، سیگنال هشدار است.

چه زمانی نسخه‌ی جدید بدهم؟

فقط برای تغییر شکننده: حذف فیلد، تغییر نوع، تغییر معنای فیلد، تغییر Status Code. افزودن فیلد اختیاری یا افزودن endpoint جدید شکننده نیست. جزئیات کامل در مقاله‌ی نسخه‌بندی.

خطا را کجا لاگ کنم؟

در سمت سرور، با یک traceId که در همه‌ی سرویس‌ها منتقل شود و در پاسخ هم دیده شود تا کاربر بتواند آن را گزارش دهد. لاگ باید ساختاریافته (JSON) و بدون رمز عبور، توکن یا داده‌ی شخصی باشد.

آیا پرسش‌های تکراری از سمت Client ایراد دارد؟

خیر — تکرار نشانه‌ی شبکه‌ی ناپایدار یا خطای Client است. آنچه ایراد دارد، ناتوانی سرور در مدیریتش است: باید Idempotency-Key، کش و محدودیت نرخ داشته باشید تا تکرار هم امن و هم ارزان بماند.

بخش ۲۳جمع‌بندی و مقالات مرتبط

آنچه باید از این مقاله با خود ببرید

API یک قرارداد است، نه یک کتابخانه. اگر فقط چهار چیز را به یاد بماند، همین‌هاست:

  • متد درست — Safe و Idempotent بودن را جدی بگیرید؛ کش‌ها و Client ها روی آن حساب می‌کنند.
  • Status Code درست — 200 برای خطا ندهید؛ 401 و 403 را قاطی نکنید.
  • کلید یکتا — هر عملیاتی که پول یا داده‌ی حساس را لمس می‌کند باید Idempotency-Key داشته باشد.
  • حداقل داده — کمترین فیلدهای لازم، صفحه‌بندی با سقف، و Cache-Control آگاهانه.

بقیه‌ی چیزها — GraphQL، gRPC، WebSocket، Webhook — فقط همین چهار اصل را در شرایط مختلف به کار می‌گیرند. اگر این چهار مورد را بفهمید، یادگیری بقیه‌ی این سری خیلی سریع‌تر می‌شود.
