Rolling Deployment؛ به‌روزرسانی تدریجی، بدون قطعی سرویس

در Rolling Deployment به‌جای خاموش‌کردن همه‌چیز و روشن‌کردن دوباره، نسخه‌ی جدید Instance به Instance جایگزین نسخه‌ی قبلی می‌شود. کلید ماجرا دو پارامتر maxSurge و maxUnavailable و یک Health Gate با Readiness Probe است.

بخش ۱مقدمه

تا وقتی یک Instance دارید، هر Deploy یعنی یک Downtime. اما به‌محض اینکه چند Instance پشت یک Load Balancer دارید، راه‌حل ساده است: هیچ‌وقت همه را با هم عوض نکنید. اول یکی، بعد دومی، بعد سومی — تا آخر. این دقیقاً همان Rolling Deployment است و ابزارهایی مثل Kubernetes، AWS CodeDeploy، Ansible و حتی اسکریپت‌های دستی systemd همه پیاده‌سازی‌هایی از همین ایده‌اند.

در این مقاله مکانیک Rolling Update، پارامترهای maxSurge/maxUnavailable، Health Gate، Rollback و اینکه چه زمانی Rolling انتخاب اشتباهی است.
Prerequisites استقرار سرور در Production و Blue-Green Deployment.

بخش ۲Rolling چگونه کار می‌کند؟

دو شرط اساسی: (۱) برنامه باید Stateless باشد یا Session خود را بیرون نگه دارد، و (۲) دو نسخه باید بتوانند هم‌زمان با دیتابیس و داده‌ی مشترک کار کنند — یعنی Schema Migration باید سازگار به عقب باشد.

بخش ۳maxSurge و maxUnavailable

پارامترمعنیاثر
maxSurgeحداکثر Instance اضافه‌ای که بالای ظرفیت مطلوب مجاز استسرعت Deploy ↑ و نیاز به ظرفیت اضافه
maxUnavailableحداکثر Instanceی که می‌تواند در همان لحظه غیرقابل‌سرویس باشدظرفیت ↓ حین Deploy؛ صفر یعنی هیچ ظرفیتی نباید کم شود
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
spec:
  replicas: 4
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1          # یک Pod اضافه بیار
      maxUnavailable: 0    # ولی هیچ ظرفیتی کم نشود
  template:
    spec:
      containers:
        - name: api
          image: registry.example.com/api:1.7.0
          readinessProbe:
            httpGet:
              path: /healthz/ready
              port: 8080
            initialDelaySeconds: 5
            periodSeconds: 5
            failureThreshold: 3
          lifecycle:
            preStop:
              exec:
                command: ["sleep", "10"]   # فرصت برای خارج‌شدن از LB
Trade-off maxSurge: 1, maxUnavailable: 0 امن‌ترین حالت است ولی به منابع اضافه و Readiness درست نیاز دارد. maxUnavailable: 1 سریع‌تر است اما حین Deploy ظرفیت واقعی کم می‌شود — در ترافیک اوج خطرناک است.

بخش ۴Health Gate و Rollback

Rolling بدون Health Check، فقط خاموش‌وروشن‌کردن آرام است. اگر Instance جدید هرگز «آماده» نشود، Deploy باید متوقف و برگردانده شود — نه اینکه همه‌ی Instanceها خراب شوند.

گیتچی را چک می‌کند؟اگر شکست بخورد
Readiness Probeآمادگی ترافیک (وابستگی‌ها، Migration، Cache)Pod به LB وصل نمی‌شود؛ Deploy متوقف می‌شود
Liveness Probeزنده‌بودن فرآیند (Deadlock)Restart خودکار Pod
startupProbeشروع سنگین (JVM، Migration طولانی)مهلت بیشتری قبل از Readiness
progressDeadlineSecondsکل مدت DeployDeployment وضعیت Failed می‌گیرد
# مانیتورینگ وضعیت Rollout
kubectl rollout status deployment/api --timeout=300s

# اگر خراب شد: برگشت فوری به Revision قبلی
kubectl rollout undo deployment/api

# یا برگشت به یک Revision مشخص
kubectl rollout undo deployment/api --to-revision=2

# تاریخچه و آخرین وضعیت
kubectl rollout history deployment/api
kubectl get events --sort-by='.lastTimestamp' | tail
Expected Behavior با image خراب: Pod جدید Ready نمی‌شود، rollout status با Timeout شکست می‌خورد، Deployment جلوی ادامه‌ی کار را می‌گیرد و ظرفیت سالم قبلی حفظ می‌ماند — کاربر چیزی نمی‌بیند.

بخش ۵مقایسه با Blue-Green و Canary

معیارRollingBlue-GreenCanary
منابع حین Deployکم (surge کوچک)دو برابرکم + زیرساخت توزیع ترافیک
سرعتمتوسطسریع (Switch لحظه‌ای)آهسته (گام‌به‌گام)
آزمودن با ترافیک واقعیخیرپس از Switch، یک‌جابله، درصدی
RollbackRollout معکوس (کندتر)Switch به عقب (فوری)حذف Canary (فوری)
مدیریت State/Schemaنیازمند سازگاری دو نسخهساده‌تر (یک لحظه‌ی Switch)نیازمند سازگاری
پیچیدگی زیرساختکممتوسطزیاد
قانون انتخاب سرویس Stateless معمولی → Rolling. نیاز به تست کامل با ترافیک ۱۰۰٪ قبل از اعتماد → Blue-Green. ریسک رفتاری نسخه‌ی جدید نامشخص است و متریک تجاری/فنی باید تماشا شود → Canary.
When NOT to Use Rolling Schemaهای ناسازگار (حذف/تغییر ستون مصرف‌شده در نسخه‌ی قدیمی)، Session حافظه‌ای بدون Replica، یا Jobهای طولانی که دو نسخه را غیرممکن می‌کنند — اینجا Blue-Green یا الگوهای Zero-Downtime را ببینید.

بخش ۶چک‌لیست و جمع‌بندی

چک‌لیست Rolling
  • برنامه Stateless است و Session/Cache بیرونی دارد (Redis، JWT).
  • Readiness Probe واقعی است: وابستگی‌ها و Migration را چک می‌کند.
  • maxSurge و maxUnavailable با ظرفیت واقعی هماهنگ‌اند.
  • preStop + Grace Period قبل از قطع کانکشن‌ها وجود دارد.
  • Schema Migration سازگار به عقب است (Expand/Contract).
  • progressDeadlineSeconds و Rollback خودکار/سریع تنظیم شده.

Rolling Deployment پیش‌فرض دنیای Kubernetes است چون ساده، کم‌هزینه و ایمن است — به شرطی که Health Gateها را جدی بگیرید. برای الگوهای پیشرفته‌تر، Zero-Downtime Deployment و معماری Production را دنبال کنید.
