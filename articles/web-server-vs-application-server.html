Web Server در برابر Application Server

این دو اصطلاح آن‌قدر در گفت‌وگوهای روزمره قاطی می‌شوند که بسیاری فکر می‌کنند یک چیزند. در این مقاله تفاوت را در سطح مسئولیت، Runtime، Session، Transaction و Dependency Injection می‌شکنیم و می‌بینیم چرا در Production معمولاً هر دو لازم‌اند — نه یکی.

بخش ۱چرا این تفکیک مهم است؟

وقتی یک تیم این تفکیک را نمی‌داند، سه اتفاق رایج می‌افتد: بک‌اند مستقیم روی پورت عمومی قرار می‌گیرد، وظایف مشترک (TLS، فایل ثابت، Rate Limiting) در هر سرویس دوباره نوشته می‌شود، و در زمان اشکال‌زدایی معلوم نیست خطا از لایه‌ی ورودی است یا از منطق برنامه.

یک جمله‌ی خلاصه Web Server می‌پرسد «چه پاسخی بدهم؟» — Application Server می‌پرسد «منطق برنامه چیست و چطور اجرا شود؟».
Prerequisites خواندن Web Server چیست؟ پیش از این مقاله توصیه می‌شود.

Cachingنگه‌داشتن پاسخ‌های تکراری در لبه.
Compressiongzip / brotli برای متن.

یک Web Server معمولاً هیچ اطلاعی از قوانین کسب‌وکار ندارد. نمی‌داند «سفارش» چیست؛ فقط می‌داند GET /orders/42 را باید به کجا برساند.

بخش ۸Runtime و چرخه‌ی حیات

تفاوت بنیادی این است که Application Server یک Runtime دارد و برنامه‌ی شما درون آن اجرا می‌شود. همین باعث می‌شود چرخه‌ی حیات برنامه از لایه‌ی ورودی جدا باشد. 

Application Server Lifecycle

  Boot → Class Loading → Dependency Injection
    → Application Ready → Serve Requests
    → Graceful Shutdown (drain) → Stop

Web Server Lifecycle

  Boot → Load Config → Bind Port
    → Accept Connections → Reload Config (SIGHUP)
چرا مهم است؟ در Zero-Downtime Deployment، توانایی Graceful Shutdown در Application Server حیاتی است: ابتدا درخواست‌های در جریان تمام می‌شوند و تازه بعد فرآیند متوقف می‌شود.

بخش ۹Session و State

Session یکی از روشن‌ترین دلایل وجود Application Server است. اگر وضعیت کاربر را در حافظه‌ی همان Instance نگه دارید، Horizontal Scaling سخت می‌شود: کاربر باید به همان Instance برگردد.

رویکردمزیتعیب
In-Memory Sessionساده و سریعنیازمند Sticky Session؛ برای Scaling ضعیف
Session در RedisStateless شدن Instanceهایک وابستگی جدید و Latency شبکه
Token (JWT)بدون وضعیت در سرورInvalidation دشوار و اندازه‌ی بزرگ‌تر
Production Note هدف نهایی در سیستم‌های مقیاس‌پذیر، Stateless کردن Application است؛ وضعیت را به Redis، دیتابیس یا Token منتقل کنید.

بخش ۱۰Transaction و Connection Pool

Transaction و Connection Pool دو مسئولیتی‌اند که Web Server هرگز ندارد. 

@Service
public class OrderService {

    private final OrderRepository orders;   // Connection Pool از اینجا تأمین می‌شود

    @Transactional                          // مرز تراکنش = مرز Use Case
    public Order placeOrder(PlaceOrderCommand cmd) {
        Order order = Order.create(cmd.items());
        orders.save(order);                 // یک عملیات اتمیک
        return order;
    }
}
مفهوممسئولیتخطای رایج
Transactionاتمی‌بودن عملیاتقرار دادن مرز تراکنش روی Controller
Connection Poolبازاستفاده از اتصال دیتابیسPool کوچک در بار بالا → Timeout
Dependency Injectionساخت و اشتراک وابستگی‌هاساخت دستی Repository در هر درخواست

بخش ۱۲چه زمانی کدام؟

When to Use a dedicated Web Server وقتی فایل ثابت، TLS، چند سرویس، Caching یا Rate Limiting دارید — یعنی تقریباً هر سرویس Production.
When to Use an Application Server هر زمان منطق کسب‌وکار، Session، Transaction یا Runtime نیاز دارید. یعنی همیشه در سمت برنامه.
When NOT to over-split برای یک اسکریپت داخلی کوچک با کاربر کم، جداکردن سخت‌گیرانه‌ی لایه‌ها فقط پیچیدگی اضافه می‌کند.

بخش ۱۳جمع‌بندی و مقالات مرتبط

Web Server و Application Server دو نقش متفاوت با دو مجموعه مسئولیت متفاوت‌اند. در Production مدرن معمولاً هر دو حاضرند: اولی در لبه ترافیک را می‌پذیرد و کارهای مشترک را انجام می‌دهد، دومی منطق کسب‌وکار را اجرا می‌کند.

گام بعدی Reverse Proxy چیست؟ — لایه‌ای که این دو را به شکل امن و کارا به هم می‌بندد.
