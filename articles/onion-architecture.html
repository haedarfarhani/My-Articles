بخش ۱مقدمه: وقتی لایه‌ها به هم نشت می‌کنند

یک سیستم فاکتور فروش را تصور کنید که با معماری لایه‌ای کلاسیک شروع شده: UI → Business → Data. در نسخه‌ی اول همه‌چیز مرتب است؛ اما بعد از چند ماه مشاهده می‌کنید موجودیت‌های دامنه‌ی شما کم‌کم به JPA وابسته شده‌اند، منطق مالیات در یک کلاس کنترلر جا خوش کرده است و لایه‌ی Data برای «بهینه‌سازی» مستقیماً از لایه‌ی Business صدا می‌زند. 

Layered — وضعیت بعد از رشد:

UI ──────────────┐
  ↓              │
Business ←── Data   (وابستگی معکوس!)
  ↓
Database

Domain مدتهاست از وسط این فلش‌ها له شده است.
  • نشت دانش دامنه: قانون مالیات بین سه لایه پراکنده می‌شود.
  • وابستگی معکوس: لایه‌ی پایین‌تر، لایه‌ی بالاتر را خبردار می‌کند.
  • تست دشوار: تست قانون مالیات نیاز به بالا آوردن Persistence دارد.
  • UI جایگزین‌نشدنی: افزودن API جدید یعنی بازنویسی دوباره‌ی منطق.
ریشه‌ی مشکل لایه‌بندیِ صرف کافی نیست؛ چون جهت وابستگی را کنترل نمی‌کند. Onion Architecture با یک جمله آمده است: یک مرکز داشته باشید (Domain) و بگذارید همه‌ی وابستگی‌ها به سمت آن جریان یابند — هرگز برعکس.

بخش ۲تاریخچه و دلیل ایجاد

Onion Architecture را Jeffrey Palermo در سال ۲۰۰۸ در وبلاگش معرفی کرد (سلسله مقاله‌های «Introducing Onion Architecture»). انگیزه‌ی او دقیقاً همان درد بخش اول بود: پروژه‌های N-Tier که در آن‌ها لایه‌ی Data به Business وابسته می‌شد و Unit Test‌ها کند و شکننده بودند.

بسترچه اتفاقی افتاد؟
دهه‌ی ۲۰۰۰ — N-Tier / Layeredلایه‌بندی رایج شد اما جهت وابستگی کنترل نمی‌شد؛ لایه‌ی Data اغلب به همه‌ی چیز وصل بود
۲۰۰۳–۲۰۰۷ — TDD و Agileنیاز به تست‌های سریع بدون DB، معماری‌های «تست‌پذیر» را ضروری کرد
۲۰۰۵ — Hexagonal (Cockburn)ایده‌ی هسته و درایور/درایو را مطرح کرد — خویشاوند نزدیک Onion
۲۰۰۸ — Onion (Palermo)حلقه‌های متحدالمرکز با مرکزیت Domain Model را رسماً توصیف کرد
۲۰۱۲–۲۰۱۷ — Clean (Martin)ایده‌های مشابه را با نام‌گذاری چهارلایه‌ای و Dependency Rule تثبیت کرد
چرا محبوب شد؟ چون به تیم‌ها اجازه داد منطق تجاری را بدون DB و بدون UI تست کنند؛ و در پروژه‌های سازمانی بزرگ، مدل دامنه به تنها دارایی پایدارِ پروژه تبدیل شد — همه‌چیز عوض می‌شد جز قواعد تجاری.

بخش ۳Onion Architecture چیست؟ (تعریف دقیق)

تعریف رسمی Onion Architecture یک روش سازمان‌دهی کد است که سیستم را به حلقه‌های متحدالمرکز تقسیم می‌کند؛ Model دامنه در مرکز است و هر حلقه فقط به حلقه‌ی داخلی‌تر وابسته است، و وابستگی‌ها با Dependency Inversion در مرز حلقه‌ها می‌چرخند تا جهت نهایی همیشه به مرکز باشد.
✅ هست…❌ نیست…
یک طرح کلی ساختار سیستم با مرکزیت Domainیک Framework یا کتابخانه‌ی قابل نصب
یک قاعده‌ی جهت وابستگی (فقط به داخل)یک Design Pattern مثل Strategy یا Observer
ترجمه‌ی عملیِ DIP در مقیاس کل پروژهفقط «ساختن پوشه‌ی Domain» — ظاهر بدون قاعده کافی نیست
همه‌پوشش برای UI، API، CLI و هر ورودی دیگرجایگزین DDD — بلکه مکمل آن است
سوءتفاهم رایج خیال نکنید «پیازی» یعنی لایه‌های زیاد بسازید! تعداد حلقه‌ها مهم نیست؛ آنچه مهم است اینکه هیچ فلشی از مرکز به بیرون نرود. پروژه‌ی کوچک با دو حلقه می‌تواند پیازی باشد.

بخش ۴مشکل قبل از استفاده

همان سیستم فاکتور را بدون معماری پیازی ببینید:

public class InvoiceRepository {

    private final EntityManager em; // JPA در کلاس تجاری!

    public BigDecimal totalTax(Invoice invoice) {
        // قانون مالیات! کجای کار است؟ لایه‌ی Data
        BigDecimal vat = invoice.getSubtotal()
                .multiply(new BigDecimal("0.09"));

        em.persist(invoice); // ذخیره‌سازی همین‌جا
        return vat;
    }
}

تحلیل مشکلات:

  • قانون تجاری در اشتباه‌ترین حلقه: مالیات باید در Domain باشد، نه در Repository.
  • وابستگی به JPA: تست قانون مالیات بدون Container ممکن نیست.
  • دو مسئولیت در یک کلاس: محاسبه + ذخیره (نقض SRP).
  • UI جایگزین‌نشدنی: API جدید مجبور است همین کلاس را صدا بزند و قانون را دوباره بشکند.
وابستگی‌ها (همه به بیرون):

InvoiceRepository ──→ JPA ──→ Database
        │
        └──→ قانون مالیات (کجاست؟ همین‌جا گم شده)

در Onion: Invoice (مرکز) ← TaxRule (حلقه‌ی سرویس) ← JpaInvoiceRepo (حلقه‌ی بیرونی)

بخش ۵ایده اصلی: Domain در مرکز

سه قانون بنیادین Onion Architecture:

قواعد سه‌گانه ۱) مرکز، وابستگی ندارد — حلقه‌ی Domain هیچ import از بیرون نمی‌گیرد.
۲) هر حلقه فقط به داخل نگاه می‌کند — وابستگی کامپایلی هرگز به بیرون نمی‌رود.
۳) در مرز حلقه‌ها DIP اعمال می‌شود — بیرونی‌ها interface‌های داخلی را پیاده‌سازی می‌کنند.

مثال ساده: قانون «فاکتور زیر ۱۰۰ هزار تومان معاف از مالیات است» را در مرکز قرار می‌دهیم:

// حلقه‌ی مرکز — هیچ وابستگی ندارد
public final class Invoice {
    private final List<InvoiceLine> lines;

    public Invoice(List<InvoiceLine> lines) {
        if (lines.isEmpty()) throw new IllegalArgumentException("empty invoice");
        this.lines = List.copyOf(lines);
    }

    public BigDecimal subtotal() {
        return lines.stream().map(InvoiceLine::amount)
                .reduce(BigDecimal.ZERO, BigDecimal::add);
    }

    // قانون تجاری اینجاست — نه در Controller و نه در DAO
    public BigDecimal tax() {
        BigDecimal sub = subtotal();
        return sub.compareTo(new BigDecimal("100000")) < 0
                ? BigDecimal.ZERO
                : sub.multiply(new BigDecimal("0.09"));
    }
}
آزمون مرز اگر فایل‌های حلقه‌ی مرکز شما import‌ای غیر از کتابخانه‌ی استاندارد زبان (java.math، java.util و…) داشته باشند، مرکز آلوده شده است و معماری عملاً شکسته است — حتی اگر پوشه‌ها مرتب باشند.

بخش ۶ساختار معماری: حلقه‌ها

حلقهمسئولیتداخل آنممنوع
۱. Domain Modelموجودیت‌ها و قواعد پایدارEntity، Value Object، قواعدهر import بیرونی
۲. Domain Servicesرفتارهای دامنه‌ای بدون جای طبیعی در Entityinterface سرویس‌ها و Repositoryهاجزئیات ORM/HTTP
۳. Application Servicesهماهنگی سناریوها (Use Case)کلاس‌های اجرایی سرویسمنطق تجاری ثابت
۴. Infrastructureجزئیات فنیDAO، ORM، Web، UI، درگاه پرداختهر قانون تجاری

Palermo تأکید داشت جای Repository interface در حلقه‌ی داخلی و جای پیاده‌سازی آن در بیرون است؛ و DAO فقط در بیرونی‌ترین حلقه می‌نشیند. این جداسازی، همان چیزی است که تست‌پذیری را ممکن می‌کند.

بخش ۷جریان داده (Data Flow)

مرحلهچه می‌شود؟
۱. Controllerورودی را می‌گیرد، به Command داخلی ترجمه و Application Service را صدا می‌زند
۲. Application ServiceEntity را از Repository می‌گیرد، رفتار لازم را هماهنگ می‌کند
۳. Domain Entityقانون را اعمال می‌کند (مالیات، اعتبار، وضعیت)
۴. Repositoryinterface در داخل فراخوانی، پیاده‌سازی بیرونی کار را می‌کند
۵. بازگشتنتیجه از همان زنجیره برمی‌گردد؛ Controller فقط پاسخ می‌سازد
نکته‌ی کلیدی فراخوانی (Call) از بیرون به داخل است، اما فلش وابستگی کامپایلی به داخل است؛ چون DAO پیاده‌سازی Repository interface است. این تقارن، رمز تست دامنه بدون DB است.

بخش ۹مثال عملی کامل: سیستم فاکتور

دامنه: Invoice، InvoiceLine، Customer با قواعد:

Rules (در مرکز)
├── فاکتور نمی‌تواند خالی باشد
├── زیر ۱۰۰,۰۰۰ → مالیات صفر؛ وگرنه ۹٪
├── تخفیف فقط برای Customerهای VIP مجاز است
└── فاکتور PAID قابل ویرایش نیست
Workflow:
1. POST /invoices — Controller ساخت InvoiceRequest را ترجمه می‌کند
2. InvoiceService قوانین را روی Invoice اعمال می‌کند
3. InvoiceRepository (interface در داخل) فراخوانی می‌شود
4. JpaInvoiceRepository در بیرون ذخیره می‌کند
5. نتیجه InvoiceResult به Controller و پاسخ HTTP برمی‌گردد
نکته‌ی طراحی توجه کنید «کجا تست می‌نویسیم؟»: چهار قانون بالا همگی در حلقه‌ی مرکزند → تست آن‌ها میلی‌ثانیه‌ای است. فقط ذخیره‌سازی به تست ادغام نیاز دارد.

بخش ۱۰پیاده‌سازی کد با Java 21

حلقه‌ی مرکز: Entity و قواعد

import java.math.BigDecimal;
import java.util.List;

public final class Invoice {
    private final String id;
    private final Customer customer;
    private final List<InvoiceLine> lines;
    private final InvoiceStatus status;

    public Invoice(String id, Customer customer,
                   List<InvoiceLine> lines, InvoiceStatus status) {
        if (lines == null || lines.isEmpty())
            throw new IllegalArgumentException("Invoice must have lines");
        this.id = id;
        this.customer = customer;
        this.lines = List.copyOf(lines);
        this.status = status;
    }

    public BigDecimal subtotal() {
        return lines.stream().map(InvoiceLine::amount)
                .reduce(BigDecimal.ZERO, BigDecimal::add);
    }

    public BigDecimal tax() {
        BigDecimal sub = subtotal();
        boolean exempt = sub.compareTo(new BigDecimal("100000")) < 0;
        return exempt ? BigDecimal.ZERO
                      : sub.multiply(new BigDecimal("0.09"));
    }

    public BigDecimal discount() {
        boolean vip = customer.tier() == Tier.VIP;
        return vip ? subtotal().multiply(new BigDecimal("0.05")) : BigDecimal.ZERO;
    }

    public Invoice pay() {
        if (status == InvoiceStatus.PAID) return this;
        return new Invoice(id, customer, lines, InvoiceStatus.PAID);
    }
}

Application Service: هماهنگی سناریو

public final class CreateInvoiceUseCase {

    private final InvoiceRepository invoices;
    private final CustomerRepository customers;
    private final IdGenerator ids;

    public CreateInvoiceUseCase(InvoiceRepository invoices,
                                CustomerRepository customers,
                                IdGenerator ids) {
        this.invoices = invoices;
        this.customers = customers;
        this.ids = ids;
    }

    public InvoiceResult execute(CreateInvoiceCommand cmd) {
        Customer customer = customers.findById(cmd.customerId())
                .orElseThrow(() -> new CustomerNotFound(cmd.customerId()));

        List<InvoiceLine> lines = cmd.lines().stream()
                .map(l -> new InvoiceLine(l.description(), l.amount()))
                .toList();

        Invoice invoice = new Invoice(ids.nextId(), customer, lines, InvoiceStatus.DRAFT);
        invoices.save(invoice);

        return new InvoiceResult(invoice.id(), invoice.subtotal(),
                                 invoice.tax(), invoice.discount());
    }
}

حلقه‌ی بیرونی: پیاده‌سازی Repository

import java.util.Optional;

public final class JpaInvoiceRepository implements InvoiceRepository {

    private final InvoiceJpaDao dao;

    public JpaInvoiceRepository(InvoiceJpaDao dao) {
        this.dao = dao;
    }

    @Override
    public void save(Invoice invoice) {
        dao.save(InvoiceJpaEntity.from(invoice));
    }

    @Override
    public Optional<Invoice> findById(String id) {
        return dao.findById(id).map(InvoiceJpaEntity::toDomain);
    }
}

تحلیل: Entity هیچ import بیرونی ندارد؛ Use Case فقط interface می‌شناسد؛ DAO و ترجمه (Mapping) کاملاً در حلقه‌ی بیرونی‌اند — با تغییر ORM هیچ‌کدام از دو فایل اول تغییر نمی‌کنند.

بخش ۱۴چه زمانی استفاده کنیم؟

  • مدل دامنه پیچیده و غنی است — قواعد تجاری ارزش اصلی محصول‌اند (مالی، بیمه، لجستیک)
  • پروژه بلندمدت و پر-تغییر است — عمر بیش از یک سال با تیم در حال رشد
  • پشتیبانی از چند ورودی مورد نیاز است — Web + Mobile API + CLI + Batch Job
  • تست خودکار و CI اهمیت دارد — خواهان تست‌های سریع و پوشش بالای دامنه
  • تعویض زیرساخت محتمل است — مهاجرت ORM، DB یا فریم‌ورک در برنامه است
  • تیم بزرگ یا چندتیمی دارید — مرز حلقه‌ها مالکیت را روشن می‌کند
  • می‌خواهید DDD را عملی کنید — Onion بهترین اسکلت اجرایی برای DDD است
نشانه‌ی طلایی اگر جمله‌ی «این قانون تجاری سال‌ها ثابت می‌ماند اما ابزارهای فنی عوض می‌شوند» در پروژه‌تان صادق است، دقیقاً حالتی است که Onion برایش ساخته شده است.

تفاوت کلیدی:

  • Onion vs Clean: هر دو متحدالمرکزند؛ Onion بر تسلط بر Model تأکید دارد، Clean بر Use Case و قاعده‌ی وابستگی.
  • Onion vs Hexagonal: Hexagonal هر ورودی/خروجی را Port می‌نامد؛ Onion حلقه‌ها را بر اساس نوع مسئولیت نام‌گذاری می‌کند.
  • Onion vs Layered: Layered جهت وابستگی را آزاد می‌گذارد؛ Onion صراحتاً ممنوع می‌کند.
مرتبط در همین سایت مقایسه‌ی عمیق این چهار معماری در مقاله‌ی Clean Architecture از همین سری آمده است.

بخش ۱۷ارتباط با SOLID

  • SRP: هر حلقه یک دلیل تغییر دارد — قانون در Domain، هماهنگی در Application، جزئیات در Infrastructure.
  • OCP: افزودن نوع جدید پرداخت = کلاس جدیدِ پیاده‌سازیِ همان interface؛ بدون تغییر Use Case.
  • LSP: پیاده‌سازی‌های Repository باید رفتار قراردادی interface را حفظ کنند (مثلاً ذخیره‌ی ناموفق استثنا بدهد).
  • ISP: interface‌های کوچک و متمرکز: InvoiceReader و InvoiceWriter بهتر از یک InvoiceDao غول.
  • DIP: هسته‌ی فلسفه‌ی Onion — بیرون به interface‌های داخل وابسته است.
// DIP در عمل — قبل و بعد

// ✗ قبل: وابستگی مستقیم به بیرون
public class InvoiceService {
    private final JpaInvoiceDao dao = new JpaInvoiceDao();
}

// ✓ بعد: وابستگی به interface در حلقه‌ی داخلی
public class InvoiceService {
    private final InvoiceRepository repository;

    public InvoiceService(InvoiceRepository repository) {
        this.repository = repository;
    }
}

برای تست Application Service از Fake ساده استفاده می‌کنیم (بدون Mock سنگین):

final class InMemoryInvoiceRepository implements InvoiceRepository {
    private final Map<String, Invoice> store = new LinkedHashMap<>();

    @Override public void save(Invoice invoice) { store.put(invoice.id(), invoice); }
    @Override public Optional<Invoice> findById(String id) {
        return Optional.ofNullable(store.get(id));
    }
}

@Test
void shouldCreateAndPersistInvoice() {
    // Arrange
    InMemoryInvoiceRepository repo = new InMemoryInvoiceRepository();
    CreateInvoiceUseCase useCase = new CreateInvoiceUseCase(
            repo, new FakeCustomerCatalog(), new UuidIdGenerator());

    // Act
    InvoiceResult result = useCase.execute(commandWithOneLine());

    // Assert
    assertTrue(repo.findById(result.id()).isPresent());
    assertEquals(0, result.tax().compareTo(BigDecimal.ZERO));
}
نتیجه چون حلقه‌ی مرکز خالص است، اکثر تست‌ها بدون Thread و بدون Network اجرا می‌شوند؛ تست‌های ادغامی فقط مرز بیرونی را پوشش می‌دهند و تعدادشان کم است.

بخش ۲۱مثال در پروژه واقعی

۱) بک‌اند (Java + Spring Boot)

com.shop/
├── domain/          # Invoice, Customer, InvoiceRepository (interface)
├── application/     # CreateInvoiceUseCase
├── infrastructure/  # JpaInvoiceRepository, SmtpMailer
└── interfaces/      # InvoiceController (REST)

درگاه پرداخت جدید فقط یک کلاس جدید در infrastructure است؛ Use Case تغییر نمی‌کند.

۲) اندروید (Kotlin + Compose)

app/
├── domain/       # قواعد سبد خرید + Repository interface
├── data/         # پیاده‌سازی با Room/Retrofit
└── ui/           # ViewModel + Compose Screen

تغییر API سرور فقط پکیج data را می‌لرزاند؛ ViewModel و قواعد دامنه دست‌نخورده می‌مانند.

۳) فرانت‌اند (TypeScript + NestJS)

src/
├── domain/           # مدل‌های TS خالص
├── application/      # سرویس‌های هماهنگ‌کننده
├── infrastructure/   # TypeORM, Axios
└── interfaces/       # Controllers / Frontend Components

یک هسته‌ی مشترک بین API و منطق سمت Client قابل اشتراک است چون به فریم‌ورک وابسته نیست.

الگوی مشترک در همه‌ی پلتفرم‌ها: مدل در مرکز، interface در حلقه‌ی داخلی، پیاده‌سازی و سیم‌کشی در بیرون.

بخش ۲۲Performance

نه — Onion Architecture خودِ Runtime را سریع‌تر نمی‌کند؛ آنچه بهتر می‌شود کیفیت نگهداری است:

بعدتأثیر
تست‌پذیری و سرعت تست✅ بهبود چشمگیر (تست دامنه بدون I/O)
نگهداری و تغییر✅ بهبود چشمگیر
Scalability سازمانی✅ بهبود
Throughput / Latency⬜ تقریباً بی‌تأثیر؛ هزینه‌ی ترجمه‌ی بین حلقه‌ها ناچیز است
مصرف حافظه⬜ بی‌تأثیر عملی

تنها هزینه‌ی واقعی، سربرِ ترجمه (Mapping Overhead) — ترجمه‌ی مدل دامنه به JPA Entity و برعکس — است؛ در مسیرهای بسیار داغ می‌توان آن را با Builderهای بهینه کاهش داد — بدون شکستن مرز حلقه‌ها.

کی نگران شویم؟ در پردازش ده‌ها هزار پیام در ثانیه، هر شیءی اهمیت دارد؛ آن‌جا پروفایل کنید و در صورت نیاز مسیر Hot Path را ساده کنید — معماری اجازه می‌دهد این بهینه‌سازی فقط محلی باشد و مرزها را نشکند.

بخش ۲۳۲۰ سؤال مصاحبه شغلی

سطح Junior

سؤال ۱ — Onion Architecture چیست؟ معماری‌ای با حلقه‌های متحدالمرکز است که Model دامنه را در مرکز می‌گذارد و هر حلقه فقط به حلقه‌ی داخلی‌تر وابسته است؛ با اعمال DIP در مرزها تا جهت وابستگی همیشه به مرکز باشد.
سؤال ۲ — حلقه‌های اصلی را نام ببرید. از داخل به بیرون: Domain Model (Entities/VO)، Domain Services (interface‌ها)، Application Services (هماهنگی) و Infrastructure/Interfaces (DAO، Web، UI).
سؤال ۳ — چرا Domain در مرکز است؟ چون قواعد تجاری پایدارترین بخش سیستم‌اند؛ ابزارها (DB/UI/Framework) عوض می‌شوند اما قواعد تجاری کمتر. قرار دادن آن در مرکز، پرنوسان‌ترین بخش‌ها را از پایدارترین بخش دور نگه می‌دارد.
سؤال ۴ — Repository interface در کدام حلقه است؟ در حلقه‌ی داخلی (کنار Domain Services)؛ پیاده‌سازی و DAO در حلقه‌ی بیرونی — نتیجه‌ی مستقیم DIP.
سؤال ۵ — تفاوت با Layered ساده چیست؟ Layered فقط وظیفه را جدا می‌کند و جهت وابستگی را آزاد می‌گذارد؛ Onion صراحتاً هر وابستگی به بیرون را ممنوع می‌کند.
سؤال ۶ — DAO و Repository فرقشان چیست؟ Repository یک مفهوم دامنه‌ای است (مجموعه‌ی اقلام قابل بازیابی) و interface آن در داخل می‌نشیند؛ DAO یک ابزار فنی برای دسترسی مستقیم به داده است و فقط در بیرون مجاز است.
سؤال ۷ — تست قانون مالیات چطور انجام می‌شود؟ مستقیماً روی Entity: شیء Invoice را می‌سازید، tax() را صدا می‌زنید و assert می‌کنید — بدون DB، بدون Framework، در میلی‌ثانیه.
سؤال ۸ — اگر import بیرونی در domain پیدا کنید چه می‌کنید؟ آن را نقض معماری می‌دانم: یا جای قانون را اشتباه انتخاب کرده‌ایم یا باید یک interface در داخل تعریف و پیاده‌سازی را به بیرون منتقل کنیم.

سطح Mid

سؤال ۹ — تفاوت Onion و Clean Architecture؟ هر دو متحدالمرکزند؛ Clean بر Use Case و چهار لایه‌ی مشخص با Dependency Rule تأکید دارد، Onion بر تسلط Domain Model و نام‌گذاری حلقه‌ای تأکید می‌کند. در عمل همپوشانی زیادی دارند.
سؤال ۱۰ — تفاوت Onion و Hexagonal؟ Hexagonal هر ورودی/خروجی را Port/Adapter می‌نامد (تمرکز بر interface‌های محیط)؛ Onion حلقه‌ها را بر اساس نوع مسئولیت نام می‌زند (تمرکز بر لایه‌بندی دامنه). هر دو جهت وابستگی را به داخل می‌چرخانند.
سؤال ۱۱ — Application Service با Domain Service فرقش؟ Domain Service رفتار دامنه‌ای بدون جای طبیعی در Entity است (مثل محاسبه‌ی ارز متقابل) و در حلقه‌ی داخلی می‌نشیند؛ Application Service فقط سناریو را هماهنگ می‌کند و منطق تجاری ندارد.
سؤال ۱۲ — چطور وابستگی معکوس را تضمین می‌کنید؟ سه ابزار: جداسازی ماژول/پکیج (کامپایل می‌شکند)، تست معماری مثل ArchUnit در CI، و بازبینی import در Code Review.
سؤال ۱۳ — اگر Use Case منطق تجاری پیدا کرد چه می‌شود؟ نشانه‌ی خوبی نیست: قانون ثابت باید به Entity/Domain Service منتقل شود؛ آنچه در Application می‌ماند فقط هماهنگی و ترتیب اجراست.
سؤال ۱۴ — چند حلقه خوب است؟ هیچ عدد جادویی وجود ندارد؛ ۲ تا ۴ حلقه برای اکثر پروژه‌ها کافی است. مهم تعداد نیست، جهت وابستگی است.
سؤال ۱۵ — DTO را در کجا تعریف می‌کنید؟ در لایه‌ی بیرونی مربوطه (interfaces یا application بسته به سیاست تیم)؛ DTO حامل داده برای عبور از مرز است و نباید وارد حلقه‌ی مرکز شود.

سطح Senior

سؤال ۱۶ — Trade-offهای واقعی این معماری چیست؟ زمان اولیه‌ی بیشتر، کد تکراری ترجمه، نیاز به آموزش تیم و ریسک مرزِ اشتباه — در برابر تست سریع، تعویض زیرساخت و نگهداری ارزان در بلندمدت. تصمیم به عمر پروژه و نرخ تغییر بستگی دارد.
سؤال ۱۷ — مهاجرت Legacy به Onion را چطور انجام می‌دهید؟ به روش Strangler: دور یک قابلیت پرتکرار مرز می‌کشم، قوانین را به Entity منتقل می‌کنم، پشت Repository interface می‌گذارم و بقیه را تدریجی جذب می‌کنم. مهاجرت آبشاری همه‌چیز، بدون پوشش تست، شکست می‌خورد.
سؤال ۱۸ — Onion و DDD چه ربطی دارند؟ Onion اسکلت اجرایی DDD است: Aggregate و Entity در مرکز، Repositoryها در حلقه‌ی دامنه، و مرزهای حلقه‌ها به تقویت Bounded Context کمک می‌کنند. DDD فکر می‌کند، Onion می‌چیند.
سؤال ۱۹ — چطور به مدیر توجیه هزینه‌ی اولیه را می‌کنید؟ با عدد: «الان افزودن یک درگاه ۳ روز و ۲ باگ دارد؛ با مرزبندی، یک روز و بدون دست‌زدن به بقیه.» هزینه را به زبان ریسک کسب‌وکار ترجمه می‌کنم، نه تئوری معماری.
سؤال ۲۰ — سنجه‌ی موفقیت این معماری چیست؟ زمان تغییر (Lead Time)، نرخ باگ پس از تغییر، زمان اجرای تست‌ها و هزینه‌ی onboarding. اگر این عدد پس از مهاجرت بهتر نشود، معماری فقط شکل گرفته، نه فایده بخشیده است.

بخش ۲۴پرسش‌های متداول (FAQ)

۱. نام «Onion» از کجا آمد؟ به خاطر حلقه‌های متحدالمرکز مانند لایه‌های پیاز؛ هر لایه‌ی بیرونی، لایه‌ی داخلی‌تر را می‌پوشاند و به آن وابسته است.
۲. آیا حتماً باید ۴ حلقه داشت؟ خیر. ۲–۴ حلقه معمول است؛ مهم جهت وابستگی است، نه تعداد دقیق.
۳. Onion همان Clean نیست؟ شبیه اما نه یکسان؛ Clean بر Use Case و قاعده‌ی وابستگی تأکید دارد، Onion بر تسلط Domain Model و حلقه‌ها.
۴. با کدام زبان بهتر است؟ همه‌ی زبان‌های شیءگرا (Java، Kotlin، C#، TS، Python) — پیش‌نیاز فقط Interface و DI است.
۵. جای Unit و Integration Test کجاست؟ Unit روی حلقه‌ی مرکز و Application Service (با Fake)؛ Integration روی پیاده‌سازی‌های بیرونی (DB واقعی).
۶. معنای DIP در این معماری؟ Dependency Inversion Principle: بیرونی‌ها interface‌های داخلی را پیاده‌سازی می‌کنند تا فلش وابستگی به مرکز برگردد.
۷. Entity فقیر (Anemic) ممنوع است؟ بله — Entityای که فقط getter/setter دارد، قانون را به بیرون می‌فرستد و مرکز بی‌ارزش می‌شود؛ رفتار و قانون را به حلقه‌ی Domain برگردانید.
۸. این معماری برای میکروسرویس هم خوب است؟ بله؛ هر سرویس می‌تواند داخل خودش پیازی باشد. مرز بین سرویس‌ها مسئله‌ی جدا (DDD Bounded Context) است.
۹. اگر ذخیره‌سازی چندگانه بخواهیم؟ دقیقاً بهترین حالت Onion: یک interface و چند پیاده‌سازی (PostgreSQL، MongoDB، فایل) که در Composition Root انتخاب می‌شوند.
۱۰. Framework چه نقشی دارد؟ فقط سیم‌کشی و جزئیات بیرونی. اگر Entity شما علامت JPA بگیرد، حلقه‌ی مرکز شکسته است.
۱۱. CQRS با Onion جور است؟ بله — جداسازی مسیر خواندن/نوشتن در Application Services قابل اعمال است و با حلقه‌ها تداخلی ندارد.
۱۲. رویدادهای دامنه کجا تعریف می‌شوند؟ در حلقه‌ی مرکز (مثل InvoiceIssued)؛ Listenerهای ایمیل/تحلیل در بیرون به آن وصل می‌شوند.
۱۳. چه ابزاری مرز را تضمین می‌کند؟ ArchUnit (JVM)، لینترهای import، جدا بودن ماژول‌ها و بررسی CI.
۱۴. برای شروع از کجا یاد بگیرم؟ SOLID و Repository Pattern، بعد یک پروژه‌ی کوچک را دستی حلقه‌ای کنید، سپس مقاله‌ی اصلی Palermo و کتاب Clean Architecture.
۱۵. سریع‌ترین راه اشتباه کردن چیست؟ کپی کردن ساختار پوشه‌ها بدون فهم «فلش وابستگی به کجاست؟» — ظاهر مرتب، جهت اشتباه.
