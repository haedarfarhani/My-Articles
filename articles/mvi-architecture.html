بخش ۱مقدمه: وقتی وضعیت در ده جا پخش است

یک صفحه‌ی جست‌وجوی زنده را تصور کنید: کاربر تایپ می‌کند، فیلتر دسته را عوض می‌کند، نتیجه‌ها بارگذاری می‌شوند، خطا رخ می‌دهد، کاربر دوباره تایپ می‌کند و درخواست قبلی باید لغو شود. حالا تصور کنید همه‌ی این وضعیت‌ها در فیلدهای مختلف یک ViewModel با setValue و postValue پخش شده باشد. 

// وضعیت MVVM برای جست‌وجوی زنده — وضعیت پراکنده

private MutableLiveData<String>      query    = ...;
private MutableLiveData<Category>    category  = ...;
private MutableLiveData<List<Item>>    results   = ...;
private MutableLiveData<Boolean>     loading   = ...;
private MutableLiveData<String>      error     = ...;
private MutableLiveData<Integer>     page      = ...;

  onQueryChanged → loading.postValue(true)
                 → results.postValue(fetch(q))
                 → loading.postValue(false)

  onCategoryChanged → results.postValue(fetch(newCategory))   // forgot loading!

  onPageChanged      → results.postValue(concat(page))        // forgot loading!

  onRetry            → results.postValue(fetch(query))        // forgot error=null

⚠️ هر متد جدید یعنی یک جای جدید برای فراموش کردن پاک کردن خطا

مشکل فقط «کد زیاد» نیست. مشکل این است که نمی‌دانید وضعیت صفحه در هر لحظه دقیقاً چیست. برای پاسخ به این سؤال که «الان اگر کاربر این دکمه را بزند چه می‌شود؟» باید چهار متد را بخوانید و مسیرهای جانبی را در ذهن اجرا کنید.

ریشه‌ی مشکل پراکندگی وضعیت و اثر جانبی پنهان. در MVI، وضعیت همیشه یک شیء واحد است و فقط از یک تابع خالص به‌دست می‌آید؛ بنابراین می‌توانید با خواندن یک امضای تابع، تمام رفتارهای ممکن صفحه را بفهمید.

بخش ۲تاریخچه و دلیل ایجاد

برخلاف MVC و MVP، MVI یک الگوی قدیمی و شناخته‌شده نیست. این نام را در سال‌های اخیر، در پیوند با موج تابع‌های خالص و برنامه‌نویسی تابعی در فرانت‌اند و اندروید رایج شد. ریشه‌ی فکری آن را می‌توان در سه جا دنبال کرد:

بسترچه اتفاقی افتاد؟
دهه‌ی ۱۹۸۰ — Elmالگوی Model → Update → View با تابع خالص؛ اولین شکل جدی MVI
۱۹۹۰s — Haskellمفهوم State خالص و عدم تکرار اثر جانبی تثبیت شد
۲۰۱۰s — Elm / Reactالگوی update(state, action) → state به‌طور گسترده استفاده شد
۲۰۱۶ — Cycle.jsنام MVI را برای ترکیب این مفاهیم به‌طور رسمی به کار برد
۲۰۱۸ — Kotlin/Multiplatformالگو به اشتراک‌گذاری منطق بین پلتفرم‌ها کمک کرد
۲۰۱۹ به بعد — Jetpack Composeچون Compose خودش یک مدل State دارد، MVI الگوی طبیعی شد
دلیل اصلی ایجاد سه نیاز: ۱) پیش‌بینی‌پذیری کامل — بدانید هر Intent چه State‌ای می‌سازد؛ ۲) تست‌پذیری با تابع خالص — بدون هیچ شبیه‌ساز؛ و ۳) اشتراک‌گذاری منطق بین چند پلتفرم بدون تکرار کد.

بخش ۳MVI چیست؟ (تعریف دقیق)

تعریف رسمی MVI (Model-View-Intent) الگویی است که کل وضعیت صفحه را در یک شیء State نگه می‌دارد و هیچ تغییری در آن مستقیماً انجام نمی‌شود. هر تعامل کاربر به یک Intent تبدیل می‌شود، یک تابع خالص به نام Reducer آن Intent و State قبلی را به State جدید تبدیل می‌کند، و View صرفاً State را نمایش می‌دهد. 
معادله‌ی بنیادین MVI:

  newState = reduce(currentState, intent)

قواعد:
  ۱) reduce  باید یک تابع خالص باشد
     - بدون ورودی جانبی (شبکه، فایل، ساعت، تصادفی)
     - بدون اثر جانبی (تغییر وضعیت مشترک، چاپ، نوشتن در فایل)
     - همیشه همان ورودی  →  همان خروجی

  ۲) State  باید تغییرناپذیر (immutable) باشد
     - هر تغییر یک شیء جدید می‌سازد

  ۳) View  فقط Intent می‌فرستد و State را نمایش می‌دهد
     - هیچ منطقی در View نیست
نقشمسئولیتمثال در Kotlin
Model / Stateکل وضعیت صفحه در یک شیء تغییرناپذیرdata class SearchState(...)
Viewنمایش State و ارسال Intent؛ بدون منطقComposable
Intentتوصیف آنچه کاربر می‌خواهد، نه اینکه چه اتفاقی بیفتدsealed interface SearchIntent
چرا Intent مهم است؟ Intent باید نیت کاربر را بیان کند، نه عمل فنی. به‌جای SetLoading(false) بنویسید SearchSucceeded(results)، و به‌جای ClearList() بنویسید UserConfirmedReset(). نتیجه: Intentها مستند و قابل مرور هستند — مثل فهرست API.
سوءتفاهم رایج MVI با MVVM یکی نیست، در حالی که هر دو ViewModel دارند. تفاوت در این است که MVVM چند منبع وضعیت دارد (LiveDataهای متعدد) و MVI یک منبع واحد (State) دارد که همه‌چیز را شامل می‌شود. این تفاوت، تمام مزایا و معایب MVI را توضیح می‌دهد.

بخش ۴مشکل قبل از استفاده

public class SearchViewModel extends ViewModel {

    private final MutableLiveData<String> query = new MutableLiveData<>();
    private final MutableLiveData<List<Item>> results = new MutableLiveData<>();
    private final MutableLiveData<Boolean> loading = new MutableLiveData<>();
    private final MutableLiveData<String> error = new MutableLiveData<>();
    private int currentPage = 1;
    private Category category = Category.ALL;

    public void onQueryChanged(String q) {
        // ۱) صفر کردن صفحه یادآوری نشده
        currentPage = 1;
        // ۲) پاک کردن خطا یادآوری نشده
        loading.setValue(true);
        search(q, category, 1, new Callback() {
            public void onSuccess(List<Item> items) {
                loading.setValue(false);
                results.setValue(items);
            }
            public void onError(Throwable t) {
                loading.setValue(false);
                error.setValue("خطا");
                // ۳) اگر پاسخ دیر برسد، وضعیت اشتباه نمایش داده می‌شود
            }
        });
    }

    public void onCategoryChanged(Category c) {
        category = c;
        onQueryChanged(query.getValue());   // ۴) فراخوانی متد با پارامتر null
    }

    public void onLoadMore() {
        currentPage++;
        // ۵) نتایج قبلی را جایگزین می‌کند، ترکیب نمی‌کند
        search(query.getValue(), category, currentPage, ...);
    }
}

بخش ۵ایده اصلی: سه پایه‌ی MVI

سه پایه‌ی MVI ۱) State واحد — همه‌ی وضعیت صفحه در یک شیء تغییرناپذیر.
۲) Intent صریح — هر کنش کاربر یک نوع مشخص با داده‌ی مشخص.
۳) تابع خالص — State جدید فقط از ترکیب State قبلی و Intent ساخته می‌شود.

چرا «تابع خالص» مهم‌ترین ویژگی است؟ تابع خالص یعنی reduce(s, i) == reduce(s, i) همیشه. این یعنی می‌توانید در تست، بدون شبکه و بدون شبیه‌ساز، بنویسید: «اگر این State و این Intent را بدهی، باید دقیقاً این State را بگیری.» این قوی‌ترین سطح تضمینی است که یک الگوی UI می‌تواند بدهد.

الگوی استاندارد MVI برای هر عملیات ناهمگام:

  ۱) View یک Intent می‌فرستد
  ۲) Reducer: loading = true ، داده قبلی حفظ می‌شود
  ۳) ViewModel اثر جانبی را اجرا می‌کند (شبکه/DB)
  ۴) نتیجه به‌صورت Intent جدید وارد می‌شود
  ۵) Reducer: loading = false ، نتیجه ذخیره می‌شود
  ۶) View State جدید را نمایش می‌دهد

نکته: در گام ۲ داده قبلی پاک نمی‌شود تا صفحه «چشمک» نزند؛
فقط loading = true می‌شود.
مدیریت پاسخ‌های خارج از ترتیب در MVI، هر Intent یک requestId می‌گیرد. در Reducer بررسی می‌کنید که این پاسخ مربوط به آخرین درخواست است؛ اگر نبود، آن را نادیده می‌گیرید. این کار رابطه‌ای در پیچیده‌ترین حالت‌ها را کاملاً قابل پیش‌بینی می‌کند.

بخش ۹مثال عملی کامل: موتور جست‌وجوی زنده

در این مثال یک صفحه‌ی جست‌وجوی زنده با فیلتر دسته‌بندی و بارگذاری صفحه‌ی بعد می‌سازیم. این دقیقاً همان سناریویی است که MVVM در بخش قبل با آن مشکل داشت. 

Intentهای این صفحه:

  SearchIntent.QueryChanged(query)      → کاربر تایپ کرد
  SearchIntent.CategorySelected(cat)    → فیلتر دسته تغییر کرد
  SearchIntent.LoadMoreRequested()      → اسکرول به پایین
  SearchIntent.RetryRequested()         → تلاش دوباره بعد از خطا
  SearchIntent.ResetRequested()         → پاک کردن جست‌وجو

State این صفحه:

  SearchState(
    query,          → متن فعلی جست‌وجو
    category,       → دسته‌ی انتخاب‌شده
    results,        → نتایج انباشته‌شده
    loading,        → آیا درخواست جاری است
    loadingMore,    → آیا صفحه‌ی بعد در حال بارگذاری است
    error,          → پیام خطا یا null
    page,           → شماره‌ی صفحه‌ی جاری
    hasMore         → آیا نتیجه‌ی بیشتری هست
  )

تست‌پذیری کامل:
  «QueryChanged("kotlin") با state اولیه داده‌شده
     → state.loading == true و page == 1 و error == null»
چرا این مثال سخت بود؟ در این صفحه چهار نوع بارگذاری وجود دارد (بار اول، فیلتر، صفحه‌ی بعد، تلاش دوباره)، سه نوع خطا ممکن است، و پاسخ درخواست‌ها می‌تواند خارج از ترتیج برسد. در MVVM این‌ها همگی به متدهای جداگانه و حافظه‌ی پنهان پخش می‌شدند. در MVI، همه‌ی این‌ها شش تابع کوچک در یک Reducer هستند.

بخش ۱۰پیاده‌سازی کد با Java 21

State و Intent

package com.example.core.mvi.search;

import java.util.Collections;
import java.util.List;

/** وضعیت کامل صفحه‌ی جست‌وجو — تغییرناپذیر، تنها منبع حقیقت. */
public final class SearchState {

    public enum Status { IDLE, LOADING, LOADING_MORE, READY, ERROR }

package com.example.core.mvi.search;

/**
 * تابع خالص. نه I/O می‌کند، نه زمان می‌خواند، نه تصادفی.
 * همیشه: (State, Intent) → State
 */
public final class SearchReducer {

    /** حداقل طول عبارت جست‌وجو برای ارسال درخواست. */
    private static final int MIN_QUERY_LENGTH = 2;

    private SearchReducer() {
    }

    public static SearchState reduce(SearchState state, SearchIntent intent) {
        return switch (intent) {
            case SearchIntent.QueryChanged q -> onQueryChanged(state, q);
            case SearchIntent.CategorySelected c -> onCategorySelected(state, c);
            case SearchIntent.LoadMoreRequested ignored -> onLoadMore(state);
            case SearchIntent.RetryRequested r -> onRetry(state, r);
            case SearchIntent.ResetRequested ignored -> SearchState.initial();
            case SearchIntent.SearchSucceeded s -> onSucceeded(state, s);
            case SearchIntent.SearchFailed f -> onFailed(state, f);
        };
    }

    private static SearchState onQueryChanged(SearchState s, SearchIntent.QueryChanged i) {
        SearchState base = s.toBuilder()
                .query(i.query())
                .errorMessage(null)
                .page(0)
                .hasMore(false)
                .latestRequestId(i.requestId())
                .build();

        if (i.query() == null || i.query().trim().length() < MIN_QUERY_LENGTH) {
            return base.toBuilder()
                    .status(SearchState.Status.IDLE)
                    .results(List.of())
                    .build();
        }
        return base.toBuilder()
                .status(SearchState.Status.LOADING)
                .build();
    }

    private static SearchState onCategorySelected(SearchState s, SearchIntent.CategorySelected i) {
        SearchState base = s.toBuilder()
                .category(i.category())
                .errorMessage(null)
                .page(0)
                .hasMore(false)
                .latestRequestId(i.requestId())
                .build();

        if (s.query().trim().length() < MIN_QUERY_LENGTH) {
            return base.toBuilder().status(SearchState.Status.IDLE).build();
        }
        return base.toBuilder().status(SearchState.Status.LOADING).build();
    }

    private static SearchState onLoadMore(SearchState s) {
        if (s.status() != SearchState.Status.READY || !s.hasMore()) {
            return s;   // در حال بارگذاری، یا صفحه‌ی آخر
        }
        return s.toBuilder()
                .status(SearchState.Status.LOADING_MORE)
                .build();
    }

    private static SearchState onRetry(SearchState s, SearchIntent.RetryRequested i) {
        if (s.query().trim().length() < MIN_QUERY_LENGTH) {
            return s.toBuilder().status(SearchState.Status.IDLE).build();
        }
        return s.toBuilder()
                .status(SearchState.Status.LOADING)
                .errorMessage(null)
                .page(0)
                .latestRequestId(i.requestId())
                .build();
    }

    private static SearchState onSucceeded(SearchState s, SearchIntent.SearchSucceeded i) {
        // قانون: پاسخ قدیمی را نادیده می‌گیریم
        if (i.requestId() != s.latestRequestId()) {
            return s;
        }
        return s.toBuilder()
                .results(i.items())
                .page(i.page())
                .hasMore(i.hasMore())
                .errorMessage(null)
                .status(SearchState.Status.READY)
                .build();
    }

    private static SearchState onFailed(SearchState s, SearchIntent.SearchFailed i) {
        if (i.requestId() != s.latestRequestId()) {
            return s;
        }
        return s.toBuilder()
                .errorMessage(i.message())
                .status(SearchState.Status.ERROR)
                .build();
    }
}

/**
 * فقط دو کار دارد:
 * ۱) نگه‌داری State و اجرای Reducer
 * ۲) اجرای اثرات جانبی و بازگرداندن نتیجه به‌صورت Intent
 */
public final class SearchViewModel {

    private final SearchRepository repository;
    private final AtomicLong requestIds = new AtomicLong();

    private SearchState state = SearchState.initial();
    private StateListener listener = state -> { };

    public interface StateListener {
        void onState(SearchState state);
    }

    public SearchViewModel(SearchRepository repository) {
        this.repository = repository;
    }

    public SearchState state() {
        return state;
    }

    public void setListener(StateListener listener) {
        this.listener = listener;
        listener.onState(state);
    }

    /** تنها ورودی View به ViewModel. */
    public void dispatch(SearchIntent intent) {
        state = SearchReducer.reduce(state, intent);
        listener.onState(state);
        executeSideEffects(intent);
    }

    private void executeSideEffects(SearchIntent intent) {
        switch (intent) {
            case SearchIntent.QueryChanged q ->
                    performSearch(q.query(), q.category(), 1, q.requestId());
            case SearchIntent.CategorySelected c ->
                    performSearch(state.query(), c.category(), 1, c.requestId());
            case SearchIntent.RetryRequested r ->
                    performSearch(state.query(), state.category(), 1, r.requestId());
            case SearchIntent.LoadMoreRequested ignored ->
                    performSearch(state.query(), state.category(),
                            state.page() + 1, state.latestRequestId());
            case SearchIntent.SearchSucceeded s -> { }
            case SearchIntent.SearchFailed f -> { }
        }
    }

    private void performSearch(String query, SearchState.Category category,
                               int page, long requestId) {
        if (query == null || query.trim().length() < 2) {
            return;
        }
        repository.search(query, category, page, new SearchCallback() {
            @Override
            public void onSuccess(List<Item> items, int totalFound) {
                dispatch(new SearchIntent.SearchSucceeded(
                        items, page, page * PAGE_SIZE < totalFound, requestId));
            }

            @Override
            public void onError(Throwable error) {
                dispatch(new SearchIntent.SearchFailed(
                        "جست‌وجو ناموفق بود", requestId));
            }
        });
    }

    public long nextRequestId() {
        return requestIds.incrementAndGet();
    }

    private static final int PAGE_SIZE = 20;
}

بخش ۲۱مثال در پروژه واقعی

۱) اپ چت با Jetpack Compose و MVI

در اپ‌های چت، MVI انتخاب طبیعی است. هر صفحه‌ی گفت‌وگو یک State دارد که شامل لیست پیام‌ها، وضعیت تایپ، وضعیت اتصال و صفحه‌بندی است. پیام‌های جدید با Intent MessageReceived وارد می‌شوند و با requestId از تداخل بین بارگذاری اولیه و پیام زنده جلوگیری می‌شود. به‌علاوه، چون State یک شیء واحد است، می‌توان کل تاریخچه‌ی گفت‌وگو را برای دیباگ لاگ کرد.

۲) اپ فین‌تک با MVI

در اپ‌های بانکی و پرداخت، MVI یک الزام عملی است: وقتی کاربر تراکنش را تأیید می‌کند، Intent TransferConfirmed ارسال می‌شود و Reducer به‌صورت قطعی وضعیت را به PROCESSING تغییر می‌دهد. اگر پاسخ شبکه دیر برسد، requestId آن را نادیده می‌گیرد. این سطح از قطعیت برای سیستم‌های مالی ضروری است.

۳) اپ فروشگاهی با جست‌وجوی زنده

همین مثال بخش ۹ در پروژه‌ی واقعی استفاده می‌شود: فیلتر دسته، جست‌وجو با debounce، بارگذاری صفحه‌ی بعد و نمایش خطا. در MVVM این صفحه حدود ۲۰۰ خط ViewModel با ده‌ها حالت ممکن داشت؛ در MVI به ۹۰ خط Reducer و ۸۰ خط ViewModel تبدیل شد و همه‌ی حالت‌های ممکن با یک نگاه قابل شمارش هستند.

۴) اپ پخش ویدئو با Compose

در اپ‌های پخش ویدئو، وضعیت پخش (پخش/توقف/جلو/عقب/بارگذاری) یک ماشین حالت پیچیده است. با MVI، هر رویداد پخش‌کننده یک Intent است و Reducer ماشین حالت را مدیریت می‌کند. نتیجه: ترتیب درست پیام‌های ویدئو حتی وقتی رویدادها با تأخیر و خارج از ترتیب می‌رسند.

۵) پروژه‌های Kotlin Multiplatform

در تیم‌هایی که منطق را بین Android، iOS و دسکتاپ به اشتراک می‌گذارند، MVI بیشترین صرفه‌جویی را ایجاد می‌کند. منطق، State و Intent در ماژول shared نوشته می‌شود و commonTest یک بار نوشته و در همه‌ی پلتفرم‌ها اجرا می‌شود. این در تیم‌های چندسکویی چند برابر صرفه‌جویی در زمان تست می‌آورد.

بخش ۲۳۲۰ سؤال مصاحبه

سطح Junior
سؤال ۱ — MVI چیست؟ الگوی معماری با سه نقش: Model/State (وضعیت کامل صفحه)، View (نمایش منفعل) و Intent (توصیف نیت کاربر). وضعیت فقط از طریق یک تابع خالص به‌نام Reducer تغییر می‌کند.
سؤال ۲ — سه جزء اصلی MVI چیست؟ State (وضعیت تغییرناپذیر)، Intent (رویداد نیت کاربر) و Reducer (تابع خالصی که State جدید را از State قبلی و Intent می‌سازد).
سؤال ۳ — Intent دقیقاً چیست؟ یک شیء که نیت کاربر را توصیف می‌کند، نه عمل فنی را. مثلاً SearchIntent.QueryChanged("kotlin") به‌جای SetQueryFieldValue.
سؤال ۴ — تابع خالص یعنی چه؟ تابعی که فقط به ورودی‌هایش وابسته است، هیچ اثر جانبی ندارد و همیشه همان ورودی را به همان خروجی تبدیل می‌کند. یعنی نه I/O، نه زمان، نه تصادفی.
سؤال ۵ — تفاوت MVI و MVVM چیست؟ MVVM چند LiveData جدا دارد و ViewModel مستقیم آن‌ها را تغییر می‌دهد. MVI یک State واحد دارد و تغییر وضعیت فقط از طریق تابع خالص Reducer انجام می‌شود.
سؤال ۶ — جریان داده در MVI چیست؟ View → Intent → ViewModel → Reducer → State → View. این جریان یک‌طرفه است و در هیچ نقطه‌ای حلقه نمی‌خورد.
سؤال ۷ — چرا State باید تغییرناپذیر باشد؟ تا وقتی State جدید ساخته می‌شود، وضعیت قبلی دست‌نخورده می‌ماند. این باعث می‌شود بتوانید تاریخچه را نگه دارید، از باگ‌های حالت جلوگیری کنید و در تست State قبلی را دوباره استفاده کنید.
سؤال ۸ — Side Effect کجاست؟ بیرون از Reducer. شبکه، دیتابیس و تایمر در ViewModel یا لایه‌ی Repository انجام می‌شود و نتیجه‌شان دوباره به‌صورت Intent وارد می‌شود.
سؤال ۹ — چطور یک Intent تعریف می‌کنیم؟ به‌صورت sealed interface در Kotlin یا یک interface با پیاده‌سازی‌های record در Java. مزیت sealed این است که همه‌ی حالت‌ها در یک فایل و قابل مرور هستند.
سؤال ۱۰ — چرا از requestId استفاده می‌کنیم؟ برای مدیریت درخواست‌های ناهمگام. اگر کاربر سریع تایپ کند، چند درخواست هم‌زمان در جریان است؛ requestId مشخص می‌کند کدام پاسخ معتبر است.
سطح Mid
سؤال ۱۱ — چطور تست Reducer بنویسیم؟ کافی است (State, Intent) بدهید و State خروجی را بررسی کنید. نه Mock لازم است، نه شبکه، نه Main Thread. این سریع‌ترین نوع تست موجود است.
سؤال ۱۲ — تفاوت Intent کاربر و Intent بیرونی چیست؟ Intent کاربر از تعامل مستقیم (کلیک، تایپ) می‌آید و Intent بیرونی از نتیجه‌ی عملیات (پاسخ شبکه، رویداد سیستم). هر دو از یک مسیر وارد چرخه می‌شوند، اما در Reducer جدا پردازش می‌شوند.
سؤال ۱۳ — آیا MVI برای صفحات ساده مناسب است؟ خیر. برای یک دکمه‌ی ساده، ساختن sealed interface و State و Reducer، اضافه‌کاری است. MVI ارزشش را از پیچیدگی وضعیت می‌گیرد.
سؤال ۱۴ — چطور Effect یک‌بارمصرف (ناوبری) مدیریت می‌شود؟ با یک Channel با بافر ۱ یا SharedFlow. اگر از State استفاده کنید، با چرخش صفحه دوباره اجرا می‌شود.
سؤال ۱۵ — چطور State بزرگ را مدیریت کنیم؟ آن را به چند State کوچک‌تر تقسیم کنید (مثلاً SearchState و CartState). این کار هم کارایی و هم خوانایی را بهبود می‌دهد.
سؤال ۱۶ — MVI و Compose چه رابطه‌ای دارند؟ مدل State ذاتی Compose است: «وقتی state عوض شود، دوباره ترکیب کن». MVI همین ایده را به قانون تبدیل می‌کند و به‌علاوه قواعد سخت‌گیرانه‌ای (تابع خالص، Intent مشخص) اضافه می‌کند.
سؤال ۱۷ — چطور پاسخ‌های خارج از ترتیب را مدیریت می‌کنیم؟ با requestId: هنگام ارسال درخواست یک شناسه می‌سازیم و در State نگه می‌داریم. وقتی پاسخ می‌رسد، در Reducer بررسی می‌کنیم که requestId پاسخ با آخرین درخواست یکی است؛ اگر نبود، آن را نادیده می‌گیریم.
سطح Senior
سؤال ۱۸ — بزرگ‌ترین چالش MVI چیست؟ مدیریت اندازه‌ی State و تعداد Intentها. با رشد صفحه، State بزرگ و Intentها زیاد می‌شوند. راه‌حل: تقسیم به چند MVI کوچک‌تر (MVI سلسله‌مراتبی) یا استفاده از زیر‌وضعیت‌های مستقل.
سؤال ۱۹ — MVI چه زمانی از MVP بهتر است؟ وقتی وضعیت صفحه چندحالته و پیچیده است و درخواست‌های ناهمگام دارید. MVP برای صفحات ساده‌تر با جریان خطی مناسب‌تر است، چون کد کمتری لازم دارد.
سؤال ۲۰ — چگونه MVI را در پروژه‌ی بزرگ‌تر مقیاس‌پذیر می‌کنیم؟ با تقسیم‌بندی Feature-Based هر فیچر MVI مستقل خودش را دارد، و در صورت نیاز با استفاده از ماژول مشترک در Kotlin Multiplatform برای اشتراک منطق بین پلتفرم‌ها.

بخش ۲۴پرسش‌های متداول (FAQ)

پرسش‌های پرتکرار
۱) تفاوت MVI و MVVM دقیقاً چیست؟ MVVM چند منبع وضعیت مستقل (LiveData) دارد و ViewModel آن‌ها را مستقیم تغییر می‌دهد. MVI یک State واحد دارد که فقط از طریق یک تابع خالص به‌روزرسانی می‌شود. نتیجه: در MVVM ممکن است ناسازگاری بین LiveDataها رخ دهد، در MVI نه.
۲) آیا MVI همان Redux است؟ بله، تقریباً. هر دو یک ایده دارند: State واحد، Action/Intent واحد، و Reducer خالص. تفاوت‌ها در واژگان و اکوسیستم ابزار است.
۳) چرا MVI برای Compose بهتر است؟ چون Compose خودش یک مدل State دارد و با تغییر State دوباره ترکیب می‌کند. MVI این را به یک قانون سخت تبدیل می‌کند: State فقط از Intent تغییر می‌کند.
۴) آیا Reducer می‌تواند suspend باشد؟ توصیه نمی‌شود. اگر Reducer suspend باشد، دیگر تابع خالص نیست و تست آن سخت می‌شود. به‌جای آن، عملیات ناهمگام را در ViewModel انجام دهید و نتیجه را به‌صورت Intent برگردانید.
۵) State باید چقدر بزرگ باشد؟ اگر بیش از ۱۵ فیلد دارد یا شامل لیست بزرگ است، آن را تقسیم کنید. قانون عملی: اگر نمی‌توانید در یک نگاه بگویید «این State چه چیزهایی را توصیف می‌کند»، بیش از حد بزرگ است.
۶) آیا MVI برای پروژه‌های کوچک مناسب است؟ خیر، مگر اینکه از Kotlin Multiplatform استفاده کنید یا تیم به‌شدت تست‌محور باشد. در غیر این صورت، هزینه‌ی پیاده‌سازی از مزیتش بیشتر است.
۷) چطور با MVI و ViewBinding کار کنیم؟ می‌شود، اما توصیه نمی‌شود. در ViewBinding، State را باید دستی در Fragment به UI منتقل کنید. این کار کار MVI را می‌کند. در Compose، State مستقیماً به Composable داده می‌شود.
۸) آیا MVI و لایه‌بندی می‌توانند با هم استفاده شوند؟ بله و این ترکیب بسیار رایج است. MVI در لایه‌ی Presentation (الگوی ارتباط با UI) و لایه‌بندی در سطح کل سیستم. در پروژه‌های بزرگ، منطق کسب‌وکار در لایه‌ی Domain قرار می‌گیرد و MVI فقط لایه‌ی UI را مدیریت می‌کند.
۹) Intent باید چه اطلاعاتی داشته باشد؟ همه‌ی اطلاعات لازم برای پردازش آن رویداد. اگر Intent فقط بگوید «کاربر کلیک کرد» و ViewModel مجبور باشد از View بپرسد «روی چه چیزی؟»، مرز MVI شکسته شده است.
۱۰) چطور State اولیه را تعریف کنیم؟ با یک متد initial() یا IdleState. این حالت باید صریح باشد تا در تست و در بازسازی وضعیت قابل استفاده باشد.
۱۱) آیا MVI برای وب هم کاربرد دارد؟ بله. الگوی Reducer در React/Redux، و الگوی مشابه در Vue و Svelte هم دقیقاً MVI است. فقط واژگان فرق می‌کند.
۱۲) چطور لاگ و دیباگ می‌کنیم؟ چون همه‌ی تغییرات از مسیر Intent می‌گذرند، می‌توانید در ViewModel یک لاگ از هر Intent و State حاصل بنویسید. این که «مسیر کاربر» را به‌طور کامل بازسازی کنید، در MVVM تقریباً غیرممکن است.
۱۳) آیا همیشه باید از sealed interface استفاده کرد؟ در Kotlin، بله — این بهترین راه است چون همه‌ی حالت‌ها در یک فایل هستند و کامپایلر شما را مجبور می‌کند همه‌ی حالت‌ها را در when پوشش دهید.
۱۴) چطور از نادیده گرفتن خطا جلوگیری کنیم؟ همیشه در Intentهای موفق، error = null قرار دهید و در Intentهای ناموفق، خطا را تنظیم کنید. این باعث می‌شود وضعیت خطا هرگز «گیر نکند».
۱۵) آیا MVI برای صفحات با فرم ساده لازم است؟ نه. برای فرم‌های ساده، MVVM یا حتی یک ViewModel ساده کافی است. MVI زمانی لازم می‌شود که وضعیت چندحالته و درخواست‌های ناهمگام داشته باشید.

جمع‌بندی

MVI اوج تلاش برای رسیدن به قطعیت کامل در رفتار رابط کاربری است. اینکه بدانید هر تعامل کاربر چه نتیجه‌ای دارد، نه تقریبی بلکه دقیق.

این قطعیت هزینه دارد: کد بیشتر، State بزرگ‌تر و منحنی یادگیری تندتر. اما برای اپ‌هایی که وضعیت پیچیده دارند، درخواست‌های ناهمگام دارند و تست‌پذیری برایشان حیاتی است، این هزینه کاملاً ارزشش را دارد.

نکته‌ی مهمی که باید به خاطر بسپارید: MVI زیرمجموعه‌ای از تفکر «حالت» است، نه یک الگوی جداگانه. اگر تفکر حالت (state machine) را بفهمید، همه‌ی الگوهای دیگر هم برایتان روشن می‌شود.

پیام پایانی سری ۱۴ مقاله‌ای این مقاله هشتمین عضو سری «معماری‌های نرم‌افزاری» است و آخرین عضو بخش الگوهای UI. شما اکنون چهار الگوی کلاسیک (MVC، MVP، MVVM، MVI) را با یک زبان مشترک می‌شناسید. در ادامه سری به سمت الگوها و معماری‌های سطح بالاتر می‌رویم: Repository Pattern، DDD، Feature-Based، Event-Driven، CQRS و Microservices.
