بخش ۱مقدمه: وقتی کد بدون ساختار فرو می‌ریزد

فرض کنید تیم شما یک اپلیکیشن فروشگاهی ساده می‌نویسد. ماه اول همه‌چیز خوب است؛ یک کلاس OrderService دارد که هم سفارش می‌سازد، هم قیمت را حساب می‌کند، هم به دیتابیس وصل می‌شود. ماه ششم کلاس به ۲۰۰۰ خط رسیده و هر تغییر کوچک، سه باگ جدید می‌سازد.

مشکل این کد «بد بودنِ نویسنده» نیست؛ مشکل این است که ساختاری برای نگه‌داشتن آن وجود ندارد. وقتی مسئولیت‌ها در یک فایل جمع شوند، هیچ قانونی جلوی رشد بی‌وقفه‌اش را نمی‌گیرد. Layered Architecture دقیقاً برای همین ساخته شده: کد را به لایه‌هایی با مسئولیت مشخص تقسیم کن و بین آن‌ها فقط اجازه‌ی عبور رو به پایین بده. 

OrderService.java — ۲۰۰۰ خط، ۱۴ مسئولیت:

  ✅ ساخت سفارش        ✅ محاسبه‌ی مالیات       ✅ اعتبارسنجی کارت
  ✅ اتصال JDBC        ✅ مدیریت تراکنش        ✅ کش کردن
  ✅ ارسال ایمیل       ✅ لاگ خطا              ✅ ساخت PDF فاکتور
  ✅ تبدیل به DTO      ✅ مدیریت انبار        ❌ و ...


میانگین زمان یک تغییر کوچک در این کد: ۴ ساعت.
میانگین زمان همان تغییر بعد از لایه‌بندی: ۲۵ دقیقه.
نکته‌ی کلیدی این مقاله لایه‌بندی ساده‌ترین معماری‌های نرم‌افزاری است و برای بیشتر پروژه‌های دنیای واقعی کافی و درست است. اشتباه رایج این است که یا آن را دست‌کم بگیریم و بی‌ساختار کد بنویسیم، یا بیش از حد لایه بسازیم. این مقاله هر دو دام را نشان می‌دهد.

بخش ۲تاریخچه و دلیل ایجاد

ریشه‌ی معماری لایه‌ای به دهه‌ی ۱۹۷۰ برمی‌گردد؛ زمانی که سیستم‌های بزرگ مدیریتی (مثل IBM mainframe) برای اولین بار به چند «سطح» تقسیم شدند. نام مشهور این رویکرد N-Tier Architecture است که یک زیرمجموعه‌ی Multi-Tier به شمار می‌رود.

بسترچه اتفاقی افتاد؟
دهه‌ی ۱۹۷۰ — Mainframeمفهوم Presentation / Business / Data برای جداسازی کاربری از پردازش و ذخیره‌سازی شکل گرفت
دهه‌ی ۱۹۹۰ — Client/Serverلایه‌ی UI از سرور جدا شد و منطق روی سرور متمرکز شد
دهه‌ی ۱۹۹۰ — توسعه‌ی سریع و بی‌نظمپروژه‌ها «Spaghetti» شدند؛ لایه‌بندی به‌عنوان پاسخ عملی پذیرفته شد
۱۹۹۷ — Microsoft Three-Tierمدل Presentation / Business Logic / Data Access به‌عنوان استاندارد صنعتی رسمی شد
۲۰۰۰ — Spring / Hibernateلایه‌بندی به‌صورت پیش‌فرض در پروژه‌های Java رایج شد
۲۰۱۲ به بعد — Clean / Onionمعماری‌های پیشرفته‌تر برای حل محدودیت‌های لایه‌بندی کلاسیک پیشنهاد شدند
دلیل اصلی ایجاد سه نیاز عملی: ۱) تقسیم مسئولیت‌ها تا کد قابل فهم باشد، ۲) جداسازی رابط کاربری از منطق تا بتوان منطق را بدون UI تست کرد، ۳) قابلیت تعویض لایه‌ها — مثلاً عوض کردن JPA با یک API بدون دست‌زدن به منطق.

بخش ۳Layered Architecture چیست؟ (تعریف دقیق)

تعریف رسمی Layered Architecture روشی برای سازمان‌دهی کد است که منطق برنامه را به لایه‌های افقی با مسئولیت مشخص تقسیم می‌کند؛ در این ساختار، هر لایه فقط می‌تواند لایه‌های پایین‌تر خود را صدا بزند و هرگز اجازه‌ی تماس مستقیم با لایه‌های بالاتر یا کناری را ندارد.
✅ هست…❌ نیست…
تقسیم‌بندی کد بر اساس مسئولیت در پوشه‌ها و ماژول‌هاالزام به مرکزیت Domain — این تفاوت اصلی با Onion/Clean است
قاعده‌ی ساده‌ی وابستگی یک‌طرفه رو به پایینیک کتابخانه یا Framework خاص
امکان تست جداگانه‌ی هر لایه با Mock کردن لایه‌ی پایینDesign Pattern مشخصی به‌تنهایی
امکان نگه‌داشتن لایه‌ی Presentation چندباره (وب، موبایل، CLI)استقلال کامل از دیتابیس (این کار Clean Architecture است)
سوءتفاهم رایج لایه‌بندی با «چند تا پوشه ساختن» فرق دارد. اگر لایه‌ی Service بتواند مستقیم از لایه‌ی Data Repository صدا بزند و Repository هم منطق کسب‌وکار داشته باشد، شما فقط پوشه‌بندی کرده‌اید، نه لایه‌بندی.

بخش ۴مشکل قبل از استفاده

همان اپلیکیشن فروشگاهی را قبل از لایه‌بندی ببینید:

@RestController
public class OrderController {

    private final DataSource dataSource;
    private final EmailSender emailSender;

    @PostMapping("/orders")
    public ResponseEntity<?> create(@RequestBody String json) {
        // ۱) پارس کردن JSON دستی
        // ۲) اتصال مستقیم به دیتابیس
        try (Connection conn = dataSource.getConnection()) {
            PreparedStatement ps = conn.prepareStatement(
                "INSERT INTO orders (total) VALUES (?)");
            ps.setBigDecimal(1, calculateTotal(json)); // ۳) منطق کسب‌وکار
            ps.executeUpdate();
        } catch (SQLException e) {
            emailSender.sendError(e);                  // ۴) اعلان خطا
            return ResponseEntity.status(500).build(); // ۵) تصمیم HTTP
        }
        return ResponseEntity.ok().build();             // ۶) پاسخ
    }
}
نشانهچرا دردسرساز است؟
SQL داخل Controllerتست این کد نیاز به دیتابیس واقعی دارد
پنج مسئولیت در یک کلاسنقض کامل SRP؛ تغییر هر بخش، بقیه را می‌شکند
تبدیل JSON با کد دستیخطاهای مبهم در زمان اجرا به‌جای زمان کامپایل
منطق مالیات داخل حلقه‌ی دیتابیسقانون تجاری به زیرساخت چسبیده و مهاجرت را سخت می‌کند
نبود امکان استفاده‌ی CLI یا Jobهر ورودی جدید باید منطق را کپی کند
بعد از لایه‌بندی:

HTTP Request
   ↓
[Presentation]   Controller — فقط: اعتبارسنجی شکل داده + تبدیل به DTO
   ↓
[Service]        OrderService — فقط: هماهنگی و تراکنش
   ↓
[Domain]         Order, Money, TaxRule — فقط: قوانین کسب‌وکار (بدون هیچ وابستگی بیرونی)
   ↓
[Data]           JpaOrderRepository, JdbcTemplate — فقط: گفت‌وگو با دیتابیس

هر پیکان یک‌طرفه است. هیچ لایه‌ای به بالا برنمی‌گردد.

بخش ۵ایده اصلی: تقسیم به لایه‌ها

ایده‌ی مرکزی ساده است: هر لایه یک سؤال را جواب می‌دهد. اگر نتوانید برای یک لایه در یک جمله بگویید «این لایه فقط مسئول چیست؟»، آن لایه را اشتباه ساخته‌اید.

لایهسؤالی که جواب می‌دهدممنوعیت کلیدی
Presentationورودی کاربر چیست و چه نمایشی بدهیم؟نباید منطق کسب‌وکار داشته باشد
Service / Applicationبرای این Use Case چه کارهایی و با چه ترتیبی؟نباید قوانین دامنه را دوباره بنویسد
Domain / Businessقانون کسب‌وکار چیست؟نباید به DB یا Framework وابسته باشد
Data / Infrastructureداده چطور خوانده و ذخیره می‌شود؟نباید تصمیم تجاری بگیرد
قانون طلایی وابستگی پیکان‌ها همیشه رو به پایین هستند. هرگز Domain → JPA، هرگز Data → Service. اگر مجبور شدید فلشی رو به بالا یا موربی بکشید، معمولاً یک قرارداد را در لایه‌ی پایین‌تر جا انداخته‌اید؛ در حالی که جای درستش یک لایه بالاتر است.

بخش ۶ساختار معماری: لایه‌ها

لایه‌بندی رایج دو شکل دارد: سه‌لایه‌ای کلاسیک و چهارلایه‌ای با Service Layer. در پروژه‌های جدید، فرم چهارلایه‌ای را ترجیح می‌دهیم چون کنترل تراکنش و مرز Use Case روشن‌تر می‌شود.

لایهمسئولیتکلاس‌های نمونه
Presentationدریافت درخواست، اعتبارسنجی شکلی، نگاشت به DTO و ساخت پاسخOrderController، OrderRequest، OrderResponse
Application (Service)اجرای Use Case، مدیریت تراکنش، انتخاب Repository مناسبOrderService، CheckoutUseCase
DomainEntity، مقدار شیئی، قوانین و Domain ServiceOrder، Money، TaxPolicy
Dataپیاده‌سازی Repository، نقشه‌ی Entity/DTO، پیکربندی DBJpaOrderRepository، OrderRow

نکته‌ی مهم درباره‌ی لایه‌ی Domain در لایه‌بندی کلاسیک: برخلاف Onion یا Clean، لایه‌ی Domain معمولاً خالی یا بسیار نازک است و منطق بیشتر در Service Layer قرار می‌گیرد. این تفاوت را در بخش مقایسه دقیق‌تر بررسی می‌کنیم.

لایه‌ی افقی (Cross-cutting) امنیت، لاگ، تراکنش، کش و اعلان معمولاً بین لایه‌ها پخش‌اند. آن‌ها را در ماژول جدا نگه دارید (AOP، Filter، Interceptor) تا لایه‌های اصلی از آن‌ها پر نشوند.

بخش ۷جریان داده (Data Flow)

دو جریان اصلی داریم: جریان رو به پایین (درخواست) و جریان رو به بالا (پاسخ و داده). در لایه‌بندی کلاسیک، جریان داده فقط یک‌طرفه و زنجیره‌ای است. 

قواعد جریان داده در Layered:

۱) داده همیشه از بالا وارد و از پایین برمی‌گردد.
۲) Controller هرگز Repository را مستقیم صدا نمی‌زند (مگر در پروژه‌های خیلی کوچک CRUD).
۳) لایه‌ی Domain داده را از بیرون نمی‌گیرد؛ ورودی آن پارامترهای ساده است.
۴) Entity دامنه هرگز به ViewModel یا DTO تبدیل نمی‌شود؛ تبدیل در Presentation انجام می‌شود.
۵) هیچ داده‌ای از لایه‌ی پایین به لایه‌ی بالا «call-back» نمی‌کند.
جریان داده و Circular Dependency اگر مجبور شدید از لایه‌ی پایین، متدی از لایه‌ی بالا را صدا بزنید (مثلاً Repository که Service را صدا می‌زند)، مدل لایه‌ای شکسته است. این دقیقاً همان جایی است که تیم‌ها می‌گویند «لایه‌بندی برای پروژه‌ی ما کافی نبود».

بخش ۹مثال عملی کامل: سیستم فاکتور

در بخش‌های بعد کد کامل همین مثال را با Java 21 می‌بینیم. فعلاً تصویر کلی سناریو را مرور کنیم:

  • کاربر یا سیستم فروشنده یک سفارش ثبت می‌کند.
  • سیستم قیمت کالا را می‌خواند، تخفیف و مالیات را محاسبه می‌کند.
  • سفارش ذخیره و یک فاکتور تولید می‌شود.
  • وضعیت سفارش تغییر می‌کند و اعلان ارسال می‌شود.
Use Case: ثبت سفارش

  ۱) Controller  →  OrderService.createOrder(command)
  ۲) Service     →  کش را چک می‌کند (Read-through)
  ۳) Service     →  ProductRepository از Data Layer
  ۴) Service     →  Order (Domain) می‌سازد و قوانین را اجرا می‌کند
  ۵) Service     →  OrderRepository.save() + InvoiceRepository.save()
  ۶) Service     →  @Transactional ثبت می‌شود
  ۷) Controller  →  OrderResponse برمی‌گرداند
مسئولیت هر لایه در این سناریو Presentation: JSON را به Command تبدیل می‌کند و خطا را به Status Code ترجمه می‌کند.
Service: ترتیب اجرا، مدیریت تراکنش و انتخاب مسیر کش را تعیین می‌کند.
Domain: قانون «سفارش باید حداقل یک قلم داشته باشد» و محاسبه‌ی مالیات را نگه می‌دارد.
Data: اجرای SELECT و INSERT و ترجمه‌ی ردیف دیتابیس به Entity.

بخش ۱۰پیاده‌سازی کد با Java 21

لایه ۴ — داده (Infrastructure)

package com.app.order.infrastructure.persistence;

import java.util.Optional;

/** قرارداد ذخیره‌سازی سفارش — این Interface متعلق به لایه‌ی بالاتر است. */
public interface OrderStore {
    Optional<OrderView> findById(String orderId);
    void save(OrderRecord record);
}

package com.app.order.infrastructure.persistence;

import java.sql.Connection;
import java.sql.PreparedStatement;
import java.sql.ResultSet;
import java.sql.SQLException;
import java.util.Optional;

/** تنها کلاسی که حرف JDBC می‌زند؛ هیچ قانون کسب‌وکاری اینجا نیست. */
public final class JdbcOrderStore implements OrderStore {

    private final DataSourceProvider dataSource;

    public JdbcOrderStore(DataSourceProvider dataSource) {
        this.dataSource = dataSource;
    }

    @Override
    public Optional<OrderView> findById(String orderId) {
        String sql = """
                SELECT id, customer_id, status, total_cents
                FROM orders
                WHERE id = ?
                """;
        try (Connection conn = dataSource.get();
             PreparedStatement ps = conn.prepareStatement(sql)) {
            ps.setString(1, orderId);
            try (ResultSet rs = ps.executeQuery()) {
                return rs.next()
                        ? Optional.of(map(rs))
                        : Optional.empty();
            }
        } catch (SQLException e) {
            throw new StorageException("خواندن سفارش ناموفق بود", e);
        }
    }

    @Override
    public void save(OrderRecord record) {
        String sql = """
                INSERT INTO orders (id, customer_id, status, total_cents)
                VALUES (?, ?, ?, ?)
                """;
        try (Connection conn = dataSource.get();
             PreparedStatement ps = conn.prepareStatement(sql)) {
            ps.setString(1, record.id());
            ps.setString(2, record.customerId());
            ps.setString(3, record.status().name());
            ps.setLong(4, record.total().cents());
            ps.executeUpdate();
        } catch (SQLException e) {
            throw new StorageException("ذخیره‌ی سفارش ناموفق بود", e);
        }
    }

    private OrderView map(ResultSet rs) throws SQLException {
        return new OrderView(
                rs.getString("id"),
                rs.getString("customer_id"),
                OrderStatus.valueOf(rs.getString("status")),
                Money.ofCents(rs.getLong("total_cents")));
    }
}

package com.app.order.domain.model;

import java.math.BigDecimal;
import java.math.RoundingMode;
import java.util.List;

public record Money(BigDecimal amount, String currency) {

    public Money {
        if (currency == null || currency.isBlank()) {
            throw new IllegalArgumentException("واحد پول الزامی است");
        }
    }

    public Money add(Money other) {
        if (!currency.equals(other.currency)) {
            throw new IllegalStateException("جمع دو پول متفاوت ممکن نیست");
        }
        return new Money(amount.add(other.amount), currency);
    }

    public Money multiply(BigDecimal factor) {
        return new Money(
                amount.multiply(factor).setScale(2, RoundingMode.HALF_UP),
                currency);
    }

    public static Money ofCents(long cents) {
        return new Money(BigDecimal.valueOf(cents, 2), "IRR");
    }
}

package com.app.order.domain.model;

import java.math.BigDecimal;
import java.util.ArrayList;
import java.util.List;

public final class Order {

    private final String id;
    private final String customerId;
    private final List<OrderLine> lines = new ArrayList<>();
    private OrderStatus status;
    private Money total;

    private Order(String id, String customerId) {
        this.id = id;
        this.customerId = customerId;
        this.status = OrderStatus.DRAFT;
        this.total = new Money(BigDecimal.ZERO, "IRR");
    }

    public static Order draft(String id, String customerId) {
        if (customerId == null || customerId.isBlank()) {
            throw new IllegalArgumentException("سفارش بدون مشتری معتبر نیست");
        }
        return new Order(id, customerId);
    }

    /** قانون تجاری: سفارش باید حداقل یک قلم داشته باشد. */
    public void addLine(OrderLine line) {
        if (status != OrderStatus.DRAFT) {
            throw new IllegalStateException("سفارش تأییدشده قابل تغییر نیست");
        }
        lines.add(line);
        total = total.add(line.subtotal());
    }

    /** قانون تجاری: بدون قلم نمی‌توان سفارش را نهایی کرد. */
    public void confirm() {
        if (lines.isEmpty()) {
            throw new IllegalStateException("سفارش بدون قلم قابل تأیید نیست");
        }
        status = OrderStatus.CONFIRMED;
    }

    public String id() {
        return id;
    }

    public String customerId() {
        return customerId;
    }

    public Money total() {
        return total;
    }

    public OrderStatus status() {
        return status;
    }

    public int lineCount() {
        return lines.size();
    }
}

package com.app.order.application;

import java.util.List;
import java.util.Optional;
import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.DisplayName;
import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.extension.ExtendWith;
import org.mockito.Mock;
import org.mockito.junit.jupiter.MockitoExtension;

import static org.assertj.core.api.Assertions.assertThat;
import static org.assertj.core.api.Assertions.assertThatThrownBy;
import static org.mockito.ArgumentMatchers.any;
import static org.mockito.Mockito.never;
import static org.mockito.Mockito.verify;
import static org.mockito.Mockito.when;

@ExtendWith(MockitoExtension.class)
class OrderServiceTest {

    @Mock
    private OrderStore store;
    @Mock
    private ProductStore productStore;
    @Mock
    private TaxPolicy taxPolicy;

    private OrderService service;

    @BeforeEach
    void setUp() {
        service = new OrderService(store, productStore, taxPolicy);
    }

    @Test
    @DisplayName("سفارش خالی نباید ذخیره شود")
    void doesNotPersistEmptyOrder() {
        var command = new CreateOrderCommand("o-1", "c-1", List.of());

        assertThatThrownBy(() -> service.createOrder(command))
                .isInstanceOf(IllegalStateException.class)
                .hasMessageContaining("بدون قلم");

        verify(store, never()).save(any());
    }

    @Test
    @DisplayName("سفارش معتبر باید محاسبه و ذخیره شود")
    void persistsValidOrder() {
        when(productStore.findBySku("SKU-1"))
                .thenReturn(Optional.of(new ProductView("SKU-1",
                        Money.ofCents(1_000_000))));
        when(taxPolicy.apply(Money.ofCents(1_000_000)))
                .thenReturn(Money.ofCents(90_000));

        var command = new CreateOrderCommand("o-1", "c-1",
                List.of(new OrderLineCommand("SKU-1", 1)));

        var result = service.createOrder(command);

        assertThat(result.total().cents()).isEqualTo(1_090_000);
        verify(store).save(any(OrderRecord.class));
    }
}

پروژه‌های فروشگاهی اینترنتی کلاسیک‌ترین نمونه‌ی لایه‌بندی هستند: لایه‌ی Presentation شامل REST API و صفحات Thymeleaf، لایه‌ی Service با OrderService و CartService، لایه‌ی Domain با Cart و Order، و لایه‌ی Data با Spring Data JPA و Redis برای کش سبد خرید. اکثر تیم‌های محصول با ۲ تا ۵ سرویس و این معماری سال‌ها بدون مشکل محصولشان را توسعه می‌دهند.

۲) اپلیکیشن بانکداری و پرداخت داخلی

در یک اپلیکیشن بانکی داخلی، لایه‌ی Service قلب سیستم است: هماهنگی احراز هویت، محاسبه‌ی کارمزد، کنترل موجودی و ثبت تراکنش. لایه‌ی Data به هر بانک متصل است و لایه‌ی Presentation فقط APIهای ثبت و گزارش را ارائه می‌دهد. چون دامنه نسبتاً ساده اما نیازمندی اتصالی زیادی وجود دارد، لایه‌بندی کلاسیک انتخاب اقتصادی درستی است.

۳) سیستم رزرو نوبت کلینیک

در این سیستم، Presentation شامل API رزرو و پیامک تأیید، Service منطق تداخل نوبت و ساعت کاری، Domain موجودیت‌های Appointment و Schedule، و Data پایگاه‌داده‌ی بیمارستان است. منطق «اگر بیمار فعال نوبت هم‌زمان داشت، رد کن» در Domain نوشته شده و با ۲۰ تست واحد پوشش دارد.

۴) پنل مدیریت داخلی (Admin Panel) و داشبورد گزارش

داشبوردهای داخلی بهترین نمونه برای لایه‌بندی سبک هستند. لایه‌ی Presentation کامپوننت‌های React یا Thymeleaf، لایه‌ی Service ساخت Query و ترکیب داده، و لایه‌ی Data کوئری‌های خواندنی بهینه‌سازی‌شده است. در این پروژه‌ها معمولاً استفاده از Clean Architecture بیش‌ازحد مهندسی شده است.

بخش ۲۳۲۰ سؤال مصاحبه

سطح Junior
سؤال ۱ — Layered Architecture چیست؟ روشی برای سازمان‌دهی کد به لایه‌های افقی با مسئولیت مشخص (مثلاً Presentation، Service، Domain، Data) که در آن هر لایه فقط می‌تواند لایه‌های پایین‌تر را صدا بزند.
سؤال ۲ — تفاوت لایه‌بندی افقی و عمودی چیست؟ لایه‌بندی افقی بر اساس نوع مسئولیت (UI / منطق / داده) است؛ لایه‌بندی عمودی یا Feature-Based پروژه را بر اساس قابلیت‌های کسب‌وکار به ستون‌های مستقل تقسیم می‌کند.
سؤال ۳ — لایه‌های استاندارد در یک سیستم تجاری کدام‌اند؟ معمولاً چهار لایه‌ی Presentation، Application/Service، Domain/Business و Data/Access هستند. بسته به پروژه ممکن است لایه‌ی Infrastructure یا Cross-cutting هم اضافه شود.
سؤال ۴ — منطق کسب‌وکار باید در کدام لایه باشد؟ در لایه‌ی Domain. قوانینی که به داده‌ی یک موجودیت مربوط‌اند باید در خود موجودیت و قوانین بین‌موجودیتی در Domain Service بنشینند، نه در Controller یا Repository.
سؤال ۵ — تفاوت لایه‌بندی و MVC چیست؟ لایه‌بندی درباره‌ی مسئولیت کد صحبت می‌کند؛ MVC درباره‌ی تقسیم‌پذیری مسئولیت در یک کامپوننت (مدل، ویو، کنترلر). یک پروژه می‌تواند هم‌زمان هر دو باشد: ساختار لایه‌ای، و داخل لایه‌ی UI یک MVC ساده.
سؤال ۶ — چرا نباید از Repository مستقیم در Controller استفاده کرد؟ چون باعث می‌شود Controller هم مسئول هماهنگی Use Case شود و هم Query. کنترلر باید فقط ورودی را اعتبارسنجی و خروجی را تولید کند؛ منطق در Service قرار می‌گیرد.
سؤال ۷ — Repository Pattern چیست و در کدام لایه قرار می‌گیرد؟ الگویی که ذخیره‌سازی داده را پشت یک Interface پنهان می‌کند. قرارداد در لایه‌ی بالاتر (Service) تعریف و پیاده‌سازی در لایه‌ی Data قرار می‌گیرد.
سؤال ۸ — تفاوت DTO و Entity در لایه‌بندی چیست؟ Entity مدل داخلی و پایدار سیستم است و DTO مدل انتقال داده بین لایه‌هاست. جداسازی آن‌ها اجازه می‌دهد ساختار دیتابیس را بدون شکستن API تغییر دهید.
سؤال ۹ — تراکنش دیتابیس (@Transactional) باید در کدام لایه باشد؟ در لایه‌ی Service، دقیقاً روی مرز Use Case. قرار دادن آن در Repository باعث می‌شود هر عملیات کوچک تراکنش مستقل شود و اتمیک بودن سناریوی کامل از بین برود.
سؤال ۱۰ — تفاوت Service Layer و Service Domain چیست؟ Service Domain شامل قوانین کسب‌وکار است، اما Service Layer (Application Service) شامل هماهنگی بین لایه‌ها و مدیریت تراکنش می‌شود. اولی «چه چیزی درست است» را تعیین می‌کند و دومی مشخص می‌کند «چه کاری باید انجام شود».
سطح Mid
سؤال ۱۱ — قانون لایه‌ها را چطور در کد اجباری می‌کنید؟ با ماژول‌بندی: هر لایه یک Gradle/Maven module مستقل با build.gradle جدا. کامپایلر اجازه‌ی ارجاع از ماژول بالا به پایین را می‌دهد و نه برعکس.
سؤال ۱۲ — تفاوت لایه‌بندی و معماری Onion چیست؟ در Onion، Domain در مرکز قرار می‌گیرد و همه‌ی وابستگی‌ها به سمت آن جریان دارند؛ در لایه‌بندی کلاسیک، Domain فقط یکی از لایه‌هاست و قاعده‌ی وابستگی صرفاً رو به پایین است.
سؤال ۱۳ — Anemic Domain Model چیست و چرا رخ می‌دهد؟ وقتی همه‌ی منطق در Service بنشیند، Entity فقط Getter/Setter دارد. معمولاً به‌دلیل عجله در نوشتن لایه‌ی Service، نتیجه‌اش مدلی بدون رفتار است که نگهداری آن سخت می‌شود.
سؤال ۱۴ — آیا باید لایه‌ی Service وجود داشته باشد؟ در پروژه‌های خیلی کوچک، خیر؛ می‌توان Controller را مستقیم به Repository وصل کرد. اما به‌محض داشتن بیش از یک Use Case یا منطق تراکنشی، لایه‌ی Service ارزش واقعی دارد.
سؤال ۱۵ — چطور یک لایه‌ی Service خوب طراحی کنیم؟ بر اساس Use Case تقسیم‌بندی کنید، متدهای کوتاه و کم‌وابسته بنویسید، خروجی را با DTO مشخص برگردانید و تراکنش را فقط در مرز سرویس مدیریت کنید.
سؤال ۱۶ — در لایه‌بندی چطور خطاها را مدیریت می‌کنید؟ خطاهای دامنه را با Exception اختصاصی در Domain مدیریت می‌کنید، خطاهای فنی در Data ثبت می‌شوند و تبدیل همه‌ی آن‌ها به پاسخ HTTP کارِ لایه‌ی Presentation است. لایه‌ی Service نباید کد وضعیت HTTP داشته باشد.
سؤال ۱۷ — لایه‌ی Data در لایه‌بندی کلاسیک شامل چه چیزهایی است؟ پیاده‌سازی Repository، کلاس‌های نگاشت (Entity دیتابیس)، DAOها، پیکربندی اتصال و پیاده‌سازی Adapterهای بیرونی مثل پیامک یا پرداخت.
سؤال ۱۸ — چه زمانی لایه‌بندی را به Feature-Based تغییر دهیم؟ وقتی ساختار لایه‌ای باعث شود دو تیم روی فایل‌های مشترک تداخل داشته باشند. در آن حالت هر فیچر پوشه‌ی مستقل خود با لایه‌های داخلی می‌گیرد.
سطح Senior
سؤال ۱۹ — مهم‌ترین محدودیت لایه‌بندی کلاسیک چیست؟ اینکه فقط قانون رو به پایین را تضمین می‌کند، نه قانون وابستگی به سمت هسته. نتیجه: لایه‌ی Data مجبور است همه‌ی مدل‌ها را بشناسد و لایه‌ی Domain نازک می‌ماند. اینجاست که معماری‌های Clean یا Onion برتری پیدا می‌کنند.
سؤال ۲۰ — چطور جلوی تبدیل لایه‌بندی به «لایه‌سازی بی‌فایده» را بگیریم؟ برای هر لایه بنویسید دقیقاً چه مسئولیتی دارد. اگر نتوانید در یک جمله بگویید «این لایه فقط…»، لایه را حذف یا ادغام کنید. لایه‌ای که فقط یک خط را به لایه‌ی دیگر منتقل می‌کند، فقط هزینه است.

بخش ۲۴پرسش‌های متداول (FAQ)

پرسش‌های پرتکرار
۱) آیا Layered Architecture همان N-Tier است؟ لایه‌بندی به تقسیم کد به لایه‌های داخل یک برنامه اشاره دارد و N-Tier به تقسیم سیستم به چند سطح که ممکن است روی چند سرور و فرایند جدا اجرا شوند. لایه‌بندی می‌تواند کاملاً در یک پروسه باشد.
۲) تفاوت لایه با ماژول چیست؟ لایه یک مفهوم معماری است؛ ماژول یک واحد فایل/کامپایل است. می‌توانید چند ماژول در یک لایه داشته باشید، یا هر لایه را یک ماژول مستقل کنید.
۳) آیا لایه‌بندی برای اپلیکیشن اندروید هم مناسب است؟ بله. در اندروید معمولاً سه لایه داریم: UI/Compose، ViewModel (که نقش Service را دارد) و Repository (که نقش Data را دارد). این دقیقاً همان لایه‌بندی با سه لایه است.
۴) تفاوت لایه‌ی Domain و لایه‌ی Business Logic چیست؟ در بسیاری از پروژه‌ها این دو یکی هستند. اصطلاح Domain تأکید می‌کند که این لایه مدل مفهومی کسب‌وکار را نگه می‌دارد، نه صرفاً یک سری if و else.
۵) چطور جلوی نشت لایه (Leaky Abstraction) را بگیریم؟ با تعریف قرارداد دقیق بین لایه‌ها. مثلاً اگر Service نباید SQL ببیند، متدهای Repository را طوری طراحی کنید که نیازی به SQL نداشته باشند و تست‌های معماری (ArchUnit) بنویسید.
۶) آیا باید برای هر لایه پروژه‌ی جدا بسازیم؟ خیر. در اکثر پروژه‌ها پوشه‌بندی کافی است. ماژول‌بندی مستقل فقط زمانی لازم است که تیم بزرگ باشد یا بخواهید قانون وابستگی را در سطح کامپایل اجباری کنید.
۷) لایه‌ی Service باید تراکنش دیتابیس داشته باشد؟ بله، تراکنش مرز Use Case است و معمولاً روی متدهای Service قرار می‌گیرد. اما مراقب باشید برای عملیات خواندن معمولی تراکنش بی‌مورد ایجاد نکنید.
۸) تفاوت لایه‌بندی و Clean Architecture دقیقاً چیست؟ در Clean، قانون وابستگی به سمت هسته (Use Caseها) است و لایه‌ی بیرونی باید این قانون را رعایت کند، حتی اگر این‌طور طراحی نشده باشد. در لایه‌بندی کلاسیک، هر لایه فقط می‌تواند لایه‌ی پایین را صدا بزند.
۹) آیا لایه‌بندی باعث کندی می‌شود؟ خودِ لایه‌بندی خیر. کندی زمانی رخ می‌دهد که N+1 Query، تبدیل بی‌مورد DTO یا حلقه‌های پرکاری در لایه‌ی Data داشته باشید. این‌ها مشکل پیاده‌سازی است، نه معماری.
۱۰) لایه‌ی UI در پروژه‌ی وب باید شامل چه چیزی باشد؟ Controller، مدل درخواست/پاسخ (DTO)، نگاشتگر بین DTO و مدل دامنه، و اعتبارسنجی ورودی. همه‌ی منطق کسب‌وکار باید به Service منتقل شود.
۱۱) آیا می‌توانم لایه‌ی Domain را حذف کنم؟ در پروژه‌های کوچک بله، اگر منطق کسب‌وکار ساده است. اما به‌محض پیچیده شدن قوانین، داشتن یک جای مشخص برای این قوانین از پخش شدن آن‌ها در Controller و Service جلوگیری می‌کند.
۱۲) تفاوت Repository با DAO چیست؟ DAO معمولاً یک کلاس ساده است که مستقیم با دیتابیس کار می‌کند و وابسته به تکنولوژی است. Repository یک قرارداد دامنه‌محور است که می‌تواند با هر فناوری پیاده‌سازی شود.
۱۳) لایه‌بندی با Event-Driven چه تفاوتی دارد؟ لایه‌بندی جریان داده‌ی همگام و مستقیم دارد. Event Driven جریان را غیرهمگام می‌کند و وابستگی را از طریق پیام کم می‌کند. می‌توانید هر دو را با هم ترکیب کنید: لایه‌بندی درون سرویس، رویداد بین سرویس‌ها.
۱۴) چطور از رعایت قوانین لایه‌ای مطمئن شوم؟ با تست معماری مثل ArchUnit در تست خودکار. مثلاً: «کلاس‌های پکیج domain نباید هیچ ایمپورتی از پکیج infrastructure داشته باشند.»
۱۵) آیا لایه‌بندی برای پروژه‌ی میکروسرویس مناسب است؟ بله، هر میکروسرویس معمولاً یک پروژه‌ی کوچک لایه‌ای است. اما اگر بین سرویس‌ها جریان پیچیده دارید، داخل هر سرویس به لایه‌بندی به‌علاوه‌ی Event Bus نیاز دارید.

جمع‌بندی

Layered Architecture ساده‌ترین و در عین حال بیشترین بازده را برای اکثر پروژه‌ها دارد. این معماری به شما اجازه می‌دهد بدون درگیر شدن با پیچیدگی‌های سنگین Onion یا Clean، مسئولیت‌ها را جدا کنید، تست بنویسید و چند کلاینت مختلف به یک منطق مشترک وصل کنید.

اما فراموش نکنید که لایه‌بندی یک قرارداد انسانی است، نه یک قانون کامپایلی. اگر تیم شما نمی‌تواند قوانین را رعایت کند، لایه‌بندی فقط چند پوشه‌ی خالی است. در آن صورت یا با ابزار (ماژول‌بندی، ArchUnit) آن را اجباری کنید، یا به سراغ معماری‌هایی بروید که ساختارشان محیط را مجبور به رعایت قانون می‌کند.

پیام پایانی سری ۱۴ مقاله‌ای این مقاله چهارمین عضو سری «معماری‌های نرم‌افزاری» است. اگر این چهار مقاله را دنبال کرده‌اید (Clean، Onion، Hexagonal، Layered)، حالا می‌دانید طیف معماری‌ها از چیدمان ساده‌ی لایه‌ای تا حلقه‌های کاملاً ایزوله‌ی دامنه کشیده شده است. مقاله‌ی بعدی سری به MVC می‌پردازد.
