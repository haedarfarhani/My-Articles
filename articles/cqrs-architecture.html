بخش ۱مقدمه: مدلی که هر دو کار را بد انجام می‌دهد

یک مدل داده را در نظر بگیرید که هم باید نوشته را خوب انجام دهد و هم خواندن را. این تقریباً همیشه شکست می‌خورد، چون این دو کار نیازهای متضاد دارند.

الگوی خواندن

نمایش لیست سفارش‌ها به همراه نام مشتری، تعداد اقلام، مجموع پرداخت‌ها و وضعیت ارسال. این یک کوئری با ۵ JOIN است که روی ۴ جدول کار می‌کند و فقط یک نمایش می‌سازد. بهینه برای نمایش، بی‌ربط به قواعد کسب‌وکار.

الگوی نوشتن

ثبت سفارش: باید قوانین را چک کند (موجودی کافی است؟ تخفیف معتبر است؟)، وضعیت را تغییر دهد و رویداد تولید کند. این یک موجودیت غنی با رفتار است که فقط با شناسه بارگذاری می‌شود. بهینه برای قواعد، بی‌ربط به نمایش.

مشکل مدل مشترک اگر هر دو را در یک مدل بریزید: ← یا مدل نوشتن را لاغر می‌کنید و قواعد را از دست می‌دهید ← یا مدل خواندن را سنگین می‌کنید و کوئری‌ها کند می‌شوند ← نتیجه: یک مدل که هیچ‌کدام از کارها را خوب انجام نمی‌دهد

نمونه‌ی واقعی از ناسازگاری

// مدلی که برای هر دو استفاده می‌شود
@Entity
public class Order {
    @Id private Long id;
    private String customerName;          // ← فقط برای نمایش لازم است
    private BigDecimal totalPaid;         // ← فقط برای نمایش
    private String shippingStatus;        // ← از جدول دیگر کپی شده
    private List<OrderItem> items;     // ← EAGER: همیشه بارگذاری می‌شود
    private List<Payment> payments;     // ← EAGER: گران است
    private String internalRiskScore;     // ← فقط برای کاربرد داخلی

    // و برای نوشتن به این‌ها نیاز دارد:
    public void addItem(...) { }         // ← قواعد اینجا
    public void cancel() { }             // ← و اینجا
}

برای نوشتن، این مدل سنگین است (۵ جدول join می‌شود). برای خواندن، ناقص است (بعضی داده‌ها کهنه‌اند و بعضی فیلدها اصلاً لازم نیستند).

تشبیه ساده فکر کنید یک رستوران دارید. آشپزخانه (Command Side) برای پخت است: دقیق، با قوانین بهداشتی سخت‌گیرانه و کند. سالن (Query Side) برای سرو است: سریع، با میزهای چیده‌شده و منوی کامل. آشپزخانه و سالن داده‌ی متفاوتی دارند و این طبیعی است.

ریشه‌ی نیاز: داده و نمایش

مسئله‌ی ریشه‌ای «نمایش» (View) و «داده» (Data) دو نگرانی متفاوت‌اند. نمایش برای خواننده بهینه است: ستون‌های از پیش محاسبه‌شده، بدون join، آماده‌ی نمایش. داده برای نویسنده بهینه است: نرمال‌شده، با قید یکتا و کلید خارجی، برای تضمین درستی. این دو همیشه در تضادند.

بخش ۳CQRS چیست؟ (تعریف دقیق)

تعریف CQRS یعنی جدا کردن مدل نوشتن از مدل خواندن؛ به‌جای اینکه یک مدل هم‌زمان مسئول اعتبارسنجی قواعد کسب‌وکار و نمایش داده به کاربر باشد، دو مدل جدا با مسئولیت‌های جدا می‌سازیم.

نام کامل: Command Query Responsibility Segregation — جداسازی مسئولیت Command و Query.

Command چیست؟

/** Command: درخواست تغییر وضعیت. خروجی: فقط موفقیت یا خطا. */
public record PlaceOrderCommand(
        String customerId,
        List<Line> lines
) {
    public record Line(String productId, int quantity, BigDecimal unitPrice) {}
}

// ← خروجی یا id می‌دهد یا استثنا پرتاب می‌کند
// ❌ هرگز یک مدل دامنه را برنمی‌گرداند
String orderId = orders.placeOrder(command);

Query چیست؟

/** Query: درخواست خواندن. خروجی: داده. هیچ تغییری نباید رخ دهد. */
public record OrderSummaryView(
        String orderId,
        String customerName,
        int itemCount,
        BigDecimal totalPaid,
        String shippingStatus,
        String orderStatus,

) {}

List<OrderSummaryView> result = queries.findOrdersByCustomer(customerId);

۱. مدل سنگین برای نمایش

SELECT o.id, o.created_at, c.name, p.status,
       (SELECT COUNT(*) FROM order_items WHERE order_id = o.id) AS item_count,
       (SELECT SUM(amount) FROM payments WHERE order_id = o.id) AS total_paid

LEFT JOIN payments p ON p.order_id = o.id
WHERE o.customer_id = ?

بخش ۵ایده اصلی: CQS و Command/Query

مرحله‌ی اول: فقط اصل CQS (بدون مدل جدا)

گران‌ترین اشتباه رایج این است که «CQRS» را با «دو مدل» یکی می‌گیریم. اما ریشه‌ی آن اصل CQS است که تقریباً رایگان است و ارزشمندترین بخش. 

// ❌ قبل: یک سرویس برای همه
@Service
class OrderService {
    void placeOrder(PlaceOrderCommand c) { }          // ← نوشتن
    Order getOrder(Long id) { }                       // ← خواندن
    List<Order> search(String q) { }               // ← خواندن
    void markAsRead(Long id) { }                      // ← نوشتن
}

// ✅ بعد: دو واسط، یک مدل
public interface OrderCommands {
    String placeOrder(PlaceOrderCommand c);
    void cancel(String orderId, String reason);
}

public interface OrderQueries {
    OrderDetails getOrder(String orderId);
    List<OrderSummary> search(String customerId);
}

قواعد طراحی Command

  • فقط یک کار انجام می‌دهد؛ نامش یک فعل است
  • خروجی شناسه یا هیچ‌چیز، نه مدل دامنه
  • ممکن است استثنا بگیرد با معنی کسب‌وکار
  • idempotent نیست — دو بار فرستادن، دو بار اثر می‌گذارد
  • ممکن است کند باشد (استفاده از صف)
  • هیچ داده‌ای برنمی‌گرداند جز شناسه

قواعد طراحی Query

  • فقط می‌خواند، هرگز تغییر وضعیت
  • سریع — همیشه
  • سازگاری نهایی قابل قبول است
  • idempotent — چند بار صدا بزنی، همان نتیجه
  • هیچ استثنای کسب‌وکاری — فقط «پیدا نشد»
  • کپی‌پذیر — هر نمایش می‌تواند یک Query جدا باشد

بخش ۶سه سطح CQRS

سطح ۱ — CQS (جداسازی امضا)

@Service
@Transactional
class OrderCommandService implements OrderCommands {

    private final OrderRepository orders;   // مدل نوشتن

    @Override
    public String placeOrder(PlaceOrderCommand command) {
        Order order = Order.create(command.customerId());
        command.lines().forEach(l ->
                order.addLine(l.productId(), l.quantity(), l.unitPrice()));
        order.place();
        orders.save(order);
        return order.id();                   // ← فقط شناسه
    }
}

@Service
@Transactional(readOnly = true)
class OrderQueryService implements OrderQueries {

    private final OrderRepository orders;   // همان repository

    @Override
    public List<OrderSummary> search(String customerId) {
        return orders.findByCustomerId(customerId).stream()
                .map(o -> new OrderSummary(o.id(), o.status().name(),
                        o.total().toPlainString(), o.createdAt()))
                .toList();
    }
}
سود سطح ۱ با تغییر صفر در زیرساخت، سه چیز به دست می‌آورید: (۱) کنترلرها دقیقاً می‌دانند چه عملیاتی موجود است؛ (۲) هیچ متدی نمی‌تواند هم‌زمان بخواند و بنویسد؛ (۳) تست Query و Command جدا نوشته می‌شود. این سطح معمولاً ارزش بهترین نسبت به هزینه را دارد.

سطح ۲ — مدل و رابط کاربری جدا

@RestController
@RequestMapping("/api/orders")
class OrderController {

    private final OrderCommands commands;
    private final OrderQueries queries;

    @PostMapping
    ResponseEntity<OrderCreatedResponse> create(
            @Valid @RequestBody PlaceOrderRequest req) {

        String id = commands.placeOrder(new PlaceOrderCommand(
                req.customerId(),
                req.lines().stream()
                        .map(l -> new LineCommand(l.productId(),
                                l.quantity(), new BigDecimal(l.unitPrice())))
                        .toList()));

        return ResponseEntity.created(URI.create("/api/orders/" + id))
                .body(new OrderCreatedResponse(id));
    }

    @GetMapping
    List<OrderSummaryResponse> list(@RequestParam String customerId) {
        return queries.search(customerId).stream()
                .map(v -> new OrderSummaryResponse(v.orderId(), v.status(),
                        v.total(), v.placedAt()))
                .toList();
    }
}

سازگاری نهایی در عمل

کاربر ثبت سفارش می‌کند و بلافاصله صفحه‌ی لیست را می‌بیند:

  ثبت سفارش     → دیتابیس نوشتن ✅
  پروژکشن        → در حال اجرا...
  صفحه‌ی لیست   → هنوز سفارش جدید را نمی‌بیند ❌
  ۱ ثانیه بعد    → پروژکشن تمام شد
  تازه‌سازی صفحه → سفارش هست ✅

سؤالاتی که باید بپرسید:
  ۱. کاربر چقدر باید منتظر بماند؟  (۵۰ms یا ۲ ثانیه؟)
  ۲. آیا می‌تواند این را ببیند؟    (UI باید بازخورد بدهد)
  ۳. اگر مشکلی پیش بیاید چه؟      (lag monitor + retry)

سه راه مدیریت سازگاری نهایی در رابط کاربری

راهپیاده‌سازیتجربه‌ی کاربر
بازخورد فوری«در حال ثبت...» سپس تأییدخوب

چرا این جدول واقعاً سریع‌تر است «تخت» یعنی نمایش لیست فقط از یک جدول خوانده می‌شود: بدون join، بدون N+1، و دو فیلد محاسبه‌شده (item_count و high_value) که در لحظه نوشته شده‌اند. در دیتابیس اصلی، این‌ها یا join می‌خواهند یا در هر ردیف محاسبه می‌شوند.

            }
        }
    }

/** مرز Command Side: فقط تغییر وضعیت. */
public interface OrderCommands {

    String placeOrder(PlaceOrderCommand command);

    void cancelOrder(String orderId, String reason);

    void markAsShipped(String orderId, String trackingCode);

    void confirmDelivery(String orderId);
}

package com.shop.order.command;

import com.shop.order.domain.*;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

import java.util.List;

@Service
@Transactional                                    // ← مرز تراکنش
public class OrderCommandHandler implements OrderCommands {

    private final OrderRepository orders;
    private final ApplicationEventPublisher events;

    public OrderCommandHandler(OrderRepository orders,
                               ApplicationEventPublisher events) {
        this.orders = orders;
        this.events = events;
    }

    @Override
    public String placeOrder(PlaceOrderCommand command) {
        Order order = Order.create(command.customerId());

        command.lines().forEach(l ->
                order.addLine(l.productId(), l.quantity(), l.unitPrice()));

        order.place();

        orders.save(order);
        events.publishEvent(new OrderPlaced(
                order.id(), order.customerId(), order.total(),
                order.lines().size(), java.time.Instant.now()));

        return order.id();                       // ← فقط شناسه
    }

    @Override
    public void cancelOrder(String orderId, String reason) {
        Order order = load(orderId);
        order.cancel(reason);
        orders.save(order);
        events.publishEvent(new OrderCancelled(orderId, reason,
                java.time.Instant.now()));
    }

    @Override
    public void markAsShipped(String orderId, String trackingCode) {
        Order order = load(orderId);
        order.ship(trackingCode);
        orders.save(order);
        events.publishEvent(new OrderShipped(orderId, trackingCode,
                java.time.Instant.now()));
    }

    @Override
    public void confirmDelivery(String orderId) {
        Order order = load(orderId);
        order.deliver();
        orders.save(order);
        events.publishEvent(new OrderDelivered(orderId,
                java.time.Instant.now()));
    }

    private Order load(String orderId) {
        return orders.findById(new OrderId(orderId))
                .orElseThrow(() -> new OrderError("سفارش یافت نشد: " + orderId));
    }
}

package com.shop.order.web;

import com.shop.order.command.*;
import jakarta.validation.Valid;
import jakarta.validation.constraints.*;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;

import java.math.BigDecimal;
import java.net.URI;
import java.util.List;

@RestController
@RequestMapping("/api/orders")
public class OrderCommandController {

    private final OrderCommands commands;

    public OrderCommandController(OrderCommands commands) {
        this.commands = commands;
    }

    @PostMapping
    public ResponseEntity<OrderCreatedResponse> create(
            @Valid @RequestBody PlaceOrderRequest request) {

        String id = commands.placeOrder(new PlaceOrderCommand(
                request.customerId(),
                request.lines().stream()
                        .map(l -> new PlaceOrderCommand.Line(
                                l.productId(), l.quantity(),
                                new BigDecimal(l.unitPrice())))
                        .toList()));

        return ResponseEntity.created(URI.create("/api/orders/" + id))
                .body(new OrderCreatedResponse(id));
    }

    @PostMapping("/{id}/cancellation")
    @ResponseStatus(HttpStatus.NO_CONTENT)
    public void cancel(@PathVariable String id,
                       @RequestBody CancelRequest request) {
        commands.cancelOrder(id, request.reason());
    }

    @PostMapping("/{id}/shipment")
    @ResponseStatus(HttpStatus.NO_CONTENT)
    public void ship(@PathVariable String id,
                     @RequestBody ShipRequest request) {
        commands.markAsShipped(id, request.trackingCode());
    }

    // ── DTO های ورودی ──
    public record PlaceOrderRequest(
            @NotBlank String customerId,
            @NotEmpty @Valid List<Line> lines) {

        public record Line(@NotBlank String productId,
                           @Min(1) int quantity,
                           @NotBlank String unitPrice) {}
    }

    public record CancelRequest(@NotBlank String reason) {}
    public record ShipRequest(@NotBlank String trackingCode) {}
    public record OrderCreatedResponse(String orderId) {}
}

package com.shop.order.web;

        return OrderSummaryResponse.from(summary);
    }

    @GetMapping
    public List<OrderSummaryResponse> list(@RequestParam String customerId,
                                              @RequestParam(defaultValue = "20") int limit) {

                .map(OrderSummaryResponse::from)
                .toList();

                .toList();

public interface CommandBus {

public interface Command<R> {
    Class<? extends CommandHandler<? , R>> handlerType();
}

public interface CommandHandler<C extends Command<R>, R> {
    R handle(C command);
}

public record PlaceOrderCommand(
        String customerId,
        List<Line> lines
) implements Command<String> {

    @Override
    public Class<? extends CommandHandler<?, String>> handlerType() {
        return PlaceOrderCommandHandler.class;
    }

    public record Line(String productId, int quantity, BigDecimal unitPrice) {}
}

@Component
class PlaceOrderCommandHandler implements CommandHandler<PlaceOrderCommand, String> {

    private final OrderRepository orders;
    private final ApplicationEventPublisher events;

    PlaceOrderCommandHandler(OrderRepository orders,
                            ApplicationEventPublisher events) {
        this.orders = orders;
        this.events = events;
    }

    @Override
    @Transactional
    public String handle(PlaceOrderCommand command) {
        Order order = Order.create(command.customerId());
        command.lines().forEach(l ->
                order.addLine(l.productId(), l.quantity(), l.unitPrice()));
        order.place();

        orders.save(order);
        events.publishEvent(new OrderPlaced(order.id(), order.customerId(),
                order.total(), order.lines().size(), Instant.now()));

        return order.id();
    }
}

@Component
class SpringCommandBus implements CommandBus {

    private final Map<Class<?>, CommandHandler> handlers = new HashMap<>();

    SpringCommandBus(List<CommandHandler> discovered) {
        discovered.forEach(h -> handlers.put(h.supports(), h));
    }

    @SuppressWarnings("unchecked")
    @Override
    public <R> R dispatch(Command<R> command) {
        CommandHandler handler = handlers.get(command.handlerType());
        if (handler == null) {
            throw new NoHandlerForCommand(command.getClass());
        }
        return (R) handler.handle(command);
    }
}

۱. فروشگاه اینترنتی — فهرست سفارش‌ها

قبل:
  GET /api/orders?customerId=5
  JOIN customers + LEFT JOIN payments + 2 زیرکوئری

  GET /api/orders?customerId=5
  SELECT * FROM order_summary WHERE customer_id = ? ORDER BY placed_on DESC
  ۲۸ میلی‌ثانیه

  item_count    ← COUNT خطوط در لحظه‌ی نوشتن

  customer_name ← کپی از جدول مشتریان
  shipping_status ← کپی از سرویس ارسال

← ۱۰۰ برابر سریع‌تر، بدون تغییر در منطق ثبت سفارش

۲. داشبورد مدیریتی — آمار تجمیعی

قبل:
  هر بار باز کردن داشبورد = ۵ کوئری سنگین روی جدول تراکنش
  با ۸ میلیون ردیف، ۶ ثانیه

بعد (Read Model تجمیعی):
  جدول daily_stats:
    date, total_orders, total_revenue, avg_order_value, new_customers

  هر شب یک job، داده‌ی روز را از رویدادها جمع می‌زند
  کوئری داشبورد: SELECT * FROM daily_stats ORDER BY date DESC

  ← ۶ ثانیه ← ۵ میلی‌ثانیه
  ← و این جدول هرگز رشد نمی‌کند (۳ سطر در سال)

۳. پلتفرم ویدیو — فهرست با فیلتر

نمایش مورد نیاز:
  عنوان، تصویر، نام کانال، تعداد بازدید، مدت، تاریخ، دسته‌بندی، امتیاز

منابع داده: ویدیو + کانال + آمار بازدید + امتیاز + دسته‌بندی

قبل:
  ۵ join برای هر ردیف فهرست + محاسبه‌ی امتیاز

بعد:
  Read Model که رویدادها را مصرف می‌کند:
    VideoUploaded    → ایجاد رکورد
    VideoPublished   → به‌روزرسانی وضعیت

  کوئری فهرست: یک SELECT ساده با ایندکس روی دسته‌بندی و تاریخ

۴. سامانه‌ی مالی — دفتر کل

مدل نوشتن (Write):
  جدول تراکنش‌ها با قید یکتا روی (account_id, reference, date)
  ← اینجا درستی حیاتی است؛ هیچ بهینه‌سازی نمایشی انجام نمی‌شود

مدل خواندن (Read):
  جدول account_balance_snapshot:
    account_id, balance, currency, as_of
  
  هر تراکنش، موجودی را به‌روز می‌کند (رویدادمحور)
  کوئری موجودی: یک SELECT از جدول snapshot

← اینجا CQRS یک الزام است، نه انتخاب:
   چون مانده‌گیری روی جدول تراکنش با میلیون‌ها ردیف، غیرممکن است

توجه: موجودی حساب پول واقعی است
      ← به همین دلیل باید سازگاری فوری باشد
      ← برای این مورد، «سفارش‌های من» کاربر یا از منبع نوشتن خوانده می‌شود

نمایش صندوق ورودی:

@Component
public class ReadModelLagMonitor {

    @Scheduled(fixedRate = 60_000)             // هر دقیقه
    public void checkLag() {
        long writeCount = jdbc.queryForObject(
                "SELECT count(*) FROM orders", Long.class);
        long readCount = jdbc.queryForObject(
                "SELECT count(*) FROM order_summary", Long.class);

        long lag = writeCount - readCount;

        if (lag > LAG_THRESHOLD) {
            alarm.send("Read Model عقب افتاده است: " + lag + " رکورد");
        }
    }

    private static final long LAG_THRESHOLD = 100;
}

بخش ۲۳۲۰ سؤال مصاحبه

سطح Junior (۱ تا ۱۰)

سؤال ۱ — CQRS چیست؟ جدا کردن مدل نوشتن از مدل خواندن. به‌جای اینکه یک مدل هم قوانین کسب‌وکار را اعمال کند و هم داده‌ی نمایش بدهد، دو مدل جدا با مسئولیت‌های جدا می‌سازیم.
سؤال ۲ — Command و Query چه تفاوتی دارند؟ Command درخواست تغییر وضعیت است و خروجی‌اش فقط شناسه یا خطاست. Query درخواست خواندن است و خروجی‌اش داده. هیچ متدی نباید هر دو باشد.
سؤال ۳ — تفاوت CQS و CQRS چیست؟ CQS (Command Query Separation) اصل بنیادی است: هر متد یا Command است یا Query، نه هر دو. CQRS معماری‌ای است که از این اصل استفاده می‌کند و مدل نوشتن و خواندن را کاملاً جدا می‌کند. CQS تقریباً رایگان است؛ CQRS هزینه دارد.
سؤال ۴ — Read Model چیست؟ یک نمایش بهینه‌شده و تخت از داده که مخصوص خواندن است. فیلدهایش دقیقاً همان‌هایی است که صفحه نیاز دارد، داده تکراری دارد، بدون join خوانده می‌شود و فیلدهای محاسبه‌شده از قبل آماده‌اند.
سؤال ۵ — سازگاری نهایی یعنی چه در CQRS؟ یعنی بعد از ثبت یک تغییر، تا مدت کوتاهی مدل خواندن هنوز به‌روز نیست. برای فهرست‌ها مشکلی ندارد، اما اگر کاربر باید «همین الان» نتیجه را ببیند، باید از منبع نوشتن بخوانید یا بازخورد مناسب نشان دهید.
سؤال ۶ — منبع حقیقت کدام است؟ همیشه مدل نوشتن. Read Model یک کپی مشتق‌شده است و می‌توان آن را هر لحظه از نو ساخت. اگر Read Model منبع حقیقت شود، عملاً CQRS را از دست داده‌اید.
سؤال ۷ — پروژکشن چیست؟ فرایندی که رویدادهای مدل نوشتن را می‌گیرد و Read Model را به‌روز می‌کند. می‌تواند همگام (درون همان فرایند) باشد یا از راه broker و به‌صورت ناهمگام.
سؤال ۸ — چرا Command نباید مدل دامنه برگرداند؟ چون باعث نشت ساختار داخلی به لایه‌ی API می‌شود. اگر فردا مدل را عوض کنید، API شما خراب می‌شود. فقط شناسه برگردانید.
سؤال ۹ — سه سطح CQRS را نام ببرید. ۱) فقط CQS با مدل مشترک، ۲) مدل نوشتن و مدل خواندن جدا ولی یک دیتابیس، ۳) Read Model اختصاصی با ذخیره‌سازی جدا. سطح ۴ هم Event Sourcing است.
سؤال ۱۰ — آیا CQRS همان DDD است؟ نه. DDD درباره‌ی مدل‌سازی دامنه است و CQRS درباره‌ی جدا کردن نوشتن از خواندن. این‌ها مکمل‌اند و معمولاً با هم به کار می‌روند، ولی CQRS بدون DDD هم ممکن است.

سطح Mid (۱۱ تا ۱۷)

سؤال ۱۱ — چرا پروژکشن باید idempotent باشد؟ چون رویداد ممکن است دوباره پردازش شود. اگر پروژکشن غیر idempotent باشد، itemCount دو برابر می‌شود یا وضعیت اشتباه ثبت می‌شود. راه‌حل: جدول پردازش‌شده یا upsert به‌جای insert.
سؤال ۱۲ — Read Model را چطور بازسازی می‌کنید؟ با اجرای یک اسکریپت که همه‌ی داده‌ی مدل نوشتن را می‌خواند و Read Model را از نو می‌سازد (truncate و پر کردن مجدد با batch). چون Read Model مشتق‌شده است، این کار همیشه ممکن و بی‌خطر است.
سؤال ۱۳ — چطور lag را تشخیص می‌دهید؟ با مقایسه‌ی تعداد رکوردهای مدل نوشتن و Read Model، یا ثبت آخرین زمان پردازش هر رویداد. این مقایسه باید زمان‌بندی‌شده اجرا شود و در صورت اختلاف زیاد هشدار بدهد.
سؤال ۱۴ — چرا نباید از Query Side چیزی بنویسیم؟ دو دلیل: اول، نقض اصل CQS. دوم، اگر Query بنویسد، Read Model دیگر با رویدادها همگام نمی‌شود و کهنه می‌شود. هر نوشتنی باید از مسیر Command برود تا رویداد تولید شود.
سؤال ۱۵ — تفاوت Read Model تخت و نرمال‌شده چیست؟ تخت یعنی هرچه لازم است در یک سطر ذخیره می‌شود و تکرار داده اشکالی ندارد؛ سریع‌ترین حالت برای نمایش است. نرمال‌شده یعنی داده تکرار نمی‌شود و برای گزارش‌های پیچیده با join مناسب‌تر است.
سؤال ۱۶ — چه زمانی به Event Sourcing برویم؟ وقتی تاریخچه‌ی کامل تغییرات ارزش کسب‌وکاری دارد (بیمه، بانک، بازی) یا می‌خواهید «بازی در زمان» انجام دهید. برای بیشتر اپلیکیشن‌ها این پیچیدگی ارزشش را ندارد.
سؤال ۱۷ — چطور مرز بین Query و Domain را خودکار حفظ کنیم؟ با ArchUnit: قاعده‌ای که می‌گوید کلاس‌های پوشه‌ی query نباید به پوشه‌ی domain وابسته باشند، و کنترلرها نباید مستقیم repository صدا بزنند. این تست در CI اجرا می‌شود.

سطح Senior (۱۸ تا ۲۰)

سؤال ۱۸ — در چه صورتی CQRS را رد می‌کنید؟ وقتی نسبت خواندن به نوشتن نزدیک یک است، کوئری‌ها ساده و سریع‌اند، تیم کوچک است، یا کاربر باید «همین الان» نتیجه را ببیند. در این حالت هزینه‌ی دو مدل و پایش، بیشتر از سودش است.
سؤال ۱۹ — چگونه تعداد Read Modelها را کنترل می‌کنید؟ با هم‌ترکیبی: نمایش‌هایی که فیلدهای مشابه دارند را در یک جدول نگه می‌دارید و فقط نمایه‌های متفاوت را جدا می‌کنید. برای هر Read Model باید دلیل مشخص و قابل دفاع داشته باشید (مثال: «فهرست اصلی» و «داشبورد تجمیعی»).
سؤال ۲۰ — CQRS چگونه به Microservices کمک می‌کند؟ Read Side اولین بخشی است که معمولاً به سرویس مستقل تبدیل می‌شود، چون سازگاری نهایی آن را تحمل‌پذیر می‌کند. مدل نوشتن سخت‌تر است، چون منبع حقیقت است. این مسیر مهاجرت کم‌ریسکی برای جداسازی سرویس‌ها فراهم می‌کند.

بخش ۲۴پرسش‌های متداول (FAQ)

آیا CQRS برای پروژه‌ی کوچک مناسب است؟ سطح ۱ (فقط CQS) بله، تقریباً رایگان است و ارزش دارد. سطوح بالاتر برای پروژه‌ی کوچک، فقط پیچیدگی بی‌دلیل می‌سازند.
آیا لازم است دو دیتابیس داشته باشم؟ نه. بیشتر پیاده‌سازی‌های موفق فقط دو جدول جدا دارند (یکی برای نوشتن، یکی برای خواندن) در همان دیتابیس. دیتابیس دوم فقط وقتی لازم است که بار خواندن واقعاً متفاوت باشد.
اگر کاربر بلافاصله بعد از ثبت، صفحه را رفرش کند چه می‌بیند؟ اگر پروژکشن ناهمگام است، ممکن است هنوز ندیده باشد. راه‌حل‌ها: (۱) پروژکشن را همگام کنید (AFTER_COMMIT)؛ (۲) در آن نمایش خاص، از منبع نوشتن بخوانید؛ (۳) در رابط کاربری بازخورد «در حال پردازش» نشان دهید.
چطور متوجه شوم Read Model خراب شده؟ سه راه: مقایسه‌ی تعداد رکوردها با مدل نوشتن، بررسی updated_at قدیمی‌ترین رکورد، و اسکریپت بازسازی دوره‌ای. گزینه‌ی چهارم: تست خودکار که تفاوت‌ها را گزارش می‌دهد.
آیا Read Model می‌تواند جدول جدا نباشد؟ بله، می‌تواند یک ویو (VIEW) در همان دیتابیس باشد. اما ویو معمولاً به اندازه‌ی جدول فیزیکی سریع نیست چون محاسبات در زمان اجرا انجام می‌شود. اگر جدول فیزیکی ندارید، باید بپذیرید که سود کمتری می‌برید.
CQRS با چه چیزی بیشترین تضاد را دارد؟ با تراکنش‌های اسیدی که همه‌چیز را در یک تراکنش می‌بینند. CQRS ذاتاً تک‌تراکنشی نیست. اگر کسب‌وکار شما به سازگاری فوری و مطلق نیاز دارد (مثل دفتر مالی)، CQRS باید خیلی محتاطانه استفاده شود.
آیا Command Bus لازم است؟ نه. Command Bus فقط یک لایه‌ی انتزاع است که کنترلر را از هندلر جدا می‌کند. بدون آن هم می‌شود مستقیم interface را صدا زد. برای اکثر پروژه‌ها، فراخوانی مستقیم ساده‌تر و شفاف‌تر است.
چطور Read Model را همگام نگه دارم وقتی چند منبع دارد؟ همه‌ی تغییرات باید از مسیر Command و از طریق رویداد عبور کنند. اگر چیزی مستقیماً در دیتابیس نوشته می‌شود (مثل یک اسکریپت پشتیبان)، آن تغییر هرگز به Read Model نمی‌رسد. این یکی از رایج‌ترین دلایل کهنگی است.
آیا فیلدهای محاسبه‌شده در Read Model خوب هستند؟ بله، این یکی از بزرگ‌ترین سودهای CQRS است. highValue یا itemCount به‌جای محاسبه در هر نمایش، یک‌بار هنگام نوشتن ذخیره می‌شوند.
مزایای CQRS برای تیم محصول چیست؟ تغییرات ظاهری (مثل افزودن یک ستون به جدول سفارش‌ها) به یک نمایش تبدیل می‌شوند و بدون تغییر در منطق کسب‌وکار قابل انجام‌اند. یعنی تیم محصول مستقل‌تر عمل می‌کند.
CQRS با چه معماری‌هایی هم‌زندگی می‌کند؟ با DDD (مدل نوشتن غنی)، با Event Sourcing (منبع حقیقت = رویدادها)، با Event-Driven Architecture (رویدادها به سرویس دیگر می‌روند)، و با Modular Monolith (دو ماژول داخل یک فرایند). همه سازگارند.
آیا در اندروید کاربرد دارد؟ به‌شکل محدود. مدل محلی (Room) می‌تواند نقش Write Model و یک کپی بهینه برای فهرست نقش Read Model را داشته باشد. ولی معمولاً ارزشش کمتر از هزینه‌اش است.
چقدر طول می‌کشد تا راه بیفتد؟ سطح ۱: یک روز. سطح ۲: حدود یک هفته. سطح ۳: دو تا چهار هفته بسته به زیرساخت. بیشترین زمان صرف طراحی این می‌شود که کدام نمایش‌ها واقعاً به مدل اختصاصی نیاز دارند.
چگونه تیم را راضی کنم؟ با عدد نشان دهید: زمان یک کوئری کند را اندازه بگیرید، سپس یک Read Model فقط برای همان یک کوئری بسازید و بهبود را نشان دهید. CQRS را به‌عنوان یک سرمایه‌گذاری موضعی معرفی کنید، نه یک بازآفرینی کامل.
مهم‌ترین توصیه برای شروع چیست؟ از سطح ۱ شروع کنید (جدا کردن interfaceها). اگر بعد از آن کوئری هنوز کند بود، آن‌وقت Read Model بسازید. CQRS کامل را فقط وقتی به کار ببرید که واقعاً به آن نیاز دارید.

جمع‌بندی

CQRS پاسخ یک تضاد بنیادی است: نوشتن می‌خواهد داده را نرمال و سالم نگه دارد، خواندن می‌خواهد سریع باشد. این دو خواسته با یک مدل قابل تحقق نیستند.

نکته‌ای که بیشتر تیم‌ها نمی‌دانند: بیشتر پروژه‌ها به بیش از سطح ۱ نیاز ندارند. جدا کردن دو interface تقریباً رایگان است و ۸۰٪ سود را می‌دهد. ساخت Read Model اختصاصی یک تصمیم جدی است که باید با عدد پشتیبانی شود.

اگر فقط یک جمله به یاد بماند: مدل نوشتن حقیقت است، مدل خواندن فقط سریع است. اگر این ترتیب را رعایت کنید، CQRS شما قابل اعتماد است؛ اگر برعکس شود، به یک سیستم ناسازگار و غیرقابل عیب‌یابی تبدیل می‌شوید.

پیام پایانی سری ۱۴ مقاله‌ای این مقاله سیزدهمین عضو سری «معماری‌های نرم‌افزاری» است. اکنون الگوهای رابط کاربری (MVC، MVP، MVVM، MVI)، الگوهای معماری (Clean، Onion، Hexagonal، Layered، Repository، DDD)، ساختار کد (Feature Based)، ارتباط سرویس‌ها (Event Driven) و جداسازی خواندن/نوشتن (CQRS) را پوشش داده‌ایم. مقاله‌ی پایانی سری: Microservices — که همه‌ی این الگوها را در سطح سیستم‌های توزیع‌شده به کار می‌گیرد.
