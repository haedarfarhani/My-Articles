HAProxy؛ Load Balancer و Reverse Proxy پرکارایی

HAProxy استاندارد صنعتی برای Load Balancing و توزیع ترافیک است. از لایه‌ی ۴ (TCP) تا لایه‌ی ۷ (HTTP)، با ACL، Health Check پیشرفته و کارایی بسیار بالا. این مقاله مفاهیم و پیکربندی واقعی آن را پوشش می‌دهد.

بخش ۱مقدمه

وقتی ترافیک از یک سرور عبور می‌کند، آن سرور یک نقطه‌ی شکست و یک گلوگاه است. HAProxy برای حل همین دو مشکل ساخته شد: توزیع بار بین چند Backend و حذف خودکار سرورهای خراب. این ابزار در بزرگ‌ترین سامانه‌های دنیا (از GitHub تا Reddit) استفاده می‌شود.

در این مقاله تفاوت Load Balancing لایه ۴ و ۷، اجزای پیکربندی (frontend، backend، listen)، ACL، Health Check و Sticky Session.
Prerequisites Load Balancing و Reverse Proxy.

بخش ۲HAProxy چیست؟

تعریف HAProxy یک Load Balancer و Reverse Proxy متن‌باز با کارایی بسیار بالاست که هم ترافیک TCP (لایه ۴) و هم HTTP (لایه ۷) را توزیع می‌کند و با Health Check فعال، سلامت Backendها را دائماً می‌سنجد.

بخش ۳لایه ۴ در برابر لایه ۷

معیارLayer 4 (TCP)Layer 7 (HTTP)
واحد تصمیمIP و پورتURL، Host، Header، Cookie
سرعتبالاترکمی کمتر، اما انعطاف‌پذیرتر
قابلیت‌هاتوزیع سادهRouting، Rewrite، Sticky، Compression
کاربرد نمونهدیتابیس، MQTT، TLS PassthroughAPI، WebSocket، Microservice
انتخاب درست اگر فقط می‌خواهید بار را پخش کنید، لایه ۴ کافی و سریع‌تر است. اگر به مسیریابی بر اساس مسیر یا دامنه، یا حفظ Session نیاز دارید، لایه ۷ را انتخاب کنید.

بخش ۵پیکربندی و ACL

global
    maxconn 50000
    log /dev/log local0

defaults
    mode http
    timeout connect 5s
    timeout client  30s
    timeout server  30s

frontend web_in
    bind *:80
    bind *:443 ssl crt /etc/haproxy/certs/site.pem
    # ACL برای مسیرهای API
    acl is_api path_beg /api/
    use_backend api_servers if is_api
    default_backend web_servers

backend web_servers
    balance roundrobin
    option httpchk GET /health
    server web1 10.0.0.11:8080 check
    server web2 10.0.0.12:8080 check

backend api_servers
    balance leastconn
    option httpchk GET /health
    server api1 10.0.0.21:8080 check
    server api2 10.0.0.22:8080 check

# Sticky Session با Cookie
backend sticky_app
    balance roundrobin
    cookie SERVERID insert indirect nocache
    server s1 10.0.0.31:8080 check cookie s1
    server s2 10.0.0.32:8080 check cookie s2

listen stats
    bind *:8404
    stats enable
    stats uri /stats
Expected Behavior درخواست‌های /api/* به مجموعه‌ی API می‌روند (با الگوریتم کم‌ترین اتصال)، بقیه به وب؛ هر سرور خراب به‌صورت خودکار از چرخه خارج و پس از بهبود بازگردانده می‌شود.
Reload بدون قطعی با haproxy -sf $(cat /run/haproxy.pid) می‌توان پیکربندی را بدون قطع اتصال‌های موجود به‌روزرسانی کرد — پایه‌ی Zero-Downtime Deployment.

بخش ۶مقایسه و جمع‌بندی

معیارHAProxyNGINX
Load Balancing تخصصی✅ بسیار پیشرفتهخوب
Health Check✅ غنی و فعالپایه (Passive/Active)
سرو فایل استاتیکضعیف/ندارد✅ عالی
Stats Page✅ داخلیبا افزونه
کاربرد اصلیلبه‌ی توزیع بارWeb Server + Reverse Proxy
AdvantagesDisadvantages
کارایی و پایداری بی‌نظیر در توزیع بارفایل استاتیک سرو نمی‌کند
Health Check دقیق و خودکارپیکربندی و یادگیری جدا از NGINX
Stats و Observability داخلیبرای پروژه‌های ساده، اضافه‌کاری است
When to Useسیستم‌های پرترافیک، Microservice با چند سرویس، و جایی که High Availability و توزیع بار حرفه‌ای لازم است.
When NOT to Useپروژه‌های کوچک تک‌سروری که NGINX به‌تنهایی هم استاتیک، هم Reverse Proxy و هم بار پایه را مدیریت می‌کند.

ترکیب رایج و قدرتمند این است: HAProxy در لبه برای توزیع و Health Check، و NGINX پشت آن برای TLS و فایل استاتیک. هرکدام را برای کاری که در آن بهترین است به کار ببرید.
