اسکوپ فانکشن‌ها در کاتلین: راهنمای کامل let، run، with، apply و also

پنج تابع کوچک در کتابخانه‌ی استاندارد کاتلین وجود دارند که ظاهرشان ساده است، اما همین پنج تابع بیشترین سردرگمی را برای توسعه‌دهندگان تازه‌کار می‌سازند: let، run، with، apply و also. تفاوت آن‌ها فقط دو چیز است — «شیء چطور در دسترس است (this یا it)» و «چه‌چیزی برمی‌گردانند». در این مقاله هر پنج تابع را با نمونه‌کد می‌شکنیم، جدول مقایسه‌ای می‌سازیم، دام‌های پنهان (نام‌گذاری، بازگشت غیرمحلی و تودرتویی) را نشان می‌دهیم و در نهایت یک درخت تصمیم می‌سازیم تا در هر موقعیت بدانید کدام را انتخاب کنید.

بخش ۱اسکوپ فانکشن چیست و چه دردی را درمان می‌کند؟

اسکوپ فانکشن (Scope Function) تابعی است که یک شیء را برمی‌دارد، یک بلوک کد را در «دامنه‌ی» آن شیء اجرا می‌کند و اجازه می‌دهد بدون تکرار نام شیء با آن کار کنید. به همین دلیل به آن‌ها «توابع دامنه» هم می‌گویند. آن‌ها در کتابخانه‌ی استاندارد کاتلین تعریف شده‌اند و نیازی به هیچ وابستگی بیرونی ندارند.

مسئله‌ی اصلی این است: وقتی چند عملیات پشت‌سرهم روی یک شیء انجام می‌دهیم، نام آن شیء مدام تکرار می‌شود و کد شلوغ می‌شود. یک اسکوپ فانکشن این تکرار را حذف می‌کند و ذهن خواننده را روی «چه کاری داریم انجام می‌دهیم» متمرکز نگه می‌دارد، نه «روی چه چیزی». 

// ✗ بدون اسکوپ فانکشن: نام شیء چهار بار تکرار شده است
val user = User()
user.name = "Gull"
user.age = 19
user.city = "Gujrat"
println(user.name)

// ✓ با apply: شیء یک بار ساخته می‌شود و بلوک داخل دامنه‌ی آن اجرا می‌شود
val user = User().apply {
    name = "Gull"   // this همان user است؛ لازم نیست نامش را بنویسیم
    age = 19
    city = "Gujrat"
    println(name)
}

به این تغییر ساده دقت کنید: در بلوک apply دیگر user. نمی‌نویسیم، چون گیرنده (this) همان شیء است. این «حذف نویز» ظاهراً کوچک، در پیکربندی‌های طولانی (مثل ساخت یک Intent یا OkHttpClient) بسیار تأثیرگذار می‌شود.

۱.۱ چرا از اسکوپ فانکشن استفاده کنیم؟

دلیلتوضیح
کد تمیزترحذف تکرار نام شیء و کاهش کد اضافه، بدون کاهش خوانایی.
کد ایمن‌تربا ?.let و with می‌توان زنجیره‌ی تکراری بررسی null را کوتاه کرد.
دامنه‌ی محدودمتغیرهای موقت فقط داخل بلوک زنده‌اند و بیرون آن نشت نمی‌کنند.
پیکربندی گویاترapply برای ساختن/تنظیم شیء، خواندن را از «ساخت» جدا می‌کند.
بدون هزینه‌ی اجراهر پنج تابع inline هستند؛ پس هیچ سرباری در زمان اجرا ندارند.
عمیق‌تر: چرا اصلاً «اسکوپ»؟ در کاتلین یک بلوک { ... } می‌تواند یک گیرنده‌ی ضمنی (implicit receiver) داشته باشد. این همان مکانیزمی است که DSLهایی مثل buildString { }، android { } در Gradle و DSLهای Compose روی آن ساخته شده‌اند. اسکوپ فانکشن‌ها در واقع سطحی از همین قابلیت زبان‌اند: یک شیء را به‌عنوان گیرنده‌ی بلوک به شما می‌دهند.

بخش ۲پنج اسکوپ فانکشن در یک نگاه

تنها دو مؤلفه، هویت هر اسکوپ فانکشن را می‌سازند:

  1. شیء چطور در دسترس است؟ یا به‌عنوان this (گیرنده) است یا به‌عنوان آرگومان it.
  2. چه‌چیزی برمی‌گرداند؟ یا خود شیء (گیرنده) را برمی‌گرداند یا نتیجه‌ی آخرین عبارت بلوک (lambda result).

با ترکیب این دو، دقیقاً چهار خانه به دست می‌آید و پنج تابع در آن‌ها جا می‌گیرند (run و with یک خانه را شریک‌اند):

تابعشیء را چطور می‌بیندخروجیمعمولاً برای…
letitنتیجه‌ی بلوکمقدار nullable، تبدیل، محدودسازی دامنه
runthisنتیجه‌ی بلوکپیکربندی + محاسبه‌ی نتیجه در یک بلوک
withthisنتیجه‌ی بلوکچند عملیات روی شیئی که از قبل داریم
applythisخود شیءپیکربندی و ساختن شیء
alsoitخود شیءعوارض جانبی: لاگ، اعتبارسنجی، زنجیره‌سازی
یک قاعده‌ی حفظ‌کردنی اگر می‌خواهید شیء را بدهید → apply (پیکربندی) یا also (کار جانبی).
اگر می‌خواهید نتیجه را بدهید → let، run یا with.
اگر با it راحت‌ترید → let یا also. اگر می‌خواهید this باشد → run، with یا apply.

بخش ۳let — کار با مقدار nullable و تبدیل

let شیء را به‌عنوان it در اختیار بلوک می‌گذارد و نتیجه‌ی بلوک را برمی‌گرداند. پرکاربردترین نقش آن، کار کردن با مقادیر nullable و «تبدیل» یک مقدار به مقدار دیگر است. 

val name: String? = user.name

// ۱) کار ایمن با مقدار nullable: بلوک فقط وقتی null نباشد اجرا می‌شود
name?.let {
    println("طول نام: ${it.length}")
}

// ۲) تبدیل و مقدار پیش‌فرض با Elvis
val upper = name?.let { it.trim().uppercase() } ?: "ناشناس"

// ۳) محدود کردن دامنه‌ی متغیر موقت
val firstEven = listOf(3, 5, 8, 9)
    .firstOrNull { it % 2 == 0 }
    .let { it?.times(10) ?: 0 }

// ۴) زنجیره‌ی null-safe روی شیء تودرتو
val city = order?.customer?.address?.let { it.city } ?: "نامشخص"

۳.۱ چرا it و نه this؟

در let عمداً از it استفاده شده تا اگر داخل بلوک به this اشاره کردید، منظورتان شیء بیرونی باشد، نه شیء دامنه. مثلاً در یک متد کلاس، داخل someValue?.let { } نوشتن this به کلاس اشاره می‌کند و این دقیقاً همان چیزی است که معمولاً می‌خواهیم.

دام: نام‌گذاری صریح it برای خوانایی اگر بلوک let طولانی است یا it تودرتو شده، نام‌گذاری صریح آرگومان (let { value -> ... }) جلوی سردرگمی را می‌گیرد. نام‌گذاری صریح فقط برای خوانایی است و هیچ هزینه‌ی اجرایی ندارد. 
// وقتی it مبهم است، خودمان نام می‌دهیم
user?.let { u ->
    settings?.let { s ->
        println("${u.name} → ${s.theme}")
    }
}

بخش ۴run و with — اجرای بلوک و بازگشت نتیجه

هر دو تابع شیء را به‌عنوان this در اختیار می‌گذارند و نتیجه‌ی بلوک را برمی‌گردانند. تفاوت اصلی‌شان در «نحوه‌ی فراخوانی» است: 

// run به‌صورت تابع الحاقی روی شیء صدا زده می‌شود (مناسب زنجیره و null-safety)
val greeting = user.run {
    "سلام $name، ${age} ساله"
}

// with به‌صورت تابع معمولی و با شیء به‌عنوان آرگومان (مناسب شیء آماده و غیرnullable)
val info = with(user) {
    "$name ($age) از $city"
}

۴.۱ run بدون گیرنده

run یک نسخه‌ی بدون گیرنده هم دارد که دقیقاً مثل یک بلوک اجرایی عمل می‌کند و نتیجه‌ی آخرین عبارت را برمی‌گرداند. برای گروه‌بندی محاسبات موقت و نگه‌داشتن متغیرها در یک دامنه‌ی کوچک عالی است. 

val config = run {
    val a = loadA()   // این دو متغیر فقط داخل این بلوک زنده‌اند
    val b = loadB()
    a + b             // نتیجه‌ی بلوک
}
موقعیتletrunwith
شیء null می‌تواند باشدبا ?. عالیبا ?. عالیمناسب نیست
زنجیره‌سازی روی یک شیءبلهبلهخیر
شیء از قبل آماده و مطمئن استنتیجه را بدهنتیجه را بدهخواندنی‌ترین
دسترسی به شیءitthisthis
چه زمانی with را به run ترجیح دهیم؟ وقتی شیء غیرnullable است و می‌خواهیم چند عملیات را روی آن انجام دهیم، with خواناتر است چون «شیء» را در ابتدای بلوک صریح می‌کند: with(bitmap) { compress(...); recycle() }. اگر احتمال null بودن هست یا می‌خواهید زنجیره ادامه پیدا کند، run انتخاب بهتری است.

بخش ۵apply — پیکربندی شیء

apply شیء را به‌عنوان this می‌دهد و در پایان خود شیء را برمی‌گرداند. این ترکیب، آن را به ابزار اصلی «ساختن و آماده‌سازی» تبدیل می‌کند: داخل بلوک پیکربندی می‌کنید و بیرون، همان شیء آماده را تحویل می‌گیرید. 

val user = User().apply {
    name = "Gull"
    age = 19
    city = "Gujrat"
}
// user یک نمونه‌ی کامل و پیکربندی‌شده است

val intent = Intent(context, DetailActivity::class.java).apply {
    putExtra("id", 42)
    flags = Intent.FLAG_ACTIVITY_NEW_TASK
}

val client = OkHttpClient.Builder().apply {
    connectTimeout(30, TimeUnit.SECONDS)
    readTimeout(30, TimeUnit.SECONDS)
}.build()

۵.۱ الگوی «ساخت و تنظیم» در یک عبارت

به خط آخر مثال بالا دقت کنید: یک Builder ساخته می‌شود، داخل apply پیکربندی می‌شود و چون apply خود builder را برمی‌گرداند، بلافاصله .build() صدا زده می‌شود. این زنجیره یکی از تمیزترین الگوهای استفاده از apply در کد واقعی است.

دام: خروجی apply همیشه خود شیء است اگر داخل apply محاسبه‌ای انجام دهید و انتظار داشته باشید نتیجه‌اش برگردد، اشتباه کرده‌اید؛ apply همیشه شیء را برمی‌گرداند و مقدار بلوک را دور می‌ریزد. برای برگرداندن نتیجه از run یا let استفاده کنید. 
// ✗ نتیجه‌ی محاسبه گم می‌شود: apply همیشه user را برمی‌گرداند
val result = user.apply { age + 1 }   // result همان user است، نه 20

// ✓ اگر نتیجه را می‌خواهید از run استفاده کنید
val nextAge = user.run { age + 1 }    // nextAge = 20

بخش ۶also — عوارض جانبی و زنجیره‌سازی

also شیء را به‌عنوان it می‌دهد و خود شیء را برمی‌گرداند. تفاوتش با apply در دو چیز است: آن‌که در also داخل بلوک this عوض نمی‌شود و شیء با it در دسترس است. به همین دلیل also برای «کارهای جانبی» مناسب است: لاگ‌گیری، اعتبارسنجی، اطلاع‌رسانی — بدون اینکه مقدار اصلی دست بخورد. 

// زنجیره‌سازی: شیء دست‌نخورده رد می‌شود و در مسیر لاگ می‌گیریم
val numbers = mutableListOf(1, 2, 3)
    .also { println("قبل: $it") }
    .apply { add(4) }
    .also { println("بعد: $it") }
// بعد: [1, 2, 3, 4]

// اعتبارسنجی بدون تغییر مقدار بازگشتی
fun save(user: User): User = user.also {
    require(it.age >= 18) { "سن باید بزرگ‌تر از ۱۸ باشد" }
}

۶.۱ قاعده‌ی نام‌گذاری: apply برای «تغییر»، also برای «نگاه»

اصطلاحاً می‌گویند: apply برای چیزی است که بیرون به داخل اثر می‌گذارد (پیکربندی)، و also برای چیزی است که داخل به بیرون اثر می‌گذارد (لاگ، اعتبارسنجی):

مقایسهapplyalso
دسترسی به شیءthisit
خروجیخود شیءخود شیء
نیت اصلیپیکربندی و تغییر شیءتأثیر جانبی بدون تغییر شیء
مثالintent.apply { putExtra(...) }user.also { log(it) }

بخش ۷انتخاب درست: این در برابر it و درخت تصمیم

بزرگ‌ترین منبع سردرگمی، تفاوت this و it است. در توابعی که از this استفاده می‌کنند (run، with، apply) لازم نیست نام شیء را بنویسید و اعضای آن مستقیم در دسترس‌اند. در توابعی که از it استفاده می‌کنند (let، also) شیء یک آرگومان عادی است و می‌توان نام دلخواه روی آن گذاشت.

۷.۱ درخت تصمیم

بخش ۸نکات ریز، دام‌ها و بهترین شیوه‌ها

اینجا همان «ریز جزئیاتی» است که تفاوت بین کد کارکننده و کد حرفه‌ای را می‌سازد.

۸.۱ همه‌ی اسکوپ فانکشن‌ها inline هستند

هر پنج تابع در کتابخانه‌ی استاندارد به‌صورت inline تعریف شده‌اند؛ یعنی بدنه‌ی lambda در زمان کامپایل داخل کد شما کپی می‌شود. نتیجه: صفر شیء lambda و صفر سربار فراخوانی در زمان اجرا. پس نگرانی از «هزینه‌ی پرفورمنس اسکوپ فانکشن» بی‌اساس است.

۸.۲ بازگشت غیرمحلی (non-local return)

چون توابع inline هستند، یک return ساده داخل بلوک، از تابع بیرونی برمی‌گردد، نه فقط از بلوک. این می‌تواند نجات‌دهنده باشد یا دام: 

fun firstNegative(list: List<Int>): Int? {
    list.forEach { number ->
        // return از خود تابع firstNegative برمی‌گرداند (نه فقط از let)
        number.takeIf { it < 0 }?.let { return it }
    }
    return null
}

// اگر می‌خواهید فقط از بلوک برگردید، برچسب بگذارید:
val value = listOf(1, 2, 3).let block@{
    if (it.isEmpty()) return@block 0
    it.sum()
}
دام: return بدون برچسب، از تابع بیرونی برمی‌گردد اگر عمدی نبوده، این رفتار می‌تواند منطق کد را بشکند. برای بازگشت از خود بلوک از برچسب (return@let، return@apply و…) استفاده کنید. دقت کنید break و continue داخل این بلوک‌ها مجاز نیستند (چون حلقه نیستند) و فقط با برچسب‌های حلقه ممکن‌اند.

۸.۳ هم‌نامی در تودرتویی

// این name به نزدیک‌ترین گیرنده (settings) اشاره می‌کند، نه user
user.apply {
    settings.apply {
        name = "dark"          // این settings.name است
        this@apply.name = "A"  // برای user باید برچسب بدهیم
    }
}

// راه روشن‌تر: گیرنده‌ی بیرونی را برچسب بزنید
user.apply outer@{
    settings.apply {
        this@outer.name = "A"
    }
}

this@apply به نزدیک‌ترین apply اشاره دارد. اگر چند apply تودرتو دارید، برچسب صریح (outer@) تنها راه قابل‌اعتماد برای دسترسی به گیرنده‌ی بیرونی است. بهترین راه‌حل، اما پرهیز از تودرتویی بی‌مورد است.

۸.۴ اسکوپ فانکشن با takeIf و takeUnless

takeIf اگر شرط برقرار باشد خود شیء را برمی‌گرداند، وگرنه null. ترکیب آن با let یا also بسیار گویا می‌شود: 

val validEmail = input
    .trim()
    .takeIf { it.contains("@") }
    ?.lowercase()
    ?: error("ایمیل نامعتبر است")

// زنجیره‌ی گویا: «اگر کاربر فعال بود، لاگ بزن و بفرست»
user.takeIf { it.isActive }
    ?.also { log("فعال شد") }
    ?.let { notify(it) }

۸.۵ بهترین شیوه‌ها

  1. هر بلوک اسکوپ فانکشن باید یک «نیت» روشن داشته باشد؛ پخش‌وپلا کردن بلوک‌های طولانی، خوانایی را کم می‌کند.
  2. برای پیکربندی از apply، برای کارهای جانبی از also استفاده کنید — نیت را با تابع هم‌راستا نگه دارید.
  3. از تودرتویی بیش از دو سطح خودداری کنید؛ اگر ناچار شدید، گیرنده‌ی بیرونی را برچسب بزنید.
  4. وقتی it گنگ می‌شود، نام‌گذاری صریح بگذارید: let { user -> ... }.
  5. از also برای تغییر وضعیت شیء استفاده نکنید؛ آن کار apply است.
  6. به‌جای زنجیره‌ی طولانی let، گاهی یک if ساده یا متغیر محلی خواناتر است.
  7. روی مقدار non-null و آماده، with معمولاً از run خواناتر است.
  8. هیچ‌وقت return غیرمحلی را ناخواسته در بلوک نگذارید؛ نیت را با برچسب صریح کنید.

بخش ۹اسکوپ فانکشن‌ها در کد واقعی (اندروید و Compose)

اکنون کاربردهای واقعی را ببینیم؛ جاهایی که این پنج تابع هر روز در کد اندروید ظاهر می‌شوند.

۹.۱ مدیریت مقدار nullable در Compose

@Composable
fun Avatar(user: User?) {
    user?.let {
        Image(
            painter = rememberAsyncImagePainter(it.avatar),
            contentDescription = it.name,
            modifier = Modifier.clip(CircleShape),
        )
    }
}

۹.۲ کار امن با فایل و منبع

fun readConfig(path: String): String = File(path).let { file ->
    require(file.exists()) { "فایل پیدا نشد: $path" }
    file.readText()
}

// پایان دادن به دامنه‌ی منبع به‌شکل گویا
val text = StringBuilder().apply {
    append("عنوان")
    append("\n")
    append("متن")
}.toString()

۹.۳ به‌روزرسانی اتمی وضعیت ViewModel

data class UiState(
    val loading: Boolean = false,
    val items: List<Item> = emptyList(),
)

private val _state = MutableStateFlow(UiState())
val state: StateFlow<UiState> = _state.asStateFlow()

fun addItems(newItems: List<Item>) {
    _state.update { current ->
        current.copy(items = current.items + newItems, loading = false)
    }
}

// نسخه‌ی گویا با run برای بازگشت نتیجه‌ی محاسبه
fun total(): Int = state.value.run { items.sumOf { it.price } }

۹.۴ اعتبارسنجی و لاگ در زنجیره‌ی پردازش

fun process(raw: String): Order =
    raw.trim()
        .takeIf { it.isNotEmpty() }
        ?.let(::parseOrder)
        ?.also { log("سفارش خوانده شد: ${it.id}") }
        ?.takeIf { it.isValid() }
        ?.apply { status = Status.READY }
        ?: throw IllegalArgumentException("سفارش نامعتبر")
الگوهای بد (Anti-patterns) ۱) استفاده از let برای پنهان‌کردن یک شرط ساده به‌جای if.
۲) زنجیره‌ی چهارپنج‌تایی از let/also/apply که هیچ‌کس نمی‌تواند سریع بخواند.
۳) تغییر وضعیت شیء با also که نیت را گمراه می‌کند.
۴) apply کردن روی شیء فقط برای اینکه یک‌بار return غیرمحلی بزنید.
۵) تکرار ?.let { } به‌جای استخراج یک متغیر و یک if تمیز.

بخش ۱۰جمع‌بندی، چک‌لیست و منابع

اسکوپ فانکشن‌ها جادو نیستند؛ فقط دو ایده را ترکیب می‌کنند: «شیء را با this یا it در دسترس بگذار» و «خود شیء یا نتیجه‌ی بلوک را برگردان». اگر همین دو محور را در ذهن نگه دارید، انتخاب بین پنج تابع به یک تصمیم چندثانیه‌ای تبدیل می‌شود.

می‌خواهید…انتخاب
روی مقدار nullable کار کنید و نتیجه بگیریدlet
شیء را پیکربندی کنید و همان شیء را بگیریدapply
کار جانبی (لاگ/اعتبارسنجی) کنید و شیء دست‌نخورده رد شودalso
چند عملیات روی شیء آماده انجام دهید و نتیجه بگیریدwith
بلوک را روی this اجرا کنید و نتیجه بگیرید (با امکان زنجیره)run

۱۰.۱ چک‌لیست نهایی

  1. نیت بلوک روشن است: پیکربندی (apply)، عارضه‌ی جانبی (also)، یا محاسبه (let/run/with).
  2. خروجی موردنیاز را می‌دانم: خود شیء یا نتیجه‌ی بلوک.
  3. در تودرتویی، از it یا برچسب صریح this@label استفاده کرده‌ام.
  4. هیچ return غیرمحلی ناخواسته‌ای وجود ندارد.
  5. itهای گنگ را با نام صریح جایگزین کرده‌ام.
  6. از زنجیره‌های طولانی و پرتکرار پرهیز کرده‌ام.
  7. روی شیء غیرnullable و آماده، with را به‌جای run در نظر گرفته‌ام.
  8. کد پس از حذف اسکوپ فانکشن، واقعاً کوتاه‌تر یا روشن‌تر می‌شود (نه فقط متفاوت).
