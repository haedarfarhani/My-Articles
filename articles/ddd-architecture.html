بخش ۱مقدمه: نرم‌افزاری که زبان کسب‌وکار را نمی‌فهمد

یک سیستم فروش را در نظر بگیرید. کارشناس کسب‌وکار می‌گوید: «وقتی مشتری بیش از ۵۰۰ هزار تومان خرید کرد و قبلاً سفارش تسویه‌شده دارد، او را وفادار حساب کنید و ۱۰٪ تخفیف بدهید». مهندس نرم‌افزار به دیتابیس نگاه می‌کند و می‌نویسد: 

SELECT COUNT(*) FROM orders
WHERE customer_id = ? AND status = 'SETTLED';

-- اگر نتیجه > 0 و مبلغ > 500000 است:
UPDATE customers SET discount = 10 WHERE id = ?;

این کد کار می‌کند. ولی هیچ‌جای آن «وفاداری» وجود ندارد. شش ماه بعد، مدیر فروش می‌آید و می‌گوید «وفاداری یعنی بیش از ۲۰۰ هزار و خرید در ۹۰ روز گذشته». برای اعمال این تغییر باید دوباره کل سیستم را بگردید و ببینید این منطق در ۱۴ جا کپی شده است: در یک @Scheduled، در یک Service، در یک Trigger دیتابیس و حتی در یک فایل اکسل که دستی به‌روز می‌شود.

نشانه‌ی اصلی مشکل وقتی افراد کسب‌وکار برای تغییر یک قانون، مجبورند به شما پیام بدهند و شما در چند فایل دست ببرید، مشکل «کد کم» نیست؛ مشکل نبودِ مدل دامنه است. DDD دقیقاً برای همین وضعیت ساخته شده است.

DDD (طراحی دامنه‌محور) یعنی به‌جای اینکه از دیتابیس شروع کنیم و کد را به‌اطراف جدول‌ها بسازیم، از زبان کسب‌وکار شروع کنیم و مدل را داخل کد به‌اطراف مفاهیم واقعی بسازیم.

در این مقاله چه می‌آموزید؟

  • DDD دقیقاً چیست و چه تفاوتی با «لایه‌بندی» دارد (بخش ۳)
  • چرا Aggregate مهم‌ترین مفهوم DDD است و چگونه مرز تراکنش را تعیین می‌کند (بخش ۶)
  • تفاوت دقیق Entity و Value Object و اینکه چرا این تفاوت روی تست اثر می‌گذارد (بخش ۶)
  • چگونه یک دامنه‌ی واقعی (سفارش) را با Java 21 مدل کنیم (بخش‌های ۱۰ و ۱۱)
  • چه زمانی DDD اشتباه است و چه هزینه‌ای می‌پردازیم (بخش‌های ۱۴ و ۱۶)

بخش ۲تاریخچه و دلیل ایجاد

ایده‌ی DDD قدیم‌تر از آن است که فکر کنید نوشته شده است. ریشه‌ی آن به دهه‌ی ۱۹۶۰ و کار William Cooper در IBM برمی‌گردد؛ او برای اولین بار عبارت «مدل دامنه» (Domain Model) را در مقاله‌ای کلاسیک معرفی کرد. ایده‌ی مرکزی‌اش ساده و انقلابی بود:

نقل‌قول Cooper «به‌جای اینکه برنامه را با توجه به پایگاه داده طراحی کنیم، باید پایگاه داده را با توجه به برنامه طراحی کنیم.»

چرا در آن زمان کسی جدی نگرفت؟

تا قبل از حدود ۲۰۱۰، نرم‌افزار «شیءگرا» در عمل یعنی «لایه‌بندی با کلاس‌هایی به نام Service و Manager». بیشتر تیم‌ها مدل دامنه را یک هزینه‌ی اختیاری می‌دیدند: «اگر وقت داشتیم اضافه می‌کنیم».

سه چیز این نگاه را عوض کرد:

  1. بحران نرم‌افزار بومی (2001): آژانس‌های دولتی پروژه‌ها را برون‌سپاری کردند و سازنده سال بعد عوض شد؛ مدل دامنه‌ی مستندشده تنها دارایی باقی‌مانده بود.
  2. موج میکروسرویس (2014 به بعد): فهمیدیم «مرز سرویس» دقیقاً همان «مرز دامنه» است و اینکه DDD ابزار طراحی این مرزهاست.
  3. تمرکز بر هزینه‌ی تغییر: داده نشان داد سیستم‌هایی که مدل دامنه‌ی صریح دارند کمتر تغییر می‌کنند و وقتی تغییر می‌دهند، محل تغییرشان محدود و قابل پیش‌بینی است.
نکته‌ی مهم برای تازه‌کارها DDD یک روش‌شناسی کشف و مدل‌سازی است، نه یک فریم‌ورک و نه یک کتابخانه. نمی‌توانید با نصب یک پکیج آن را به پروژه اضافه کنید. بخش بزرگی از کار، گفت‌وگو با کسب‌وکار است — و این کار در هیچ ابزاری خودکار نمی‌شود.

بخش ۳DDD چیست؟ (تعریف دقیق)

DDD یعنی طراحی نرم‌افزار با تمرکز بر «مدل دامنه»: مدلی که مفاهیم، قواعد و زبان کسب‌وکار را بازتاب می‌دهد — نه ساختار دیتابیس و نه ساختار شبکه. این تعریف از خود ایوانز است و سه جزء جدا دارد که اغلب با هم اشتباه گرفته می‌شوند:

  1. Strategic Design (طراحی راهبردی) — تقسیم سیستم به زیرسیستم‌ها و زمینه‌های محدود (Bounded Context). این بخش درباره‌ی مرزها است و در سطح سیستم کار می‌کند.
  2. Tactical Design (طراحی تاکتیکی) — ساخت مدل داخل یک زمینه‌ی محدود با Entity، Value Object، Aggregate، Domain Service و Domain Event. این بخش درباره‌ی مدل است و در سطح کلاس‌ها کار می‌کند.
  3. Ubiquitous Language (زبان همه‌جاست) — یک واژگان مشترک بین کسب‌وکار و کد که در هر دو طرف دقیقاً یک معنا دارد.
تعریف یک‌خطی DDD یعنی «کسب‌وکار را مدل کن، مدل را داخل کد بنویس، و نام‌های کد را همان نام‌های کسب‌وکار بگذار».

DDD یعنی «لایه‌بندی» نیست

این مهم‌ترین سوءتفاهم درباره‌ی DDD است. هر پروژه‌ای لایه‌ی repository، service و controller دارد، اما این لایه‌بندی است، نه DDD. تفاوت‌ها:

بخش ۴مشکل قبل از استفاده

برای فهمیدن ارزش DDD، باید درد «بدون DDD» را دقیق بدانیم. چهار الگوی رایج در کدبیس‌های بزرگ که DDD درمان می‌کند:

۱. مدل داده‌ای به‌جای مدل دامنه (Data Model)

// مدل داده‌ای کلاسیک: کلاس فقط یک کیسه‌ی داده است
public class Customer {
    private Long id;
    private String name;
    private String email;
    private String phone;
    private Integer statusCode;   // ← عدد بی‌معنا
    private Integer typeCode;     // ← عدد بی‌معنا

    // هیچ رفتاری وجود ندارد؛ «مشتری» نمی‌داند چه کاری می‌کند
}

قواعد کسب‌وکار کجا می‌روند؟ در CustomerService که به‌مرور به یک کلاس ۱۰۰۰ خطی تبدیل می‌شود: 

public class CustomerService {
    public void process(Long id) {
        // ۲۸۷ خط کد با ۱۴ if و ۹ حلقه و ۵ پرس‌وجوی دیتابیس
        // و هیچ‌کدام ربطی به «مشتری» به‌عنوان یک مفهوم کسب‌وکاری ندارد
    }
}

۲. مدل贫血 (Anemic Domain Model)

حالت رایج‌تر و بدتر: کلاس‌ها ساختار دارند ولی هیچ رفتاری ندارند و همه‌ی منطق در سرویس‌هاست. Customer فقط getter/setter دارد. این یعنی کسب‌وکار «هیچ‌جا» نیست — قوانین در سرویس‌ها پخش‌اند و کسی نمی‌تواند بگوید قانون «وفاداری» دقیقاً کجاست.

۳. نشتی جزئیات فنی به دامنه (Leaky Abstraction)

public class CustomerService {
    public List<Customer> findActiveCustomers() {
        // ← منطق کسب‌وکار به SQL آلوده شده
        return jdbcTemplate.query(
            "SELECT * FROM customers WHERE status = 1", this::map);
    }
}

حالا تغییر دیتابیس (مثلاً مهاجرت به MongoDB) یعنی بازنویسی منطق کسب‌وکار. این دقیقاً همان چیزی است که DDD با مرز Aggregate و Repository حل می‌کند.

۴. قوانین پخش‌شده و تکراری

قانون «سفارش بالای ۱۰۰ عدد باید تأیید مدیر بگیرد» ممکن است در پنج جا نوشته شده باشد: کنترلر، سرویس، یک Trigger، یک Job زمان‌بندی‌شده و یک سرویس بیرونی. تغییر قانون یعنی پنج ویرایش و امید به اینکه همه را پیدا کنید.

هزینه‌ی پنهان این وضعیت هیچ‌کدام از این مشکلات در کوتاه‌مدت دردناک نیستند. درد در ماه ششم شروع می‌شود: تغییری که باید ۳۰ دقیقه طول بکشد، سه روز می‌گیرد چون «نمی‌دانیم این قانون کجاها کپی شده». DDD سرعت تغییر را بهبود می‌دهد، نه سرعت نوشتن کد را.

بخش ۵ایده اصلی: زبان مشترک و مدل دامنه

اگر فقط یک چیز از DDD را باید به خاطر بسپارید، آن یکی Ubiquitous Language (زبان همه‌جاست) است. ایوانز آن را چنین تعریف می‌کند:

Ubiquitous Language «یک زبان مشترک بین برنامه‌نویسان و متخصصان کسب‌وکار، در یک محدوده‌ی مشخص، که در آن مدل و کد ساختار مشترکی دارند.»

یعنی نامی که کارشناس فروش به کار می‌برد، باید دقیقاً همان نام در کد باشد. اگر کسب‌وکار می‌گوید «سفارش در وضعیت تأییدنشده»، در کد نباید OrderStatus.PENDING_REVIEW باشد.

واژه‌ی کسب‌وکار❌ نام اشتباه در کد✅ نام درست در کدچرا؟
سفارشOrderEntityOrderپسوند Entity نویز است
سبد خریدCartObjectShoppingCart«Cart» واژه‌ی فنی است، «سبد خرید» واژه‌ی کسب‌وکار
تخفیفDiscountDTODiscountDTO یعنی داده‌ی انتقال، نه قاعده‌ی کسب‌وکار
مهلت پرداختexpireTimePaymentDeadlineواژه‌ی کسب‌وکار، نه پیاده‌سازی فنی

زبان مشترک چگونه ساخته می‌شود؟

  1. Event Storming: یک کارگاه ۲ تا ۳ ساعته با کسب‌وکار، توسعه‌دهنده و QA. روی تخته، «رویداد»های دامنه را می‌چینید: «سفارش ثبت شد»، «پرداخت تأیید شد»، … این واژه‌ها دقیقاً همان‌هایی هستند که باید کلاس Event شما باشند.
  2. مدل دامنه‌ی مشترک: یک مستند کوچک یا یک ویکی که در آن هر مفهوم با تعریف، مثال، و قواعدش آمده است.
  3. تداوم در کد: نام مفهوم در کد، نام فیلد در DTO، نام جدول در دیتابیس و نام تسک در Jira — همه یکی.

مدل دامنه چه ویژگی‌هایی دارد؟

  • مدل، قواعد کسب‌وکار را در خود نگه می‌دارد، نه در سرویس‌ها
  • مدل مستقل از ذخیره‌سازی است: در دامنه هیچ @Entity وابسته به JPA نیست
  • مدل مستقل از رابط کاربری است: هیچ DTO فرمی در آن نیست
  • مدل قابل تست بدون زیرساخت است
  • مدل کوچک و دقیق است، نه همه‌چیز از همه‌چیز
تست تشخیص سریع یک کلاس از مدل دامنه را بردارید و ببینید آیا بدون هیچ کتابخانه‌ی بیرونی (بدون Spring، بدون JPA) قابل new کردن و فراخوانی است. اگر بله، مدل دارید. اگر نه، Service دارید.

بخش ۶مفاهیم کلیدی دامنه

پنج مفهوم، ستون فقرات DDD تاکتیکی هستند. بیایید هرکدام را با یک مثال واحد (سفارش) تعریف کنیم.

Entity (موجودیت)

چیزی که هویت دارد، حتی اگر ویژگی‌هایش عوض شود. دو کاربر با نام یکسان دو Entity متفاوت هستند. معیار تشخیص: آیا می‌توانید بگویید «این همان یکی است»؟ اگر بله، Entity است. 

public final class Order {          // ← Entity: دارای هویت
    private final OrderId id;    // ← هویت، هرگز عوض نمی‌شود
    private CustomerId customerId;
    private List<OrderLine> lines = new ArrayList<>();
    private Money total;         // ← ویژگی‌ها عوض می‌شوند

    // مقایسه بر اساس هویت، نه بر اساس محتوا
    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof Order other)) return false;
        return id.equals(other.id);   // ← نکته‌ی کلیدی
    }

    @Override
    public int hashCode() {
        return id.hashCode();
    }
}

Value Object (شیء مقداری)

چیزی که هویت ندارد و تمام ارزشش در مقادیرش است. «۱۰۰ هزار تومان» یک Value Object است؛ دو تا از آن با مبلغ یکسان برابرند. VOها تغییرناپذیر (Immutable) هستند و در عمل ۲۰ تا ۳۰٪ کدبیس واقعی را می‌سازند چون پارامترهای نامعتبر را در constructor حذف می‌کنند. 

public record Money(BigDecimal amount, Currency currency) {

    public Money {
        Objects.requireNonNull(amount, "مبلغ نمی‌تواند null باشد");
        Objects.requireNonNull(currency, "ارز نمی‌تواند null باشد");
        if (amount.scale() > 2) {
            throw new IllegalArgumentException("مبلغ بیش از دو رقم اعشار ندارد");
        }
        if (amount.signum() < 0) {
            throw new IllegalArgumentException("مبلغ نمی‌تواند منفی باشد");
        }
    }

    public Money add(Money other) {
        if (!currency.equals(other.currency)) {
            throw new IllegalArgumentException("جمع دو ارز متفاوت ممکن نیست");
        }
        return new Money(amount.add(other.amount), currency);
    }

    // مقایسه بر اساس محتوا — و چون record است، خودکار انجام می‌شود
}

Aggregate (تجمیع) و Aggregate Root

این مهم‌ترین مفهوم DDD است. Aggregate یک مجموعه‌ی شیء است که با هم یک واحد تراکنش می‌سازند. قاعده‌ی طلایی:

قاعده‌ی Aggregate «یک تراکنش، فقط یک Aggregate را تغییر می‌دهد. سایر Aggregate‌ها از طریق شناسه (id) ارجاع می‌شوند، نه شیء.»
چرا این قاعده انقدر مهم است؟ اگر داخل یک تراکنش به دو Aggregate دست بزنید، قفل لازم می‌شود و race condition وارد سیستم می‌شود. اگر Aggregate را کوچک نگیرید (مثلاً کل سیستم را یک Aggregate کنید)، عملکرد فرو می‌ریزد. اندازه‌ی درست Aggregate یک تصمیم معماری واقعی است.

Aggregate Root تنها شیءی است که بیرون از Aggregate می‌تواند آن را دریافت و ویرایش کند. بقیه‌ی اعضا فقط از داخل Root در دسترس‌اند. این قاعده باعث می‌شود کسی نتواند order.getLines().get(0).setPrice(-100) بکند و سیستم را خراب کند.

Domain Service

وقتی یک قاعده به بیش از یک Aggregate مربوط است، جای طبیعی‌اش داخل هیچ‌کدام از آن‌ها نیست. آن‌وقت یک Domain Service بدون وضعیت (stateless) می‌سازید: 

public final class LoyaltyPolicy {

    private LoyaltyPolicy() {}   // ← فقط متد استاتیک، نه آبجکت

    public static boolean isLoyal(Customer customer, OrderHistory history) {
        // این قاعده هم به Customer مربوط است، هم به OrderHistory
        return history.settledCountInLastDays(90) >= 3
            && history.totalSpentInLastDays(90).isGreaterThan(Money.toman(2_000_000));
    }
}

رویدادی که در دامنه اتفاق افتاده و گذشته است. تفاوتش با پیام سیستمی این است که پیام سیستمی درباره‌ی «اطلاع‌رسانی» است، اما Domain Event درباره‌ی تغییر وضعیت:

        OrderId orderId,

بخش ۷Repository و Service دامنه

Repository در DDD فقط یک الگوی دسترسی به داده نیست؛ یک جمع‌کننده‌ی موجودیت‌های یک Aggregate است. این تعریف، تمام تفاوت‌ها را توضیح می‌دهد.

بخش ۹جریان داده (Data Flow)

جریان خواندن در یک DDD سالم همیشه یک مسیر مشخص دارد. هر گام جداست و می‌توان آن را تست کرد:

قواعد جریان داده

  • ورودی همیشه Command است، نه مستقیم Entity — تا لایه‌ی بالا نتواند بی‌دلیل فیلدهای مدل را عوض کند
  • خروجی همیشه DTO است، نه Entity — تا ساختار مدل در API لو نرود
  • تبدیل فقط در دو نقطه: Request → Command در لایه‌ی UI و Entity ⇄ JPA در لایه‌ی زیرساخت
  • هیچ‌گاه لایه‌ی UI مستقیم Repository را صدا نزند
  • هیچ‌گاه Aggregate دوم در همان تراکنش بارگذاری نشود

جریان نوشتن — چه چیزی ذخیره می‌شود؟

در یک تراکنش، این‌ها ذخیره می‌شوند:
  ✅ Order (Aggregate 1)  → جدول orders
  ✅ OrderLineهای آن     → جدول order_lines
  ✅ OutboxEventهای آن   → جدول outbox_events

در این تراکنش، این‌ها ذخیره نمی‌شوند (فقط ID خوانده می‌شوند):
  ⛔ Customer             → فقط customer_id خوانده می‌شود
  ⛔ Product              → فقط product_id خوانده می‌شود

بعد از commit، به‌صورت ناهمگام:
  📤 ارسال OrderPlaced به صف
  📧 ارسال ایمیل
  📊 به‌روزرسانی گزارش‌ها
الگوی Outbox اگر رویداد دامنه را قبل از commit در Kafka بفرستید و تراکنش fail شود، یک رویداد برای سفارشی می‌فرستید که اصلاً ثبت نشده. راه‌حل استاندارد: رویداد را در جدول outbox در همان تراکنش بنویسید، و یک پروسه‌ی جدا آن را به صف منتشر کند. این یکی از مهم‌ترین الگوهای عملی DDD است.

package com.shop.domain.order;

import java.util.List;

public final class Order {

    private final OrderId id;
    private final String customerId;
    private final List<OrderLine> lines;
    private OrderStatus status;
    private Money total;
    private final List<DomainEvent> events = new ArrayList<>();

    private Order(OrderId id, String customerId) {
        this.id = id;
        this.customerId = customerId;
        this.lines = new ArrayList<>();
        this.status = OrderStatus.DRAFT;
        this.total = Money.zero("IRR");
    }

    // ── نقطه‌ی ورود: ساخت از طریق کارخانه ──
    public static Order draft(String customerId) {
        if (customerId == null || customerId.isBlank()) {
            throw new OrderError("شناسه‌ی مشتری الزامی است");
        }
        return new Order(OrderId.newId(), customerId);
    }

    // ── متد دامنه: افزودن ردیف + اعتبارسنجی ──
    public Order addLine(String productId, int quantity, Money unitPrice) {
        ensureModifiable();
        if (quantity <= 0) {
            throw new OrderError("تعداد باید بزرگ‌تر از صفر باشد");
        }
        if (lines.size() >= 50) {
            throw new OrderError("سفارش نمی‌تواند بیش از ۵۰ ردیف داشته باشد");
        }
        if (lines.stream().anyMatch(l -> l.productId().equals(productId))) {
            throw new OrderError("این محصول قبلاً در سفارش هست؛ تعداد را تغییر دهید");
        }

        lines.add(new OrderLine(productId, quantity, unitPrice));
        recalculateTotal();      // ← مدل همیشه سازگار می‌ماند
        return this;
    }

    // ── انتقال وضعیت ──
    public Order place() {
        ensureModifiable();
        if (lines.isEmpty()) {
            throw new OrderError("سفارش بدون ردیف قابل ثبت نیست");
        }
        this.status = OrderStatus.PLACED;
        this.events.add(new OrderPlaced(id, customerId, total, Instant.now()));
        return this;
    }

    public boolean requiresApproval() {
        return total.isGreaterThan(Money.toman(10_000_000));
    }

    public void cancel(String reason) {
        if (status == OrderStatus.CANCELLED) {
            throw new OrderError("سفارش قبلاً لغو شده است");
        }
        if (status == OrderStatus.DELIVERED) {
            throw new OrderError("سفارش تحویل‌شده قابل لغو نیست");
        }
        this.status = OrderStatus.CANCELLED;
        this.events.add(new OrderCancelled(id, reason, Instant.now()));
    }

    private void ensureModifiable() {
        if (status != OrderStatus.DRAFT) {
            throw new OrderError("سفارش در وضعیت " + status + " قابل ویرایش نیست");
        }
    }

    private void recalculateTotal() {
        Money sum = Money.zero("IRR");
        for (OrderLine line : lines) {
            sum = sum.add(line.subtotal());
        }
        this.total = sum;
    }

    public List<DomainEvent> pullEvents() {
        List<DomainEvent> copy = List.copyOf(events);
        events.clear();
        return copy;
    }

    // ── getter های محدود (بدون setter!) ──
    public OrderId id()                { return id; }
    public String customerId()        { return customerId; }
    public OrderStatus status()       { return status; }
    public Money total()              { return total; }
    public List<OrderLine> lines() { return List.copyOf(lines); }
}
نکته‌ی کلیدی کد بالا هیچ setTotal() عمومی وجود ندارد. total فقط از راه addLine تغییر می‌کند. یعنی امکان ساختن موجودیت ناسازگار وجود ندارد — این دقیقاً همان چیزی است که «مدل دامنه‌ی درون‌گرا» انجام می‌دهد.

package com.shop.domain.order;

import java.math.BigDecimal;
import java.math.RoundingMode;
import java.util.Currency;
import java.util.Objects;

public record Money(BigDecimal amount, Currency currency) implements Comparable<Money> {

    public Money {
        Objects.requireNonNull(amount, "مبلغ نمی‌تواند null باشد");
        Objects.requireNonNull(currency, "ارز نمی‌تواند null باشد");
        if (amount.signum() < 0) {
            throw new OrderError("مبلغ نمی‌تواند منفی باشد");
        }
        if (amount.scale() > 2) {
            throw new OrderError("مبلغ بیش از دو رقم اعشار ندارد");
        }
    }

    public static Money zero(String currencyCode) {
        return new Money(BigDecimal.ZERO, Currency.getInstance(currencyCode));
    }

    public static Money toman(long amount) {
        return new Money(BigDecimal.valueOf(amount), Currency.getInstance("IRR"));
    }

    public Money add(Money other) {
        requireSameCurrency(other);
        return new Money(amount.add(other.amount), currency);
    }

    public Money multiply(int factor) {
        if (factor < 0) {
            throw new OrderError("ضریب نمی‌تواند منفی باشد");
        }
        return new Money(amount.multiply(BigDecimal.valueOf(factor))
                .setScale(2, RoundingMode.HALF_UP), currency);
    }

    public boolean isGreaterThan(Money other) {
        requireSameCurrency(other);
        return amount.compareTo(other.amount) > 0;
    }

    private void requireSameCurrency(Money other) {
        if (!currency.equals(other.currency)) {
            throw new OrderError("عملیات روی دو ارز متفاوت ممکن نیست");
        }
    }

    @Override
    public int compareTo(Money other) {
        requireSameCurrency(other);
        return amount.compareTo(other.amount);
    }

    @Override
    public String toString() {
        return amount + " " + currency.getCurrencyCode();
    }
}

final class OrderEntityMapper {

    private OrderEntityMapper() {}

    // ── دامنه → دیتابیس ──
    static OrderJpaEntity toJpa(Order order) {
        var entity = new OrderJpaEntityWriter().create();
        entity.apply(order.id().value(), order.customerId(),
                order.status().name(), order.total().amount(),
                order.total().currency().getCurrencyCode());

        for (OrderLine line : order.lines()) {
            entity.addLine(line.productId(), line.quantity(),
                    line.unitPrice().amount());
        }
        return entity.build();
    }

    // ── دیتابیس → دomain ──
    static Order toDomain(OrderJpaEntity e) {
        Order order = Order.restore(
                new OrderId(e.id()), e.customerId(),
                OrderStatus.valueOf(e.status()));

        for (OrderLineJpaEntity l : e.lines()) {
            order.restoreLine(new OrderLine(l.productId(), l.quantity(),
                    new Money(l.unitPrice(), Currency.getInstance(e.currency()))));
        }
        return order;
    }
}

package com.shop.infrastructure.persistence;

import com.shop.domain.order.*;
import org.springframework.stereotype.Repository;
import org.springframework.transaction.annotation.Transactional;

import java.util.List;
import java.util.Optional;

@Repository
@Transactional
class JpaOrderRepository implements OrderRepository {

    private final OrderJpaDao dao;

    JpaOrderRepository(OrderJpaDao dao) {
        this.dao = dao;
    }

    @Override
    @Transactional(readOnly = true)
    public Optional<Order> findById(OrderId id) {
        return dao.findById(id.value())
                  .map(OrderEntityMapper::toDomain);
    }

    @Override
    @Transactional(readOnly = true)
    public List<Order> findByCustomerId(String customerId) {
        return dao.findByCustomerId(customerId).stream()
                  .map(OrderEntityMapper::toDomain)
                  .toList();
    }

    @Override
    public void save(Order order) {
        if (dao.existsById(order.id().value())) {
            dao.deleteByOrderId(order.id().value());
        }
        dao.save(OrderEntityMapper.toJpa(order));
    }

    @Override
    @Transactional(readOnly = true)
    public boolean existsById(OrderId id) {
        return dao.existsById(id.value());
    }
}

package com.shop.application;

import com.shop.application.command.PlaceOrderCommand;
import com.shop.domain.DomainEvent;
import com.shop.domain.order.*;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

import java.util.List;

@Service
public class OrderApplicationService {

    private final OrderRepository orders;
    private final EventPublisher events;

    public OrderApplicationService(OrderRepository orders, EventPublisher events) {
        this.orders = orders;
        this.events = events;
    }

    @Transactional                        // ← تنها مرز تراکنش
    public OrderId placeOrder(PlaceOrderCommand cmd) {
        Order order = Order.draft(cmd.customerId());

        cmd.lines().forEach(l ->
                order.addLine(l.productId(), l.quantity(), l.unitPrice()));

        order.place();

        orders.save(order);
        events.publishAll(order.pullEvents());   // ← در همان تراکنش (Outbox)
        return order.id();
    }

    @Transactional(readOnly = true)
    public List<OrderView> listByCustomer(String customerId) {
        return orders.findByCustomerId(customerId).stream()
                     .map(OrderView::from)
                     .toList();
    }
}

@FunctionalInterface
public interface Specification<T> {
    boolean isSatisfiedBy(T candidate);
    String message();

    default Specification<T> and(Specification<T> other) {
        return candidate -> {
            if (!isSatisfiedBy(candidate)) return false;
            if (!other.isSatisfiedBy(candidate)) return false;
            return true;
        };
    }

    default Specification<T> or(Specification<T> other) {
        return candidate -> isSatisfiedBy(candidate) || other.isSatisfiedBy(candidate);
    }
}

public final class OrderSpecifications {

    public static Specification<Order> hasAtLeastOneLine() {
        return o -> !o.lines().isEmpty();
    }

    public static Specification<Order> totalBelow(Money limit) {
        return o -> !o.total().isGreaterThan(limit);
    }

    public static Specification<Order> isPlaceable() {
        return hasAtLeastOneLine().and(totalBelow(Money.toman(100_000_000)));
    }
}

final class InMemoryOrderRepository implements OrderRepository {

    private final Map<String, Order> storage = new ConcurrentHashMap<>();
    private int saveCount = 0;

    @Override
    public Optional<Order> findById(OrderId id) {
        return Optional.ofNullable(storage.get(id.value()));
    }

    @Override
    public void save(Order order) {
        saveCount++;
        storage.put(order.id().value(), order);
    }

    @Override
    public boolean existsById(OrderId id) {
        return storage.containsKey(id.value());
    }

    @Override
    public List<Order> findByCustomerId(String customerId) {
        return storage.values().stream()
                .filter(o -> o.customerId().equals(customerId))
                .toList();
    }

    int saveCount() {
        return saveCount;
    }
}

۱. سامانه‌ی بیمه‌ی ایرانیان

بیمه یکی از نمونه‌های کلاسیک DDD است. دلیلش پیچیدگی است combinatorی قوانین است: پوشش پایه + پوشش تکمیلی، با تخفیف نردبانی که به نسبت بیمه‌ی پرداختی و سال‌های بدون ادعا و نوع خودرو و شهر وارد می‌شود.

// مدل دامنه: تخفیف به‌صورت اشیا، نه if-else
public interface DiscountPolicy {
    Money apply(Order order, CustomerId customerId);
}

public final class SeasonalCampaignPolicy implements DiscountPolicy {
    private final String campaignCode;
    private final Percentage rate;
    private final LocalDate from;
    private final LocalDate to;

    @Override
    public Money apply(Order order, CustomerId customerId) {
        if (LocalDate.now().isBefore(from) || LocalDate.now().isAfter(to)) {
            return order.total();              // ← کمپین تمام شده
        }
        return order.total().minus(order.total().multiply(rate.toFraction()));
    }
}

public final class DiscountEngine {
    private final List<DiscountPolicy> policies;

    public Money calculate(Order order, CustomerId customerId) {
        Money result = order.total();
        for (DiscountPolicy policy : policies) {
            result = policy.apply(order, customerId);
        }
        return result;
    }
}

قاعده‌ی ۱۰۰۰ برابر اگر DDD یک لایه به مسیر اضافه کند (مثلاً ۵ میکروثانیه) و کل سرویس ۱۰ میلی‌ثانیه طول بکشد، هزینه‌ی لایه‌بندی ۰٫۰۵٪ است. هر چیزی که بیشتر از ۱٪ وقت را بگیرد، مشکل از لایه‌بندی نیست.

ریشه‌ی واقعی کندی در DDD

  • Aggregate بیش از حد بزرگ — بارگذاری ۱۰۰۰ سفارش با ۵۰٬۰۰۰ ردیف برای یک تغییر وضعیت
  • N+1 Query — حلقه‌ای که برای هر خط سفارش یک query می‌زند
  • مرز اشتباه Aggregate — تغییر یک رکورد، بارگذاری یک Aggregate غول‌پیکر
  • Domain Event ناهمگام زیاد — صدها رویداد در هر تراکنش
  • Value Object حجیم — ساخت Money در یک حلقه‌ی یک‌میلیونی

بهینه‌سازی‌های عملی

۱. بارگذاری تنبل با مرز مشخص

// ❌ N+1: برای هر سفارش یک query جدا
for (Order order : orders) {
    System.out.println(order.lines().size());   // ← lazy load در هر تکرار
}

// ✅ در یک query
@Query("select distinct o from OrderJpaEntity o left join fetch o.lines")
List<OrderJpaEntity> findAllWithLines(Pageable pageable);

۲. جداسازی مدل خواندن از مدل نوشتن

نوشتن:  Aggregate کامل → Order → outbox_events
خواندن:  یک Query ساده مستقیم → OrderView (بدون ساخت Aggregate)

چرا؟ چون برای نمایش لیست سفارش‌ها نیازی به کل Aggregate نیست.
ساختن Aggregate برای فقط خواندن، هزینه و پیچیدگی بی‌دلیل است.

۳. اجرای قوانین سنگین بیرون از مسیر بحرانی

تحقیق در دیتابیس ۵ هزار خطی:    → داخل تراکنش، سریع
ساخت ObjectGraph ۱۰ هزار تایی:  → خارج از تراکنش، با cache
محاسبه‌ی نرخ بیمه:               → memoize در PremiumSchedule
اعتبارسنجی پیچیده‌ی آدرس:        → index اختصاصی یا بیرون از تراکنش

۴. اندازه‌گیری واقعی

@Test
@DisplayName("افزودن ۱۰۰۰ خط سفارش نباید بیش از X طول بکشد")
void addingThousandLinesIsFast() {
    Order order = Order.draft("c1");
    long start = System.nanoTime();

    for (int i = 0; i < 1_000; i++) {
        order.addLine("product-" + i, 1, Money.toman(10_000));
    }

    long elapsedMs = (System.nanoTime() - start) / 1_000_000;
    assertThat(elapsedMs).isLessThan(50);   // ← معیار قابل اندازه‌گیری
}
جمع‌بندی بخش Performance قبل از هر بهینه‌سازی، اول اندازه بگیرید. در ۹۰٪ مواردی که تیم‌ها فکر می‌کنند DDD کند است، مشکل واقعی یکی از این سه مورد است: Aggregate بزرگ، N+1 یا بازسازی بیش از حد مدل. هر سه، مشکل مدل‌سازی‌اند نه مشکل معماری.

بخش ۲۳۲۰ سؤال مصاحبه

سطح Junior (۱ تا ۱۰)

سؤال ۱ — DDD چیست و چه تفاوتی با لایه‌بندی دارد؟ DDD یعنی طراحی نرم‌افزار بر اساس مدل دامنه، جایی که مفاهیم و قواعد کسب‌وکار داخل کد مدل شده‌اند. لایه‌بندی فقط کد را به لایه‌های فنی تقسیم می‌کند (Controller، Service، DAO) و هیچ تضمینی نمی‌دهد منطق کسب‌وکار کجا باشد. در DDD منطق در مدل دامنه است و لایه‌بندی فقط ابزار انتقال آن است.
سؤال ۲ — Entity و Value Object را تفاوت بدهید Entity هویت دارد (مثل Order با id) و برابری‌اش بر اساس شناسه است؛ ویژگی‌هایش تغییر می‌کنند. Value Object هویت ندارد (مثل Money یا Email)، تغییرناپذیر است و برابری‌اش بر اساس مقدار است. VO اعتبارسنجی را در سازنده اعمال می‌کند و معمولاً درون همان جدول ذخیره می‌شود.
سؤال ۳ — Aggregate چیست و چه چیزی را تعیین می‌کند؟ Aggregate یک گروه از اشیاء است که با هم یک واحد تراکنش می‌سازند. مهم‌ترین چیزی که تعیین می‌کند مرز تراکنش است: یک تراکنش فقط یک Aggregate را تغییر می‌دهد. سایر Aggregate‌ها فقط با شناسه ارجاع می‌شوند، نه با شیء.
سؤال ۴ — Ubiquitous Language چیست؟ یک واژگان مشترک بین برنامه‌نویسان و متخصصان کسب‌وکار که در هر دو طرف دقیقاً یک معنا دارد. نامی که کارشناس می‌گوید باید همان نام در کد باشد. اگر زبان‌ها جدا شوند، ترجمه‌ی اشتباه نام‌ها شروع می‌شود و مدل دامنه به‌تدریج نامعتبر می‌شود.
سؤال ۵ — Aggregate Root چه ویژگی‌هایی دارد؟ تنها عضوی از Aggregate که بیرون از Aggregate قابل دسترسی و ویرایش است. بقیه‌ی اعضا فقط از داخل Root در دسترس‌اند. این قانون تضمین می‌کند که هیچ‌کس نتواند مستقیم یک عضو را تغییر دهد و موجودیت را در وضعیت ناسازگار بگذارد.
سؤال ۶ — چرا نباید در لایه‌ی دامنه از JPA استفاده کرد؟ چون مدل دامنه به فریم‌ورک وابسته می‌شود. نتیجه‌ها: تست واحد نیازمند دیتابیس یا شبیه‌سازی می‌شود، مهاجرت به ORM دیگر غیرممکن می‌شود، و مدل دامنه عملاً به یک لایه‌ی نازک روی دیتابیس تبدیل می‌شود.
سؤال ۷ — Domain Event چیست و چه تفاوتی با پیام معمولی دارد؟ رویدادی که در دامنه اتفاق افتاده و حالت گذشته را توصیف می‌کند؛ مثل OrderPlaced. تفاوت با پیام سیستمی این است که پیام سیستمی درباره‌ی اطلاع‌رسانی است و وابستگی ایجاد می‌کند، اما Domain Event درباره‌ی تغییر وضعیت است و معمولاً از طریق نام با گذشته مشخص می‌شود.
سؤال ۸ — Domain Service کی لازم است؟ وقتی یک قاعده‌ی کسب‌وکار به بیش از یک Aggregate مربوط است، جای طبیعی‌اش داخل هیچ‌کدام از آن‌ها نیست. در این حالت یک سرویس بدون وضعیت در لایه‌ی دامنه می‌سازیم. مثال: محاسبه‌ی وفاداری که هم به مشتری نیاز دارد هم به تاریخچه‌ی سفارش.
سؤال ۹ — Repository در DDD برای چه ساخته می‌شود؟ برای جمع و نگهداری موجودیت‌های یک Aggregate Root. یک Repository برای هر Aggregate Root، نه برای هر Entity و نه برای هر جدول. اگر برای OrderLine هم Repository بسازید، مرز Aggregate را نابود کرده‌اید.
سؤال ۱۰ — چرا متدهای Domain روی خود کلاس هستند؟ چون مدل داده‌ای (فقط getter/setter) اجازه می‌دهد موجودیت در وضعیت ناسازگار قرار بگیرد؛ مثلاً مجموع خطوط با مجموع مبالغ نخواند. متدهای دامنه (addLine) هر تغییری را از یک نقطه عبور می‌دهند و سازگاری را تضمین می‌کنند.

سطح Mid (۱۱ تا ۱۷)

سؤال ۱۱ — Bounded Context چیست و چگونه آن را تعیین می‌کنید؟ مرزی که در آن یک مدل معنی‌دار و یک زبان مشترک وجود دارد. تعیین آن از طریق Event Storming و تحلیل زبان انجام می‌شود: اگر دو بخش از سیستم نیاز به دو مدل متفاوت از یک موجودیت داشته باشند، آن‌ها در دو Bounded Context هستند.
سؤال ۱۲ — چگونه اندازه‌ی درست Aggregate را تعیین می‌کنید؟ سه معیار: (۱) کمینه باشد — کوچک‌ترین چیزی که همیشه با هم تغییر می‌کند؛ (۲) در یک تراکنش قفل شود — تغییر همزمان دو نفر نباید نیاز به قفل متقابل داشته باشد؛ (۳) کلاس‌هایی که همیشه با هم خوانده می‌شوند در یک باشند. اگر Aggregate خیلی بزرگ باشد، contention و کندی می‌آورد؛ اگر خیلی کوچک، مدل ناسازگار می‌شود.
سؤال ۱۳ — چه زمانی یک متد در Repository بد است؟ وقتی نام متد جزئیات فنی را لو بدهد، مثل findByStatusAndCreatedAtBetweenAndCustomerIdIn. این یعنی DAO را فقط rename کرده‌اید. متد خوب از زبان کسب‌وکار می‌آید: findUnshippedFor(customerId).
سؤال ۱۴ — تفاوت Data Mapper و Active Record چیست؟ در Active Record همان کلاس دامنه نقش مدل دیتابیس را هم دارد و save() روی خودش است؛ در نتیجه مدل به ORM گره می‌خورد. در Data Mapper (روش پیشنهادی DDD) کلاس دامنه کاملاً از دیتابیس جداست و یک mapper جدا تبدیل را انجام می‌دهد. هزینه‌اش کد بیشتر و سودش استقلال و تست‌پذیری است.
سؤال ۱۵ — چرا نمی‌توان دو Aggregate را در یک تراکنش تغییر داد؟ از نظر تئوری می‌توانید، اما عملاً باعث مشکلاتی می‌شود: قفل همزمان روی دو سطر در دو جدول مختلف (و در سیستم توزیع‌شده، روی دو نود متفاوت) که به بن‌بست و کاهش تکرارپذیری می‌انجامد. راه‌حل استاندارد، استفاده از رویداد دامنه و Saga است.
سؤال ۱۶ — الگوی Outbox چه مشکلی را حل می‌کند؟ مشکل انتشار رویداد در کنار تراکنش. اگر رویداد را قبل از commit به Kafka بفرستید و تراکنش fail شود، رویدادی برای چیزی که ذخیره نشده منتشر می‌شود. Outbox رویداد را در همان تراکنش در یک جدول می‌نویسد و یک پروسه‌ی جدا آن را به صف منتشر می‌کند؛ پس انتشار گران‌بار شدن حداقل یک‌بار را تضمین می‌کند.
سؤال ۱۷ — چرا DDD برای همه‌ی پروژه‌ها مناسب نیست؟ چون هزینه‌ی مدل‌سازی واقعی است: زمان، نیاز به دانش دامنه، پیچیدگی کد و مقاومت تیم. برای یک CRUD ساده یا یک MVP دو هفته‌ای، این هزینه بازگشت ندارد. DDD را جایی به کار ببرید که پیچیدگی کسب‌وکار واقعاً بالاست.

سطح Senior (۱۸ تا ۲۰)

سؤال ۱۸ — چگونه تشخیص می‌دهید یک Aggregate بیش از حد بزرگ است؟ سه نشانه: (۱) هر بارگذاری Aggregate داده‌ی زیادی می‌آورد که استفاده نمی‌شود؛ (۲) دو کاربر برای تغییر دو چیز متفاوت در همان Aggregate نیاز به قفل دارند؛ (۳) کلاس‌های Aggregate بیش از ۲۰۰ خط دارند. در این حالت Aggregate را به چند Aggregate تقسیم کنید و از طریق شناسه ارتباط دهید.
سؤال ۱۹ — چگونه DDD را در یک تیم بزرگتر از ۱۰ نفر جایگزین می‌کنید؟ با شروع از یک Bounded Context محدود که بیشترین درد را دارد: یک دامنه‌ی پیچیده با منطق پراکنده. ابتدا زبان مشترک را با Event Storming درباره‌ی همان دامنه توافق کنید، سپس مدل را داخل همان دامنه بسازید، و به‌تدریج به دامنه‌های دیگر گسترش دهید. مهاجرت تدریجی، هم ریسک کمتری دارد و هم مقاومت تیم را کم می‌کند.
سؤال ۲۰ — چه زمانی DDD و CQRS و Event Sourcing را ترکیب می‌کنید؟ وقتی دو نیاز همزمان دارید: پیچیدگی دامنه بالا (→ DDD) و نیاز به گزارش‌ها و audit trail کامل از تاریخچه‌ی تغییرات (→ Event Sourcing). در این حالت Event Store جای دیتابیس اصلی می‌نشیند و وضعیت فعلی به‌صورت فولد رویدادها محاسبه می‌شود. این ترکیب قدرتمند اما پرهزینه است و فقط وقتی ارزشش را دارد که تاریخچه‌ی تغییرات واقعاً ارزشمند باشد (بیمه، بانک، بازی).

بخش ۲۴پرسش‌های متداول (FAQ)

DDD فقط برای سیستم‌های پیچیده است؟ تقریباً بله. DDD وقتی ارزش دارد که منطق کسب‌وکار پیچیده و پرتله‌باشد. برای یک CRUD ساده یا یک پروژه‌ی دو هفته‌ای، یک لایه‌بندی تمیز چند برابر ارزان‌تر است.
آیا DDD و TDD با هم سازگارند؟ بله، و حتی مکمل‌اند. TDD روی رفتار تمرکز دارد و DDD روی ساختار. ترکیب این‌ها یعنی مدل دامنه‌ای دارید که با تست‌های سریع قفل شده است — که دقیقاً همان چیزی است که DDD به شما وعده می‌دهد.
آیا هر Aggregate باید یک جدول جدا داشته باشد؟ نه. Aggregate یک واحد تراکنش و یک زمان است، نه الزاماً یک جدول. اعضای داخل Aggregate می‌توانند در چند جدول باشند و حتی می‌توانند در یک ستون به‌صورت JSON ذخیره شوند (OrderLineها). معیار درست بودن، مرز تراکنش است نه تعداد جدول‌ها.
تفاوت Aggregate و Bounded Context چیست؟ Bounded Context مرز مدل‌سازی است: کجا یک زبان مشترک وجود دارد. Aggregate مرز تراکنش است: کم‌ترین واحدی که باید یک‌جا تغییر کند. یک Bounded Context معمولاً چند Aggregate دارد.
آیا می‌توان یک Entity در دو Bounded Context داشت؟ بله، و این در واقع طبیعی است. کالا در Context فروش مدل متفاوتی از کالا در Context انبار دارد. این دو نباید یکی شوند؛ باید از طریق یک لایه‌ی ضدخورده (ACL) و ترجمه‌ی مدل بین آن‌ها ارتباط برقرار کنند.
DDD آیا همان ORM نیست؟ نه. ORM مسئله‌ی ذخیره‌سازی را حل می‌کند، DDD مسئله‌ی مدل‌سازی. این‌ها مکمل‌اند. با DDD می‌توانید از هیچ ORMی استفاده کنید و حتی از JPA در لایه‌ی زیرساخت.
آیا DDD برای موبایل مناسب است؟ بخش تاکتیکی بله. مدل دامنه‌ی خالص و قابل تست در پروژه‌ی اندروید بسیار مفید است. بخش راهبردی (Bounded Context) در اپ موبایل معمولاً کم‌کاربرد است، چون معمولاً یک سرور و یک کلاینت داریم.
چرا متدهای Aggregate را static نمی‌سازم؟ چون همیشه دارد روی یک نمونه‌ی موجود کار می‌کند. آنچه static است سازنده‌ی کارخانه‌ای است (Order.draft) یا قاعده‌ای که به هیچ نمونه‌ای نیاز ندارد (LoyaltyPolicy.isLoyal).
اگر یک قانون در چند جا لازم شد، کجا بگذارم؟ اگر به یک Aggregate مربوط است، متد همان Aggregate. اگر به چند Aggregate مربوط است، Domain Service. اگر واقعاً مشترک و بی‌ربط به دامنه است، یک Utility ساده. نکته: قانون نباید در لایه‌ی application یا UI باشد.
آیا DDD باعث کندی تیم نمی‌شود؟ در ابتدا بله، چون کشف مدل زمان می‌برد. بعد از بلوغ مدل، تغییرات سریع‌تر می‌شوند چون محل تغییر مشخص است. اندازه‌گیری کنید: زمان سپری‌شده از پیشنهاد تا استقرار.
Event Sourcing همان DDD است؟ نه. Event Sourcing یک تصمیم درباره‌ی ذخیره‌سازی است: به‌جای نگه‌داشتن وضعیت فعلی، رویدادها را نگه می‌دارید. DDD درباره‌ی مدل‌سازی است. می‌توانید DDD بدون Event Sourcing داشته باشید (حالت رایج‌تر).
Repository را کجا تعریف کنم؟ در لایه‌ی دomain. دامنه مالک قرارداد است؛ زیرساخت آن را پیاده می‌کند. این همان اصل Dependency Inversion است و به شما اجازه می‌دهد مدل را بدون زیرساخت تست کنید.
آیا یک میکروسرویس = یک Bounded Context؟ تقریباً، ولی نه همیشه. یک Bounded Context می‌تواند در یک میکروسرویس باشد. گاهی چند Bounded Context کوچک در یک سرویس زندگی می‌کنند و گاهی یک Bounded Context باید در دو سرویس شکسته شود (به‌ندرت). این تصمیم سازمانی است، نه فنی.
چطور متوجه شوم مدل مدل نیست؟ سه نشانه: مدل نمی‌تواند بدون دیتابیس تست شود؛ تغییر یک قانون نیازمند تغییر چند لایه است؛ و هیچ‌کسی نمی‌تواند توضیح دهد «سفارش» در این سیستم یعنی چه. اگر این سه را دارید، مدل شما فقط یک پوشه‌ی کلاس است.
آیا Anonymous Entity ممکن است؟ بله. اگر موجودیتی هیچ ویژگی‌ای جز هویت ندارد (مثل یک رکورد لاگ)، می‌توانید @Entity نباشید و شناسه را به‌عنوان Value Object نگه دارید. همه‌ی اشیا نباید Entity باشند.
چطور مدل را مهاجرت دهم وقتی اشتباه طراحی شده؟ به‌ندرت از صفر شروع کنید. مدل را با تست‌های رفتاری قفل کنید، سپس به‌تدریج restore را اضافه کنید و کلاس‌ها را به Aggregate منتقل کنید. مهاجرت تدریجی DDD‌شده از مهاجرت بزرگ بسیار کم‌ریسک‌تر است.
مهم‌ترین یک جمله‌ای که باید به خاطر بسپارم چیست؟ «قواعد کسب‌وکار را در جایی بگذارید که کسی که آن کار را انجام می‌دهد بتواند پیدایش کند.» اگر کاربردی که یک سفارش را ثبت می‌کند، قانون اعتبارسنجی سفارش را در Order پیدا کند، مدل درست است.

جمع‌بندی

DDD یک روش برای فکر کردن است، نه یک فریم‌ورک. ارزش آن در سه چیز است: زبان مشترک که سوءتفاهم را حذف می‌کند، مرز Aggregate که تراکنش را قابل فهم می‌کند، و تست‌پذیری که به شما اجازه می‌دهد بازطراحی را با اطمینان انجام دهید.

و مهم‌تر از همه: DDD را به هر پروژه‌ای تحمیل نکنید. اگر مسئله‌ی شما پیچیدگی دامنه است، DDD بهترین پاسخ است. اگر مسئله‌ی شما حجم ترافیک است، به دنبال کش و معماری توزیع‌شده بروید. اگر مسئله‌ی شما CRUD است، یک لایه‌بندی ساده و تمیز کافی است — و این یک تصمیم حرفه‌ای است، نه یک شکست.

پیام پایانی سری ۱۴ مقاله‌ای این مقاله دهمین عضو سری «معماری‌های نرم‌افزاری» است. اکنون الگوهای رابط کاربری (MVC، MVP، MVVM، MVI)، الگوهای معماری (Clean، Onion، Hexagonal، Layered، Repository) و مدل‌سازی دامنه (DDD) را پوشش داده‌اید. در ادامه سری به معماری‌های سطح بالا می‌رسد: Feature-Based، Event-Driven، CQRS و Microservices.
