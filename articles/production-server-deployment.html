بخش ۱مقدمه

استقرار یعنی انتقال کد از محیط توسعه به سرور و اجرای پایدار آن. یک استقرار خوب قابل‌تکرار، قابل‌بازگشت و امن است. در این مقاله مسیر کامل را از ساخت سرور تا اولین Deploy و Rollback مرور می‌کنیم.

در این مقاله آماده‌سازی سرور و کاربر، ساختار پوشه‌ها، سرویس systemd، خط لوله‌ی Deploy و چک‌لیست نهایی.
Prerequisites Web Server vs Application Server و NGINX.

بخش ۲آماده‌سازی سرور

گاماقدام
کاربر سرویسکاربر غیر root با دسترسی محدود (deploy / app)
SSHکلید عمومی، غیرفعال‌کردن رمز و ورود root
فایروالفقط پورت‌های لازم (22/80/443) باز باشد
ساختار پوشه/opt/app/releases و /opt/app/current (Symlink)
Runtimeنسخه‌ی مشخص JVM/Node/Python و قفل‌شده
محیطمتغیرها در فایل env یا Secret Manager، نه در کد
# ساخت کاربر و مسیرها
sudo useradd --system --home /opt/app --shell /usr/sbin/nologin app
sudo mkdir -p /opt/app/releases /opt/app/shared
sudo chown -R app:app /opt/app

# فایروال
sudo ufw default deny incoming
sudo ufw allow 22,80,443/tcp
sudo ufw enable
اصل ۱۲-Factor برنامه باید Stateless باشد، پیکربندی از محیط بخواند و لاگ‌ها را روی stdout/stderr بنویسد؛ این‌گونه استقرار و مقیاس‌پذیری بسیار ساده‌تر می‌شود.

بخش ۳معماری استقرار

بخش ۴سرویس با systemd

; /etc/systemd/system/myapp.service
[Unit]
Description=My App
After=network.target

[Service]
Type=simple
User=app
WorkingDirectory=/opt/app/current
EnvironmentFile=/opt/app/shared/app.env
ExecStart=/opt/app/current/bin/start.sh
Restart=on-failure
RestartSec=5
# Graceful shutdown
KillSignal=SIGTERM
TimeoutStopSec=30

[Install]
WantedBy=multi-user.target
sudo systemctl daemon-reload
sudo systemctl enable --now myapp
sudo systemctl status myapp
journalctl -u myapp -f        # مشاهده‌ی زنده‌ی لاگ‌ها
Expected Behavior سرویس پس از بوت خودکار بالا می‌آید، در صورت خطا مجدداً راه‌اندازی می‌شود و لاگ‌ها در journald جمع می‌شوند.
Graceful Shutdown SIGTERM را با مهلت مشخص مدیریت کنید تا اتصال‌های در جریان قبل از خاموشی تمام شوند؛ این پیش‌نیاز Zero-Downtime Deployment است.

بخش ۵خط لوله Deploy و Rollback

set -euo pipefail
RELEASE="/opt/app/releases/$(date +%Y%m%d%H%M%S)"

# 1) انتشار نسخه‌ی جدید در پوشه‌ای جدید
mkdir -p "$RELEASE"
rsync -a --delete ./dist/ "$RELEASE/"

# 2) Symlink اتمیک به نسخه‌ی جدید
ln -sfn "$RELEASE" /opt/app/current.tmp
mv -Tf /opt/app/current.tmp /opt/app/current

# 3) Reload بدون قطعی
sudo systemctl reload myapp

# 4) بررسی سلامت
curl -fsS http://127.0.0.1:8080/health || {
  echo "health failed -> rollback"
  ln -sfn "$PREV_RELEASE" /opt/app/current
  sudo systemctl reload myapp
  exit 1
}

# 5) پاک‌سازی نسخه‌های قدیمی (نگه‌داشتن ۵ نسخه)
ls -1dt /opt/app/releases/* | tail -n +6 | xargs -r rm -rf
Expected Behavior هر Deploy در پوشه‌ی مستقل انجام می‌شود و سوییچ با Symlink اتمیک است؛ اگر Health Check شکست بخورد، خودکار به نسخه‌ی قبلی برمی‌گردد.
Migration دیتابیس مهاجرت‌های دیتابیس باید Backward Compatible باشند: ابتدا Schema را اضافه کنید، سپس کد جدید را Deploy کنید و در نهایت نسخه‌ی قدیمی را حذف کنید.
