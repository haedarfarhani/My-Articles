بخش ۱مقدمه: چرا Array کافی نیست؟

یک سیستم فروشگاهی را تصور کنید که باید Users، Products، Orders و Categories را مدیریت کند. اگر فقط از Array استفاده کنیم، با چند محدودیت بنیادی روبرو می‌شویم: اندازه ثابت است، حذف یک عنصر میانی نیاز به جابه‌جایی دارد، و جستجوی سریع بر اساس یک کلید کاری دشوار است. 

User[] users = new User[100];
// اگر بیش از ۱۰۰ کاربر شود چه می‌شود؟
// حذف کاربر دوم و جابه‌جا کردن بقیه؟

جاوا برای حل این مشکل یک چارچوب استاندارد از ساختار داده فراهم کرده است: Java Collections Framework (JCF). این چارچوب مجموعه‌ای از interfaceها، پیاده‌سازی‌ها، الگوریتم‌ها و متدهای کمکی برای مدیریت گروهی از objectها است. این مقاله روی انتخاب درست تمرکز دارد، نه حفظ کردن API.

درباره نسخه‌ی جاوا مثال‌ها و بحث پیاده‌سازی داخلی این مقاله بر پایه‌ی Java 21+ است، مگر اینکه خلاف آن ذکر شود. هرجا جزئیات داخلی به نسخه وابسته باشد، صریحاً اعلام می‌کنیم.

بخش ۲Collection چیست؟

Collection در جاوا به یک ساختار داده اشاره می‌کند که می‌تواند مجموعه‌ای از objectها را ذخیره، اضافه، حذف، جستجو، پیمایش و مرتب کند. 

import java.util.ArrayList;
import java.util.List;

List<String> names = new ArrayList<>();

names.add("Ali");
names.add("Sara");
names.add("Reza");

System.out.println(names);
// [Ali, Sara, Reza]

تحلیل خط به خط:

  • List<String> names: یک متغیر از نوع interface؛ فقط عملیات List قابل فراخوانی است.
  • new ArrayList<>(): پیاده‌سازی واقعی که در زمان اجرا استفاده می‌شود.
  • names.add(...): اضافه‌کردن عنصر به انتهای لیست، ترتیب حفظ می‌شود.
  • System.out.println(names): toString لیست را چاپ می‌کند.

Interface مشخص می‌کند «چه عملیاتی وجود دارد» و Implementation مشخص می‌کند «این عملیات چگونه انجام می‌شود». همین جداسازی باعث می‌شود بتوانید بدون تغییر کد مصرف‌کننده، پیاده‌سازی را عوض کنید.

نکته‌ی انگلیسی قسمت Algorithms همان متدهای کمکی در کلاس java.util.Collections است (sort، shuffle، binarySearch و...).

بخش ۴Collection و Collections

این دو اغلب اشتباه گرفته می‌شوند:

  • Collection یک interface است: Collection<String> names;
  • Collections یک utility class است: Collections.sort(names); · Collections.reverse(names); · Collections.max(names);
List<String> names = new ArrayList<>(List.of("Reza", "Ali", "Sara"));
Collections.sort(names);              // [Ali, Reza, Sara]
Collections.reverse(names);           // [Sara, Reza, Ali]
String max = Collections.max(names);  // Sara

بخش ۷List

List مجموعه‌ای است که مرتب (ordered)، شاخص‌دار (index-based) و قابل تکرار است.

List<String> names = new ArrayList<>();

names.add("Ali");
names.add("Sara");
names.add("Ali");

System.out.println(names);
// [Ali, Sara, Ali]  ← تکراری مجاز است
System.out.println(names.get(0)); // Ali

بخش ۸ArrayList

ArrayList یک Dynamic Array است: یک آرایه‌ی داخلی که با پر شدن، بزرگ‌تر می‌شود. مفهوم Capacity (ظرفیت) با Size (تعداد عناصر فعلی) متفاوت است؛ ظرفیت معمولاً بزرگ‌تر از اندازه است. 

import java.util.ArrayList;
import java.util.List;

List<Integer> numbers = new ArrayList<>();

numbers.add(10);
numbers.add(20);
numbers.add(30);

System.out.println(numbers.get(1)); // 20
System.out.println(numbers.size()); // 3

هنگام resize، ArrayList آرایه‌ی بزرگتری می‌سازد و عناصر را کپی می‌کند؛ این کپی گران است اما به‌ندرت رخ می‌دهد.

بخش ۱۱Set

Set فقط عناصر یکتا (Unique) را نگه می‌دارد.

import java.util.HashSet;
import java.util.Set;

Set<String> usernames = new HashSet<>();

usernames.add("ali");
usernames.add("sara");
usernames.add("ali");   // نادیده گرفته می‌شود

System.out.println(usernames); // [sara, ali]  ← دو عنصر، ترتیب قابل پیش‌بینی نیست

مقدار تکراری ذخیره نمی‌شود چون Set قبل از درج، بر اساس equals (و hashCode در HashSet) بررسی می‌کند که آیا عنصر معادلی وجود دارد یا نه.

بخش ۱۲HashSet

HashSet روی یک Hash Table ساخته شده است و یگانگی را با hashCode و سپس equals تعیین می‌کند. ترتیب iteration در آن تضمین‌شده نیست. 

import java.util.HashSet;
import java.util.Set;

Set<Integer> numbers = new HashSet<>();

numbers.add(10);
numbers.add(20);
numbers.add(10);

System.out.println(numbers.size());        // 2
System.out.println(numbers.contains(20));  // true
مزایامعایب
میانگین O(1) برای add/remove/containsبدون ترتیب iteration
مناسب تشخیص یگانگی سریعکیفیت وابسته به hashCode است

بخش ۱۳equals و hashCode

قرارداد (Contract) بین equals و hashCode حفظ آن‌ها را الزامی می‌کند:

اگر a.equals(b) == true
آنگاه a.hashCode() == b.hashCode()

import java.util.Objects;

public final class User {
    private final Long id;
    private final String name;

    public User(Long id, String name) {
        this.id = id;
        this.name = name;
    }

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof User user)) return false;
        return Objects.equals(id, user.id) && Objects.equals(name, user.name);
    }

    @Override
    public int hashCode() {
        return Objects.hash(id, name);
    }
}
اگر قرارداد نقض شود اگر دو شیء برابر داشته باشید اما hashCode متفاوت بدهند، HashSet و HashMap آن‌ها را در bucketهای متفاوت می‌بینند؛ نتیجه: عنصر تکراری در Set یا دو کلید ظاهراً یکسان در Map. 
import static org.junit.jupiter.api.Assertions.*;
import java.util.HashSet;
import java.util.Set;
import org.junit.jupiter.api.Test;

class UserEqualityTest {

    @Test
    void equalUsersMustCollapseInSet() {
        Set<User> users = new HashSet<>();
        users.add(new User(1L, "Ali"));
        users.add(new User(1L, "Ali"));

        assertEquals(1, users.size());
    }
}

بخش ۱۴LinkedHashSet

LinkedHashSet همان رفتار Set یکتا را دارد، اما ترتیب درج (Insertion Order) را حفظ می‌کند.

import java.util.LinkedHashSet;
import java.util.Set;

Set<String> names = new LinkedHashSet<>();

names.add("A");
names.add("B");
names.add("C");
names.add("A"); // تکراری

System.out.println(names); // [A, B, C]  ← ترتیب درج حفظ می‌شود

هزینه‌ی نگه‌داشتن ترتیب، حافظه‌ی کمی بیشتر برای زنجیره‌ی link بین entryهاست؛ اما میانگین زمان عملیات هنوز O(1) است.

بخش ۱۵TreeSet

TreeSet داده‌ها را مرتب (Sorted) نگه می‌دارد؛ پیاده‌سازی استاندارد آن بر پایه‌ی یک درخت متعادل (در OpenJDK معمولاً Red-Black Tree) است.

import java.util.Set;
import java.util.TreeSet;

Set<Integer> numbers = new TreeSet<>();

numbers.add(30);
numbers.add(10);
numbers.add(20);

System.out.println(numbers); // [10, 20, 30]  ← مرتب صعودی
System.out.println(numbers.iterator().next()); // کوچک‌ترین: 10
OperationComplexity
addO(log n)
removeO(log n)
containsO(log n)

TreeSet برای داده‌های Comparable مرتب آسان است؛ برای نوع سفارشی می‌توانید یک Comparator پاس دهید.

Set<Task> byPriority = new TreeSet<>(Comparator.comparingInt(Task::priority));

بخش ۱۸Deque

Deque یعنی Double Ended Queue: می‌توان از هر دو سر اضافه یا حذف کرد.

import java.util.ArrayDeque;
import java.util.Deque;

Deque<Integer> deque = new ArrayDeque<>();

deque.addFirst(10);
deque.addLast(20);

System.out.println(deque.removeFirst()); // 10

می‌توان از Deque به عنوان Queue (FIFO) و Stack (LIFO) استفاده کرد:

Deque<Integer> stack = new ArrayDeque<>();

stack.push(10);
stack.push(20);

System.out.println(stack.pop()); // 20
System.out.println(stack.peek());// 10
چرا ArrayDeque بهتر از Stack قدیمی است؟ کلاس Stack قدیمی است، از vector ارث‌بری می‌کند (به‌همراه overhead همگام‌سازی) و API آن با Deque ناهمخوان است. در جاوا مدرن، ArrayDeque پیاده‌سازی پیشنهادی استاندارد برای Stack است.

بخش ۱۹PriorityQueue

PriorityQueue برخلاف Queue معمولی بر اساس Priority عمل می‌کند، نه بر اساس ترتیب ورود. پیاده‌سازی استاندارد آن یک Heap است.

import java.util.PriorityQueue;
import java.util.Queue;

Queue<Integer> queue = new PriorityQueue<>();

queue.offer(30);
queue.offer(10);
queue.offer(20);

System.out.println(queue.poll()); // 10  (کوچک‌ترین، چون natural ordering صعودی است)
System.out.println(queue.peek()); // 20

در natural ordering، کوچک‌ترین مقدار priority بالاتری دارد. برای معکوس کردن، Comparator بدهید.

PriorityQueue<Task> tasks =
        new PriorityQueue<>(Comparator.comparingInt(Task::priority));
OperationComplexity
offer (insert)O(log n)
poll (remove min/max)O(log n)
peekO(1)

نکته: iterating روی PriorityQueue ترتیب مرتب نمی‌دهد؛ فقط poll یکی‌یکی ترتیب درست را می‌دهد.

بخش ۲۰Map

Map ساختار Key → Value است و کلیدها یکتا هستند.

import java.util.HashMap;
import java.util.Map;

Map<Long, String> users = new HashMap<>();

users.put(1L, "Ali");
users.put(2L, "Sara");

System.out.println(users.get(1L));         // Ali
System.out.println(users.containsKey(2L)); // true

users.computeIfAbsent(3L, id -> "Guest");

بخش ۲۱HashMap

HashMap یک Hash Table است. مراحل کار (بر اساس پیاده‌سازی OpenJDK در Java 21): 

HashMap
   ↓
hash(key)        ← spread: h = hashCode ^ (h >>> 16)
   ↓
index = (n - 1) & hash
   ↓
Bucket
   ↓
Node (key, value, hash, next)
  • Hash Function: ابتدا hashCode() کلید گرفته می‌شود، بیت‌های بالا به پایین spread می‌شوند تا توزیع بهتر شود.
  • Bucket: آرایه‌ی داخلی؛ ایندکس از (n - 1) & hash به دست می‌آید (n توان ۲ است).
  • Collision: چند کلید در یک bucket به صورت linked list ذخیره می‌شوند.
  • equals: هنگام مقایسه در یک bucket، اول hash و سپس equals بررسی می‌شود.
  • Treeification: اگر یک bucket بیش از حد بزرگ شود (آستانه‌ی ۸ در OpenJDK) و ظرفیت جدول به ۶۴ رسیده باشد، آن bucket به یک درخت (red-black) تبدیل می‌شود تا جستجو O(log n) بماند.
  • Load Factor: به‌طور پیش‌فرض ۰.۷۵؛ وقتی نسبت پرشدگی از آن بگذرد، جدول دو برابر می‌شود.
  • Resize: بزرگ‌کردن آرایه و توزیع مجدد entryها (rehash) — عملیاتی گران اما به‌ندرت رخ‌دهنده.
«table[i]» یک زنجیره است. درج کلیدی با hash یکسان در همان chain قرار می‌گیرد؛
در lookup، ابتدا bucket پیدا می‌شود، سپس با equals و hashCode مطابقت بررسی می‌شود.
Average در برابر Worst case Average → O(1) وقتی تابع hash خوب توزیع کند. اما Worst case بسته به پیاده‌سازی و کیفیت hash می‌تواند O(n) شود (همه‌ی کلیدها در یک bucket). پس O(1) یک تضمین مطلق نیست.

بخش ۲۳LinkedHashMap و LRU Cache

LinkedHashMap علاوه بر Map semantics، ترتیب iteration را مدیریت می‌کند.

import java.util.LinkedHashMap;
import java.util.Map;

Map<Integer, String> map = new LinkedHashMap<>();

map.put(1, "A");
map.put(2, "B");
map.put(3, "C");

System.out.println(map); // {1=A, 2=B, 3=C}  ← ترتیب درج

LinkedHashMap یک حالت دوم دارد: Access Order. اگر سازنده‌ی سوم را با true بسازید، هر دسترسی (get/put) عنصر را به انتها منتقل می‌کند؛ همین پایه‌ی یک LRU Cache ساده است: 

import java.util.LinkedHashMap;
import java.util.Map;

public final class LruCache<K, V> extends LinkedHashMap<K, V> {

    private static final float LOAD_FACTOR = 0.75f;
    private final int capacity;

    public LruCache(int capacity) {
        super(capacity, LOAD_FACTOR, true); // accessOrder = true
        this.capacity = capacity;
    }

    @Override
    protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > capacity;
    }
}

import static org.junit.jupiter.api.Assertions.*;
import org.junit.jupiter.api.Test;

class LruCacheTest {

    @Test
    void shouldEvictLeastRecentlyUsed() {
        LruCache<Integer, String> cache = new LruCache<>(2);
        cache.put(1, "A");
        cache.put(2, "B");
        cache.get(1);      // 1 تازه‌ترین می‌شود
        cache.put(3, "C"); // 2 باید حذف شود

        assertFalse(cache.containsKey(2));
        assertTrue(cache.containsKey(1));
        assertTrue(cache.containsKey(3));
    }
}
همگام‌سازی خودِ LRU مبتنی بر LinkedHashMap در محیط چندرشته‌ای ایمن نیست؛ برای concurrency باید محافظت یا پیاده‌سازی دیگری در نظر بگیرید.

HashMap برای دسترسی همزمان عمومی مناسب نیست؛ با چند ریسمان می‌تواند دیتای ناسازگار یا حلقه‌ی بی‌پایان بدهد (در نسخه‌های قدیمی) یا ساختار داخلی map را خراب کند.

import java.util.concurrent.ConcurrentHashMap;

ConcurrentHashMap به جای قفل روی کل map، از تکنیک‌هایی مثل قفل‌های دانه‌بندی‌شده و عملیات اتمیک (CAS) استفاده می‌کند و اجازه‌ی خواندن همزمان بدون بلاک‌شدن را می‌دهد.

Thread-Safe به معنای Atomic در همه‌ی ترکیب‌ها نیست مثلاً «بررسی وجود کلید، اگر نبود درج کن» با دو فراخوانی جدا، به‌طور خودکار atomic نیست. برای عملیات‌های ترکیبی از putIfAbsent، compute، merge استفاده کنید.

بخش ۳۳ConcurrentModificationException

// بد
for (String name : names) {
    if (name.equals("Ali")) {
        names.remove(name); // ممکن است ConcurrentModificationException بدهد
    }
}

این استثنا از مکانیزم fail-fast می‌آید: Collection یک شمارنده‌ی تغییر (modCount) دارد؛ Iterator اگر ببیند این شمارنده تغییر کرده، استثنا می‌دهد. راهکارهای درست: 

// راهکار ۱: Iterator
Iterator<String> iterator = names.iterator();
while (iterator.hasNext()) {
    if (iterator.next().equals("Ali")) {
        iterator.remove();
    }
}

// راهکار ۲ (خوانا و مدرن): removeIf
names.removeIf(name -> name.equals("Ali"));
نکته: fail-fast در برابر fail-safe iteratorهای ConcurrentHashMap ضعیفاً سازگارند و معمولاً استثنا نمی‌دهند؛ این که کدام رفتار را می‌خواهید، یک تصمیم طراحی است.

بخش ۴۰Memory و Performance

انتخاب Collection فقط Time Complexity نیست. این عوامل هم مهمند:

  • Memory Usage: هر reference شیء و هر node حافظه می‌برد.
  • Cache Locality: داده‌ی پیوسته (مثل ArrayList) از دید CPU سریع‌تر خوانده می‌شود.
  • Object Allocation: LinkedList برای هر عنصر node جدا می‌سازد.
  • Boxing: تبدیل int→Integer هزینه‌ی حافظه/CPU دارد.
  • Resizing: بزرگ‌شدن ArrayList/HashMap گران است اما به‌ندرت.
  • Hashing: کیفیت hashCode مستقیماً توزیع و سرعت را تعیین می‌کند.
  • Tree Traversal: TreeSet/TreeMap همیشه O(log n) دارند.
  • Pointer/Reference Overhead: ساختارهای پیوندی overhead reference دارند.

به همین دلیل، ArrayList در عمل — با وجود Complexity مشابه در بعضی عملیات — ممکن است به‌دلیل locality بهتر سریع‌تر باشد. برچسب Time Complexity، تصویر کامل را نمی‌دهد.

  1. همیشه استفاده از ArrayList بدون توجه به نیاز.
  2. استفاده‌ی بی‌دلیل از LinkedList به‌خاطر باور غلط «درج/حذف همیشه O(1)».
  3. تصور اینکه HashMap همیشه O(1) تضمینی است.
  4. تصور اینکه HashSet ترتیب را حفظ می‌کند.
  5. استفاده از TreeMap بدون نیاز به sorting.
  6. استفاده از Vector در پروژه‌ی جدید.
  7. استفاده از Hashtable در پروژه‌ی جدید.
  8. استفاده از Stack به جای ArrayDeque.
  9. Override نکردن equals/hashCode.
  10. تغییر Collection هنگام iteration.
  11. استفاده از synchronized collection بدون درک Thread Safety.
  12. استفاده از ساختار پیچیده برای مسئله‌ی ساده.
  13. نادیده‌گرفتن Memory overhead.
  14. نادیده‌گرفتن null behavior.
  15. اشتباه گرفتن Collection با Collections.

import static org.junit.jupiter.api.Assertions.*;
import java.util.*;
import java.util.concurrent.ConcurrentHashMap;
import org.junit.jupiter.api.Test;

class CollectionsBehaviorTest {

    @Test
    void shouldNotAllowDuplicateValues() {
        Set<String> names = new HashSet<>();
        names.add("Ali");
        names.add("Ali");
        assertEquals(1, names.size());
    }

    @Test
    void arrayListShouldKeepInsertionOrder() {
        List<String> names = new ArrayList<>(List.of("B", "A", "C"));
        assertEquals(List.of("B", "A", "C"), names);
    }

    @Test
    void hashMapShouldReturnStoredValue() {
        Map<Long, String> users = new HashMap<>();
        users.put(1L, "Ali");
        assertEquals("Ali", users.get(1L));
    }

    @Test
    void treeSetShouldIterateSorted() {
        NavigableSet<Integer> numbers = new TreeSet<>(Set.of(30, 10, 20));
        assertEquals(List.of(10, 20, 30), new ArrayList<>(numbers));
    }

    @Test
    void priorityQueueShouldPollSmallestFirst() {
        Queue<Integer> queue = new PriorityQueue<>(List.of(30, 10, 20));
        assertEquals(10, queue.poll());
    }

    @Test

}

بخش ۴۷پروژه عملی: Task Management System

نیازمندی‌ها: مدیریت Users، Tasks، Priority، Tags و Status. برای هر انتخاب Collection دلیلی داریم:

List         → tasks          (ترتیب و دسترسی شاخصی)
Set          → tags           (یگانگی)
Map          → users by id    (lookup سریع)
PriorityQueue→ priority tasks (شرکت با اولویت)
Deque        → task history   (push/pop اخیر)
ConcurrentHashMap → counters   (شمارنده‌های همزمان)

import java.util.*;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.atomic.AtomicInteger;

public record Task(String id, String title, int priority, Set<String> tags) {}

public final class TaskManager {
    private final List<Task> tasks = new ArrayList<>();
    private final Set<String> tags = new LinkedHashSet<>();
    private final Map<String, String> usersById = new HashMap<>();
    private final PriorityQueue<Task> priorityQueue =
            new PriorityQueue<>(Comparator.comparingInt(Task::priority));
    private final Deque<String> history = new ArrayDeque<>();
    private final ConcurrentHashMap<String, AtomicInteger> counters = new ConcurrentHashMap<>();

    public void registerUser(String id, String name) {
        usersById.put(id, name);
    }

    public void addTask(Task task) {
        tasks.add(task);
        tags.addAll(task.tags());
        priorityQueue.offer(task);
        history.push(task.id());
        counters.computeIfAbsent("created", key -> new AtomicInteger()).incrementAndGet();
    }

    public Task nextPriorityTask() {
        return priorityQueue.poll();
    }

    public Optional<String> lastTouchedTask() {
        return Optional.ofNullable(history.peek());
    }

    public List<Task> tasks() { return List.copyOf(tasks); }
    public Set<String> tags() { return Set.copyOf(tags); }
}

import static org.junit.jupiter.api.Assertions.*;
import java.util.Set;
import org.junit.jupiter.api.Test;

class TaskManagerTest {

    @Test
    void shouldReturnHighestPriorityTaskFirst() {
        TaskManager manager = new TaskManager();
        manager.addTask(new Task("t1", "low", 30, Set.of("backend")));
        manager.addTask(new Task("t2", "high", 10, Set.of("critical")));

        assertEquals("t2", manager.nextPriorityTask().id());
    }

    @Test
    void shouldCollectUniqueTags() {
        TaskManager manager = new TaskManager();
        manager.addTask(new Task("t1", "a", 1, Set.of("ui", "api")));
        manager.addTask(new Task("t2", "b", 2, Set.of("api")));

        assertEquals(Set.of("ui", "api"), manager.tags());
    }
}

هر انتخاب دلیل دارد: ArrayList برای ترتیب، LinkedHashSet برای یگانگی با ترتیب، HashMap برای lookup، PriorityQueue برای اولویت، Deque برای تاریخچه و ConcurrentHashMap برای شمارنده‌های همزمان.

بخش ۴۹۳۰ سؤال مصاحبه

مقدماتی

  1. Collection چیست؟ ساختاری برای نگهداری و مدیریت گروهی از objectها.
  2. List چیست؟ مجموعه‌ی مرتب و شاخص‌دار با عناصر قابل تکرار.
  3. Set چیست؟ مجموعه‌ی بدون عنصر تکراری.
  4. Map چیست؟ ساختار key→value با کلیدهای یکتا.
  5. ArrayList چیست؟ پیاده‌سازی List روی آرایه‌ی پویا.
  6. تفاوت Collection و Collections؟ اولی interface، دومی utility class.
  7. آیا Map زیرمجموعه Collection است؟ نه.
  8. Stack و Queue چه تفاوتی دارند؟ LIFO در برابر FIFO.
  9. Deque چیست؟ صف دوطرفه با امکان درج/حذف از هر دو سر.
  10. چرا از List.of استفاده کنیم؟ immutable و ایمن در برابر تغییر ناخواسته.

متوسط

  1. ArrayList در برابر LinkedList؟ دسترسی شاخصی در ArrayList بهتر؛ ولی در عمل ArrayList اغلب برنده است.
  2. HashMap چگونه کار می‌کند؟ با hashCode، bucket و مقایسه‌ی equals در زنجیره.
  3. HashSet یگانگی را چگونه تشخیص می‌دهد؟ با hashCode و سپس equals.
  4. TreeMap در برابر HashMap؟ TreeMap مرتب است اما O(log n)، HashMap میانگین O(1).
  5. Comparable و Comparator؟ یکی ترتیب طبیعی داخل کلاس، دیگری قواعد خارجی.
  6. LinkedHashMap چه مزیتی دارد؟ حفظ ترتیب درج یا accessOrder.
  7. PriorityQueue چگونه مرتب می‌کند؟ با heap؛ فقط poll ترتیب درست می‌دهد.
  8. چرا ArrayDeque به Stack ترجیح دارد؟ API مدرن و بدون overhead همگام‌سازی.
  9. مفهوم Capacity و Size؟ ظرفیت داخلی در برابر تعداد عناصر فعلی.
  10. Amortized یعنی چه؟ میانگین روی دنباله‌ی عملیات، نه تضمین تک‌عملیات.

پیشرفته

  1. Collision چیست؟ دو کلید با یک bucket/index برای hash؛ با زنجیره یا درخت حل می‌شود.
  2. Load Factor چیست؟ نسبت پرشدگی که آستانه‌ی resize را تعیین می‌کند (پیش‌فرض ۰.۷۵).
  3. Treeification؟ تبدیل bucket بزرگ به درخت برای حفظ کارایی در بدترین حالت.
  4. ConcurrentHashMap چگونه Thread Safety می‌دهد؟ با تکنیک‌های دانه‌بندی‌شده و عملیات اتمیک، نه یک قفل جهانی.
  5. چرا HashMap Thread Safe نیست؟ چون عملیات‌های آن اتمیک نیستند و حالت مشترک بدون همگام‌سازی تغییر می‌کند.
  6. چرا ArrayList معمولاً از LinkedList بهتر است؟ locality بهتر، overhead کمتر و پیاده‌سازی ساده‌تر.
  7. LinkedHashMap چگونه LRU می‌سازد؟ با accessOrder و removeEldestEntry.
  8. fail-fast چیست؟ تشخیص تغییر غیرقانونی در حین iteration با ConcurrentModificationException.
  9. ConcurrentModificationException کجا رخ می‌دهد؟ هنگام تغییر ساختار Collection در حین پیمایش.
  10. تفاوت synchronizedList و ConcurrentHashMap؟ اولی قفل بزرگ و iteration دستی؛ دومی دانه‌بندی‌شده و iterator ضعیفاً سازگار.

بخش ۵۰پرسش‌های متداول (FAQ)

  1. آیا ArrayList همیشه بهترین List است؟ برای اکثر سناریوها بله، اما نه برای صف/استک (ArrayDeque بهتر است).
  2. چرا LinkedList کمتر از تصور استفاده می‌شود؟ چون هزینه‌ی پنهان جستجو اغلب O(n) است و locality ضعیف دارد.
  3. آیا HashMap ترتیب را حفظ می‌کند؟ نه؛ برای ترتیب از LinkedHashMap یا TreeMap استفاده کنید.
  4. آیا HashSet ترتیب را حفظ می‌کند؟ نه؛ LinkedHashSet یا TreeSet را در نظر بگیرید.
  5. HashMap سریع‌تر است یا TreeMap؟ HashMap میانگین O(1)، TreeMap همیشه O(log n) اما مرتب.
  6. چه زمانی TreeSet استفاده کنیم؟ وقتی به داده‌ی مرتب و عملیات بازه‌ای نیاز داریم.
  7. آیا Vector هنوز استفاده می‌شود؟ تنها در کدهای قدیمی؛ در پروژه‌ی جدید استفاده نکنید.
  8. آیا Stack منسوخ است؟ خود کلاس legacy است؛ ArrayDeque جایگزین پیشنهادی است.
  9. آیا ConcurrentHashMap همیشه بهتر از HashMap است؟ نه؛ اگر دسترسی همزمان ندارید، overhead بی‌دلیل است.
  10. Collection بهتر است یا Array؟ آرایه برای اندازه ثابت و performance حساس؛ Collection برای انعطاف و API غنی.
  11. چه زمانی LinkedHashMap استفاده کنیم؟ برای ترتیب درج/دسترسی و LRU.
  12. آیا List.of قابل تغییر است؟ نه؛ تغییر آن UnsupportedOperationException می‌دهد.
  13. تفاوت unmodifiableList و List.of؟ اولی نما روی منبع متغیر، دومی immutable واقعی.
  14. چرا باید equals/hashCode را با هم پیاده کنم؟ چون HashSet/HashMap بر اساس هر دو کار می‌کنند.
  15. چطور از ConcurrentModificationException بپرهزم؟ با Iterator.remove، removeIf یا ساخت یک copy.
