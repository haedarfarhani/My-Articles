معماری کامل Production؛ از اینترنت تا Database

این مقاله‌ی پایانی، همه‌ی لایه‌هایی که در این آکادمی دیدیم را در یک معماری کامل کنار هم می‌چیند: Internet → DNS → Firewall → NGINX (TLS و Load Balancing) → چند Backend → Redis و PostgreSQL. برای هر لایه توضیح می‌دهیم چه می‌کند، چرا آنجاست، چه چیزی می‌تواند خراب شود و کدام تصمیم Production را باید بگیریم.

بخش ۱معماری کامل در یک نگاه

اصل حاکم بر کل معماری هر لایه فقط با لایه‌ی مجاور خود حرف می‌زند، هر لایه یک مسئولیت دارد، و هر جزء حساس در شبکه‌ی خصوصی است. اگر این سه قاعده رعایت شود، سیستم قابل نگهداری و مقیاس‌پذیر می‌ماند.

بخش ۲لایه‌ی ورودی: DNS و Firewall

رکورد DNSکاربردمثال
Aنام به IPv4app.example.com → 203.0.113.10
AAAAنام به IPv6app.example.com → 2001:db8::1
CNAMEنام به نام (Alias)www → app.example.com
TXTمتادیتا و تأیید مالکیتSPF، DKIM، تأیید SSL
# فقط پورت‌های لازم را باز کنید (نمونه با ufw)
sudo ufw default deny incoming
sudo ufw allow 22/tcp     # SSH
sudo ufw allow 80/tcp     # HTTP (ریدایرکت به HTTPS)
sudo ufw allow 443/tcp    # HTTPS
sudo ufw enable
sudo ufw status verbose
Production Note پورت‌های Backend (8080/8081)، Redis (6379) و PostgreSQL (5432) هرگز نباید عمومی باشند. دسترسی دیتابیس را به شبکه‌ی خصوصی یا VPN محدود کنید.

بخش ۳لایه‌ی لبه: NGINX

upstream app {
    least_conn;
    keepalive 32;
    server 10.0.0.11:8080 max_fails=3 fail_timeout=15s;
    server 10.0.0.12:8080 max_fails=3 fail_timeout=15s;
    server 10.0.0.13:8080 backup;
}

server {
    listen 443 ssl http2;
    server_name app.example.com;

    ssl_certificate     /etc/letsencrypt/live/app.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/app.example.com/privkey.pem;
    ssl_protocols       TLSv1.2 TLSv1.3;

    add_header X-Content-Type-Options "nosniff" always;
    add_header X-Frame-Options "SAMEORIGIN" always;
    add_header Referrer-Policy "strict-origin-when-cross-origin" always;

    location = /health { access_log off; return 200 "ok"; }

    location /static/ { root /var/www/app; expires 30d; }

    location / {
        proxy_pass http://app;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
High Availability در لبه یک NGINX تنها نقطه‌ی شکست تک است. برای HA واقعی، یا دو NGINX پشت یک Floating IP/Keepalived بگذارید، یا از یک Load Balancer ابری در جلوی آن‌ها استفاده کنید.

بخش ۴لایه‌ی اپلیکیشن: Backendها

تصمیمتوصیه‌ی Productionدلیل
Bind Address0.0.0.0:8080 در شبکه‌ی خصوصیفقط NGINX و شبکه‌ی داخلی دسترسی دارند
Statelessوضعیت در Redis یا Tokenامکان Scaling افقی
Configفقط از Environment Variableتصویر و کد قابل انتقال می‌ماند

GET /health   → زنده بودن فرآیند (Liveness)
GET /ready    → آماده‌بودن برای دریافت ترافیک (Readiness)
GET /metrics  → معیارهای Prometheus

بخش ۵لایه‌ی داده: Redis و PostgreSQL

جزءنقشخطای رایج
RedisCache، Session، Rate Limit، Queueاستفاده به‌عنوان منبع اصلی داده
PostgreSQLمنبع اصلی داده و تراکنشعدم تنظیم Connection Pool و Index
Replicaخواندن و Failoverفرض تکرارسازی فوری (Replication Lag)
Backupبازیابی در حادثهپشتیبانی بدون تست بازیابی
هرگز این کار را نکنید باز کردن پورت ۵۴۳۲ یا ۶۳۷۹ روی اینترنت. Redis بدون احراز هویت و PostgreSQL با رمز ضعیف، از رایج‌ترین علل نفوذ و از دست‌رفتن داده هستند.

بخش ۶مرزهای شبکه و پورت‌ها

پورتسرویسدر دسترس از
22SSHفقط IPهای مدیر یا Bastion (ترجیحاً)
80HTTPعمومی — فقط برای ریدایرکت به HTTPS
443HTTPSعمومی
8080 / 8081 / 8082Backendفقط لبه و شبکه‌ی داخلی
3000 / 5000Node.js / ASP.NET در حال توسعهدر Production پشت Proxy
6379Redisفقط شبکه‌ی خصوصی
5432PostgreSQLفقط شبکه‌ی خصوصی
آدرسمعنا
127.0.0.1فقط همان میزبان (Loopback) — امن‌ترین حالت
0.0.0.0همه‌ی رابط‌ها — فقط وقتی لازم است
Private IPفقط شبکه‌ی خصوصی VPC
Public IPقابل دسترس از اینترنت
قاعده‌ی Bind اگر فقط NGINX روی همان سرور به Backend وصل می‌شود، Backend را روی 127.0.0.1 ببندید. اما اگر Backendها روی سرورهای جدا هستند، 0.0.0.0 روی رابط خصوصی لازم است — با Firewall محدود.

بخش ۷Config و Secret

درست:  Config از Environment Variable

  DATABASE_URL=postgres://user:***@db.internal:5432/app
  REDIS_URL=redis://cache.internal:6379
  JWT_SECRET=***

اشتباه:  مقدار داخل کد یا تصویر Docker

  # هرگز:
  SPRING_DATASOURCE_PASSWORD=hardcoded-in-repo
نوعمثالمحل نگه‌داری
پیکربندی غیرحساسپورت، نام سرویس، سطح لاگفایل Config یا Env
Secretرمز دیتابیس، کلید JWTSecret Manager یا Env رمزگذاری‌شده
Certificateکلید خصوصی TLSمدیریت‌شده با مجوز محدود
Common Mistake کامیت‌کردن فایل .env. حتی پس از حذف، تاریخچه‌ی Git آن را نگه می‌دارد؛ در صورت لو رفتن، کلید را باطل و جایگزین کنید.

کجا کند شد؟Tracesمسیر یک درخواست در چند سرویس
تفکیک Liveness و Readiness Liveness می‌گوید فرآیند زنده است (اگر نه، Restart کن). Readiness می‌گوید آماده‌ی ترافیک است (اگر نه، از Load Balancer حذف کن). این تفکیک، پایه‌ی Zero-Downtime Deployment است.

بخش ۱۰Zero-Downtime Deployment

Rolling Deployment

  v1  v1  v1
  v2  v1  v1   ← یک نمونه از گردش خارج، به‌روزرسانی، بازگشت
  v2  v2  v1
  v2  v2  v2

الزامات:
  ۱) Health Check و Readiness
  ۲) Graceful Shutdown (Connection Draining)
  ۳) سازگاری نسخه‌ها در دیتابیس (Expand/Contract)
  ۴) امکان Rollback
روشمزیتملاحظه
Rollingبدون منابع اضافهدو نسخه هم‌زمان فعال‌اند
Blue-GreenRollback فوریدو برابر منابع
Canaryریسک کنترل‌شدهنیازمند مسیریابی درصدی
خطاهای رایج انتشار ۵۰۲ به‌دلیل نبود Healthy Instance، ۵۰۳ به‌دلیل اشباع Backend، و Connection Reset به‌دلیل Shutdown ناگهانی. هر سه با Health Check، Graceful Shutdown و ظرفیت کافی قابل پیشگیری‌اند.

معماری Production خوب، ساده‌ترین معماری‌ای است که مسئولیت‌ها را جدا می‌کند، هر جزء حساس را ایزوله می‌کند و در برابر خرابی تاب‌آور است. هیچ‌کدام از این لایه‌ها آداب نیستند؛ هرکدام یک محدودیت واقعی را حل می‌کنند.

بازگشت به ابتدای آکادمی نقشه‌ی راه معماری سرور — اگر این مقاله را خواندید، حالا می‌توانید از ابتدا مسیر را با درک کامل مرور کنید.
