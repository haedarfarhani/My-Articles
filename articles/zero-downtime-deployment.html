Zero-Downtime Deployment؛ استقرار بدون حتی یک درخواست از‌دست‌رفته

Downtime هیچ‌وقت «کوچک» نیست: هر ثانیه، درخواست‌های شکست‌خورده، خطای 5xx و اعتماد سوخته است. در این مقاله تکنیک‌های عملی Zero-Downtime Deployment را می‌بینیم: از Graceful Shutdown و Connection Draining تا تعویض Symlink اتمیک و Migration سازگار با Expand/Contract.

بخش ۱مقدمه و مدل ذهنی

Zero-Downtime یعنی در طول Deploy، هیچ درخواستی با خطای اتصال یا 5xx مواجه نشود. سه پیش‌نیاز مفهومی دارد:

پیش‌نیازسؤال کلیدی
افزونگی (Redundancy)حین تعویض یک Instance، چه کسی ترافیک را می‌گیرد؟
خروج تمیز (Graceful Shutdown)Instance قبلی درخواست‌های در جریان را چه می‌کند؟
سازگاری نسخه‌هانسخه‌ی v1 و v2 در همان لحظه با چه داده‌ای کار می‌کنند؟
در این مقاله هر سه ضلع را در سطح سیستم عامل، Load Balancer و دیتابیس پیاده‌سازی می‌کنیم و در پایان یک چک‌لیست قابل استفاده در هر Deploy داریم.
Prerequisites Reverse Proxy، Load Balancing و Blue-Green Deployment.

بخش ۲Graceful Shutdown با SIGTERM

وقتی systemd یا Kubernetes تصمیم می‌گیرد فرآیند را ببیند، ابتدا سیگنال SIGTERM می‌فرستد. اگر برنامه آن را نادیده بگیرد، بعد از مهلت (مثلاً ۳۰ ثانیه) SIGKILL می‌رسد و هر آنچه در جریان بود — پاسخ‌های نصفه، تراکنش‌های باز — قطع می‌شود. کار درست: شنیدن SIGTERM، بستن Listener، اتمام درخواست‌های در جریان و بستن منابع. 

// Node.js — Graceful Shutdown
const server = http.createServer(app);
server.listen(3000);

let shuttingDown = false;

process.on('SIGTERM', () => {
  if (shuttingDown) return;
  shuttingDown = true;
  console.log('SIGTERM received: closing server');

  // 1) هیچ درخواست جدیدی نپذیر
  server.close(() => {
    console.log('all connections drained, exiting');
    process.exit(0);
  });

  // 2) اگر بعد از timeout همه‌چیز تمام نشد، اجباری خارج شو
  setTimeout(() => {
    console.error('forced exit after timeout');
    process.exit(1);
  }, 25_000).unref();

  // 3) اتصال‌های دیتابیس/کش را ببند (بعد از drain)
});

// خطاها نباید فرآیند را بدون مدیریت بکشند
process.on('unhandledRejection', (err) => {
  console.error('unhandled rejection', err);
});
Kill Switch تایم‌اوت مهلت Graceful Shutdown باید کمتر از مهلت terminationGracePeriodSeconds در Kubernetes و کمتر از مهلت شبکه‌ی Load Balancer باشد، وگرنه SIGKILL وسط کار می‌رسد.
Keep-Alive و idle درخواست‌های جدید به‌سرعت قطع می‌شوند، اما کانکشن‌های Keep-Alive idle ممکن است باز بمانند. راه‌حل: بعد از server.close، کانکشن‌های idle را با server.closeIdleConnections() (Node 18+) ببندید و منتظر بقیه بمانید.

بخش ۳Connection Draining در Load Balancer

محیطمکانیزم Drain
HAProxyserver ... weight 0 یا اکشن set server state maint؛ کانکشن‌های فعال ادامه می‌یابند
NGINX Plusdrain پارامتر روی server؛ اتصال‌های جدید نمی‌گیرد، فعالی‌ها تمام می‌شوند
NGINX OSSحذف از upstream + proxy_pass reload؛ به worker_shutdown_timeout دقت کنید
Kubernetes (Service)preStop sleep + Endpoint removal propagation؛ ترتیب: endpoint حذف، سپس SIGTERM
AWS ALBConnection Draining (Deregistration Delay، پیش‌فرض ۳۰۰ ثانیه)
# systemd: تعریف مهلت تمیز برای واحد برنامه
[Service]
ExecStart=/usr/bin/node /srv/app/server.js
KillSignal=SIGTERM
TimeoutStopSec=30          # بعد از این، SIGKILL
KillMode=mixed

# Kubernetes: ترتیب درست حین حذف Pod
lifecycle:
  preStop:
    exec:
      command: ["sleep", "10"]   # فرصت برای حذف endpoint و تخلیه ترافیک
terminationGracePeriodSeconds: 40

بخش ۴Symlink و Switch اتمیک

در Deploy سرور سنتی (بدون Kubernetes)، راه سبک برای Zero-Downtime این است که نسخه‌ی جدید را کنار نسخه‌ی قبلی آماده کنیم و در یک لحظه فقط «نشانه‌گر» را عوض کنیم. در سیستم فایل، این نشانه‌گر یک Symlink است و چون ln -sfn عملیات اتمیک دارد، کلاینت‌ها یا یا نسخه‌ی جدید می‌بینند یا قدیمی — هرگز حالت نیمه‌کار. 

# ساختار استاندارد Capistrano-style
/srv/app
├── releases/
│   ├── 202610050930   # نسخه‌ی قبلی (در حال اجرا)
│   └── 202610051500   # نسخه‌ی جدید (آماده‌شده، تست‌شده)
├── shared/            # .env، storage، logs مشترک بین releases
└── current -> releases/202610050930   # Symlink فعال

# Deploy بدون توقف
rsync -a build/ /srv/app/releases/202610051500/
ln -sfn /srv/app/releases/202610051500 /srv/app/current

# Reload سریع (نه restart): workerهای قدیمی درخواست‌های در جریان را تمام می‌کنند
sudo systemctl reload myapp       # اگر unit از ExecReload استفاده می‌کند
sudo nginx -s reload              # صفر کردن کانکشن‌های قطع‌شده نیست؛ graceful است
Expected Behavior در لحظه‌ی Switch، دو نسخه چند ثانیه هم‌زمان در جریان‌اند: workerهای قدیمی درخواست‌های شروع‌شده را تمام می‌کنند و درخواست‌های جدید به نسخه‌ی جدید می‌روند. برای کاربر این انتقال نامرئی است.
دام Cache اگر opcache (PHP)، Class-Path (JVM) یا Process Manager شما مسیر واقعی فایل را کش کرده باشد، ممکن است بعد از تغییر Symlink هنوز کد قدیمی اجرا شود. راه‌حل: opcache_reset یا Reload فرآیند پس از Switch.

بخش ۵Migration با Expand/Contract

سخت‌ترین ضلع Zero-Downtime، دیتابیس است: حین Deploy دو نسخه از کد هم‌زمان زنده‌اند و هر دو باید با Schema کار کنند. قانون طلایی: هیچ مهاجرتی را نابرگشت‌پذیر و ناسازگار اجرا نکنید — تغییرات را به دو فاز تقسیم کنید.

فازچه می‌کنیم؟نتیجه
Expandستون/جدول/اندیس جدید اضافه می‌شود؛ چیز قبلی دست نمی‌خوردنسخه‌ی قدیمی و جدید هر دو کار می‌کنند
Migrate Dataداده به ساختار جدید به‌صورت Batch/Backfill کپی می‌شوددو مسیر موازی فعال
Contractپس از اینکه همه‌ی نسخه‌ها روی کد جدید رفتند، ساختار قدیمی حذف می‌شودالگو تمام؛ Schema تمیز
عملیاتسازگار با دو نسخه؟روش امن
افزودن ستون nullable✅مستقیم
حذف ستون❌ بلافاصلهاول بایستان در کد، بعد در فاز Contract حذف
تغییر نوع ستون❌ستون جدید + Backfill + Dual-Write + Switch
افزودن اندیس✅ با احتیاطCREATE INDEX CONCURRENTLY / ALGORITHM=INPLACE
Rename ستون❌ستون جدید + Dual-Write + خواندن با fallback + حذف قدیمی
-- فاز Expand: ستون جدید را اضافه کن، قدیمی را نگه دار
ALTER TABLE orders ADD COLUMN total_cents BIGINT NULL;

-- Backfill تدریجی (بدون قفل طولانی)
UPDATE orders SET total_cents = ROUND(total * 100)
WHERE total_cents IS NULL AND id BETWEEN 0 AND 10000;

-- کد v1 روی total کار می‌کند؛ کد v2 روی total_cents می‌نویسد (Dual-Write)

-- فاز Contract (بعد از Deploy کامل و فاصله‌ی امن)
ALTER TABLE orders DROP COLUMN total;
Lock و Latency Migration روی جدول بزرگ می‌تواند Lock بگیرد و همه‌ی درخواست‌ها را بلاتر کند. برای Postgres lock_timeout کوتاه بگذارید و عملیات سنگین را Batch کنید؛ برای MySQL از ALGORITHM=INPLACE, LOCK=NONE یا ابزار gh-ost/pt-online-schema-change.

بخش ۶چک‌لیست و جمع‌بندی

چک‌لیست Zero-Downtime
  • حداقل دو Instance سالم پشت LB در تمام لحظات Deploy.
  • برنامه SIGTERM را می‌شنود و درخواست‌های در جریان را کامل پاسخ می‌دهد.
  • مهلت Shutdown < terminationGracePeriodSeconds < مهلت شبکه LB.
  • Readiness قبل از ورود ترافیک و preStop قبل از قطع LB چک می‌شود.
  • Switch نسخه با Symlink/Service اتمیک است و Reload نه Restart.
  • Migrationها Expand/Contract هستند؛ Lock کوتاه و Backfill تدریجی.
  • پس از Deploy، متریک 5xx و Latency را چند دقیقه تماشا می‌کنید.

Zero-Downtime یک ویژگی نیست؛ مجموعه‌ای از عادت‌های مهندسی است که به‌طور هم‌زمان در کد، زیرساخت و دیتابیس اجرا می‌شوند. برای دیدن تصویر بزرگ، سری آکادمی معماری سرور را دنبال کنید.
