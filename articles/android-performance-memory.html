بخش ۲حافظه در اندروید: چرخه حیات اشیا و سطل‌های GC

در اندروید، حافظه توسط ART (Android Runtime) با یک Garbage Collector نسلی مدیریت می‌شود. درک این مدل به شما می‌گوید چرا برنامه‌ی شما «ناگهان» فریز می‌شود و چرا بعضی اشیا هرگز جمع نمی‌شوند.

۲.۱ هزینه‌ی یک GC چیست؟

  • GC خاموش (Young): معمولاً چند میلی‌ثانیه؛ تقریباً نامرئی است.
  • GC کامل (Full): کل Heap را اسکن می‌کند؛ در لحظه‌ی رندر می‌تواند چند فریم را ببلعد.
  • Heap بزرگ: اشیای زیاد ← زمان اسکن بیشتر ← GCهای کُندتر ← چرخه‌ی معیوب.
  • اشیای بزرگ (بیت‌مپ): مستقیم به Large Object Space می‌روند و نوسان heap را تشدید می‌کنند.
نکته: Allocation گران‌تر از چیزی‌ست که فکر می‌کنید تخصیص مکرر ابجکت در حلقه‌ی رندر (مثل Paint، Rect یا لیست فیلترشده) هم حافظه می‌سوزاند هم فشار GC را بالا می‌برد. در Compose و View، الگوی «بساز-دور بینداز» را با remember یا بازاستفاده از بافرهای آماده بشکنید.

بخش ۳Memory Leak: تعریف، علل و نشانه‌ها

نشت حافظه یعنی شیءای که دیگر از نظر کسب‌وکار مرده، اما از نظر GC زنده است، چون یک مرجع (Reference) فراموش‌شده آن را به زنجیره‌ی Root وصل نگه داشته است.

۳.۱ نشانه‌های عملی نشت

  • مصرف حافظه بعد از باز کردن/بستن یک صفحه هرگز به سطح اولیه برنمی‌گردد (پله‌ای بالا می‌رود).
  • در Memory Profiler، نمونه‌هایی از Activity بعد از تخریب، روی می‌مانند.
  • کرش OutOfMemoryError روی دستگاه‌های ارزان‌قیمت با حافظه‌ی کم.
  • تاخیر ناگهانی GC و فریز کوتاه هنگام اسکن heap بزرگ.
هشدار: نشت در پس‌زمینه خودش را نشان می‌دهد اپ در foreground ممکن است ماه‌ها بی‌مشکل کار کند. نشت وقتی کشنده می‌شود که اپ را در پس‌زمینه رها می‌کنید: سیستم برای آزادسازی حافظه تلاش می‌کند، نمی‌تواند، و در نهایت پروسه را kill می‌کند — کاربر فکر می‌کند اپ «کرش کرده» در حالی که قربانی حافظه‌ی بالای شماست.

بخش ۴LeakCanary: ریشه‌یابی عملی نشت حافظه

LeakCanary کتابخانه‌ی متن‌باز Square است که در نسخه‌ی دیباگ، خودش شیءهای تخریب‌شده را نگه می‌دارد، بعد از تخریب، ارجاع‌ها را بررسی می‌کند و اگر زنده مانده باشند، هلال نشت (Leak Trace) را گزارش می‌دهد — دقیقاً با نام کلاس و خطی که مرجع را نگه داشته است. 

// build.gradle (app) — فقط برای debug؛ در release حذف می‌شود
dependencies {
    debugImplementation "com.squareup.leakcanary:leakcanary-android:2.14"
}

// نیازی به هیچ کد دیگری نیست! LeakCanary خودش:
// ۱) onActivityDestroyed را رجیستر می‌کند
// ۲) بعد از ۵ ثانیه منتظر می‌ماند تا Activity تخریب و GC شود
// ۳) اگر زنده ماند، نوتیفیکیشن نشت با Trace کامل می‌دهد

۴.۱ خواندن یک Leak Trace

┬───
│ GC Root: System class
│
├── com.example.app.analytics.Tracker instance
│    ↓ Tracker.context
│                     ← خط مقصر: مرجع نگه‌داشته‌شده
├── com.example.app.MainActivity instance
│    ↓ Activity.mDestroyed = true   ← یعنی تخریب شده ولی زنده است
╰───

قاعده‌ی خواندن: از پایین به بالا بیایید؛ اولین فیلدی که به یک شیءِ تخریب‌شده اشاره می‌کند، همان مرجع خراب است. در مثال بالا، Tracker یک singleton است و context آن به Activity قدیمی اشاره می‌کند — راه‌حل: استفاده از applicationContext. 

// ✗ نشت: Activity در مقدار اولیه نگه داشته می‌شود
class Tracker(private val context: Context)      // اگر context = Activity باشد

// ✓ درست: هیچ‌وقت به Activity وابسته نشو
class Tracker(@ApplicationContext private val context: Context)

// یا اگر واقعاً به Activity نیاز دارید: WeakReference
class Scroller(activity: Activity) {
    private val ref = WeakReference(activity)
    fun scroll() { ref.get()?.let { /* ... */ } }   // اگر null شد، یعنی Activity رفته
}
عمیق‌تر: LeakCanary چگونه کار می‌کند؟ این کتابخانه از ترکیب ObjectWatcher و WeakReference استفاده می‌کند: بعد از تخریب، شیء در یک WeakReference نگه داشته می‌شود و اگر بعد از یک چرخه‌ی GC هنوز زنده بود، یعنی مرجع قوی دیگری وجود دارد. سپس با heap dump و تحلیل ارجاعات (aha library)، مسیر دقیق نشت را پیدا می‌کند.

بخش ۵نشت‌های کلاسیک: Listener، Context و Coroutine

سه نشت در کد اندروید بیش از بقیه تکرار می‌شوند. هر سه یک ریشه دارند: یک ثبت (register) بدون جفتِ خودش (unregister).

۵.۱ Listenerها و Callbackها

class PlayerActivity : AppCompatActivity() {

    // ✗ MediaPlayer این listener را نگه می‌دارد تا release شود
    override fun onStart() {
        super.onStart()
        mediaPlayer.setOnCompletionListener { finish() }   // ← ارجاع به Activity
        mediaPlayer.start()
    }

    // release فراموش شده + listener پابرجا = نشت کامل

    // ✓ راه‌حل: هم جفت کردن register/unregister، هم release
    override fun onStart() {
        super.onStart()
        mediaPlayer.setOnCompletionListener(listener)
        mediaPlayer.start()
    }
    override fun onStop() {
        mediaPlayer.stop()
        mediaPlayer.release()
        super.onStop()
    }
    private val listener = MediaPlayer.OnCompletionListener { /* بدون ارجاع سنگین */ }
}

۵.۲ نشت از طریق Context

Contextعمرکجا مجاز استخطر نشت
Applicationکل عمر پروسهService، Singleton، DIتقریباً صفر
Activityتا onDestroyUI، Dialog، inflateبالا
Serviceتا stopSelfکار پس‌زمینهمتوسط

۵.۳ Coroutineهای ناامن

class BadMapFragment : Fragment() {

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        // ✗ GlobalScope: تا ابد زنده است و به view این fragment اشاره می‌کند
        GlobalScope.launch(Dispatchers.IO) {
            val data = api.load()              // شاید ۱۰ ثانیه طول بکشد
            binding.title.text = data.title     // ← binding از view تخریب‌شده!
        }
    }
}

class GoodMapFragment : Fragment() {

    override fun onViewCreated(view: View, savedInstanceState: Bundle?) {
        super.onViewCreated(view, savedInstanceState)
        // ✓ lifecycleScope: با تخریب view لغو می‌شود
        viewLifecycleOwner.lifecycleScope.launch {
            val data = withContext(Dispatchers.IO) { api.load() }
            binding.title.text = data.title     // اگر لغو شده باشد، اصلاً اجرا نمی‌شود
        }
    }
}
آفت شماره ۱: تأخیر (delay) در لود شدن اگر کاربر از صفحه‌ای که در حال لود است خارج شود و request شما لغو نشود، وقتی جواب بیاید، کد تلاش می‌کند به view تخریب‌شده دست بزند — یا نشت ایجاد می‌کند یا کرش. همه‌ی جمع‌آوری‌ها را به lifecycle گره بزنید: lifecycleScope، repeatOnLifecycle و collectAsStateWithLifecycle.

بخش ۶Android Studio Profiler: حافظه، CPU و شبکه

LeakCanary نشت را پیدا می‌کند؛ اما برای «کندی» باید از Profiler استفاده کنید. پروفایلر سه منحنی اصلی دارد و هر کدام یک زبان متفاوت حرف می‌زنند.

۶.۱ نقشه‌ی راه استفاده از Profiler

  1. Memory: منحنی را باز کنید؛ لحظه‌ی GC را با دکمه‌ی «Force GC» تشدید کنید و ببینید کف کجا می‌نشیند.
  2. Heap Dump: بعد از تخریب صفحه، دکمه‌ی Dump را بزنید و با فیلتر Activity چک کنید چند نمونه مانده است.
  3. Allocation Tracking: در لحظه‌ی اسکرول، ببینید کدام کلاس بیش از حد تخصیص می‌گیرد (معمولاً Adapter یا Modifier).
  4. CPU: بازه‌ی فریز را پیدا کنید و ببینید کدام method روی Main Thread سنگین است (معمولاً inflate یا JSON parse دستی).
  5. Network: پاسخ‌های تکراری و JSONهای بزرگ را شناسایی و cache کنید.
// مثال: رهاسازی باگِ Allocation در حلقه‌ی رندر
// ✗ در هر onDraw یک Rect می‌سازد — ده‌ها هزار تخصیص در دقیقه
override fun onDraw(canvas: Canvas) {
    val rect = Rect(0, 0, width, height)          // تخصیص جدید در هر فریم
    canvas.drawRect(rect, paint)
}

// ✓ بافر آماده و بازاستفاده
private val rect = Rect()
override fun onDraw(canvas: Canvas) {
    rect.set(0, 0, width, height)
    canvas.drawRect(rect, paint)
}

بخش ۷رندرینگ و Jank: فریم‌های جاافتاده

UI اندروید در سه مرحله اجرا می‌شود: Measure، Layout و Draw — و همه باید در ۱۶.۷ms تمام شوند. رایج‌ترین مرتکبانِ نقض این بودجه در View System و Compose یکسان‌اند: کار سنگین روی Main Thread و بازترسیم زیاد.

هشدار: اندازه بگیرید، حدس نزنید خیلی از «بهینه‌سازی‌ها» اثری ندارند یا حتی کندتر می‌کنند (مثلاً premature optimize در Kotlin). همیشه قبل و بعد را با Macrobenchmark یا JankStats اندازه بگیرید و فقط تغییراتی را نگه دارید که عدد را جابه‌جا کرده‌اند.

بخش ۸Cold Start: ریشه‌یابی و بهینه‌سازی راه‌اندازی

Cold Start زمانی است که پروسه از صفر ساخته می‌شود: کلاس‌ها بارگذاری، Application ساخته، Activity ایجاد و اولین فریم رندر می‌شود. هر کاری که در Application.onCreate بگذارید، مسیر کاربر را سنگین‌تر می‌کند.

۸.۱ تکنیک‌های عملی

// ✗ بارگذاری سنگین در onCreate — همه‌ی SDKها هم‌زمان
class App : Application() {
    override fun onCreate() {
        super.onCreate()
        analytics.init(this)          // ۳۰ms
        crashReporter.init(this)      // ۲۰ms
        remoteConfig.fetchSync()      // ۸۰ms شبکه!
        database.warmUp()             // ۵۰ms
    }
}

// ✓ تأخیر آگاهانه: فقط آنچه واقعاً لازم است
class App : Application() {
    override fun onCreate() {
        super.onCreate()
        AppInitializer.getInstance(this)      // App Startup: ترتیب وابستگی‌ها
        // بقیه فقط وقتی لازم شد
    }
    fun initHeavySdk() {
        // Lazy delegate یا call در اولین استفاده‌ی واقعی
    }
}

// پیش‌گرم‌سازی هوشمند در جایی که واقعاً کاربر است
class MainActivity : AppCompatActivity() {
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        installSplashScreen()                // SplashScreen API
        setContentView(R.layout.activity_main)
        lifecycleScope.launch(Dispatchers.Default) { prewarmCache() }  // خارج از مسیر رندر
    }
}
نکته: اندازه‌گیری Cold Start با Macrobenchmark می‌توانید زمان timeToInitialDisplay و timeToFullDisplay را در هر کامیت بگیرید و در CI آستانه (threshold) بگذارید — به این ترتیب هیچ‌کس بدون دیدن عدد، «بهینه‌سازی» را merge نمی‌کند.

بخش ۹Baseline Profiles و R8: سرعت و حجم در یک بسته

اگر فقط یک بهینه‌سازی با بیشترین اثر انجام دهید، همین است: Baseline Profile به ART می‌گوید کدام مسیرهای کد را از قبل AOT کند، و R8 کد مرده را حذف و نام‌ها را کوچک می‌کند.

۹.۱ Baseline Profile چیست؟

به‌صورت پیش‌فرض، اندروید اپ را در ابتدا تفسیری (Interpretation) اجرا می‌کند و بعد از مدتی AOT می‌کند. Basline Profile یک فایل نصبی است که «مسیرهای گرم» (ورود، اسکرول اول، لاگین) را از قبل کامپایل می‌کند — نتیجه‌ی رایج: ۲۰ تا ۴۰ درصد بهبود در Cold Start و روانی اسکرول اول. 

// build.gradle — ماژول baselineprofile
plugins { id("androidx.baselineprofile") }

dependencies {
    baselineProfile(project(":baselineprofile"))   // ماژول تست مخصوص
}

// اجرای تولید پروفایل (روی دستگاه یا امولاتور)
// ./gradlew :app:generateReleaseBaselineProfile

۹.۲ تنظیمات R8 که واقعاً مهم‌اند

// proguard-rules.pro — نمونه‌های کاربردی
# حذف لاگ‌های ساخته‌شده با buildConfig.DEBUG
-assumenosideeffects class android.util.Log {
    public static int v(...);
    public static int d(...);
}

# مدل‌های داده‌ی مورد استفاده در serialization نباید نام‌شان عوض شود
-keepclassmembers class com.example.data.model.** { *; }

# ورودی/خروجی‌های JNI
-keepclasseswithmembernames class * { native <methods>; }
تکنیکاثر بر سرعتاثر بر حجمهزینه‌ی پیاده‌سازی
Baseline Profile۲۰–۴۰٪ بهبود≈۰کم (یک ماژول تست)
R8 / Resource Shrinkکم۲۰–۴۰٪ کوچک‌ترکم (تنظیم پیش‌فرض + keep rules)
Lazy Initمستقیم در Cold Startصفرمتوسط (نیازمند بازآرایی)
Crash-only نگه‌داشتن کش‌هاکمصفرکم
عمیق‌تر: Baseline Profile در کجا قرار می‌گیرد؟ فایل تولیدشده در assets/baseline.prof بسته‌بندی می‌شود و در هنگام نصب توسط PackageManager به ART داده می‌شود؛ یعنی کاربر اولین باری که اپ را باز می‌کند، همان مسیرهای بهینه را اجرا می‌کند، نه بعد از چند روز استفاده. برای اپ‌های بزرگ، این تنها راه «گرم‌شدن» منصفانه است.

بخش ۱۰جمع‌بندی، چک‌لیست و منابع

پرفورمنس اندروید یک مهارت اندازه‌گیری است، نه حدس. چرخه‌ی درست این است: اندازه بگیر → ریشه را پیدا کن → یک تغییر بده → دوباره اندازه بگیر → فقط آنچه عدد را جابه‌جا کرد نگه دار.

۱۰.۱ چک‌لیست بازبینی کارایی

  1. هیچ I/O، پارس JSON سنگین یا فراخوانی شبکه روی Main Thread وجود ندارد.
  2. همه‌ی register/unregisterها جفت‌اند و release()ها در تخریب صدا زده می‌شوند.
  3. هیچ GlobalScope یا scope بدون مالک در پروژه نیست؛ جمع‌آوری‌ها به lifecycle گره خورده‌اند.
  4. Contextهای وابسته به Activity در singletonها استفاده نمی‌شوند (@ApplicationContext).
  5. Memory Profiler بعد از باز/بسته‌شدن صفحه، کفِ پایدار نشان می‌دهد.
  6. لیست‌ها key دارند و onBindViewHolder عاری از کار سنگین است.
  7. Cold Start با Macrobenchmark اندازه‌گیری شده و برایش آستانه‌ی CI گذاشته شده.
  8. Baseline Profile تولید و در build نهایی بسته‌بندی می‌شود.
  9. R8 فعال است و assumenosideeffects برای لاگ‌ها تنظیم شده.
