بخش ۱مقدمه: کدِ بد از ندانستن سینتکس نمی‌آید

تصور کنید یک توسعه‌دهنده‌ی جاوا هستید که سینتکس زبان را خوب می‌دانید: کلاس، ارث‌بری، interface، generic و stream را می‌شناسید. با این حال، پروژه‌ای که تحویل می‌گیرید پر از کلاس‌هایی است که مستقیم به هم گره خورده‌اند. مشکل اینجا کمبود دانش زبان نیست؛ مشکل، طراحی (Design) است. کدی که کار می‌کند و کدی که برای تغییر ساخته شده، دو چیز متفاوت‌اند.

به این زنجیره توجه کنید. هر کلاس، جزئیات پیاده‌سازی کلاس بعدی را می‌داند: 

OrderService  →  PaymentProcessor  →  StripeClient  →  HttpClient

حالا فرض کنید می‌خواهیم درگاه پرداخت را عوض کنیم. اگر PaymentProcessor مستقیماً نوع StripeClient را سازد و به آن وابسته باشد، تغییر درگاه به معنای دست‌زدن به چند فایل است. اگر OrderService هم مستقیماً به PaymentProcessor وابسته باشد، یک تغییر ساده در لایه‌ی پایین، تا لایه‌ی بالای دامنه نشت می‌کند.

علامت هشدار طراحی هر جمله‌ای در ذهن شما که با «اگر فردا این را عوض کردند، مجبورم...» شروع شود، یک علامت است که در آن نقطه به یک مرز طراحی (design boundary) نیاز دارید — و همین‌جاست که الگوهای طراحی وارد می‌شوند.

Design Pattern (الگوی طراحی) یک راه‌حل عمومی، شناخته‌شده و آزموده‌شده برای یک مسئله‌ی تکرارشونده در طراحی نرم‌افزار است. آن را «سینتکس» در نظر نگیرید؛ یک الگو، واژگان مشترکی است برای حرف‌زدن درباره‌ی ساختار و رابطه‌ی اجزا. در ادامه اول دقیقاً روشن می‌کنیم که یک الگو چیست و چه چیزی نیست.

بخش ۲Design Pattern دقیقاً چیست؟ (و چه چیزی نیست)

تعریف دقیق: الگوی طراحی، توصیفی از یک راه‌حل برای یک مسئله‌ی طراحی تکرارشونده است، به‌همراه شرح اینکه چرا این راه‌حل کار می‌کند و در چه شرایطی به آن نیاز دارید. الگو نامی برای یک ساختار راه‌حل است، نه کدی که کپی کنید.

۲.۱ الگو چه چیزی نیست

چیست؟چرا این‌طور نیست
Library یا Frameworkالگو کد نیست، پس نمی‌توانید آن را «اضافه» یا «نصب» کنید.
Packageهیچ بسته‌ای وجود ندارد که «Strategy» را برای شما بیاورد؛ هر بار خودتان می‌سازید.
کلاس آمادهالگو ساختاری از چند type و رابطه‌ی آن‌هاست، نه یک کلاس مشخص.
Algorithm یا Data Structureالگوریتم «گام‌های محاسبه» را می‌گوید؛ الگو «ساختار و تعامل» را.
کد قابل Copy/Pasteمحیط، زبان و مسئله‌ی شما متفاوت است؛ الگو باید هر بار اقتباس شود.

مثال ملموس: بارها پیش می‌آید که ساخت یک شیء پیچیده شده است (پارامترهای زیاد، فیلدهای اختیاری و ترتیب مبهم). این یک مسئله‌ی تکرارشونده در خانواده‌ی Creation (ساخت) است و الگوی Builder برایش راه‌حل دارد. نکته‌ی مهم این است که الگو برای مسئله‌ی درست به کار می‌رود؛ Builder راه‌حل «ساخت پیچیده» است، نه راه‌حل همه‌ی مسائل.

بخش ۳یک مثال واقعی: سیستم Notification

با یک نمونه‌ی ساده ولی واقعی شروع می‌کنیم. یک سرویس اعلان داریم که نوع ارسال را با String می‌گیرد: 

public class NotificationService {

    public void send(String type, String message) {
        if (type.equals("email")) {
            // send email
        } else if (type.equals("sms")) {
            // send sms
        } else if (type.equals("push")) {
            // send push notification
        }
    }
}

در ابتدا این کد ساده و بی‌آزار است. اما با بزرگ‌شدن محصول، نوع‌ها زیاد می‌شوند: Email، SMS، Push، WhatsApp، Telegram، Slack و... . هر نوع جدید، یک else if تازه به همین متد اضافه می‌کند.

مسئله فقط تعداد ifها نیست اگر مسئله فقط تعداد if بود، با switch یا Map هم می‌شد جمعش کرد. مسئله‌ی واقعی این است که این کلاس هم‌زمان سه کار می‌کند: تشخیص نوع، ساخت متن، و ارسال. این یعنی وابستگی زیاد (Tight Coupling)، نقض مسئولیت واحد، و دشواری تست.

حالا همان مسئله را با یک interface و الگوی Strategy بازطراحی می‌کنیم. این فقط یک تغییر ظاهری نیست؛ ما محور تغییر (axis of change) را جدا می‌کنیم: 

public interface NotificationChannel {
    void send(String message);
}

public final class EmailChannel implements NotificationChannel {
    @Override public void send(String message) {
        // send email
    }
}

public final class SmsChannel implements NotificationChannel {
    @Override public void send(String message) {
        // send sms
    }
}

public final class NotificationService {
    private final NotificationChannel channel;

    public NotificationService(NotificationChannel channel) {
        this.channel = channel;
    }

    public void send(String message) {
        channel.send(message);
    }
}

اکنون نوع جدید یعنی WhatsApp فقط یک کلاس جدید است؛ NotificationService دست‌نخورده می‌ماند. در بخش ۲۸ همین سیستم را قدم‌به‌قدم بازسازی می‌کنیم و Unit Test می‌نویسیم.

بخش ۴Patternها کدام مشکل را حل می‌کنند؟

الگوها برای «زیباتر کردن کد» نیستند؛ برای حل مجموعه‌ای از دردهای مشخص طراحی‌اند. در ادامه هفت نشانه‌ی رایج را با مثال می‌بینیم.

۴.۱ وابستگی شدید (Tight Coupling)

public class OrderService {
    private final MySqlOrderRepository repository = new MySqlOrderRepository();
}

OrderService هم تصمیم ساخت گرفته، هم به یک پیاده‌سازی خاص وابسته است. نتیجه: نمی‌توان بدون دیتابیس واقعی تست کرد و تعویض دیتابیس به یک بازنویسی تبدیل می‌شود.

۴.۲ تکرار کد (Code Duplication)

public void sendEmail(String to, String body) { /* retry + logging + template */ }
public void sendSms(String to, String body)   { /* retry + logging + template */ }

منطق retry و logging دو بار تکرار شده. الگوهایی مثل Template Method یا Decorator این تکرار را جمع می‌کنند.

۴.۳ کدی که به‌سختی تغییر می‌کند (Hard-to-change)

public double calculateTotal(String customerType) {
    if (customerType.equals("regular")) return base;
    if (customerType.equals("vip")) return base * 0.9;
    if (customerType.equals("employee")) return base * 0.7;
    return base;
}

هر نوع مشتری جدید، این متد را تغییر می‌دهد. الگوی Strategy هر قاعده را به یک کلاس جدا می‌برد تا افزودن قاعده، ویرایش نباشد بلکه افزودن باشد.

۴.۴ تست دشوار (Difficult Testing)

public class BookingService {
    private final PaymentGateway gateway = PaymentGateway.live(); // اتصال واقعی
}

هر تست واحد باید به شبکه بزند. اگر وابستگی از بیرون تزریق شود (BookingService(PaymentGateway g))، در تست یک fake ساده کافی است. این همان Dependency Injection است که الگوها را تست‌پذیر می‌کند.

۴.۵ ساخت شیء پیچیده (Complex Object Creation)

new User("ali", "ali@mail.com", "0912...", "Tehran", null, null, 30, true, false, "fa");

این «فاجعه‌ی پارامترهای موقعیتی» است: خواندن ندارد، ترتیب مهم است و مقادیر اختیاری گیج‌کننده‌اند. الگوی Builder این را به زنجیره‌ی خوانا تبدیل می‌کند.

۴.۶ منطق شرطی بزرگ (Large Conditional Logic)

switch (action) {
    case "create" -> create();
    case "update" -> update();
    case "delete" -> delete();
    // ...
}

وقتی هر شاخه منطق جدی دارد، Command یا Strategy هر شاخه را به یک شیء تبدیل می‌کند.

۴.۷ تفکیک ضعیف مسئولیت‌ها (Poor Separation)

وقتی یک کلاس هم اعتبارسنجی می‌کند، هم ذخیره، هم ایمیل می‌فرستد، الگوهایی مثل Facade و Repository مرزها را روشن می‌کنند.

جمع‌بندی بخش هر الگو یکی از این دردها را هدف می‌گیرد، اما هیچ الگویی همه‌ی آن‌ها را هم‌زمان حل نمی‌کند. قبل از انتخاب الگو، مشخص کنید کدام درد واقعاً در پروژه‌ی شما وجود دارد.

بخش ۵چرا از Design Pattern استفاده می‌کنیم؟

الگوها در اصل ارزش خود را از چند ویژگی می‌گیرند که کیفیت بلندمدت پروژه را تعیین می‌کنند:

هدفتأثیر الگومثال
کاهش وابستگی (Low Coupling)وابستگی به interface جای وابستگی به implementationStrategy، Factory
افزایش چسبندگی (High Cohesion)هر کلاس یک مسئولیت روشن داردSRP در همه‌ی الگوها
قابلیت نگهداری (Maintainability)تغییر در یک جای مشخص محدود می‌ماندFacade، Adapter
قابلیت تست (Testability)جایگزینی وابستگی با fake در تستDI + Strategy
استفاده‌ی مجدد (Reusability)رفتار مشترک قابل ترکیب استDecorator، Template Method
انعطاف‌پذیری (Flexibility)افزودن قابلیت بدون تغییر کد موجودObserver، Factory Method
کنترل پیچیدگیمرزهای روشن بین بخش‌های سیستمFacade، Mediator
مهم‌ترین هشدار این مقاله الگو هدف نیست؛ ابزار است. اگر الگو را فقط برای حرفه‌ای‌تر به‌نظررسیدن استفاده کنید، خروجی معمولاً کدی است با تعداد کلاس بیشتر، پیچیدگی بیشتر و خوانایی کمتر — یعنی دقیقاً برعکس هدف.

بخش ۶چه زمانی استفاده از Pattern ضروری است؟

تقریباً هیچ الگویی ذاتاً و همیشه «ضروری» نیست. الگو وقتی ارزشمند می‌شود که یک مسئله‌ی واقعی و تکرارشونده داشته باشید. این زنجیره را در نظر بگیرید: 

Requirement Change
        ↓
Existing Design
        ↓
Modification becomes difficult
        ↓
Repeated problem
        ↓
Suitable Pattern

نکته‌ی کلیدی کلمه‌ی «تکرارشونده» است. یک بار سخت بودن یک تغییر، هنوز الگو توجیه نمی‌کند؛ وقتی الگو‌ی همین درد چند بار در پروژه دیده شد، آن‌وقت الگو هزینه‌ی خود را جبران می‌کند.

نیاز واقعیالگوی پیشنهادی
چند نوع رفتار قابل تعویض در زمان اجراStrategy
چند implementation زیر یک abstractionFactory
ساخت شیء با پارامترهای زیاد و اختیاریBuilder
یک نمونه‌ی کنترل‌شده و مشترک (با احتیاط)Singleton
اطلاع‌رسانی یک رویداد به چند شنوندهObserver
پردازش زنجیره‌ای یک درخواستChain of Responsibility
افزودن رفتار بدون تغییر کلاس اصلیDecorator
قانون سرانگشتی اگر بتوانید با کمی refactor یا جداسازی ساده مشکل را حل کنید، همان را انجام دهید. الگو زمانی وارد می‌شود که مرزهای طراحی واقعاً لازم شده باشند.

بخش ۷چه زمانی نباید Pattern استفاده کرد؟

این بخش از مهم‌ترین بخش‌های مقاله است. اگر مسئله ساده است، الگو اضافه نکنید. به این مثال نگاه کنید: برای برگرداندن یک نام ثابت، یک interface و یک کلاس ساخته شده است. 

interface UserNameProvider {
    String getUserName();
}

class DefaultUserNameProvider implements UserNameProvider {
    @Override
    public String getUserName() {
        return "Heydar";
    }
}

وقتی فقط یک implementation وجود دارد و هیچ نیاز واقعی به abstraction نیست، این لایه فقط پیچیدگی است. در عین حال، این معادل کاملاً کافی است: 

String getUserName() {
    return "Heydar";
}

بخش ۸Design Pattern و SOLID

SOLID پنج اصل طراحی شیءگراست و الگوها معمولاً بویژه برای رسیدن به SOLID وجود دارند. ابتدا هر اصل را کوتاه و با مثال جاوا می‌بینیم، سپس نقشه‌ی ارتباط الگوها با آن‌ها را می‌کشیم.

۸.۱ SRP — اصل مسئولیت واحد

// بد: دو مسئولیت در یک کلاس
class Invoice {
    void calculateTotal() { /* ... */ }
    void printPdf() { /* ... */ }
}

// خوب: هر کلاس یک دلیل برای تغییر
class Invoice { double calculateTotal() { /* ... */ return 0; } }
class InvoicePrinter { void print(Invoice invoice) { /* ... */ } }

۸.۲ OCP — اصل باز/بسته

// بد: برای افزودن نوع جدید باید این کلاس را تغییر دهیم
class ShippingCalculator {
    double cost(String type) {
        return switch (type) {
            case "standard" -> 20_000;
            case "express"  -> 50_000;
            default -> 0;
        };
    }
}

// خوب: بسته برای تغییر، باز برای توسعه
interface ShippingStrategy { double cost(); }
class StandardShipping implements ShippingStrategy { public double cost() { return 20_000; } }
class ExpressShipping  implements ShippingStrategy { public double cost() { return 50_000; } }

۸.۳ LSP — اصل جانشینی لیسکوف

interface Rectangle { int area(); }
class Square implements Rectangle {          // مربع را جدا نگه می‌داریم
    private final int side;
    Square(int side) { this.side = side; }
    public int area() { return side * side; }
}

اگر یک زیرنوع نتواند جای والد خود بنشیند بدون آنکه رفتار را بشکند، وراثت غلط است.

۸.۴ ISP — اصل تفکیک interface

// بد: interface چاق
interface Machine { void print(); void scan(); void fax(); }

// خوب: interfaceهای کوچک و متمرکز
interface Printer { void print(); }
interface Scanner { void scan(); }
class SimplePrinter implements Printer { public void print() { /* ... */ } }

۸.۵ DIP — اصل وارونگی وابستگی

// بد: سیاست به جزئیات وابسته است
class ReportService { private final MySQLDatabase db = new MySQLDatabase(); }

// خوب: هر دو به یک abstraction وابسته‌اند
interface Database { void save(String data); }
class ReportService {
    private final Database database;
    ReportService(Database database) { this.database = database; }
}

بخش ۱۳Singleton (Creation)

تعریف: تضمین می‌کند یک کلاس فقط یک نمونه داشته باشد و یک نقطه‌ی دسترسی جهانی به آن بدهد.

مسئله: یک منبع مشترک (پیکربندی، connection pool، cache) باید تنها یک نمونه داشته باشد.

// نسخه‌ی بد: static global به‌جای کنترل lifecycle
public class AppConfig {
    public static final AppConfig INSTANCE = new AppConfig();
    public String apiUrl = "https://api.example.com";
}
// INSTANCE.apiUrl = "..." ; قابل تغییر از هر جای برنامه — و تست‌ناپذیر

راه‌حل: نمونه را خصوصی و از دسترس خارج نگه دارید و از ساخت تکراری جلوگیری کنید. برای thread-safety از الگوی holder استفاده کنید.

public final class AppConfig {
    private final String apiUrl;

    private AppConfig(String apiUrl) { this.apiUrl = apiUrl; }

    // Initialization-on-demand holder: lazy + thread-safe بدون synchronized
    private static final class Holder {
        private static final AppConfig INSTANCE = new AppConfig("https://api.example.com");
    }

    public static AppConfig instance() { return Holder.INSTANCE; }

    public String apiUrl() { return apiUrl; }
}

بخش ۱۹Decorator (Structural)

تعریف: رفتار جدید را در زمان اجرا و با پوشاندن یک شیء، به آن اضافه می‌کند، بدون تغییر کلاس اصلی.

public interface DataSource {
    void write(String data);
}

public final class FileDataSource implements DataSource {
    private final String path;
    public FileDataSource(String path) { this.path = path; }
    @Override public void write(String data) { /* write to file */ }
}

public abstract class DataSourceDecorator implements DataSource {
    protected final DataSource wrapped;
    protected DataSourceDecorator(DataSource wrapped) { this.wrapped = wrapped; }
    @Override public void write(String data) { wrapped.write(data); }
}

public final class EncryptionDecorator extends DataSourceDecorator {
    public EncryptionDecorator(DataSource wrapped) { super(wrapped); }
    @Override public void write(String data) { wrapped.write(encrypt(data)); }
    private String encrypt(String data) { return "enc(" + data + ")"; }
}

public final class CompressionDecorator extends DataSourceDecorator {
    public CompressionDecorator(DataSource wrapped) { super(wrapped); }
    @Override public void write(String data) { wrapped.write("zip(" + data + ")"); }
}

DataSource source = new CompressionDecorator(
        new EncryptionDecorator(new FileDataSource("out.txt")));
source.write("hello");

بخش ۲۵Command (Behavioral)

تعریف: یک درخواست را به یک شیء تبدیل می‌کند، تا بتوان آن را پارامتریزه، صف‌بندی، لاگ یا واگرد (undo) کرد.

مسئله: یک ویرایشگر متنی می‌خواهیم که عملیات را اجرا و واگرد کند.

public interface Command {
    void execute();
    void undo();
}

public final class TextEditor {
    private final StringBuilder text = new StringBuilder();
    public void insert(String value) { text.append(value); }
    public void deleteLast(int length) { text.delete(text.length() - length, text.length()); }
    public String text() { return text.toString(); }
}

public final class InsertCommand implements Command {
    private final TextEditor editor;
    private final String value;

    public InsertCommand(TextEditor editor, String value) {
        this.editor = editor;
        this.value = value;
    }

    @Override public void execute() { editor.insert(value); }
    @Override public void undo() { editor.deleteLast(value.length()); }
}

public final class CommandHistory {
    private final java.util.Deque<Command> history = new java.util.ArrayDeque<>();

    public void run(Command command) {
        command.execute();
        history.push(command);
    }

    public void undoLast() {
        if (!history.isEmpty()) history.pop().undo();
    }
}

import static org.junit.jupiter.api.Assertions.*;
import org.junit.jupiter.api.Test;

class CommandTest {

    @Test
    void shouldInsertAndUndo() {
        TextEditor editor = new TextEditor();
        CommandHistory history = new CommandHistory();

        history.run(new InsertCommand(editor, "Hello"));
        assertEquals("Hello", editor.text());

        history.undoLast();
        assertEquals("", editor.text());
    }
}

    }
}

الگوهای رایج در اندروید:

  • Repository: پنهان‌کردن منبع داده (شبکه/دیتابیس) از لایه‌ی بالاتر.
  • Observer: جریان‌های داده (LiveData/Flow/Rx) اصول آن را در خود دارند.
  • Strategy: انتخاب منبع داده یا الگوریتم تزریق شده بر اساس شرایط.
  • Factory / Builder / Adapter / Decorator / Facade / Singleton: در کتابخانه‌ها و لایه‌بندی.
تفاوت مهم برخی نام‌هایی که در اندروید می‌بینید (مثل Repository یا ViewModel) لزوماً الگوی GoF نیستند؛ آن‌ها Architectural Pattern یا Framework Convention هستند. تفاوت قائل شوید: الگوی طراحی در سطح کلاس، معماری در سطح سیستم، و قرارداد فریم‌ورک در سطح پیاده‌سازی.

بخش ۳۰اشتباهات رایج در استفاده از Pattern

  1. استفاده از الگو فقط برای حرفه‌ای نشان‌دادن کد.
  2. ساخت abstraction بدون نیاز واقعی (Premature Abstraction).
  3. ایجاد interface برای هر کلاس، حتی وقتی فقط یک implementation وجود دارد.
  4. استفاده‌ی بی‌دلیل از Singleton برای همه‌چیز.
  5. Factoryهای بیش از حد پیچیده با زنجیره‌های تودرتو.
  6. ساخت تعداد زیادی کلاس برای یک مسئله‌ی کوچک.
  7. ترکیب چند الگو بدون نیاز واقعی.
  8. کپی‌کردن الگو بدون درک مسئله‌ای که حل می‌کند.
  9. نادیده‌گرفتن هزینه‌ی پیچیدگی و تعداد مراحل ذهنی برای خواننده.
  10. استفاده از الگو فقط به‌خاطر این‌که در یک کتاب یا مقاله آمده است.
سنجه‌ی نهایی پس از اعمال یک الگو، از خود بپرسید: «آیا تغییر بعدی آسان‌تر شد؟ آیا تست ساده‌تر شد؟ آیا کد برای یک تازه‌وارد خواناتر شد؟» اگر جواب «نه» است، الگو را بردارید.

بخش ۳۲۱۰ تمرین عملی

هر تمرین شامل صورت مسئله، محدودیت، ورودی/خروجی، راهنما و تست پیشنهادی است.

تمرین ۱ — Payment System با Strategy

مسئله: چند روش پرداخت (کارت، نقد، کیف پول). محدودیت: باید بدون تغییر Context قابل افزودن باشد. ورودی: مبلغ و نوع پرداخت. خروجی: نتیجه‌ی پرداخت. راهنما: یک PaymentStrategy با متد pay(Money). تست: هر استراتژی را جدا تست کنید و ترتیب فراخوانی در Context را با یک fake بررسی کنید.

تمرین ۲ — Notification Factory

مسئله: کارخانه‌ی ساخت کانال بر اساس نوع. محدودیت: نوع ناشناخته باید خطای رفتاری مشخص بدهد. راهنما: از switch روی enum استفاده کنید. تست: نوع درست نمونه‌ی درست بسازد.

تمرین ۳ — User Builder

مسئله: ساخت کاربر با فیلدهای اختیاری. محدودیت: نام و ایمیل اجباری و غیرnull. خروجی: یک record immutable. تست: ساخت با حداقل فیلدها و رد null.

تمرین ۴ — Logging با Observer

مسئله: چند مقصد برای لاگ (فایل، کنسول، سرویس). محدودیت: حذف یک شنونده نباید به باقی اثر بگذارد. تست: اشتراک/لغو اشتراک را بررسی کنید.

تمرین ۵ — API Adapter

مسئله: یک SDK خارجی با امضای متفاوت. خروجی: یک interface داخلی که مصرف‌کننده بشناسد. تست: تبدیل واحدها (مثلاً تومان به ریال) را دقیق بررسی کنید.

تمرین ۶ — Decorator برای هزینه‌ی ارسال

مسئله: ترکیب هزینه‌ی پایه + بیمه + ارسال سریع. راهنما: هر افزودنی یک Decorator باشد. تست: ترتیب پوشش‌ها نتیجه‌ی درست بدهد.

تمرین ۷ — Facade برای Order Management

مسئله: یک نقطه‌ی ورود ساده برای مراحل سفارش. محدودیت: Facade نباید منطق تجاری داشته باشد، فقط هماهنگ‌کند. تست: ترتیب مراحل با یک ترتیب‌سنج ثبت شود.

تمرین ۸ — Refactor switch بزرگ با Strategy

مسئله: یک switch بزرگ در محاسبه‌ی تخفیف. خروجی: هر قاعده یک Strategy؛ نگاشت نوع به استراتژی در یک map. تست: با @ParameterizedTest همه‌ی حالت‌ها.

تمرین ۹ — Singleton درست و تست

مسئله: یک پیکربندی یگانه. محدودیت: lazy + thread-safe بدون استفاده‌ی مستقیم از synchronized. راهنما: holder idiom. تست: assertSame دو نمونه.

تمرین ۱۰ — پروژه‌ی کوچک با ۳ الگو

مسئله: ترکیب Strategy + Factory + Observer در یک سناریوی ساده (مثلاً پردازش سفارش). خروجی: سه الگو با مسئولیت روشن و تست‌های جدا. راهنما: اول مسئله را بنویسید و دلیل انتخاب هر الگو را مستند کنید.

بخش ۳۳پروژه‌ی نهایی: E-Commerce Order System

یک سیستم سفارش با قابلیت‌های: ساخت سفارش، پرداخت، ارسال، اعلان، تخفیف و لاگ. ابتدا تحلیل می‌کنیم چرا هر الگو:

Order Creation   → Builder        (پارامترهای زیاد و اختیاری)
Payment          → Strategy       (چند روش پرداخت)
Shipping         → Strategy       (چند روش ارسال)
Notification     → Factory + Strategy (چند کانال)
Event Notification → Observer     (چند شنونده)
Logging          → Decorator      (افزودن لاگ بدون تغییر)

import java.util.Objects;

public record Money(long amount, String currency) {
    public Money {
        Objects.requireNonNull(currency);
    }
}

public interface PaymentStrategy { void pay(Money amount); }

public interface ShippingStrategy { Money cost(); }

public interface NotificationChannel { void send(String to, String message); }

public interface OrderObserver { void onPlaced(String orderId); }

public final class Order {
    private final String id;
    private final Money total;

    private Order(Builder builder) {
        this.id = builder.id;
        this.total = builder.total;
    }

    public static Builder builder(String id) { return new Builder(id); }

    public String id() { return id; }
    public Money total() { return total; }

    public static final class Builder {
        private final String id;
        private Money total = new Money(0, "IRR");

        private Builder(String id) { this.id = Objects.requireNonNull(id); }

        public Builder total(Money total) { this.total = total; return this; }
        public Order build() { return new Order(this); }
    }
}

public final class CheckoutService {
    private final PaymentStrategy payment;
    private final ShippingStrategy shipping;
    private final NotificationChannel notifications;

    public CheckoutService(PaymentStrategy payment, ShippingStrategy shipping,
                           NotificationChannel notifications) {
        this.payment = payment;
        this.shipping = shipping;
        this.notifications = notifications;
    }

    public Money checkout(Order order, String recipient) {
        Money grandTotal = order.total().amount() == 0
                ? shipping.cost()
                : new Money(order.total().amount() + shipping.cost().amount(), order.total().currency());
        payment.pay(grandTotal);
        notifications.send(recipient, "Order " + order.id() + " confirmed");
        return grandTotal;
    }
}

import static org.junit.jupiter.api.Assertions.*;
import org.junit.jupiter.api.Test;

class CheckoutServiceTest {

    @Test
    void shouldPayGrandTotalAndNotify() {
        // Arrange
        StringBuilder paid = new StringBuilder();
        StringBuilder notified = new StringBuilder();
        CheckoutService service = new CheckoutService(
                amount -> paid.append(amount.amount()),
                () -> new Money(20_000, "IRR"),
                (to, message) -> notified.append(to));
        Order order = Order.builder("O-1")
                .total(new Money(100_000, "IRR"))
                .build();

        // Act
        Money total = service.checkout(order, "ali@mail.com");

        // Assert
        assertEquals(120_000, total.amount());
        assertEquals("120000", paid.toString());
        assertEquals("ali@mail.com", notified.toString());
    }
}

بخش ۳۴Performance، پیچیدگی و Clean Code

الگوها الزاماً Performance را بهتر نمی‌کنند. بسته به پیاده‌سازی ممکن است:

  • شیءهای بیشتری بسازند (مثلاً Builder یا Decorator).
  • یک لایه غیرمستقیم (indirection) اضافه کنند و تعداد فراخوانی متدها را بالا ببرند.
  • مصرف حافظه را کمی افزایش دهند.

پس هر الگو را از چند زاویه بسنجید:

۳۴.۱ الگو در کنار Clean Code

الگو به تنهایی Clean Code نمی‌سازد. ممکن است یک الگو کاملاً صحیح پیاده شده باشد اما:

  • نام‌گذاری بد باشد.
  • کلاس‌ها بیش از حد بزرگ باشند.
  • abstraction بی‌دلیل باشد.
  • وابستگی‌ها اشتباه جهت‌دهی شده باشند.

پس الگو باید در کنار این‌ها بنشیند: Clean Code · SOLID · Separation of Concerns · Dependency Injection · Testing · Refactoring.

بخش ۳۶بیست سؤال مصاحبه

۳۶.۱ مقدماتی

  1. Design Pattern چیست؟ راه‌حلی توصیفی برای مسائل طراحی تکرارشونده؛ کد نیست، ساختار است.
  2. چرا از الگو استفاده می‌کنیم؟ کاهش وابستگی، افزایش تست‌پذیری و قابلیت تغییر.
  3. سه دسته‌ی اصلی GoF چیست؟ Creational، Structural، Behavioral.
  4. آیا الگو همیشه لازم است؟ نه؛ فقط وقتی مسئله‌ی واقعی و تکرارشونده باشد.
  5. فرق الگو با فریمورک؟ الگو توصیف راه‌حل است؛ فریمورک کد قابل فراخوانی.

۳۶.۲ متوسط

  1. Factory و Builder چه تفاوتی دارند؟ Factory انتخاب نوع می‌کند؛ Builder ساخت پیچیده را قدم‌به‌قدم می‌کند.
  2. Strategy و State چه تفاوتی دارند؟ در State خودِ وضعیت انتقال بعدی را تعیین می‌کند؛ در Strategy انتخاب معمولاً بیرونی است.
  3. Adapter و Facade چه تفاوتی دارند؟ Adapter interface را تبدیل می‌کند؛ Facade آن را ساده می‌کند.
  4. Decorator و وراثت چه تفاوتی دارند؟ Decorator ترکیب رفتار را در زمان اجرا ممکن می‌کند و از انفجار کلاس جلوگیری می‌کند.
  5. Observer چه زمانی مشکل‌ساز می‌شود؟ اگر شنونده‌های جاگذاشته لغو نشوند، نشت حافظه و اطلاع‌رسانی تکراری رخ می‌دهد.
  6. تفاوت Factory Method و Abstract Factory؟ اولی یک محصول، دومی یک خانواده از محصولات هم‌راستا.
  7. چرا Builder با immutable خوب است؟ چون تا لحظه‌ی build هیچ شیء ناقصی ساخته نمی‌شود.

۳۶.۳ پیشرفته

  1. چه زمانی Pattern باعث Overengineering می‌شود؟ وقتی مسئله ساده یا یکتاست و abstraction بی‌فایده اضافه می‌کند.
  2. Pattern را از روی Code Smell چگونه تشخیص می‌دهید؟ با دنبال‌کردن محور تغییر: switch بزرگ، ساخت تکراری، وابستگی مستقیم.
  3. Patternها چگونه با SOLID ارتباط دارند؟ بیشترشان ابزار رسیدن به OCP، DIP و SRP هستند.
  4. آیا Singleton همیشه مناسب است؟ نه؛ با DI تقریباً همیشه جایگزین بهتری وجود دارد.
  5. چگونه یک Pattern را Unit Test می‌کنید؟ از طریق رفتارش با fake/injection و بررسی ترتیب و نتیجه.
  6. چرا Decorator تریجیح دارد بر ارث‌بری زیاد؟ چون ترکیب در زمان اجرا و بدون انفجار کلاس ممکن می‌شود.
  7. تفاوت Architecture و Pattern چیست؟ معماری درباره‌ی مرزهای کلی سیستم؛ الگو درباره‌ی کلاس/شیء داخل یک لایه.
  8. کجا از Strategy پرهیز می‌کنید؟ وقتی فقط یک رفتار ثابت دارید یا یک switch کوچک کافی است.

بخش ۳۷پرسش‌های متداول (FAQ)

  1. آیا Design Pattern فقط برای Java است؟ نه؛ مفهوم زبانوآزاد است و در همه‌ی زبان‌های شیءگرا معنا دارد.
  2. آیا باید همه‌ی ۲۳ الگوی GoF را یاد بگیریم؟ نه؛ الگوهای رایج (Strategy، Factory، Builder، Observer، Adapter) را عمیق یاد بگیرید.
  3. آیا الگو باعث پیچیده‌شدن کد می‌شود؟ می‌تواند؛ اگر بی‌دلیل بیاید، بله. اگر برای مسئله‌ی واقعی بیاید، کاملاً برعکس.
  4. آیا Singleton بد است؟ ذاتاً نه، اما اغلب حالت جهانی می‌سازد و تست را سخت می‌کند.
  5. آیا Factory همیشه بهتر از new است؟ نه؛ برای انتخاب نوع یا پنهان‌سازی وابستگی خوب است، نه برای هر new.
  6. آیا در پروژه‌ی کوچک الگو لازم است؟ بیشتر وقت‌ها نه؛ چند abstraction درست کافی است.
  7. آیا Design Pattern خودش معماری است؟ نه؛ در سطح پایین‌تر از معماری قرار دارد.
  8. از کجا بفهمم کدام Pattern مناسب است؟ از مسیر تصمیم: ساخت/ساختار/رفتار و سپس نگاشت نشانه به الگو.
  9. آیا الگوها Performance را بهتر می‌کنند؟ همیشه نه؛ در بعضی حالت‌ها یک لایه غیرمستقیم اضافه می‌کنند.
  10. آیا باید برای هر کلاس interface بسازم؟ نه؛ interface را وقتی بسازید که نیاز واقعی باشد.
  11. تفاوت Pattern و Algorithm؟ الگو ساختار/تعامل؛ الگوریتم گام‌های محاسبه.
  12. آیا برای اندروید لازم است؟ مفید است، اما بخشی از کار همان الگوهای عمومی است، نه یک مجموعه جدا.
  13. الگو را از کجا شروع کنم؟ از درد واقعی در کد خودتان: switch بزرگ، ساخت پیچیده، وابستگی سخت.
  14. آیا می‌توان چند الگو را ترکیب کرد؟ بله، اما با دلیل روشن و مسئولیت متمایز.
  15. آیا الگو قسمتی از Clean Architecture است؟ نه؛ ولی در خدمت آن استفاده می‌شود (مثل Repository در مرز دامنه).
