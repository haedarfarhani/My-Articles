معماری کامل Backend در Production

این مقاله‌ی پایانی سری، همه‌ی لایه‌ها را در یک معماری Production کنار هم می‌چیند: Internet → DNS → Firewall → NGINX (TLS و Load Balancing) → چند Backend → Redis و PostgreSQL — و برای هر لایه تصمیم‌های واقعی و دلایلشان را توضیح می‌دهد.

بخش ۱معماری در یک نگاه

سه قاعده‌ی حاکم ۱) هر لایه فقط با لایه‌ی مجاور حرف می‌زند. ۲) هر جزء یک مسئولیت دارد. ۳) هر جزء حساس در شبکه‌ی خصوصی است.

بخش ۲لایه‌ی ورودی و لبه

لایهمسئولیتنکته‌ی Production
DNSنگاشت دامنه به IPرکوردهای A/AAAA و CNAME؛ TTL مناسب برای Failover
Firewallمحدودکردن پورت‌هافقط 22، 80، 443 عمومی
TLSرمزنگاری و احراز هویتفقط TLSv1.2 و TLSv1.3
Load Balancingتوزیع و Health Checkالگوریتم و Passive/Active Health
Rate Limitingمحافظت از منابعبر اساس IP و مسیر
upstream app {
    least_conn; keepalive 32;
    server 10.0.0.11:8080 max_fails=3 fail_timeout=15s;
    server 10.0.0.12:8080 max_fails=3 fail_timeout=15s;
    server 10.0.0.13:8080 backup;
}
server {
    listen 443 ssl http2;
    server_name app.example.com;
    ssl_certificate     /etc/letsencrypt/live/app.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/app.example.com/privkey.pem;
    location = /health { access_log off; return 200 "ok"; }
    location / { proxy_pass http://app; }
}

سطح HAراهکار
تک سروربدون تحمل خطا
چند BackendLoad Balancer + Health Check
لبهدو NGINX با Floating IP
دادهPrimary/Replica و Backup تست‌شده
روش انتشارویژگی
Rollingبدون منابع اضافه، دو نسخه هم‌زمان
Blue-GreenRollback فوری، دو برابر منابع
Canaryریسک کنترل‌شده، نیازمند مسیریابی درصدی
Zero-Downtime پیش‌نیازها: Health Check و Readiness، Graceful Shutdown (Connection Draining)، سازگاری نسخه‌ها در دیتابیس (Expand/Contract) و امکان Rollback.

معماری Production خوب، ساده‌ترین معماری‌ای است که مسئولیت‌ها را جدا می‌کند، اجزای حساس را ایزوله نگه می‌دارد و در برابر خرابی تاب‌آور است. هیچ‌کدام از این لایه‌ها تزئینی نیستند؛ هرکدام یک محدودیت واقعی را حل می‌کنند.
